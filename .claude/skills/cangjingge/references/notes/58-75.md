## 58. 袁瑗（快手 磁力引擎）·《Agentic AIGC驱动的广告素材修复实践》
- 可读程度：全文
- 一句话主张：广告素材被拒后的修复不是"调一次大模型"，而是"理解→决策→生成→评估"的闭环系统，修复成功 = 风险消除 × 内容保真 × 时序稳定 × 复审通过。
- 关键做法：
  - 先判"可修复域"：策略型违规（如绝对化用语）可修；原则型违规（资质缺失、类目禁投）"修复无意义，直接下线"。不是所有被拒素材都值得修。
  - 风险定位到镜头/帧级（给出时间段），不是只给一个风险标签；文本按最小语义句切分并对齐时间戳。
  - 决策层做"价值排序"：用素材价值分决定"修谁"——高价值多给算力，低价值限流/延后；再按"效果×成本"选修复方法（高性价比方法优先）。
  - 路由：风险局部、边界明确 → 精准编辑；风险贯穿整段叙事 → 片段重新生成；两者都不行 → 停止或转人工。"编辑优先保护已有价值"。
  - 文案修复用 SFT + GRPO，双奖励：安全是二元信号，营销是连续信号（用 High/Low 成对比较，只学相对优劣）；冲突时"安全是锚点"（SPARC），先探索折中、再向安全侧最小幅度校准。
  - 评估体系先于迭代：评估准则分合规判断、修复完整度、边界控制（该改的改、不该改的守住最小改动）、视频可用性四类；强调"没有自动评估就没有迭代速度"。
  - 数据飞轮：线上拒审/badcase → AI 预标注 → AI 筛选（同类已够的丢弃，只留难样本）→ 低置信度转人工复核 → 进训练集。
- 反模式 / 踩过的坑：把 AIGC 当一次调用；修复后"合规≠能投好"（缺营销价值评估）；一个违规点改完又触发"次生违规"（"第一"改成"最佳"仍违规）；直接把规则文档喂模型（规模上不可行、判例无统一标准）。
- 对 ME 有用吗：中——"先判值不值得修、安全做锚点、改动要最小、编辑优先于重写"的思路可借鉴到 ME 的素材/文案修复和广告被拒处理；训练、视频编辑模型那部分大厂专属。
- 适用领域标签：业务agent案例, 验证/评测, 闭环/Loop

## 59. 裴明明（网易智企）·《从"会用 Agent"到"组织级生产力"：网易帝王蟹多 Agent 设计与实践》
- 可读程度：全文
- 一句话主张：单 Agent 只有一份上下文，做不了复杂任务；多 Agent 要成为生产力，必须补齐"角色边界、编排依赖、状态恢复、独立校验"四件事，平台管秩序，Harness 管单个 Agent 的秩序。
- 关键做法：
  - 四平面：控制面（理解/规划/调度/终止）、执行面（按任务动态装配 Worker）、能力面（Skill/工具/MCP/知识库走同一套接口）、治理面（成本、审计、安全）。
  - 任务规划落成 DAG，"任务前进由依赖决定；任务完成由证据决定"；主控只派发依赖已满足的节点，计划未确认前一律阻断派发。
  - 完成的定义只认"记录+产物"：专家自述"已完成"不算；结果清单要有 13 项硬门禁（路径、归属、摘要非空、产物真实存在、下游节点存在、状态值必须在 pending/running/completed/failed 内）。
  - 校验两层各判其责：流程层查存在性（状态、清单、字段），专家层查质量（内容合规、验收标准）；未通过就回到修订循环，设上限，达到上限后"失败品不作交付"。
  - 状态存在进程之外（每次任务一个目录，workflow.json 落盘即提交，写盘用临时文件整份替换，事件带幂等键去重），中断后"只重派未提交节点"，恢复靠取驱动租约。
  - 渐进式推进（LOOP）：每轮把"当前状态、待办、预期状态、预期产物"给全；解析不到约定的结构化输出，状态就不转移，下一轮明确指出缺失项；用它替代穷举硬编码异常（因为异常没有有限清单）。
  - 意图识别逐层出分（规则+向量 → 小模型 → LLM 兜底，0.95/0.85/0.72 分档），"识别只出候选，派发由状态机决定"；强依赖/写操作重/共享状态的倾向单 Agent。
  - 指标：人效 3–5×，任务成功率 99.5%，人工介入率 11.5%，工具/Skill 调用准确率 94.2%；经验沉淀走 EERO（执行→评估→反思→优化）回写 Skill 和评测集。
- 反模式 / 踩过的坑：输出格式漂移（status 写成"完成/finished"）；失败多发生在交接处，依赖不落结构就一路往下传；校验不独立等于自检自证；用户一句话有多种读法（"取消当前任务"可能是真取消也可能是答复）而硬编码按字面办；每个角色共用一份持续膨胀的记忆。
- 对 ME 有用吗：高——"完成以机器可读回执为证、状态落盘可恢复、校验与生产分离、未解析到约定输出就不推进"与 ME 的 Inngest 回执/人批闸思路高度一致，且不需要大规模基础设施。
- 适用领域标签：多agent协作, Harness/边界, 验证/评测

## 60. 许晓斌（阿里巴巴 研发基础设施）·《软件工程的下一步 —— 真实世界的 AI 软件交付》
- 可读程度：全文（页面文字偏少，主要是论点和表格）
- 一句话主张：软件交付的瓶颈已不是写代码（编码只占 20–30%），而是质量验证与架构复杂度控制；成熟期软件的质量问题损失是孵化期的数千上万倍，需要 10–100 倍的验证频次和更接近真实环境的验证范围。
- 关键做法：
  - 把软件工程拆成六类问题：需求与价值、复杂性、质量可信、持续演化、多人协作、经济与风险；指出孵化期和成熟期的问题不能用同一套办法。
  - 对比主流 Benchmark 的验证环境：多数只在仓库内测试，缺生产拓扑、真实流量、长时间运行、发布与恢复；"离线成功不代表线上外部依赖可用"。
  - 环境要做成"可维护的对象"（Aone Ground），验证沙箱每天创建数百万个（Open Sandbox），AI 代码评审运行过数百万真实评审任务。
  - 为 Agent 重新设计身份系统（Open AgentAuth）和发布系统（Aone Guardrail）。
  - 架构边界和长期演化仍需人来把关："当下需要架构师设定目标"；引用 SWE-Milestone：独立任务得分约 93%，连续演化只剩约 21%。
- 反模式 / 踩过的坑：5 年没改的限流代码里藏着已不可查的白名单逻辑，机器数量降低后触发线上故障——"当前用 AI 的方法对此无能为力"；测试通过但契约被破坏、用全局抑制代替精确修复。
- 对 ME 有用吗：中——"验证环境比写代码更稀缺、把测试通过当成完成会漏契约"这一判断对 ME 有启发；基础设施部分（沙箱、发布系统）是大厂专属。
- 适用领域标签：验证/评测, 开发流程, 安全/权限

## 61. 赵恒（Datus AI）·《如何构建 AI Native 的数据语义层：从 Data Agent 实践到可执行的 Semantic Runtime》
- 可读程度：全文
- 一句话主张：Agent 不会消除口径漂移，只会放大它；语义层要从"能查指标"升级成能进入推理循环的"可执行语义运行时"，由编译器证明正确性，而不是靠 prompt 提醒。
- 关键做法：
  - 让 Agent"要指标，而不是要 SQL"：指标定义（含过滤条件）写成一份 YAML，所有消费者（看板、分析师、Agent）拿到同一个数。
  - 一个"收入为什么下降"的问题 = 6–11 次工具调用，每一跳都要沿用同一份口径；指出传统语义层只覆盖第一跳（聚合），明细探索退回手写 SQL 时口径和粒度悄悄丢失。
  - 编译器规划器在编译期拒绝它无法证明安全的查询：多条关联路径时列出全部候选而不是猜；会造成行数放大（fan-out）的聚合直接拒绝并给出更细粒度的改法。
  - "指标代数"：从定义自动推导每个指标是否可加、可上卷、可重构、可归因，Agent 聚合前先问引擎。
  - 结构化错误合同：稳定错误码 + 候选名字 + 一句修正提示（四类：未知指标、扇出风险、路径歧义、值不在值域），让 Agent 修正而不是原样重试。
  - 归因当作工具：引擎计算分解、Agent 负责解释，分段结果必须对总量对账（残差 < 1e-7）；方法随指标类型选择。
  - 少量可组合的参数化指标代替几千个离散指标 + 检索；本体（对象、关系、值域）让 Agent 在写查询前能看到可走的路径。
  - 三条路径对照实验：直接写 SQL、只给指标文本、完整运行时；差别不在"能不能出数"，而在错误是否被发现（前两条的错数静默进入报告）。
- 反模式 / 踩过的坑：指标查对了但下钻丢了"排除已取消订单"的过滤；比率求平均；两张事实表同时 join 导致两边都放大；衍生指标膨胀到几千个、检索全是近义词；错误信息是 47 行堆栈导致 Agent 重试 3–5 轮；取消订单是否计入收入这类口径"是决策问题不是抽取问题"，应由人确认一次后写进定义。
- 对 ME 有用吗：中——"每个口径只定义一次、错误要可行动、对不上总量就不报"对 ME 的广告/SEO/CRM 指标口径治理有参考价值；但编译器和多语种方言支持对 ME 体量过重。
- 适用领域标签：验证/评测, 记忆/学习, Harness/边界

## 62. 赵鑫鹏（阿里云 / Mooncake 社区）·《从 Rollout 到权重同步：Mooncake 如何支撑高性能强化学习系统》
- 可读程度：全文
- 一句话主张：强化学习系统里，KV 缓存、rollout 数据、模型权重这三类数据的存放和搬运可以用统一的存储 + 传输引擎优化。
- 关键做法：
  - 存储层（管对象位置、副本、生命周期）与传输引擎（已知地址间搬运）分开。
  - rollout 数据：元数据与大块张量分离、字段就绪即可读、碎片聚合批量读写；报告对传统序列化路径的读取改善约 10–14 倍，但提醒"组件改善不等于整体吞吐同倍提升"。
  - 权重按"不可变版本 + 清单"管理，先落盘冷副本再释放内存，权重同步用直传或点对点分发。
- 反模式 / 踩过的坑：讲者自己强调数据面优化消除不了生成长尾或环境耗时；单个组件的提速倍数不能直接当成整体收益。
- 对 ME 有用吗：低——纯 GPU 集群强化学习训练基础设施，ME 没有训练，也没有这个规模。
- 适用领域标签：基础设施

## 63. 赵钰莹（极客邦科技）·《从 Agent 到自主智能：2026 AI 技术演进与 2027 趋势前瞻》
- 可读程度：全文
- 一句话主张：2026 年 AI 产业进入"价值兑现期"，技术优先级由模型能力转向稳定交付、业务验收、单位成本和人才；2027 年模型、智能体、具身智能三线并进。
- 关键做法：
  - 引用数据：89% 的受访组织已配置智能体可观测；管理 AI 支出的受访者从 63% 升到 98%；固定同一模型，只把执行框架从最小升到完整，SWE-bench 100 题首次通过率从 52.5% 升到 65.5%。
  - Gartner 预测到 2027 年底超 40% 的智能体项目可能因成本上升、价值不清或风控不足被取消——项目须绑定业务指标、接受成本与效果持续评估。
  - 人才层面强调"问题定义、工作流设计、结果验证"三种能力，以及 FDE（前线部署工程师）需求快速增长。
  - 智能体远景：保存任务状态与可编辑记忆、分层规划并持续验证、失败回退重试；"持续学习"路径是验证反馈→沉淀为记忆和 Skill→再蒸馏。
- 反模式 / 踩过的坑：只看模型调用量不看投入产出比；"部署增加不等于项目能持续运行"。
- 对 ME 有用吗：低——行业趋势综述，价值在于几条可引用的数据（执行框架比换模型影响更大、成本治理普及），没有可直接落地的机制。
- 适用领域标签：组织, 业务agent案例

## 64. 赵雨森（网易智企 CodeWave）·《Code Agent 的 Loop 工程实践》
- 可读程度：读不出（文字层为空，整本是图片幻灯片；我只看图读了约 35/74 页，未读部分不代表无内容）
- 一句话主张：做企业级应用的全自主代码生成（L4）时，用"闭环、分治、封装变化"三条原则设计 Loop：容易断裂处加反馈闭环，大环拆成小环，确定的事用脚本规则（开环）、不确定的事交给 AI 并用闭环收敛。
- 关键做法：
  - 先把需求标准化：原始需求 → 解析 → 按模块粗切 → 结构化需求（EARS 化）→ 用户确认，再做技术设计，再生成代码；按功能模块和领域拆解（"分治"）。
  - 用"工作流 + SubAgent 的任务管理器"替代单 Agent 纯自主、纯 Skill 引导、多 Agent 串通：任务独立隔离、便于注入知识、可暂停重试（断点续跑），并带依赖分析补缺失任务。
  - 封装变化原则：确定性场景（如 y=f(x)、跑脚本处理）适合开环；含 AI、有人填写、外界环境、异常的非确定性场景才用闭环；"闭环也有成本，并不一定全都要是环"。
  - 把吴恩达的三层环用在产品迭代上：基础编程 Agent 环（分钟）→ 产研测试环（小时）→ 外部用户反馈环（天）。
  - "No Data No BB"：建立覆盖各阶段的 Benchmark（需求解析、数据建模、页面还原度、e2e 用例生成等），评估策略按类型选：准确率用"评分点打分的 LLM 裁判"、页面还原用"脚本算法+AI"混合、需求文档解析用纯规则匹配。
  - 方案灵活时"小成本试错、策略可切换组合"：提示词热更新、各阶段模型可在线热切换、thinking 强度可调；后台有"接入策略管理"界面。
  - 自动化评测平台：数据集管理、自动执行（支持断点续跑）、自动测试与报告、链路追踪与告警。
- 反模式 / 踩过的坑：Agent 擅自跳过步骤；单 Agent 在 40+ 数据实体、150+ 服务端逻辑、60+ 页面的规模下丢页面细节；Skill 太多时选错或忽略关键 Skill；多 Agent 互相捧场把错误放大；测试薄弱时"心里没底"、只能感性判断。
- 对 ME 有用吗：高——"确定的用脚本规则、不确定的才上 AI 闭环""评测先于优化""策略可热切换"和 ME 的 Loop 设计问题高度同构，且不依赖大规模基础设施；注意这条只基于看图的部分页面。
- 适用领域标签：闭环/Loop, 开发流程, 验证/评测

## 65. 路香菊（爱奇艺）·《边创造，边评估，纳逗Pro剧本空间的多Agent实践》
- 可读程度：全文（页面文字偏少，多为产品截图说明）
- 一句话主张：把"评估剧本"的经验判断沉淀成专家 Agent + Skill + 证据核验，让评估可复核、可迭代；创作侧按编剧工作流串起多个 Agent。
- 关键做法：
  - 三类 Agent：主 Agent 统筹汇总、用户 Agent 反馈受众体验、专家 Agent 按维度（题材、人物、情节节奏、量化与市场）给判断；"Agent 决定谁来做，Skill 规定怎样做"。
  - Skill 能力包：触发条件、评估规则与正反例、执行步骤与输出约定；方法与样例独立版本化，用典型剧本做固定回归样本，记录调用轨迹与失败点。
  - 分工原则：专业判断交给模型，戏份统计、格式检查、引用核验交给确定性脚本。
  - 针对问题的对策：评分漂移 → 固定评分锚点与正反例、分歧回查证据；幻觉/引用错配 → 核验引用锚点，无证据结论降级或不采纳；偏好冒充专业 → 拆开事实问题、类型标准与受众偏好；成本延迟 → 按维度路由、共享解析缓存、只重评变更处。
  - 建议验证指标：专家一致性、引用有效率、改稿回归通过率、单次耗时与成本。
- 反模式 / 踩过的坑：同一稿件反复评估结论不稳；不存在的台词被当成扣分依据；个人口味压过目标受众标准；多个 Agent 重复读全文、重复评论。
- 对 ME 有用吗：中——"无证据结论降级不采纳、固定评分锚点、核验引用"可用于 ME 的审稿/评估类 agent（例如内容审核、AI 可见度判断）；创作和娱乐场景本身不相关。

- 适用领域标签：组织, 验证/评测, 开发流程

## 75. 龙进（腾讯云 CubeSandbox）·《AI Agent 执行环境的规模化难题：CubeSandbox 的解法与实践》
- 可读程度：全文（部分页只有标题，没有正文数据）
- 一句话主张：Agent 负载正在变成长周期、有状态、大规模并行，沙箱要以 MicroVM 强隔离为底座、用统一快照原语同时兑现算力弹性（快速拉起、高密度）和状态弹性（克隆、暂停唤醒、跨机迁移）。
- 关键做法：
  - 数据：单次冷启动 48 ms，50 并发下 P99 约 137 ms；单实例额外内存 < 5 MB，96 核物理机实测存活沙箱 2000+；基于快照创建 64 ms，状态回滚 82 ms。
  - 冷启动只发生一次：直接从内存/磁盘快照恢复；只读共享 + 写时复制，Agent 大部分时间在等模型，所以可以错峰超卖。
  - 像管理 Git 分支一样管理沙箱：快照、克隆、回滚三个原语，支持并行路径探索和故障秒级重置；会话空闲自动暂停释放算力。
  - 安全：沙箱内视为零信任域，API 密钥不落盘、进出流量强制管控与审计；独立内核限定爆炸半径。
  - 选型六问：安全隔离边界、单机并发长尾、长稳运行密度、集群水平扩展、快照恢复耗时、外部凭证是否明文进入沙箱。兼容 E2B，改两个环境变量即可迁移。
- 反模式 / 踩过的坑：用通用编排（K8s 多控制器对账）拉 8192 个沙箱时 etcd 成为瓶颈、冷启动被拖垮、GPU 闲置等环境；快照恢复不会重跑启动入口，外部长连接要能重连。
- 对 ME 有用吗：低——大规模沙箱基础设施；唯一值得带走的是"密钥不进执行环境内部"的安全原则。
- 适用领域标签：基础设施, 安全/权限
