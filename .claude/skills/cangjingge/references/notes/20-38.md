## 20. 崔飞飞（架构师）·《让 Agent 成为企业的生产力》
- 可读程度：全文（图片版，23 页全部看过）
- 一句话主张：把工作交给 Agent 之前要回答四件事——执行能否持续、行动有没有边界、经验能否被组织复用、业务价值能否被验证；平台沉淀能力，验证过的经验才回流成企业资产。
- 关键做法：
  - 四问：执行（任务能否持续完成）/ 治理（行动是否有明确边界）/ 沉淀 / 收益（质量、端到端用时、人工投入与总成本）。
  - 生命周期：构建制作 → 协作执行 → 验收结果 → 持续改进；底层「运行与治理」= Runtime/Sandbox、Agent Identity、AI 网关、观测与审计。页底原话：任务交付产生结果，验证后的经验回到企业资产中。
  - 进化回路：Trace 记录过程 → Code/LLM/Agent Judge 判结果 → Dataset 沉淀失败案例与专家结论 → 实验与回归验证后「逐步发布」。
  - 角色：业务负责人（定目标、验收、处理例外）/ 领域专家（维护经验、核验质量、复盘失败）/ 平台团队（Runtime、权限策略、观测、预算、发布）；并建议把经验沉淀纳入贡献评价。
  - 满帮案例的「决策大脑闭环」：感知 → 分析 → 决策 → 执行 → 验证 → 学习；自治四级 L0 建议（只给证据，人执行）/ L1 确认（Agent 生成参数，人确认）/ L2 受控自治（低风险白名单动作自动执行并验证）/ L3 闭环自治；推进原则：自治升级以权限、回滚与效果验证全部达标为前提。
  - 广告业务案例（Yeahmobi 等，投放全流程串联）：100+ 日活 Agent、130+ MCP 工具、1500+ Skill；强调客户要的是随时看清钱花在哪、每步怎么走，而不是事后报表（所以要观测+评估+实验的数据飞轮）。
- 反模式 / 踩过的坑：「假集成」——保留业务自己的编排状态机，通用底座只做运行/隔离/网关，不替代业务状态机；案例页提示故障任务状态仍在业务侧维护。
- 对 ME 有用吗：高——自治 L0–L3 + 「低风险白名单才自动、升级须满足回滚与验证」几乎就是 ME「花钱/发布要人批」的分级版本；Trace→Judge→Dataset→回归的写法也能直接当 ME 的 Check/Tune 骨架（不必上平台）。
- 适用领域标签：闭环/Loop, 安全/权限, 业务agent案例

## 21. 张凯寓（43 AI 联合创始人）·《从通用 Agent 到用户自己的工作系统：用户级 Harness 与 CLOAK 产品实践》
- 可读程度：全文（图片版，看了约 1–30、38–47 页，共约 40/48 页；31–37 页是案例画面未看）
- 一句话主张：模型变强后瓶颈移走了，Agent = Model + Harness；产品要把「用户自己的资料、方法、标准」做成独立于执行工具的资产，让用户与 Agent 在现场共同完成，而不是产品团队预先穷尽用法。
- 关键做法：
  - 数据页：生成时间 60→5 分钟（12 倍），但审核 10→30、返工 10→30，整件事总耗时仍约 100 分钟——「生成更快，整件事未必更快」。
  - Harness 五块：Context、Memory/State、Tools/MCP/Skills、Rules/Permissions、Evals/Recovery；区分系统级 Harness（执行工具）和用户级 Harness（用户自己的资产）。
  - CLOAK 的用户资产：业务知识、工作方法（Skills/流程）、规则与标准、项目记录与成果；工作区是一个文件夹树（00 当前工作 / 01 企业资料 / 02 工作方法 / 03 项目库 / 04 工具应用 / 05 业务知识 + AGENTS.md、CLAUDE.md），案例里已累积 3,870 个文件。
  - 案例（一家香氛品牌）：Agent 改图后把新图「放回原项目」供前后对比，并明确说「我没有替你做选择，也没有把它选定导出」——把决定权留给人；另有「评审交接」页，让确认与修改被下一步接住。
  - 产品原则：不能把产品尚未解决的使用成本，全部转化成对用户自觉性的要求；共享成熟方法、保留必要差异；「昨天的经验参与今天的行动，今天的反馈改变明天的工作」。
- 反模式 / 踩过的坑：产品把本可由用户决定的部分过早写死；用「+AI」只做局部提效（先问「这件事本来该长什么样」）。
- 对 ME 有用吗：中——「客户资产（VI、历史、规则）独立于执行工具、以文件工作区喂给 Agent」与 ME 的客户私有记忆/配置同构；但这是一个通用桌面产品的形态，不直接适用 ME 的多支柱闭环。
- 适用领域标签：Harness/边界, 记忆/学习, 业务agent案例

## 22. 张前园（中泰证券 大数据中心）·《用本体驯服大模型：金融跨域智能体的确定性工程》
- 可读程度：全文（文字版）
- 一句话主张：不要让模型自由碰数据；给它一个有结构的世界（本体+指标口径+血缘+权限在结构里），模型只负责翻译与转述，数值与结论由确定性引擎产出，权限是「算出来」而不是「配出来」。
- 关键做法：
  - 五个设计目标：答得对、答得全（跨域）、答得安全、答得起（规模）、答得久（演进）。
  - 分层：入口层大模型（意图识别/实体解析/路由，只做翻译）→ 语义层（唯一身份、口径、血缘、关系）→ 执行层（规则链+图查询，统一入口）→ 数据层（数据永远在库里，一条值不进图）。
  - 大模型岗位说明书：做＝语义理解、翻译、转述、假设生成与盲区提示；不做＝数据计算（指标数值一律规则引擎产出）、最终判定、权限判定、事实生成（未覆盖领域诚实拒绝）。
  - 五条公理：模型为推理而非复用；边方向即因果；推理必须成环；模型先于数据；无场景不建实体。
  - 指标矩阵：6,260 条指标语义入册；血缘一登记，归因从「全库」变成图上两跳；标签必须引用已登记的指标（否则是「口径黑户」）。
  - 权限：范围=任职关系并集、零按人特批、聚合屏障（k-匿名桶+强制上卷，给结果不给数据）、行列正交。
  - 知识是种子不是建筑：执行留痕→盲区发现→知识补录→版本进化；低置信降级、审校后升级；高频路径沉淀为 Skill。
- 反模式 / 踩过的坑：三个故事——①「高净值」同一页 PPT 出现 4.2 万 vs 2.5 万（定义没登记）；②问「创收为什么没达标」，相似度检索挑了最像的「佣金下滑」，真凶是主力产品停售（缺血缘）；③合规一问「电脑岗能看客户手机号吗」答不上（权限不在结构里）。另：6000+ 指标平铺导致上下文装不下（推理溢出）、ETF 有两个父类却按单亲假设（推理出错）。RAG「概率给不出正确性」、Text2SQL「同题异构、绕过语义层就是绕过安全边界」。
- 对 ME 有用吗：高（原则层）——「指标口径先登记再用」「模型不碰数、数值由确定性代码出」与 ME 已踩过的坑同类（例如广告按各自结果种类判、线索质量口径）；但不要照搬图数据库/本体平台这套重建设，ME 量小，一张口径表+检查即可。
- 适用领域标签：Harness/边界, 记忆/学习, 业务agent案例

## 23. 张国强（字节跳动 资深技术专家）·《从 App 到 Agent：字节跳动 Supabase 的 Agent-Native 规模化实践》
- 可读程度：只有目录（文字版只抽到目录和小标题，主体是架构图/截图，我没有逐页读图）
- 一句话主张：字节把自家 Supabase（2025.11.30 上线）从 App 后端扩展成 Agent 后端：Serverless、数据像代码一样分支/回滚、统一模型入口、沙箱、记忆库。
- 关键做法（仅来自小标题，细节未核实）：
  - Data as Git：线上分支可拉出开发、AI 生成变差时可秒级 Restore、误删时可 Time Travel 用 SQL 看历史。
  - AI Gateway：统一模型入口，解决 API Key 泄漏、多模型接口不统一、模型故障无降级、缺用户级 Token 配额/限流。
  - Sandbox 两种形态：Agent in Sandbox / Agent call Sandbox；记忆库提供身份隔离、长期记忆与混合检索。
  - 落地案例：豆包应用生成、Coze 编程（用分支做前后端并行试错、开发与生产隔离）、Trae（用 skills 一键部署上线）。

- 对 ME 有用吗：低——自研存算分离、大规模 Serverless 与 ME 无关；唯一可联想的是「让 Agent 改库前先在分支上试」，但这是我的引申，幻灯片未展开。
- 适用领域标签：基础设施

## 24. 张忻正（bilibili 技术专家）·《当代码不再稀缺：大型工程 AI 狂欢下的确定性底座》
- 可读程度：全文（文字版，有乱码字但可读）
- 一句话主张：AI 是放大器，不负责补短板；规则机器能查、结果能复现的地方交付才真的变快。用四个底座把工程规则变成 Agent 可执行的交付闭环：约束、定位、验证、度量，最终回答「这个 MR 敢不敢直接合」。
- 关键做法：
  - 约束：契约先行——改字段先改 proto，各端代码构建时生成、不许手写、CI 查兼容性与「生成代码不许手改」；本地跑和 CI 一样的检查（pre/build/test/analysis/package/pin-align），红灯越早越便宜。分层规则写进构建文件（Chrome 的 DEPS/checkdeps 例子）。
  - 定位：用构建图直接回答「改了契约会影响谁、打进哪些包、要跑哪些测试」（bazel rdeps/aquery），不靠全仓 grep 或可能过期的 RAG；构建挂了先重放失败的 action 看真实命令，而不是只看源码瞎修。
  - 验证：要能证明「用户看见了」——真浏览器 + CDP，四份证据：造的数据、接口返回、DOM、网络和 Console；失败时按证据分层判断改哪一层（后端/BFF/前端渲染）。验证要便宜：同一批研发、同一套构建集群，构建耗时 P50 下降约 46%–50%，每天构建次数约 180→360。
  - 度量/放权：「可直接合」＝契约检查过、接口测试过、开关随时能关、接口返回有数据、DOM 有标、Console 干净，缺最后一条「用户看见」就不合；机器能判证据，CODEOWNER 不用签。
  - 实验：150 个迭代需求里挑 50 个最适合 AI 的，<5 个没返工直接合进主干；能直接合的全是「出错能马上撤回」的类型（后端实验开关拨一下就关），凡涉及客户端的一个都没直接合，因为拿不出「用户看见了」的证据。
  - 六个 Agent 只留一个（Code Agent），其余砍掉或变成它的工具。
- 反模式 / 踩过的坑：规则只写在文档、靠人记靠人看；文档会过时（引用研究称 800 个项目中 82.3% 出现过文档与代码不一致）；规则会拖后腿、补丁越贴越多说不清是哪条在起作用；引用另一研究称仓库级上下文文件并未普遍提升任务成功率、推理成本平均增加 20% 以上；开 10 个 Agent 不等于快 10 倍（同一条队列排队等反馈）；「写得越快，没人敢合的代码越多」。
- 对 ME 有用吗：高——「可撤回 + 证据齐才自动放行」与 ME 的 B/C 自动、A 级要人批同向；「规则要机器可查、别只写在文档」「文档会过时、规则要定期重验」正好对 ME 的 CLAUDE.md/memory 膨胀问题敲警钟。
- 适用领域标签：验证/评测, Harness/边界, 开发流程

## 25. 彭德跃（炎融科技）·《把 KV Cache 复用从前缀扩展到任意块》
- 可读程度：部分（图片版，只看了 2–5 页/共 46 页）
- 一句话主张：RAG 等场景里文档顺序一变，前缀缓存就整体失效；ProphetKV（ICML 2026 poster）按「问题关心什么」只重算约 20% 的 token，复用文档块 KV。
- 关键做法：
  - 复用文档块 KV → 用查询注意力挑 token → 只重算被选中的 token（20% 预算恢复块间注意力）。
  - 页面给出的数字：精度保留 ≥95%（相对全量重算），16K 上下文下 prefill 加速 4.6 倍（Llama-3.1-8B / H100 实测）。
  - 讲者从存储视角算「跨块复用之后的成本账」（后半部分我没看）。
- 反模式 / 踩过的坑：前缀复用要求「内容和顺序都一致」，第一个不同的块之后全部作废；页面推算 6 个块随机排列时首块相同概率 1/6、全部相同 1/720（假设条件，非实测）。
- 对 ME 有用吗：低——这是推理引擎/存储层优化，ME 不自己跑模型。唯一可联想（我的引申，不是讲者原话）：调用 API 时把稳定内容放在提示词前部才吃得到缓存。
- 适用领域标签：基础设施

## 26. 彭超 & 韦优·《AI 驾驭之道：告别单点外挂，重塑组织系统》
- 可读程度：全文（图片版，看了 2–13 页/共 20 页；第 14–20 页未看，多为收尾与问答）
- 一句话主张：个人提效进不了组织成果，因为协作有三个断点；用 GCC（Goal/Context/Constraints）把「任务合同、可信上下文、可执行规则」做进系统，再用计划→执行→验证闭环交付，人负责定目标、裁决例外、承担发布责任。
- 关键做法：
  - 反直觉算术：编码耗时减半，整条链只省约 10%（100h→90h，示意数字，非行业均值）。
  - 三个协作断点：上下文靠人传 / 交接靠猜 / 验收靠感觉；对应留下的依据：有来源和 Owner 的项目规则、任务范围+接口契约+接收人、独立样例+真实检查+版本证据。
  - GCC：Goal（什么算完成：目标、范围、验收条件、预算与停止条件）/ Context（依据什么行动：来源、版本、权限、Owner，只取当前任务所需）/ Constraints（工具权限、检查与回退、异常升级与人工裁决）。
  - 组织 AI 能力四台阶：L1 工具使用 → L2 资产共享（换个人能接着做）→ L3 可验证交付（跨角色仍能验收）→ L4 持续优化；分水岭问题：换一个人、换一次任务，还能否稳定交付？页脚：升级依据是交付能力，Agent 数量不代表成熟度。
  - 三个高频失败模式及「先改这一件事」：只发账号→限制批量并明确下一站谁接；一句话做完整系统→切成能独立验收的小任务；靠 AI 自己证明正确→提前确认关键样例与预期结果。自动修复有预算，连续失败、高风险和不确定结果交给 Owner。
  - 四周试点：选范围记基线 → 补共同依据 → 跑通最小闭环（计划、执行、验证、失败预算、交付证据）→ 比较复盘；四项结果一起看：交付周期、评审等待、返工与缺陷、每项已验收需求成本。
- 反模式 / 踩过的坑：只发账号就期待产出；范围不断扩大、完成标准模糊；同一份错误假设被反复「自证通过」。
- 对 ME 有用吗：中——「任务合同含预算与停止条件」「自动修复有失败预算，超了就交人」可直接套到 ME 的单次动作；其余偏大团队组织改造。
- 适用领域标签：Harness/边界, 开发流程, 组织

## 27. 徐帅（传音控股 软件工程部）·《从试点到规模化：大型研发组织迈向 Agent 驱动的提效实践》
- 可读程度：全文（文字版）
- 一句话主张：单点变快不等于整体交付变快；要从按职能的局部提效，转到「完整任务牵引」：Agent 执行、人管目标与例外，并用同口径度量决定是否推广；经验必须复核评测后才进入规则。
- 关键做法：
  - 先承认现状：四个职能领域（洞察规划/设计/编码 Review/故障分析）各有局部成果（例如某 MVP 80→25 人日、39 个故障 Skill），但「横向端到端尚未拉通，整体交付未见显著改善」，且不同口径的数据「不能合并为端到端收益」。
  - 复盘一个项目的 103 个问题：需求源头 21 + 需求传递 25 + 设计遗漏 28 = 74 条（71.8%）集中在前期规格与跨职能交接，因此先补规格、统一版本、变更通知相关任务。
  - 借 Palantir 的 Data / Logic / Action 三分：共同业务对象与有效版本、判断与交接依据、受控执行与全过程回流。
  - 双流：业务交付流（计划驱动）+ 质量改进流（事件驱动：Review/测试/线上问题触发）；两流共享实体与证据。

  - 分工结论：规则引擎做确定性、高频、可枚举任务；端侧模型做轻量语义理解、分类、参数抽取；云端做复杂推理、长文本、多轮规划；用户要的是「能直接操作的界面」而不只是对话。
- 反模式 / 踩过的坑：高频轻量请求全走大模型浪费能力；纯端侧的冷启动与设备碎片化。
- 对 ME 有用吗：低——ME 没有端侧模型场景；唯一同向的是「能用确定性规则/代码解决的先不用大模型」，ME 本来就是这样做的。
- 适用领域标签：基础设施

## 35. 李佳奇·《AI 在研发组织落地的三段式路径：从人使用 AI 干活到 AI 自主交付》
- 可读程度：全文（图片版，看了 2–14、27–40 页，共约 27/46 页；中间第 15–26 页是「个人提效到组织产出」的细节未看）
- 一句话主张：AI 落地不是接入问题而是管理问题——先度量（看得清），再嵌入流程，最后有边界地让 AI 自主交付；「无法度量＝无法运营」。
- 关键做法：
  - 三个坑：①把「使用率高」当「落地成功」（使用率、出码率是过程指标，一和考核挂钩就变成优化指标本身；「考核什么，就会得到什么」）；②提效停留在个人电脑，红利在交接处蒸发；③AI 在干什么看不见（看不见用量、产出、风险）。
  - 度量两层必须一起看：使用率（有没有在用，看趋势不搞绝对值排名）+ 产出贡献率（AI 代码进主干占比、AI 参与任务占比、AI 产出被采纳保留的比例）；只看使用率会被刷，只看贡献率会逼人硬塞 AI。
  - AI 代码如何认定：工具侧打标 / 统一工具与提交规范 / 人工抽样校准；原则是「口径稳定、趋势可信，而不是逐行精确」。
  - 度量要先于推广：否则预算失控、争议无据、优化无向；建设原则：全公司统一口径、全流程贯通、一个数据账本。
  - 自主交付的四个前提：结果指标显著变化 + 过程指标优秀（高出码率/渗透率/贡献率）+ 交付流程明显变化 + 团队主动追求；缺任何一个退回人机协作。渐进路径：人审（AI 做、人审）→ 抽检（AI 做、按比例抽检）→ 自主+监控（指标监控、异常升级）。
  - 老流程是为人设计的（默契补全、人在环），换成 AI 做执行者时流程要重做：规格先行、AI 独立执行并在关键节点留痕、自动验收（测试与校验前置）、在各协作渠道里为 AI 设计角色。
  - 平台化：把本地 Claude Code、Codex 等迁到云平台托管（已接管 20000+ 研发需求），给每个需求项目配 AI 项目助手作为调度入口。
- 反模式 / 踩过的坑：把「端到端」喊成 KPI；用演示案例定预期；一步到位跳过人机协作阶段（「一次事故就整体崩塌」）；先推广后度量，补课成本远高于一开始建好仪表盘。
- 对 ME 有用吗：高——「度量产出而非动作数」「人审→抽检→自主+监控」「小样本也要先稳定口径」正好对应 ME 量小、反馈慢、要逐步放权的处境；还提醒不要把审批通过率/动作数当成功指标。
- 适用领域标签：开发流程, 验证/评测, 组织

## 36. 李俊（蚂蚁集团 CIO 技术部）·《别再给 Agent 一个「毛坯房」了：构建 Agent 拎包入住的开发环境实践》
- 可读程度：部分（文字版只抽到小标题；另按页读图看了 19–27 页/共 31 页，前半「到哪一步/Agent 住哪/五特性」只看了标题）
- 一句话主张：编码不是瓶颈，环境才是；要把环境改造成 Agent 友好的（跑得住、记得住、管得了、分得清、说得通），而且翻新、验证、协同必须同步做。
- 关键做法：
  - 五特性：跑得住（7×24 小时、安全隔离的沙箱）、记得住（计算存储分离）、管得了（多人多 Agent 共享/接管/恢复会话）、分得清（出入流量管控、身份凭证透传）、说得通（成本与效果可观测）。

  - 验证：「可验证的反馈＝AI 的能力边界」；分层验证：秒级（编译/类型检查/单测）→ 分钟级（集成/契约/浏览器自动化）→ 人工判断（业务价值/体验/伦理）；另有 5 层「验证工作流」架构（编排→执行→验证→交付→能力 CLI），验证层有「环境不匹配 vs 代码失败」的判别和 5 维度打分。
  - 协同：人通过「指挥面」指挥多环境里的 Agent，Agent 之间用共享文件交接（页底原话大意：协同靠共享文件，别把人当中间人）。
- 反模式 / 踩过的坑：本地跑 Agent 会 rm -rf 你的真实文件、合上电脑 Agent 就停、笔记本跑不了 100 个 Agent 并发、无法标准化；企业环境没有公开反馈（答案藏在内部系统、验证一次成本高）。
- 对 ME 有用吗：低——说的是蚂蚁内部云主机/沙箱环境；唯一可借的是「先把工作流改造成有机器可判的反馈」和「Agent 交接靠共享文件而不靠人转述」，ME 已经有类似做法。
- 适用领域标签：基础设施, 验证/评测

## 37. 李凯（美团 Agent 应用技术负责人）·《美团企业级 Agent 的平台化应用实践》
- 可读程度：全文（文字版）
- 一句话主张：把「逻辑 Agent」拆成配置、状态、运行引擎，共享计算（推理集群 + 短周期沙箱），身份/能力/变更通过平台治理；多 Agent 与人的协作用 Issue/Task 做控制面，人确认关键节点。
- 关键做法：
  - 手脑分离：推理集群（脑，会话外置）+ 隔离执行沙箱（手）+ 按用户/群授权挂载的持久工作空间；逻辑 Agent 数十万、日消息百万、每日 Token 数千亿；沙箱增量快照，默认集群日快照上传量 95T→17T，无缓存预取启动 3.5s→1.5s。

  - 应用等级：L0 辅助工作 / L1 流程重塑 / L2 系统自治 / L3 更大范围自主决策（长期愿景）；是否进入 L2 取决于实际流程与交付如何变化。

## 38. 李峥峰（阿里巴巴 高级研发工程师，Open Code Review 作者）·《Open Code Review：百万真实任务验证的确定性工程与 Agent 协同》
- 可读程度：全文（文字版）
- 一句话主张：把确定性的部分（定位、过滤、范围）交给工程，把动态决策留给 Agent；评审质量不能只看用户采纳，要用固定样本与客观缺陷真值衡量，并把评审范围留成可审计的 Manifest。
- 关键做法：
  - 背景：Faros AI 报告（约 22,000 开发者、4,000+ 团队）显示吞吐上去后质量发生变化；阿里内部评审工具跑了数百万真实评审任务、拦截数百万缺陷，评审建议总量同比翻倍而其中人提的减少。
  - 通用 Agent 的问题：「AI 报告已经生成，评审真的完成了吗」——用大量真实 PR 回归通用 Agent，规模放大后不可接受；先把脚本写进 Skill 收敛行为，规模化后维护与执行治理又成问题，于是做成垂直 Agent，「边界交给工程，决策留给 Agent」。
  - 专项小模型替代两类高频边界清晰的任务：评论定位（Qwen3-8B，成功率 37.35%→85.65%，耗时 3s→1s 内）和误报过滤「反思模型」（Qwen3-30B-A3B，误报拦截率 30.09%→52.63%，耗时 5s→500ms 内），训练数据来自真实线上反馈，噪声大时用少量专家和用户反馈做锚点、多模型协同标注挑可靠样本。
  - 每次评审除报告外附可追踪的 Manifest：哪些文件审完、哪些未完成及原因，让人和下游 Agent 能核对评审范围。
  - 评测：开源 AACR-Bench，80 多位资深工程师「AI 辅助 + 人工校验」交叉标注，问题覆盖率相对传统数据集提升 285%，支持 10 种语言；用固定样本与缺陷真值衡量结果，再结合执行轨迹定位原因并回归验证。
  - 自身 RSI（自我进化）：多 PR 各自评审通过、合在一起却功能冲突；风险是「实现正确≠需求正确」「AI 倾向最快方式，缺少全局观，风险堆积到未来」；所以采用人类介入的流程，合并前分层检查，任何一层出问题都要打回。
- 反模式 / 踩过的坑：「用户采纳」不再是缺陷真值——当 AI 替人处理评论后，人的行为指标与客观缺陷真值正在分离；只看通过不看覆盖范围。
- 对 ME 有用吗：高——ME 里「人批准了建议」也不等于建议对（业务结果 3–28 天后才知道），这一讲直接说明要用独立真值和固定样本去评；Manifest 的思路（记录哪些没做完）适用于 ME 每次批量动作的回执。
- 适用领域标签：验证/评测, Harness/边界, 闭环/Loop
