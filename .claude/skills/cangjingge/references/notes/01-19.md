## 1. Larry（平安集团）·《AI 组织转型实践：团队级数字工程师如何驱动数字军团协同》
- 可读程度：部分（文字层为空，仅靠图像抽读第 3–14 页，共 22 页；第 1–2、15–22 页未读）
- 一句话主张：AI 是放大器，清晰的系统放大效率、混乱的系统放大混乱，所以先把系统、知识、责任理清，再谈组织级编排。
- 关键做法：
  - 「知识蒸馏」四步：采集（代码图谱/文档/历史变更/专家访谈）→ AI 按模板预写 → 专家纠偏 + Owner 审核入库 → 发布后增量刷新，在途需求隔离、上线后回写。基线回答「改哪里、为什么、影响谁、怎么算对」。
  - 「测试补全」：存量补网、增量定标（动代码前先出 P0 测试清单并由专家确认预期）、变更过闸、结果回流；AI 护栏写明「禁止为跑绿篡改语义」。
  - 知识是存量、上下文是按任务取出的切片，按权限、按时效切；多 Agent「隔离优先、摘要共享」。
  - 数字工程师「注册即定岗」：编号、角色、架构域、职责、负责人；每个数字工程师配一位人类负责人，日报周报向上，人定目标/做判断/最终验收。
  - 交付运营看「端到端需求承接率」，阻塞设 24h 闭环 + 超时预警 + 指派手扶人；资产运营把知识/Skill/评测集做体检、A/B 升级或淘汰。
  - 人机混编小队约 5 人 + 数字工程师；人保留目标、合规风控、授权与最终判断。
- 反模式 / 踩过的坑：经验停留在个人、知识隐性、依赖交错时，AI 只会把混乱放大；规模化不是先上工具而是先把职责与验证依据显化。
- 对 ME 有用吗：低 — 讲的是几百人研发组织的编排；唯一可借的是「每个 agent 配一个人类负责人、注册即定岗」这个小点，ME 的 agent 本来就少。
- 适用领域标签：组织, 多agent协作, 开发流程

## 2. casa（前天猫/饿了么/得物，现独立开发）·《AI 时代的一人公司：从 Idea 到 Growth 的完整工作流》
- 可读程度：全文（第 20 页后「五个坑」一页文字层缺字严重，只读到标题级信息）
- 一句话主张：一人公司里人只做三件事——定做什么、画边界、对结果负责；AI 出候选并交回可查证据，已验证的重复步骤固化成命令。
- 关键做法：
  - 五阶段（Idea→设计→实现→验收→发布增长），每阶段都要有「依据」收尾：需求证据、含异常态的 Demo、真实链路、验收记录、经营反馈回到下一轮 Idea。
  - 需求验证：先发一条「产品设想帖」（标注尚未上线）看回复内容而非点赞数；「想试」继续追问，「不错」不算需求；停止线与继续线事前定好。
  - 给 AI 的任务单用 GCCD（目标/上下文/约束/完成条件）：例子里把「刷新丢任务」写成可验收的五类场景，输出格式固定为「操作→实际观察→结论」，未执行必须标「未验证」，不许猜通过。
  - 实现上只留减少返工的东西：AGENTS.md、Makefile 固化命令、独立任务并行、整合时避免多个 agent 同写一处。
  - 增长用「靶向」：每天/每周设目标，建行动也设停止线；「动作数量不能替代效果」。
  - 验收强调：守住数据边界、重复操作不重复扣费、失败原因与可重试。
- 反模式 / 踩过的坑：只信直觉、只画成功态、一句模糊任务、只跑通一次、只顾发帖（原页五个坑，大意如此）；热度≠需求，AI 汇总后要回原帖核对。
- 对 ME 有用吗：中 — GCCD 任务单 + 「未执行不许写通过」+「先发小实验再决定继续/停」与 ME 的小量、慢反馈、人批的节奏契合；但整体是产品冷启动，不是营销 agent 设计。
- 适用领域标签：开发流程, 验证/评测, 闭环/Loop

## 3. 于思（字节跳动）·《AI 驱动复杂业务漏洞挖掘：从业务规则建模到攻击路径验证》
- 可读程度：全文
- 一句话主张：业务漏洞要先理解业务规则，AI 负责推理和设计实验，确定性的执行交给程序，结论必须有黑盒证据。
- 关键做法：
  - 先让 AI 交叉读 PRD、技术方案、代码、接口，生成「接口画像」（使用角色、输入对象、预期权限），再按功能/角色圈出候选接口。
  - 四组差分实验：D 正常业务、A 保护基线、B 只加待测变化、C 撤销变化对照复验；靠 A/B/C 对比判定限制是否失效。
  - 把日常工具和数据（账号、物料、代理、日志）封装成 Skill，AI 按任务加载。
  - 「AI 负责推理，程序负责确定性执行」：参数装配、发包、字段解析、证据保存固定为脚本；已验证的操作按资产沉淀，下次先读取再复用。
  - 攻防经验单独维护成知识库，AI 按场景读取，更新经验不用改 Harness/Workflow。
  - 实验失败时 AI 先查日志和代码补齐前置条件，保持实验变量不变再重跑。
- 反模式 / 踩过的坑：白盒只能指出疑点，不能当结论；基础设施（账号、物料、代理）决定能验证多少场景，不是模型。
- 对 ME 有用吗：低 — 安全测试领域；可借「对照组实验设计（基线/待测/撤销复验）」思路，但 ME 流量小、无法跑这种密集实验。
- 适用领域标签：验证/评测, Harness/边界, 安全/权限

## 4. 亓隆基（货拉拉）·《AI Agent 如何进入货拉拉实时交易系统》
- 可读程度：部分（文字层为空，图像抽读第 3–10、34–42 页，共 42 页；中间 11–33 页三个业务案例细节未读）
- 一句话主张：用 Agent「拓展系统能力边界」而不是重做已有能力；模型决定起点，Harness 决定下限，Dual Loop 决定方向，业务知识决定上限。
- 关键做法：
  - 起手先问三件事：新增了什么以前做不到的能力？有没有带来新的业务结果？收益是否覆盖复杂度与成本？不用 Agent 能解决的先问「为什么还要 Agent」。
  - Harness 三次演进：模型自主规划 → 工作流 + 状态机 → 「高代码」Harness（用代码编排 LLM 节点和状态机）。结构的第一价值是让业务过程可度量，过程可度量策略才能被优化。
  - Dual Loop：内环是 Agent 能力（意图识别、指令遵循、Badcase 率），外环是业务指标（触达率、配对率、ROI、效率）。页面案例：内环指标持续升、外环触达率持续降，根因是圈选司机时没选中高意向的人——只有外环能发现。
  - 用 LLM 加速闭环：LLM-as-a-Judge 规模化评测 → Badcase 分布 → 优化；「金牌话术萃取」把已验证有效的打法回灌策略。原话大意：Judge 不是终审，人工抽检校准它，业务指标验收它。
  - 业务知识按确定性分流：确定的进代码、「什么是好」进评测指标、「有效打法」进策略（不是都塞 Prompt）。
  - AI 运营线：业务动作一律走标准 Tool，带参数校验、权限、幂等、审计和人工审批；人定目标、边界、授权，Agent 在授权范围内执行。
  - 页面汇总数字：意图识别 99%、选车正确 93%、下单时长 −25%；配对率 +12%；33+ 个运营 Agent，执行效率 +80%，0 人工操作失误（自报）。
- 反模式 / 踩过的坑：只盯内环指标会在错误方向上越做越好；模型自由发挥无法遵循 SOP、过程不可度量；把知识全写进 Prompt。
- 对 ME 有用吗：高 — 「内环优化 agent、外环看业务指标」正对应 ME 的 Check/Tune；Judge 由人抽检校准、业务指标验收，以及「动作走标准 Tool + 审批」都可直接对照 ME 的人批机制。
- 适用领域标签：闭环/Loop, Harness/边界, 业务agent案例

## 5. 任卿（阿里千问办公）·《软硬一体：打造 AI 时代的工作方式》
- 可读程度：全文
- 一句话主张：模型过剩、上下文稀缺——企业级 Agent 的差距在能否把「独有的上下文」稳定喂给 AI，并把可控做成架构约束。
- 关键做法：
  - 四道门槛：①识别 GUI 行为序列（不只看 prompt）；②用业务「本体」（实体/属性/关系/动作/权限）取代线性对话；③人和 Agent 双向驱动；④按岗位自助定制（App+Tools+Skills）。
  - 判断：技能市场会随模型贬值，本体和数据才复利；把多家交付经验沉淀成一次性的行业本体。
  - 企业上下文：数据 → 结构化文件系统 → 知识图谱/本体 → Agent 调用（150PB 数据 vs 1M 窗口，所以靠检索+压缩+图谱）。
  - 主动性跃迁：从「事-人-AI」到「事-AI-人」：巡检发现异常 → 主动提醒并说明影响与依据 → 按授权处理并复查。
  - 约束执行做成三段：事前沙箱划界、事中 AI 自动审批高危动作、事后文件防误删；数据最小授权、敏感拦截、全程留痕。
  - 电商案例（自报）：跨平台经营作战台、ROI 智能盯办（按设定目标定时检查投放，出降出价/换素材等建议）。
  - 硬件（A2 / EVA 录音与桌面助手）把语音输入沉淀为上下文与「数据复利」。
- 反模式 / 踩过的坑：通用模型「聪明但不懂业务」、单点提效业务没变快、想用又不敢用、缺原料缺闭环（四个症状都归因于工程链路缺东西）。
- 对 ME 有用吗：中 — 「事-AI-人」主动发现+说明影响+授权后处理、投放定时盯办与 ME 同路；但 150PB 上下文压缩、感知硬件、私有化全栈对 ME 是大厂专属。
- 适用领域标签：业务agent案例, 安全/权限, 记忆/学习

## 6. 任磊达（腾讯）·《把 Loop 接进团队：游戏研发实践中的 Loop Engineering》
- 可读程度：全文
- 一句话主张：关键不是 prompt，而是 build loop——把人的纠错沉淀进工作流（规则/Skill/验收），让同类错下次少犯。
- 关键做法：
  - 「反馈信号流向」：常规做法是纠正流向模型厂商、工作流收不到；Build Loop 是纠正流进工作流，「纠一次沉淀一次」（思考复利）。agent 出错时问「为什么出错、下次能否不出错」，再让它从成型视角 review 工作流。
  - 注意力三模式：事前只定边界（proposal/plan.yaml），事中释放（DAG/状态机，hook 盯确定性问题），事后审查（MR + 执行记录，自动回灌 Hook/Skill）。过早 clarify 会问出很多自己也不知道的问题。
  - 四个「暴论」：不建大而全知识库（无 owner 的知识库是搜索噪音，改用就近文档，「8 层就近结构」，每模块一个有 owner 的 Skill）；不让 Agent 写单测（单测变成锁，验证留给 human in the loop，Why 写行内注释）；不给 Skill 做 Evaluation（追随厂商、仍像抽奖，改用 Loop + 错误日记）；MR 不是审批而是确保负责人对变更负责（以 Agent 名义提交、负责人自己合入、多 Agent 预审）。
  - 区分两种 Loop：面向确定性的 Loop 提高 ROI；面向不确定性的 Loop 要 fail fast、勇于重做。
  - 工作台：用状态机 + 事件 + 目录而非聊天窗；日历/tmux 插件让「长任务人离开后 loop 还在转」；管线工作台「改得越多出题越多」确保 owner 认知清晰。
  - Pass^K（每步可验收，信任是连乘）对比 Pass@K（多抽几次碰绿）。
- 反模式 / 踩过的坑：装更多插件≠有 Loop；覆盖率排行榜只是指标游戏；Skill eval 焊死某代模型可能负优化；把 MR 当审批会转嫁负担；知识库没有 owner。
- 对 ME 有用吗：高 — 「纠正进工作流而非只改一次 prompt」「注意力只放在事前定边界、事后做判断」「没有 owner 的知识库=噪音」都直接对应 ME 的人批机制与记忆设计；唯一不适用的是他们的游戏研发场景细节。
- 适用领域标签：闭环/Loop, 记忆/学习, 开发流程

## 7. 何伟（阿里 AE）·《从生码到可信交付：Harness For Hybrid Coding 实践》
- 可读程度：全文
- 一句话主张：生码变快后，用统一分层架构 + 双环 Harness（外环协调三端、内环生码自验证）+ 分阶段验证，才能让一人交付三端并保住质量。
- 关键做法：
  - 外环（主 Agent）：环境准备→需求澄清→方案规划→三端生码→独立评测→知识沉淀；内环（各端）读取共同 Spec，按计划生码并自验证，失败则定位修复后重验。
  - 状态与产物写盘：按 PLAN/EP（端内执行计划）恢复未完成任务；共同 Spec 保留业务规则、契约、验收条件。
  - 经验治理：真实反馈提炼成规则 → 候选更新经评审 → 用固定用例回测（比较覆盖、通过、重复问题、耗时、成本）→ 才应用。「产品回归验证业务变化，Harness 回测验证规则变化」。
  - 三阶段验证：研发验证（逻辑单测 + 页面场景 Journey，保留截图/UI Tree/日志）、集成验证（真实接口/账号）、发布验证（按影响面选回归，记录依据和剩余风险，异常有开关/降级/回滚）。
  - 证据判定按 UI/交互/埋点三维打分，页面里例子 9/9 场景通过、失败 0、未决 0。
  - 结果（自报）：10 个业务场域上线，需求吞吐同比 +320%，线上 Bug −80%。
- 反模式 / 踩过的坑：外环规划时漏派 iOS 端、共同规格转端内需求时漏字段（均已记录并修正）；Android 首轮只覆盖 16 个字段中的 10 个。
- 对 ME 有用吗：中 — 「规则变更要用固定用例回测、不是改完就算」和「已通过/待补/未决分别记录」值得借来管 ME 的 playbook 更新；三端移动开发、六层架构本身不相关。
- 适用领域标签：验证/评测, Harness/边界, 开发流程

## 8. 余锦泽（早稻田客座/工业智能）·《Agent 的记忆不在对话里》
- 可读程度：全文（附录细节页略读）
- 一句话主张：指标定义和表间关系不能只靠对话提炼或模型判断写进记忆，应写进「本体」，写入前用数据核对，并分「已验证/人工断言/候选」。
- 关键做法：
  - 流程：大模型只「提出候选」→ 程序用数据校验，给出已验证或候选 → 业务人员确认/否决/修改并填写理由；全过程记录来源、版本、检查条件。
  - 证据分级：模型不能把自己提的候选标成「已验证」；人工确认时状态不变，确认记录另存；人工审核结果和程序校验结果分别记录、互不覆盖。
  - 关系的四项校验（以包含率、唯一性、名称依据、引用方向）：默认包含率阈值 60%，20%–60% 通常记为候选，低于 20% 不保留。
  - 两类检查互补：数据校验拦「名称合理但取值不符」，语义复核拦「取值相符但业务无关」；对抗测试里数据校验拦下 6/6，纯语义复核 0/6。
  - 回答时按问句组装本体子图，SQL 执行前做约束校验（只读、白名单表、扇形陷阱检查、问句与 SQL 意图核对），答案旁附「计算规则卡」。
  - 反馈回路：答案卡「待改进」→ 评审队列 → 人工否决即时传到下游并作为下轮反例；高频使用却仍是候选的优先补证据。
  - 效果（自报，小样本）：只补实体与关系 8 题答对 2；加指标定义与校验答对 6；真实平台 487 条已验证关系，盲评抽查 60 条中 59 条为真；人工审核量减少约七成。
- 反模式 / 踩过的坑：记忆框架（Mem0/Zep/Letta 等）由模型判断新增/更新/冲突，错误关系写入后会被反复使用；「记忆投毒」是已知风险，企业里甚至不需要攻击者，一条错的连接就够；记忆提供给 agent ≠ 被使用（带语义工具的 agent 只有约三分之一的题调用了）。
- 对 ME 有用吗：高 — ME 的「学习挂 memory 哪一层」「哪些结论升级为行业经验」正需要「候选/已验证/人工断言」分级和「模型不能自己升级状态」；唯一不适用的是 SQL/数仓具体校验。
- 适用领域标签：记忆/学习, 验证/评测, 安全/权限

## 9. 俞昊晟（Cherry Studio）·《从通用 Agent 到业务 Harness：画边界，而不是画路径》
- 可读程度：全文

## 18. 唐飞虎（Kimi）·《现代高速开源治理的 AI Native 实践》
- 可读程度：全文（第 17–19 页之外的社区健康度、许可证细节页略读）
- 一句话主张：治理 Agent（Mira）把内部 Agent Harness 的上下文/工具/权限/观测四项底座迁到开源社区；速度和安全要兼得，靠渐进式授权、人机协同审批和全链路审计。
- 关键做法：
  - 渐进式授权四级：L0 只读诊断（不写任何内容）→ L1 建议模式（草稿，人点击才发）→ L2 低风险自动（打标签、关重复 Issue、CLA 校验等可回滚动作，事后审计抽查、一键回滚）→ L3 高风险人审（合并、发版、权限变更，Mira 只给证据，维护者批准，关键动作双人复核）。
  - 升级条件：同一动作类型准确率连续达标才开放更高权限；降级：一次误判自动降级，全量复盘后才能重新申请。分级不是静态配置，随准确率与社区反馈动态调整。
  - 所有写操作必须经权限网关：鉴权、分级、审批、留痕；审批动作本身也写审计日志（谁批的、依据、当时的证据）。
  - 全链路审计可回放：用当时的完整上下文重放任意动作，每个自动动作带申诉入口，人类可随时翻盘。
  - 核心观点（引自他人文章）：Review 是事件，信任是状态；机器承担「读」，人保留「控制与信任」。
  - 效果（页面自报，带星号）：Issue 首次响应 21 天→4 分钟，PR 审查周期 6 天→8 小时，维护者治理工时 20→6 小时/周。
- 反模式 / 踩过的坑：「低质量 PR 自动关闭」被提到 L2 自动级，结果学生的第一个 PR（描述不规范但代码成立）被秒关，社区公开质疑，新贡献者 PR 量下滑，信任修复花了三个月。修正为三条红线：「关闭/拒绝」类动作一律回到 L3 人审（可以自动建议，不能自动拒绝）；首次贡献者保护名单（只给建议性评论）；每个自动动作附申诉入口，人 48 小时内回应。结论：自动化的边界不是技术能力，而是社区信任。
- 对 ME 有用吗：高 — L0–L3 渐进授权 + 一次误判即降级 + 「对外负面动作永不自动」，与 ME 对客户/对外动作的人批规则几乎一一对应，可直接拿来写 ME 的动作分级表；审计可回放也对应 ME 的回执要求。
- 适用领域标签：安全/权限, Harness/边界, 业务agent案例

## 19. 孙鹏（阿里千问）·《重塑大模型评价体系，构建全自动、可进化的「探测式」评测管线》（页面标题：Read, Don't Write；方法名 BoRP）
- 可读程度：全文（后半评测数据与消融页略读）
- 一句话主张：对话满意度不要让大模型「生成评语和分数」，而是给两个正负提示，读取模型最后一层隐藏状态的差值向量，再用轻量回归预测评分，成本低且与人工对齐更好。
- 关键做法：
  - 先写 Rubric（评分契约：维度 + 1–5 分档边界 + 可观察信号），冷启动时先从无标注流量里挖两端案例（BlindProbing + 极化指数 PI），再让 Teacher LLM 从高/低案例归纳多个 Rubric 草案，业务人员融合补充。
  - 评分映射：约 700 条会话由专家按 Rubric 标 1–5 分（标注者一致性 K-α > 0.90），用 PLS 回归学习隐藏表征→人工分；逆密度采样补尾部。
  - 成本手段：不解码、共享前缀 KV Cache、长会话 middle-out 压缩、按模型规模选量化；用中间层与末层分歧筛出高风险样本。
  - 结果（自报）：Qwen3-4B 的 BoRP 与 Qwen3-Max 生成式评判相近（K-α 约 0.73），明显优于专用微调评判（0.49）。
  - 对比发现：同一模型换评分输出协议（先理由后分数/先分数后理由/只给分数）效果会变，生成式评判不稳。
- 反模式 / 踩过的坑：LUI（对话界面）时代轮次、对话时长无法证明满意（聊得久可能是问题没解决）；通用 LLM Judge 有中心化倾向和提示词敏感；人工评估质量高但成本高吞吐低。
- 对 ME 有用吗：低 — 需要访问模型隐藏状态、大规模标注与训练回归器，ME 不自训模型也无流量；只有「先写显式 Rubric、用两端案例归纳标准、人工小样本校准」这点理念可轻借。
- 适用领域标签：验证/评测, 基础设施
