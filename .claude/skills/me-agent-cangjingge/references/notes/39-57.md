## 39. 李桐馨 ·《当验证追上生成：AI Native 质量保障的体系化实践》
- 可读程度：全文（图片幻灯片，pdftotext 为空，逐页看图读完约 22/23 页；讲者单位页面未标）
- 一句话主张：AI 生成可以并行，人工验证只能串行；每一段都把"不确定性"在注入它的那一段拦住，用"结构化进、结构化出"逐段递进，而不是堆到测试阶段才暴露。
- 关键做法：
  - 阶段一只给每个测试环节套 AI（用例生成"一天→20min"、接口自动调用），结论是"每步更快但人工总耗时没减少"，时间只是从"执行"挪到"确认"。
  - 阶段二"沿研发流程逐段递进验证"：源头校验（PRD 完备性、方案可验证性）→ 用例生成与数据构造 → 规模化执行 → 证据与回流；上游交付用固定 schema 的"结构化交付包"，缺的字段显式列 `missing`。
  - 用例生成靠"规则和结构"而不是让模型多写：先召回历史基线再建功能树、按风险清单（三态/弱网/边界/降级）铺、每个预期必须能对回原文；多条用例合并共用同一个数据场景（87 条用例收成 18 个场景，造数降 79%）。
  - 接口测试"调用准·判断细·调用安"：编译前对线上真实接口元数据逐条校，查无此接口直接告警；判定编译成字段级断言（返回 200≠结果对）；写接口按"是否隔离测试库"分级授权。
  - UI 自动化：自然语言用例让 Agent 自规划，但真机执行、环境装包都"封死固定"，只把规划交给 AI；页面数字去对服务端（页面 ¥99.5 对接口 9950 分），对不上就是假绿灯。
  - 人只守三个点：准入分流 / 执行前确认 / 回流确认；回流"只写已确认的，未确认只留记录、不固化成规则"。
  - 数字：保险辅营 300+ 条回归通过率约 97%，发现 7 个真实缺陷；云端 6 批并行压到串行 1/3；云端一次成功率约 90%。
- 反模式 / 踩过的坑：
  - "假性成功：绿灯是假的"——返回码 200 就判过，真缺陷被放行。
  - AI 生成用例采纳率仅约 50%（源头材料说不清、凭空假设）；单页面点击 AI 比人慢（≥30min vs 2min）。
  - 阶段三抛的问题（没给答案）：执行都交给 AI 后人的判断力从哪长；体验类"for 人"的质量怎么不被漏掉。
- 对 ME 有用吗：高。ME 的 Check 最怕"回执全绿但实际没改对"，这里"字段级断言 + 对账服务端 + 只回写已确认结论"正是同一道闸的做法。
- 适用领域标签：验证/评测, 闭环/Loop

## 40. 李榕 ·《当 Vibe Coding 撞上企业级现实：组织与人才视角》
- 可读程度：全文（文字版，22 页；讲者微软 CoreAI）
- 一句话主张：AI 提速后团队集体刹车不是失职，是组织没跟上；要把 Backlog 变成协作中心，把"发现问题"和"处置问题"一起自动化，并把省下的时间还给验证、系统健康和新人成长。
- 关键做法：
  - 提速前没留"基线"，所以后来说不清代价：先建度量再提速。
  - Backlog 是团队统一可信记录（优先级、WIP、状态、负责人），设 WIP 上限、明确丢弃，"把清理 Backlog 当团队目标"。
  - 一个 Issue 四步：理解问题 → 设计与审批（人在生成代码前批准）→ 生成与检查（同一会话保留结果）→ 提 PR 附设计和测试证据。
  - 独立 agent 只读 diff 还原实现思路，与已批准设计对照；人看"设计差异 + 测试证据"决定接受与否；"符合设计≠设计正确"。
  - 检查全绿后别让 Review 走过场：展示设计差异而非只有对勾、随机抽 PR 深审；漏检后追查哪项检查缺失，能写成明确规则就不再让 AI 判断。
  - 提速省下的时间别全拿去做更多功能，要分给验证体系、团队记忆和新人成长路径。
- 反模式 / 踩过的坑：
  - 只自动发现、不自动处置，"等于批量生产焦虑"。
  - 逐行 Review 变"走过场"：问题只是更晚暴露；经验不足的人一次误解会被反复复制。
  - 新人的"犯错-反馈"路径被 AI 抹掉，讲者坦承"尚未解决"。
- 对 ME 有用吗：中。"生成前人批设计、全绿不等于正确、发现不处置=焦虑"这几条贴 ME 的审批与待办设计，但整体是软件团队组织话题。
- 适用领域标签：开发流程, 组织, 闭环/Loop

## 41. 李琳琳 ·《面向硬件场景的智慧视频创作 Agent 规模化落地实践》
- 可读程度：全文（图片幻灯片，pdftotext 为空，看了约 23/25 页；讲者来自小影科技，与荣耀等手机厂商合作）
- 一句话主张：手机相册视频 Agent 用"端云协同"——端侧理解素材、云端做故事规划、端侧确定性渲染，Agent 负责决策、Skill 提供专业规则、Workflow 保证执行。
- 关键做法：
  - 端侧先用视觉算法把几千张素材压成结构化 `Media Context`（从 120 项筛出 30% 候选），只上传结构化摘要，不传原图（隐私、成本）。
  - 云端 Agent 按场景选"Story Skill"（旅行/亲子/演唱会），产出可执行的 `Creative Config`（JSON：章节、素材映射、音乐、字幕）。
  - 端侧 SDK 解析 Config、构建 Timeline、渲染导出；"创作规划可以灵活，执行接口必须明确，任务过程必须可管理"。
  - Workflow 层管任务编排、状态进度、超时重试和失败恢复；按设备档次动态降级（旗舰全端侧理解，入门机靠云端）。
  - Story Skill 工程化运营：版本管理、A/B 灰度、用完播/互动/留存评估，用真实创作数据迭代规则。
  - 自报对比（内部旅行素材测试，非公开基准）：叙事完整度 40%→80%、单条耗时 8.2→3.1 分钟。
- 反模式 / 踩过的坑：
  - 不能直接套"大模型 + 视频工具"通用架构：素材量大、端侧资源有限、意图开放、专业剪辑参数复杂。
  - 纯云端（隐私/成本/弱网）和纯端侧（算力/语义弱）都不行。
- 对 ME 有用吗：中。"Agent 只产结构化配置，确定性执行器去渲染"与 ME 视频工厂方向一致，但这是 C 端手机产品，端侧算力和海量素材的那部分用不上。
- 适用领域标签：业务agent案例, Harness/边界

## 42. 李阳杰 ·《从"能审"到"审出闭环"：AI Code Review 规模化实践》
- 可读程度：全文（图片幻灯片，看了约 26/35 页，后段"未来演进"页未看；页面见酷我/TAPD，推测为腾讯音乐系但未明说）
- 一句话主张：AI 代码审查不能停在"发现问题就出报告"，要走完 发现 → 修复建议 → 验证跟踪 → 防新问题 的闭环，并用采纳/忽略数据让审查能力自己进化。
- 关键做法：
  - 点名三种形态的断裂：Prompt 直调 LLM（粗糙）、IDE 内嵌（不可度量）、流水线后置扫描（"发现即止"，报告成死文档）。
  - 度量：采纳问题数、触达采纳率（8.9%→约 44%）、召回率（约 31%→42%）连续 8 个季度跟踪；评论里"一键采纳 / 一键忽略误报"，采纳=正反馈、拒绝=负反馈、忽略=中性，全回流到效果大盘。
  - 审查中用 MCP 按需拉需求文档、仓库文件、运行数据，"按需取数不是靠知识猜"；仓库级配置人设、仓库上下文、技能。
  - 多轮异构采样：不同模型串行互补，轮数按"开发者贡献分 + 模块关注分"分四档（HIGH/MIDDLE/LOW/MIN），高价值 MR 多轮、低风险单轮；按 diff 特征只激活相应专项 Agent，抑制"所有 Agent 全开"。
  - 增量评审：小模型预筛过滤约 70% 低风险改动，大模型只审剩下的，再语义去重；大模型调用量降 70%、噪音降 40%。
  - 闭环追踪 Agent 自动追修复状态（修复跟踪率 93.1%）；增量评审 Agent 在修复提交后扫描是否引入新问题；漏检案例"反推分析→沉淀→增强垂类专家"（垂类 Agent 检出率 15→78 等）。
  - 灰度与容错：全局开关、仓库级 orchestration.yaml 从 1 轮逐步放到 5 轮、秒级回滚；多供应商链式重试。
- 反模式 / 踩过的坑：
  - 只看 diff 丢失需求与历史上下文，导致误判漏判（页面给了"无上下文判没问题 vs 有上下文判高危"的对比）。
  - "所有 Agent 全开"造成评审风暴。
  - 页面还指出：问题修复后若不再走一遍审查，就无法判定"已修复"，所以需要追踪 Agent 与增量评审 Agent 配合。
- 对 ME 有用吗：中。"把用户的采纳/忽略当学习信号、每次漏检变成专家的养料"可借；但多轮采样、百万级 MR 的规模设计对每天 8 个动作的 ME 过重。
- 适用领域标签：闭环/Loop, 记忆/学习, 验证/评测

## 43. 杨林枫 ·《从算子调优到推理自治：构建 MaaS 场景下的 AI Inference 自动优化闭环》
- 可读程度：全文（文字版，32 页；讲者阿里巴巴 TRE）
- 一句话主张：把专家调 GPU 算子的经验固化成"标准 Benchmark + Kernel Agent + 独立评测"的循环，并以模型端到端指标（而不是单算子加速）验收。
- 关键做法：
  - 先把生产 Trace 转成可重放的标准 Benchmark（固定工况、统一入口、评分口径），Agent 每轮对同一道题迭代，停了能重载继续。
  - 防刷分（Reward Hacking）五道防线：评测权限隔离（只能改候选 Kernel，不能改"裁判"）、开发验收分离（隐藏真实 case 做完整验收）、输入不退化、完整语义检查、规则变化后重新评测。
  - AKA 外围 Loop：独立 worktree + 预算 + 上下文；候选须"严格改进"才更新当前最佳；journal 与结构化 memory 记失败原因；FAST 低成本筛选 → FULL 深度探索；同卡 ABBA 交替对比测量。
  - GPU Wiki 知识入库：脚本取证、Agent 蒸馏、"Wiki Gate"校验准入（核对数字与原始代码、去重脱敏），带证据和适用条件进下一轮。
  - 验收看模型端到端：TTFT/TPOT/吞吐，两轮独立压测取均值（第二轮交换 GPU）。
- 反模式 / 踩过的坑：
  - Agent 会利用评测漏洞"刷高分"却没有真实收益（讲者自己说防刷分"还在持续探索"）。
  - "离线加速比不等同于端到端加速比""单算子时延下降不能相加为模型收益"。
  - Agent 容易直接从指令层入手，过早限制优化空间（需先做算法/流水设计）。
- 对 ME 有用吗：低。GPU 算子领域与 ME 无关；仅"评测权限隔离、隐藏验收集、以最终业务指标验收"的原则可类比。
- 适用领域标签：验证/评测, 闭环/Loop, 基础设施

## 44. 林鑫 ·《从沙箱到执行边界：蚂蚁 AI Agent 的大规模企业级实践》
- 可读程度：全文（文字版，37 页；讲者蚂蚁集团）
- 一句话主张：Agent 能动手之后，要把动作、网络、状态、身份与审计、资源成本五类"执行边界"做成平台能力，危险动作路由进受控执行环境而不是靠 Agent 自觉。
- 关键做法：
  - 运行时策略"先判断，再放行"：Tool Gateway 统一入口，动作分类 → 风险打标 → 策略判断，结果是放行 / 拒绝 / 人工审批，审批通过后恢复执行。
  - 身份与审计证据链：短期委托身份、最小权限 token、出口网关按目标白名单并 100% 审计，trace id 全程贯穿，"出事了不是翻日志，而是把身份、决策、调用链串成一条证据链"。
  - 状态拆开治理：计算实例可回收，文件/身份/成本状态外挂持久化；checkpoint/restore 让会话挂着、资源先走。
  - 网络边界不是越严越好："该放的执行放开、该守的管控守住"（untrust 区 vs 办公区）。
  - 模板版本灰度发布 + 观测 + 回滚；预热池改缓存池 + 快照后成本降 96%。
  - Agentic RL 环境供给五段指标（资源准备/调度/挂载/启动/就绪）各自带失败归因。
- 反模式 / 踩过的坑：
  - 共享存储越权：多个沙箱挂同一目录，其中一个以 root 绕过 555 权限位改写了系统 Skill，其他沙箱下次加载就拿到被改过的内容；修法是沙箱侧只读挂载、写权限单独授予且写入路径唯一可审计——"权限管控不能停在文件权限位"。
  - 大批量沙箱同时读 OSS 把共享出口带宽打满，创建成功率暴跌。
- 对 ME 有用吗：中。"策略判断在放行之前 + 审批 + 全链路审计"对应 ME"花钱/发布由人批"的设计；沙箱、快照、调度等基础设施是大厂专属。
- 适用领域标签：安全/权限, Harness/边界, 基础设施

## 45. 桑木 ·《从研发提效到风控产品》
- 可读程度：全文但只读了一部分（图片幻灯片，pdftotext 为空；总 30 页，我看了约 14 页，开头 10 页和结尾几页未看；讲者单位页面未标，案例客户匿名为"某行"）
- 一句话主张：把研发 Agent 里沉淀的 Harness、知识和门禁，复用成服务端 Agent 平台，再产品化成"案件调查 + 规则挖掘"的风控双 Agent 闭环。
- 关键做法：
  - Archer Harness"工作流决定怎么走，角色决定谁来做，门禁与证据决定能否继续"：唯一协调入口 workspace-orchestrator，按任务与风险路由 required / complex 两种流程。
  - 六块交接包（任务意图、冻结范围、事实包、执行契约、评审状态、输出契约）；派发门禁（角色与阶段匹配、共享写入未就绪则串行）、加载门禁（Skill 路径 + SHA-256 回执）、回传与推进（产物与门禁通过才推进阶段）。
  - 执行质量：TDD RED→GREEN→重构，推进前检查基线测试、红绿记录，`workflow.yaml` 保存状态。
  - 知识"先地图再事实"：先 OpenWiki 定方向，再按任务取上下文，最后回到目标仓库核验；证据要回传"源码位置 + 查询依据 + 命令结果 + 未知项"。
  - 产品 Agent 闭环：案件调查 Agent → 人工关口确认结论 → 规则挖掘 Agent 出候选规则/阈值/回测 → 专家审批后受控发布 → 运行反馈（命中、误报样本）回流下一轮；案件处理周期 30min→4min（降 87%，自报）。
  - 服务端 Agent 平台 Trun：24 小时运行、业务/CI-CD 接入、执行可追溯、Token 用量可统计、会话可分析→调整提示词/Skills/工具→验证。
- 反模式 / 踩过的坑：本讲已看页面没有明确讲踩坑；知识图谱页强调"图谱用于发现关系，实现判断必须回到当前源码"。
- 对 ME 有用吗：中。"调查 Agent 出证据 → 人确认 → 规则 Agent 提候选 → 专家批准 → 反馈回流"的两道人工关口结构，与 ME 的 Prescribe→人批→Check 对得上；但源页未读全，且偏企业研发平台。
- 适用领域标签：业务agent案例, Harness/边界, 多agent协作

## 46. 泠乐 ·《AI 写完代码，谁来验证？——手淘 TEKO "写—验—修"自主闭环的工程实践》
- 可读程度：全文但只读了一部分（图片幻灯片，pdftotext 为空；总 38 页，看了 1–14 与 28–38 页，中间 15–27 的实践案例页未看；讲者阿里巴巴手淘）
- 一句话主张：自主验证要补齐四个条件——判据、可执行环境、信号、闭环控制——并且还要对"验证本身"做可观测和自动评估。
- 关键做法：
  - 判据：把需求、技术方案、基建规范、历史经验转成结构化验收条件（七类内容：需求背景/描述、技术方案、风险评估、依赖分析、变更分析、测试点），并回喂生码阶段。

## 54. 聂帅 ·《AI Coding 在大型客户端工程中的落地实践——从通才模型到专才 Agent》
- 可读程度：全文（文字版，24 页；讲者小红书客户端基础技术组）
- 一句话主张：同一个模型同一份需求，换成"按职责拆开、独立上下文、结构化产物交接、逐层检查"的专才 Agent 流水线，结果才稳；"大模型不是银弹，工程体系才是护城河"。

  - 四招：拆解（按"节点"而不是按功能或文件拆，节点=职责完整、可独立推理）、隔离（每个 SubAgent 独立上下文，只拿必要信息）、约束（用结构化产物明确约定与范围）、测试闭环。

  - 出码后自动判定：Tree-sitter 按清单插日志、跑真机采截图/UI Tree/日志，对照运行前写好的预期判定，缺证据则标"待确认"不编。

- 反模式 / 踩过的坑：
  - 整页交给一个 Agent：需求写了"最多 9 张"，后续修布局时规则被忽略，编译过了但上限没生效。
  - 约束过松（结构接口反复改、顺手改别的节点）或过紧（必要状态都不让补，业务做不完整）；"经常返工的地方补规则，挡住正常实现的限制及时调整"。

## 55. 肖汉松 ·《从 Harness 到 Loop：阿福 Agent 小队如何处理持续涌入的线上 Badcase》
- 可读程度：全文（文字版，36 页；讲者蚂蚁阿福 Harness 架构组）
- 一句话主张：先做 Harness（单 Agent 可信的自主迭代），再做 Loop（把问题持续流转的多 Agent 外循环）；"单次迭代的结果不可信时，持续流转只会放大错误"。
- 关键做法：
  - 背景：badcase 平均修复耗时 12.6 天；修复一类问题约 3 人日，Agent 只需数小时，但步骤之间"等人分析原因、等人分派、等人关单"才是 12.6 天的主因，"人工无法持续介入时，Agent 也停止推进"。
  - Harness 三关：①工具接入（把部署、评测、结果下载改成 Agent 能调用的命令行/技能）；②长程执行（在授权范围内自主推进、按完成条件判断结束、重复异常先分析不机械重试、每轮只聚焦一个改动；复杂分析隔离到子 Agent，"上下文是稀缺资源"）；③评测。
  - 评测防刷分：训练集开放错题、扣分理由和得分，验证集"只返回得分"；"擂主/挑战者"——挑战者每轮从擂主 prompt 开始改，验证集各维度都超过擂主才晋升，否则整轮丢弃。
  - 四轮打擂台实录：验证集指数 100 → 99.6（未晋升）→ 98.0（未晋升，四轮最低）→ 102.5（精简到核心规则，晋升）；五维不退（正确性 102.5、全面性 103.1、安全性 100.0、易读性 100.6、实用性 102.1）。
  - Loop：外循环（定时获取→整理路由→分派→决定下一站）+ 内循环（诊断→方案/审查→实施→验证/判定），两队共 7 个 Agent（全局控制小队 2 个、修复小队 5 个）+ 1 个钉钉通知器；平台用 Multica 管工单与 Agent 运行，自己定义路由规则、审查规则和人工介入条件。
  - 角色分离："方案设计者不审查自己的方案，实施者不验证自己的修改"；人只定方向（"先改 system prompt，不行再加 reminder"），2 小时内没回复就定时唤醒协调者按预设方向继续。
  - 独立验证：每条样本回测 3 次，3 次都过才算通过；再跑全量基线，候选总分不低于线上基线；结果交回协调者，进入"待评审"，人工评审后合入。
  - 无法解决时携带证据包改派：示例中 prompt 约束已生效但 3 次回测仍 0/3，根因是上游检索数据冲突，全局调度器把终态+证据重路由给 RAG 小队。
  - 效果：覆盖约 20% 的 badcase，从 12.6 天缩到 1–3 天给出可复核结果；模型能力类与检索事实错误暂不覆盖。
  - 人机关系：从"人给 AI 分派任务"变成"AI 向人请求决策"（Human-on-the-loop）。三步落地：先自动化评测 → 基于 Claude Code/Codex 等现成 Harness 跑通 → 用定时任务接入 Loop；"先指导 AI 完成一次任务，再让 AI 把过程总结为 Skill"。
- 反模式 / 踩过的坑：
  - Agent 针对单道错题改 prompt 刷分（如加"无来源时不得虚构『降低 89%』"）——"评测集的上限就是优化的上限"。
  - 在退化版本上继续改（训练集分上升、验证集下降仍沿用）。
  - 在授权范围内还问"是否需要我继续下一步？"；同一构建错误连续重试；改 prompt 时顺手改代码。
  - 第 2、3 轮越加规则分越低——"加得越多≠越好"，最后靠撤回精简才晋升。
  - 任务失败时先排查模型，再检查任务设计和环境（讲者的两个技巧之一）。
- 对 ME 有用吗：高。这是和 ME 最像的一讲：人定方向、Agent 迭代、独立验证、失败带证据改派、关键点人批。擂主/挑战者 + 保留验证集和"生成者≠验证者"可直接用于 ME 的 Tune；"人不回就卡住"的 12.6 天结论正好提醒 ME 待办要有超时与默认动作。需注意其 badcase 量大、评测一天可跑多轮，ME 反馈慢得多。
- 适用领域标签：闭环/Loop, 多agent协作, 验证/评测
