# GitHub 检查费：改完之后大概花多少，Ray 要在网页上改什么

这份是给 Ray 看的。检查还是那些检查，只是不再每次推一下就各跑一遍。

## 以前

仓库一旦改回私人的，GitHub 会按分钟收费。审计时大约是：

| | 数字 |
|---|---|
| 每次往 PR 推一下 | 大约 24 分钟 |
| 一天大约 33 个 PR，每个推 3 次 | 大约 100 次 |
| 一个月 | 大约 7.5 万分钟，四百多美元 |

那 24 分钟里，真正干活往往只有几十秒，但每个检查单独排队、单独装一遍依赖，GitHub 不足一分钟也按一分钟算。编译和全仓类型检查是大头（大约 9 到 11 分钟）。

## 现在

| 什么时候跑 | 跑什么 | 大约几分钟 |
|---|---|---|
| PR 还是草稿 | 不跑这些检查 | 0 |
| 标成可审查，或可审查之后又推了一次 | 轻检查合成 1 次，再加 1 次把结果报上去 | 大约 3 到 6，再加 1 |
| 同一次 | 合并闸（草稿上的反复推送不跑） | 大约 1 |
| 每次 PR | 不再在 GitHub 上编译，也不再跑全仓类型检查 | 0 |

按「每个 PR 只在最后标成可审查时跑一轮」估算，一轮大约 **5 到 8 分钟**：

- 一个月大约 **5,000 到 8,000 分钟**。一天大约 33 个 PR，一个月大约 1,000 个；1,000 乘 5 到 8。
- 免费额度是个人/免费组织 **2,000 分钟**，Pro 或 Team **3,000 分钟**。所以还会超出免费额度，但比现在的 7.5 万少一个数量级。
- 超出的部分按便宜机器计价（大约普通 Linux 三分之一），大约 **10 到 20 美元**，不是四百多美元。
- 这是估算，不是 GitHub 已经跑出来的账单。装依赖如果偏慢，会靠近区间上沿。

如果 PR 标成可审查之后又连推好几次，每一推都要再跑一轮，分钟按次数往上加。想卡在免费额度里，代理的 PR 请一直保持草稿，准备好再标成可审查。

轻检查跑在 1 核的便宜机器上，单次最多 15 分钟。按现在的量应该够。如果哪次被 15 分钟掐掉，再把这一项换回普通的 2 核机器。

全仓类型检查一次就要 5 到 6 分钟。33 个 PR 都跑，光这一项就大约 6,000 分钟，免费额度装不下。网站编译本来也不看类型错误。所以上线时的编译仍由 Render 做，GitHub 不再每个 PR 编一遍。

## Ray 要在 GitHub 上做的事

1. **先改规则，再合这个改动。** 打开仓库 → Settings → Rules → Rulesets → 名叫 **Protect main** 的那条 → 必过检查里 **删掉 `Application build`**。不删的话，每个 PR 都会一直等一个不会再出现的检查，谁也合不进去。
2. **其它检查名字先别动。** 还是这些：`ai-orchestrator-tests`、`Ledger entries valid`、`Code change has ledger entry`、`Ledger refs exist`、`ops-review-loop-tests`、`Kernel architecture test`、`Tour catalog boundary test`。另外规则集 **Risk gate** 里的 `Risk gate` 也不要动。
3. **给 Actions 设一个消费上限。** 账单 / Budgets 里给 Actions 设每月 0 美元或 10 美元。到顶就停，不要再自动扣到几百美元。
4. **这个改动先别合**，等两件事：账单恢复（现在付款失败，检查根本起不来），以及你已经删掉 `Application build`。然后等这个 PR 上的检查变绿再合。这是动规则的改动，要你本人说合。

合进去之后，打开一个已经可审查的 PR，应该看到上面那些老名字。如果它们一直转圈、始终不出现，不要改别的规则；把 Protect main 的必过检查改成只留 **`Publish PR check results`**。不要改成 `Run PR checks`：草稿上这项没跑也会显示通过（跳过的任务算成功）。

## 你说「合 N」的时候

草稿不能合，而且草稿上这些检查还没跑。流程是：先把那个 PR 标成可审查，等上面的检查变绿，再合。标成可审查会自动开跑，不用你去点 Actions。

要临时看某一个 PR 的全仓类型检查和编译：Actions → **PR Application Validation** → Run workflow → 填 PR 号。这不会自动跑，也不花钱，除非你去点。
