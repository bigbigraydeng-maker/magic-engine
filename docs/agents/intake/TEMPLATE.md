## 0b. 岗位完整性检查（设计「一整根支柱的 Agent」时必填；只做单个小动作的 Agent 写「不适用：不是支柱岗位」）

> **为什么有这一节**：上面第 0 节问「它负责的一个决定或动作」，这会鼓励把岗位切成碎片——每片都合理，合起来却没人管预算、没人管效果（2026-10-21 PM 看广告 Agent 学习库时发现）。设计一个支柱的 Agent 之前，先逐项回答：这份工作里「该有的七件事」各由谁做、现在做到哪。**「缺」不是不许，是必须写出来并排队，不许假装没有。**
> 角色与做法见 `docs/agents/agent-designer.md`。

| # | 这份岗位该有的事 | 谁负责（Agent 名 / 窗口 / 「没人」） | 现在状态（有 / 薄弱 / 缺）+ 证据（文件、表、最近条数） | 最小要补什么（一句话；不是「全部重做」） |
|---|---|---|---|---|
| 1 | **目标**：这根支柱要拿到什么结果、怎么算拿到 | | | |
| 2 | **预算**：钱怎么分、上限和盈亏线在哪、谁定 | | | |
| 3 | **动作**：真正去改东西（建、改、停），以及动作的授权和撤回 | | | |
| 4 | **效果**：做完之后怎么知道有没有用（哪条带来了客人 / 结果）；量不出来怎么记 | | | |
| 5 | **学习**：外部的做法怎么变成我们验证过的规则（来源、验证、落地条数） | | | |
| 6 | **守门**：出错怎么自动停手、谁能一键停、数据过期怎么办 | | | |
| 7 | **资产**：这根支柱要用的素材 / 页面 / 受众 / 账户，谁管、怎么批准、怎么过期 | | | |

**再答三问（答不出来就不过关）：**
1. 这个设计让 PM 每天或每周看到的哪一个**决定**变好了？（说不出来 = 在加层，不是在做岗位）
2. 它依赖的上游（数据、别的 Agent）现在是不是真的有东西？（对应新问 A）
3. 上线后怎么判断「它真的被用了」？（动作记录条数、被采纳率、待办被处理率——写出数字从哪来）

## 6. 回执（每跑一次留什么）

| 项 | 填 |
|---|---|
| 落点（默认 `cron_run_logs`；会动手的另有内核 `action_runs`；需要新表 → 写理由，**先问 PM**） | |
| 运行记录用的任务名（`jobName`，写进 9-24 §4.4「叫醒登记」那一列；体检按它查） | |
| 事件叫醒的 Agent：用 `cronRunIdFromInngestRun`（`src/lib/cron/run-logger.ts`）写运行记录（确认：是 / 否 / 不适用） | |
| 处理几条 → `processed`；失败几条 → `failed_count`（**经 `finish({ failed })` 传入**） | 确认：是 / 否 |
| `summary` 统一五键：`agent`、`produced`、`undeterminable`、`reasons`、`cost_usd` | 确认：是 / 否 |
| 重跑：首次为准，不覆盖（写出怎么做到的） | |
| 需要超过 180 天的证据吗（`cron_run_logs` 180 天硬删） | |
