### 三条跳过规则（合计跳过 1,350 条）

| 跳过什么 | 条数 | 为什么不判 |
|---|---:|---|
| 没存原文的行 | 731 | AI 调用当时失败，没有原文就没有证据，改它等于凭空判断。这 731 条现在没有一条带着名次 |
| **有原文但品牌列表是空的行** | **612** | 见下，子牙复审抓出来的 |
| 手工核对为「澳洲/香港的中旅」 | 7 | 见下，魏征复审抓出来的 |

**为什么跳过那 612 条（原计划里有 203 条要改，全部剔除）**
这类行是当年解析器整条失败留下的。没有竞品列表就没有「排第几」的参照系 ——
硬补出来的名次**必然是第 1 名**，实测 203 条全部会被补成第 1 名（对照组：品牌列表正常的行里第 1 名只占 72%），
抽样核对里至少 10% 的原文中，客户前面还明明白白列着 1–6 家别的公司。
更要命的是 `brands_mentioned` 会从空数组变成**只含客户一条**，周报表的品牌排行（进月报、客户看得到）
就会在这 203 个回答里只记客户、一家竞品都不记 —— 系统性偏向客户，踩 CLAUDE.md 铁律 8「绝不凭空注入客户业务数据」。

这 612 条的正确修法是**拿存着的原文重跑一次解析器**，不是猜一个名次。另开一张单。

**顺带挖出根因（不在本次范围，要单独修）**：`supabase/migrations/20260430000003_add_parse_error_message.sql`
**从来没在生产库跑过** —— 直接 select 那一列，库里报「column does not exist」。
而 `src/lib/ai-tracker/orchestrator.ts` 在解析失败时会把这一列塞进 update，
**整条 update 因此被数据库拒掉，而那段代码没检查返回错误** —— 于是解析失败被静默吞掉。
**这个洞现在还在往下漏新数据。**

  --out <持久路径>/cts-ai-rank-plan.json --apply --confirm

安全闸：
- 只更新 `client_brand_rank` 和 `brands_mentioned` 两列；每条 UPDATE 都带 `client_id = CTS` 双保险；不删行、不插行。

**2026-04-27 那一周为什么不动**：库里存的是「1000 条回答」，但那一周实际有 1194 条。
三个原因叠在一起，只有第三个是这次要修的：
1. 当年写快照那段代码读数据没分页，而数据库接口默认最多返回 1000 行 —— **存下来的就是个被悄悄截断的数**；
2. 快照是周中写的（`created_at = 2026-04-30T06:09`），后面的回答还没跑完；
3. 名次误判（本次修复）。

→ **原样留着，单独开一张单**，连带把「读数据没分页」这个 bug 本身修掉。

**另外 6 周有回答但从来没有周报表行**（2026-05-11 / 05-25 / 06-01 / 06-08 / 08-03 / 08-10，分别只有 37 / 111 / 137 / 85 / 18 / 1 条回答），

其中 08-03 那 18 条一条原文都没有，造出来会是「提及率 0%」，而诊断收集器里有条硬规则：提及次数为 0 → **直接判 0 分**。

## 明确不改的东西（PM 与本窗口已议定）

- `diagnostic_runs` / `diagnostic_findings` / `diagnostic_narratives`：不改历史行。它们是「某天的诊断快照」，事后改写等于篡改记录。客户门户上的 AI 可见度分会在下一次诊断自然变对；PM 若要它立刻变对，就补跑一次 CTS 诊断。
- `flywheel_metrics`：不改。只增不改的时序表，改历史点会让趋势和归因失真。只在趋势上标一个「2026-09-20 口径修正」。
- 月报是每次现算的，历史行一修就自动变对。（另有一套会存档的月报表 `datasource_monthly_reports`，实查 **CTS 一行都没有**，所以这次不受影响 —— 但这是"CTS 恰好没数据"，换个客户不成立。）
- 客户门户**不直接读**这两列（`src/app/portal` 下 grep 零命中），客户能看到的只有诊断分和月报。

## 已知没修干净的地方（诚实记账）

1. **7 条「澳洲/香港的中旅」被排除在外，不代表它们现在是对的。** 判定函数认通名 `china travel service`，
   而 CTS Tours NZ 只服务新西兰。根治要给判定函数加「地域锚点」—— 那是改已上线的共享代码。
   **只在回填脚本里偷偷加一条规则不行**：线上下周再跑还会造出同类行，历史和现在就永远对不上。→ 单独开单。
2. **612 条解析失败的行仍记着「没提到」**，其中确实提到了客户的占一部分。要拿原文重跑解析器才能修。→ 单独开单。
3. **有 17 条改动会连带挪动竞品的名次**（客户插进品牌数组，后面的 rank 整体 +1）。竞品名次原本来自解析器读 AI 回答的排序，是没错的数据，现在被一个「按客户在原文里出现位置」估出来的值顶开。这是审计报告明写的已知口径局限。
4. **只靠域名认出来的有 52 条**（引了客户网址算提到，是有意口径），它们的名次同样是按 URL 在正文里的位置估的。
