## 2. 迁移单位与顺序

**单位 = 系列**（预算、学习期、受众都挂在系列/广告组上）。顺序按「风险最低、花费最小」到「最贵、最不能出错」：

**交接方法（每批通用，叫「50/50 交接」）**：
1. 官方户先建**暂停草稿**（只暂停；建完回读 targeting 三项、版位、目标、表单、预算，名字不作数）；
2. 旧的设定预算降到一半 → 读回确认 → 旧户上限随之下调 → 官方户上限上调 → 读回确认（**先降后升，顺序不能反**，见 §3.3）；
3. **PM 点名说「开」**（点名层级，方案 §8.5）→ 新的以另一半预算上线，两边并跑；
4. 并跑期按判据比较（§5）；达标 → 旧的**暂停**（不删、不归档，留作回滚）→ 新的预算补满 → 上限再调一次；
5. 旧的暂停满 7 天没出问题，再归档。
> 为什么不「新旧各开一份全额」：总上限只有 $150，现在设定合计已 $115–118，余量约 $2–5，放不下第二份。旧的本来就要退役，降到一半几乎不损失它的学习进度；代价是**并跑期这一批的总产出会少一截**（Reborn 并跑 7–14 天，粗估少 0–17 条线索，**估计值**）。

### 3.1 规则

1. 总闸看**设定的日预算**（不是实际花费），口径同上海团方案 §6.5。
2. 两户**日上限之和永远 ≤ $150**（统筹填值时已满足：120 + 30）。
3. 每次改预算/改上限**前后都读回**（§3.3）；读不全不动。
4. 阶梯假设**上海团 $30 已在官方户上线**；若上海团没上线，官方户那一栏整体减 $30，其余不变。

### 3.2 阶梯表（对齐迁移批次；已用脚本逐阶段自检：合计 ≤ 150、各户 ≤ 自己的上限、两户上限合计 ≤ 150，全部 ✅）

| 阶段 | 发生了什么 | 个人 设定 / 上限 | 官方 设定 / 上限 | 合计 |
|---|---|---|---|---|
| 0 现状 | — | 115 / 120 | 0 / 30 | 115 |
| 0b | 10/8 再营销 +20%，先把 Reborn 腾 $5（§6.6） | 118 / 120 | 0 / 30 | 118 |
| 1 | 上海团上线 | 118 / 120 | 30 / 30 | 148 |
| 2a | 批 1 交接中（ThruPlay 旧 8、新 7） | 111 / 112 | 37 / 38 | 148 |

> 合计停在 148 而不是 150，是因为 §6.5 的算法把余量留成 $2（上海团 30 + 再营销 +8 + Reborn 腾 5 之后）。上限数列在阶段 2a 之后取「设定 + 1」，两户上限合计正好 150。

### 3.3 每次调上限的读回步骤（顺序固定：先降后升）

1. **读回前**：两户在投设定预算合计、两户当前上限、客户总上限（150）；用 `launch-budget-headroom.ts` 算出本步之后的余量，**必须 ≥ 0**。
2. 改被降的那条广告预算 → **读回**：该系列设定预算 = 目标值，其他系列一分没动，状态不变。
3. **降被减户的上限**（它的设定预算已落地之后才能降，否则会判「已超自己上限」）→ 读回。
4. **升被增户的上限**（降完才升，保证两户上限合计 ≤ 150）→ 读回。
5. 官方户新系列激活（PM 点名说「开」）→ 读回三层状态与预算。
6. **读回后**：再算一次余量和两户上限合计，写进回执。上限由统筹经面板/接口改（我方窗口不碰生产库）。

## 4. 风险与回滚

| 风险 | 怎么发生 | 控制 | 每批回滚 |
|---|---|---|---|
| 学习期重置 | 旧的降 50%、新的刚起步 | 旧的本来要退役；新的前 7 天不改；改完旧户设定 7 天内不再动 | 新的暂停、旧的恢复原预算（旧的只是暂停，保留历史，**恢复后可能要重新学习，不保证回到原水平**） |
| 双投互相竞价 | 同一主页、同一批人群在两个账户同时投 | 并跑期 ≤ 14 天；比较时看频次，> 3 且点击率下降就提前收口；受众跨账户没法互相排除，只能靠预算占比控制 | 同上 |
| 官方户被限制或拒付 | 官方户陡升 + 付款卡问题 | 按批递增；每批前后读账户状态；**旧的不删、不归档，满 7 天无异常才收**；付款不稳不开下一批 | 官方户出事 → 立刻把个人户预算恢复并报 PM（付款是 PM 的事） |
| 归因/数据集断档 | 留资线索按表单问题 key 归表、不按账户；ME 取数按账户号；两户用不同像素 | 迁移前后用同一张表单，**命名沿用现有约定**；两户都已在每日取数里；留资不依赖像素 | 回滚后线索仍进同一张表 |
| 系统里指向个人户的配置没同步 | `winner_reel_sync_config` 等 | §1.6 清单，批 1 前先改 | 回滚时指回旧广告组 |
| 官方户留资跑不出来 | 接口建不了、真人建了也可能不投 | 批 2 先小额证明（样本 ≥ 25 条才判）；不行就停在批 1，个人户继续跑留资 | 批 2 失败 → 官方户新系列暂停，个人户 Reborn 恢复 $55 |
| 迁移期总产出下降 | 并跑期旧的降到一半 | 先迁小的、后迁大的；PM 可随时喊停 | — |
| 一次迁太快被 Meta 风控 | 官方户累计只花过 $610、设定预算从没到过 $100+ | 按阶梯推进，官方户日预算 $30→45→100→148 逐级 | 退回上一阶梯 |

## 5. 验收与谁做

**每批「完成」的可观察条件**（缺一不算）：①官方户新系列三层状态、预算、目标、版位、表单读回与设计一致；②并跑期判据达标（ThruPlay：`audience_network`=0；留资：样本 ≥ 25 条且成本在判据内）；③旧系列已暂停、官方户已补满、两户上限已调整，**每一步的前后读回都在回执里**；④回执（谁/改前改后/依据/时间/怎么撤回）**随同一个 PR 合进主干**；⑤**官方户「已知清单」已同步更新**（上海团方案 §8.5 第 9 条的表：新建的暂停草稿由回执覆盖、不进清单；PM 点名「开」之后转入授权清单；退役的实体划掉）——清单不更新，账户级兜底就会误报或漏报。

**必须 PM 本人点头（在执行窗口的对话里亲口说，转述不算）**：每批官方户新系列的**激活**（点名层级，方案 §8.5）· **任何预算改动**（旧的降半、新的补满）· 个人户的最终去留。日上限的改动由统筹执行，同样要 PM 知情。

**谁做**：执行窗口（广告执行）只读核对 + 建暂停草稿 + 回读；PM 点名授权；**卫青审每一批的草稿和回读**，并监督并跑期；**子牙看架构**（`is_primary` 切换、`winner_reel_sync_config` 指向、账户级上限与总上限的一致性）。本计划本身只是文档，**没有一步被执行**。
