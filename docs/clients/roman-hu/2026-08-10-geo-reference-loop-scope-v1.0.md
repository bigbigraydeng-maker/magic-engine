## 1. 为什么是 Roman

Roman 是 ME 2.0 第一条**完整走通**的参考闭环：目标 → 发现 → 分析 → 处方 → 授权 → 执行 → 验证 → 结果 → 学习。

选他不是因为他最容易，是因为他能把整条链的每一段都真正压到 —— 有真实的 AI 可见度数据在跑、有自己的域名、有真实的商业目标。**这条链跑通之后，第二个客户就是复制；跑不通，后面每一个客户都是重新发明。**

**「参考」的含义**：Roman 这一轮的目的是**验证架构**，不是最大化 Roman 的业务成效。范围窄、变更少、每一步都留证据，比"做得多"重要。

## 4. WP08 —— 基线（依赖 WP02–WP04，**不依赖 WP07**）

### 4.1 依赖关系（冻结）

```
WP02 (测量运行时契约) → WP03 (不可变存储) → WP04 (执行 + 成本/覆盖控制) → WP08 (Roman 基线)
```

**WP08 不依赖 WP07。** 基线是纯测量，不写任何页面，所以它可以在页面能力还没做完之前就跑。这一条要写死，否则整条链会被 WP07 无谓地卡住。

WP03 的 migration **apply 是单独授权的运维动作**，不夹在任何 PR 里。它是**跑真实基线的启用闸门** —— 数据总得有地方落。但它**不是** WP02–WP04 写代码或合代码的前置（见 [WP00 契约 §9.2](../../specs/2026-08-10-me2-wp00-contract-freeze-v1.0.md)）。

### 4.2 WP08 的具体产出

1. **规范业务实体**：品牌名、别名、要与竞品区分开的判据（同名异实体是 `qualified mention` 判定的主要噪声源）。
2. **经核实的自有域名 / 别名清单**：判 owned-domain 层引用只需要这一份，**不需要页面台账**（见 §4.4）。
3. **规范页面集合**（条件性）：本轮要不要固定一组受管页面。⚠️ 这一项才依赖页面身份，见 §4.4 与 §5.1。
4. **PM 批准的不可变查询集版本**：问题文本一经锁定永不可改，改就是发新版本。
5. **观测身份的取值**：引擎族 / 模型与版本 / 语言 / 市场 / **样本计划**。**全部要 PM 签字**，因为它们直接决定成本。
6. **测量计划的取值**：**节奏**（多久跑一次）、预算上限、停手规则。
   > 🔴 **节奏不是观测身份的一部分。** 观测身份是「这一次是怎么问出来的 + 怎么读出来的」（[GEO 测量契约](../../specs/2026-08-10-me2-geo-measurement-contract-v1.0.md) §3.1 采集七项 + §3.3 解释身份）；节奏是「我们打算多久问一次」，属于测量计划。把节奏混进身份里，会让「改了频率」看起来像「换了一次不可比的观测」，反过来也会让人以为只要频率一样就可比。
7. **一次基线批次**，走受治理路径，如实记录覆盖率、成本与失败。

### 4.3 为什么现有的 252 次调用不能直接当基线

四条，任何一条单独成立都足以否掉。按 [GEO 测量契约](../../specs/2026-08-10-me2-geo-measurement-contract-v1.0.md) §6.1 的三条判据分类：

| 归属判据 | 缺什么 |
|---|---|
| **① 采集身份** | **没有查询集版本** —— 现有客户级问题可以被原地改写，留不下「这次和上次问的是不是同一批」的证据 |
| **① 采集身份** | **没有任何一层 sample 概念** —— 既没有样本计划，也无法重建样本序号；语言与市场也没落在观测行上（只挂在问题上） |
| **② 解释身份** | **没有 parser 版本，也没有指标 / 归类规则版本** —— 拿不出「两侧是同一把尺子量的」这个证据 |
| **③ 质量阈值** | **14% 的错误率没有被计入分母**，客户级也没有 parser 置信度。直接用成功那批算比例会系统性高估，而且高估幅度随下次错误率变化 —— 于是「真的改善了」和「这次报错少了点」在数字上无法区分 |

**冻结：历史 252 次调用作为「趋势参考」可以看，作为基线**不可用**，也不可用于任何客户可见的成效声明。**（映射规则见 GEO 测量契约 §8。）

### 4.4 域名归属 vs 页面归属 —— 两档，别当成一档

引用类指标分两档，**门槛完全不同**：

| 档 | 需要什么 | Roman 今天能不能做 |
|---|---|---|
| **owned-domain citation**（引用落在客户自己控制的域名上） | 一份**经核实的自有域名 / 别名清单** | ✅ **可以** —— 只要 PM 确认域名与别名，WP08 就能报这一档 |
| **direct owned-page citation**（引用能对应到某一个受管页面） | **可信的页面记录或确定性规范化规则**（用来消解重定向 / 别名 / 追踪参数，并支撑页面级 lineage） | ❌ 今天不行，见 §5.1 |

**三条冻结**：

1. **域名归属可核实时，WP08 就报 owned-domain citation。** 不许因为「页面台账没有」就连这一档也不报。
2. **WP08 必须显式声明本轮要不要做页面级归属**（或要不要固定一组规范页面队列）。要做，页面身份就是 WP08 的前置；不做，就在基线里明确标注该指标**本轮不可算**。
3. 🔴 **页面台账缺失时，`direct owned-page citation` 的结论永远是「不可算」，绝不是 0。** 报 0 会被读成「一次都没被引用」—— 那是一个不同的、而且是错的事实。

## 5. WP09 激活前置（三条硬缺口）

**WP09 依赖 WP05 + WP07 + K-WP01 + K-WP02 + WP08 全部就位。** 除此之外，下面三条是 Roman 特有的、今天还不存在的东西。**三条都补齐之前，WP09 不许开工。**

### 5.1 前置一：没有规范页面身份（页面台账为空）

**现状**：Roman 名下页面台账 0 条。

**为什么卡死 WP09**：resolve 要产出**两样东西**（[Page 能力契约](../../specs/2026-08-10-me2-page-optimization-capability-v1.0.md) §3.1）：

| 产出 | 靠什么 | Roman 现状 |
|---|---|---|
| **路由决策**（这个 URL 走哪个 provider） | 已连接的 provider + 域名匹配 | ❌ 缺，但缺的原因是 §5.2（一个 provider 都没连），**不是**页面台账 |
| **规范页面身份**（这是哪一个受管页面） | 可信的页面记录，或确定性规范化规则 | ❌ 缺 |

WP09 要做的是「改这一页、并且能在 T+7/14/28 说清改的就是这一页」。**没有规范页面身份，改得出去也接不上页面级 lineage 与归因** —— 那正是这条参考闭环要证明的东西。

> ⚠️ 措辞纠正：既有的 `resolvePageUpgradeExecution(pageUrl, providers)` **本身能靠域名 / provider 匹配给出路由结果**，它不以页面台账为前提。不要把「Roman 缺台账」写成「这个解析器什么都解析不了」—— 那句话不成立。

**要补什么**：一份可信的 Roman 站点页面记录（或一套确定性的 URL 规范化规则），且要能持续更新，不是一次性人工列表。

**谁来决**：Build Control Room（是否把站点抓取列为 WP08/WP09 的前置任务，以及放在哪个 WP 里做）。

### 5.2 前置二：没有任何发布通道

**现状**：Roman 在 ME 里**一条 CMS 连接记录都没有**。

**为什么卡死 WP09**：按现有的 provider 路由逻辑（`src/lib/cms/page-upgrade-plan.ts`），**一个 provider 都没连**时会落到「只存草稿」。也就是说 **WP09 的 apply 段今天在 Roman 身上无路可走** —— 能生成 diff，但改不出去。这是「没连通道」造成的，跟 §5.1 的页面台账是两个独立缺口。

**这是本史诗与仓库现实之间最大的一条缺口。**

**要补什么**：确定 Roman 站点实际用什么发布，然后按 [Page 能力契约](../../specs/2026-08-10-me2-page-optimization-capability-v1.0.md) §6.2 的中立性规则接一个适配器。

**🔴 不假设。** 本文**不推断** Roman 的发布通道。任何 WP 在实施时凭印象填一个 provider，就是在拿客户的线上站点赌。

**谁来决**：PM 提供事实（通道 + 凭据 + 谁有权限），Build Control Room 定适配顺序。

### 5.3 前置三：没有增长 Goal

**现状**：Roman 名下 0 个 Goal。

**为什么卡死 WP09**：Kernel 在数据库层有一条**双向** CHECK —— `purpose = 'growth'` 与 `goal_id IS NOT NULL` 必须同真同假。也就是说：

- 增长动作没挂 Goal → 数据库直接拒
- 非增长动作挂了 Goal → 数据库也拒（防伪造 Goal）

这条约束是刻意的，写在数据库层就是为了让「给增长任务编一个目标」不可能。所以 **Roman 的第一个页面优化动作在有真实 Goal 之前，连提交都提交不了。**

**要补什么**：一个真实的、PM 认可的 Roman 增长目标。

**🔴 不许为了让流程跑通而编一个占位 Goal。** 仓库已经因为「强制挂 Goal」造过一个假目标（`[Migration] Unassigned Backlog`），每个查询还得把它过滤掉。不要再造第二个。

**谁来决**：PM。

## 6. WP10 —— 复测与学习

- **时点**：T+7 / T+14 / T+28，T 为干预真正生效的时刻（不是提交时刻，也不是审批时刻）。
- **同队列**：复测必须过 [GEO 测量契约](../../specs/2026-08-10-me2-geo-measurement-contract-v1.0.md) §6.1 的**三条判据** —— ① 采集身份与基线逐项一致（含样本计划）；② 解释身份一致，或两侧用同一 parser / 规则版本重跑原始回答；③ 置信度、覆盖率、失败率达标。
- **可比性闸在归因之前**：拿到 `not_comparable` 就停在闸前，不出具任何「提升 / 下降」的结论。
- **覆盖 / 成本 / 解释身份差异必须可见**，不许折叠进一个总分。**不许只升级 parser 就直接比新旧数字。**
- **学习记录**：有效与无效的方法**都要留**。只留成功案例的学习库会让系统越来越自信、越来越错。
- **学习记录不授予自主执行权。** 它是给人和给下一次推理看的证据，不是自动放大回路的输入。

## 7. 成功 / 失败语义

### 7.1 三分类（不是二分类）

| 分类 | 含义 | 判据要点 |
|---|---|---|
| **own**（可归因于我们） | 变化发生在我们干预的那一页 / 那一组问题上，且时间与干预对齐，且同队列可比 | 三条同时成立才算 |
| **defer**（还不能判） | 窗口没到 / 覆盖不足 / 队列不可比 / 证据不够 | **这是一个正当结论，不是失败** |
| **unattributable**（无法归因） | 变化确实发生了，但成因指不回我们的干预（客户自己也在动、平台改了算法、竞品动作） | 必须能说出为什么指不回去 |

**冻结：三个分类都必须能被产出。** 只有「成功 / 失败」两档的系统，会在证据不足时被迫二选一，而它总会选看起来好的那个。

### 7.2 什么算这一轮参考闭环成功

**架构层面（这才是主要目标）**：

- 从基线证据到授权、到执行、到验证、到结果、到学习记录，**lineage 每一段都能查到**，中间没有断头
- 每一次对外写入都有一条对应的授权记录，**没有任何写入绕过 Kernel**
- 停手的地方都停得干净：解析不了、快照过期、校验不过、覆盖不足 —— 都是明确的停，不是静默跳过
- 该说「判不了」的时候真的说了「判不了」

**业务层面（次要，且允许为负）**：

- Roman 的 GEO 指标在同队列下有可解释的变化 —— **变好、变差、判不了，三者都是有效结果**
- 一次诚实的「这个干预没用」比一次不可比的「提升了 30%」价值高得多，因为前者能进学习库，后者只能进 PPT

### 7.3 什么算失败

- 出现任何绕过 Kernel 的对外写入
- 出现假的审批入口 / 假的成功回执
- 用不匹配的队列宣称提升
- 变更范围超出 1–3 页
- 为了让流程跑通而编造 Goal、编造页面清单或假设发布通道
- 因为验证读不回来就再 apply 一次，或把「读不回来」写成成功
- 为了让端到端测试变绿而提前 apply 生产 migration
- 页面台账缺失时把 `direct owned-page citation` 报成 0
- 悄悄改变了 `src/lib/execution/auto-run.ts` 等既有生产行为

## 8. 节奏

> 🔴 **本节讲的是测量计划，不是观测身份。** 节奏（多久跑一次）属于计划；观测身份是「这一次怎么问出来的 + 怎么读出来的」。两者不许混（§4.2 第 6 条）。

| 阶段 | 频率 | 说明 |
|---|---|---|
| 基线 | 一次 | WP08。跑之前 PM 要签字确认引擎 / 模型 / 样本计划及其对应成本 |
| 干预 | 一次，1–3 页 | WP09 |
| 复测 | T+7 / T+14 / T+28 | WP10。三次都用与基线相同的**观测身份**；改的是时点，不是身份 |
| 常规监测节奏 | **未定** | 参考闭环跑完之后再定，不在本轮范围内 |

**成本口径**：每一次测量批次的预算上限要在跑之前定死，跑到上限就停手并如实报告部分覆盖（GEO 测量契约 §7）。**不许「先跑完再看花了多少」。**
