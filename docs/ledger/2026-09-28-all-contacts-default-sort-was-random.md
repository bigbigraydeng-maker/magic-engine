## 怎么发现的

PM 当晚测 WhatsApp，用搜索框能找到测试联系人（确认数据是对的），但在「全部客人」默认列表里翻不到——即使那条消息是当天刚发生的。

## 根因

`contacts.id` 是 **UUID**。`crm/contacts/route.ts` 的分页查询原来是 `.order('id', { ascending: true })`——按 UUID 字符串排序，等于按**随机顺序**选出第一页的 20 个人。页面上「最近联系 ↓」那个箭头只对**已经选出的这一页**做客户端排序（`page.tsx` 注释原话：「排序只对当前页生效」）——两层叠加：先随机挑 20 个人，再把这 20 个人按最近联系排一下。今天刚建档的人，只要没被随机挑中，永远上不了第一页。

CTS 库里 1026 个联系人，这不是偶发——每次打开默认视图都命中。

## 改了什么

`getPaged` 的排序列从 `id` 改成 `first_seen_at` 倒序。

**这不是完整修法，老实说清楚差在哪**：`first_seen_at` 是「第一次进线」，不是「最后一次接触」——一个很久以前进线、今天刚回消息的老客人，这次修法**不会**把他排到前面。真正对的是按跨渠道最新触点时间排序，但这份 SQL 现在的架构是「先拉一批人 → 再拉这批人的触点 → 内存里组装」（见文件头注：335 人量级下比窗口函数简单，到几千人再换物化视图），无法做到「先按最新触点排序、再分页」——那需要物化视图或者给 `contacts` 表加一个缓存列，是一次独立的设计，不在今晚顺手做。

选 `first_seen_at` 是因为它是这次查询里唯一已经在选的列里、单调、不为空的时间字段——至少能让「今天新进来的人」被看见，比随机排序好，但不是终局方案。

## 资源优先级判断（按 §11）

- **频率**：高——每次打开默认视图都命中，不是偶发
- **IMPACT 闭环关键度**：高——卡在「看见谁在说话」这一步，属于给错误信号的 Measure（该联系的人系统给你看不见）
- **收入关联度**：中——直接影响能不能及时跟进新线索

零低、两个高 → **P0**。今晚先做了「不再随机」这一半，「真正按最新接触排」记进这张卡，等专门排期。
