# 急停到底多久生效 & 策略行里的 $1 是什么（只读核实 · 2026-10-19）

回答 105 号独立复核提出的两个缺口，经 18 号转来。全部只读：读代码 + 查生产库，没改任何设置、没发任何事件。

## 一、把客户 autonomy_mode 改回 observe，策略多久变成"需人批准"

**结论：设计上是几秒到几分钟，但生产里没有任何一次是这样发生的；实际每一次都是等到每天 NZ 06:02 那轮对账才生效，最坏要按 ~24 小时算，在 Inngest 去重边界上可能到 ~48 小时。不能当急停用。**

**代码里的触发链**（`ad-strategy-config/route.ts:~135-143` → `autonomy/notify.ts` → `inngest/functions/ads-autonomy-sync.ts` → SQL 函数 `ads_sync_autonomy_policy`）：
- 设置页保存会发事件 `ads.autonomy_mode.changed`，**仅当 autonomy_mode 或日上限真的变了**。发送失败只 `console.warn`，**不影响保存、也不报错给人**
- worker：`retries: 2`；失败写一行 `sync_failed:` 回执
- 兜底：每天 `google-data-pullback-daily`（17:00Z ≈ NZ 06:00）末尾调 `reconcileAutonomyMode`，**用同一个幂等 id 重发**（`notify.ts` 注释：Inngest 24 小时内去重）
- 副作用：已签发的授权决定有效期 `decision_ttl_seconds=900`（15 分钟），已签发的"允许"在窗口内仍可被消费

**生产实测**（`ads_autonomy_sync_receipts`，共 4 批同步，每批 9 个动作键）：

| 客户 | 设置被改的时间 | 策略被同步的时间 | 滞后 |
|---|---|---|---|
| CTS | 09-26 01:42Z | 09-26 17:03Z | 15.3 小时 |
| CTS | 10-11 15:28Z | 10-11 17:02Z | 1.6 小时 |
| CTS | 10-11 21:09Z | 10-12 17:02Z | **19.9 小时** |
| NAL | 09-24 13:25Z | 09-26 17:03Z | **51.6 小时** |

**4 批全部落在 17:02–17:03Z（= 每日对账那一轮），没有一批是保存后几分钟内同步的。** 也就是说"保存即发事件"这条快路径，在生产里没有被观察到生效过。原因我没查（可能是函数没在 Inngest 里手动 Sync，仓库文档 STATE.md:174 提过新增函数上线要手动 Sync；也可能事件发送失败被吞）——**未核实，不下结论**，只陈述"4/4 走的是慢路径"。

**最坏生效时间（依据）**：
- 事件路径不工作 → 等下一次 17:00Z 对账 → **≤ 24 小时**（实测 19.9 小时）
- 事件被 Inngest 收了、但 worker 3 次都失败 → 对账重发同一个幂等 id 被 24 小时去重吞掉 → 要再等一轮 → **最坏接近 48 小时**（理论推导，没在生产见过）
- 实测最大值 51.6 小时（NAL 首次，当时可能有别的原因）

**不可接受。更快的急停办法**（都未执行，按"现有入口"列）：

## 二、策略行里的 spend_cap_per_run_usd = 1.00 是什么

**结论：它卡的是"这个动作自身这一次运行要花多少 API 成本"，不是"这个动作能改动的广告花费"。不是预算保险。**

依据：
- `kernel/registry-ads.ts` 文件头注释："广告花费**不进** Kernel 成本字段（§14 K4），这里的上界是「这一步自身会不会烧 API 钱」，全部是 0"
- 每个 ads.* 动作定义：`costModel: { kind:'fixed', estimate: () => 0, stepCeilingUsd: zeroCeilings([...]) }`——估算恒为 0
- `kernel/authorize.ts:468-496`：`costCap = policy.spend_cap_per_run_usd ?? 0`（**没写＝0，不是不限**），判据是 `costEstimate > costCap` 才拒。估算恒 0，所以 $1 与 null（CTS 的 `auto_pause_on_d3`）**效果完全相同：都不会拦任何广告动作**
- 它会写进授权决定的 `cost_cap_usd`（实查 NAL 那条决定 `cost_cap_usd=1`、`cost_estimate_usd=0`）

所以各窗口应当把它理解为"防模型调用烧钱的上限"，**不要当预算保险**。真正限制广告花费的是：信封里的变动比例 ≤20%、账户日上限（含 20% 缓冲）、客户总闸，以及这些只管 AI 自治路径、不管人按的止损（见 T6 回执）。
