# ME Tour 管理模块 · 规划（旅游行业 · L2 版本能力）

**日期**：2026-09-14
**状态**：规划草稿，**未授权实施**。等 PM 拍板后才走设计 + 双审 + 五道 Build Gate。
**触发**：CTS Golden China 路线图做完后，PM 提出——「这个功能今后旅游类客户都会复用，应该做进 ME 后台的 Tour 管理模块，每个新团在推广前统一备好内容、定价、行程、地图」。

---

## 一句话结论

把「一个旅游团在推广前要准备的东西」（**内容 / 定价 / 行程 / 地图**）收进 ME 后台的一个 **Tour 管理模块**，让 FDE / PM 在一个地方录一次，就能自动产出各渠道要用的素材（路线图是其中第一块，已做出可复用内核）。
**建议：先立项、单独做，不要和「画地图」混在一个窗口顺手做。** 这是旅游行业的一条正经能力线，第一步是**统一现有的多份团事实源**（不是新建 ME 自己的团数据库，见下面「现实地基问题」），是多步开发。

---

## 为什么要做（现在的痛点）

- 今天一个团要推广，准备工作是**散的**：行程文字在客户官网代码里、价格在邮件/表格里、地图靠人临时画、广告文案又是另一套。
- 换个团、换个客户，全部重来一遍，没有沉淀。
- 结果：慢、容易出错（货不对板：片尾写错团、地图城市画错）、无法规模化到「签一个旅游客户就能快速起量」。

一句话：**每个新团在推广前都要过同样四道准备工序，现在没有一个地方统一管，所以每次都手工重来。**

---

## 模块管什么（PM 视角）

一个「团」在 ME 后台是一条记录，录一次，下面四块自动打通：

| 块 | 录入什么 | 自动产出 |
|---|---|---|
| **行程 Itinerary** | 城市顺序、每城住几晚、城市间怎么走（飞机/高铁/大巴/游轮）、每天做什么 | 结构化行程，喂给下面三块 |
| **内容 Content** | 卖点、亮点、官网链接 | 各渠道文案（社媒/广告/邮件）、SEO 文章——**必须回官网 grounding，不编** |
| **定价 Pricing** | 不录入，读统一后的外部事实源 | 报价、落地页价格块（对外遵守消费者法「From NZD $X」写法），价格随事实源更新自动跟着变 |
| **地图 Map** | 由行程自动读 | **PC + 手机两版路线图**（今天已做出内核） |

**谁用**：FDE / PM 在 ME 后台录团 → 一键产出素材 → 客户官网 / 社媒 / 广告直接用。

---

## 层级判定（me-platform-tier-gate）

- **模块整体 = L2 旅游行业能力（ME 旅游版的一部分）**：所有**旅游类**客户通用（CTS、以后签的其他旅行社），但换成地产/电商客户用不上（他们没有「多城市+交通接驳的团」这种结构）。→ 归 L2 Playbook / ME 旅游版，不是 L1 平台通用。
- **模块内部的可复用内核**按 L1 判：
  - **行程转路线地图生成器**（今天做的）：输入结构化行程 → 输出图。这块换客户/换团都通用，是 L2 旅游版下的一个内容生成能力。已登记候选，本次已实现首例（CTS 7 个团）。
  - **官网 grounding 抓取**、**HTML→PDF 渲染**、**AI 文案生成** 等：这些是**已登记的平台候选**（见 `docs/registry/platform-candidates.md`），本模块应**复用**，不得另起。
- **红线**：客户具体的团数据（CTS 的 Golden China 城市/价格）是 **L4 客户配置**，进数据库按 client 隔离，绝不硬编码进 shared runtime。
- **红线（补，`ME_PRODUCT_DEFINITION.md` §3.2）**：团的价格/库存/出发日期是外部经营事实，ME 只能 Connect 读取 + 保存最小营销快照，不得新建一套完整的团数据库替代客户/工厂/私信 Agent 现有的事实源——详见下面「现实地基问题」一节。
- **PM 拍板项**：ME 旅游版是否正式立版（进 `docs/registry/product-versions.md`）——这是商业/产品决策，不由 agent 定。

## 现实地基问题：先统一现有事实源，不建 ME 自有第三份团数据

**红线（`ME_PRODUCT_DEFINITION.md` §3.2）**：旅游库存、正式报价、出票和预订后台明确列在「ME 不直接负责」——这些系统是各自业务事实的 Source of Truth，ME 只能通过 Connector 读取必要事实、保存「最小保存原则」（§3.3）允许的营销快照，**不得自建一套替代性的团/价格/行程数据库**。

**现状盘点（不是从零开始，已有三份互相独立、且已被记录在漂移中的团事实）**：

1. `chinatravel` 仓 `src/lib/data/tours.ts`——客户官网的团数据，散文式行程，是最接近「客户真实在售内容」的一份。
2. `factory_config.render.creatomate.offers`——视频工厂用的团/档位事实字典（见 PR #1632/#1642）。
3. `config/clients/cts/offerings.yaml`——私信回复 Agent 用的在售团配置（#1577）。

`docs/ROADMAP.md`（"上面这次发现"一条，2026-09-13）已经记录 2 和 3 是**两套独立维护、语义高度重叠、会漂移**的事实源，并建议"把其中一份定为唯一真相源，另一份改成读它、不再各自维护"——**这个统一工作本身还没做**。此外仓库里已有 `FirstPartyTour`（`src/lib/web-intelligence/first-party-tours.ts`，已经建模了 `tour_cities` / `itinerary` / `departure_dates` / `departure_pricing`，是从客户官网读取的第一方团 feed）和 `tailor_made_itineraries` 表（客户定制行程单，`payload jsonb`）。

**在这个背景下再新建 `tours` / `tour_departures` 表，会变成第四份事实源**，而不是解决问题。价格或出发日期一旦更新，各渠道（官网／视频工厂／私信 Agent／地图生成器）会继续给客户不同答案——这正是 CLAUDE.md 铁律 0「Domain Semantics Gate」要防的事。

**修正后的第一步不是"建表"，而是**：
- 先确认 `factory_config.offers` / `offerings.yaml` / `FirstPartyTour` 三者能否收敛成一个唯一事实源（或明确谁是权威源、其余改成只读它）；
- ME 侧只保存 Tour 管理模块渲染地图/文案/落地页**必需的最小快照**（城市序列、交通方式、天数——地图生成器的输入），不复制完整的价格/库存/出票状态；
- 价格、出发日期、库存这类会变的经营事实，优先做成 Connector 读取（即便当前"外部系统"只是客户仓库的一个 YAML/TS 文件，也应该有唯一权威指针，而不是复制一份进 ME 自建表）；
- 只有在评估完上述统一路径确实无法满足 Tour 管理模块的读写需求后，才考虑新建 ME 自己的最小快照表，且需在方案中写明为什么现有三份事实源 + `FirstPartyTour` + `tailor_made_itineraries` 都不能承载。

---

## Build vs Connect vs Buy

- **团的价格 / 库存 / 出发日期 = Connect，不 Build**：按 `ME_PRODUCT_DEFINITION.md` §3.2，这些是外部经营事实，ME 通过统一/接入现有事实源（`factory_config.offers` / `offerings.yaml` / `FirstPartyTour`）读取，不自建替代表。
- **Tour 管理后台 UI = Build（小范围）**：管的是「录入营销所需的最小快照 + 一键生成素材」这层交互，不是团数据本体。
- **地图生成 = Build（已做内核）**：per-tour 自动出图，无现成 SaaS 能按 CTS 品牌 + 中国真实边界 + 自适应布局出图；成本为零（纯渲染）。
- **AI 文案 / SEO 内容 = 复用 ME 现有** `src/lib/ai/` + SEO writer skill，不新建。
- **PDF 渲染 = 复用**已登记的 HTML→PDF 候选。
- **地图底图数据 = Buy/Free**：用公开地理边界数据（Natural Earth 类，免费），不买地图服务。

## 分步计划（建议顺序，每步是独立可交付）

> 每步都走：设计 → 子牙(架构)+魏征(挑刺) 双审 → 五道 Build Gate → 实现 → 验证。风险级见每步标注。

1. **P1 · 统一现有团事实源（地基）** [A 级：可能涉及新表/schema，取决于统一方案]
   先完成「现实地基问题」一节要求的评估：`factory_config.offers` / `offerings.yaml` / `FirstPartyTour` 三者收敛为唯一事实源（或明确权威源、其余只读它）；ME 侧只新增/复用**营销所需最小快照**（城市序列、交通方式、天数——供地图生成器使用），价格/库存/出发日期继续 Connect 读取，不复制进 ME 自建表。只有在评估后确认现有结构无法承载时，才新建最小快照表，并在设计里写明为什么 `FirstPartyTour` / `tailor_made_itineraries` 不适用。

2. **P2 · 路线图生成器产品化** [B 级]
   把原型（受跟踪：`docs/specs/prototypes/tour-route-map/`）搬成 ME 里的正式能力：输入 = P1 的营销快照，输出 = PC + 手机两版 SVG，落 ME 的公开桶。**产品化前置：把品牌色/logo、底图、地理标注规则参数化**（当前原型这三样是 CTS/中国硬编码），才能支持非中国目的地/其他客户。复用今天验证过的设计系统与自适应布局。

3. **P3 · Tour 管理后台 UI** [B 级]
   ME 后台一个页面：列出客户的团、录入/编辑地图所需的营销快照（城市/天数/交通/活动/卖点）、一键生成地图 + 预览。**价格/出发日期/库存只读展示**（来自统一后的事实源），不在 ME UI 里另存一份可编辑的价格主数据。

4. **P4 · 内容 + 定价产出** [B 级]
   接 ME 现有 AI 文案 / SEO writer / grounding，从营销快照产出各渠道文案；价格块直接读统一事实源的当前价格，不做 ME 自己的价格计算/存储。强制官网 grounding。

5. **P5 · 一键交付** [C 级]
   把四块产物打包（地图 + 文案 + PDF brochure + 落地页片段），FDE 一键取用。

**建议节奏**：P1+P2 先做（地基 + 已验证的地图内核），能立刻让「录团→出图」跑通；P3-P5 视优先级排。

## 地图内核怎么并进来（今天的产出如何复用）

原型已存进**受跟踪路径** [`docs/specs/prototypes/tour-route-map/`](./prototypes/tour-route-map/)（gen.py + specs.py + 底图数据 + README），验证了全部难点：
- 按团实际城市**自动缩放**中国地图（2 城到 12 城都成立）；
- **真实地理边界**（不手画）、台湾按中国惯例标注；
- **自适应布局**（城市少=详细卡片，城市多=紧凑列表）；
- **PC 宽版 + 手机竖版**两套，页面按屏宽自动切；
- CTS 品牌色 + logo（⚠️ **硬编码**，见下）。

P2 就是把这套逻辑从原型脚本，搬成 ME 里读数据、落桶的正式服务。**设计不用重来**，主要工作 = 接上数据源 + 存储 + **把品牌色/logo、中国底图、台湾标注这三样硬编码项参数化**（当前是 CTS/中国专用），才能支持其他客户/非中国目的地。

## Reuse Statement（复用边界）

- **复用了什么平台能力**：今天的地图生成器复用了公开地理数据 + 已有 CTS VI；产品化后复用 ME 的 `src/lib/ai/`、SEO writer skill、HTML→PDF 候选、公开桶存储。P1 不新建团数据本体，而是复用/收敛 `factory_config.render.creatomate.offers`、`config/clients/cts/offerings.yaml`、`src/lib/web-intelligence/first-party-tours.ts`（`FirstPartyTour`）这三份已存在的事实源。
- **平台共享**：地图生成器（营销快照 → 出图）、内容/定价产出管道（读统一事实源，不自建价格主数据）。
- **行业专属（L2 旅游版）**：整个 Tour 管理模块只服务旅游类客户；营销快照的最小 schema（若最终确需新建）属旅游版地基。
- **客户专属（L4）**：CTS 的具体团/价格/城市/活动 = client 配置，进库隔离，不入 shared runtime。
- **红线核对（Codex 复审 2026-09-14 修正）**：地图生成器**逻辑**不含写死的客户名/城市/价格（全来自输入 specs），**但视觉资产（CTS 品牌色/logo、中国底图、台湾标注惯例）当前硬编码**——当前范围严格是「中国线路 · CTS 首例」，候选表状态 `candidate · 1/2`，未取得旅游版共享资格。**产品化前置**：① 品牌/logo 参数化（按 client 读，下沉 L4）② 底图/地理规则参数化（支持非中国目的地）③ 团事实走 Connector。三样未做前不得当平台共享直接搬。
- **没有新建替代性事实源**：团的价格/库存/出发日期不复制进 ME 自建表，遵守 `ME_PRODUCT_DEFINITION.md` §3.2「ME 不直接负责旅游库存、正式报价」+ §3.3 最小保存原则；仍在 client-private 范围内的是"哪些团在推广、怎么推广"，不是"团本身卖多少钱、还有没有位"。
