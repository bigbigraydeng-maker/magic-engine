**写入者**：本会话，唯一。分支 `feat/crm-whatsapp-groups-design`（当前仅设计稿，未动代码）。

## 背景

PM 给了一段真实的 NAL WhatsApp 群聊记录（客户 Mirko + 员工 Ben Wang / Jessica Zhang / leah 拉在一个群里谈货运报价）。查证结论：这类"员工手动拉群、把客户和好几个同事放一起聊"的场景，ME 现在**完全看不到**——不是哪个客户特有的问题，是 Meta 官方接口从根上不对普通（非 API 建的）群聊开放数据。

同一轮里查到 Meta 官方确实有一个「群组 API」（[developers.facebook.com/.../whatsapp/groups](https://developers.facebook.com/documentation/business-messaging/whatsapp/groups)），但它解决的是另一件事：**不是"读到员工自己拉的群"，是"企业自己用接口建一个新群，从建群那一刻起消息就能被系统收到"**。这份设计稿评估怎么用这个官方能力，把"多人协作对话进系统"这件事做成 ME 的一个功能，而不是继续指望员工事后手动复制粘贴。

## 目标 / 非目标

**目标**：员工在 ME 后台某个客户的对话里，能一键拉同事和客户进一个officially由 ME 建的 WhatsApp 群；群里往后发生的每一句话（不管客户说的还是哪个同事说的）自动同步进这个客户在 ME 里的完整记录，换人接手时新员工打开客户卡片就能看到全部历史。

**非目标（本轮不做）**：
- 不追溯接入员工现有的、已经在用的私人群（比如 PM 给的这个 Mirko 群）——技术上做不到，Meta 不允许把一个已存在的普通群"过户"成 API 群。
- 不做"通话"功能（另一份候选，本轮不合并进来）。
- 不做多客户共享同一个群（一个群从设计上只服务一个 CRM 联系人）。

## 前提条件（顺序不能跳）

1. **NAL 需要先拿到「官方业务账户」（OBA）**——比现在 CTS 在用的普通 WhatsApp Business Platform 号码等级更高，需求文档已经在另一条待办里（"Meta developer 申请几个档次"那次对话）。没有 OBA，群组 API 调不通，这是硬闸门，不是本设计能绕开的。
2. **需要一份"员工手机号 ↔ 员工身份"的对照表**（每个客户各自的花名册，比如 NAL 的 Ben Wang 用哪个号、Jessica Zhang 用哪个号）。这是**客户配置**，不是平台通用数据——不同客户团队构成完全不同，禁止写死进共享代码（对应 CLAUDE.md §0 铁律）。现在 ME 没有这张表，需要新建一个小的 Setting UI（FDE 能填，不进 Supabase Studio 手填）。
3. 现有 `clients.whatsapp_phone_number_id` 绑定机制（CTS 已用、NAL 还没申请）继续复用，群组 API 挂在同一个官方号下，不是另开一个号。

## 需要验证的技术未知项（动工前必须先在沙盒号上实测，不能凭文档猜）

- 群消息的 Webhook 负载具体长什么样：`messages[].from` 在群聊场景下是不是"具体发言人的号码"（客户本人或某个员工本人的号），有没有单独的字段标出"这是哪个群"。现有 `src/app/api/webhooks/whatsapp/route.ts` 全文假设 `from` 就是客户号码本人，这个假设在群场景下大概率不成立，必须先拿沙盒号跑一遍真实 payload 再动代码，不能照抄现有一对一处理逻辑。
- 员工用自己的私人 WhatsApp 账号点邀请链接加入群后，员工发的消息是否真的会推送到 ME 的 Webhook（多方信息认为会，因为群挂在企业号名下，但文档没有逐字写死这一条，需要沙盒实测钉死）。
- 客户点邀请链接这一步的用户体验——会不会被客户误认成陌生营销链接而不点。

## 初步方案（供子牙 / 魏征审，非定稿）

1. **建群入口**：`PersonDrawer` 加一个「邀请同事进群」按钮，员工勾选同事（花名册里选） → 新增接口 `POST /api/clients/[id]/crm/contacts/[cid]/whatsapp-group` 调用 Meta 群组 API 建群，拿到邀请链接 → 通过既有一对一对话把链接发给客户。
2. **数据模型**：`conversations` 表需要区分"这是一对一对话"还是"这是群对话"（初步想法：加一个 `kind` 字段，`direct` | `group`，不新建平行表，复用现有 `conversation_messages`）。群消息落库时除了现有的 `direction`（in/out），新增"发言人是客户还是员工、如果是员工是谁"的归属字段——查花名册表，查不到就存"未知发言人"，不能瞎猜。
3. **读侧**：CRM 时间线渲染群消息时按发言人显示名字（客户 vs 具体哪个同事），跟 PM 这次直接贴给我看的聊天记录效果一样。
4. **限制照抄官方**：群成员上限 8 人、每个企业号最多建 1 万个群、不支持撤回/删除消息、不支持隐藏成员名单——这些不是 ME 的产品缺陷，是 Meta 的硬限制，UI 上要如实告知员工。

## 风险分级（初判，子牙复审时可改）

B 级——新增对外 UI + 新增接口 + 改动共享的 WhatsApp webhook 处理逻辑，不碰鉴权/资金/数据库表结构破坏性变更，但因为改的是"跨多文件的核心链路"（webhook 是所有客户共用的入口），按 CLAUDE.md §4「触碰已上线功能」算大任务，需要子牙（架构）+ 魏征（挑刺）两轮设计阶段复审，通过后再排期实现。

## 验收（本轮设计稿的验收，不是最终功能的验收）

子牙出架构意见 + 魏征挑出的坑，都写进本文件「复审意见」一节；PM 看到复审意见后决定要不要正式排期开发。**本轮不写一行 `src/` 代码。**

## 复审意见

（待魏征回填）

### 子牙（架构）

**总体判断**：方向可以继续往下走，但初步方案第 2 点（`conversations` 加 `kind` 字段、复用现有 upsert 路径）低估了群聊和一对一聊天在身份识别上的根本差异，会踩中 `identity.ts` 和 webhook 现有代码明确写死的假设。这不是"多加一个字段"级别的改动，动工前要先把建模改掉，不能在现有 `upsertConversation`/`resolveContact` 调用链上直接叠加 `kind` 分支。

**1. 复用现状**

复用得对：`resolveContact`/`buildIdentities`（`src/lib/crm/identity.ts`）、`conversation_messages`、`clients.whatsapp_phone_number_id` 绑定机制都该继续用，不该另起一套联系人合并逻辑或另建一张群消息表。`conversations` 这张表本身也是从 `messenger_conversations` 改名统一过来的（见 `20260726000004_unified_contacts.sql`），历史上就是"多渠道共用一张会话表"的设计意图，群聊算进来符合这个方向,不是新支柱。

**2. 花名册该放哪一层——同意"客户配置"，但要挂在已有位置，不要新建概念**

同意不能进共享 runtime：不同客户团队构成完全不同，写死会重复 2026-08-30 那次"平台通用当成客户语义"的错误。

但设计稿说"需要新建一个小的 Setting UI"没找准落点——仓库里已经有 `src/app/dashboard/clients/[id]/settings`、`_components/SettingsDrawer.tsx` 这套客户级配置 UI 的既有骨架，花名册（员工手机号 ↔ 员工身份）应该是这套 Settings 下新增的一个板块，而不是一个独立的新页面/新概念。落库建议比照 `clients.facebook_page_id` 之类"客户专属配置项"的既有模式（要么挂 `clients` 表的一个小表，要么一张 `client_staff_directory(client_id, phone_e164, display_name)` 之类的簿子），但**不要**让这张表的行为经过 `contact_identities`/`resolveContact` 的合并逻辑——员工手机号绝对不能被当成一种"跨渠道身份键"去参与联系人合并，理由见第 3 点。

**3. `kind: direct|group` 思路——字段本身合理，但现有 upsert/resolve 链路的隐藏假设必须先破除，这是最大的坑**

现有 `upsertConversation`（`src/app/api/webhooks/whatsapp/route.ts:216-306`）和它调用的 `resolveContact` 建立在两条对一对一场景成立、对群场景不成立的假设上：

- **`conversation_id` = 发消息人的 `wa_id` 本人**（`conversation_id: waId`，第 267 行注释明写"WhatsApp has no separate thread id — the wa_id IS the thread key"）。群场景下这条假设直接崩：群里企业号收到的每一条群消息，`from` 是"这次发言的人"的号码（客户或某个员工），不是"群"本身的稳定标识。如果不改这条路径,同一个群会因为不同发言人产生**多条**`conversations` 行（每人一条，key 是各自的 `wa_id`），而不是设计稿设想的"一个群一条会话"。这个建模必须先改成"群场景下 `conversation_id` 用 Meta 群组 API 返回的群 ID，`participant_psid` 之类的字段才用来记发言人"，不能照抄现有 upsert。
- **`resolveContact` 假设传进去的电话号就是客户本人**（`identity.ts` 头部注释："只认电话和邮箱，不认姓名"，并且 `buildIdentities({phone: ...})` 会去建/合并 `contacts`）。群里员工用自己私人号发言,如果沿用现有调用方式把 `from` 原样传进 `resolveContact`,**员工的私人手机号会被当成一个新联系人身份写进 `contact_identities`，在最坏情况下如果员工号码恰好在别的客户身上被误标注/巧合命中,还会触发合并逻辑**——这是对客户数据红线的直接冲击（CLAUDE.md §8），不是小概率的边缘 bug。正确做法是群消息落库时先查花名册（第 2 点那张表）判断发言人是不是内部员工：是员工 → 完全不过 `resolveContact`，直接用群创建时就绑定好的 `contact_id`（设计稿目标里说的"群从设计上只服务一个 CRM 联系人"，这个绑定应该在建群那一刻就存死,群消息落库不该每次重新做身份解析）；是客户 → 才按现有客户身份路径走。这一条建议直接写进正式方案,不要留到实现阶段才发现。
- **`last_message_from` 只有 `'customer'|'page'` 两个值**（CHECK 约束,`20260726000004` 之后的 `conversations` 表定义）,群场景至少要能表达"哪个员工说的",现有二值约束需要跟着这次改动一起扩展,否则"谁最后说的话"这个字段在群聊里要么报错要么被迫说谎。

一句话:`kind` 字段本身没问题,但"复用 `conversation_messages`"不等于"复用现有 `upsertConversation` 函数"——群场景需要一条新的、结构上不同的落库路径,只是最终写进同一张表。请在正式方案里把这条路径画出来,而不是在现有函数里加 if。

**4. 沙盒实测是否必须前置——同意设计稿判断,理由要更硬**

这几条不是"锦上添花的验证",是**决定第 3 点怎么建模的输入**,顺序不能倒:

- `messages[].from` 在群场景下具体是什么、有没有单独字段标群 ID——这直接决定 `conversation_id` 该塞什么值,不实测就无法定表结构,边做边验会导致中途改 schema。
- 员工私人号进群后消息是否真推到 webhook——这决定"员工归属识别"这条链路是否可行；如果实测发现推不到,第 3 点第二条的整个方案作废,必须重新设计(比如退回"只认证过的企业侧号码")。这种量级的分支不能在写完代码后才发现。

这两条建议**动工前**在沙盒号上实测,不是"风险可接受,可以边做边验"级别的未知项——它们决定的是数据模型,不是实现细节。第三条(客户体验:会不会被当成营销链接)可以边做边观察,不是架构级阻塞,可以放宽。

**5. 平台通用 vs NAL 专属试点——建议先当试点,但要素必须按平台化写**

按 Reuse First 判断:群聊场景(员工代表企业跟客户混聊)不是 NAL 独有的业务语义,CTS、其他任何走 WhatsApp 的客户理论上都可能有"多个员工跟一个客户混聊"的场景,所以"群消息进 CRM 时间线"这个能力本身该按平台能力设计(这也是设计稿目标写的方向,同意)。

但建议**执行上**先在 NAL 单客户試点:一是第 4 点的技术未知项还没实测钉死,过早把接口/UI 泛化成"所有客户都能建群"意义不大;二是前提条件里 OBA 目前只有 NAL 在申请路径上,CTS 还在用普通号,做成"全平台功能"但只有一个客户能用,不产生额外复用收益,只增加维护面。**试点不等于把 NAL 语义写死进共享代码**——按 Reuse Statement 的口径,共享部分是"群组建群接口 + 群消息落库路径 + 花名册 UI 骨架",NAL 专属的只是"当前唯一开着的客户配置"(跟 `facebook_page_id` 只给 CTS 开的先例一致,见 `20260726000001` 迁移文件底部"Enable the sync for CTS Tours NZ only")。正式方案里请显式写这条 Reuse Statement,不要含糊带过。

**结论**:方向批准,但正式排期前,方案第 2 点必须落到已有 Settings UI 骨架下,第 3 点必须画出"群场景走独立建模路径、不经过现有 `resolveContact` 直传发言人号码"的图,第 4 点两条技术未知项维持"动工前必须实测"不降级。

### 魏征（挑刺）

结论先说：**这份设计稿目前的状态是"技术方案"，不是"能上线的方案"——它漏掉了至少两类一旦发生就无法收回的真实事故（员工私人手机号泄给客户、客户手机号泄给不该看到的员工），而且现在文档里连"要不要做"的判断依据都没给够。下面按 PM 给的六个方向逐条挑，附代码依据。**

#### 1. 隐私/权限坑——员工手机号泄露给客户（本设计最大的坑，文档完全没提）

WhatsApp 群组的机制是：**任何成员一旦在群里，就能看到其他所有成员的手机号和头像**——这是 WhatsApp 客户端自己的行为，不是 ME 能通过代码控制的东西。设计稿第 41 行只写"员工勾选同事（花名册里选）→ 调用 Meta 群组 API 建群"，**完全没有讨论谁能被拉进这个群、拉错了会发生什么**。

具体会翻车的场景：
- FDE 手滑勾错了人（比如把还在试用期、没打算长期对接这个客户的同事也拉进去）——这个同事的私人手机号从此永久暴露给客户，**无法撤回**。WhatsApp 不提供"事后隐藏某个已经在群里待过的成员的号码"这种功能，哪怕后续把这个人移出群，客户手机通讯录/聊天记录里这个号码已经留下了。
- "勾选同事"这一步的候选名单从哪来？如果是"这个客户名下所有花名册条目"，那只要花名册维护得不够严格（比如员工离职但花名册没删），离职员工的号码也可能被选中拉群。

**这道防线必须在设计里写清楚，而不是留到实现阶段自由发挥**：
- 谁有权限点"邀请同事进群"这个按钮？是不是要求该员工本人在被邀请前先"确认愿意让自己的私人号码暴露给这个客户"（类似一次性授权动作），而不是别人替他点？
- 有没有考虑让员工用**企业配的、不是私人的号码**加群，而不是自己的私人 WhatsApp？如果没有这个选项，就要在设计里明说"这个功能的代价是每个参与群聊的员工都要接受私人号码暴露给客户"，让 PM 带着这个认知去决定要不要做，而不是等上线后员工自己发现。

#### 2. 数据完整性坑——退群/被移除，ME 怎么知道

设计稿"需要验证的技术未知项"一节（33-38 行）只列了三条，**全部是关于消息 payload 的**，一条都没提"群成员变化"这件事。但 WhatsApp 群组里任何成员都能把别人移出群（客户完全可以把某个员工移出去），也可以自己退群。这跟消息同不同步是两个独立的技术问题，不能漏。

需要在"技术未知项"里补一条，动工前必须查清楚：
- Meta 群组 API 有没有"成员加入/退出/被移除"的 Webhook 事件？如果有，事件里给不给出"谁把谁移除的"？
- 如果没有这个 Webhook（大概率没有，官方文档目前只强调消息同步），ME 拿什么手段发现"这个员工其实已经不在群里了，但花名册和 UI 还显示他是参与者"？现在设计里没有任何轮询或对账机制。

不解决这条，会出现**静默丢消息且没人知道**的情况——完全符合 CLAUDE.md §3 下半段"发现不许死在日志里"的红线，但这次连"发现"这一步都没有，因为没人在监控群成员漂移。

#### 3. 身份归属坑——花名册漂移导致的两种误伤

设计稿第 30 行已经承认"员工手机号↔身份"是客户级配置，这个方向是对的。但漏了两种会**把消息安到错误的人头上**的场景：

- **手机号回收**：员工离职换号，运营商把这个号码重新分配给别人（NZ/AU 运营商号码回收是常态，不是罕见情况）。花名册条目如果没有及时清理，旧号码可能被新号主（跟这个客户毫无关系的陌生人）持有；反过来，员工用新手机号继续跟客户对话，花名册还是旧号码，新号码的消息只能走"查不到就存'未知发言人'"这条兜底——兜底本身没问题，但设计稿没写"未知发言人持续出现"要不要报警、谁来定期核对花名册这件事。
- **一个员工服务多个客户**：设计稿自己举了这个风险但没给方案（"花名册只在单客户维度配置"是问题陈述，不是解决方案）。如果同一个员工同时服务两个客户，两边花名册各自独立维护他的手机号，一旦某一边漏填或填错，这个员工在另一个客户群里发的消息就会被归到"未知发言人"，客户交接时新员工看到的历史记录里会有一堆"未知发言人"，等于白建。

**这两种情况现在都只能靠人工按时核对花名册**，设计稿完全没提维护责任——花名册建完谁来保持它是对的？多久核对一次？没有这个机制，"未知发言人"会越积越多，功能上线三个月后可能相当比例的消息都挂着"未知发言人"，比不做还难看。

#### 4. 并发/幂等坑——重复建群 + 假成功

设计稿"初步方案"第 41 行的接口 `POST /api/clients/[id]/crm/contacts/[cid]/whatsapp-group` 完全没提并发控制和错误处理，这是能直接导致"UI 显示建群成功、实际没建成"的真实缺口：

- 两个不同的人（或同一个人手滑点两下）几乎同时点"邀请同事进群"，会不会在 Meta 那边建出两个群？设计里没有任何"这个联系人是否已有一个活跃群"的检查，也没有数据库层面的唯一约束（比如 `UNIQUE(client_id, contact_id) WHERE status = 'active'`）。两个群一旦都建成，未来客户和员工可能各自在不同的群里说话，CRM 时间线只能显示其中一个群同步的消息，另一半**悄悄丢在另一个从未被记录过 group_id 的群里**。
- Meta 群组 API 报错（比如超过每个企业号 1 万个群的上限、员工号码格式不对、业务账号还没验证）时，接口怎么处理？设计稿完全没写失败路径。按 CLAUDE.md §3 的标准，"没有 Ray 授权事件和 provider receipt，不许伪造完成"这条同样适用在这——UI 绝不能在没拿到 Meta 明确的建群成功回执之前就说"建群成功"，必须能区分"请求已发出，等 Meta 确认"和"确认建成"两种状态，且要给出失败时的用户可见提示，不能只在日志里报错。

这条必须在实现阶段的技术方案里写清楚"幂等键是什么、失败时 UI 显示什么"，现在设计稿的粒度还答不出这两个问题。

#### 5. 法律/合规坑——客户手机号暴露给"原本没有权限接触这个客户"的员工

这条比 PM 提的问题更深一层：**查了当前代码库，ME 现在没有任何"哪个员工能看哪个客户的联系方式"的访问控制层**（`src/lib`、`src/app` 里搜不到任何 `client_staff` / `staff_assignments` / `client_access` 一类的表或逻辑；`supabase/migrations/20260803020000_rls_lock_policies_to_service_role.sql` 之后的 RLS 策略统一收敛成"只认 service_role"，即**权限判断目前全部在应用层做，数据库层不区分员工归属**）。

也就是说，"这个新功能会不会让没权限的员工看到客户手机号"这个问题，**现在在 ME 里问不出答案**，因为"权限"这个概念在员工-客户维度上本来就没有被建过模。这不是这份设计稿一份文档能解决的坑，但必须在文档里如实写清楚这个事实，而不是假装"权限模型"已经存在、这个新功能只是要去对接它——子牙审的时候如果没意识到这一点，会把这次的风险评估建立在一个不存在的地基上。

另外一条容易被忽略的连带效应：设计稿第 41 步"通过既有一对一对话把链接发给客户"——**客户点这个邀请链接算不算同意"被拉进一个能看到多名 ME 员工手机号的群"、以及"自己的手机号会被这些员工看到"？** 现在设计里没有任何客户侧的告知文案。链接发过去等于默认客户已经同意，但客户很可能根本不知道点了链接会发生什么（PM 提的第 6 点问题里也隐含了这层——客户体验部分设计稿只写了"会不会被当成营销链接不点"，没写"点了之后客户自己也在暴露隐私，要不要提前告知"）。

#### 6. 假安全感——"不追溯私人群"这句话必须配一条主动通知，不能只是设计稿里的一句免责声明

设计稿第 23 行只在"非目标"里轻描淡写一句"技术上做不到"，**没有配套任何面向员工的沟通计划**。PM 提的风险是真实的：一旦这个功能上线，最容易被误传成"以后 ME 系统啥都能看到"的小道消息版本，尤其是完全没参与这次设计讨论、只是听说"WhatsApp 群现在有了"的普通员工。结果是他们会更放心地在旧的私人群里继续聊报价、合同细节——因为"反正系统看得到"——而这恰恰是错的，旧群从设计上根本连不上系统。

这条必须变成设计稿里的一个明确的交付项，而不是留白：**功能上线当天，必须有一条发给全体使用 WhatsApp 对客沟通的员工的通知，原话讲清楚"只有从 ME 后台新建的群才会同步进系统，之前用手机自己拉的群、以及所有一对一私聊，跟现在完全一样，ME 看不到、也不会开始看到"**。没有这条主动澄清，这个功能上线净效果可能是负的——员工警觉性从"知道系统看不到、所以对私聊内容更谨慎"退化成"以为系统都能看到、反而更随意"。

#### 额外发现（顺带挑出，非 PM 原六条之一）

- **群内客户自行拉人**：WhatsApp 群默认所有成员都能拉新人进群（除非群设置改成"仅管理员可添加成员"）。设计稿"非目标"第 25 行说"一个群只服务一个 CRM 联系人"，但如果没有在建群时把群设置成"仅 ME（管理员）可添加成员"，客户完全可以自己把同事拉进来——这个新成员的消息会被同步进系统，但系统里没有这个人的任何身份记录，只能落"未知发言人"，而且这个人的手机号会被所有已在群里的 ME 员工看到（互相暴露，双向问题）。建群参数里必须显式设置"仅管理员可拉人"，这条要写进"初步方案"第 41 行，不能遗漏。
- **消息识别路径要跟通用联系人识别逻辑（`src/lib/crm/identity.ts` 的 `resolveContact` / `buildIdentities`）明确划清边界**——这一点跟子牙第 3 点"员工号码不能直传 `resolveContact`"是同一个坑，从两个角度都踩中了，说明这不是可以再讨论要不要做的可选项，是正式方案里必须钉死的一条：**花名册命中的员工消息必须在进入 `resolveContact` 之前就被拦截分流**，绝不能让员工手机号进入面向客户的身份合并逻辑，否则会把员工的号码当成一个新客户线索创建出虚假联系人，或者反向把员工身份和某个真实客户的历史记录错误合并。
