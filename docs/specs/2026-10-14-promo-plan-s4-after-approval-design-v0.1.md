## 0. PM 版（先看这里）

**现在的状态：** 你点「批准」后，什么都不会发生（页面上写着「批准后还没有自动生成待办」）。计划里写了「每周 3 条帖子、每月 2 条短视频、第 20 天一篇博客」，但没人把它变成「哪天做哪件事」。

**我原本建议：批准后自动写一批待办卡到执行看板。两位审查员查完，这个建议我收回，原因是查出四个会出事故的点：**
1. **客户自己的页面会原样显示这些卡**（包括广告预算和受众）——不是「只是内部提醒」，等于对客户外发了没核实的东西。
2. **视频卡点开就有「生成视频」按钮**，绕过视频工厂的对账和分镜自检（正是 9-28 那类事故）。
3. **两个人同时点批准，会留下几百张重复的卡**，没有办法自动清。
4. **退回/撤销出错时，会留下「计划已批准、待办却全没了」**，页面还写着「已派 N 张」。

修这四处要动客户页面、执行看板、派发程序，是一整块单独的活，不该塞进「批准」这一步里一起上。

**所以我改成分两步：**
- **S4a（建议先做，小、安全）：只做「排期表」。** 页面按周列出「哪天发几条帖子 / 快拍 / 短视频、哪天博客和邮件到期、哪个阶段有广告」，批准前就能预览；排期表头部写「共排出 N 件」（不放在批准按钮旁，免得被读成「批准后会派 N 件」）。**纯计算、只读、不写任何数据、不碰客户页面、不调用任何生成服务。** 批准后仍然不会自动派活（页面如实写）。你能看到的是：计划终于变成「每天做什么」。
- **S4b（以后，单独立项）：** 把排期变成执行看板上的待办卡。要先把上面四点和另外几项前置条件（见 §8）做完，再来一次设计审。

**你要定一件事（回一个字就行）：**
- 回 **「B」**：按新建议做 S4a（只做排期表，我推荐）。
- 回 **「A」**：坚持批准后就写待办卡——那要先做完 §8 的前置条件，更大、更慢，而且会碰客户页面（A 级里的 A 级），我会重新出设计再审一遍再动手。

## 2A. S4a 设计（建议先做）：排期表，纯读

- **一个纯函数** `expandPromoSchedule(spec, playbook)` → 逐日排期，不读库、不写库、不依赖服务器时区。页面（草稿预览 + 已批准查看）和批准按钮旁的「约 N 件事」都用它，所以数字一致。
- **新增一个组件** `ScheduleTable`：按日历周分组，每天列出要做的事；已过去的日期灰显；每周小计。草稿时标「预览（还没批准，不会派任何待办）」，已批准时标「排期（批准后暂不自动派活，下一步另做）」。
- **不写库、不新增接口、不动批准路由、不动执行看板、不动客户门户。** 因此不触发魏征查出的 1–4 条风险。风险级别 **B**（纯计算 + 页面），不必等 PM「合 N」。
- **排期规则（吸收两位审查的边界意见，全部进测试）：**
  - 日期一律用 UTC 日历天（`Date.UTC` + `getUTCDay`），不用字符串加减、不用本机时区；测试在非 UTC 时区环境下跑；日期必须往返校验真实存在（`2026-02-30` 拒绝），范围限定在计划起止 ±1 年内。
  - **每周条数按「日历周」统一分配，再按阶段切**（不再「各阶段各自向上取整」，避免跨阶段周超过 N）；固定的星期表放 `playbooks.ts`（标 `unvalidated_default`）：N=1→周三；2→周二/周四；3→周一/三/五；4→周一/二/四/五；5→周一至周五；6→周一至周六；7 及以上→每天，**超出 7 的部分不排，页面写「每周最多排 7 条，计划里写了 N 条」**。
  - 阶段起止在周中：只在落在阶段内的那些天里取，按星期表里属于该周的那几天落点；落点不在阶段内就不排（不补、不超），所以一周被切成两段时总数不会超过 N。
  - 阶段只有 1 天且当天不在星期表里：0 件，页面如实显示「这段没有排上」。
  - N=0：不排；整份计划总数为 0 时页面写「这份计划还没排出任何每天要做的事」。
  - **短视频每月 N 条**：折算成「阶段天数 × N ÷ 30，四舍五入，至少 1 条（N>0 时）」，在阶段内均匀落在工作日（可由行业剧本改）。**与每周对账口径不完全相同**（对账按滚动 7 天、每月 N 条折成 N×7÷30），M 很小或阶段首尾不足一周时会差几条——v0.2 曾写「共用折算函数」，实现时发现要改已上线的对账函数、风险升级，故不强行统一，页面表头固定写明差异（「做事以本表逐日为准，对账只看整体进度」）。
  - 博客 / 邮件：到期日就是步骤里写的日期。广告：每个阶段开始日显示「计划开投日（开投需要 PM 在广告审批页另行批准，目前广告没有投）：日预算 X（币种以广告账户为准），受众引用 Y」，只读展示；该日在计划的暂停区间内时加注。
  - 规模与日期防护（第二轮设计审补充，实现与测试已覆盖）：日期必须是 2000–2100 年内的真实日期（`9999-12-31` 会让现有日期加减出带 + 号的怪字符串，按字符串比较的逐日循环会死循环，所以逐日循环一律按天数计数）；阶段不得重叠 / 倒置；所有阶段合计 ≤ 800 天、步骤 ≤ 200 个；展开后超过 1000 件只给汇总不展开；说明按原因聚合、最多 20 条；主题等文字截断到 80 字。**不改保存校验（`spec.ts`）**：v0.2 曾写「频率上限 21」，改为只在排期函数里封顶（每周 ≤ 7、每月 ≤ 1000），避免已保存的计划突然变成不合法。阈值放 `playbooks.ts`。
- **文案不误导：** 每条只复述计划里填的主题和数字；固定一句「以上是计划原文，未经官网核实，发布前必须核对」。不写任何搜索量、效果预估。
- **验收（当场试跑）：** 纯函数测试（同输入同输出、跨月跨年、阶段首尾不足一周、N=0/N>7、1 天阶段、非 UTC 时区、日期非法）；页面本地渲染 + 模拟接口截图「草稿预览」「已批准查看」「排得太密提示」；不碰生产库。

## 2B. S4b 设计（待前置条件满足；下面是第一轮设计，仅供参考，**不批准按此实现**）

### 2.1 一个纯函数：`expandPromoSchedule(spec, playbook)` → 逐日排期

输入已通过校验的推广结构，输出「某天 → 做什么」的列表，不读库、不写库：

| 步骤类型 | 展开规则（默认值放 `playbooks.ts`，标 `unvalidated_default`） |
|---|---|
| 社媒·帖子 `posts_per_week=N` | 阶段内每个「周一起算的周」平均摊到 N 天（N=3 → 周一/三/五；N=2 → 周二/周四；N≥7 每天）；阶段首尾不足一周按比例向上取整，不超过 N |
| 社媒·快拍 `stories_per_week` | 同上，从周二开始错开，避免和帖子全撞同一天 |
| 社媒·短视频 `reels_per_month=N` | 阶段内按天数平均摊开（N 条均匀落点），落点避开周末 |
| 博客 / 邮件 | 到期日就是步骤里写的 `due_date` |
| 广告 | 每个阶段开始日一张「准备广告草稿」卡（见 2.3） |

同一输入永远同一输出（有测试固定）。日期按计划里的日期字符串算，不依赖服务器时区。

### 2.2 批准时：把排期翻成 `PlanTask[]`，交给**现有**派发

- 推广计划批准时，`approve` 路由不再写 0 张，而是 `expandPromoSchedule → promoScheduleToTasks → dispatchPlanTasks`（既有函数，既有去重、既有失败撤销）。
- 每张卡带 `promo_ref: { phase_id, step_id }`，所以重复批准、重试都不会重复派。
- 卡片三件套（铁律 3）：**what**（这天要发什么、对应计划哪个阶段、为什么）· **how**（去哪个工作台、先查什么）· **href**（直达链接：社媒去内容工作台，视频去视频工厂下单页，博客去博客生成页，邮件去邮件任务页，广告去广告审批页）。
- 一次批准最多派 200 张；超过则**整份不批准**，返回「排得太密，请减少条数或缩短阶段」，不派任何卡。
- 批准回执（已有）里记下：派了几张、跳过几张、按哪版排期规则（`schedule_rule_version`）。

### 2.3 广告卡只提醒，不碰账户

每个含广告步骤的阶段，开始日前 3 天一张卡：「准备本阶段广告素材与暂停草稿；开投需要 PM 在广告审批页点头」。卡里写日预算和受众（来自计划），但**不调用任何广告接口**。建「暂停草稿」留给以后（走现有 draft-and-gate，另立项）。

### 2.4 页面

- 推广计划页新增「排期表」：按周分组，每天列出要做的事；草稿时显示「预览（还没批准，不会派任何待办）」，已批准显示「已派 N 张待办，去执行看板看」。
- 批准按钮旁写明：「批准后会在执行看板生成约 N 张待办（只是内部提醒，不发布、不花钱）」——N 由同一个纯函数算出来，批准前就能看见。

### 2.5 Inngest / 回执

没有对外副作用、不花钱、不跨步骤异步接力；批准仍是同步写内部待办，回执写在计划记录里（派发数、时间、操作者、排期规则版本）。依据 CLAUDE.md §3 的例外条款在 PR 写明；以后加「自动出稿 / 建广告草稿」这类对外动作时必须上 Inngest。

## 4. 风险与应对

| 风险 | 应对 |
|---|---|
| 一次派出太多卡，看板被淹 | 上限 200；批准前页面先显示张数 |
| 排期规则不合行业（例如周末更适合发） | 规则是 L2 默认数据，标「未验证」；FDE 可在卡上改到期日；不替任何行业写数字 |
| 重复批准 / 并发批准 | 沿用现有「标题+到期日+类型+平台+步骤编号」去重和乐观锁；已知残余风险同 §5.2（PM 10-14 已接受） |
| 批准后改计划 | 已有：批准后内容锁定，要改先退回草稿（清没开始的卡） |
| 卡片里编造事实 | 卡片只复述计划里 PM/FDE 自己填的主题和数字；不写任何官网未证实的内容 |

## 8. 第一轮设计审记录（子牙 + 魏征，2026-10-14）与 S4b 前置条件

两位审查员都判「改设计再审」，方向和复用思路没问题，不需要重做。**S4a 已吸收其中排期边界、日期算术、规模防护三类意见（§2A）；以下是 S4b（批准后写待办卡）必须先满足的前置条件，缺一不可：**

1. **客户门户可见性（魏征，高）**：`portal/[clientId]/plan/page.tsx`、`portal/[clientId]/page.tsx` 读取 `execution_items` 时不分来源，会把推广卡（含预算、受众、未核实排期）显示给客户。→ 门户按来源排除 `marketing_plan` 卡，或只显示已完成的；卡的说明只放中性内部话，预算 / 受众放结构化字段；加测试。
2. **视频卡不得有生成入口（魏征，高）**：`social_reel` 卡在 `ContentStudioDrawer` 里会出现「生成视频」（直调 Visual / Video Studio），绕过视频工厂铁律。→ reel 卡单独设执行目标指向视频工厂；drawer 对该类卡隐藏生成入口；加「reel 卡不得出现生成入口」测试；加「推广卡永不带自动出稿白名单 action_type」测试。
3. **并发批准重复卡（魏征，高）**：先查后插、无唯一约束，两次同时批准会各插一批、输家不清理。→ 部分唯一索引（`marketing_plan_id + 推广步骤 + 到期日 + 类型 + 平台`，迁移只写不应用）或批准前先抢占。这会改表结构，S4b 升为 A 级 + 迁移，「不迁移」的说法作废。
4. **撤销与零卡状态（魏征，高）**：`revokePlanTasks` 先删卡再改状态、失败不补；批准路由的撤销没有 `status='draft'` 保护。→ 撤销加状态保护；页面「已派 N 张」只用实时计数，已批准且 0 张时提示；一张进行中的卡会锁死退回，需给出「标跳过」路径。
5. **派发函数入参（子牙，不符）**：`dispatchPlanTasks(plan)` 只读 `plan_data.tasks`。→ 增加可传入任务清单的内部函数，不用克隆计划的办法。
6. **生产包副作用（两人都指出）**：派发后会按维度建 draft 生产包（失败只记日志）。S4b 推广卡**不建**生产包（加 `skipPackages`），与手工加卡一致。
7. **看板不渲染直达链接（子牙，不符）**：`execution/_client.tsx` 对 `in_house` 卡不显示按钮，卡里的 href 显示不出来。→ 看板补一处按 `steps_json.href` 渲染。
8. **广告卡类型（两人都指出）**：`PlanTaskKind` 没有广告类，未知类型会静默落成社媒（社媒文案 / 生成入口）。→ 新增类型须同时改维度、素材依赖、执行目标、drawer、测试四处。
