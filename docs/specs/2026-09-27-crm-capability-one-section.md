# CRM 合成一个板块 + 基础能力 / 行业层 / 客户层怎么切（v0 设计稿，待 PM 拍板）

**状态**：起草中 —— 界面盘点还没回来，第四节「合并方案」等它齐了再定稿
**提出人**：PM 2026-09-27。原话意思：
> 客户消息、商务邮箱、今天该联系谁、全部客人……这都是 CRM 的组件，设计如何合并到一个板块。我认为「客户消息」是个鸡肋功能，「全部客人」里的决策清单也是鸡肋。
> 理想状态是有一个基础的 CRM capability，然后基于不同行业跟客户去拓展 —— 他们都是 FDE 客户，可以基于业务需求做变化的定制式 CRM。这也是 Magic Engine 的特色：大部分功能通用，针对高级别客户有个性化定制开发。因为他们基本上所有路径都一致：从 Facebook（今后 TikTok / IG）来客户，需要用到 WhatsApp、Messenger、邮件、电话，我们帮他 process 和管理客户。这个总体框架没变。

## 一、先说三件查实了的事（这三件决定后面怎么切）

### 1. PM 说的「总体框架没变」，数据上成立

两个客户的路径确实是同一条：**外部平台进线 → 一段对话 → 人跟进 → 记录状态**。所以基础能力可以共用，这一点不用争。

### 2. 但两个客户的**渠道重心几乎相反** —— 这是切层的真正依据

实测（生产库，按渠道方向统计触点）：

| 渠道 | CTS（1014 人） | NAL（197 人） |
|---|---|---|
| 邮件 进 / 出 | **1657 / 717**（566 人 / 280 人） | 15 / 7（9 人 / 3 人） |
| 私信 进 / 出 | 798 / 500 | **187 / 149** |
| FB 表单 进 | **764**（703 人） | 3（3 人） |
| 电话 出 | **642**（594 人） | **0** |

**CTS 的重心是邮件 + 电话；NAL 几乎只有私信，电话一条都没有，表单只有 3 条。**

所以：
- 一个把「打电话」摆在最显眼位置的 CRM，对 NAL 完全没用
- 一个只做私信的 CRM，对 CTS 等于废掉七成
- 而**这不是行业差异，是这家客户怎么做生意的差异** —— 所以它该落在**客户层配置**，不是行业层

这也对上了 NAL 的目标口径：NAL 月目标是**开聊 300 个**（看消息不看留资），CTS 是成交。

### 3. 代码其实已经快通用了 —— 全 CRM 只有**一处**写死客户 id

`grep CLIENT_ID src/lib/crm/ + crm 界面` 只有一个命中：`ContactDetail.tsx:41` 的 `NAL_CLIENT_ID`（NAL 标已成交回传 Meta 用）。

已有的「按客户配」机制也已经在跑：

| 配什么 | 存在哪 | 现状 |
|---|---|---|
| 跟进阶段档位 | `client_pipeline_stages` 表 | CTS 9 档 / NAL 6 档，已在用 |
| 额外列 | `table-columns.ts` 的 `CUSTOM_COLUMNS` 注册表 | CTS「感兴趣的团」，NAL 无 |
| 进线 / 付款打标 | `clients.leads_config` jsonb | CTS 已有内容，NAL 是 `{}` |
| 有没有 Google 表格要同步 | `sheet-followup-sync.ts` 的 `CLIENT_FOLLOWUP_SHEETS` | 只有 CTS |

**结论：PM 要的「基础能力 + 定制」不是要新建，是要把已经长成这样的东西显式命名、并补上缺的那两块（统一入口 + 渠道配置）。**

## 二、Platform Tier Classification（Full）

**被判定对象**：把散在 7 个界面上的 CRM 收成一个板块，并显式定义「基础 CRM 能力 + 行业层 + 客户层」三层扩展模型。

**建议层级**：**L1 Capability（既有能力的边界澄清 + 收口），不是新增能力线。**

**归属**：ME 6 支柱中的**口碑 / 社媒共用的「进线与客户管理」**——严格说 CRM 是**平台基础设施**（Measurement / Growth Contract 的落地面），不是第 7 根支柱。

> ⚠️ **不申请新支柱。** 「CRM」听起来像一条新能力线，但它是 6 支柱共用的底座：广告带来的线索、社媒私信、口碑评价里的客人，最后都落到同一份 contacts。把它抬成支柱会触红线 1（禁包装升级）。

**换客户测试**：✓
- 反例客户 1（NAL）：基础能力不用改。默认行为要改的只有「哪些渠道亮出来、哪个渠道排第一」（NAL 无电话、几乎无邮件）和「目标口径」（开聊数 vs 成交）。**这两项今天是隐含的，必须落成客户层配置** —— 不落，基础能力里就会慢慢长出 `if (客户 === CTS)`。
- 反例客户 2（一个悉尼地产客户，库里 `real_estate` 已有 4 家）：同样不用改基础能力；阶段档位来自它自己那张配置表；地产要的「带看预约」是**行业层**的东西（不是单客户）。

**换行业测试**：✓（但有一个前提没满足，见下）
- 反例行业 1（旅游）：阶段含「已付定金 / 已付全款 / 即将出行」，出行日期驱动唤回 —— 这是行业级，不是 CTS 独有。
- 反例行业 2（物流）：没有出行日期，成交 = 一票货；关心的是开聊数和报价响应速度。
- 🔴 **前提没满足**：`clients.industry` 今天是**自由文本、不成体系** —— 库里同时存在 `travel` 和 `Travel — Tour Operator`、`flooring` 和 `SPC/hybrid flooring wholesale (B2B trade)`，29 家里 **17 家是 NULL**。**行业层现在没有可用的键。** 在把它规范成 slug 之前，任何「按行业分流」的代码都会静默落到默认分支。

**智能层 or 执行手**：智能层。CRM 是 ME 自己判断（谁该先联系、聊到哪一步了、下一步做什么）+ 受治理地执行（回私信 / 回邮件）。外部平台（Meta / WhatsApp / 邮箱）是挂在它下面的 L3 Connector。

**红线检查**：
- 红线 1（禁包装升级）：✓ 不申请第 7 支柱，CRM 归平台基础设施。
- 红线 2（禁客户 / 行业事实进 shared runtime）：⚠️ **现在就有一处违反** —— `ContactDetail.tsx:41` 的 `NAL_CLIENT_ID`。它今天是既有分支、范围很小，但合并时它会被搬进新板块的公共外壳，**那一刻必须下沉成配置**，否则下一个客户要改外壳。
- 红线 3（禁直建 L1）：✓ 不是新建，是既有 L1 的边界澄清。
- 红线 4（换客户测试语义级）：✓ 见上，已列两个反例客户逐条推演。
- 红线 5（换行业测试语义级）：✓ 见上，并点明 `industry` 字段不可用是前提缺口。
- 红线 6（L1 走五道 Build Gate）：本稿是 Architecture/Reuse Gate 的前置；Repository Fact / Domain Semantics 已在第一节做完（含实测）。
- 红线 7（L2 只装行业级）：✓ 渠道重心、目标口径判为**客户层**而非行业层 —— 依据是 CTS 和 NAL 的差异来自生意做法，不是来自旅游 vs 物流。

**PM 待拍板项**（我不能替你决定的）：
1. 「客户消息」和「决策清单」要不要**删掉**（你已经说是鸡肋；删是不可逆的对外改动，要你点头）。
2. 三层里「行业层」现在要不要做 —— 库里只有 4 家地产、2 家物流、2 家旅游，**样本可能还不够支撑行业剧本**；我倾向先只做「基础 + 客户层」两层，行业层留空槽。
3. 「高级别客户才有的定制」在商业上怎么界定（`plan_tier` 现在 CTS 是 growth、**NAL 是 starter**，跟你说的「都是 FDE 客户」对不上）。

**结论**：
- 原本想法层级：可能被当成「新增 CRM 能力线」
- 判定层级：**既有 L1 Capability 的收口 + 两层（客户层已有 / 行业层留空槽）扩展模型**
- 下一步：等界面盘点齐 → 补第四节合并方案 → 三方审 → PM 拍上面三项

## 三、三层怎么切（用实测差异划，不是凭感觉）

| 层 | 放什么 | 判据 | 今天在哪 |
|---|---|---|---|
| **基础能力（所有客户共用）** | 进线收口成一个人（identity）· 一条全渠道时间线 · 冷热分段 · 「今天该联系谁」排序 · AI 判阶段 + 写理由 · 记一笔 / 改阶段 / 别再联系 · 回私信 / 回邮件 · 多人同时改的保护 | 换客户、换行业都不用改 | 已有，且只有 1 处写死客户 id |
| **行业层（同行业客户共用）** | 阶段档位模板 · 该行业的「下一步该干什么」话术 · 行业特有字段（旅游=出行日期；地产=带看预约） | 换客户不改、换行业要改 | ⚠️ **键不可用**：`industry` 自由文本、17/29 为空。**先规范化，再谈行业层** |
| **客户层（这一家独有）** | **哪些渠道亮出来 + 哪个排第一**（CTS 邮件/电话 · NAL 只有私信）· **目标口径**（成交 vs 开聊数）· 额外列（感兴趣的团）· 成交后动作（CTS 同步表格 · NAL 回传 Meta）· 要不要同步 Google 表格 | 只服务一家 | 部分已有（阶段表 / 注册表 / leads_config），**渠道和目标口径还没落成配置** |

**一句话判据**：明天把 CTS 换成 NAL、再换成一个悉尼地产客户，**基础层这段代码要不要改？** 要改 → 说明它其实属于下面两层，必须下沉。

## 四、合并成一个板块

盘完 7 个界面（每条都有文件:行号依据）。先说两条跟 PM 判断不一致的地方。

### 4.1 🔴「客户消息」不是鸡肋 —— 它是「AI 出草稿、人只审批」的唯一落点

`messenger/page.tsx` 独有、别处**一个都没有**的能力：

| 独有能力 | 在哪 |
|---|---|
| **AI 草稿待批准面板**（verifier gate / confidence / 报价名核对 / 语义红旗，三按钮批准） | `messenger/_components/DraftApprovalPanel.tsx` —— **全仓唯一** |
| **需求卡 Brief** 全字段（想去哪 / 顾虑 / 我们承诺过什么 / 下一步 / 风险 / 意向强度） | `messenger/types.ts` —— 「我的客人」页只取了其中一个字段 |
| **24 小时回复窗口倒计时** | `replyWindow` —— 丢了会让人写完发不出去 |
| 4 个计数 + 4 个筛选 + 自动落到该看的队列 | `messenger/page.tsx` |

而且今日待办有**两条**任务指向它（`manual-items.ts` 的对话健康告警、`messenger-draft-items.ts` 的草稿待批）。

**删掉它 = 删掉 PM 自己 2026-07-28 拍板的那个产品形态（「一条待办流 = 查看 + 授权」）在私信这条线上的唯一实现。**

它看起来像鸡肋的原因我猜是：CRM 抽屉里也能回私信，所以感觉重复。但抽屉那边**只复用了发送框**（`MessengerReply.tsx` 头注明写「不新增任何发送能力，整块复用私信页那个 ReplyBox」），**草稿审批、需求卡、窗口倒计时一个都没有**。

→ **建议：不删。合并时把它当成「私信这条线的审批视图」收进新板块。**

### 4.2 ✅「决策清单」确实该退役 —— 而且它比你想的更没人用

- 它读的是**跟「今天要联系」完全同一个接口**（`/crm/today`），判据也是照抄（`decision-list.ts` 头注明写「照抄已经算好的桶」）。真实差别只有「去掉所有按钮 + 拍平布局」。**全仓最接近「同数据同展示」的一对。**
- **全仓没有任何入口指向它** —— 无工具卡、无侧边栏、无待办、无邮件链接。**只有已经在 CRM 里的人才点得到那个 tab，而那个人恰好不需要只读版。** 1 个月没动过。

但退役前要保住它的两样东西（不是功能，是约束）：
1. **「零写操作」这个定位本身** —— 给 PO / 非跟进角色一个不会误点的入口。合并后如果只剩带按钮的视图，这个角色就没有安全入口了。
2. **截断诚实提示**（每桶只回前 300 人，且「目前没有能看到全部名单的入口」）和**空态三分**（都处理完了 / 没到期 / 压根没数据）。这两条在合并后的板块里必须继续成立。

### 4.3 真正的重复是 PM 没点名的那一处 —— 两个「点开一个人」各缺一半

| | 「今天要联系」的抽屉 `PersonDrawer`（15KB） | 「全部客人」的详情 `ContactDetail`（15KB） |
|---|---|---|
| 回私信 / 回邮件 | ✅ | ❌ |
| ⭐ 重要标记 | ❌ | ✅（全仓唯一） |
| NAL 确认已成交 → 回传广告 | ❌ | ✅（全仓唯一） |
| 时间线渲染 | `ContactTimeline`（20KB） | `TimelineItem`（3.9KB）——**另写了一份** |

两份独立实现、各缺一半、时间线还各写一份。**`DncBanner.tsx` 的头注就是这个分裂的事故记录**：「它最早只长在『今天要联系』那页的抽屉里，而今日待办下发的人工任务 href 指向的是『全部客人』…FDE 照着任务点进去，页面上根本没有任务里说的那个按钮」。

→ **合并的第一刀应该切在这里**，而不是切「客户消息」。

### 4.4 顺手发现两个真问题（都不在 PM 的清单上）

1. **「我的客人」页对非地产客户是死页，但侧边栏对所有人都显示。** 那一页只在 `industry === 'real_estate'` 或有房源时才有内容，否则整页换成一段劝返文案；而侧边栏那个入口**不带行业判断** —— 所以非地产客户点进去必然扑空。（最老的一页，2026-08-02 之后没动过。）
2. **「待认领的 Facebook 消息」会混进不是 Facebook 的东西。** 那个接口只筛「还没认到人」，**没有筛渠道** —— 同一张表里认领不上的邮件 / WhatsApp 对话会出现在这一页，并被首页那个角标数成「Facebook 消息认不出是谁」。相邻两条路由都显式筛了渠道并留了注释警告这件事。

### 4.5 合并方案（一个板块，四个视图 + 一个共用的人物面板）

```
客户（一个板块，一个入口）
├── 今天做什么      ← 今天要联系（看板/列表）+ 决策清单退役后的只读模式
├── 全部客人        ← 横表 + 搜索 + 4 段分组 + 自定义列
├── 待回消息        ← 客户消息（私信 + 草稿审批 + 需求卡 + 24h 窗口）
│                     商务邮箱（邮件线程，只读）收成这里的一个渠道页签
└── 待认领          ← 陌生会话认人（保留，并修掉渠道没筛的问题）
     ↑
     └── 四个视图点开任何一个人，弹的是**同一个**人物面板（PersonDrawer 收口后的那一份）
```

**关键是那条「↑」**：先把两个「点开一个人」合成一份（4.3），四个视图才真的是同一个板块的四个角度，而不是四个各自长着半套详情的页面。

**22 条「合并时绝对不能丢」的能力已逐条列出（含出处）**，实现时按它验收。其中 10 条是**全仓唯一写入口**：新建客人 · 群发 BCC + 批量记一笔 · 认领陌生会话 · 推迟/叫回 · 「分错了」反馈 · ⭐重要标记 · NAL 确认已成交 · 取消「别再联系」· AI 草稿批准 · 人工发送。丢任何一条 = 那个功能在 ME 里就没有了。
