# 推广计划 → 每日计划槽位 · 设计稿 v0.1（只是设计，没写代码）· 116 号窗口 · 2026-10-15

**风险级**：A（碰批准链之后的执行链；本稿只设计只读的一段）。**只做 CTS、East Inter**。不新增能力线。
**来由**：18 号转 74 号的位置图结论——「推广计划要能真指挥执行器，不是更多页面」。排期先后：社媒 → 邮件 → 广告；社媒日常归 97 号，**我只负责「推广计划步骤 → 每日计划槽位」这一段**，97 管入口和发布。

## 0. PM 版（先看这里）
**现状（我查了库）：** 推广计划批了以后，没有任何东西被它指挥——它只会「看」。社媒每天做什么，是另一套每日计划（`campaign_daily_v1`，CTS 一共 4 份，最近一份 10-06）在管，两边互不相通。
**这一段做什么：** 让推广计划**每天知道每日计划有没有照它排**。计划里写了「每周 3 条帖子」，系统每天算出「这周应该哪几天发」，对照每日计划里实际排了哪几天，缺的那几天推一条待办给你：「计划里排了周一/三/五发帖，每日计划只排了周一，缺周三、周五」+ 怎么补 + 直达每日计划页。
**这一段不做什么（要先说清楚）：**
- **不替每日计划写内容、不写 `social_plans`。** 每日计划要求每个排上的日子都带完整草稿（标题 / 正文 / 行动语 / 图 / 链接），草稿要对着官网核实过——这是内容生成，不是翻译一下日期。这一步归 97 号那边的代理，**推广计划只给它「哪天、发什么类型、来自计划哪一步」这张清单**。
- 不碰发布；槽位只是「应该有」，不是授权；审核→授权→发布链原样不动。
- 不碰视频工厂；Reel 只给「哪天需要一条」，成片只能走工厂工单。

**为什么没人用（回答 18 号要的问题）：** 查到的事实——营销计划表 2026-05 建了 12 份、06 建了 18 份、08 只有 1 份，**09、10 月 0 份**；批准过的一共 9 份；CTS 的每日计划 4 份、最近 10-06。**原因我没法从库里证明**，只有三个未验证的猜测：①计划页是「人填表」，没人愿意填（所以第一刀改成 AI 起草）；②计划批准后什么都不会发生，用了没回报（所以本稿让它开始「盯着」每日计划）；③社媒日常转到每日计划页去做了。这三条要等 PM 或 97 号确认，我不假装知道。

## 1. 设计
### 1.1 纯函数：计划槽位清单 `promoSlotProposal(spec, playbook, fromDate, days)`
- 复用已有的排期表函数 `expandPromoSchedule`（S4a 已上线），取其中 `post / story / reel` 三类，输出 `[{ date, slots: {post, story, reel: 'EXPECTED'|'NONE'}, refs: [{ kind, phase_id, step_id }] }]`。
- **只带类型标记和 `promo_ref`，不选曲、不写文案、不带价格**（97 的放行规则、文案红线都在它那边；本函数不碰）。
- 日期口径：账户时区的「今天」起往后 7 天（沿用 `resolveToday`）；读不到时区 → 不给清单并写明原因（不按 UTC 悄悄算）。

### 1.2 缺口检测：读每日计划，对照
- 读 `social_plans` 里该客户最新一份 `campaign_daily_v1`（**只读**）：每天三个槽位的 `PLANNED / NOT_PLANNED`。
- 对照结果分四种，**必须分开说**：
  1. 计划有、每日计划也排了 → 不出声；
  2. 计划有、每日计划**没排**（或排了但没有对应草稿）→ **缺口**（出待办）；
  3. 计划没有、每日计划排了 → 不管（每日计划可以比计划多）；
  4. **每日计划读不到 / 没有这份计划** → 「没读到」，**不能当成「全是缺口」也不能当成「没缺口」**，单独说原因。
- 只对「已批准、已开始的计划」检测；草稿不检测。
- 价格屏、BGM 等 97 的放行规则**本函数不判**，只给类型。

### 1.3 出口
- 把缺口作为 `daily_plan_gap` 类发现，进现有的「推广计划每日检查」（PR #2701）回执与今日待办——**同一条管道，不新建**。待办三件套：what（缺哪几天哪类）/ how（打开每日计划页，让代理按计划补草稿；只产草稿，仍要你审核授权才会发）/ href（每日计划页）。
- 新增只读接口 `GET /api/clients/[id]/marketing-plan/[planId]/promo/slot-proposal`（内部账号，只读）：返回 1.1 的清单，供 97 号的代理 / 入口直接读。**不写 `campaign-daily-plan` 的任何文件**（97 已声明那是它的）。

### 1.4 数据口径（74 号清单的硬规则，本段适用的部分）
- 每格带「业务日期」和「读取时间」；读到 0 不当成没排——区分「真没排 / 读不到 / 本来没接」。
- 邮件已发数、自动发图文帖尝试数、社媒读数链的「未接通」展示，**不在本段**（它们属于对账行，另一段）。

## 2. 不做 / 以后
- 不写每日计划、不生成任何文案图片视频、不调用任何生成服务。
- 邮件（只能出人工任务卡）、广告（开投只认 PM 本人）是排在后面的两段，本稿不设计。
- S4b「计划变成真任务」仍不做（前置条件仍未满足，见 `2026-10-14-promo-plan-s4-after-approval-design-v0.1.md` §8）。

## 3. 风险与应对
| 风险 | 应对 |
|---|---|
| 把「应该有」误当成授权 | 清单类型是 `EXPECTED`，不是 `PLANNED`；文案固定写「只产草稿，仍要审核授权」 |
| 每日计划读不到被当成全缺口，刷屏 | 读不到单独一类发现，且走现有降频 |
| 每日计划按 7 天整份覆盖，覆盖即清空审核 | 本段只读，不写；提示里不引导绕过 POST |
| 与 97 的文件冲突 | 只动 `src/lib/marketing-plan/promo/`、`pm-todo/`、一个新只读路由；不动 `campaign-daily-plan/route.ts`、`lib/campaign/daily-plan.ts` |
| 平台化 | 共享代码不出现客户名 / 行业词；CTS 规矩（全英文无倒计时、价格闸）在 97 那一层，不进本函数 |

## 4. 当场试跑计划（no_publish）
对 CTS 真实每日计划（只读）+ 内存里的一份已批准计划：算出本周槽位清单 → 与真实每日计划对照 → 生成一条真实缺口待办；读不到每日计划的分支用假库验证。不写任何库。
