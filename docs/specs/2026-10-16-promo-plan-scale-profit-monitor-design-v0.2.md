# 推广计划页「利润监控（只读）」设计 v0.3 · 116 号 · 2026-10-16（已吸收子牙、魏征各两轮审查意见）

- 状态：**设计稿，PM 点头前不动代码**。风险级 **B**（页面 + 只读纯函数 + 一段服务端写入的客户配置；无数据库迁移、无新接口、无新定时任务、不写 Meta）。§11：频率 中 / IMPACT 高 / 收入 中 → **P2**。平台层级：既有「广告」支柱 L1 的扩展，不新增能力线。
- PM 方向（2026-10-16 原话）：「并没有目标倒推这个逻辑，而是更注重在增大规模的同时，保证利润，监控广告预算。」**不做**目标倒推。加预算只认 PM 本人（RL-02）；本页**不构成加预算授权**，页首固定一行写明，文案禁止出现「可以加 / 建议加 / 有空间」，单测扫这些词。

## 1. 三个问题（只读，推广计划页首屏一块；读不到写「没读到」，不当 0；每格带业务日期 + 取数时间）
1. **每座广告成本 C，同时显示两个窗口**：「累计」（自 `since` 起）与「最近 28 天」，各自带座位数；C = **campaign 级**花费 ÷ 同期新增订单**座位数**，两侧按**同一个截止日（两边最新日的较小者）**一起截断；并列显示按订单数的口径。`since`（默认 2026-08-14）是**花费表的数据起点，不是广告投放起点**（0624、0707 的广告更早），页面和每个 C 都带这条注释。**提醒一律取两个窗口里更差的那个。**
2. **每座留存 R（盈亏线）**：近期成交团官网加权价 ×（毛利率 − 销售佣金率）。Sales 纯佣金制：无固定人工，佣金是变动成本，每座贡献 = R − C。**v1 的 R 一律按「Sales 成交 10%」算，是保守下限**（公司直接成交 20% 的单没有渠道来源可分，等有来源再拆）。
3. **余量 = R ÷ C**（两窗口各算一个）；先行指标另列：CPL、线索到订单率；**边际成本要求相邻两个窗口各自 ≥ 12 座才显示**，否则写「样本不足」。

**判不了的条件（任一成立，该窗口的 C 与余量写「判不了」+原因，不给数）**：**已填座位数**（只数 `party_size` 已填的，不含空人数的推算上限）< 12（暂用，待 PM 定）；分母 0；花费或订单任一侧没读全；**花费最新日距今 > 3 天**（比一本账的 7 天严；按今天 10-16、花费停在 10-10 的实情，这一块今天会显示「判不了：花费数据停在 10-10」，这是对的，说明要先把 Meta 花费拉取补上）；毛利率 / 佣金率没配置；成交周期无配置（现状：`SALES_CYCLE_DAYS_NOT_STORED_YET`，全库没存，**v1 不做滞后对齐**，只用上面「同一截止日」截断，已删除原稿「复用 salesCycleDays」一句）。

## 2. 数据口径（审查中逐条核过的事实标来源）
- 花费：`ad_daily_insights`，**写死 `level='campaign'`**（表里 campaign/adset/ad 三级并存，不过滤会翻 3 倍；单测造三级数据要求得数不翻倍），并按 campaign 名排除 CTS 账户里已知的 Oztop 遗留广告。读取**扩展 `promo/facts.ts` 的 `loadInsights`**（已带新鲜度、覆盖度规则），不新写读表；NZD，两账户合计，币种/时区读不到就判不了。数据库实况：花费到 2026-10-10。
- 订单：`crm_bookings`，`status='active'`，座位数 = `party_size`。**`party_size` 为空的单**（线上 22 张有效单里 6 张，最近三张全空）：单独计数并显示「X 单没填人数」；C 给**区间**（下限按已填人数，上限按每单 1 座），区间太宽判不了；**所有提醒一律取最坏端**（C 取上限、余量取下限），页面显示整个区间；**禁止补默认值**。取消单排除。已知偏差**方向不确定**（重复客人第二单被算新增；退订在窗口之后；无渠道来源全算广告；订单是 10-12 至 10-14 集中补录的），页面写「偏差方向不确定」，不写「偏悲观」。
- 价格：v1 读团目录价；**目录从未发布，且与官网是两个来源**；页面显示「最后与官网对账日期」，对不上则告警，不静默混用（PM：以官网为主）。
- 配置：毛利率、佣金率放 **`marketing_plans.generation_meta.economics`**（客户配置，非共享代码）。**不放 `plan_data`**（子牙审出：通用 PATCH 整块替换 `plan_data`，会冲掉它，且客户员工有权限改）。`generation_meta` 里已有服务端写入先例 `promo_checks`；通用 PATCH 不碰它，退回草稿路径只摘掉 approval_receipt / promo_checks / weekly_reviews 三项，其余保留。v1 由 FDE 服务端写入，不开接口、不做编辑界面；**写法约束**：只对 JSON 做局部合并（只设 `economics` 一个键，如 `generation_meta || jsonb_build_object('economics', …)`），写完立刻读回，确认 `approval_receipt` 等原有键仍在（整块替换会让已批准计划被判「批准后内容被改过」）；并把 `economics` 加进 `types.ts` 的 `generation_meta` 类型。**取用规则**：配置挂在计划上，但按客户取：「已批准优先，否则最新草稿」那一份；同一客户多份计划的值不一致 → 判不了，不挑一份；新建计划不会继承旧计划的 `economics`，FDE 要重写，没写时待办提示。没配置 → 判不了，不用默认值。CTS 值：毛利 20、佣金 10（PM 2026-10-16 原话）。
- 成交率基线 2.6%（19/733，74 号样本，数据到 10-03，老板亲自跟进时测的）：Sales 接手后单独统计，线索数 < 下限时写「样本不足」。

## 3. 提醒（进已有每日检查，不新增函数；按**客户**去重）
- 新增码：`unit_cost_near_breakeven`（余量 < 1.3，**连续 3 个待办运行日**才报，页面显示当前阈值；连续天数沿用现有机制，从历史**每日检查回执**数，不重算历史（订单是补录的，重算不稳），按「客户 + 码」；**迟滞**：余量回到 ≥ 1.4 才清零，避免 1.02/0.99/1.01 来回清零）、`unit_cost_over_breakeven`（余量 < 1，**待办跑的每一天都报，不套 `shouldRemindToday`**；待办周五周六不跑，这两天的亏钱信号周日补报，不是日历日每天）、`conversion_below_baseline`、`marginal_cost_rising`、`profit_inputs_unreadable`。阈值、样本下限均「暂用值，待 PM 定」。
- 不放在每份计划各自的检查里（会按 `plan_id` 重复报，且被「推广结构读不出来」的早退吞掉）：改为 `runPromoPlanWatch` 里**每个客户只算一次**的独立函数，放在早退之前；失败只回 `profit_inputs_unreadable`，**不抛错、不拖垮计划检查**。**可注入**：`runPromoPlanWatch(supabase, now, { buildProfit })`，默认实现读库；现有三个 watch 测试文件**不改断言**，传一个返回空的桩（现有假数据库对所有表名返回同一份计划行，新函数不能直接用它）。**锚点**：回执里盈亏条目的 `plan_id` 固定取「配置所在的那份计划」；连续天数在 `promo-plan-watch-items.ts` 的 `streakOf` 里按「客户 + 码」计，不按「计划 + 码」，计划换 id 不清零。
- 归类：`profit_inputs_unreadable` 是我们这边的欠账，分流到 `promo_plan_watch_broken`（开发栏，不占 PM 清单）；亏钱类走 PM 栏。
- **文案与版面（防被读成加预算授权）**：块标题叫「利润监控（只读）」，不叫「放量」；页首固定一行「本页不构成加预算授权，只认 PM 本人」；**不出现绿色 / 「健康」「安全」「充足」**；没有提醒时写「未触发提醒，不代表可以加预算」；提醒的 how 只写「去广告账户核对 X」，不写「减 / 加 / 暂停」；亏损类文案固定为「按最保守的分成算，余量 X」，不写「亏损」；本块与「批准计划」入口隔开，不相邻；禁词单测扫：可以加、建议加、有空间、放量空间、安全、健康、充足。
- `PromoBoard` **不改必填字段**；盈亏块由独立函数 `buildProfitMonitor` 提供，页面读取时附带（可选字段），**不进 acknowledge 路由**。读订单失败只让这一块判不了。
