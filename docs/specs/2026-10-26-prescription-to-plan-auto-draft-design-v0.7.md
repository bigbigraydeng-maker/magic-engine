## 0. 先说结论
1. **流程**：处方批准成功 → 发一个业务可读的 Inngest 事件 `prescription.approved.plan_draft.requested` → 后台函数用第一刀的构建器出「种子」→ 映射成一份 `promo_v1` 计划草稿（**未批准**）→ 写回执 → 处方页显示草稿链接与状态。
2. **批准永远先成功**：生成放在批准**之后**的异步事件里；生成失败只落「机器可读回执 + 一条人话提示 + 重试入口」，**绝不回滚、绝不拖住批准**。
3. **同一份处方的同一版本只生成一份**：幂等键 = 处方 id + 版本，存 `marketing_plans.generation_meta.from_prescription`（不新开表、不入指纹，v0.6 §1.11）。
4. **广告 Agent 要的字段要齐**：受众、预算分配、素材引用、排期。所以**第二刀（受众 / 素材 / 起止日）并进主线**，不能只出账户 + 日预算（§4 重排刀序）。
5. **PM 只点「同意」和「开投」两下**：现在是四下（批处方、批素材、批计划、开投）。§6 给出收敛方案，但那是**授权语义的改动，写作「待 PM 拍板」，本稿不替他定**。

## 1. 触发与流程（推翻 v0.6 §4–§5 的显式按钮）
```
PM 点「批准处方」──(同步，照旧成功)──► approve 路由
                                         └─ 成功后 fire-and-forget：send 事件
                                            prescription.approved.plan_draft.requested
                                            data = { request_id, client_id, prescription_id, version, requested_by:'approve' }
Inngest 函数 plan-draft-from-prescription（concurrency limit 1，key = prescription_id）
  1) 门：处方已 approved、是广告类、有 ad_plays、目标有周期；否则写回执 status='skipped' + 原因
  2) claim：读 marketing_plans 里 generation_meta.from_prescription = (prescription_id, version) 的草稿；已有 → 回执 status='already_exists'，结束
  3) buildPlanSeed（第一刀 + 第二刀字段）→ 映射 → parsePromoSpec 校验（与 PUT /promo 共用同一个校验函数）
  4) 插入 marketing_plans（status='draft'，generation_meta.from_prescription = { prescription_id, version, request_id, seed_fingerprint, generated_at }）
  5) 写回执 status='created'，plan_id
失败任一步 → 回执 status='failed' + reason_code + 人话原因；不抛给批准路径
```
- **事件名**业务可读；**每个关键阶段有机器可读回执**（CLAUDE.md Inngest 硬约束）：回执字段 = `request_id、client_id、prescription_id、version、status(skipped|already_exists|created|failed)、reason_code、plan_id?、cost/provider 影响（本函数只读 Meta：Graph 读次数）、no_publish=true、authorization='none'（草稿不带授权）、created_at`。
- **no_publish / authorization**：回执里固定写 `no_publish: true`、`authorization: 'none'`，函数里没有任何发布、扣费、Meta 写入、客户可见外发的代码路径（fail-closed 靠「根本没有这个出口」，加测试：函数源码不 import 任何 Meta 写入模块）。
- **事件发送本身失败**（Inngest 不可达）：approve 路由 catch 后仍成功返回，并把「事件没发出去」写成回执 `status='failed' reason_code='event_not_sent'`（回执落点见 §3），处方页给重试入口。
- **回执落点（技术待核，不上抛 PM）**：优先复用现有账本表 `flywheel_actions`（`ads.create_ad` 已在用，payload 存 jsonb），新增一个 action 类型 `ads.plan_draft`；**需先核对该表有没有对 action 取值的检查约束**——若有约束，要改约束 = 迁移，则退而用 `prescriptions` 行上已有的 jsonb 字段存最近一次回执（只存最近一次，历史靠 Inngest 运行记录）。无论哪种，PR 正文必须写明实际落点。
- **不用 Inngest 的例外**：无。这是「批准 → 异步生成 → 回执」，正是硬约束点名的场景。

## 2. 幂等与防重复
- 键 = `(prescription_id, version)`；`generation_meta.from_prescription` 存键 + 种子指纹（规范形，v0.6 §5）。
- 三层防线（一层都不单靠）：① Inngest 函数 `concurrency: { limit: 1, key: prescription_id }` 串行；② 事件去重 id = `prescription_id:version`；③ 函数第 2 步的读库判重。**已知限制**：没有数据库唯一索引，三层都过了仍有理论上的竞态（两个不同 Inngest 区域同时认领）；**可选加固**是给 `generation_meta->'from_prescription'` 加一个部分唯一索引——那是迁移，按边界由 PM 亲手合，本稿默认**不做**，上线后看回执里 `already_exists` / 重复率再决定。验收要真跑「连点批准两次」看只生成一份。
- 处方改版（version+1）、旧草稿已批准时的行为，照 v0.6 §6：新版本生成新的草稿（键不同），**不覆盖已批准计划**；「改版草稿会顶掉已批准计划」（`pickPlanForPrescription`）问题**必须先修**（§4 的 plan-pick 小刀，先决）。
- 人改保留：同版本重试（失败后重试）只会走「还没有草稿」的分支；若草稿已存在且被人改过，**不覆盖**，回执 `already_exists`。

## 3. 失败与重试（PM 看到什么）
处方页（`prescription/new` 与计划页处方卡两个面，沿用第一刀的共享组件位置）新增一块「广告计划草稿」状态，大白话：
- 生成中：「正在根据这份处方起草广告计划草稿……」
- 已生成：「已生成一份**未批准**的广告计划草稿（点这里查看）。草稿不等于批准，开投仍要你本人点。」
- 跳过：「没有生成：这份处方没有填广告打法」（附原因）。
- 失败：「草稿没生成成功：<人话原因>（不影响这份处方已批准）」+ **[重试]** 按钮（POST 同一个路由，重发同一事件；失败的回执不算「已完成」，所以重试合法）。
- 状态读自回执（只读），不在面板里做任何阈值算术（第一刀守的规矩）。

## 5. 先决问题：处方页面板显示哪一份种子
第一刀的面板读「页面现算」（只读）。自动生成后，处方里会存档一份 `content.plan_seed`（写处方时的快照）。**建议口径**：面板显示**存档那份**并标「按 X 点的数据生成」，旁边给一个**只读**的「按当前数据重新算」按钮（现算一份仅展示，不写库、不覆盖存档）。理由：PM 看到的数字必须是草稿里实际用的那一份，否则「页面 $25、草稿里 $50」会让人以为系统在骗人。这是技术口径，由第二刀开工前确认，不上抛 PM。

## 6. 【待 PM 拍板】把四下点击收敛成两下（授权语义的改动）
现状：PM 要点四次——批处方、批素材、批计划、开投。目标：只点「同意」和「开投」。统管 74 的初判是两处合并，**本稿只列方案和风险，不替 PM 定**：
- **A. 取消「批素材」**：素材走审查 agent（生产方与质检方必须是两个不同角色，苏东坡/马良审）的结论自动入 creative_pool。风险：这去掉了一道人工授权，素材将被用于花钱投放。**保护条件（若采纳）**：只有独立审查角色给出的「通过」结论才入池；池里每条素材记「谁/什么时候/哪份审查结论」；「开投」那一下 PM 仍然看得到素材；审查没通过的素材绝不入池；工厂产出方自己写的「没问题」不算。
- **B. 「批处方」与「批计划」合成同一个确认**：处方页上显示草稿计划的摘要（账户、日预算、受众、素材、起止日），一个「同意」按钮。**两条授权记录仍各自独立落库**——各自有「谁、何时、哪个版本（含内容哈希）」，不合并成一条模糊记录。风险：PM 点「同意」时看的是处方还是计划？**保护条件**：按钮文案写死「同意以上处方和广告计划草稿（不包含开投）」；批准绑定**计划草稿的版本哈希**，草稿在点击后被改动则授权作废；若草稿没生成成功，只显示「批准处方」（单独一条授权），不出现合并按钮；**10-19 事故**（PM 点了两个「我已核实」以为是批准）是反向教训——一个按钮写入多条授权必须在文案里逐条列出。
- 以上两项都**不**改变：开投只能 PM 本人点；agent 不得代点；批准不等于花钱。
- 需要 PM 在这两项上各回「采纳 / 不采纳 / 改」；**在他回话前 S5 不开工**，S1–S4 不依赖它。

## 7. 与边界的关系
本稿的功能**自己**会写一张产品表（`marketing_plans` 的草稿行）——这是产品的正常写路径，不是开发窗口改生产数据；开发与验收阶段，窗口**不动生产数据、不动 Meta 账户**：试跑一律 dry_run；真写入要 PM 一句话。A 级与带迁移的 PR 由 PM 亲手合；P0 审（碰批准路径）交 Codex。

## 8. 验收（PM 能自己验的）
1. 批准一份新的广告处方 → 几秒内处方页出现「已生成未批准草稿」+ 链接，打开是计划页的草稿，账户/日预算/受众/素材/排期每个字段带依据或留空原因。
2. **连点两次批准（或重复事件）→ 仍只有一份草稿。**
3. 人为让生成失败（只读演练：关掉某个依赖）→ 批准照常成功，处方页显示失败原因 + 重试，点重试后生成成功。
4. 草稿必须能被 PUT /promo 原样接受；生成→保存→重读→指纹相等。
5. 全程没有任何 Meta 写入、没有预算授权记录被写、没有自动批准。

## 9. Reuse Statement
