## 0. 给 PM 的一页话

**你定了什么（2026-10-29）**
1. ME 管得到的发信路径（触发型邮件、短信），每一封都由 ME 决定「发不发、发给谁、发什么」；服务商只当发信通道，不再让对方后台里长出会自己发信的流程。定期 newsletter 仍在 Mailchimp 里发，靠发前闸和巡检盯着（126 号手册）。
2. 欢迎信、行前通知、感谢信这类「触发型」邮件：ME 决定、Resend 发。**第 2、3 次跟进邮件仍由销售点发送**（127 / 129 号设计，不变）。
3. 短信：另配一家服务商，首选 ClickSend（价格公开、能直接在后台申请），谈不拢再换 Twilio；这个选择我来定。短信两类用途：**第一批 = 行前（服务类）**；**第二批 = 营销**——发给潜在意向客户（你选了**放宽**口径：明确同意的人，加上最近咨询过、自己留过手机号的人），短信带链接，点开后填表单或直达指定网页（你 10-29 追加，§4.14）。
4. 定期 newsletter：继续用现成引擎（现在是 Mailchimp），**不自己做**；等触发型邮件跑稳后，拿一封真实 newsletter 免费试 Resend 自带的群发，够用再迁。

**为什么这样**：这次一位客人一天收到两封欢迎信，根子不是 Mailchimp 不好，而是「两套自动发信各发各的、互相不知道」，而且 ME 看不到谁收了什么（退订也要隔天才同步一次）。换成另一个全家桶，发信规矩还是散在对方后台里，很可能再来一遍。让 ME 做唯一的决定者，才是「绑得紧」。

**阶段 2 前我会单独问你的两件事**（现在不用答）：
- **常设授权**：触发型邮件每天可能有很多封，不可能每封等你点。我想让你本人授权「一类信 + 触发条件 + 每日上限 + 有效期」，条件一变（哪怕改一个字）就自动作废、系统停发。这比 126 号手册默认的「每次发送都要你本人点头」宽，所以必须你亲口定；先例是已经在跑的「自动安抚回复」（由你按客户开关）。
- **首日只发哪一封**：129 号 SOP 定的是「第 1 次当天只发 1 封，替代自动欢迎信」；这份方案保留 ME 自动欢迎信。两个同时开，新线索首日就收 2 封，吃满 7 天额度。要你定留哪个。

**时间**：短信是最长的一根线——新西兰要先申请「专用短号码」（运营商认的 4–6 位短号，不是普通手机号），官方页面写 4–6 周。邮件部分分 5 个阶段（§5），每个阶段都要你说「开始」才动。

**覆盖面很小，也赶不上近期的团**：CTS 在 ME 里有 26 个有效订单，其中只有 9 个有手机号；最近的团 11/03 出发，短号码最快 12 月初才下来，赶不上；用得上的是 2027 年 3 月起的团。

**钱**（详见 §6）：Mailchimp 不变；给客户发信另开一个独立的 Resend 账号（免费档起步，必要时 US$20/月）。短信每个要发的客户：号码开通费 NZ$65 起 + 月费 NZ$65 起（ClickSend 公布价，实际以他们报价为准），另按条收费（我没核到官方单价）。

**风险**（要你知道，不是要你现在决定）：
- **Resend 的条款要求收件人「明确同意」**，而 Facebook 表单留资用的是「勾选退出」式（表单上有「我不要收邮件」）。Mailchimp 现在发的也是这批人，但 Resend 是否认这种同意，只能在实际发信中看出来——所以客户发信用独立账号，免得连累 ME 自己的系统邮件。
- 短信：营销类必须先有客人同意；新西兰供应商说服务类不用事先同意，但 Twilio 页面说发送前都要取得同意。**我们按更严的来**，第一期服务类短信也只发给有明确联系依据的人。客人回 STOP，要在 10 分钟内处理。**营销短信（你选了放宽）有法律风险**：新西兰要求营销短信有同意，「最近咨询过、留过手机号」算不算默示同意，我没读法条原文，也要看 ClickSend 肯不肯接受（他们的页面写「必须能证明客人 opt-in」）。所以发之前必须先问清法务和 ClickSend（问题清单见 §7-7）；申请短号码时同意依据必须如实写，不能写成「客人都勾选过同意」；任何一方说不行，我就退回严格口径。
- Resend 群发有硬线：退信率要低于 4%、投诉率要低于 0.08%，超了账号可能被无预警关停（§4.9）。

**要你（或 CTS 同事）动手的事**——开户必须你或 CTS 本人做；提交表单、改域名设置需要你明确点头，并建议由本人操作（涉及公司注册信息）：
1. **用途已定**（你 10-29 回「行前」）：已付款客人的行前通知和预订确认，服务类、不带促销。
2. **让 CTS 在订单确认邮件里补一句短信说明**（CTS 销售 / 负责人）：英文原文已写在申请材料第 5 节，可直接复制。不补的话，申请和之后发短信都缺「客人同意」的依据。
3. **在 ClickSend 开户并提交新西兰短号码申请**（你或 CTS 负责人本人）。申请材料草稿我已备好：`docs/clients/cts/2026-10-29-nz-short-code-application-pack.md`，空着的是公司注册信息等只有你们知道的内容。入口：ClickSend 后台 → Global Sending，官方说明 https://help.clicksend.com/en/articles/43924-new-zealand-64 。
4. **阶段 1 前**：为客户发信新开一个独立的 Resend 账号（ME 现有那个继续只发系统邮件和外联）。
5. **阶段 2 开工前**：问清谁管 CTS 域名的解析记录，把 Resend 后台给出的几条记录加进去。其中 SPF 是域名里声明「哪些系统可以代表我们发邮件」的一条记录，只能有一条，要与现有的合并、不能覆盖，否则现在的发信会坏。
6. **营销短信之前**：先问清法务和 ClickSend（问题清单见 §7-7）；官网表单和 Facebook 表单也要加一句「同意收短信」并留证，逐步把默示同意换成明确同意（官网表单由官网仓库的窗口改；改正在投的 Facebook 表单要先通知广告总控窗口）。

**现在没有要你回答的问题。** 你选了营销短信「放宽」口径（风险你担）：我加了三条护栏，发之前必须先问清法务和 ClickSend（问题清单在 §7-7，你转给律师或 CTS 的法务顾问即可）。你确认订单确认环节没有短信说明，已记成待办，CTS 要补一句话（英文原文在申请材料第 5 节）。

## 1. 层级判定（me-platform-tier-gate · Full）

- **被判定对象**：ME 对外发邮件和短信的「通道」——邮件走 Resend、短信另配一家，加上让两者共用的触发型发送编排（关口、授权、账本、回传）。
- **建议层级**：**两个 L3 Connector**（Resend 适配器、短信适配器）+ **一段新增的共享编排代码**（触发型发送：规则触发、常设授权、先写账本再发）。编排属平台治理基础设施，**不是新 L1 / 新支柱**：它不新增「判断」能力，只把已有的发信闸做法（`sendMailNew`）与自动发送先例（F1 自动安抚）用到「规则触发」这个新场景。
- **不是「接上现成总线」**：`messaging/channels.ts` 没有任何生产调用方（ROADMAP Phase 24.M 的 M3 一行明说；`channel-dispatch.ts` 头注释也写刻意不接它），本方案不依赖它；要不要把新编排挂进去，阶段 2 实现设计时再定（零调用方，改接口无兼容成本）。
- **归属**：不新增支柱。邮件渠道沿用 ROADMAP 2026-09-08 的判定（补齐已有策略层缺的邮件渠道）；短信 = Phase 24.M 的 M9（此前写「优先级靠后，PM 明确」，PM 2026-10-29 提前）。
- **换客户测试**：✓。客户 1（物流、新西兰，如 NAL）：欢迎信文案与触发规则不同 → 客户层模板与配置；静默时段、频次上限、消息类别读客户配置，共享代码不改。客户 2（地产、澳洲，如 Roman）：短信发件名走 ACMA 登记而不是新西兰短号码 → 适配器的国家规则差异，共享编排不改。
- **换行业测试**：✓。旅游 → 地产：「行前通知」是旅游行业模板，进 Industry Playbook 候选，不进共享代码；旅游 → 物流：欢迎信换成「报价已收到」确认信，只换触发规则与模板。
- **智能层 or 执行手**：发送是执行手（Connector）；关口、授权、对账是治理层。
- **红线**：1 ✓ 不包装新能力线；2 ✓ 客户名与数字只在客户配置和模板（L4）；3 ✓ 不直建 L1；4–5 见上两条；6 不适用（非 L1）；7 ✓ 单客户事实不进行业层。
- **PM 待拍板项**：无新支柱 / 新版本；商业口径 = 短信第一批用途、短信费用谁出、常设授权放宽、首日只发哪一封（§11-B）。
- **结论**：原本想法「找一家和 ME 绑得更紧、能发短信的服务商」→ 判定：**不换全家桶**；L3 适配器 + 新增触发型发送编排（复用三条真在用的发送路径的做法）。无 L1 候选，不登记候选表。

## 4. 设计

### 4.1 四条原则
1. **决定权在 ME**：ME 管得到的每一封信、每一条短信发出前都过同一个关口并**先写账本**；供应商后台不得出现会自己发信的流程、脚本或定时任务（由 126 号手册 NL-05 / NL-18 巡检发现）。Mailchimp 网页里手动发 newsletter 不在这条之内，靠发前闸与巡检盯着。
2. **供应商可换**：供应商只实现适配器接口；名单、同意、退订、发送账本、频次计数都在 ME。
3. **宁可少发，不重发、不错发**：所有闸 fail-closed，读不到数据按「不通过」；状态不明保持 pending（沿用 `sendMailNew` 语义）。
4. **现成的事用现成引擎**：newsletter 管理继续用 Mailchimp，ME 只管「谁能收、什么时候能发」，**不自建 newsletter 管理**。

### 4.2 谁发什么

| 类型 | 例子 | 谁决定发不发 | 谁发 | 状态 |
|---|---|---|---|---|
| 触发型邮件 | 新人欢迎信（与 129 的「第 1 次那 1 封」合并方式待 PM 定，§11-B）、行前通知、回团感谢信 | ME（关口 + 常设授权） | Resend（经 ME 适配器） | 本方案 |
| 销售点发送的邮件 | 通话后模板邮件、第 2 / 3 次跟进（127 / 129 号设计） | 真人 + 关口（`sendMailNew`） | 员工邮箱（Outlook / Microsoft Graph） | **不变**，在飞 |
| 短信 | 第一批：行前通知、预订确认（服务类）；第二批：营销短信（发给潜在意向客户——放宽口径：明确同意的人 + 最近咨询过的人；带链接，点开填表单或直达指定网页） | ME（关口 + 常设授权） | 短信供应商 | 本方案（阶段 3 / 3b） |
| 定期 newsletter | 春季团 newsletter | 人 + 发前闸（126 号手册） | Mailchimp | 不变，不自建 |
| 私信 / WhatsApp | 客人先来信之后的回复 | 真人 / F1 自动安抚 | Meta / WhatsApp | 不变 |

### 4.3 总体流程

```
触发（新线索进库 / 行程节点 / …）
   │  去重键 = (客户, 触发名, 联系人, 去重范围)  ← 欢迎信「终身一次」，行前通知按出发班期
   ▼
发送关口：开关 → 授权 → 收件人 → 别再联系 → 同意依据 → 历史欢迎检查 → 静默时段 → 抢联系人锁
   │ 不通过 → 写 blocked(原因)，该出待办的出待办
   │ 锁内：频次（跨渠道）+ 去重键唯一插入 → 先写 pending
   ▼
适配器：email → Resend（Idempotency-Key = 去重键）｜ sms → 短信供应商
   ▼
供应商回调（限长读体 → 验签 → 存原始事件 → Inngest）→ 状态表更新；每封信只写一条出站触点
   ▼
CRM 抽屉 / 频次计数 / 每日对账（供应商实发 vs ME 状态表；回调丢失用定时拉取兜底）
```

### 4.5 授权：常设授权（有界自治），不是 NL-14 的逐次授权

126 号手册 NL-14 规定发送类动作一律档 3：授权记录由登录身份的审批接口写入，绑定（内容指纹 + 收件分组 + 人数 + 发送时间），内容改了授权作废，默认只演练（手册 L115）；内核 v1 明确不放行不可逆外发（`kernel/outward-authorization.ts:116-122`）。**本方案要的「常设授权」比这更宽，是一次有意的放宽**，必须 PM 亲口定（§0、§11-B）。先例：F1 自动安抚——「唯一不经人工审核直接自动发送的路径」，由 PM 按客户开关；它的模板是硬编码、不读客户事实，因为读了事实就等于绕过双签闸。

触发型发送每天可能有很多封，不可能每封都让 PM 点。做法：PM 本人授权的不是某一封，而是一组绑死的条件：

`客户 + 触发规则 + 受众规则 + 渲染后模板的指纹 + 每日上限 + 有效期（缺省 90 天）`

- **任何绑定项变了**（改了一个字、换了触发规则、改了受众规则、过了有效期）→ 授权立即作废，系统停发并出一张拍板卡；
- **撞到每日上限**不作废：当天不再发，排到次日并出一张提醒卡（上限是闸，不是授权条件）；
- **模板里的团名、价格、日期是客户事实**：授权只绑模板指纹，不绑事实新鲜度。所以必须有每日事实对账（126 号 NL-02）；对不上 → 该模板的授权自动暂停；
- 没有有效授权 → 不发（fail-closed），状态表写 `blocked / no_authorization`；
- 授权只能由 PM 本人通过登录身份的审批接口写入；「状态字段 = 已授权」「别的窗口转述 PM 同意」都不算（126 号手册 §4）；
- 默认只演练（影子模式，§4.11）：先只写「本该发给谁」，不真发，PM 看完对照结果再授权真发；
- 与 126 号 WP5（newsletter 逐封授权）共用同一种授权记录**形状**（范围一个是「一封」、一个是「一组条件」）。**先与 126 对齐，再动手实现**（§10）。

### 4.6 发送关口（顺序；任何一步读不到数据都按「不通过」）
1. 开关 / 客户配置有效（**严格解析，坏值 = 关闭**；不用 `leads_config` 那种坏值回落默认的读法，`email-compose/config.ts` 的 `readLimit` 就是回落默认）；
2. 授权有效（§4.5，指纹一致）；
3. 收件人有效（邮箱 / 号码格式、号码统一成国际格式；不是系统或自动发件地址）；
4. 别再联系（ME 的联系人标记 + 供应商侧抑制名单；沿用 `manual-send-dnc-gate` 的 fail-closed 做法）；
5. 同意依据（按消息类别与来路；记下依据，如 `form_disclosure_attested`；§4.8）；
6. **历史欢迎检查**（仅欢迎信）：任何一条路径欢迎过他就不再发——ME 状态表 ∪ Mailchimp 的 `auto_e1_batch_*` 标签与欢迎邮件收件记录。表格脚本只看自己表格里的「E1 已发」列，**ME 发出的人不在那一列**，所以必须由 ME 去查；
7. 静默时段（短信；缺省收件人当地 9:00–20:00，读客户配置）；
8. 抢联系人锁（沿用 `acquireContactLock`）；
9. **锁内**：频次（PM 口径：同一客人 7 天（168 小时滚动）最多 2 封邮件，含群发、含一对一、含欢迎信；来源并集宁多勿少，读不到按已满）+ 去重键唯一插入（已有则直接返回，不再发）；短信另设上限（读客户配置，建议值：营销类每人每 7 天 1 条；服务类每个事件 1 条）；
10. **先写 pending → 调供应商（带 Idempotency-Key）→ 补记结果**。超时 / 网络错误保持 pending，**24 小时内用同一个 Idempotency-Key 重放对账**（Resend 的键 24 小时过期），绝不记成失败后另发一封。

**去重键**：`(客户, 触发名, 联系人, 去重范围)`。去重范围按触发定：欢迎信 = 终身一次（与表格脚本「邮箱重复就跳过」一致）；行前通知 = 出发班期；感谢信 = 行程。**模板指纹不进去重键**（改模板不会让同一个人再收一封），它只进授权与账本。

### 4.7 回传：供应商发生的事，回到 ME
- **Resend 回调**：`email.sent / delivered / delivery_delayed / bounced / complained / failed / suppressed` 更新状态表；`opened / clicked` 只累计计数，**不写触点**（避开「苹果邮件替客人预读」那类老坑，见台账 2026-10-29-crm-email-open-counts-as-last-contact）。
  - **硬退信** → 该地址标无效，之后不再发（不等于别再联系）；**投诉** → 该联系人立刻「别再联系」+ 当日待办（带联系人链接）。
  - 回信：触发型邮件的 Reply-To 指向 CTS 现有邮箱，回信由现有邮箱同步（M2）进 ME，**阶段 2 不开 Resend 收信**。
- **短信回调**：送达回执更新状态表；入站回复先过「退订词」判定（§4.8）；其他回复进会话（channel = sms）并出待办。
- **接收口**：限长读体 → 验签 → 存原始事件 → Inngest 事件 → 处理函数；重放同一事件不重复入库；验签失败拒收并计数。Resend 回调的签名细节按官方文档核（§11）；ClickSend 若没有签名，则用不可猜的 URL 令牌 + 来源限制 + 回读核对。
- **回调丢失兜底**：每天（短信每 N 分钟）定时拉取供应商近 48 小时的发送 / 入站记录，与状态表对账；对不上 → 待办。

### 4.8 同意与退订
- **邮件**：每封触发型邮件带 ME 托管的一键退订（`List-Unsubscribe` 与 `List-Unsubscribe-Post`，经 Resend 的 `headers` 写入）。令牌是**签名令牌**（含联系人、渠道、签发时间），不用裸联系人编号，页面不回显名称。**客人本人点退订，系统立即执行；系统自己绝不「恢复订阅」**（恢复必须客人重新同意，NL-15）。
- **退订范围**：第一期沿用全局「别再联系」（宁严勿松）。代价是：退订过欢迎信的人，行前通知（服务类）也会被挡——这时由销售电话补，不让系统发。「只退订营销邮件、仍收行前通知」需要按渠道 / 类别记录的退订，放进阶段 2 实现设计。
- **短信两类**：**服务类**（行程 / 预订相关通知，不含促销）、**营销类**。营销类必须有记录在案的同意；服务类是否需要事先同意，Spark 说不用、Twilio 说要（§3-1、3-3）——**按更严的来**：第一期服务类也只发给有明确联系依据的人（已付款客人 = 订单即依据；咨询者须在表单里留下手机号并同意联系，需先补话术）。ME 把消息类别写进每次发送的状态表。**第一期只做服务类；营销类放阶段 3b（PM 10-29 追加，选了放宽口径），法务与 ClickSend 答复后才开（§4.14）。**
- **同意记录**：现有 Facebook 表单与官网表单没有「同意收短信」一句，所以没有存量同意；营销类短信上线前必须先补话术并留证（表单字段 + 时间 + 来源）。
- **STOP**：手机回 STOP 类词 10 分钟内处理（Spark）。①词表比 Messenger 那份宽（STOP / STOPALL / UNSUBSCRIBE / CANCEL / END / QUIT 及中文）；②**含 STOP 的短句进「疑似退订」**：立刻暂停对该号码的所有自动短信，出待办 30 分钟内人工确认，确认不是退订再恢复——因为法规说法是「含 STOP 或其变体都算」，而 Messenger 那份故意只认整句（避免「can you stop by」误判）；③退订**按（客户, 号码）记录**，不只按联系人（一个人多个号码、一个号码多个联系人）；④回调丢失时靠定时拉取入站短信兜底（§4.7）；⑤恢复必须客人重新同意。另给一种非短信的退订方式（官网页面）。
- **静默**：只在收件人当地白天发；行程紧急变更例外，状态表注明。
- **内容**：新西兰要求的固定提示语、禁止类目（赌博、放贷等）以供应商页面为准（§11 待核：提示语是否适用于零费率号码）。

### 4.9 域名、送达与名单卫生
- **独立 Resend 账号**：ME 现在同一把钥匙发系统邮件、PM 待办、广告 / cron 告警和冷外联；一旦被投诉拖累封号，全部一起停。**客户发信用独立账号、独立钥匙**（免费档起步）。
- **域名**：每个客户一个发信域名（Pro 含 10 个）。CTS 域名的解析记录由 CTS 域名管理人添加；SPF 只能有一条，要与 Mailchimp / Outlook 现有的合并；DKIM、DMARC 按 Resend 给出的记录。From 沿用 CTS 现在对外的发件地址与署名，Reply-To 指向现有邮箱。
- **同意与条款**：条款写「明确同意」，不分事务 / 营销。每个收件人的同意依据（来路、表单披露文本版本、时间）必须随状态表可查；Facebook 表单的「勾选退出」是否被 Resend 认可是**实测才知道的风险**（§8）。
- **自家闸线**（建议值，读客户配置并写明来源日期；用**最小样本 + 较长窗口**避免小数字抖动）：滚动 30 天、至少 20 封时，退信率 >3% 或投诉率 >0.04% → 暂停该客户批量类发送并出当日待办；**任何一次投诉**都出当日待办；单个硬退信 → 地址标无效。CTS 旧欢迎信的退信率是 2.5%（§3-15），接近但低于 3%；新人邮箱填错是常态，所以在线索入库时先做格式与域名收信检查。
- **名单卫生闸（迁移与批量前）**：不发给 Mailchimp 里已退订 / 已清理（cleaned）/ 已归档的人，不发给 ME 标了别再联系的人，不发给历史硬退信地址；只迁「有同意依据、近期有效」的地址，不整库倒入。
- **每日对账**：供应商实发数 vs ME 状态表，不一致 → 待办。
- **预热**：触发型量很小（每天个位数到十几封），不需专门预热，但切换首周每天看退信 / 投诉。

### 4.10 短信：供应商与新西兰短号码
- **供应商**：首选 **ClickSend**（官方公布新西兰短号码价格、后台直接申请、有子账号与回执 / 入站回调）；Twilio 备选（ME 电话已在用，但新西兰短号码要联系销售、价格未公开）。适配器与供应商无关，换供应商只需重新申请短号码——**短号码绑定供应商，所以要先选定再申请**。
- **新西兰**：每个要发短信的客户一个专用短号码，4–6 周开通。服务类用「标准费率」（客人回复要付费）；营销类要「零费率」（退订免费）。先申请服务类，营销类以后另申请。
- **第一批用途（PM 2026-10-29 定）= 行前**：对象 = 已付款客人（ME 里 `crm_bookings` 状态有效、有出发日期、联系人有手机号）；触发 = 出发前 N 天（读 `crm_bookings.departure_depart_on`，去重范围 = 出发班期）；类别 = 服务类，不带促销。现状覆盖（2026-10-29 生产库只读）：CTS 26 个有效订单只有 9 个有手机号，最近的团 11/03 出发，短号码最快 12 月初才下来，用得上的是 2027 年 3 月起的团。同意依据：官网隐私政策（「订单确认、更新和旅行文件」；回 STOP 退订）+ 订单确认环节补一句并留记录（PM 10-29 确认现在没有，CTS 要补；已有订单不能倒填，§11-B）。申请材料草稿：`docs/clients/cts/2026-10-29-nz-short-code-application-pack.md`。
- **澳洲**：字母发件名要在 ACMA 登记册登记（2026-07-01 起；要 ABN；§3-4 未读原文）；有澳洲客户时单独走。
- **数据库**：`sms` 要加进两张表的 channel 白名单（A 级迁移，§5 P3）。
- **回执与对账**：每条短信一行状态（类别、模板指纹、供应商消息号、状态、费用）；每日对账同 §4.9。
- **费用谁出**：短信号码与按条费用属于第三方成本，是否按既有「第三方费用转嫁」流程给客户开票，PM 定（§11-B）。

### 4.11 欢迎信的过渡与切换（CTS 是第一个）
**现状（2026-10-29 核）**：Mailchimp 自动欢迎流程 10/14 起暂停；每天 8:01 的表格脚本批次（已换成 2027 春季新版）只发 Facebook 来路的新人；官网订阅新人没有欢迎信（10/28 手动补发了 4 位）。**过渡期不改任何东西，也不再新建 Mailchimp 流程**（台账卡 2026-10-29-cts-welcome-email-no-new-mailchimp-flow）。

**范围**：阶段 2 只覆盖**已在 ME 里**的人（Facebook 表单留资、CRM 手建）。官网订阅是直接写进 Mailchimp 的，ME 看不到，所以第一期覆盖不到；要覆盖得让网站把订阅同时写给 ME（跨仓库，另开设计）或另想办法（阶段 2b，§5）。在此之前继续按 PM 说「发」手动补发。

**切换步骤（阶段 2；每一步 PM 说「开始」或「切」）**
1. **影子期**：ME 对每个新线索算出「本该发欢迎信」的名单并写状态表（标 `shadow`），**不真发**；每天与「8:01 批次实际发的」对照，**连续 5 个有新线索的日子一致**才进下一步。
2. **授权**：PM 看影子结果和测试信（只发 hello@），本人授权（§4.5）。
3. **切换当刻**（选一个工作日，同一天内连续做完）：先**等当天 8:01 批次跑完**（读脚本运行记录确认已发）；然后 PM 把表格脚本里 `dailySendE1Batch` 的触发器**改成 2099 年的一次性日期**（不删；与 E2–E4 同一做法，见 `docs/ledger/evidence/2026-10-28-wp0a-defuse-landmines.md`，Google 弹「未验证此应用」授权页时不要点继续）；确认改成后，ME 才开真发。批次与 ME 之间的空档（批次之后、ME 开通之前进来的人），由 ME 开通后第一轮补发（24 小时内，NL-01）。ME 的「历史欢迎检查」（§4.6-6）保证当天已被批次欢迎的人不会再收。
4. **验证**：切换后 7 天，①**没有任何人收到 2 封欢迎信**（Mailchimp 报告与 ME 状态表，两边数一致）；②应收的人 24 小时内都收到（有人因别再联系 / 无效邮箱被拦属正常，状态表要写明原因）。
5. **回滚**：**只停 ME 的授权**（一条记录），**不复活批次**。空档里的新人由人工补发（PM 说「发」，同 10/28 做法）。批次只有在表格「E1 已发」列已按 ME 发出的名单补标、并且「待发」干跑结果为 0 之后才允许恢复——因为批次靠那一列判重，ME 发出的人不在那一列，直接重开会把他们再欢迎一遍。

### 4.12 Newsletter：保留现成引擎，不自建
- 继续 Mailchimp；ME 只管名单、同意与退订的事实（以 ME 为准）和发前闸（126 号手册）。**不在 Mailchimp 里新建任何会自动发信的流程**。
- **阶段 5 试验**：拿一封真实 newsletter 走 Resend Broadcasts（免费档 1,000 联系人，当前 CTS 名单约 900，增长中），对照六条再定去留：①个性化称呼与兜底（如「Kia ora, Ni hao,」）；②能否直接贴 CTS 现有 HTML；③分组能否按条件包含 / 排除（或由 ME 推送成员）；④每人退订与抑制名单自动生效；⑤报告（去机器人打开口径、点击）；⑥成本（1,000 人以上约 US$40/月）。六条全过才迁；否则继续留 Mailchimp（或再评 Brevo）。

### 4.13 Inngest 事件与回执字段（CLAUDE.md §3 的最低要求）
- **事件名**（业务可读，命名沿用 127 的 `<域>.<对象>.<动词>`；最终以实现设计为准）：`crm.triggered_send.requested` → `crm.triggered_send.gated`（通过 / 被拦）→ `crm.triggered_send.sent` → `crm.provider_event.received`（回调）→ `crm.triggered_send.reconciled`（T+1 对账）。
- **每个阶段的机器可读回执**：request id、client id、source record id（联系人 + 触发来源事件）、status、cost / provider 影响、授权状态（授权记录 id、模板指纹、是否 shadow）、created_at。
- **人工审核只推进到下一事件，不等于发送授权**；发送、扣费、客户可见外发 fail-closed：没有有效授权事件和供应商回执，不许伪造完成。

### 4.14 营销短信（第二批；PM 2026-10-29 追加）
**要什么**：给**潜在意向客户**发营销短信，短信里带一个链接；客人点开后可以**填表单**，或者**直接去指定网页**。
- **对象**：ME 里「有意向」的联系人 + 有手机号 + **同意依据成立**（明确同意，或下面「放宽」口径下的默示依据）+ 不是别再联系 + 不是已订客人 + 不是销售正在跟的（排除集读客户配置）。
- **同意口径（PM 2026-10-29 选了「放宽」）**：除了「明确同意收短信」的人，也发给**最近咨询过、自己留过手机号的意向客户**（默示同意：他主动咨询并留了号码，我们发与他咨询相关的信息）。这是**有法律风险的口径**：新西兰要求营销短信有同意（Spark、ClickSend 页面；法条原文未核，§11-C），默示同意要「与咨询相关、近期」才站得住；风险由 PM 承担。下面三条是我设的护栏，**发之前必须过**：
  1. **先问清法务和 ClickSend**（问题清单见 §7-7）：默示同意站不站得住、多久算「最近」、ClickSend 的新西兰营销短号码接不接受默示依据（它的页面写「必须能证明客人 opt-in」，这是供应商层面的规则，可能比法律更严）。**任何一方说不行，就退回严格口径（只发明确同意的），不再另问 PM。**
  2. **如实陈述**：申请短号码和之后任何对外说明，同意依据按实际写（「客人咨询时提供了手机号」），**不能写成「客人勾选了同意」**——不实陈述会让号码被收回。
  3. **每个收件人记同意依据**：`explicit_sms_optin`（明确同意）或 `inferred_enquiry`（默示：哪条咨询、哪天），写进发送记录，可审计、可随时收紧。
- **护栏参数**（建议值，读客户配置，法务答复后定）：默示依据只认**最近 90 天内他自己提交的咨询**（官网表单、Facebook 表单、私信里留的号码）；内容必须与他咨询的团 / 主题相关，不发无关促销；首条短信写明是 CTS Tours、为什么收到（「你咨询过…」）、带退订；只发 1 条，不追发；回 STOP 立即永久停；点进表单并勾选 → 升级为明确同意。
- **同意采集仍要做**（官网表单与 Facebook 表单加「同意收短信」一句，ME 记「谁、何时、哪个表单、话术版本」；改正在投的 Facebook 表单要先通知广告总控窗口，不能擅自改）：让以后的收件人逐步从「默示」换成「明确」，也是严格口径的退路。已有的意向客户可以用一封邀请邮件换成明确同意。
- **号码**：营销类要「零费率」短号码（客人退订免费），和行前用的「标准费率」不是同一种。申请时向 ClickSend 问清：一个号码能不能两种用途都挂、还是要两个号码、各自多少钱（申请材料草稿 §3、§6）。
- **短信内容与链接**：开头写明是 CTS Tours；一个链接，**用客户自己的域名**（不用公共短链——运营商常拦，未核）；每人一个令牌，点击与表单提交回 ME 做归因；结尾写 Reply STOP；价格、日期、团名逐句对官网（客户数据红线 8）。每个模板绑指纹授权（§4.5），改一个字就要重新授权。
- **落点**：两种都支持，用令牌区分、让 ME 比较哪种转化更好——①官网上的短表单；②指定网页（团页或活动页）。落地页与表单在客户域名，由官网仓库的窗口建；ME 记录点击和提交（沿用官网表单现有回传路径与 utm，阶段 3b 实现设计查清）。
- **节奏与闸**：沿用 §4.6 全部闸；营销类每人每 7 天最多 1 条（建议值，读客户配置）；静默时段；退订 10 分钟内处理；退信 / 投诉 / 退订率超线自动暂停（§4.9）。
- **衡量**：发送 → 点击 → 表单 / 页面访问 → 新咨询 / 订单，逐级写回（IMPACT 的 Check）；样本 <20 不下结论（沿用 126 号 NL-09）。
- **阶段**：P3b。前提 = P3 服务类试点跑通 + **法务与 ClickSend 对「放宽」口径的答复** + 零费率号码批下来 + 落地页 / 表单就绪 + 模板授权（同意采集上线不再是硬前提，但仍要做）。风险 A。

## 8. 风险、护栏与不做
- **Resend 的「明确同意」与 Facebook「勾选退出」**：新增风险，Mailchimp 阶段不存在这个问题。护栏：独立账号；每人同意依据可查；每封带一键退订；闸线（§4.9）；先小量。若 Resend 事后认定不符，退路 = 触发型邮件换发信通道（适配器可换）。
- **切换期双发 / 漏发**：影子期 + 等批次跑完再切 + 历史欢迎检查 + 回滚只停 ME；批次靠「E1 已发」列判重，ME 发出的人不在那一列，所以**绝不直接重开批次**。
- **新公共入口**（回调、退订）：验签 / 签名令牌、限长、幂等、重放不重复；A 级审查。
- **同意与法规**：第一期只做服务类短信，且按更严口径；营销类先补同意留证。法条原文未读（§11-C）。
- **送达**：新发信域名首周盯退信 / 投诉；自家闸线低于条款线。
- **隐私**：状态表、待办、台账、PR 里不放逐人邮箱 / 手机号，只放哈希前 8 位代号与汇总数字（沿用 126 号 NL-20）。
- **不做**：不自建 newsletter 管理；不迁 Mailchimp 名单、不改 Mailchimp 任何设置；不做营销短信；不替客户申请短号码；不动内核授权；不改 126 / 127 / 129 的代码与卡；不把第 2 / 3 次跟进改成自动发；不为本方案新建能力线或支柱。
