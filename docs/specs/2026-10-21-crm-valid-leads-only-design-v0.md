## 1. PM 要什么（原话）

ME CRM 里「今天要联系谁」判断得不准；这里应只自动提取「有效 Leads」——只保留有效咨询的客人信息，
自动过滤类似 Guardian-reports、Cuong Nguyen Manh 这样的。

## 2. 事实（只读生产库，2026-10-21 用线上真代码重算）

| CTS 联系人 | 1196 | |

**根因**：系统把「info@ 收到一封邮件」一律当新客人。现有三层防线都不管这件事：
`mail-sender.ts` 只拦 noreply 一类发件地址；`contact-kind.ts` 只按域名分散客/同行/员工；
`automated-touch.ts` 只判「我们发出去的」是不是机器发的。**没有一层问「这个人发来的话是不是咨询」。**

### 诚实交代：这次只能把 364 减到约 348

PM 点名的这类（陌生邮件）只占 16 个。名单大头是别的：364 人里 162 人最后一次来往在 31–90 天前、
48 人在 90 天前。「客人来过消息、我们没回」不分多久都算今天要联系。这是**另一件事**
（要不要给「今天要联系」加年龄线），是 PM 才能定的业务口径，本稿**不做**，只在汇报里提一次。

## 4. 「合格线索」口径（白纸黑字，先于代码）

PM 2026-10-05 已定：**表单发来关于旅游的真实问询 = 合格；私信里对方发超过两条 = 合格。**
本稿新增第三条（**邮件咨询**，需 PM 点头）：

| 渠道 | 合格线索 | 本次改不改 |
|---|---|---|
| 网站表单 / 广告表单 | 关于旅游的真实问询 | **不改**（不进筛选） |
| Facebook 私信 / WhatsApp | 对方发超过两条；**只来一两条且没留联系方式的不是垃圾**，不动 | **不改**（不进筛选） |
| 电话 | 打进来的都算 | **不改** |
| **邮件（新）** | 对方发来的信里**在问我们的团 / 价格 / 行程 / 出发日期 / 订位，或在跟进我们之前的往来** | **本稿要做** |

**邮件里「不是咨询」的 5 类**（行业无关的通用类别，写进共享代码）：

1. **推销 / 合作邀请**：供应商、地接社、中介来推销（Cuong、LavinGo、chajense、jing Hui）
2. **群发营销 / 订阅**：通讯、促销（TASUKI newsletter、SANA、Afterpay、Daisuke）
3. **系统通知**：服务商状态通知（Twilio 号码审核）
4. **自动回复**：「Automatic reply / 我不在办公室」（Sarah Andersen-Clay）
5. **抗议 / 投诉类群发信**：与是否买团无关的表态信（Guardian-reports、Mark B、Ethan、EJ、Paola）

**「是咨询」的正面证据**（任一即可，宁可放过）：问价格 / 报价 / 行程 / 日期 / 订位；

## 5. 设计

### 5.1 只管一类人（缩小误伤面）

**进筛选的条件（全部满足才进）**：这个人名下**每一条**记录都是「对方发来的邮件」；
我们没有任何人工发出的记录；没电话；没表单 / 私信 / WhatsApp / 电话记录；阶段是空或「新线索」
（员工动过阶段的人不碰）；没有被人标过「这是真客人」。

不满足 → 一律不筛、行为和今天完全一样。CTS 现在满足的 18 人（占「今天要联系」的 5%）。

### 5.2 两层判断，宁可漏筛

- **第一层（确定性规则，不花钱）**：自动回复主题（复用 `isAutoReply`）；通用的群发服务中转域名
  （例：邮件群发服务的转发地址）。命中 → 直接判「不是咨询」并写原因。
- **第二层（大模型，仅对第一层没判掉、且满足 5.1 的人）**：Content Engine（gpt-4o-mini，
  沿用 `travel-agent-customer-extract.ts` 同款调用）。输入：主题 + 已存的前 255 字预览（库里本来就有，
  不另取正文）。输出：`类别（5 类 / enquiry / unsure）`、`confidence`、一句原因、依据原文的短引文。
  **只有「类别 ∈ 5 类」且「confidence 高」且「引文真的出现在原文里」才判不是咨询；其余（含 unsure、
  解析失败、调用失败、超时）一律不筛。** 邮件内容当数据不当指令（防提示词注入，同提取器写法）。
- **费用**（估算，未对账单核实）：每封约 400 词元进 + 80 出，gpt-4o-mini 约 \$0.0001/封；
  CTS 现有 18 人 + 校准集约 150 封 ≈ 不到 \$0.02。之后每个新来的陌生邮件人调用一次。

### 5.3 判完怎么办：不让人凭空消失，只有「今天要联系」「先放着」两张名单

- 判为不是咨询 → 把这个人的阶段改成新阶段「**非咨询**」（`not_enquiry`，`marketing_action = suppress`，
  不是终态），**改阶段事件里写原因**（`contact_stage_events.note`，如「不是咨询：疑似供应商推销」，
  `changed_by = system`）。现有机制 `segmentContact` 对 `stageSuppressed` 的人本来就判 `excluded`
  → 落「先放着」，页面上显示原因。**不新增状态概念，不加表、不加列。**
- 「先放着」里那一行读阶段事件的最新 `note` 当原因（读侧批量取，只取阶段=非咨询的人，几十行）。
- **一键拉回**：销售在「先放着」里点「这是真客人」→ 用现有的改阶段入口改回「新线索」（`advanceContactStage`）。
  机器此后**永远不再判这个人**（5.1 的条件：阶段不是空 / 新线索 → 不进筛选；被拉回的阶段事件
  `changed_by` 是人，留痕）。
- 营销副作用：阶段「非咨询」按 `suppress` 处理 = 不再给他发营销。供应商 / 抗议者本来也不该收；
  万一错筛，拉回即恢复。

### 5.4 什么时候判

- **新来的**：邮件同步新建联系人后，旁路调用（和 `runAgentCustomerHook` 同款：失败只告警，不影响主同步）。
- **存量**：一次性「干跑脚本」，**只读**，不写库。

### 5.5 开关与上线（不许直接开）

- 配置：`clients.leads_config.enquiry_screen.enabled`（默认关；`leads_config` 是 jsonb，不需要改表）。
- 关着时：新代码只**计算并打印**，不改阶段。
- **干跑 → PM 点头 → 才打开**。干跑只读跑 CTS 全量，给 PM：「352 → N，挪走 M 个」，
  **至少 30 个被挪走（不足则全部）的名单 + 原因供抽查**。当场试跑**不外发任何消息**。
- 打开动作含：①在 CTS 的阶段表里加一行「非咨询」；②对存量命中者批量改阶段 → 都是**写生产库，
  PM 点头后才做**。

## 6. 判据怎么校准（用生产数据，不靠感觉）

- **金标准（必须全部判「是咨询」）**：CTS 里**我们用邮件回过信的人**（人工回信 = 事实上的真咨询），
  取他们的第一封来信，跑分类器。**任何一个被判「不是咨询」= 判据不合格，改了再跑。**
- **反例标准（应判「不是咨询」）**：上表 16 个手工确认的。目标 ≥ 14/16；漏掉的留在名单里可以接受，
  错筛不可接受。
- 「Attn BAKER」两封必须保持「是咨询」（已手工确认）。
- 校准结果写进 PR 正文与本稿 §9。
