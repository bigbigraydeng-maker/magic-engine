# 素材流程改为「数据驱动」· 设计 v0.6（增量，仅供讨论）· 只设计，未写代码 · 119 号 · 2026-10-21

> 在 v0.1–v0.5 之上：冲突处以本稿为准。吸收 74 转来的两审终核。**本稿不构成对 `bounded_auto` 或任何自动花钱的授权。** 改完这轮仍有两处需 PM 口径（见 §8）。

## 1. 自动入池素材怎么满足 3010 计划闸
先说事实：3010 v0.5 §3 已定**第一版计划闸只硬拦「账户、日期、预算」三项，素材/受众只出黄色提醒、不当闸**。所以第一版里，新素材不在计划步骤清单里**不会被拦**。
面向以后把素材升级为硬闸时，**写死选 A**：计划广告步骤增加声明 **`素材来源 = 素材池`**（`creative_source: 'pool'`，属于广告步骤字段，在 PM 批计划时随计划一起批、进「广告相关字段指纹」），此后该步骤可用的素材由**素材池内状态**（`testing/scaling`，质检回执有效）决定，不要求逐条出现在计划里；未声明该来源的步骤，素材仍须逐条列入计划并经 PM 批。不采用「按标签匹配」（会触指纹）。列入 §6 第一步清单（A 级，PM 批或 3010 实现时定）。

## 2. 新建放大组：内核没有对应动作 + 刹车（解决 v0.3 §3 与 v0.4 §3 的矛盾）
- **内核现状**：`registry-ads.ts` 唯一新建类动作是 `ads.add_retargeting_adset`（再营销、挂已有系列），**不能借用**。晋升需要**新注册动作**（暂名 `ads.promote_to_scale_adset`），要改 `registry-ads.ts` 与 `envelope-facts.ts`——**A 级内核改动**，列入 §6 第一步，走子牙+魏征。
- **学习期口径澄清（消除矛盾）**：`envelope-facts.ts`（约 584–591）对新建类 `learningApplicable=false`，学习期排除**不适用于新建放大组**；v0.3 §3 的「放大是死路」**只指对已存在广告组加预算**（学习期读不到时被信封拒）。晋升为新建，不被此拦；晋升之后对该放大组的**加预算**才受学习期约束（读不到则拒，只出建议）。
- **写死：在 `creative_flow_enabled=true` 且 `bounded_auto` 之前，晋升一律只出建议**（不建组）。
- **开启之后的刹车（硬判据）**：
  1. 每日最多晋升 **N 个**（初值 N=1）；
  2. **所有放大组日预算之和 ≤ 放大总预算**（硬判据，严格 ≤，**不得使用客户上限×1.2 的 20% 缓冲**——为此在动作的信封事实里单设「严格上限」，不借用 `clientCap` 的缓冲）；
  3. 起步额 `min(放大总预算×30%, 测试组日预算×3)`（v0.4 §3）；
  4. 仍受 2999 日预算闸与 3010 计划闸（取最小）。

## 3. 晋升的原子顺序
1. 先**停/降 0 测试组**（收类，永远放行）→ 写回执①；
2. 再**建放大组**（`ads.promote_to_scale_adset`）→ 写回执②；
3. **任一步失败，整体不开始后续步骤**；若第 1 步成功、第 2 步失败：**测试组保持已停**（偏保守，总花费更少），出「晋升半途失败」待办，不自动回滚去重开测试组。两步各有机器可读回执，同一 `promotion_id` 串起。
- 「受众互斥规则沿用」：`circuit-detectors.ts` 里只找到字样，**没找到实现**，**列待核**（§6）；核实前晋升不得声称受众互斥已保证。

## 4. 两个预算数与 `creative_flow_enabled` 的「只能 PM 本人写」——写保护机制
现在只有口头约束：`ad_strategy_configs` 有通用 `PATCH /ad-strategy-config`，别的窗口、cron、service_role 都能写，放大总预算被改就等于绕过 PM 授权。机制：
1. **通用 `PATCH` 拒收**这三个键（`test_budget_cap_cents`、`scale_budget_cap_cents`、`creative_flow_enabled`），与现有对 promo 键的做法一致，返回 400。
2. **专用路由**写入：必须是 `requireSpendActivationAuthority` 同一套 **PM 本人身份校验**（只放行 PM 一人）；每次写入追加审计行（谁、何时、旧值→新值）；`creative_flow_enabled` 只能由该路由置 true（且要求该客户当时 `bounded_auto`，否则提示「仍只出建议」）。
3. **数据库层**：对 `service_role` 撤销这三列的直接写权限（列级 REVOKE，照 3002 对工单哈希列的做法），只经受保护窄函数写；**如实写**：函数自身无法验证调用者身份，真伪根仍是 PM 管理员会话，数据库层只防直写（与 3002 同一限度）。
4. 验收：**非 PM 写入被拒**（通用 PATCH、service_role 直写、cron 三条路都被拒）；写入留审计；NAL 等未开启客户不受影响。
