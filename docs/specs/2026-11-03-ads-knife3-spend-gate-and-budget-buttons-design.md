## 2. 3a：加钱类动作的 PM 本人闸

**2.1 哪些动作算加钱类**——每个 `ads.*` 动作定义**必须明写** `spendIncrease: true | false`（不按信封事实类型推断：减预算的事实类型也是「改预算」，推断会把刹车误收进来）：
- `true`：`ads.scale_unit_budget`、`ads.budget_move_plan`（加的一侧）、`ads.add_retargeting_adset`。后两个今天没有执行能力，照样标。
- `false`：`ads.pause_unit`、`ads.pause_campaign`、`ads.cut_unit_budget`、`ads.cut_campaign_budget`、`ads.swap_creative`。
- 守卫测试：注册表里任何 `ads.*` 动作没写这个字段 → 测试红。
- **关整个系列（`ads.pause_campaign`）是刹车，不进闸，偏离方案原文**：现有拍板是「付费客户都能暂停、只有 PM 能开投」（`spend-activation.ts:4-6`）。
- **撤回**（把改动恢复到改前）不过闸：只恢复已批准改动之前的状态，写明为例外。

**2.2 五道闸（每道单独测，冻结那次提交上做一次变异检验：逐道删掉，对应测试必须红）**
1. **策略同步**：`sync-policy` 对 `spendIncrease` 动作一律写 `require_approval`。去重依据加上「同步规则版本号」（本刀 +1），部署后第一次同步会把这三个动作的策略行重写一遍（策略版本号 +1，在路上的自动放行作废——正是想要的）。设置页这三个动作显示「要 PM 批」。
2. **授权预检**（`preflight` ⑥b，`bounded` 分支之前）：`spendIncrease` 动作遇到 `auto_approve` → 拒，复用可恢复拒绝码 `outward_requires_human_policy`，理由写「加钱类只能 PM 本人批，这个客户的规则却配成了自动」。防有人手改策略表或同步失败。
3. **签批准**（`approveRun` 任何写入之前）：`spendIncrease` 动作，批准人必须在 PM 名单里；不在 → 抛 `NOT_AUTHORIZED`，不签、不改 run（run 仍等 PM）。同一处顺带**预跑一次执行时会跑的信封判定**（见 2.3），判不过就以可恢复拒绝落一条 deny，免得 PM 批完死在执行前。
4. **复用旧授权**（`reuseLiveAuthorization`）：`spendIncrease` 动作的旧放行，签字人不在 PM 名单或不是人签的 → 返回 null 重新授权，不复用（否则会一直撞第 5 道直到过期）。
5. **执行前复核**（Gateway `assertDecisionMatches`，领取执行权之前，拒了不消耗授权）：放行必须 `decided_by==='human'` 且签字人在 PM 名单里。
- 通用审批页：把三个加钱类动作登记进 `dedicated-approval-entries.ts`（入口指向广告健康页），通用页在调 `approveRun` 之前就挡掉，不出现「批了没人跑」。
- O1 批准路由把 `NOT_AUTHORIZED` 答成 403「只有 PM 能批加预算」（现在会答 409）。

**2.3 PM 批的加预算用「人工放量信封」**（解决 F8）
- 新增 `HUMAN_SCALE_ENVELOPE`：保留 ±20%、客户日上限、**72 小时只改一次**（B-04 对人也适用）、不在 Meta 实验里、必须有撤回处理；**学习期读不到不再拒**，改成在预览和批准记录里写「学习期没读到，PM 知情批准」。
- 选用条件不靠可自报的 `triggered_by`，而是**放行决策由 PM 名单里的人签**（第 3 / 5 道已核实的事实）。AI 或别人签的加预算仍走原自治信封。
- 72 小时冷却口径**不改**（实现时决定）：`envelope-facts.ts` 把执行前失败的 run 也算「动过」是有意的宁严勿松（注释里写明另开卡做精确版）。本单靠「批准时预跑同一套信封判定」让 PM 批不了必死的改动，执行前被拒只剩并发窗口这一种情况。

**2.4 PM 名单**
- 新环境变量 `ADS_SPEND_APPROVER_EMAILS`（精确邮箱）。**PM 11-03 定：只放 `ADMIN_EMAILS` 第 1 个（PM 本人 gmail）**。没配 / 为空 = 谁都批不了加钱（fail closed），不回落到 `ADMIN_EMAILS`。
- 判定 `isSpendApproverEmail` 放 `auth/whitelist.ts`；内核经 `deps.isSpendApprover` 注入（`index.ts` 与信封事实解析器同一做法），`deps.ts` 工厂必须透传，补一条架构测试（09-27 漏过一次同类注入）；缺依赖 → 第 3–5 道一律拒。
- 架构测试锁住 `approveRun` 的批准人参数只来自登录会话（不来自请求体）。
- 重开暂停的广告（`requireSpendActivationAuthority`）判据换成同一名单（另外 5 个邮箱失去重开权，PM 已知情）。**上线确认卡开新系列（F11）本单不动**，是否也收进名单单独问 PM（§6）。
- **部署顺序**：先在 Render 配 `ADS_SPEND_APPROVER_EMAILS` → 手动重新部署 → 读回确认 → 再合 3a。否则合进去那一刻重开广告会全部失败。配 Render 环境变量是改生产配置，合 3a 前一并请 PM 点头。

## 3. 3b：成绩单每行调预算

**3.1 界面**：成绩单每行加「调预算」列，三个按钮「加 10%」「加 20%」「减到…」。共用账户、别家主页的组、实验中的组、没有可改日预算的单位（CBO 下的广告组改系列，复用 O1 那段「系列下只有一个在投组」检查，抽成共用函数，不复制）按钮灰掉并写原因。

**3.2 预览**（服务端现算，不信前端数字）：
- **当场读 Meta** 这个组 / 系列的当前日预算和 `updated_time`（F12：快照会吞掉人在 Ads Manager 的改动）。读不到 → 「加」禁用。
- 改前 / 改后日预算（账户币种）、客户日上限余量。
- **B-04**：Meta `updated_time` 或 ME 执行记录在 72 小时内 → 「加」禁用（保守：Meta 那边任何编辑都算），「减」照常。
- **调用与执行时同一个信封判定函数**（人工放量信封），判不过 → 「加」禁用并写哪一条没过。
- **E-13 放量七条**、**C-06 冻结期**：没有代码，逐条列出标「没核对」；条文从规则手册读进预览配置，不写死在组件里。
- 加：只给 +10% / +20%；减：下限按止损算法（−20%、最低金额）算好，复用 `ads-strategy/stop-loss.ts` 的函数并补测试。

**3.3 提交**
- 新路由 `GET/POST /api/clients/[id]/ad-health/budget-change`；**不改 O1 路由**（O1 现有测试不受影响）。
- 加：复用 `submitO1BudgetScale`，加两个参数（倍数 1.1 / 1.2、来源 `ads_health_scorecard`，理由文案按来源）；仍强制 `requireHumanApproval`；`cycle_date` 用新西兰当天日期，同一天同一单位同一改动跟 O1 撞键时拿回同一条 run（同一件事），不同倍数不撞。
- 减：复用止损提交和 `requireStopLossAccess`（全局管理员都能批，刹车不收紧）。
- 闸没就位（名单为空或内核没注入判定）→ 加的请求 503「加钱的闸还没装好」。

## 4. 3c：自带最小回看

- 提交时填：观察几天（默认按行业参数，旅游 7 天，取不到就 7）、什么算成（默认「单次主结果成本不比改前差 20% 以上」）。
- **执行成功后**才写 `flywheel_actions`（`payload` 里放观察天数、判据、到期日、`action_run_id`；系列降预算本来就写一行的，挂到那一行上，不重复写）。
- 逻辑放 `src/lib/ads-strategy/`，由每日拉数路由调用并 `.catch`，失败不影响拉数（那个路由已超 800 行，不往里加逻辑）。
- 三档（C-17 v1.1 最小回看）：
  - **动了**：读回生效，观察期数据齐，样本过门槛，按「什么算成」写成 / 不成；
  - **没动**：读回失败，或被人在 Ads Manager 改回；
  - **没测成**：观察期里断投、又改过、样本不够、Meta 事后补数还没稳定；**零投放和缺数据分开写**（第 2 刀查到的教训：没有行 ≠ 没拉到）。
- 只写运行记录和这一行的结论，不写归因、不进 `flywheel_outcomes`（第 4 刀）。结论在成绩单那一行显示一句；只进客户私有层。

## 5. 验收

- **3a**：五道闸逐道单测 + 冻结提交上变异检验；`spendIncrease` 字段守卫；名单为空谁都批不了；非名单批准抛错且 run 仍挂着；人工放量信封在学习期读不到时放行、在 72 小时内拒；执行前被拒不记「动过」。**当场试跑**：本机测试替身走「提交 → 非 PM 点批准被拒 → PM 点批准 → 执行前复核通过 → 停在 Meta 写入前」；生产只读：部署前读 CTS / NAL 加预算策略行，部署后读回已变成 `require_approval`、版本号 +1，贴进改动单。

## 9. 3a 实现回填（代码复审后，2026-11-03）

| 设计稿原文 | 实际实现 | 原因 |
|---|---|---|
| §2.2 通用审批页：登记进专属入口表 | 另设挡法 `spend_increase`（`kernel-approval/service.ts`），不登记 | 登记会把加预算从通用待办里摘掉，而加预算没有自己的待办 → 从所有待办里消失（违反「管道不许断头」） |
| §2.2-1 去重加「同步规则版本号」 | 去重加「上次写的目标模式」 | 效果相同、不用维护版本号；生产回执 `to_mode` 全有值（CTS 90 / NAL 9），只有三条加钱类会被重写一次 |
| §2.3 批准记录里写「学习期没读到，PM 知情批准」 | **没做**，挪到 3b 预览里显示 | 批准记录由数据库函数写，加字段要改函数；预览里让 PM 批之前看到更有用 |
| §2.3 设置页这三个动作显示「要 PM 批」 | **没做**，挪到 3b | 纯展示；3a 只管闸 |
| §5「执行前被拒不记动过」 | 口径不改（见 §2.3 末条） | 与 §2.3 矛盾，以 §2.3 为准 |
