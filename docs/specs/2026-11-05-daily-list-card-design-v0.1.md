# 社媒 Agent 第 2 刀 · 每日清单卡 设计 v0.2

- 日期：2026-11-05 · 窗口：97 号 · 风险级别：**A**（对外发布授权）· 上游：[开发计划 v1.2](./2026-11-05-social-agent-high-frequency-facebook-dev-plan-v1.md) §4 / §5 第 2 刀；[按日公开设计 v0.2](./2026-11-04-reel-scheduled-go-public-design-v0.2.md)
- PM 2026-11-05 对第 2 刀回「做」。

## 1. 做完 PM 看到什么

客户社媒页顶上一块「今天到后天要发的 Reel」：每条一行（团名标题、发布日、Facebook 正文、首评、事实核对结论、看片链接），默认全勾。PM 看完点一次「放行勾上的 N 条」= 对这 N 条**分别**授权；没勾的那几条视为剔除，填一句原因。今日待办里每天一条「今天到后天有 N 条 Reel 等你放行」（直达这块）。

## 2. 与计划的一处偏离（请审查判断）

计划写「清单卡用 confirmation-card 出，每天 06:30」。本稿改为**页面清单 + 拉模式待办**，不走 confirmation-card：
- confirmation-card 现有用法是「打开页面时出卡」（`openWeekPack`），每张卡一条内核策略、一行 action_runs；每天一张会每天新增一行要人批的卡，且卡的内容哈希在条目变化时作废、要重出。
- 清单本身已经满足计划要求的三条：①逐条绑指纹（见 §3）②卡外新增条目不放行（客户端只提交它显示过的条目，服务端逐条比对指纹）③可单条剔除并记录。
- 审计落点：每条授权写进流量记录的 `scheduled_go_public`（已有）：`card_run_id = daily-list:<list_id>`、`authorized_by`、`authorized_at`、`fingerprint`；剔除写进工单 `brief.weekly_pack.excluded_by_card`。
- 06:30 推送改为今日待办拉模式（今日待办 5 类里的「要你授权」类）。

## 3. 授权怎么证明「PM 看到的 = 要发的」

现在：预览发一次性口令（绑指纹、5 分钟过期），批卡时核口令。清单卡：
- 服务端 GET 清单时对每条跑 `buildContext`（读 Facebook 草稿、核团目录、核出镜授权），返回显示内容和 `grantFingerprint(ctx)`（视频 id + 正文 + 首评 + 审片时间），以及 `list_id = sha256(按发布日排序的 [工单 id, 指纹, 发布日])`。
- PM 放行时客户端提交 `list_id` + 勾选的 `[{work_order_id, fingerprint, publish_on}]` + 剔除的 `[{work_order_id, reason}]`。
- 服务端逐条：重跑 `buildContext` → 当前指纹必须等于提交的指纹、当前发布日必须等于提交的发布日、发布日不早于今天、没有进行中/已用的授权 → 同一次乐观锁写入 armed 授权。任一条不符只拒那一条，回执写原因。
- 口令被指纹比对取代的理由：口令本身就是「这个人对这个指纹点过预览」的凭证；清单把指纹直接显示在 PM 看的那一屏里并原样带回，作用相同，少一次往返。只认全局管理员（`requireGlobalAdmin`），与现有按日公开授权同级。

## 4. 剔除

- 工单 `brief.weekly_pack`：删 `publish_on`，写 `excluded_by_card: { at, by, reason, list_id }`（乐观锁，`updated_at` 比对）。
- 每日排期器跳过带 `excluded_by_card` 的工单（新原因 `excluded_by_card`），不再自动排。要重新排：工厂里改片（新版本）或 PM 清掉这个标记（第 2 刀不做界面，记后续）。
- 已有授权的条目不能剔除（走「已授权、还没公开」面板的撤回）。

## 5. 连带改动

- 第 1 刀的 `DAILY_BLOCK_ONLY_PENDING` 改为 `true`：周卡审过的周可以再排，因为现在有清单能批。
- 每日排期器跳过 `excluded_by_card`。
- 「已排」计数只算今天及以后（第 1 刀审查建议 ③）。

## 6. 不做

- 第二阶段「每周一张整周清单」（PM 14 天后再定）；自动降级 / 升级统计（本刀只把剔除、撤回记下来，作为以后的证据）；图文（第 3 刀）；缩略图（先给看片链接）。

## 7. 考卷（单测）

1. 提交的指纹与当前不符（正文被改）→ 该条拒绝，别的条照常。
2. 清单之后新排进来的条目（不在提交里）→ 不授权。
3. 发布日被改 / 已过 → 拒。
4. 已有 claimed / consumed 授权 → 拒；armed → 视为已授权、不重写。
5. 剔除写标记 + 删发布日；每日排期器不再排它。
6. 非全局管理员 → 403；工单不属于这个客户 → 404。
7. 列表：只列 `publish_on ∈ [今天, 后天]`、没有 armed/claimed/consumed 授权的条目；`buildContext` 失败的条目带原因显示、不可勾。
8. 待办：有 N 条等放行 → 1 条待办；N=0 → 无。

## 8. 当场试跑

合并后，CTS 不开 `social_agent`：用每周排出来的条目（今天 08:30 第一次写库）在线上打开清单 GET，核对返回的条目与指纹；放行动作在 PM 亲手点之前不做。

## 9. v0.2 修订（子牙 + 魏征设计复审 6 条必改，全部吸收；§1–§8 与本节冲突时以本节为准）

**9.1 服务端自己核「这条在清单上」（必改 1）**
- 放行接口不收客户端的清单编号。服务端按 GET 的同一套条件重建清单（发布日在今天..后天、没有 armed/claimed/consumed 授权、没剔除、`buildContext` 通过），每条提交必须在重建结果里且指纹、发布日一致；不在 → 该条拒绝（`not_on_list`）。
- `list_id` 由服务端对**本次批准的条目**重算（sha256，按发布日排序的 [工单 id, 指纹, 发布日]），写进授权 `card_run_id = daily-list:<list_id 前 16 位>` 与回执。
- 开关：`reelCardMode !== 'scheduled'` → 放行 409；GET 照列但每条 `selectable=false`，原因「按日公开没打开」。

**9.2 没勾 ≠ 剔除（必改 2）**
- 剔除是单独按钮、必须填原因，每次只剔一条。没勾的条目本次不批，留在清单里，到期按 9.5 处理。
- `buildContext` 失败、不可勾的条目永不自动剔除。

**9.3 剔除只有一个写入点，且留在版本分组里（必改 3）**
- 标记写在工单 `brief.weekly_pack.excluded_by_card = { at, by, reason }`，同时删 `publish_on`（乐观锁）。
- `schedule-writer.ts` 的 `refusalFor` 新增拒绝 `excluded_by_card`：每周、每日两条排期路径都经过它。
- 每日版本规则：被剔除的条目继续参与分组；**同组最新一条是被剔除的那条 → 整组不排**（最新：`excluded_by_card`，其余：`version_excluded`）。只有剔除之后新出的版本（创建更晚、成为最新）才能排。每周路径本来只留最新一条，最新被写入器拒绝 → 整组不排，旧版本不复活。
- 清单授权路径拒绝带 `excluded_by_card` 的工单；写入器的「已有转公开记录」判断也看 `scheduled_go_public`（建议 3）。

**9.4 批次回执落库（必改 4）**
- 每次放行 / 剔除在 `flywheel_actions` 写一行，`action_type = social_daily_list_decision`（新增一行数据，不改表结构）：request_id、client_id、list_id、actor、每条 { work_order_id, fingerprint, publish_on, outcome, reason }、dry_run、no_publish: true（只授权、不发布）、created_at。
- 不上 Inngest 的原因：放行只写授权，执行器每 30 分钟自己读授权（拉模式）；替代回执就是这一行。顺带发一个 `social/daily_list.decided` 事件（只供以后订阅，现在没人听）。

**9.5 时间缺口与过期（必改 5）**
- 每日排期提前到新西兰 **06:30**（`SOCIAL_WEEKLY_DRAFT_CRON` 改 `30 6 * * *`，登记表同步），早于今日待办（07:00/08:00，周一到周五）。每周节奏的客户也随之提早 2 小时，行为不变。
- 待办统计「发布日 ≥ 今天、没授权、没剔除」，不只看到后天；周六周日没有待办，所以周五的待办会带上周末的条目。
- 新待办 `reel_daily_list_pending`，归 `decide` 栏（对外、撤不回）。只对开了社媒 Agent 的客户出。
- 过期：每日排期跑时，把「发布日已过、从没授权（没有 armed/claimed/consumed）、没剔除」的工单删掉 `publish_on`，写 `brief.weekly_pack.expired_unapproved = { at, publish_on }`，让它回到内容池；不算剔除、不算判错；计数进运行回执，待办加一句「昨天有 N 条没批，已过期回到池子」。只对开了社媒 Agent 的客户做。

**9.6 考卷与试跑（必改 6）**
- GET 与放行两头各一题：事实错、禁词、无出镜授权、不在内容池、清单之后新增。
- 另加：清单窗口外的条目被拒；开关没开 409；没勾不等于剔除；剔除最新版本后旧版本不复活；每周路径也拒绝剔除过的；过期条目删掉发布日；剔除与授权并发（同一条先剔后批 → 批被拒）。
- 放行接口支持 `dry_run`：逐条给判定、不写库。当场试跑 = 上线后对 CTS 线上条目 GET + 放行 `dry_run` 跑一次完整链路。

**9.7 建议吸收**
- 默认勾选：事实核对有提醒的不默认勾；今天的条目已过公开时点时提示「授权后下一次检查（30 分钟内）公开」。
- 「不做」各开一张台账卡：清除剔除标记的界面；计划 §4 的自动降级 / 升级与每日上限执行前当场核；平台 24 小时 30 条检查。
