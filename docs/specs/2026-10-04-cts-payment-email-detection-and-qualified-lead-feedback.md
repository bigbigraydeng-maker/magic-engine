## 0. 先说结论

1. **成交识别能做，大半零件已有，但比第一版想的要动更多地方。** 邮箱每天已同步；"我们自己发出的『款已收到』确认句"识别器已存在（`src/lib/mailchimp/paid-signal.ts`，现在只给邮件营销打标签，没写回成交表）。缺：读完整正文、提取金额和发票号、区分定金/全款、对上 Facebook 线索、防重复、写进现有成交审核链。
2. **成交走现有闸门**：来源用已有的 `inbox_extract`（数据库约束已含，不用改）→ 双车道（PM 2026-10-04 改口：不要人批）：证据齐全的自动车道由 AI 自动批准路径外发，有疑点的进人工审核页 → `sendApprovedOutcome`。**但现有"AI 自动批准"会放行任何来源的待批成交（复审查实：查询里没有按来源过滤），必须同 PR 先堵上，否则人工闸是摆设。**
3. **"合格"标回 Meta 潜在客户中心：没找到官方直接改阶段的接口（未实测）。** 可走的是 CRM 线索阶段回传，网上资料写的门槛是"月 ≥200 线索 / 28 天内 / 转化率 1–40%"，**这些数字我只读到摘要级别，没逐字核实，CTS 满不满足现在不知道**，所以先量、先核（PR0），再决定后面做不做。
4. **对 Meta 的期望要降低**：员工记录没有日期、Meta 事件不得早于 7 天、CRM 回传另有 28 天限制。这套**只改善今后的线索**；旧的合格和成交补不回广告学习。
5. **【PM 2026-10-04 改口：成交不要人批，查到付款凭据就自动标成交并发送】** 这消除了"周末没人批发不出去"的问题，但把"人审"换成"机器自动"：撤不回的事件现在只靠规则把关。所以采用**双车道**（§5）：证据齐全的走自动车道，有任何疑点的才留给人；上线前先空跑观察（§7-9）。

## 2. 数据流

```
 CTS 邮箱 info@（Graph，Inbox + Sent Items）
   │  已有：每天同步，只存约 255 字摘要
   ▼
 [新 A1] 取全文：对窗口内所有 outbound 邮件按 message id 取完整正文（有数量上限、分块）
   │      （不靠 255 字摘要筛——确认句常在摘要之后，会漏单）
   ▼
 [新 A2] 剥离引用链/转发/页脚，再判定（见 §3）；只在命中确认句的同一句或相邻句里取金额
   │      输出：类型(deposit/full/balance/unknown) · 金额+币种 · 发票号 · 证据位置(邮件id+偏移)
   ▼
 [新 A3] 对线索：邮箱精确 = 唯一可自动绑定；电话后8位(须同国家码)/全名 = 只是候选，批准人点选
   │      lead id 来源：Sheet1 同邮箱那一行（现成可靠）；contacts→touchpoint 这条链未核实，作兜底
   ▼
 [新 A4] 查重（见 §3 防重）→ intake（现有 buildIntakeRow）：
   │      source_kind=inbox_extract，source_ref=邮件id，order_ref=发票号，必须有 contact_id
   │      review_status=pending_review；AI 自动批准查询排除本来源（白名单制，见 §5）
   ▼
 人工审核页（现有）→ PM 批准（confirm:true，现有 CAS）
   ▼
 sendApprovedOutcome（现有）→ 7天窗口 / 拒联 / 唯一键 / dry_run → MetaCapiWriter（含 user_data.lead_id，PR #2210）
   ▼
 me_conversion_writebacks 回执 + me_conversion_audit（现有，只增不改）
```

**证据怎么存**（复审指出：审计表只增不删，存原文会和"客人要求删除个人信息"冲突）：库里只存**邮件 id + 偏移量 + 发票号**，不存邮件原文句子；审核页需要展示证据句时，**现场回 Graph 取**。取不到分两种：Graph 暂时失败 → 显示"暂时读不到，稍后重试"，不算失败也不放行；邮件确已被删 → 不得批准（保守取舍，宁可漏发不可凭空发）。
**删除个人信息**：邮件编号 `source_ref`、发票号 `order_ref` 只存在成交行里，这两列是不透明的业务编号、本身不指向某个人，实现时**没有**把它们补进"已删除必须为空"约束（清掉邮件编号会让防重键失效、同一封邮件会被重新识别）；客人要求删除时邮箱/电话/姓名/线索编号照旧清空；**审计表里不放发票号和邮箱**，只记"已创建 + 成交行编号"。

合格线索支线（B）：

```
 Sheet1 员工跟进记录（R列≤505行 / S列≥506行，CTS_NOTE_COLUMN_SWITCH_ROW）
   + 邮箱 outbound 是否有"发票已发出、未付"
   ▼
 [新 B1] 规则判定 qualified / excluded / ambiguous（纯函数，配置驱动）
   ▼  ambiguous → 小模型仲裁（可关）；输出必须带逐字引用，对不上整条丢弃
 [B2] 落点见 §4.4（与现有 Lead 事件的关系）
```

Inngest（CLAUDE.md §3）：成交识别作为 `conversion-daily-pipeline`（cron 06:00 NZ）的新步骤 `detect-cts-payments`，**放在 AI 审核步骤之前并分块**（现有 pipeline 按块 `step.run` 推进，避免撞单步时限）。该 pipeline **现在没有任何 `inngest.send`**，所以 `conversion.payment_email.detected`、`conversion.outcome.proposed` 两个业务可读事件都是**新建**，不是复用。回执 = `me_conversion_audit` 的 `created` 行 + 步骤计数（扫描几封 / 命中几封 / 对上线索几条 / 缺金额搁置几条 / 超 7 天几条 / unknown 几条）。人工批准只推进到下一事件，外发授权仍由 `sendApprovedOutcome` 的闸负责。

## 3. 成交判定规则、防重与误判风险

**算成交**（PM 2026-09-05：定金算，尾款不算）：
- "deposit … received" → `purchase`，金额 = 定金额。
- "received in full" 且该人之前**没有** purchase → `purchase`，金额 = 全款。
- 之后又来的 balance/final payment → **不入库，只记报表**。（复审指出：现有 `balance` 类型会被映射成真实发给 Meta 的 `BalancePaid` 事件，所以"记 balance"不等于"不发"；本设计选择干脆不生成 balance 记录。）
- **`unknown`（只写 "Payment received, thank you"，没写 deposit/full）：不进待批，只进报表。**

**防重**（Meta 服务端事件不去重，撤不回）：
- 现有 CTS 表格同步已经在写 `crm_sheet_sync` 的 purchase；现有唯一索引只管 `(client, source_kind, source_ref)`，**邮件来源与表格来源互相看不见**，同一人会出两条 Purchase。
- 新增一个**跨来源**防重键：有 `meta_lead_id` 时 = `(client, meta_lead_id, purchase)`；**没对上线索时退化为 `(client, 归一化邮箱, 发票号)`，两者都缺 = 不得进入可批准状态**（PR1 用 migration 落实）。
- 键的取值顺序写死：①有 `meta_lead_id` 用它；②否则用归一化邮箱+发票号；③两者都缺 → 不能自动判重，该人同客户**近 30 天内已有任何来源的 purchase**（含 `crm_sheet_sync`、`crm_stage_manual`、`messenger_conversation`）时一律标"疑似重复"进人工清单，不进待批。键必须覆盖**所有**现有成交来源，不只是表格同步。
- 重发同一份确认、换邮箱重复识别、人工补发都要被这个键挡住（PR3 测试覆盖，并含"重跑同一封邮件不会把已拒绝的记录重置为待批"）。

| 误判 | 后果 | 防线 |
|---|---|---|
| 催款信/付款条款被当收款（"once payment has been received…"） | 给没付的人发成交 | 沿用 paid-signal 条件词/否定词过滤 + 证据回原文核对 |
| 完整正文带引用链、页脚条款、内嵌转发（旧判据只看主题前缀） | 把引用里的金额/旧确认当本次 | **先剥离引用链和页脚再判定**；金额只在命中句同句/相邻句取；"balance $4,500 due" 这类第二个金额不取 |
| 多个金额/多张发票 | 金额取错 | 多于一个候选 = `金额存疑`，进人工，不选 |
| 客人自己说付了（inbound） | 假成交 | 只认 outbound 确认句，inbound 不产生成交 |
| 定金后取消/退款 | **事件撤不回** | 同线程近 N 天有 refund/cancel 字样 → 不进待批、只进人工清单；批准页展示线程提示。PM 要明确知道 **Meta 里没有撤回**；退款要在 CTS 自己的成交表留痕。**批准后、真正发出前的最后一刻再重查一次线程有无取消字样**；发出之后才发生的退款，没有补救办法，这是接受的风险（§7-8） |
| 付款人 ≠ 填表人（代付、夫妻、旅行社代订） | 挂到别人线索，污染 Meta 学习 | 邮箱精确才自动绑定；电话/名字只是候选，批准页显示线索摘要，批准人**点选**确认；多条同时命中不自动选 |
| 电话后 8 位撞号（+64 与 +61） | 对错人 | 必须同国家码 |
| 币种/GST | 金额错 | 只收 NZD/AUD/USD；GST 不推算，正文怎么写就怎么记 |
| 缺金额 | 无金额成交对优化价值有限，且 Meta 可能拒收 | PM 已定：仍进待批、可无金额发出（§7-1）；不估算、不按价目表补；PR0 核实 Meta 是否强制要金额 |
| 首次只回看 30 天 | 历史补不回 | 7 天外只记报表 |
| 候选筛选漏单 | 少识别 | 不靠摘要，改按全文（A1） |

**拒联闸**（复审指出现有代码只在 `contact_id` 非空时才查）：本来源**强制要求 `contact_id`**，没有 = 不入待批，否则"现有闸"其实没经过。

## 4. 合格线索：规则、Meta 侧、与现有实现的关系

### 4.1 Meta 侧能不能改"潜在客户中心"阶段（均**未经 CTS 账号实测**）
- 可查到的官方路：Conversions API for CRM（阶段变化作为事件回传，用 `lead_id` 对回）。
- **没找到官方 API 直接改潜在客户中心某条线索的阶段**；也没有资料说明 CRM 回传会不会把线索在"潜在客户中心"里自动移到对应列。要用 `test_event_code` 测试事件核实（PR5，测试事件不进广告系统）。
- 若 PM 要的是"看板里的列也变"而官方没有路 → 见 §7-4。

### 4.2 门槛是否成立（PR0 先量，量之前不开发 PR5）
- 月线索量：线索表约 786 行，覆盖多久未核实；若月均 <200 则 CRM 回传不成立。
- 转化率、28 天窗口、payload 字段：逐字核对官方文档后才写进结论（目前只是摘要级）。
- CTS 成交常 1–3 个月，成交大多超窗口；**"合格"比"成交"更适合这条路**。

### 4.3 合格规则
输入：员工跟进记录 + 是否开了定金发票未付（邮箱 outbound 发票/付款链接且无确认句）。
- **合格**（任一）：明确写 2027 / next year / 明年 / 具体月份想去；强烈兴趣词（very keen / interested / great talk，词表放行业配置），**哪怕没说时间也算（PM 2026-10-04 定：松口径）**；开了定金发票未付。兴趣来源 = 员工跟进记录 + 邮箱往来里客人表达的兴趣（后者只读本窗口已有的邮件摘要/全文，不新增存储）。
- 松口径的代价：按上个窗口人工分类粗算，合格占比从约一成升到约两成，仍在资料所写 1–40% 内，但分母要在 PR0 重算；"有意向但没说时间"这一档质量最低，人审时单独标出，便于日后回头统计这一档的实际成交率。
- **排除**（压倒合格）：wrong number / not interested / already booked 等。
- **含糊 → 不自动**：否定肯定并存、"keen"同句带 price/too expensive、既无时间也无强烈意向。
- 规则版本号写进每条结果。

| 误判 | 后果 | 防线 |
|---|---|---|
| 把不会买的标合格 | 广告学错人群 | 初期每条人审；含糊不自动；排除压倒合格 |
| 记录是旧的，后来已订别家 | 过期好评 | 邮箱近期有"已订/退款"则排除 |
| 员工记录没有日期 | event_time 只能取判定时刻 | 事件时间 = 判定时间；"线索创建超多少天不发"的天数**等 PR0 逐字核实官方门槛后再定**（暂按资料所写 28 天） |
| 同一线索反复判定 | Meta 不去重 | 库唯一键 `(meta_lead_id, 阶段)`，永远只发一次，发出后不降级 |
| 仲裁编造原因 | 假证据 | 逐字引用回原文核对，失败整条丢弃 |

### 4.4 与现有实现的关系（复审指出设计稿第一版漏了这点）
- `cts-crm-sheet-sync.ts` **已经**在产出"合格线索"（Lead 事件）：限 +64 电话、排除词写死 `wrong number / not interested`，且已有 `lead` 记录在走同一审核/外发链。
- 所以 PR4 **不是新增一路**，而是：**替换**现有判定函数（词表进配置、加 2027/明年/发票未付/含糊档），仍产出现有的 `lead` 记录；不并存两套，避免同一人出两种合格记录。
- 真正新增的只有 CRM 阶段回传（PR5）：需要新的 outcome 类型（`lead_stage`）。**这要 migration**：现有 `outcome_kind` 约束只允许 purchase/balance/lead，且"金额必填"约束会误伤阶段事件；TS 里的类型表、事件名映射、AI 审核文案也都是三值。所以 **PR1 必做，不是"可能为空"**。

## 5. 人工确认点

1. **成交：双车道（PM 2026-10-04 定：不要人批）**。
   - **自动车道**（全部满足才进）：outbound 确认句；类型明确为 deposit 或 full；邮箱精确对上线索；金额与币种在同句取到且唯一；无转发/引用冲突；线程无取消/退款字样；跨来源防重通过；7 天窗口内；强制 contact_id；非拒联。满足 → 自动写成交行（`inbox_extract`），走现有 AI 自动批准路径外发，**沿用其熔断与硬顶**（单批条数、金额上限）。
   - **人工车道**（任一不满足）：电话/名字候选、缺金额、多金额、疑似重复、有取消字样等 → 进审核页，不自动发。（PM 已定"没金额也发"：缺金额是否放进自动车道，等 PR0 核实 Meta 是否强制要金额后再定，在此之前缺金额留在人工车道。）
   - **AI 自动批准必须改成白名单制**：现状 `ai-auto-review-run` 的查询按客户、待批、未脱敏、重判次数过滤，没有来源条件，判据只有姓名/金额/天数，批准后直接外发；改成只有明确列出的来源才能自动批准，`inbox_extract` 仅在上述严格条件下加入（不是整个来源放开）。此改动与 PR3 同合并，单独算 A 级。白名单初始内容 = 生产里当前实际在被 AI 批准的来源（开工前先查 CTS/NAL 的 `ai_auto_review_enabled` 与已批记录来源分布），保证现有来源行为不变。
2. **对不上线索**：仍可批准（Meta 靠邮箱/电话匹配，PR #2210 前的老路），页面标红。
3. **合格批准**：初期每条人工；放开自动是后话，本设计不含。
4. **一次性测试事件**（PR5）：发到真实广告账号前必须 PM 回"可以"，且先用 `test_event_code`。
5. **干跑闸**：`clients.conversion_stage !== 'live'` 一律走现有 `dry_run`。
6. **剩余天数提醒**：批准页按剩余天数倒排，剩 ≤2 天标红并进今日待办提醒。

**PR0 实测（只读，生产库 CrazyContent，2026-10-04）：**
- CTS 开关现状：`conversion_stage=live`、`ai_auto_review_enabled=false`；`me_sale_outcomes` 里只有 `crm_sheet_sync` 的 lead 记录（已批 61 / 待批 66 / 已拒 533），**一条 purchase 都没有**。

## 12. 实现后 A 级复审（子牙 + 魏征 Round 1，2026-10-04）已落实的修改

以本节为准，覆盖前文与之冲突的写法（尤其 §3 防重键、§2 的"30 天"）：
- **防重**：数据库只保留一个唯一索引（同客户 + 同邮箱不分大小写 + 同单号）。去掉了"同一线索编号只能一条 purchase"的索引——同一客人订第二个团是合法的第二笔成交，线索级唯一会拦下它，并让表格同步把它当"已同步"吞掉。跨来源的"同一个人已有成交"由应用层判断：该联系人**已有任何来源、任何时间**的有效 purchase（不是文中写的"近 30 天"）就转人工；人工拒绝过的成交，30 天内同一联系人再识别出确认信也转人工，不自动发。
- **自动车道新增条件**：金额必须在确认句**同一句**（邻句金额带旗标、转人工）；邻句/全文出现 total/price/fee/fare/cancellation/refund 字样的金额不取；正文出现与所取币种不同的币种代码 → 转人工；收件人必须恰好一个且无抄送；取消/退款字样改查**本封邮件全文**（线程里存的只是 255 字摘要）；自动发送上限由 3 万降到 1 万。
- **识别器漏洞**：`is yet to be received / due to be received / required to be received` 这类"还没收到"的将来式原来被当成确认句（复审实测），已排除；口语新规则收紧为"received with thanks / received well"后必须是句末或 and。
- **熔断基线**：AI 熔断的"历史日均/单笔上限"只数 AI 自己批准的，邮箱识别的自动批准不再抬高它。
- **不饿死新邮件**：候选改为新到旧排序，单次上限 100 封，整段 90 秒时间预算，到点标 truncated。
- **待办出口**：新增待办类型 `payment_email_needs_human`（五类里归"系统判不了真假、要你认一下"），把"认出了款已收到却没法自动记成交"的邮件数量和原因分布下发到今日待办，不再只留在运行日志。
- 仍是已知缺口：①没有发票号也没有线索编号时，数据库兜不住，只靠应用层按联系人查重（并发或同一人两条联系人记录仍可能重复）；②自动批准后发送抛错的记录会停在"已批准"，靠人在页面重试（与 AI 路径一致）；③`do_not_contact` 只读联系人镜像列，发送环节才查不可变触点（发送仍会拦）。
