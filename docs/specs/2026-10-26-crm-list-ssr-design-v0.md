# 「全部客人」首屏由服务器直接带数据 —— 设计稿 v0（2026-10-26）

窗口 76 起草。状态：**设计稿，待子牙 + 魏征审**。风险级：**B**（不碰鉴权判据本身、不碰数据库、不改任何业务规则；但动的是员工天天用的那一页的取数路径）。
PM 2026-10-26 说「要有提速页面 loading」，看完实测分解后回「做」。

## 1. 现在慢在哪（实测，不是估计）

生产实测（Chrome，PM 账号，warm load）：页面约 **3.5 秒**可用。

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 服务器返回 HTML | 0.9 秒 | 现在返回的是**空壳**，不含任何客人数据 |
| 浏览器加载 JS 并 hydrate | ~0.05 秒 | 第一个接口请求在 0.95 秒才发出 |
| `/api/.../crm/contacts` | **1.4–1.6 秒** | 接口自带 `Server-Timing`，服务器端 1386ms |

接口内部（取自 `Server-Timing`，非推测）：
`enrich 516ms` · `touches_briefs 317ms` · `rpc_stages 189ms` · `gate 185ms` · `page_rows 176ms` · `assemble 3ms`

**关键结论：慢的不是某条查询重，是来回次数多。** 每次 Supabase 来回约 180ms，这一页要来回五六次。已验证两次：把「找同行/员工」从拉 2230 行降到 96 行（降 96%），只省约 30ms。所以继续抠查询没有意义。

**真正的浪费是：浏览器要等服务器把空页面发完、自己加载完，才回头去要数据——白白多等一轮。**

## 2. 要做的事

把「全部客人」第一屏改成**服务器一次把页面和数据一起发出来**。首屏不再有第二轮往返。

预期：3.5 秒 → **约 1.5 秒**（= 服务器渲染 HTML 时顺带算数据，省掉 0.9 秒空转 + 一轮网络往返）。

## 3. 怎么改

### 3.1 把取数逻辑抽成可复用函数（不改逻辑，只改位置）
`src/app/api/clients/[id]/crm/contacts/route.ts` 里的 `getPaged()` 现在直接返回 `NextResponse`。拆成两段：
- `loadPagedContacts(clientId, query, viewerEmail, timer) → PagedPayload`（纯数据，新文件 `src/lib/crm/contacts-page.ts`）
- 路由里的 `getPaged()` 变成薄壳：调上面那个 + 包成 `NextResponse` + 设 `Server-Timing`。

**逐字搬运，不许顺手改判据。** 搬完接口的返回必须与搬之前逐字一致（§5 有验收办法）。

### 3.2 页面拆成「服务器壳 + 客户端表格」
- 现 `app/.../crm/all/page.tsx`（783 行，`'use client'`）→ 原样搬到 `_components/AllContactsClient.tsx`，只加一个新 prop。
- 新 `page.tsx` 是**服务器组件**：跑同一道 `requirePaidClientAccess` 鉴权 → 调 `loadPagedContacts` → `<AllContactsClient initial={payload} .../>`。
- 客户端：`initial` 有值且这次是**默认视图**时，直接用它渲染，**跳过第一次 fetch**；之后翻页、筛选、搜索一切照旧走接口。

### 3.3 什么时候**不**做服务器首屏（必须守住）
网址带任何会改变首屏内容的参数时，服务器不预取，退回现在的行为：
- `?view=smart`（智能视图，另一条取数路径 `getPriority`）
- `?contact=`（直接打开某人抽屉）
- 任何筛选 / 搜索 / 翻页参数
理由：预取的是「默认平铺第 1 页」，参数一变就不是它，强行用会让用户先看到一屏错的再跳变。

## 4. 风险与守则（给复审重点看）

1. **鉴权不许绕过**：服务器组件必须跑与接口**同一个** `requirePaidClientAccess`，不通过就不渲染数据。这是这刀唯一碰到安全面的地方。
2. **首屏数据与客户端第一次请求必须同口径**：服务器用的 query 要与客户端默认 query 逐字相同（page=1、perPage、无筛选），否则会「先显示一屏、再跳变一屏」。
3. **不改任何业务判据**：分段、排序、同行/员工判定、补全层，一行都不动。
4. **失败要退回而不是炸页**：服务器预取抛错时，降级成现在的行为（发空壳、浏览器自己去取），页面不许白屏。
5. **观测不能丢**：SSR 路径也要记录耗时（服务器日志里打一条），否则以后没法回答「到底快了多少」。
6. **不引入新依赖、不改数据库、不碰 cron**。

## 5. 怎么验收（做完必须拿出这些证据）

1. **接口返回逐字未变**：抽离前后，用同一组参数各调一次 `/api/.../crm/contacts`，JSON 做深比较，必须完全相同（含 `total`、`columns`、`items` 顺序）。
2. **首屏内容与客户端渲染一致**：SSR 出来的第一屏与「关掉 SSR 时客户端取到的第一屏」items 的 id 顺序必须相同。
3. **实测前后对比**：同一台机器、同一账号，各测 3 次，记录「可用时间」与 `Server-Timing`，写进 PR。**没量到就不许说变快了。**
4. **带参数的网址不走 SSR**：`?view=smart` / `?contact=` 各测一次，行为与现在一致。
5. 全量测试 + 类型检查全绿；关键分支做变异测试。

## 6. 不做的事
- 不动智能视图（`getPriority`）的取数路径——它要拉全量触点，是另一件事，单独排。
- 不做缓存 / CDN。
- 不合并那几条并行的小接口（`workbench-summary`、`nudge-list` 等）——它们不在关键路径上。

---

## 7. v1 决定：**SSR 这刀不做**（2026-10-26，子牙 + 魏征两审后）

两位独立审查都给「需改后再审」，而且结论一致：**方向没错，但现在不值得做**。我逐条核实后同意，改做性价比高得多的那个。

### 7.1 我在 §2 写的「3.5 秒 → 1.5 秒」是错的

子牙和魏征各自指出同一件事：**那 0.9 秒不是空转**。`dashboard/layout.tsx` 和 `clients/[id]/layout.tsx` 本来就串着 `auth.getUser()` 和两次库查。阻塞式直出之后首字节要等到 2.0–2.3 秒，总可用 2.2–2.6 秒 —— 省约 1 秒，不是 1.5 秒；而且**这 2 秒里浏览器什么都不显示**，今天至少还有外壳和「加载中」。站内跳转（员工最常见的进入方式）会变成「点下去卡住两秒再整页跳出来」，体感更差。
另外 §1 的分解只解释了 2.35 秒，离实测 3.5 秒还差 1.1 秒（渲 50 行 + 几个并行小接口），这刀一点都不治。

### 7.2 「原样搬一下」搬不动 —— 四个硬拦路（我已逐条核实）

| 拦路 | 代码证据 | 后果 |
|---|---|---|
| 首次取数是 `Promise.all([contacts, pipeline-stages])` 两发 | `all/page.tsx:165-167` | 跳过它 → 阶段下拉空白、抽屉里改不了「到哪一步」、NAL「标已成交」面板失效 |
| `loading` 初值 `true`，表格整块被 `!loading` 挡住 | `page.tsx:55` / `:622` | 不跑首次取数 → 有数据也永远显示「加载中」 |
| 客户端每页 50，接口默认 100 | `page.tsx:78` vs `route.ts:76` | 首屏渲 100 行、分页器按 50 算 → 第 51–100 人翻页时重复出现 |
| 行内日期全按**运行时本地时区**算 | `contact-table-types.ts:135/147/155`、`list-helpers.ts`、`ContactTableRow.tsx:105` | 服务器 UTC、浏览器 NZDT（UTC+13）→ 新西兰每天 00:00–13:00 首屏把「今天」写成「昨天」，水合后再跳回。而日期列正是员工判断「现在该不该打」的依据 |

还有三条安全面：HTML 里会直接含客人姓名电话邮箱（必须显式 `force-dynamic`、`contacts-page.ts` 必须 `import 'server-only'` 以免 service_role 钥匙被带进浏览器包、以及**退出登录后按返回键**能否靠 bfcache 把名单重画出来 —— 共用电脑场景）。

### 7.3 改做这个（已实现）

魏征从同一份 `Server-Timing` 里挑出一处现成的浪费：`getPaged` 后半段是**严格串行**的 `touches_briefs 317ms` → `enrich 516ms`，而 `enrich` 的原料（`loadEnrichmentInputs`）**只要这一页的 contact id**，那串 id 在上一步 `page_ready` 就已经拿到了。照同文件 `touchesEarly`（`route.ts:509`）的现成写法提前发出去即可。

- 实测（同一组真实数据，各跑 3 次取中位数）：**301ms → 146ms，省 155ms / 51%**。
- 另加 `all/loading.tsx` 骨架屏：站内跳转从「原地不动」变成点下去立刻换屏。
- 代价：路由里约 10 行 + 一个新文件；不碰鉴权、不碰时区、不往 HTML 写客人信息、不碰缓存，`Server-Timing` 原样保留，787 行路由测试原样有效。

顺带修掉一处自己引入的回归：前面把「找同行/员工」改成按域名收窄后用到了 `.or()`，而路由测试的假数据库没实现这个方法 → `?kind=trade` 空列表那条测试 500。补了夹具（`route.test.ts` 的 builder 加 `or`），不是产品代码的问题。

### 7.4 以后真要做 SSR 的前提
先把上面四条拦路和三条安全面各自有结论；并且**不做阻塞式直出**，走 `Suspense` + async 服务器组件流式（首字节不被数据拖住），最好只直出前 10 行。本节即是那次的起点，不要再从 v0 开始。
