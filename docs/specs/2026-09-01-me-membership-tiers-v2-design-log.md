## 获客渠道 → 客户画像（2026-09-02）

**获客路径**：线上——PM 本人（大瑞老师）个人 IP 讲"海外流量"，覆盖小红书/LinkedIn/抖音；线下——演讲、商会活动。转化路径是**培训 → 体验 → 诊断 → 客户**，不是"投广告转化陌生人"。

**倒推的核心画像特征**：AU/NZ 华人中小生意主，靠商会/华人网络认识彼此（高密度熟人网络），数字营销基础一般，买单前先经过培训/诊断建立信任，同时要被中文圈（小红书/微信）和主流市场（Google/Facebook）两边看到。

### 修正（2026-09-03）：原"四画像"表把两个独立维度混成一件事

**发现的问题**：HBay 同时出现在"产品/门店型生意主"（生意形态）和"想省心的规模化老板"（服务档位偏好）两行——同一个客户不能同时是两个互斥画像的证据，根因是把**"这是什么生意"**和**"他想自己动手还是想找人管"**这两个独立维度硬塞进了一张表。改成两个独立轴：

**轴一：生意形态**（决定日常需要哪些功能）

| 类型 | 例子 | 生意逻辑 | 日活驱动 | 几乎不碰的东西 |
|---|---|---|---|---|
| A. 信任驱动型服务生意 | 旅行社（CTS）、地产经纪（Park Homes/Roman）、留学中介（双子）| 咨询成交，一单几千到几万，靠信任 | **CRM + 留资提醒**（私信/邮件里有没有新客人）| SEO 仪表盘、关键词报告——太技术 |
| B. 产品/门店型生意 | 地板经销（Oztop）、瓶装水（HBay）| 靠"被搜到 + 看着靠谱"驱动进店/下单，相对标准化 | **口碑监控（GBP 评分）+ 本地 SEO**，周活不是日活 | CRM——客户多是一次性路人，不是靠关系维护 |

**轴二：DIY vs 委托意愿**（决定买哪个档，跟生意形态无关）

| 类型 | 特征 | 日活驱动 |
|---|---|---|
| 新手观望 | 刚做完培训/诊断，还没决定认真投入 | **不会主动打开任何仪表盘** |
| 自己动手型 | 愿意自己操作工具 | 落在免费/$39/$199/$499，具体打开哪块由轴一决定 |
| 委托型 | 想要有人管，不是要工具 | 一个月一次月度策略会，日常操作型功能全部不碰 |

**用真实客户校验**：CTS（轴一 = A 服务型）+ 走 Enterprise（轴二 = 委托型）；HBay（轴一 = B 产品型）+ 也走 Enterprise（轴二 = 委托型）——两者生意形态不同，但都落在委托这一端，这才是他们都在定制档的真实原因，不是因为"日常行为一样"。

### 综合洞察：产品默认假设"每根支柱配一个仪表盘"是错的

轴二落在"新手观望"或"委托型"的客户**不会主动打开仪表盘**——不管轴一是 A 还是 B。这两类合起来可能是获客渠道里最大的一块，原设计里"主动推送/通知"只是分散在各支柱里的可选项，值得考虑**提升成一条跨支柱基础设施能力**：

- 免费/$39：每月一次"网站访问量 + 新联系人"邮件摘要，不用登录就能感知价值
- $199：加上"口碑/竞品关键变化"提醒（评分变了、竞品降价了）
- $499：更即时的推送（差评、广告异常、竞品大动作）

**层级判定（本节内已完成，非待办）**：`docs/specs/2026-06-05-mcp-phase2-product-design.md` §1.2/§1.3、§4.1-4.3、§5.2、§8 已经设计并拍板了同一条"跨支柱推送基础设施"——`clients.notification_email` 字段 + 后台 UI、`notification_log` 表（`channel` 字段本就预留 `'email' / future 'wechat'`）、周报渲染模板，PM 已拍板"周一 + 周五各一封"频率、微信渠道"暂不做"。跑 [me-platform-tier-gate](../../.claude/skills/me-platform-tier-gate/SKILL.md) 判定结果（Inline 模式）：

> [跟班 · Tier] 这是 **L1 平台基础设施**（跨 6 支柱的通知/摘要触达层，不专属某一支柱）——已在上述 2026-06-05 spec 里拍板为共享设计，本次只是在这层之上按会员档位加分层触发规则，不新增能力线、不需要登记 candidates。
> [跟班 · 判据] 换客户测试 ✓：`notification_email`/`notification_log`/触发规则全部按 `client_id` 参数化，没有一条默认行为只对首个客户成立；换行业测试 ✓：推送频率只随会员档位变化、不随行业变化，不存在"只对某行业成立"的默认值；红线 1（禁包装升级）✓ 未新造"XX Intelligence"名义；红线 2（禁客户/行业事实进 shared runtime）✓ 未写入客户名或行业硬编码。
> [跟班 · 结论] 归位既有 L1，无需登记候选，可以继续往下写方案——不允许绕开这份既有拍板重新设计一套并行的通知渠道。是**复用**该既有设计（大概率）、**修订**其范围（比如把"周报"扩展为按会员档位分级的推送触发条件/频率），还是有充分理由**废弃**重来，留给下方"待定"项继续讨论。

**渠道现状核查（2026-09-03 三次修正，重新按当前仓库状态跑 Reuse/Build-vs-Connect 判定）**：2026-06-05 spec 当时把邮件渠道锁定成 SendGrid，但那之后仓库已经落地了另一套事务邮件能力——`docs/STATE.md:195` 把 **Resend** 登记为"全部事务邮件"供应商，`docs/ENV.md:145` 已登记 `RESEND_API_KEY`，`src/lib/email/sender.ts` 已提供统一的 `meMailFrom`/`ME_MAIL_TO_ADDRESS` 封装，且 `src/app/api/cron/weekly-seo-report/route.ts:38-60` 已经用 `Resend` SDK + 这套封装每周给客户发周报。也就是说邮件发信能力**不是空白**，`admin-key-expiry/route.ts:5-6` 那句"SendGrid not yet built"只是一处没跟着 P1 → P22 之后的供应商切换更新的过期注释，不能当作"仓库仍然选型 SendGrid"的证据。**渠道选型改为已按现状复核**：邮件走**已建成的 Resend + `src/lib/email/sender.ts`**（不新增 SendGrid SDK / 不新增第二套邮件供应商），微信按 §1.3/§8 拍板"暂不做"不变。真正要新建的实施量收窄为：`clients.notification_email` 字段 + 后台 UI、`notification_log` 表 migration、按会员档位分层的触发规则、复用 `weekly-seo-report` 同款 Resend 发信路径的推送渲染模板/cron 路由——这些要计入 GO BUILD 工作量，但发信通道本身是复用而非新建。真正待定的只是"要不要在这条还没建的推送链路上按会员档位加分层触发规则"。

## 已定（截至 2026-09-01）

### 总体框架
- **不推翻 #1273-1276 的地基**，免费/$39 档的"网站+域名+邮箱"部分保留；这次重新设计的是**6 支柱在各档怎么分布 + 定价 + 具体额度**
- CRM / 邮件读取等工具走 **Connector 原则**：会积累数据、越用越准的判断层（学习型能力）—— ME 自己造（L1）；其他一切能买/能接的 —— 用 Connector 接，是"ME 帮你配好的工具"，不代表 ME 要重新发明它。跟已冻结的公司级战略决策 [#1131](https://github.com/bigbigraydeng-maker/magic-engine/issues/1131) 一致（ME 不做完整 CRM 公司，只做 CRM 之上的 Marketing-to-Sales 判断层）

### 免费档
- 定位：**数字基建，不是支柱能力**。6 支柱要等基建就绪后才能展开
- 功能：二级域名网站（一次性开发，边际成本近零）+ 每月一次网站流量报告 + 每日查收邮件内容
- **"每日查收邮件内容"是新能力，还没建过**——已记为待登记候选（不是 CTS 那种单客户定制邮箱托管，是面向所有自助客户的通用产品功能），登记判定推迟到设计定稿后再走 [me-platform-tier-gate](../../.claude/skills/me-platform-tier-gate/SKILL.md) 完整流程
- 名额策略未最终拍板（见"待定"）

### 跨档设计原则：agentic 是"从 $39 起就在跑的圆圈"，不是某个价位才解锁的开关（2026-09-02 修正）
- **错误理解（已推翻）**：不要把"AI 自主执行 vs 只给建议"当成某个价位（比如 $199 或 $499）才解锁的二元开关
- **正确模型**：从 $39 起 agent 就已经在跑了，档位越高不是"第一次有了 agent"，是**同一个 agent，圈子越套越大**。三个独立的轴：
  1. **宽度**：这根支柱在这个档位有没有（存在/不存在）
  2. **深度**：跑得多勤（频次）、能干多少事（权限范围，比如预算笼子大小）
  3. **综合实现能力**：花多少资源去实现——链接多少数据源、分析多深、调用多贵/多聪明的模型，这决定了离"真正对结果负责"的完整 IMPACT 闭环有多近
- 具体应用：广告支柱不是"$199 只给建议、$499 才有自主执行"，而是"$199 广告 agent 就已经能自主执行了，只是预算笼子小（$1,000/月硬顶）；$499 是同一个 agent，预算笼子改由客户自己配置真实预算（不是 ME 定一个更大的数字），差异在判断更深"（细节见下方矩阵）

### $39 档
- 核心原则：**"麻雀虽小，五脏俱全"**——哪怕功能窄，也必须是一个完整 IMPACT 闭环（发现问题 + 客户能自己动手 + 能看到结果变化），不能只给诊断不给"能自己修"的东西
- 支柱不强制每档都有，按**"AI 能不能独立判断 + 有没有对外发布/花钱风险"**排序进场，顺序由产品经理故意设计，用来引导客户往上升级：
  - **AI 可见度**：月度监控（1 个引擎，ChatGPT）+ 客户能自己动手的小任务（具体任务待定）
  - **竞品监控**：只读监控，无发布动作
  - **SEO**：轻量强度（弱于 $199），参考 Semrush 的打法（细节待定）
  - **口碑**：不止 GBP，还有行业专属口碑网络（餐饮、旅游各自的点评平台），前提是客户自己去授权绑定——这些行业专属 Connector 以后逐个接入时按 L2 Playbook 登记，非阻塞
  - **社媒（内容工厂：图片/视频）**：从 $39 起有，但数量/强度受限——图片 10-15 张/月、视频剪辑 2-3 条/月。**视频 = 剪辑客户上传素材，不是 AI 从零生成**（原因见下方"跨档设计原则"）
  - **广告**：$39 不给，从 $199 才开始有

### 跨档设计原则：视频功能默认走"剪辑客户素材"，不是"AI 生成"
- **原因**：AI 从零生成视频依赖完整 master brief 才能写出好提示词，在客户信任/数据还没建立起来的低档位是"抽盲盒"，质量没保证；而且 AI 生成视频（Muapi 类）单条真实成本 $0.6-4，是全场景唯一真正烧钱的项。剪辑客户自己上传的真实素材是确定性处理（掐头去尾+字幕+模板拼接），不用 AI 猜画面，稳定性更高，成本也低得多（是服务器渲染时间，不是按次调用生成式 API）
- **复用现状核查（2026-09-02 修正，别把 CLI 原型当已上线能力）**：客户免登录素材上传管道已上线，但只是把成片存成未分析的 `client_assets`；生产里唯一接了这条路径的入口是 `src/app/api/clients/[id]/content-factory/[postId]/video/route.ts`，它接收的是**人已经剪好的成片**，只做落库（写 `source_video_url`），不做任何剪辑。"边走边录"自动剪辑（`renderWalkTalkProof`，`src/lib/factory/walk-talk-proof.ts`）**没有接入任何生产 worker 或 API 路由**，目前只被 `scripts/render-walk-talk-proof.ts` / `scripts/render-walk-talk-from-srt.ts` 两个本地 CLI proof 脚本调用。也就是说"客户传素材，ME 剪"这条 $39 承诺里"ME 剪"的自动化部分（认领客户原片 → 剪辑 → 字幕 → 模板拼接 → 交付）**还没有产品化链路**，只有 PoC 脚本；GO BUILD 前要把这条从 CLI 原型接成真正的生产 worker，不能按"基本不用新建"排期
- 没素材可传时的兜底机制（要不要留 AI 生成保底、要不要设上传门槛）留给后续产品设计阶段决定，不占用这次分档设计的时间
- **这条原则默认对 $199/$499 也生效**，除非后面讨论到更高档位时明确要引入 AI 生成来补客户素材不足

### $39 档成本测算（真实数字，不是拍脑袋）
- 目标毛利 ≥80%，但 **80% 不能只算 compute 成本**——Stripe 手续费（2.9% + $0.30/笔）在 $39 这么薄的档位上就已经占了 3.7%，还没算客服/获客/基础设施
- 真实成本基准（引用 Claude 跨会话 memory `reference-ai-api-unit-costs-2026-08`，2026-08 公开定价，不在本仓库内，下次续聊时 Claude 会自动带上）：诊断/监控类 AI 调用每次 ~$0.05-0.30 NZD；图片 ~$0.03-0.05 NZD/张；**视频是全场景唯一真正烧钱的项目**，最低配（480p·6 秒）也要 ~$0.6-1 NZD，720p·15 秒能到 $4+
- **基础额度包**（compute 成本约 $1.5-3/用户/月，**compute-only contribution margin 92-96%，不是完整毛利**）：4 项监控（AI 可见度/竞品/SEO/口碑）各每月 1 次 + 图片 10-15 张/月 + **视频剪辑 2-3 条/月**（剪辑客户自传素材，不是 AI 生成——成本是 worker 渲染 + 存储 + 传输，按次调用生成式 API 的 $0.6-4/条不计入这里，单条剪辑成本远低于此）；加上 Stripe 手续费（$39×2.9%+$0.30=$1.431/笔）后，真实毛利约 **88.6%-92.5%**——且这仍未计入视频剪辑本身的 worker 渲染/存储/传输成本，也未计入客服和基础设施，完整毛利会比这个数更低
- **"挖爽感"加码版**（compute 成本约 $3-5/用户/月，同样是 compute-only 口径）：AI 可见度监控从月度提到**周度**（这是"周度提频"唯一生效的地方，基础额度包仍是月度）+ 每月额外送 1 条 AI 生成的最低配视频（480p·6 秒，区别于基础额度包"剪辑客户素材"的那 2-3 条）+ 每月一份可分享的"增长战报"一页纸（复用诊断报告生成器，几乎零成本，顺带是免费传播钩子）；加上 Stripe 手续费后真实毛利约 **83.5%-88.6%**，同样未计入 worker/存储/传输/客服/基础设施
- 技术实现：**复用现有 MTC 账本**（`src/lib/mtc/`），不新造配额系统——把"一次性买 MTC"扩展成"$39 订阅每月自动发一批 MTC"，这本来就是 #1275 的范围；视频/图片复用现成的视频工厂后台，不重造

### 这轮新增的 4 个功能（复用已有能力，2026-09-02 采纳 3 条 + 1 条另记候选）

1. **llms.txt 自动生成 + 提交** —— 填上 $39 档"AI 可见度小任务"的具体答案，已有试点验证过（[#1179](https://github.com/bigbigraydeng-maker/magic-engine/issues/1179)），低风险、可撤销、AI 能独立判断，放 $39
2. **效果归因反馈** —— 补上矩阵里一直缺的 IMPACT Check/Tune 环节（之前所有支柱都停在"Act"，没有"做完有没有效"的反馈），复用 CRM 已有的 `attribution.ts`，$199 起给
3. **竞品广告库透视** —— 用 Meta Ads Library 公开数据看竞品在投什么广告，不需要客户授权（零风险），放竞品支柱较低档位
4. **本地同行批量发现** —— 复用 `dataforseo/business-listings.ts`，PM 明确这**不是独立功能，就是竞品支柱本身**（可以是行业级批量扫，也可以是具体公司追踪），已合并进竞品支柱定义，不单独列

**广告笼子设计原则（2026-09-02 定稿，2026-09-02 补充护栏边界）**：**不限制功能，只限制预算**——笼子里客户能用的功能就是 Meta/Google/TikTok/ChatGPT 平台原生提供的那些，ME 不额外阉割"能不能开新广告系列"这类功能白名单。但**预算硬顶只是消费上限，不是唯一的安全阀**：预算内仍可能出现投错地域、受众被平台自动放宽、错误文案直接触达客户等事故。现有 `src/lib/ads-strategy/ad-draft.ts` 和 `src/lib/meta/ad-publisher.ts` 采用的"暂停创建 → 回读 → 人工批准 → 激活"模式必须作为独立于预算之外的护栏保留——动作授权范围、目标/创意回读校验、审批闸门、可回滚、紧急暂停按钮，都不能因为"不限制功能"这句话被理解为连审批/回读环节也一起去掉。

**广告 $499 vs 定制档的差异**：不是自动化程度不同（两者的"自主"范围一致，见下方澄清），是**配置方是谁**——$499 客户自己通过自助 UI 配置；定制档由 ME 的人帮客户摸清业务后配置。风险提示（未来做自助投放工具时要处理）：客户自己配错笼子（预算单位搞错、受众设太宽）时，钱烧出去之前没有人会发现，需要新手引导/合理默认值/紧急暂停按钮这类护栏。

**"自主执行"的边界澄清（2026-09-02 补充，消解与"人工批准"护栏的表述冲突）**：这里的"AI 在预算笼子里自主执行"指的是 agent 能自主完成**判断 + 起草**——不用人告诉它该不该投、投多少、投给谁，它在预算笼子和既有护栏范围内自己拿主意、自己生成待激活的广告草稿。但**激活动作本身不豁免**上面"广告笼子设计原则"里的"暂停创建 → 回读 → 人工批准 → 激活"模式：每一次新建/变更广告系列，AI 起草后仍停在暂停态，仍需人工回读确认才能真正花钱激活。也就是说，"自主"消灭的是"客户/PM 要手动想策略、手动配置广告"这一步，不消灭"钱花出去之前有人看一眼"这一步——$499 与定制档在这一点上完全一致，唯一差异仍是配置方是谁。

## 定制档：不重新设计服务内容，重新定义卖点

**结论（2026-09-02 四轮审阅收窄；2026-09-05 按 #1279 再次修正定价口径）**：定制档服务内容本身**不需要重新设计**——跨支柱综合判断 + 月度策略会 + VI 一致性协调这套"卖点"沿用已验证的 Enterprise FDE playbook（[`docs/registry/pricing-playbook-enterprise-fde.md`](../registry/pricing-playbook-enterprise-fde.md)）的**服务范围写法**没有问题。**但定价口径必须按 PM 2026-08-31 拍板（PR #1279）走**：该 playbook 原先的固定报价结构（一次性 Setup $3,000 + Base 月费 $2,500 起 + 广告管理费边际阶梯）**已作废**，定制档现在是 **case by case、逐单面议、对外不挂任何固定数字**。本设计早前版本（含会员对比页 artifact 初稿）曾照搬这套固定数字，属未核对 #1279 的疏漏，已于 2026-09-05 同步改为"逐单面议"。**"沿用"不等于"照单全收现有 ChatGPT 承诺"**：该 playbook 原先第 17 行把 Meta / Google / ChatGPT 三个平台的账号接管与**首次投放**写进 Setup Fee、第 34 行把 ChatGPT 列为广告管理费可选平台之一——这曾直接违反本文件上方"四个广告主仓库现状核查"的结论。**这处矛盾已解决**：playbook 第 17、34、70 行（Setup 说明、广告管理费可选平台、服务边界表）已于 2026-09-02 同步修订，移除 ChatGPT 首投与管理承诺，标注"待 Connector 完成上线门槛后生效"。**ChatGPT Ads Connector 在仓库里仍完全不存在**，连暂停/改预算这种最基础的管理动作都做不到，仍不能出现在任何承诺列表里（不分自助档还是定制档）；在 Connector 从零建完并通过首投上线门槛之前，定制档销售**不得**按修订前的 playbook 原文签约 ChatGPT 相关条款。

**原因**：$499 的自助工具本身应该已经足够好用（不是"故意做残"来逼你升级）。定制档真正卖的不是"更强的工具"，是**跨 6 支柱的综合判断 + 对最终增长结果负责**——自助档是每根支柱各自转各自的小闭环，定制档是 ME 的人把 6 个小闭环拧成一个大闭环（这个月预算该往 SEO 还是广告倾斜、品牌调性怎么在各渠道保持一致）。这跟 IMPACT 强调"完整闭环"的逻辑一致，且现有 Enterprise FDE playbook 的实际内容（月度策略会、跨渠道预算分配、VI 一致性协调）本来就是在做这件事——但这条"内容不用重新设计"的结论**仅限于非广告的策略/协调服务**，广告部分（尤其 ChatGPT）仍受 Connector 完成门槛约束，两者不能混为一谈。
