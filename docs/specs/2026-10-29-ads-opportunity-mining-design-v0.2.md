# 「广告机会挖掘」设计 · v0.2 · 只设计，未写代码 · 2026-10-29

> **一句话**：每天把 Meta 现成的"切法"数据（小时、版位、设备、年龄性别……）存下来，跟我们自己收到的真实进线和后续成交对上，
> 先用统计筛掉偶然、再让 AI 讲人话，找出人工看不到的漏钱点和便宜进线点，变成"建议做一个对照测试"，测完再验。
>
> **IMPACT 位置**（2026-10-29 按产品定义更正，见 v0.3 §0）：横跨闭环——数据底座与对账服务 **I（Inspect）/ M（Measure）**，挖机会排序属 **P（Prescribe）**，对照测试期满判定属 **C（Check）**，结论回写属 **T（Tune）**；数据底座同时是 Check 读结果的证据来源。不新增支柱，挂在既有「广告」支柱下。
> **风险级**：本文档 C。实现阶段 1（新表 + 视图 + 每天自动跑）**A，改库结构须 Ray 亲手合**；阶段 2–4 B；阶段 5（开 Meta 对照测试）A。
> **本稿不构成对任何自动改广告、自动花钱的授权。本模块任何时候都不向内核提交广告动作（§4.6）。**
>
> v0.1 → v0.2：吸收子牙（架构）与魏征（挑刺）两份审查，二者均为「改后放行」。逐条处理见 §10。v0.1 文件未提交，已由本稿替代。

## 4. 设计

### 4.1 不做"每分钟"，也不必"每小时去拉"

Meta 最细就是小时，而且报表本身有约 2 小时延迟。**一天结束后一次性拉"昨天按小时拆开"**，得到的就是完整的 24 小时，比每小时拉一次更准、更省额度。"一小时内发现出事"是心跳的活。

### 4.2 数据层：一张长表（阶段 1，A）

新表 `ad_breakdown_stats`：

| 列 | 说明 |
|---|---|
| `client_id`, `ad_account_id`, `level`（先只存 `ad`）, `entity_id` | |
| `stat_date` | 账户时区日期 |
| `breakdown_key` | `hour_account_tz`（主用）、`placement_device`、`age_gender`、`region`；观众时区小时如要留，另存 `hour_audience_tz`，只作参考 |
| `breakdown_value` | `jsonb` |
| `breakdown_sig` | 程序生成的文本键（固定键顺序、空值统一写法），**作唯一键用** |
| `spend`, `currency`, `impressions`, `clicks`, `link_clicks` | `reach` 不能跨小时或跨切法相加，Meta 在小时拆分下可能不给，实测后决定存不存 |
| `meta_leads` | Meta 自报留资（留资类几种动作**取最大值，不相加**，手册 §十三第二条）；拿不到存 `null`，不存 0 |
| `fetched_at` | |

- 唯一键 `(ad_account_id, level, entity_id, stat_date, breakdown_key, breakdown_sig)`；索引 `(client_id, breakdown_key, stat_date)`。
- 每天拉昨天 + 重拉前 7 天，用 `time_increment=1` 一次拉 8 天，每种切法每账户一次调用。
- 体量（子牙复算）：每账户每天写入约 1.8 万行（重拉覆盖），净新增约 2.3 千行。保留至少 13 个月。接口额度按这个量核，超限按心跳 v0.2 §10 的办法降频并写回执。
- 权限 `FOR ALL TO service_role USING (true) WITH CHECK (true)`。

### 4.3 进线层（阶段 1 一起建，A）

视图 `ad_lead_events_v`：Meta 表单进线 → 按**该广告所属账户的时区**换算本地小时、星期几 → 带 FB/IG。

质量分档用通用名 `lead / engaged / qualified / won`，各档对应哪个阶段由 `client_pipeline_stages` 配置（不写死任何客户的阶段名）。
判档规则：看**这条进线之后**这个人**曾经走到过的最高阶段**（读 `contact_stage_events`），不看当前阶段。报价后丢单的仍算 `qualified`；同一个人多次进线时，阶段变化只归给时间上最近的那次进线。

### 4.4 对账（Measure：数据可信度）

按**账户、滚动 7 天**比：Meta 报的留资 vs 我们收到的进线。差距 > 30% 且绝对差 ≥ 5 → 写回执，出 dev 车道待办「进线可能漏同步，或归因口径变了」。阈值是初值，跑 2–3 周再定。（v0.1 按"每条广告每天"比，CTS 每条广告每天不到 0.3 条，永远不会触发，已改。）

### 4.5 挖掘引擎：统计在前，AI 在后

**能算的组合（受 §2.1 限制）**

| 组合 | 花费侧 | 进线侧 | 口径 |
|---|---|---|---|
| 账户时区小时 × 星期几（按账户或按广告） | Meta | 我们的进线 | **双方核对过** |
| 版位 × 具体位置 × 设备 | Meta | Meta 自报 | 只有 Meta 口径 |
| 年龄 × 性别 | Meta | Meta 自报（未实测） | 只有 Meta 口径 |
| 地区 | Meta | 无 | 只能看点击率 / 千次曝光成本，不判进线 |

每个账户每周实际能比的格子在一两百个，不是"几千个"。

**第一层：确定性统计（纯函数，带夹具测试，放 `rules/stats.ts`）**

1. **比法**：每个格子跟"同账户其余格子合计"比，不跟包含它自己的总数比。
2. **样本门槛按"预期进线"**：按这个格子的花费 × 其余格子的平均进线率，算出它"本该来几条"；预期 ≥ 3 条才参与判断。点击少的漏钱格子（如视频插播位）因此不会被直接当成样本不足而漏掉。
3. **收缩估计**：小样本格子的进线率往整体拉，防止"1 次点击 1 条进线"排第一。
4. **多重比较控制**：同一类组合内用错误发现率控制（Benjamini–Hochberg，10%）。
5. **不反复挖同一批数据**：按**不重叠的 4 周窗口**判，每个窗口只判一次；第二个独立窗口方向一致，才升级为"可做测试"的发现。
6. **排除学习期、改设置后 7 天、Meta 实验期**（复用 §3），每次报告排除了多少花费。
7. **能力预估要先说清**：按 CTS 主账户每天约 4 条表单进线估算，**多数 4 周窗口会"没有发现"**。这是正常结果，不是系统坏了。阶段 3 用历史数据给出这个概率的实际估算，写进 v0.3。

阈值在阶段 3 回放**之前**锁定，写进配置和夹具；回放不许为了凑出某条结论调参数。

产出的发现分五类：

| 类型 | 判据 | 可给的处方 |
|---|---|---|
| 漏钱格子 | 花费占比 ≥ 5%，实际进线显著低于预期 | 对照测试 |
| 洼地 | 进线成本显著低于其余，花费占比低 | 对照测试 |
| 交叉反转 | 两个维度单看不显著，叠起来方向相反且显著 | 对照测试 |
| 时段差异 | 某时段显著贵或便宜 | **只出"建议设计对照测试"**，不出"建议改投放时段"（见下） |
| 质量错配 | 进线便宜但几乎不走到 `qualified` | 等质量数据攒够再开 |

**时段类为什么只能出测试建议**：
- 平均每条成本不等于多花一块钱的边际成本，高峰贵可能只是竞价本来就贵。
- 看到广告和提交表单之间有时间差，会跨小时；阶段 2 用真实数据量化这个差距的分布，再决定是否按"看到的时间"重新归位。
- 改投放时段要用总预算模式，一改就重置学习期（手册 §十三）。

**第二层：AI 解读**

- 输入**只有**过了筛子的格子（编号、数字、置信区间），不给原始数据。
- **固定格式输出**，每条必须引用格子编号；程序核对编号存在，**所有数字（含"建议测几天"）都由程序算好再填**，AI 写的数字一律丢弃。
- "可能原因"一律加"推测："字头。
- `analysis.ts` 的中文词表只作附加；上线前用中文样本测一轮护栏。
- 每客户每周一次，花费上限写进配置（复用 `safeCharge`），超限跳过并写回执。

### 4.6 出口：只建议"做对照测试"，绝不自动改广告

发现写进新表 `ad_opportunity_findings`（阶段 1 一起建）。状态：`proposed` → `accepted` → `testing` → `verified` / `failed` / `dismissed`。

- **本模块任何时候都不向内核提交广告动作。** 原因：据 2026-10-19 的记录（今天未重新核实），CTS / NAL 的全部 9 种广告动作在内核里是自动批准、永不过期，包括加广告组和调预算；走内核等于跳过 PM。实现时加一条测试，证明本模块的代码路径不会发出任何广告动作。
- **每次开对照测试都要 PM 本人逐条授权**，授权记录绑定这条发现的编号和测试方案。别的窗口转述不算。
- **测试用 Meta 自带的对照测试工具**（受众不重叠、预算可控），不用"同系列里复制一个组"：后者受众重叠、预算由系统自动分，新组还在学习期，天然吃亏，测不准。
- 给 PM 看的：每客户每周最多 3 条，进今日待办「要你拍板」车道；其余进**仅内部可见**的广告健康页「机会」卡片。对外不出现（若将来对客户展示，走对外文案与供应商名封装规则）。
- **验证**：测试期满，自动回读两组数据，用同一套统计判"真的更好吗"，写回 `verified` / `failed`。
- **学到的东西写进客户私有记忆，标"只供参考，不作任何自动动作的前提"。** 读它的只有本模块的 AI 解读层和人；广告自动驾驶、内核、D 系列规则不读。

### 4.7 工作流（Inngest）与回执

| 事件 | 触发 |
|---|---|
| `ads.breakdown_stats.captured` | 每天每账户拉完 |
| `ads.lead_reconcile.checked` | 对账完成 |
| `ads.opportunity.mined` | 每 4 周窗口挖掘完成（含 AI 花费） |
| `ads.opportunity.accepted` | PM 同意去设计测试（**不等于授权改广告**） |

## 7. 平台层级判定（Full）

**被判定对象**：广告多维切法存储 + 进线对账 + 统计/AI 机会挖掘 + 对照测试闭环。

**建议层级**：**L1 Capability**，挂在既有「广告」支柱下，为 Inspect / Measure / Prescribe / Check 共用的数据与分析能力扩展；Meta 读取属 **L3 Connector**（复用既有连接器）。

**归属**：☑ 6 支柱之一：广告。☑ 平台基础设施：Measurement / Verification（对账、测试判定）。

**换客户测试**：✓
- NAL（物流，进线多为私信）：统计口径不变；私信进线接不上 → 进线侧数据少 → 多数格子"样本不足"，**少出结论，不出错结论**。
- Roman（地产中介）：缺广告编号 → 时段类自动标"进线数据缺失"，只剩 Meta 口径的版位/设备类。
- 质量分档走 `client_pipeline_stages` 配置。

**换行业测试**：✓ 旅游 / 物流 / 地产的最佳时段天然不同，但判断方法相同；结论只落客户私有记忆，不内置任何"某行业晚上更好"的先验。

**智能层 or 执行手**：智能层（找机会、出对照测试建议、测试期满判定效果）；执行只能由 PM 本人授权开测试。

**红线检查**：
- 1 禁包装升级：✓ 是广告支柱既有闭环能力的扩展，不新设能力线
- 2 客户/行业事实不进共享代码：✓ 阈值、阶段映射、花费上限都在配置
- 3 禁直建 L1：⚠ 直接按 L1 设计。理由：多维存储、对账、统计筛选对任何投 Meta 的客户同样成立，客户差异只在配置。子牙 + 魏征已审，均为「改后放行」
- 4 / 5 换客户、换行业语义级：✓ 见上
- 6 走五道 Build Gate：✓ 实现前再过 Repository Fact
- 7 L2 只装行业级：✓ 不写行业剧本

**PM 待拍板项**：无新增（投入与优先级 PM 已于 2026-10-29 明确）。阶段 1 合并（A，改库结构）与阶段 5 第一条测试开投，届时各问一次。
