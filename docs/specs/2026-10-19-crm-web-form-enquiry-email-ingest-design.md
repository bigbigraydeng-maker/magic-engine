# 网站表单咨询邮件 → CRM 客人（定稿 v1.0：第一期已上线，第二期待样本）

状态：设计稿，只写文档，未写代码。风险级别：**B**（碰 CRM 入库和客人个人信息，按规矩视同两审）。
起因（2026-10-19）：PM 要「info 邮箱里最新的 Enquiry 同步进 CRM」；CTS 员工提交测试表单（姓名 Baker）后 CRM 里看不到。查下来不是同步慢，是系统按规则把表单通知邮件当「公司内部邮件」跳过了。统筹已定为 P0。

## 一、结论

- 网站联系表单的通知邮件是**从公司自己的邮箱（info@）发给自己的**。入库规则看「发件地址是不是自家域名」，命中就整封跳过、不建人。
- 结果：**真客人从网站表单发来的咨询，在员工第一次回复之前，CRM 里看不见**。员工回复后也**不一定**出现客人：没有客人来信的线程不建人，只会挂到「本来就存在的人」名下，所以会留下没有联系人的孤儿会话（子牙审查指出，原稿此处说错）。只读核实：「Contact form」类邮件会话 18 个，其中 8 个没挂联系人；「Tour enquiry」类 52 个，其中 7 个没挂联系人。合计至少 15 个真咨询线程在联系人列表里看不见（这只是有员工回复过的下界）。
- 修法：识别出这类通知邮件，**不看发件地址，改读表单里填的客人邮箱**，建人或匹配已有的人，挂「网站表单」渠道触点。表单里填的邮箱如果仍是自家域名，仍判员工、不建人（PM 2026-08-04「同事不建人」规则不变）。

## 四、设计

### 4.1 识别「这是网站表单通知」（缺一不可，避免误伤）
1. 收件箱方向（对方是发件人）；
2. 发件地址的域名是客户自家域名（也就是现在被跳过的那一类）；
3. 主题去掉开头的 `Re:` / `Fw:` / `回复:` 后，**以**该客户的「表单通知主题前缀」开头。
   - 注意：现有 `isFormEnquirySubject` 是 `/contact form/i`，匹配主题任意位置，是给「已建人后判是不是咨询」用的，**不能当识别器**；识别器要新写（匹配开头）。
   - 前缀清单放客户配置（`leads_config` 新增可选清单，默认只含 `contact form`；CTS 再加 `tour enquiry`、`tailor-made enquiry`）。**必须同时做设置页面板和保存接口白名单**（保存接口是显式白名单，只往配置里加一个键，FDE 填不进去），否则字段没人能填。

### 4.2 提取客人是谁
优先级：①Reply-To 里的邮箱（列表读取的 `$select` 要新增 `replyTo`；单封读全文的 `$select` 也要加）；②没有就对这一封读全文（沿用 `fetchMessageText`，只对已识别的表单通知调用），按样本确定的格式取「Email」「电话」「姓名」行。
- **识别和提取放在 `syncMailbox` 里、读完邮件之后、`planMailIngest` 之前**（`planMailIngest` 是纯函数、不碰网络）。给 `MailMessage` 加可选字段 `formCustomer?: {email, name, phone}`，`planMailIngest` 据此处理。
- **线程层先扫描**：info@ 发给 info@ 时，已发送文件夹里还有一份副本（对方也是 info@）。按时间排序可能让副本先命中「自家域跳过」，把整条线程（含客人原信）作废。所以要先找出含表单通知的会话，再决定线程对方；**只丢那份已发送副本，不丢线程**。
- **每小时重复读的去重**：回看窗口里同一封通知每轮都会读到，先查 `conversation_messages` 里是否已有该消息 id，已有就不再拉全文。
- 取不到合法邮箱 → **不猜、不建人**，走 4.5。
- 取到的邮箱再过一遍现有 `classifySender`：仍是自家域名 → 判员工（测试单），不建人；是机器人地址 → 跳过。**Baker 这种测试单仍不进客人名单，这是设计，不是漏。**
- **防伪造（魏征/子牙都要求）**：自家域发件地址不等于真从网站表单来，外人可以伪造 From 并指定 Reply-To。关口：主题必须匹配 + 提取的邮箱必须过 `classifySender` + 只有 Reply-To 与正文「Email」一致、或正文有明确的表单字段结构时才采信；是否核对邮件认证头（Graph 的 `internetMessageHeaders`）待样本验证后定。垃圾提交会进名单这一点要明说接受与否（见 4.5 的限流）。

### 4.3 建人 / 匹配 / 触点
- **复用现成封装 `src/lib/crm/web-form-lead.ts:mirrorWebFormLead`（原稿漏了）**：它已经做「建人 + web_form 触点」，且带 `mergeStrategy:'reject'`、`overwriteDisplayName:false`、按客户国家补电话区号、遇到歧义身份不抛出。**绝不能直接调默认的 `resolveContact`**：默认是自动合并，网站表单是公开的，有人用 A 的邮箱加 B 的电话提交一次，两个真人的全部历史就被永久合并、撤不回（子牙判：若仍走默认合并，风险级别升 A）。
- 它目前要求传 `leadId` 当幂等键；改造让调用方传「Graph 消息 id」，`source_ref` 沿用该 id。官网以后若也往 `/api/clients/[id]/leads` 推同一条咨询，会重复出现——两条路并存时要以邮箱 + 时间窗去重，实现时明确。
- 触点来源：邮件触点现在 `channel='email'`、`source='microsoft_mail'`（写死在 `writeTouchpoints`）。**通知邮件本身不写邮件触点，只写一条 `web_form` 触点**，避免同一封信两条触点。
- 会话（`conversations`）的「对方」改成这位客人（`storeThread` 用 `thread.counterparty` 写会话对方和发件人名，对方改对就不会把 info@ 写进去）。
- 通知邮件触发下游：`runAgentCustomerHook` 与 `emitNewInboundMessageEvents` 会对这封也触发（事件接 F1-F4 治理回复）；**要明确：表单咨询是否也触发自动回复相关事件**——这是业务判断，默认不触发，待 PM 定。
- 「最早来源」：`first_source` 只在身份新建时写，已经以 email 身份存在的客人（员工先回复过的）仍显示「邮件」，来源标签靠新增的 web_form 触点补。顺带：来源标签文案三处不一致（列表「官网表单」、时间线/看板「网站表单」），实现时一并统一。

### 4.4 不误伤员工内部邮件
只有同时满足 4.1 三条才进这条路；真员工之间的内部邮件（主题不含表单前缀）仍按现在规则跳过。表单里填的邮箱是自家域名仍判员工。

### 4.5 识别不了时：fail-closed + 回执
- 现有同步的纪律是「一条失败就在该线程提前停，水位线不越过失败那条」（`syncMailbox`），原稿「一封异常不影响同一轮其它邮件」与此冲突，**改为沿用现有纪律**：识别为表单但提取不到合法邮箱 → 不建人、不丢弃，按线程失败处理（水位线不前进，下一轮靠 6 小时回看窗口重试），并在回执里计数；
- 回执新增 `formEnquiries`：识别几封 / 新建几人 / 匹配几人 / 判员工测试几封 / 提取失败几封 / 因去重跳过几封。要改的文件：`mail-ingest.ts`（`MailSyncResult`、返回体）、`api/cron/mailbox-sync/route.ts`、`api/cron/messenger-sync-hourly/route.ts`（汇总里每个邮箱的结果已带上，合计要自己加）及对应测试；
- **连续提取失败要进今日待办**：`mailbox-run.ts` 的 `loadMailboxRun` 目前只读最近一条终态记录，「连续」需要读多轮，要扩展；
- **限流 / 去重**：同一邮箱或同一电话短时间重复提交不重复建人；单轮新建人数设上限，超过上限转待办人工看（防机器人批量提交）。

### 4.6 为什么不是别的办法
- 「把 info@ 从自家域名里排除」：会让真同事之间的邮件被建成客人，违反 8/4 规则。
- 「让网站表单直接写 CRM」：是另一条更大的改动（官网插件），不在本稿；本稿只修邮箱这条已经在跑的路。

## 五、历史回补（只估算，不执行，等 PM 点头）

- **能估多少：** 回执里只有「地址 + 被跳过的封数」，每小时同步会重新读到同一批邮件，**同一封会被重复计数，所以算不出过去 N 天被跳过的表单原信封数**。库里也没有这些原信（被跳过的信从没入库）。
- **能得到的下界：** CRM 里「Contact form:」会话 22 个，说明至少这些客人在员工回复后被看见；从没被回复过的表单咨询，库里没有任何痕迹。
- **要得到真数：** 请有 info@ 权限的人按 `docs/clients/cts/2026-10-13-cts-enquiry-definition-and-form-spec.md` §4 的方法，在邮箱里搜 `Contact form:`、`Tour enquiry:` 各数一个窗口的封数；或用 GA4 的 `enquiry_thank_you` 事件对照。
- **回补本身是写生产库**（把过去的表单原信补成客人和触点），属于需要 PM 点头的操作：先出数量与样例名单（不含内容）给 PM 看，再执行。本稿不跑。

## 八、临时办法（更正：原稿说「换非 CTS 邮箱提交就能验证」是错的）

## 十、10/21 前的最小可上线版本（统筹要求：CTS 10/22 开投，线索走「广告 → 官网 → 联系表单」）

### 10.1 范围（只做这些）
1. **只识别 `Contact form:` 一类**（样本已有）。`Tour enquiry:` 等其它类先不做，没样本不假设。
2. **识别条件**（缺一不可）：收件箱方向；发件地址**等于配置里的表单发信地址**（`info@ctstours.co.nz`，不是整个自家域）；主题去掉 `Re:/Fw:/Fwd:/回复:` 后**以** `contact form:` 开头，且**带 Re/Fwd 前缀的一律不当表单**；认证头 `dmarc=pass` 且 DKIM 的 `d=` 是自家域（读不到认证头 = 不采信，进失败回执，不建人）。
3. **提取**：Reply-To 的邮箱（必须与正文 `Email` 行一致才采信）；姓名取正文 `Name` 行；电话**只作为触点摘要的一部分，不作为身份**（魏征/子牙：带电话会把默认合并变危险）。
4. **建人**：复用 `mirrorWebFormLead` 的 `reject` 策略（不自动合并、不覆盖老客人姓名），**只带邮箱一个身份**；撞上歧义不抛出，记回执交人。提取的邮箱再过一次 `classifySender`：自家域 / 机器人地址 → 判员工或跳过，不建人（Baker 测试单仍不进客人名单）。
5. **触点**：只写一条 `web_form` 触点（摘要 = 兴趣 + 留言前 200 字，**不存电话和留言全文**）；这封通知**不写**邮件触点；会话对方 = 这位客人。
6. **不触发自动回复相关事件**（默认，待 PM 另定）。
7. **fail-closed**：识别为表单但认证不过 / 提取不到合法邮箱 / Reply-To 与正文邮箱不一致 → **不建人、不静默丢**：把这封存成会话+消息、对方标「待认人」（用于拦住水位线，下轮仍会重试），回执计数；连续失败进今日待办。
8. **限流**：单轮新建人数设上限（先定 20），超过的不自动建、转待办人工看。
9. **回执**：`MailSyncResult` 里新增 `formEnquiries` 计数（识别几封 / 建人 / 匹配 / 判员工 / 失败 / 去重跳过）。**不改两条 cron 路由文件**（避免被合并闸判成 A 级）：每个邮箱的完整结果已经原样带进每小时汇总的 `results`，不需要动路由。
