## 3. 设计

### 3.1 给 `crm_bookings` 增补两列（改已上线表；对方窗口已同意加在 bookings 上）

- `source` text **null 允许**，CHECK ∈ `company_confirmed` / `customer_stated` / `staff_entered`。旧行（现在 0 行）与以后手工录的单，来源为空 = 页面显示「来源未标」，按「待核实」算，**不回填猜值**。
- `evidence_ref` text null，存**发票号**（CTS 发票号 = 5 位纯数字，由导入工具校验，数据库只约束长度与不含空白；归一化 = 大写 + 去掉空白和连字符，与付款邮件识别的发票号提取用同一个规则）。同客户同号唯一（部分唯一索引 `where evidence_ref is not null`）；**建单后不可改**（触发器，写法照 `crm_booking_events` 追加审计的样子），新列必须进审计的 changed 列表。
- `crm_booking_create` 加两个可选参数 `p_source`、`p_evidence_ref`（默认 null，**旧调用不受影响**）；`company_confirmed` 必须同时带 `evidence_ref`（函数里校验）。
- 写 `source`/`evidence_ref` 的唯一入口是该数据库函数；界面「加订单」第一步不暴露这两个字段。
- 迁移只含 `alter table … add column`（可空，不重写表）+ 部分唯一索引 + 触发器 + 函数替换；先在本机 Postgres 沙盘重放，**生产 apply 要 PM 回「同意」**。

### 3.2 金额：第一步不显示（需要 PM 一句话）

`crm_bookings` 刻意**不存金额**（对方设计：只记进度）。统筹原先要「定金/全款金额」。要显示金额只有两条路：①给订单再加金额列（改表，且与对方设计取向相反）；②只显示「已收定金/已收尾款 N 单」（节点状态，不涉及金额）。**建议第一步走②**，金额等 PM 明说要再另议。见 §8 Q3。

### 3.3 销售进度页（独立只读页）

- **位置**：`/dashboard/clients/[id]/sales-progress`（服务端页；客户首页入口卡片、Tour 目录页页头链接留后续步骤）。不放进客人页，不放进 Tour 目录页（目录页页头写明不记订单、权限是另一份名单、81 号窗口正在改它）。
- **权限**：`requireBookingAccess(clientId, 'view')`（名单制）。页面、每个取数接口各自带同一道闸；无权限的账号取不到数据；换成别的客户 id 取不到。
- **共享代码里只认「销售单元」**：适配器接口 `listSalesUnits(clientId) → [{unitId, label, date?, capacity?, capacityNote?, unitStatus}]`；CTS 适配器读 `tour_catalog_departures`（只读，不写，不读 `internal` 其他键）；旅游词（团、出发日、座位）只在适配器与文案配置里。换成地产（楼盘/户型）或物流（发运批次）时外壳不改。
- **一行（一个出发日）显示**：
  1. **座位上限**：主来源 = 该出发日的 `internal.capacity`（内部座位，**不对外**；3 月四团均为 20）；若该团另有对外的团级 `max_group_size`（公开口径，上海周边团官方 18），**取两者较小者**并标注「内部 20 / 官方 18，按 18 算」。**不往 `max_group_size` 写 20，也不改任何对外字段**（CTS 红线：对外不出现人数上限；`max_group_size` 在发给官网的数据里，而 `internal` 不进任何输出）。都没有 = 「上限未设置」，剩余显示「上限未设置」，不默认 20。适配器只取 `internal.capacity` 这一个键，读后丢弃整个 `internal`。
  2. **已订人数**（只统计 `status=active`，人数 = 各单 `party_size` 相加）：**公司确认**（`source=company_confirmed`）｜**客人自述**（`customer_stated`）｜**待核实**（`staff_entered` 与来源未标）。**对外只说「公司确认」一栏。**
  3. **人数未填 N 单**：`party_size` 为空的订单单列，**不按 1 计**（订单窗口确认员工不一定都填）。
  4. **剩余**（保守算法，避免第一批全是待核实时高估空位而超卖）：上限 − （三栏之和）；旁小字「仅算公司确认：N」；若还有人数未填的单，加提示「另有 N 单人数未填，剩余可能更少」。已订 > 上限显示红字「超订 N 人」，不显示负数；只提示不拦截，文案写明「系统不会拦截，请销售自行把关」。
  5. **付款进度**：已收定金 N 单 / 已收尾款 N 单（读节点状态，不涉及金额；§3.2）。
  6. **证据强度**（由现有列推出，一行取最弱）：**强** = 公司确认且定金已收；**弱** = 公司确认但定金未收；**未核实** = 客人自述 / 待核实。
  7. 每个数字可点开看是哪几张订单（只显示发票号、日期，不显示姓名电话）。
  8. 页头「数据截至 xx 时刻」；订单与出发日同一次查询读取。已取消的订单不计入任何栏；已取消/已关闭的出发日不进主列表，上面挂着的有效订单单列一行。
- 另放两行小字：「订单未挂出发日」条数、「CRM 里阶段为已付但没有订单」的人数（只读差额，不联动）；3/25 等上限、3/27 日本团无上限的显示规则同上。
- 「公司确认」口径、剩余算法写在页面的服务端常量 + 测试里，第一步不做配置界面。
- **测试**：无权限账号/别的客户 id 取不到；适配器无 `insert/update/delete/rpc` 且返回值里无 `internal` 其他键（用含航司航线的夹具断言）；内部 20 + 官方 18 → 按 18 并带差异说明；上限都缺 → 上限未设置；`party_size` 空的单不进人数、进「未填」；取消的单不计；剩余保守算法与超订显示。

### 3.4 3 月四团的数据怎么进来（导入工具）

- 来源：邮箱只读摸出的草稿（本地 Dropbox，含客人信息，**不进仓库**）；3/11 共 8 单 15 人、3/18 共 1 单 2 人、3/25 与 3/26 暂 0 单；全部是定金；CTS 销售对 8 条问题的核对回复后再定稿。
- 工具：本地脚本（不进生产服务），三步：**预览**（按电话/邮箱对 `contacts`，**只读查找，不调 `resolveContact`**——它会在没命中时建人、命中时改最近接触时间；对不上或命中两人的单进「待人判断」清单，不自动建、不自动合并；打码清单 + 汇总）→ **PM 在对话里说「导」**才执行 → **应用**：逐单调 `crm_booking_create`（带来源与发票号，`departure_id` 用团目录现值，快照由函数写），每单一个事务、带审计；任何一单失败立即停止并报告已成功的几单。
- **撤回**：对已导入的单调现有的 update 函数置 `cancelled`，`cancel_note` 写「导入批次 <日期> 撤回」；不删行。
- 「定金/尾款是同一单的两个节点，不是两张订单」：草稿里「同一客人同一团两张发票」的情形不自动判断，进待人判断由人选（尾款 → 在原单上用现有的「已收款」操作；另一批人 → 见 §8）。
- 个人信息：原件不复制进仓库；脚本输出一律打码；PR/文档只出现代号。

### 3.5 「报价与付款」里的「报价」

订单从**发票**起算（`evidence_ref` 是发票号）。报价单号（如 `CTS4270406-…` 形状）是另一种编号，建单后 `evidence_ref` 不可改，报价→发票是两个编号，硬放同一行会冲突；报价阶段仍由 CRM 现有阶段承载。PM 若要在订单里看报价，另议。

## 6. 风险与防线

1. **错数**：对外只说「公司确认」；每单可点开看发票号；来源缺失一律按待核实；`party_size` 空不当 1；剩余用保守算法；同一发票号只能进一次（部分唯一索引）。
2. **钱与外发**：本设计没有任何到 `me_sale_outcomes`/Meta 的路径（只读 `crm_bookings` 与出发日）；第一步不显示金额、不存金额。
3. **不往对外字段写座位**：上限只读内部座位；`max_group_size` 只读不写；适配器测试断言。
4. **个人信息与权限**：页面名单制闸 + 取数接口各自同闸；号码/姓名不出现在进度页；导入原件不进仓库。
5. **改已上线表**：只加可空列 + 部分唯一索引 + 触发器 + 带默认值的新参数（旧调用不受影响）；迁移先在沙盘重放；生产 apply 要 PM 同意；回滚 = 清空新列并去掉触发器/索引（列可空，旧数据不受影响）。
6. **与订单与付款窗口的边界**：本设计不改它的付款节点、提醒、自动勾选逻辑；只加两列和一个读页；加列的迁移由我出方案，**它的作者复核**（对方已同意方向，未复核具体 SQL）。
