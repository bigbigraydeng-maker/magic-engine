# 跨账户「当日实际花费」闸 —— 设计稿 v0.1（只设计，无代码）

日期：2026-10-19 · 窗口：119 · 风险级别：**A**（碰钱的闸）→ 本稿只出设计，不动代码
触发：PM 2026-10-19「按顺序做」四件事里的第 4 件

---

## 0. 先更正一条写错了的现状

[docs/ROADMAP.md](../ROADMAP.md) 写「**运行时跨账户日上限强制** —— 运行时没人查『这个客户今天全部账户加起来花了多少』，洞仍开着」。

**这句话不准确。** 实查 [`src/lib/capabilities/ads/envelope-facts.ts`](../../src/lib/capabilities/ads/envelope-facts.ts)：

| 位置 | 它真的在比什么 |
|---|---|
| 第 128-138 行 | 各账户**上限之和** ≤ 客户总闸（配置是否自相矛盾） |
| 第 250-251 行 | 单账户**在投预算设置之和** ≤ 该账户上限 |
| 第 256-259 行 | **跨账户在投预算设置之和** ≤ 客户总闸 |

所以运行时**有**一道跨账户闸，而且在授权和下发给 provider 前各查一次。准确的说法是：

> **闸在，但口径是「预算设置的合计」，不是「今天实际花掉多少」。**

这个差别要紧，因为两者会分开：

1. **Meta 单日可超投**（官方允许日预算上浮，实测上限约 25%）——设置合计不超，实际花费可以超
2. **改预算不退已花的钱**——上午 $120 的预算已经花掉 $100，下午调成 $40，当天实际仍是 $100 起
3. **CBO 与 ABO 混用**时，判据只认 `budget_level='abo'` 的广告组预算（第 250 行），系列级 CBO 预算走另一条；两种并存的账户，"设置合计"本身就不是当天会花的钱
4. 卫青 2026-09-27 查实的 CTS 事故（两账户各花各的、合计 10 天超客户总闸）正是这个差别造成的——不是因为没有闸

## 1. 这道新闸要解决的，只有一件事

**在「今天这个客户名下所有广告账户加起来已经花了多少」超过客户总闸时，拦住任何会让它继续多花的动作。**

不负责：预算设置的自相矛盾（第 128 行已管）、单账户超投（第 250 行已管）、Meta 自己的超投行为（我们管不了，只能不再加钱）。

## 2. 最大的拦路事实：今天的花费我们现在拿不到

`circuit-cap-facts.ts` 的 `readLastCompleteSpend` 取的是**最后一个完整日**（昨天），因为 `ad_daily` 这类表由每天 06:00 NZ 那轮拉数写入。

所以「今天已经花了多少」有三条路，代价差很远：

| 路 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A · 保守折算** | 不拉新数据。用在投预算设置之和 × 超投余量系数（Meta 约 1.25）与客户总闸比，超了就拦 | 零新增 API 调用、零新表 | 会误拦（预算设的高但实际花不动的账户）；不是真花费 |
| **B · 动作前现拉** | 只在 Kernel 要动钱那一刻，对该客户所有账户各拉一次当日 insights | 每次动作几个 API 调用 | 当日 insights 本身滞后（Meta 自己有延迟），且拉数失败就得 fail-closed |
| **C · 当日多轮拉数** | 新增一个白天多次的拉数任务，把当日花费入库 | 新 cron / Inngest + 新表或新列 + 配额 | 最重；而且 `render.yaml` 是受保护路径，自动判 A 级 |

**建议：先做 A，把 B 留给「真的要放开自动加预算」那一步。** 理由：今天四个客户里 `autopilot_enabled` 只有一个是 true 且还在演练模式，零个广告动作真执行过（`action_runs` 里 `ads.*` 为 0 条）。在一次都没真跑过的链路上先上最重的 C，是在没有证据的地方加复杂度。

## 3. A 方案的判据（写成可实现的样子）

挂在哪：`envelope-facts.ts` 第 256-259 行那条跨账户比较之后，**加一条更严的**，不替换原有的。

```
已有：  跨账户在投预算设置之和  ≤  客户总闸
新增：  跨账户在投预算设置之和 × OVERSPEND_FACTOR  ≤  客户总闸
            其中 OVERSPEND_FACTOR = 1.25（Meta 日预算上浮余量，待核：见 §5）
```

- 任一账户读不到在投预算 / 币种 → 沿用现有 `unavailable`（fail-closed），不猜
- 只对**会让钱变多的动作**生效（`new_spend` 与加预算；`ads.*` 动作到 purpose 的映射已在同文件第 42 行附近）。暂停、关停这类让钱变少的动作**不受这条拦**，否则会出现"超支了反而不许暂停"
- 拒绝时的原因码要新开一个，不要混进现有的 `facts:客户当前跨账户日预算已超过客户总上限`——两条拒绝的含义不同，混在一起以后查不出是哪条拦的

## 4. 顺带必须一起修的两条（不修的话这道闸是装在沙子上）

1. **探针与闸的判据不一致**：`envelope-facts` 有「只绑 1 个账户且上限为空 → 回落成客户总闸」（第 129-131 行），`circuit-probe` 没有这个回落，所以它对单账户客户报的 `cap_missing` 是**假阻塞**。两边必须同源，否则探针每天报一个不存在的问题。
2. **CBO 预算不在判据里**：第 250 行只认 `budget_level='abo'`。先确认在投的客户里有没有 CBO 系列；有的话这道闸对那些系列等于不存在，要么补 CBO 口径，要么明说"本闸不覆盖 CBO"并在探针里把它标出来。
