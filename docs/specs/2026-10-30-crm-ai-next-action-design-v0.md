- **硬事实**：程序按消息方向和时间算出来、不需要读懂内容的事实（例如「客人某天发来消息，我们之后没有真人回过」）。

- **参考答案题库**：一批真实客人 + 一份答案，用来考模型。PM 逐条确认之前只叫「参考答案」，不叫「金标准」。

## 0. 给 PM 的一页

**第一件事：CRM 的核心改成「每位客人一张 AI 判断卡」，「今天要联系」按它排。**
现在的名单按「最近有动静」排，读不懂话：客人追问了没人回的被埋到一百多名，昨天打过去其实是语音信箱的却排第一。实验里 AI 前 25 名有 12 人要挪 10 位以上，你看过说「基本都对」。

**第二件事：分工是「程序算事实、模型读内容、规则当护栏」，而且模型不能悄悄把热的人藏起来。**
谁在等谁、连续几通没接、上封邮件几天没回、新线索 / 回头客、7 天发了几封——程序算。态度、今天做什么、渠道、理由——模型读原文判。客人在等我们 / 新线索 / 回头客这三类人，模型想把他挪出今天名单，**必须拿出一句逐字核对过的客人原话**，否则人留在今天名单、标「需要人看」。客人一来新消息，旧卡立即作废。

**第三件事：用 Claude Haiku 5.5，CTS 一家每天大约 0.2–0.3 美元，另设每天 1 美元硬上限。**
五个模型同题比过它最准（三项全对 21/40，排序相关 0.71，零编造）；线上现在用的 gpt-4o-mini 不行。价格、格式兼容、准确度都要在正式调用方式下重测一次再上线。

**第四件事：能做成会学习的 agent，「学习」= 改提示词、例题和阈值，不训练模型。**
同事点「判断不对」、你每周抽查、客人后来回没回，都会记下来。agent 自己起草改进版并考试，**考得过才送到你面前，你回「换」才上线**。例题也算提示词的一部分，一起考、一起批。

**第五件事：先修数据，再上 AI。**
语音信箱被记成「通话成功」、同事邮件被当成客人来信、「已报价」误判、同一人两张卡、机器人回复当成真人联系、Mailchimp 群发记录不全导致「7 天 2 封」数不准。这些不修，AI 读的就是错的材料。

**第六件事：分 8 刀，影子期至少两周且至少抽查够数，你说「开」才换排序。**
需要你拍板的业务问题两个（§14），需要你知道的一件事一个（§15：Anthropic 会经常性地读到 CTS 所有客人对话）。

## 1. PM 要什么（2026-10-29 / 10-30）

- CRM 的核心对象是**每位客人的 AI 判断**：谁在等谁、态度、下一步、渠道、什么时候、为什么。「今天要联系」按它排。
- PM 的常识（全部要能判出来）：①我们回邮件后客人又追问 → 必须跟进；②连续两通没接 → 别再打，换渠道；③我们群发了一批，5–7 天没回 → 换渠道跟进；④客人说还没准备好 → 等；⑤答应过的事 → 去兑现；⑥回头客再次留资 → 强信号；⑦同行 / 供应商 → 不是线索。
- 新问题（10-30）：**这套判断能不能变成一个不断学习、越来越准的 agent？** → §10。

## 2. 证据（三次只读实验，2026-10-30，CTS；全程没写库、没发消息）

| 实验 | 做法 | 结论 |
|---|---|---|
| ① 参考答案 | Claude Opus 读完 40 位客人全部往来，逐个判断 | PM 看后「基本都对」（**整体认可，未逐条确认**）。在等我们回话的 16 人，现在前 10 名只覆盖 5 人；4 人不该在名单上 |
| ② 线上模型 | 同样材料喂给 CRM 现在的 AI 通道（gpt-4o-mini） | 四项全对 3/40；把我们发的跟进信当成客人提问；理由里有编造 |
| ③ 五模型同题 | 程序先算好硬事实，五个模型吃同一份材料 | Haiku 5.5（关闭「先想再答」）：态度 33/40、渠道 30/40、紧急度差 ≤1 级 35/40、三项全对 21/40、排序相关 0.71、零编造、约 0.0008 美元/人。Sonnet 5.5 同样准但贵 15 倍；gpt-4o-mini 相关 0.45 |

实验的局限（v0.1 补写，避免高估）：
- 样本 40 + 5 人全部来自「今天要联系」，**没有「先放着」的人**——模型在那一侧准不准没测过。
- 后加的 5 位同团客人，答案是 agent 自己定的，PM 没确认。
- 「谁在等谁」程序对上 32/40，但算法对着这 40 人调过三轮，偏乐观。
- 每个模型只跑了一遍，没测「同一个模型重跑一次结果变多少」。
- 自动编造检查标出 8 处，人工复核**全是误报**——这个检查现在还不能当闸用（§10.4）。
- 实验调用方式（直连、关思考、无强制格式）和线上不一样，正式方式下要重测（WP-3）。

实验顺带发现的数据错误（§9 全部纳入范围）：语音信箱记成通话成功、机器读聊天误判「已报价」、票务同事的报价被记成客人来信、同一人两张卡、机器人自动回复当成我们联系过。

实验脚本（未提交，在 focused-yalow 工作区）：`scripts/crm-ai-judgment-dryrun.ts`，是 WP-2 / WP-3 的原型；客户数据不进仓库。

## 4. 核心对象：判断卡

新表 `crm_contact_judgments`（客户私有，按 `client_id` 隔离，只许 service_role）。每次重判写新行，不覆盖。

| 字段 | 谁给 | 说明 |
|---|---|---|
| `subject_type`、`subject_id` | 程序 | 判断的单位，默认「客人」；可配置成「公司」（§11 多客户） |
| `who_waits`、`waiting_since` | 程序 | 客人等我们 / 我们等客人 / 都没在等 |
| `facts` | 程序 | 硬事实快照（§5.1） |
| `basis_inbound_at` | 程序 | 这张卡读到的「客人最近一条真话」时间，用于判卡是否过期（§5.4） |
| `stance` | 模型 | 热 / 温 / 暂不 / 不感兴趣 / 不是线索 / 已成交 |
| `next_action` | 模型 | 打电话 / 邮件 / 短信 / WhatsApp / Messenger / 只记一笔 / 等 / 不联系 |
| `wait_until` | 模型 | 「等」时到哪天；必须在材料里出现，且不超过行业剧本给的上限 N 天 |
| `downgrade_quote` | 模型 + 程序校验 | 模型把热的人往下判时引用的客人原话，程序逐字核对过才算数 |
| `urgency` | 模型 | 1–5 |
| `why`、`channel_reason` | 模型 | 一句中文理由（带日期）、渠道理由 |
| `examples_used` | 程序 | 这次用了例题包里哪几道（§10.5） |
| `guardrail_overrides` | 程序 | 护栏改了哪一项、为什么 |
| `status` | 程序 | `ok` / `needs_human` / `skipped_guardrail` / `stale`（被新入站作废） |
| `prompt_version`、`model`、`input_hash`、`trigger`、`cost_usd`、`latency_ms`、`claimed_at`、`attempts` | 程序 | |

- 判断卡**不改**客人阶段、不发消息、不写客人资料。现有 AI 简报继续生成，但不再是排序依据。
- **隐私实话**：`why` 和 `facts` 里会出现客人说过的内容（转述或短引文），所以这张表是客人个人数据，删客人 / 合并客人时必须级联处理（§13.2）。
- **保留期**：90 天内全部保留；90 天后每位客人只留最新一张 + 被纠错 / 抽查 / 题库引用过的。

## 5. 分工：程序算事实 · 模型判内容 · 规则当护栏 · 失败要保守

### 5.1 程序算的硬事实（确定性，有单测）

搬实验脚本 `computeFacts` 的口径到 `src/lib/crm/judgment/facts.ts`，复用现有判据：

| 硬事实 | 口径 / 复用 |
|---|---|
| 谁在等谁 + 从哪天起 | 客人真发来的话晚于我们最后一次**真人**回应 → 客人等我们；填表本身不算；通话里我们答应了要发东西且之后没发 → 客人等我们；我们最后伸手在 30 天内 → 我们等客人；否则都没在等。真人 / 机器用 `automated-touch.ts`、`human-actor.ts` |
| **什么不算客人说话** | 邮件打开、链接点击（含 Mailchimp 回传，库里存成入站）、表单自动确认、AI 客服接管期间的消息——**一律不算客人开口**（WP-2 单测钉住） |
| 上次聊上之后连续几通没接 / 语音信箱 / 秒挂 | `isUnansweredCall` + §9.1 新增的「客人是否开口」字段 |
| 我们最后一封真人邮件、几天了、客人回没回 | |
| **每位客人 7 天内收到几封邮件（含群发）** | 见 §5.5。数不准时当「已满」 |
| 新线索、回头客 | `returning-lead.ts` |
| 通话表态 | `call-stance.ts`，只认已核验、客人本人说的 |
| 别再联系 / 同行 / 非咨询 / 已成交 | `dnc.ts`、`segments.ts`、`contact-list-view.ts` |
| 各渠道今天能不能用 | §5.6 |

时间线每行标清「客人 → 我们」「我们的人 → 客人」「我们的机器 → 客人」「内部备注」。

**合并时间线只在「同一个已验证的邮箱或电话」时做**；仅仅是「疑似同一人」（名字像、时间近）的另一张卡**不喂给模型**，只在卡片上标「可能和另一张卡是同一人」（§9.4）。

### 5.2 模型判的（读内容）

态度、今天做什么、渠道、等到哪天、紧急度、一句理由。常识规则措辞写在**行业剧本**里，不写死在共享代码（§11、WP-3 审查清单）。

### 5.3 护栏（模型之后，模型改不了）

1. **别再联系 / 退订 / 同行 / 非咨询 / 已成交**：模型之前判，这些人不送模型，`skipped_guardrail`。
2. **7 天最多 2 封邮件（按客人算）**：计数已满或**不确定** → 不许建议邮件，改电话 / 短信 / WhatsApp（可用时）或「等」。
3. **不编事实**：`why` 里的日期必须在材料里；引号里的原文必须逐字在材料里。不过 → `needs_human`，理由换成程序写的硬事实句。
4. **不写截止日 / 倒计时 / 「名额有限」**（客户配置）。
5. **不说价格**。
6. **渠道必须真能用**（§5.6）。
7. **「最急」必须有硬事实撑着**：客人等我们 / 新线索 / 回头客 / 约好回电到期之一，否则紧急度最高 4。
8. **不许悄悄藏起热的人（v0.1 新增）**：硬事实是「客人等我们」「新线索」「回头客」之一时，模型若判成「等 / 不联系 / 不感兴趣 / 不是线索」，必须给出 `downgrade_quote`（客人原话，程序逐字核对在材料里）。没有或对不上 → `needs_human`，人**留在今天名单**。
9. **「等到哪天」有上限**：`wait_until` 的日期必须在材料里出现（客人自己说的），且不超过行业剧本的上限 N 天（旅游剧本默认值在 WP-3 定，配置可改）；超了截到 N 天。
10. **模型单独判的「不感兴趣」要自动回来**：如果「不感兴趣」只来自模型（没有通话表态、没有人手标记），给一个自动回来日期，天数等 PM 回 §14-1；PM 回复前用一个保守的临时值，**不预先决定「永不回来」**。
11. **显示时再查一遍**：护栏 1、2、6（别再联系、7 天 2 封、渠道可用）在**页面显示那一刻**按最新数据重查，不信卡上写的。

### 5.4 失败、过期、没钱：保守，谁都不消失

| 情况 | 行为 |
|---|---|
| 模型超时 / 报错 / 格式不对（重试 1 次后） | `needs_human`，按硬事实定档（§6.2：客人等我们 → 最高档，至少按 4 排；新线索 / 回头客 → 至少 4；其余按规则顺序），卡片写「AI 没判出来，需要人看一眼」 |
| **卡过期**：客人有比 `basis_inbound_at` 更新的真话 | 旧卡立即作废（`stale`），按规则顺序排，**强制进今天要联系**，直到新卡出来 |
| 当天预算用完 | 已有且没过期的卡继续用（标「X 天前的判断」）；**来了新入站又没钱 → 按硬事实给 `needs_human`，绝不沿用旧卡** |
| 功能关掉 | 名单回到现在的规则排序 |
| 模型判「不联系 / 等」且通过护栏 8 | 人移到「先放着」/ 种草唤醒，可翻到，卡片写原因和回来日期 |

### 5.5 每位客人 7 天收几封邮件：要先建一个可靠的数（v0.1 新增）

- v0 写「复用 `email-compose/quota.ts`」是错的：它按**发件邮箱**算，不按客人算。
- 按客人算的现有判据是 `email-templates/gates/frequency.ts` 的 `evaluateFrequency`：要去读发件箱已发邮件，单次最长 25 秒，只适合发信那一刻用，不适合每天给几百人判卡。
- 而且 Mailchimp 的「已发」记录不全：近 30 天有打开记录的客人 433 位，有已发记录的只有 74 位。
- **设计**：WP-2 建一个按客人的 7 天邮件计数（真人邮件 + 发件箱已发 + **Mailchimp 每次群发的完整收件人记录**，补上全量记录），存成可直接查的数；`evaluateFrequency` 在发信时仍照用。数据源有缺口（例如某次群发收件人没同步全）→ 这批客人记「不确定」→ 护栏 2 当已满。
- **验收**：拿最近一次真实群发，核对计数里的收件人数与 Mailchimp 后台报告一致。

### 5.6 渠道能不能用（v0.1 新增）

| 渠道 | 现状缺口 | 补法（WP-2 / WP-3） |
|---|---|---|
| WhatsApp | `reachableChannel` 不认识 WhatsApp | 加：有 WhatsApp 对话或号码已验证在 WhatsApp 上 |
| Messenger | 没查 24 小时回复窗口 | 客人最后一条 Messenger 超过 24 小时 → 不能随便发，降级或标「需模板 / 人工判断」 |
| 短信 | 新西兰短信同样受《反垃圾电子信息法》约束（要有同意、能退订） | 只在有同意依据、没退订时建议短信；同意依据口径写进客户配置 |
| 跨渠道 | 没有「一天内对同一客人最多联系几次」的上限 | 加客户配置：每位客人每天最多 1 次主动联系（任何渠道），超了改「等」 |

## 6. 「今天要联系」怎么排

### 6.1 谁进名单
沿用分段 + 4 列映射（#3396 §11.2），再加：
- 判断卡判「今天要做」、分段却放在「先放着」的 → **拉回今天要联系**。
- 判断卡判「等 / 不联系」且通过护栏 8 的 → 挪到折叠区，可翻到。
- 过期卡、`needs_human` 且硬事实是客人等我们 / 新线索 / 回头客的 → **必在今天要联系**。

### 6.2 顺序（从高到低）
1. 置顶 ⭐
2. 约好今天回电到期
3. 判断卡 `urgency` 高的在前；同级里「客人等我们」在前，再按等待天数多的在前
4. `needs_human` / 过期卡：**按硬事实定档**——客人等我们 → 按 urgency 5 那档；新线索 / 回头客 → 按 4；其余按 3
5. 兜底：`compareNextAction`

### 6.3 当天的稳定性（和 `day-list.ts` 的规矩对齐）
- 每天早上（新西兰时间）冻结一次顺序。
- **当天重判只能把人往上挪**（客人新来消息、新线索进来）；往下挪、挪出名单，**等第二天早上冻结时才生效**。
- 由**我们自己的动作**触发的重判（我们打了电话、发了邮件），当天只更新卡片文字，不动位置；卡片原位变灰。

### 6.4 卡片上显示什么
沿用 10-29 的「每行三样」：名字 / 一句话原因（= `why`）/ 一个渠道（= `next_action`）。点开看：谁在等谁、态度、护栏改了什么、判断时间和版本、「判断不对」按钮。

## 7. 什么时候判、花多少、怎么防超支

### 7.1 触发：以轮询为主，事件只为更快
- 实查（审查人）：全仓约 18 个文件直接写往来记录表，9 个写对话消息表，2 个写通话分析表，还有别再联系、合并、改阶段等，**没有数据库触发器**。在每个写入点都发事件不现实，也容易漏。
- **主机制 = 每 10–15 分钟轮询一次**：找「最新一条往来晚于最新判断卡」的客人 → 重判（同样排除群发、打开、点击、我们自己的机器信）。验收窗口：客人来消息后 **10 分钟内出新卡**（或旧卡已标过期）。
- **事件只为快**：已有的几个事件（新消息到达、通话分析完成、发信回执）顺带触发重判。用 Inngest 的合并等待（debounce）把 5 分钟内的事件合成一次，**并设最长等待**（不超过 10 分钟），避免一直有消息就一直不判。
- **晨扫（每天 6:30 新西兰时间）**：候选池 = 今天要联系 + 先放着里 30 天内有往来的 + **所有「客人等我们」的人** + **所有被卡挪走、但「等到哪天」已到期的人**。输入没变且卡不到 3 天的跳过。
- **手动**：卡片「重新判断」按钮，同一人 10 分钟内只允许一次（新加的冷却，存数据库）。注：v0 说「沿用 AI 起草的冷却」不对——AI 起草的冷却是 10 秒、只在内存里，这里不能照搬。
- **补数据 / 纠正脚本不触发重判**：WP-1b 那类批量纠正跑完，由下一次晨扫统一重判，避免一次纠正触发几百次模型调用。

### 7.2 占位与重试（照 `crm/facts/infer.ts`）
- 唯一键 `(client_id, subject_id, input_hash, prompt_version)` 只用来防**同一时刻的重复调用**；占位超过 15 分钟没完成算过期，可重新占；失败后 6 小时内不自动重试同一输入（手动重判和新入站不受限）。
- **`input_hash` 不含每天都会变的东西**（等了几天、今天日期），只含往来内容、硬事实里的事件和日期本身、版本号。这样晨扫才能真正跳过没变化的人；「等了几天」由显示时现算。
- 手动重判和「卡过期」带一个 `force` 标记，绕过「输入没变就跳过」。

### 7.3 预算账本（v0.1 更正）
- v0 写「复用 `agent_learning_budget_reserve / settle`」是错的：**这两个数据库函数生产库里不存在**；只有 `agent_learning_trial_reserve / settle`，而且是全平台按天一个数，不分客户、不分用途。
- **决定**：WP-4 新建一张**按客户 / 按天 / 按用途**的预算账本（含「先预留、后结算」两个数据库函数），迁移由 Ray 亲手合。不改 `agent_learning_trial_spend`——它的含义是「对照试验全局每日上限」，改了会动到现有试验功能。
- CTS 初始上限 1 美元/天，其中**留 30% 给「客人新来消息」的重判**，晨扫用不到这部分。
- **另开一张卡**：`agent-learning` 现有的蒸馏、X 读取两个调用方依赖那两个不存在的函数，现在可能一直在「账本不可用 → 零外呼」，需要另查（不在本稿范围）。

### 7.4 每天花多少（CTS，粗估；按实验③实测计费单位 × 缓存价目）

## 10. 学习闭环：让它越用越准（IMPACT 的 Check → Tune）

### 10.1 「学习」是什么
- **是**：根据纠错和结果，改**提示词的常识规则、例题包、程序阈值**。
- **不是**：训练或微调模型。
- **算 agent**：自己发现哪类判断老被纠正、自己起草改进版、自己考试；**上线永远要过闸**（§10.5）。

### 10.2 信号从哪来
1. **同事纠错**：卡片「判断不对」按钮，单选原因（他其实没在等 / 其实在等、不该 / 应该今天联系、渠道不对、态度不对、不是客人、依据写错、我们在系统外回过了、其他）+ 可选一句话。**隐性信号**（同事没照卡片做、做了别的）只记录不算纠错。
   - **存在哪**：复用已有的 `crm_segment_feedback` 表（它本来就是「分错了 → 记下来改规则，不改这个人」的语义，已有接口），加几列：判断卡 id、原因代码、正确的态度 / 渠道 / 紧急度。不另建表。
   - **它生产库里是 0 行**（8 月上线至今没人点过「分错了」）——这是证据：**纠错会很少**，不能指望它驱动学习。所以影子期出口设「最少抽查张数」，主要信号来自 PM / 指定同事的主动抽查。
2. **结果回填（7 天后）**：建议的动作做了之后 7 天内，客人有没有主动回话 / 约时间 / 填订单 / 付定金；按「当天是否被联系」分层（别拿「被打了才回」自我印证）。CTS 成交量小，结果只作参考。
3. **PM 每周抽查**：每周一页，含①今天名单里随机 10 张；②**折叠区 / 「不联系」那一侧随机 5 张**（防只看被选中的人造成偏差）；③被纠错最多的 5 张。PM 回「对 / 不对」。

### 10.3 存在哪
- 纠错、抽查、结果回填都指向当时那张判断卡，`client_id` 隔离。
- 例题和题库**只存硬事实 + 正确答案 + 判断卡 id**，不另存客人原文；需要原文时回原表读，删客人跟着删。

### 10.4 参考答案题库与每周离线考试
- **叫法**：PM 逐条确认之前叫「参考答案」。v1 = 实验的 40 位（PM 整体认可）+ 5 位同团客人（**答案是 agent 定的，PM 未确认，单列，不算分只观察**）。WP-7 开工前请 PM 逐条过 40 位，确认的才进「已确认」组。
- **补题**：每月按层抽新题——今天名单 / 先放着 / 不联系三侧各抽，PM 逐条确认后入库。**放行以新题上的分数为准**（老题算法调过，偏乐观）。
- **重跑噪声**：每个版本对同一题库跑 3 遍，算出「同一版本自己跟自己差多少」；候选版本比当前版本好的幅度要大于这个噪声才算「好」。
- **编造检查先修再用**：实验里自动检查标了 8 处全是误报（「截至今天」、中英翻译加引号、原文里本就有的日期写法）。WP-7 先把这三类写成单测，**在实验数据上做到零误报**，才拿它当闸（编造 > 0 自动拒绝）。
- **打分**：态度、渠道大类、紧急度差 ≤1 级、三项全对、排序相关、编造数、格式错误数。打分程序进仓库（`src/lib/crm/judgment/eval.ts`），题库材料存客户私有存储，不进仓库。
- **复用**：`agent-learning/lesson-trial` 的「同题、有 / 没有这条改动各跑一次」写法；`lesson-verify` 的结论三档（支持 / 反对 / 证据不足）；`/api/admin/agent-learning/trial` 的「只读、限流、花费记账」接口形状。广告那套回测程序不能直接跑 CRM，打分程序新写。

### 10.5 候选版本、例题包、谁能改什么
- **例题包是冻结的、有编号的快照**（例如 `crm-judgment-v3 / 例题包 7`），**算提示词版本的一部分**，和规则一起考试、一起等 PM 回「换」。不做「每次判断现场挑例题」。判断卡记录用了包里哪几道（`examples_used`）。
- **例题入池要二次确认**：一条纠错要经 PM 抽查确认，或两位不同同事给出相同纠正，才能进例题池；题库里的客人永远不进例题池（防泄题）。
- **候选版本存放**：存在数据库里**客户私有的覆盖层**（只对这家客户生效的规则措辞 / 阈值 / 例题包），默认未启用；**行业剧本只能通过代码 PR + PM 改**，agent 碰不到。
- **agent 自己可做**：汇总纠错找模式（同类错误本周 ≥3 次）、起草候选（存未启用）、跑考试、写报告。
- **需要 PM**：候选上线（回「换」）；护栏改动（只能人改代码）；升级为行业经验。
- **自动拒绝**：新题分数下降、或不超过重跑噪声、或编造 > 0、或格式错误率上升。
- **回退**：客户配置里「当前版本」一个值，改回即生效。

### 10.6 升级成行业经验（只在有证据时）
同时满足：≥2 家同行业客户的纠错指向同一规则；两家各自题库新题上都不降分；文字过 `memory/lesson-shareability.ts` 脱敏闸并走 `memory/write-lesson.ts` 唯一入口；通过代码 PR 改行业剧本；PM 批准。现在只有 CTS，第一期不会发生。

## 11. 平台层级判定（me-platform-tier-gate · Full）

**被判定对象**：CRM「每位客人 AI 判断卡」+ 按功能选模型 + 判断的学习闭环

**建议层级**：既有能力的扩展，分三层：
- **L1（平台共享）**：判断卡形状与存储、硬事实计算、护栏框架、失败兜底、轮询 / 触发 / 预算、按功能选模型、离线考试与版本闸、纠错存储。归属 = 平台基础设施里的 **Next Best Action + Verification / Learning（Memory）**，作用在已存在的 CRM 名单引擎上。不新增支柱、不新增能力名。
- **L2（行业剧本）**：常识规则措辞、阈值默认值（含「等待上限 N 天」）、判断单位默认值、是否每日冻结。挂在现有 `IndustryPlaybook` 上扩字段。
- **L4（客户配置）**：7 天 2 封、不写倒计时、我方员工邮箱、每日预算、跨渠道每日上限、短信同意口径、当前版本、私有覆盖层、纠错和题库。

**和产品定义的边界（§3.1 / §3.2）**：产品定义说 ME 不自建「CRM 系统本体」。本稿服务的是**营销带来的线索的转化**（广告表单、官网咨询、社媒私信进来的人），属于 §3.1 的 Next Best Action；判断与结果回流到 Check 和归因（这批线索最后成没成，回到广告 / 渠道效果）。**只作用于营销来源的线索，不做通用销售管理**（不扩阶段、订单、团队绩效等 CRM 本体功能）。§9 的数据修复是让证据可信的前提，不是扩 CRM 范围。

**换客户测试**：✓（有条件）

## 13. 不做 / 隐私

### 13.1 不做
- 自动给客人发任何消息（发信仍走 127 号通道、人点发送）。
- CRM 内写邮件对所有客人开放（PM 说先等）。
- 判断卡自动改阶段；承诺自动进「我欠他」列。
- 真正合并重复联系人（归 10-17 设计）。
- 训练 / 微调模型。NAL / Oztop 接入另开。

### 13.2 隐私与删除
- 判断卡的 `why` / `facts`、纠错备注、题库快照都含客人内容 → 都按客人个人数据处理。
- **删除客人**：判断卡、纠错、题库快照中该客人的条目一并删（外键级联 + 私有存储清理），WP-4 / WP-5 / WP-7 各自有测试。
- **合并客人**：判断卡、纠错改挂到保留的那个客人；被合并那张的旧卡标作废。
- 外发给模型的只有「这个人的往来 + 硬事实」，与简报同一外发边界；DeepSeek 对本功能硬排除。
