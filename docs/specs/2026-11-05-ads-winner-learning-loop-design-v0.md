## 0. 给 PM 的大白话（10 行）

1. 今天 winner 的经验是「人记得就用，忘了就丢」：写进了工厂的赢家表，但工厂出片照的是另一个配方，所以出来的片不像 winner。
2. 这份设计把它改成一个会自己转圈的环：**发现赢家 → 拆成骨架 → 你确认 → 工厂照骨架出片 → 投了之后对比 → 升级或退役**。
3. 不新增 agent：广告 agent 多一个「找赢家」的本事，视频工厂多一个「照赢家骨架出片」的配方，马良审片多一张「照没照做」的对账表。
4. **保证工厂一定用上**靠三道硬闸：你确认过的赢家自动成为这个客户出广告片的默认骨架；出片单上必须写「照哪条赢家」；审片时逐项对账，没照做的进不了待审。
5. 价格、出发日这类事实永远从团目录现取，不从旧片子抄，避免把过期价格做进新片。
6. 花钱的三件事（出片花的生成费、开投、加预算）全部照旧只认你本人。
7. 你每周最多收到 1 条「要不要认这个赢家」，不回就一直是候选，系统不会拿候选去出片。
8. 赢家看腻了、成本涨了，系统提议退役，你点头才退。
9. 今天的三个坑（变体不像 winner、按错误的数挑赢家、按客户主结果误判）先写成考题，每次改动都要先过题。
10. 第一刀只做「考题 + 后台看得到当前赢家和它的状态」，不花钱、不碰数据库结构。

## 1. 层级判定与 Build vs Connect

**Tier Classification（Full，因为动视频工厂与广告诊断两块共享代码）**

- **被判定对象**：赢家经验闭环（发现、拆解、入库、按骨架出片、对比、调整）。
- **建议层级**：**L1 既有能力的扩展**——挂在既有支柱「广告」（发现 / 对比）与「社媒」（视频工厂出片）之下；平台基础设施归「记忆 / 验证」。**不新增能力线、不新增支柱、不新增 agent**。
- **换客户测试**：✓。Oztop（地板电商）、NAL（物流）同样有「哪条广告在自己的结果种类上最便宜」→「拆出骨架」→「照骨架出片」。客户差异只在：结果种类（留资 / 私信 / 下单）、事实来源（团目录 / 产品目录）、骨架里的具体字（价格卡写什么）——全部来自客户配置与事实适配器，不进共享代码。
- **换行业测试**：✓。地产（楼盘留资）、电商（下单）适用同一环；行业差异（比较门槛、观察天数、骨架模板能出哪几种）放行业手册 / 行业模板。
- **红线检查**：红线 1（禁包装升级）✓ 不叫「赢家智能层」；红线 2（客户事实不进共享）✓ 骨架内容存 `winner_structures` 行（客户私有），事实从适配器取；红线 3（禁直建 L1）✓ 是既有 L1 的扩展；红线 4/5 ✓ 见上；红线 6 ✓ 走五道门；红线 7 ✓ 行业层只装「骨架有哪些位、哪些位必须现取事实」。
- **Build vs Connect**：
  - **Connect（已有）**：Meta 只读（广告、视频、创意）、Remotion 出片机、Creatomate、团目录、CRM。
  - **Reuse（已有平台代码）**：素材成绩单、结果种类口径、合格客人、马良 v2、事实比对、工厂下单与变体单、今日待办、Inngest。
  - **Build（新，平台共享）**：①赢家候选发现规则；②视频拆骨架（模型 + 复核）；③「骨架 → 配方参数」的通用映射（一个配方，不是每条赢家一个）；④对账列与审片对照；⑤对比与升级 / 退役规则。

## 3. 闭环六步

授权级别沿用藏经阁第六部：**L0 只读诊断 · L1 出草稿、人点才做 · L2 低风险可回滚自动做 · L3 高风险只给证据、人批**。
回执一律写 Inngest 事件 + 机器可读回执（CLAUDE.md §3：request id、client id、来源记录 id、状态、花费影响、授权状态、created_at）。

### 3.1 ① 发现（L0，确定性代码）

- **输入**：每日广告数据（已有日同步）；素材成绩单 `src/lib/ads-strategy/entity-tree/creative-compare.ts`（`judgeCreatives`，按广告组自己的结果种类，`resolveCoreMetric`）。
- **做什么**：每天找「候选赢家」——同一广告组内 `comparability = enough` 的广告里，满足：上线 ≥ 7 天、自己结果 ≥ 30 个、每个结果成本 ≤ 同组可比广告中位数的 0.8 倍、Meta 三项排名无「低于平均」。实验中的组跳过（`diagnostics/context.ts` 的 `experimentIds`）。
- **不用模型。**
- **产出**：`{ client_id, ad_id, adset_id, video_id, result_type, results, cost_per_result, peer_median, window, comparability }`。整条标「参考，不是因果」（手册 C-19：同组里 Meta 先挑人再分钱）。
- **回执**：`ads.winner_candidate.detected`。
- **验证者**：考卷（§6）；同一广告已在赢家表的不重复报。
- **读不到 / 判不了**：写「判不了：<原因>」（读不到结果种类、点击不够、只有一条素材），不当成「没有赢家」。

### 3.2 ② 拆解（L0，模型 + 独立复核）

- **输入**：候选的视频（Meta 视频源，只读）、广告正文、标题、按钮、表单编号。
- **确定性代码**：按镜头切点 + 固定时间点抽帧；读正文；从团目录取这个团的现行事实（`tour-catalog/store-publish.ts` `loadPublishedTourFacts`）。
- **模型做的**：读帧和正文，填**结构化骨架**（不是自由文本）：
  - `hook = { seconds, visual_kind, text_lines[], fact_slots[] }`（例：`fact_slots = [price, room_basis, departure_date, departure_city]`）；
  - `scenes[] = { seconds, place, inclusion_slot }`；
  - `endcard = { seconds, fact_slots[], url }`；
  - `style = { text_size, pace_s_per_scene, safe_area_ok, music_id? }`；
  - `copy = { body_matches_screen: bool }`、`cta_type`、`form_kind`、`placement_mix`；
  - `win_reason_tags[]`（从固定词表里选，不许自造）。
- **复核（生产≠审核）**：马良 v2（`src/lib/maliang/render-check-v2.ts`）用另一套提示词读同一批帧，逐项核骨架（「第一帧真的有价格吗」「每景只有一个地点吗」）；确定性代码核：第一帧识别出的价格 = 团目录价格。三方对不上的项标「待人核」，不许自动通过。
- **回执**：`ads.winner_structure.extracted`（含两份结论与不一致项）。
- **花费**：每条候选一次拆解 + 一次复核，单客户每周上限沿用马良补审的上限做法（`weekly_loop.maliang_weekly_cap_usd` 同款字段，单独键）。
- **失败**：没看成（下载失败 / 超时 / 解析失败）不写骨架，下周重试；不拿半份骨架入库。

### 3.3 ③ 入库与确认（L1：PM 点头才生效）

- **存哪**：现有 `winner_structures`，不建新表、不改表结构。「候选 / 已验证」放 `performance.verification = { state: candidate | verified | human_asserted, verified_by, verified_at, evidence_ref }`；`status` 照旧管 `active / fatigued / retired`。
- **规则（藏经阁第八部）**：模型只能写 `candidate`；PM 在今日待办点「认」才变 `verified`；PM 的确认和程序的复核分开记、互不覆盖。
- **工厂只认 `verified` 的**：`pickWinner` 改成只取 `active` 且 `verified`，**按这个赢家自己结果种类的单次成本排序**（留资看每个留资，私信看每个开聊），不再用 `cost_per_thruplay`；只有「视频播放」目标的才按看完成本。
- **11-04 那条**：PM 说了「记进工厂」，记为 `human_asserted`（人工断言）；骨架是 74 号拆的、还没经第二方复核。第一刀补复核；复核过、PM 再看一眼，才升 `verified`。
- **回执**：`ads.winner_structure.verified` / `.rejected`（带 PM 理由）。

### 3.4 ④ 照骨架出片（L1；出片生成费、对外发布、开投都要 PM）

这是 PM 问题的核心。**三道硬闸，保证工厂一定用上 winner：**

1. **默认骨架**：客户有 `verified` 赢家时，后台下广告片（工厂页「下单」、内容卡片「生成视频」、变体单）**默认带上当前赢家**，页面写明「照赢家 <名字/编号> 做」。下单的人要换成别的骨架，必须选一个理由（固定选项），写进工单。
2. **数据驱动配方**：在 `recipe.ts` 注册**一个**通用配方 `winner_skeleton_v1`，它不写死任何赢家，只把骨架字段翻译成出片机参数（首选 Remotion 明信片模板，加一个「价格放第一帧」开关）。以后来第二条、第三条赢家，**只多一行数据，不改代码**。骨架里的价格、出发日等 `fact_slots` 一律在建单时从团目录现取；目录里取不到 = 拒单，不拿旧片的字顶。
3. **对账表自动加列**：出片前的配方对账（CLAUDE.md §8）自动加上赢家各列：第一帧有没有价格卡、每景是不是一地一包含、结尾有没有复述、单景时长、字号、安全区、正文是否与画面一致。工单写 `order_type = variant_from_winner`、`winner_structure_id`（字段已有）。任何一列「未满足」= 工单进不了待审，写明缺哪列。

- **变体纪律（藏经阁第九部）**：变体每次只改一样（换团、换开场第三行、换音乐、换一景），改了什么写进工单。
- **出片后**：照旧走视频工厂流程 + 马良审 + 苏东坡审 + PM 授权（CLAUDE.md §8）；分镜自检表照出。
- **回执**：`factory.winner_variant.ordered` → `factory.winner_variant.reviewed`。

### 3.5 ⑤ 验证（L0，确定性代码）

- **何时**：变体上线后，它和赢家各自的结果 ≥ 30 个，或满 14 天，先到为准。
- **比什么**：
  - **内环**：每个结果成本（按单元自己的结果种类），点击率、按秒的留存（手册：按「看到第几秒」比，不按百分比）。
  - **外环**（藏经阁第七部）：合格客人（`portfolio/qualified-leads.ts`，CRM 走到已报价及以后）——**只记录不判定**，进来不满 14 天标「观察中」（`QUALIFIED_OBSERVE_DAYS`），人判与 AI 判分开数。
- **结论四档**：变好 / 变差 / 持平 / 说不清（样本不够、同期有别的改动、放的位置不一样）。同组比较一律标「参考，不是因果」；PM 出钱做 Meta 原生 A/B 时才能写「因果」。
- **回执**：`ads.winner_variant.outcome_concluded`，写进现有 `flywheel_outcomes`，遵守 `me-agent-loop-upgrade` §4 的「一个动作一张卡」契约。

### 3.6 ⑥ 调整（L1：系统提议，PM 点头）

- **升级**：变体「变好」（单次成本 ≤ 赢家 0.8 倍，双方都 ≥ 30 个结果）→ 提议它成为新赢家（走 ③ 的确认）。
- **退役**：赢家连续 2 周 7 天频率 > 3 **且**每个结果成本 > 它被确认时的 1.5 倍 → 提议退役（`status = fatigued`）；PM 点头才改。退役的骨架保留，标退役原因。
- **标签命中率**：每次变体结论回写到赢家的每个标签——「保留这个标签的变体赢了几次 / 改掉它的输了几次」。命中率低的标签下次拆解时降权，不删历史。
- **升行业层**：要第二个同行业客户也出现同骨架的 `verified` 赢家，才把骨架写进行业模板；之前只在客户私有层。
- **回执**：`ads.winner_structure.promoted` / `.retired`。

## 4. 授权总表

| 步 | 级别 | 谁动 | 什么情况降级 |
|---|---|---|---|
| ① 发现 | L0 | 程序 | 考卷有一题答错 → 停报，修完再开 |
| ② 拆解 | L0（花模型费，有上限） | 模型 + 马良复核 | 一次被 PM 判「拆错了」→ 之后每条都要 PM 看过才入候选 |
| ③ 确认 | L1 | PM | — |
| ④ 出片 | L1；生成费、发布、开投 L3 | PM 点出片 / 授权 / 批钱 | 一次「照骨架却不像」被 PM 打回 → 该配方暂停自动对账放行，逐条人核 |
| ⑤ 验证 | L0 | 程序 | 一次结论被证明错（例如按错结果种类）→ 该类比较停出结论 |
| ⑥ 调整 | L1 | PM | — |

「关、拒、发、花钱」全部要人批；没有任何一步自动开投、自动加预算、自动发布。

## 5. 外环与学习分层

- 外环指标：合格客人（只记录）；内环：单次成本（按单元结果种类）。样本不够写「未决」，不写 0。
- 学习三层：**客户私有**（`winner_structures` 行、客户配置）→ **行业**（行业模板只装「骨架位与事实位」，要第二家同行业证据）→ **全局**（只装「先确认再用、按自己结果种类挑、事实现取」这类纪律）。
- 记忆手册（Claude 记忆）只给开发窗口看，**不是生效位置**；生效位置是数据库里的 `verified` 骨架 + 工厂默认配方 + 对账列。

| Q3 按客户主结果误判（D3 历史题，WhatsApp 组 10-25 → 10-30 被连判 6 天） | 一个 WhatsApp 开聊组，0 留资、很多开聊 | 按开聊判，既不当「输」也不和留资组比 |
| Q4 位置混比 | 同一视频 Facebook 每个留资 4.57、只投 Instagram 9.98 | 判「不可比（位置不同）」，不说视频变差 |
| Q5 候选不出片 | 只有一条 `candidate` 赢家 | 工厂不默认用它，下单页提示「有一条待你确认的赢家」 |
| Q6 事实过期 | 骨架里记着 NZ$2,699，团目录现价变了 | 建单用目录现价；目录取不到 → 拒单 |

起步 6 题；PM 每打回一次相关结果，补一题（藏经阁第十部「纠一次沉淀一次」）。

## 7. PM 注意力预算（藏经阁第十三部）

- 每个客户每周最多 1 条「要不要认这个赢家」，多了合并成一条列表。
- 退役提议每周最多 1 条，与上一条合并。
- 不回：7 天后待办过期自动清，候选保持候选（工厂不用），不会因为没人回就自动生效。
- 出片审批、开投审批走现有入口（待审收件箱、广告加钱闸），不另加一条。

## 9. 开工十问

1. **IMPACT 哪一段 / 外环？** Measure（发现、验证）→ Prescribe（骨架）→ Act（出片）→ Check（对比）→ Tune（升级退役）；外环 = 合格客人。
2. **确定的 vs 交给模型？** 发现、对比、升级退役、事实取数、对账全是代码；只有「读视频拆骨架」用模型，且被另一方复核。
3. **对外动作与授权？** 出片生成费、发布、开投全是 PM；系统自己只做只读和草稿。
4. **完成证据？** 每步一个 Inngest 事件 + 回执；出片单带 `winner_structure_id` 和对账表；结论写 `flywheel_outcomes`。
5. **谁验证？** 拆解由马良复核、事实由代码核、出片由马良 + 苏东坡 + PM 审；结论由考卷守。
6. **学到的写哪层？** 客户私有 → 行业（要第二家）→ 全局只写纪律；候选 / 已验证 / 人工断言分开记，PM 才能升已验证，退役有阈值。
7. **考卷？** §6 起步 6 题，合成数据，离线回放。
8. **PM 纠正落哪？** 补考题 + 候选状态回退 + 台账卡，三选一并记台账。
9. **读不到时说什么？** 「判不了：<原因>」，不当 0、不当「没有赢家」。
10. **占 PM 多少注意力？能不能不加 agent？** 每周 ≤ 1 条确认 + 现有审批；不加 agent，给广告 agent 和视频工厂各加一个本事。

## 11. 不做 / 未决

**不做**：自动开投、自动加预算、自动发布；训练模型或在线学习；新建表；把骨架写成行业定论（要第二家客户）；为每条赢家写一个配方；在主页日常帖里强推价格开头（10-15 PM 说过重复）。

**要 PM 拍板的业务问题（只有这三个）**：
1. 确认过的赢家，是只当 **广告片**的默认骨架，还是 **主页日常 Reel** 也默认用？（建议只管广告片，主页按 10-15 穿插。）
2. 除了你，CTS 员工能不能点「认这个赢家」？（建议只有你。）
3. 照赢家出变体的生成费，每月给多少上限？（不定就每条都单独问你。）
