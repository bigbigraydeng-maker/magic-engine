# 「新线索没人跟进 / 积压」做成今日待办一条（设计稿 v0.1，最小版）

状态：设计稿，待子牙 + 魏征审，未写代码。风险级别：**B**（只读、不加表、不外发、不改数据结构）。
起因（统筹 18，2026-10-18）：`crm-lead-followup-digest` 每天在跑，但只会发一封收件人写死的汇总邮件，开关还关着；CTS 窗口外积压 170 条没有任何人被指派。

## 一、结论

不再靠「开邮件开关」。让它**复用待办的既有写法**：新增一个 `-items` 文件，把「填了表没人回」按客户合成**一条**待办，带 what / how / href，跟其它待办一起进每天的「今日待办」邮件和页面。邮件汇总信本身保持关闭，不删。

## 二、现状（只读核实，2026-10-18）

- 每天 NZ 早 8 点跑，7 个客户，最近三次 completed；开关没开，`sent=false`。
- CTS：窗口内新线索 0，窗口外积压 170；NAL 积压 3；Roman 1。
- 判据已经有现成的，且已经有测试：`lib/crm/lead-followup-due.ts` 的 `findLeadFollowupDue`（窗口内要列的）和 `countLeadFollowupBacklog`（窗口外积压数）。它已经处理：机器人回复不算跟进、别再联系 / 结论阶段 / 推迟中的不列、以最近一次留资为锚点。**不重写判据。**
- 待办现有 25+ 个 `-items` 文件，统一由 `manual-items.ts` 调度，每种待办 `kind` 必须在 `five-kinds.ts` 的穷举表里分车道（类型检查强制）。

## 三、新增内容

1. 新文件 `src/lib/pm-todo/lead-followup-items.ts`，一个函数 `pushLeadFollowupItems(supabase, items, now)`，只读，一行写操作都没有。
2. 新 `kind`：
   - `lead_followup_due` —— 窗口内（7 天）有填了表、超过 24 小时没人回的人。
   - `lead_followup_backlog` —— 窗口外积压（只有数字、不逐条列），**合并进同一客户的同一条**，不另起一条。
3. 一个客户一条，不是一个人一条（CTS 积压 170 条，一人一条就是 166 件事故重演）。
4. 车道：归 `client_side`（「要转给客户那边的：客人来信没回」），不进 PM 的拍板栏。

## 四、一条待办长什么样（字段）

| 字段 | 内容 |
|---|---|
| what | 「CTS 有 N 个客人填了表、超过 24 小时没人回过（最久 X 天）；另有 M 个更早的积压，一直没人跟。每拖一天，这个人就更可能选别家」——把代价说出来 |
| how | 「点链接打开『全部客人』，看『今天要联系』里排前面的人，逐个打电话或回私信；每个人处理完在他页面上记一笔（没打通也记）。不用回也要记一句，否则这条会一直在。注意：这里『没人回过』只算真人（电话、手写记录、真人回复）；Facebook 私信的任何外发整类不算——因为里面混着 Meta 自家 AI 客服的自动回复，所以『今天要联系』页里显示已联系的人，这里可能仍然列着」 |
| href | 该客户「全部客人」页（绝对网址，复用 `email-reply-items.ts` 的拼法，避免被链接闸判坏） |
| 负责人 | 第一版不加字段：把「客户的销售」写进 how（子牙审：现有设置里没有可读的销售名单，加字段要改 `daily-todo.ts` 映射和渲染，且全员同值没有信息量） |

## 五、「负责人」（第一版不做字段）

统筹要求带负责人。子牙审后结论：**第一版不加字段。** 原因：①客户设置里没有可读的销售名单（核实过 `leads_config`，只有域名规则和预订配置）；②`ManualItem` 加字段后，`daily-todo.ts` 会把它重新映射成另一个展示类型，字段不改映射到不了邮件和页面，改动面比想象大；③读不到名单时全员同值，没有信息量。做法：how 里写「转给客户的销售」。等客户设置里真有销售名单再单独加。

## 六、关停与自愈

- 待办**不存状态**，每天重新算：有人在系统里记了一笔真人跟进（电话、手写记录、非机器人外发），下一次计算他就不在名单里，待办自己变小 / 消失。
- 没有「已读 / 已处理」按钮，不新增任何写入。
- 重复跟进的抑制由既有判据负责，这里不再造第二套。

## 七、跟既有东西的关系

- **汇总邮件**：`crm-lead-followup-digest` 保持关闭，不删不改。
- 🔴 **表格跟进记录要先同步（子牙审发现，原稿漏了）**：digest 挑名单前，对配了表格的客户先跑 `syncSheetFollowupNotes`，把员工在表格上记的电话同步成触点；漏了它，CTS 约 224/331 个已被打过电话的人会被误列（digest 文件头有实测）。这一步**会写库**，不能放进「一行写操作都没有」的待办里。处理：待办只读判据；同步另由每天一次的独立步骤负责（沿用 digest 里那一步，不在待办里调），并在 how 里写明「CTS 表格上记的电话要先同步，否则数字偏高」。**试跑拿到的 170 / 3 / 1 因此可能含水分，不能当真值，第十节要对比同步前后。**
- **Facebook 同步失败待办**（`facebook_sync_failing`）：那条说「线索进不来」，这条说「进来了没人回」，互补，不合并。
- **不进 Inngest**：纯只读、无外部副作用、由每天的待办汇总拉取，符合 CLAUDE.md「无外部副作用的纯函数不必上 Inngest」。回执仍是每天待办邮件里的这一条。

## 八、安全与口径

- 红线：不含客户私有名字进共享代码；客户名来自 `clients`，判据读每个客户自己的阶段配置（沿用 `lead-followup-due` 已有做法，不写死 `deposit_paid` 这类旅游阶段名）。
- 只读客户的线索，不外发、不改联系人、不写触点。
- 超过 `MAX_PER_CLIENT`（15）的名单这条待办**不逐个列名**，只给数量和入口，避免把客人名单塞进邮件。
- 🔴 失败不静默（子牙审纠正：`manual-items.ts:268` 一类的 `.catch` 只是 `console.warn`，读失败 = 当天这条待办静默消失）。做法：catch 里往 items 里 push 一条兜底待办「线索待办这栏今天没算出来」（参照 `ai_alerting_broken` 的写法），不当 0。
- 两个新 kind 加进 `NEVER_DROP_KINDS`：链接是登录后台页，探活易判成坏链接而整条被丢。
- 客户范围：待办用 `client_status='active'` 的客户名单（`client-roster.ts`），不是 digest 那套 `facebook_page_id` 非空；没有表单线索的客户得到空结果，无害。

## 十一、复用声明

- 复用：`lead-followup-due` 全部判据、`manual-items` 调度、`five-kinds` 车道表、`email-reply-items` 的链接写法。
- 平台共享：待办生成逻辑；客户差异只来自各客户自己的阶段配置与销售名单。
- 新增：一个 `-items` 文件、两个 `kind`（加进车道表和 `NEVER_DROP_KINDS`）、一条读失败兜底待办。**无新表、无新字段。**
