# CRM 名单「没变就不重读」设计稿 v0

状态：草稿，等 PM 回「开始」才写代码。风险级：第 1 刀 A 级（要在数据库加一张小表和触发器，按规矩由 Ray 亲手合）；第 2、3 刀 B 级。
来源：PM 2026-11-16「检查 CRM 页面加载速度慢的问题」→「出方案」。

## 1. 要解决的事（一句话）

CRM 名单每打开一次，都把这个客户的全部联系记录和全部客人整批读一遍；改成「数据没变就直接用上次读到的，变了才重读」。

## 2. 已经量到的事实（2026-11-16，全部只读）

| 事实 | 数字 | 怎么量的 |
|---|---|---|
| CTS 数据量 | 9,329 条联系记录、1,610 位客人 | 查库 |
| 数据库自己取完全部联系记录 | 0.08 秒 | `EXPLAIN ANALYZE` |
| 名单请求，连续使用 | 2.6 到 2.9 秒（其中读取约 1.5 秒） | 线上连续 10 次，`Server-Timing` |
| 名单请求，停一分钟后第一次 | 5.5 到 8.7 秒（其中读取 4.0 到 6.8 秒） | 线上 3 次 |
| 停久了变慢发生在哪 | 数据库服务内部：十页读取每页 0.03–0.28 秒变成 0.4–1.3 秒；一条小查询只从 0.05 变 0.17 秒 | 网关回报的内部处理时间 |
| 已上线的改进 | 十页同时取（PR 3868）：今天要联系 10.7 → 约 4.2 秒 | 线上 3 次 |

两条已经排除的猜测：数据库批次函数（2026-11-15 装了没变快，已撤）；让服务器到数据库的连接多保持一会儿（2026-11-16 对照实验证明不对症，没提交）。

结论：慢的大小跟「读多少」成正比。要治本只能少读，不能靠调连接。

## 3. 做法

**一个「变更计数器」。** 数据库里加一张很小的表，每个客户一行、一个数字。名单用到的那几张表（见第 5 节）只要有任何新增、修改、删除，数据库自己把这个客户的数字加一。由数据库来加，是因为写这些表的地方很多（页面、来电、来信、定时任务、还有人工直接改库），靠程序各处记得通知一定会漏。

**服务器记住上次读到的原始数据。** 每次打开名单：
1. 先读这个客户的计数器（一条很小的查询）。
2. 数字跟上次一样 → 直接用内存里那份原始数据，不再读库。
3. 数字变了或内存里没有 → 照现在的办法完整读一遍，连同当时的数字一起记住。

**排序和分栏每次照旧现算。** 「今天该不该联系」跟当前时间有关（回电到期、暂缓到期），所以只省「读」，不省「算」。算出来的名单跟现在逐字相同。

先读计数器、后读数据：即使读数据的途中有人改了东西，记下的也是旧数字，下一次一定会重读，不会把新旧混在一起当成最新。

## 4. 做完 PM 能看到什么

- 名单、今天要联系、手机外勤页：数据没变时，打开不再有「读取」那一段等待；停一分钟再打开也一样。
- 有人记了一笔、来了新电话或新邮件：下一次打开照常完整读一遍，看到的是最新的，不会看到旧名单。
- 具体能快到几秒，第 2 刀的对照阶段就能在线上量出来，这里不猜。

## 5. 计数器要盯的表

名单两个接口（`crm/contacts` 智能视图、`crm/today`）实际读的表：`contacts`、`contact_touchpoints`、`contact_identities`、`conversations`、`conversation_messages`、`conversation_briefs`、`contact_stage_events`、`client_pipeline_stages`、`tailor_made_itineraries`、`clients`（只看 `leads_config`、`country`）。

漏盯一张表 = 那张表改了名单不更新。所以有第 2 刀的对照阶段专门抓这个。

## 6. 切片（每刀开工前问 PM）

- **第 1 刀（A 级，Ray 亲手合）**：加计数器表和触发器。不改任何页面行为。触发器只做一件事：把对应客户的数字加一。先在数据库分支上真跑新增 / 修改 / 删除 / 批量写入各一次，确认数字变化正确、写入不变慢、触发器失败不会挡住正常写入之外的东西；撤回办法（删触发器）写进 PR。
- **第 2 刀（B 级）**：服务器接上计数器和内存，但**只对照、不启用**：每次请求仍按现在的办法完整读，同时拿内存那份比一比，不一样就记一条。跑满 3 个工作日，零不一致才进第 3 刀。有不一致 = 第 5 节漏了表，补上再跑。
- **第 3 刀（B 级）**：正式启用，带一个环境开关，出问题一步关掉回到现在的读法。上线后量 3 种情况：连续用、停一分钟后、刚有人改过数据后。
- **以后再议**：现算那 0.5 秒、登录检查 0.2 到 0.7 秒、页面打开时另外 3 个请求。

## 7. 风险

1. 触发器写错会挡住往客人和联系记录表里写数据。这是最大的风险，所以第 1 刀单独做、单独审、先在分支库上跑。
2. 漏盯表导致名单不更新。靠第 2 刀对照阶段抓。
3. 内存占用：CTS 一份约 3MB，客户数个位数，可忽略。服务器重启后第一次照常完整读。
4. 来信很密的时段计数器一直在变，省不下多少；结果仍然正确，只是那时候跟现在一样快慢。

## 8. 这次不做

升级数据库档位（要花钱，且没证据能解决）；把服务器搬到离数据库近的地方；重写排序规则；改页面样式。

## 9. 平台层级（跟班 Inline）

- 归位：既有 CRM 能力下的读取优化，共享工具层，不新增能力线，不登记候选。
- 换客户 / 换行业：计数器按客户一行，没有写死任何客户或行业；任何接入 CRM 的客户直接受益。
- Reuse Statement：复用现有两个名单接口的读取与计算、`fetchAllParallel`、`Server-Timing` 计时；新增的是计数器表、触发器和一层内存；无客户私有事实进共享代码。
