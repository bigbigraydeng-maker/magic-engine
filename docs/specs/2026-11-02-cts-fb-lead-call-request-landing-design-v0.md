# Facebook 客人「邮件 → 专属落地页 → 打勾请顾问回电」设计稿 v0（2026-11-02，草稿，不含代码）

> **风险级别：A**（新增免登录公共写入口、碰客人联系方式与同意、跨两个仓库）。**只有设计，不改线上任何东西。**
> **来源**：PM 2026-11-02 在 76 号窗口：欢迎邮件里放一个「Book a call with us」，点开专属落地页，客人只要打勾就让顾问回电；页面要说明「您看到这个页面是因为您填过 Facebook 表单，我们已经有您的电话和邮箱」。PM 说「专属链接可以开发」，并补充：**Facebook 表单里填的团，不一定是客人最终要去的**。
> **落地页本身**（已做，草稿）：CTS 官网仓库 PR chinatravel#293，路径 `/campaigns/shanghai-beyond`，目前没有打勾、没有专属链接。
> **依赖**：专属链接机制**不另造**，复用 76 号之外 127 号窗口的设计稿 PR 3412（邮件点击跟踪 v0.4：每人一个签名令牌、CTS 自己的域名只做跳转）。本稿只加「落地页链接」这一类和「打勾回电」入口。

## 0. 给 PM 的一页

**一句话**：欢迎信里的按钮换成「这位客人专属」的链接；客人点开落地页，页面写明他为什么看到这页；他打一个勾，系统就在 CRM 的「今天要联系」里给他建一条「客人主动要求回电」，分给他的跟进人；整个过程**不会自动给他发任何东西**。

- **客人看到的**：落地页顶部一句「您看到这个页面，是因为您填写了我们的 Facebook 表单，我们已经有您的电话和邮箱」，下面一个勾「请旅行顾问给我回电」和一个提交按钮。页面不显示他的名字、电话、邮箱。
- **同事看到的**：CRM 今天要联系里出现这位客人，标「客人主动要求回电」，时间线里有一条记录。
- **团的问题（PM 补充）**：客人在 Facebook 表单里填的团只当「线索」，**不当最终意向**。落地页「其他团」只调整顺序、**永远显示全部**；回电记录里「感兴趣的团」记的是「他在这页上点的」，和表单里填的团分开存。
- **紧迫感**：只用真实信息（下一个出发日），**不写数字、不写订金、不写限时倒计时**（PM 11-02 定）。
- **没有别人能冒充**：令牌是签名的、有有效期；没有令牌或令牌坏了，页面只显示电话号码和普通咨询表单，**不显示打勾**。

## 1. 不做

- 不自动给客人发邮件 / 短信，不自动打电话；打勾只建「待回电」。
- 不做打开跟踪；不改销售自由写的邮件。
- 不在页面回显任何个人信息；不在网址里放邮箱、电话、联系人编号。
- 不在本稿内做「Facebook 表单一填完立刻发信」（那是发信底座阶段 2，另稿）。

## 2. 层级判定（Inline）

- **L1 共享**：专属链接 + 公共回电入口（客户无关，参数是令牌和来源标识）；**L3 Connector**：官网页面只是展示和提交；**L4 客户配置**：CTS 的域名、落地页文案、跟进人分配规则。
- 换客户测试：把 CTS 换成 NAL / 地产客户，入口代码不用改，改的只是域名和页面文案。

## 3. 设计

### 3.1 令牌
- 复用 PR 3412 的签名令牌：含联系人、用途（`landing`）、签发时间；**不含**邮箱、电话；有效期建议 30 天（客人收信后几周内还会点）。
- 给每位新进 Facebook 客人签发：落地页链接形如 `https://go.<CTS域名>/l/<令牌>`，先跳转到 `ctstours.co.nz/campaigns/shanghai-beyond?t=<令牌>`（跳转页只做跳转，沿用 3412 的「新域名只做跳转」做法）。

### 3.2 落地页（CTS 官网仓库）
- 页面读 `t`，**不自己验签**，只在有 `t` 时显示「为什么看到这页 + 勾 + 提交」。
- 提交 = `POST` 到 ME 的公共入口；成功后页面变成「已收到，顾问会尽快联系您（工作时间 …）」。
- 没有 `t` / 提交返回令牌无效：折回现在的「Call 电话 + 咨询表单」，不报技术错误。

### 3.3 ME 公共入口 `POST /api/public/call-request`
1. 限长读体、限速（按令牌和来源 IP）。
2. 验签、查有效期；失败一律返回同一句话，不区分原因。
3. 找联系人；**已标「别再联系」（do_not_contact）的人：什么都不记**，页面照常显示「已收到」。
4. 幂等：同一客人 24 小时内只算一次。
5. 写一条入站触点（来源=落地页，`metadata.call_requested=true`，页面标识，同意文案版本号和时间）。
6. 在 CRM 里建「回电」并分给该客人的跟进人（没有跟进人就按现有分配规则）。
7. 发一个业务可读的事件（`crm.call_requested`），带回执：请求号、客户编号、联系人编号、状态、来源页、时间；**事件不触发任何外发**。
- **只有 POST 才写**：邮件扫描器、链接预取只会发 GET，什么都不记。

### 3.4 「感兴趣的团」
- 落地页上客人点的团（本页的 Shanghai & Beyond，或「其他团」里点过的）记进触点元数据 `interest_page`。
- Facebook 表单里的团仍存在它原来的地方，两者**分开存、分开显示**；同事看到的是「他在表单里选了 A 团；在落地页上看了 Shanghai & Beyond」。

### 3.5 「其他团」更智能（官网仓库，随落地页做）
- 先推 2 个团并写出理由（理由只用团数据里已有的城市 / 天数 / 价格），再是「你有多少时间」的天数筛选。
- 有令牌且 ME 能给出「表单里填的出发时间 / 预算」时，只用来**调顺序**；因为表单团不一定是最终要去的，**不隐藏任何团**。

### 3.6 发信接入（需先核实）
- 每天 8:01 的欢迎信是 PM Google 账号下的表格脚本发 Mailchimp 批次。要把每人专属链接放进信里，需要二选一：①ME 每天在批次前给当天新人签发令牌，写进 Mailchimp 的一个合并字段；②脚本向 ME 取令牌。**①更安全（脚本里不放签名密钥）**，但要核实 Mailchimp 合并字段写入权限。**这一项实现前先做只读核实。**
- 阶段 2（ME 自己发信）上线后，令牌直接在发信时生成，上面的接入作废。

## 4. 安全与隐私

- 新增免登录写入口 = A 级：必须有限速、验签、幂等、不回显、不区分失败原因。
- 页面文案「我们已经有您的电话和邮箱」只在令牌通过格式检查时显示；不是所有访问者都看到。
- 同意：勾的文案、版本号、时间随触点保存；Facebook 表单的同意依据沿用 `form_disclosure_attested`。
- 同事话术：不对客人说「我们看到你点了链接」（沿用 3412 的规则）。

## 5. 分步实施（都是 A 级，各自要 PM 回「合」）

1. **前置**：PR 3412 合并并实现（令牌签发、跳转域名）。
2. ME：公共回电入口 + 令牌用途 `landing` + 回执 + 测试（试跑只对 hello@ 的测试联系人）。
3. 官网（chinatravel 仓库）：落地页打勾组件 + 更智能的「其他团」。
4. 发信接入（见 3.6，先只读核实）。
5. 当场试跑：用 hello@ 测试联系人走完「发链接 → 点开 → 打勾 → CRM 出现回电」，拿真实输出，**不对任何真实客人发送**。
