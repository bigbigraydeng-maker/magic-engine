# 素材进料与共用库设计 v2

**日期**：2026-08-02 · **状态**：设计待 PM 确认
**v1 被魏征审出 6 BLOCKER（其中 3 条是事实错误），本版为重写，不是打补丁。**

---

## 0. PM 拍板的前提

1. **客户自己实拍的素材坚决不可以共用给同行**
2. 素材按**画面语义**找，不按行业硬分组（一张地板图同时是「地板」和「温馨家居」）
3. **不设行业墙**——房产客户可用地板客户的图库室内图；唯一的墙是「客户实拍」
4. 上传链接进来的素材**默认「未核实」**，只在需要打真价时由 FDE 确认那几张（2026-08-02 拍板）

## 2. 两条正交的属性（v1 把它们混成一个字段，是错误根源）

```
source     —— 这东西哪来的（决定能不能给真价背书）
ownership  —— 谁能看见它（决定能不能跨客户共用）
```

**`source`（唯一的真实性判据）**

| 值 | 含义 | 能给真价背书 |
|---|---|---|
| `client_verified` | FDE 逐张确认过是客户实拍 | ✅ **只有这一个** |
| `client_provided` | 上传链接进来的，**未核实** | ❌ |
| `fde_shot` | 我们为该客户实拍 | ✅ |
| `stock` | 图库下载 / 全网抓取 | ❌ |
| `ai_generated` | AI 生成或 AI 改写 | ❌ |
| `unknown` | 历史存量，来源不明 | ❌ |

**`ownership`（唯一的可见性判据）**：`client_exclusive` | `industry_shared`

**红线只认 `source`，不认 `ownership`**——避免「AI 衍生物归了客户 → 被当成真料」这类误用（魏征 M1）。

---

## 3. 隔离：三层，不靠查询纪律

v1 的「唯一查询帮手」被证明强制不了，改为：

1. **物理分表**：行业共用素材放**新表 `shared_clips`**，客户素材留在 `client_assets` / `video_clips`。跨客户查询在结构上不可能发生——不是"记得加条件"，是"没有那张表可查"
2. **存储分桶**：客户专属图走**带签名的临时地址**；共用素材才用公开地址。数据层再漏，图也拿不到
3. **CI 断言**：以 Oztop 身份跑检索，断言 CTS 那 44 张一张都不出现（魏征 N9）

新表而非「`client_id` 改可空」的理由（v1 的方案被推翻）：改可空后所有既有查询都要补条件，遗漏即泄漏；而现存两处按 id 取图**本来就不带 client_id**，正是向量检索"返回 id 再解引用"的模式——风险不可控。

## 3.5 现实校正：素材不缺，是路没通（2026-08-02 清点）

设计 v1/v2 前两版都建立在「数据库里 81 张 = 全部素材」这个错误前提上。实际清点：

| 位置 | 媒体文件 | ME 能看到 |
|---|---|---|
| Supabase `visual-assets` | **81** | ✅ 唯一 |
| Dropbox `MagicLab_Studio/Oztop` | **480** | ❌ |
| Dropbox `MagicLab_Studio/_shared/library` | **525** | ❌ |
| Dropbox `MagicLab_Studio/CTS` | **199** | ❌ |
| Dropbox `相机上传`（含今天新拍） | **444** | ❌ |
| Dropbox `TradePlus`（按 6.5mm/9mm 分好的产品图） | 53 | ❌ |
| Dropbox `_shared/music` | **17 首音乐** | ❌ |

**系统只看得见 3%。** 且 PM 手工归档的结构（`CTS/` `Oztop/` `_shared/library` `_shared/music` `_shared/raw_intake`）**已经就是本设计要建的分层**——ME 要做的是读它，不是另建一套。

连带推翻的旧结论：「CTS 零真实素材」（实为 199）·「Oztop 只有 7 条真料」（实为 480）·「工厂没有音乐」（实为 17 首读不到）。

## 4. 进料：五个入口（Dropbox 是主入口）

| 入口 | 现状 | 默认 source | 默认 ownership |
|---|---|---|---|
| **⭐ 0. Dropbox 同步**（PM 亲自持续录入的主来源） | ❌ **要建** | 见下表（目录即意图） | 见下表 |
| **A. 客户免登录链接** `/upload/[token]` | ✅ 已建 | `client_provided`（**未核实**） | 客户专属 |
| **B. FDE 后台上传** `/dashboard/clients/[id]/assets` | ✅ 已建 | 上传时选：客户实拍 / 我们拍 / 图库 | 客户专属 |
| **C. 全网抓取** `stock-harvest`（**Apify/Pinterest**，凭据已配；Unsplash 那份是死代码） | ✅ 已建 | `stock` | **行业共用** |
| **D. AI 生成/改写** `stock-transform` | ✅ 已建 | `ai_generated` | 衍生物归触发客户 |

### 入口 0：Dropbox（PM 拍板 2026-08-02）

**授权**：全盘**只读**，代码里硬编码只扫 `MagicLab_Studio/`。PM 现有 2500 个文件与归档习惯一个字不改——系统适应人，不是人迁就系统。

**PM 的动作只有一个：把文件丢进某个文件夹。** 不建目录、不改名、不填表。

**目录即意图**（丢错也能救）：

| 路径 | source | ownership | 说明 |
|---|---|---|---|
| `MagicLab_Studio/<客户名>/**` | `fde_shot` | 该客户**专属** | 可给真价背书 |
| `_shared/library/**` | `stock` | **行业共用** | 同行可用 |
| `_shared/music/**` | — | 共用音乐 | 直接解「BGM 与前作同曲」 |
| `_shared/raw_intake/**` | `unknown` | **待定** | 系统看图猜客户 → 今日待办一键确认 |
| `相机上传/`、其它顶层目录 | — | **不扫** | 混私人内容；要用就自己拖进 raw_intake |

**丢错的救法**：`raw_intake` 里的素材由 vision 分析猜归属，在今日待办出一条「12 张新素材待归属（看起来像 Oztop 展厅）」，PM 点一下确认或改选客户。**猜错的代价是点一下，不是数据泄漏**——未确认前一律按"客户专属且不可共用"处理。

**同步方式**：只读、只拉、**永不写回**；按文件路径 + 修改时间做幂等，重复跑不重复入库。

**客户上传页一个字都不改**（魏征 N2）——PM 定的「点链接 → 选文件 → 传完」三步不能加东西。来源判定全部放 FDE 侧。

**FDE 确认通道**（按 PM 选的 B 方案）：素材库页每张图一个「确认是客户实拍」按钮，点了才 `client_provided → client_verified`，带审计记录（谁、何时、哪张）。平时不用点，只在要出「打真价」的片子时确认那几张。

## 5. 检索：先不上向量

**第一批做法**：扩展已有的 `asset-library/search`
- 加 `ownership` 过滤（本客户专属 + 行业共用）
- 加结构化过滤（`objects` / `scene` 命中）
- 排除视频行（`vision_metadata.kind='video'` 的行没有 scene/objects，会污染排序——魏征 M6）
- 库小于 N 张时它已经会跳过 LLM 直接返回全部，81 张这个量级足够

**什么时候才上 pgvector**：满足全部三条再上——① 单客户可选素材 > 500 张 ② 图片描述与检索词统一语言 ③ 先用 20 条真实检索需求做人工标注集把相似度阈值定出来（不能拍脑袋定阈值）。

**阈值不达标时返回空**，不是「交给人审」（魏征 N8）——`strategist` 已有「真料不够就少几镜」的既有路径，走它。

## 6. 加工：I2I 与 I2V

沿用现有链路，本设计只定规则：

| 场景 | 做法 |
|---|---|
| 抓来的图进成片 | **必须先 I2I 改写**（现有红线：原图永不进成片） |
| 共用图给某客户用 | **I2I 改写成该客户风格**，防同行片子雷同 |
| 客户实拍 | **不改**——改了就不真了 |
| 静图要动 | I2V（Muapi 图生视频） |
| 打真价 | 只能 `source='client_verified'` 或 `fde_shot` |

**成本闸门**（魏征 M7）：
- `(source_asset_id, client_id)` 唯一约束——同一张图给同一客户只改一次
- 衍生物计入现有工厂日预算闸
- 硬上限：每客户每天衍生 ≤ 20 张（$0.80/天/客户）

## 7. 交付分两批（顺序与 v1 相反）

**第一批：把已有素材接进出片 + 来源标记 + 隔离**
- 理由：CTS 44 张、Oztop 37 张**躺着一张没用上**（CTS 进出片的真料 = 0），这是当下最痛的断点，而共用池初期本来就是空的
- 内容：source/ownership 字段（分两个 PR：先可空回填，再加约束——魏征 M8）· FDE 确认通道 · 存储签名地址 · 检索加归属过滤 · **接进 `evaluate.ts` 的 `sourceImagePool`** · CI 隔离断言
- **有真实使用方**，不会重蹈「建完零调用方」（魏征 M3，本仓有前科）

**第二批：共用池真正跑起来**
- `stock-ingest` 改为抓取产物进 `shared_clips`
- 共用库浏览页（未改写原图**只给缩略图、不给下载**——魏征 N7）
- FDE 补标通道（把历史存量按审计流程升为共用）
