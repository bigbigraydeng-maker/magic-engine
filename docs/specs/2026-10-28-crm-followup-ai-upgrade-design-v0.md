## 0. 给 PM 的一页（先结论）

**第一件事：能做；我给的节奏只是起点，每个人的下一步由他自己的情况决定。**
传统做法是按日历发信。ME 的做法：每天按证据给每个客人选「今天最该做的一件事」（也可能是什么都不做），做完核对有没有用，再用结果改下次的选择。

**第二件事：先修三个地基毛病，再上 AI，否则 AI 会在错的名单上写信。**
①名单把填完广告表单后自动出现的那句话当成「客人回话了」（我估 228 个里约 100 个是假的）；②销售电话记录里没有「什么时候打的」；③「交给系统跟」没有系统在跟，约 330 个表单客人现在没有任何后续动作排着。10-26 新的留资广告已经开了，新线索正在重新进来，这几周是修地基的窗口。

**第三件事：你的三个问题，默认答案如下（第 4 周按真实结果调，不是铁律）。**
1. **时机**：第 1 次 = 进线当天，电话 + 只发 1 封邮件；第 2 次 = 最近一次联系后第 3 个工作日；第 3 次 = 距第 1 封满 7×24 小时之后，电话优先；之后不追，等他自己说的出行时间。报价之后沿用你和销售已定的「3 个工作日 + 再 3 天」。邮件主动来问的客人走满三次，广告表单客人走轻量版。
2. **内容**：第 1 次 = 回答他问的事 + 问 1 个具体问题；第 2 次 = 1 条新信息（他看的团的最新出发日 / 价格，只引官网）+ 1 个问题；第 3 次 = 替代选项 + 「现在不合适也没关系」。每句话都有出处，没出处的不写。
3. **AI 怎么做**：每个客人一条时间线 → 每天算他的状态和下一步（含「不打扰」）→ 模板里 AI 只填两个小空格（引用他的一句原话、问一个具体问题；价格日期链接由系统从上架团目录填）→ 另一个角色核对 → 同事在 CRM 里改一句、点发送（发送时系统再卡一遍 7 天 2 封、退订、旅行社）→ 3 / 7 / 30 / 90 天核对结果 → 每周写一页建议，你批了才改。AI 不替你发。

**第四件事：分三期。**
- **本周**（不写功能）：SOP v1 跟同事过；用网站真实的算法再数一遍审核里的估算；把存量客人分批做成人工名单；核对并标记 7 位说过「退订」的客人。
- **一个月**：修三个地基毛病 + 第 2 / 3 次提醒 + 在 127 号做的发邮件面板里预填；先试跑一周（建议只发到 ME 自己的邮箱，不进 CTS 的系统），你看 10 份真建议再决定对 CTS 打开。
- **一季度**：按客人出行时间排节奏、异议分类、官网浏览接到客人、对照组实验、复制到 NAL / Oztop。

**现在只问你一件事：**「主动来问的」客人重点跟三次，「广告表单客人」轻量跟（只有他回过话或通过电话才继续）——行不行？**回 `分档` 就行。**
后面还有两件，等这件定了我再问：①约 330 个存量客人先跟哪一批（我建议先「电话聊上了、没有书面回复」的 178 人）；②授权同事核对并标记 7 位说过「退订」的客人。

> 已定、不再问：「7 天 2 封」含群发和一对一（你 10-28 对 127 号说过，我沿用；回信算不算，127 号稿默认算，我也按算）。我自己拍的技术选择：发送只走 127 号那一条路径（发送时的闸最全），Outlook 草稿箱只作兜底；第一期 AI 只填两个空格，不自由写作。
> 优先级（按 §11 打分，逐项见 §7）：修地基 P0 · 第 2 / 3 次提醒 P0 · 合成一个数数函数 P0 · 结果核对 P0 · 异议分类 P2 · 官网浏览接到客人 P3。清零退订客人是合规红线，不走打分，先于自动节奏做。
> 诚实的边界：第一期做得到的「ME 独有」是三样——把「欠他回复」和「该推他一把」放进同一个状态里、新表单带来的结构化出行时间、价格日期的核对闸。「用结果自动调节奏」第一期做不到（约每周 56 个表单客人、约 1% 成交，定金层测不出），只做记录和观察。

## 1. 范围与边界

### 1.1 属于 IMPACT 的哪一段

| 阶段 | 本稿覆盖 |
|---|---|
| **Inspect** | 关系账本（触点分类）、事实包、信号清单 |
| **Measure** | 结果阶梯、基线、验证窗口、可比性限制 |
| **Prescribe** | 状态派生、行业跟进节奏、下一步最佳动作（含「不打扰」） |
| **Act** | AI 只填两个空格 → 独立核对 → 预填进 CRM 里 127 号的发邮件面板 → 员工发送（发送时全部闸）→ 回执 |
| **Check** | 3 / 7 / 30 / 90 天核对 |
| **Tune** | 客户私有记忆、周报、建议卡、向行业手册晋升的判据 |

> 没有进入 Check 和 Tune 的「自动发信」只能叫执行完成，不能叫闭环完成（产品定义 §6）。所以本稿把 Check / Tune 和 Act 放在同一期。

### 1.2 Build vs Connect（产品定义 §11 的六问）

1. **属于哪一段？** Prescribe + Act（受控预填，人发送）+ Check + Tune。
2. **是否直接增强 Digital Marketing Intelligence？** 是：选「下一步最佳营销动作」、验证结果、学习。
3. **市场上有没有可靠产品？** 有——邮件序列（Mailchimp 流程）、CRM 提醒（各类 CRM），它们多是**日历驱动**的。它们能不能读客人的话、核对事实、按结果学习：**我没有逐个产品核实**，按常见产品能力判断；护城河的论证不依赖这一点，而依赖下面第 6 条。
4. **ME 是否只需要它们的数据 / 动作 / 结果？** 是：发信走 127 号设计的 `sendMailNew`（Outlook Connector），名单和触点用现有 CRM 数据，**不新建 CRM 本体**（不加联系人管理、不加阶段看板；只在 CRM 首页已有的「今天要联系」里多一个分组「该再联系」）。
5. **外部连接失败时能不能诚实显示 UNKNOWN？** 能：读不到的一律写「没读到」，发前闸读不到按「不通过」（对齐 Newsletter 手册 NL-09）。
6. **自建会不会形成数据 / 决策 / 学习的护城河？** 会：账本 + 状态 + 结果核对 + 客户私有记忆，是别家日历式序列做不出来的。

> 与「CRM 默认连接、不自建本体」的关系：本稿**不增加 CRM 功能**，只增加决策层（什么时候、对谁、说什么、凭什么、有没有用）。联系人 / 触点 / 名单页是已有资产，不动。产品定义 §16.7 要求盘点 CRM（保留 / 连接 / 采购 / 退役 / 停止新增）；**本稿的前提是「保留现有名单引擎、不新增 CRM 本体功能」，请 PM 知悉。**

### 1.3 不做什么

- 不发任何邮件、不改任何设置、不动 Mailchimp（本稿是文档）。
- 第一期**不让 AI 自动发**；「跑稳一个月再说」是 PM 10-23 的原话，沿用。
- 不新建 CRM 页面、不新建「第七条能力线」、不新设支柱。
- 不碰 Newsletter / 群发（126 号窗口 + PR #3331 管），只**共用数数函数和发前闸**。
- 不做「通话后选模板发邮件 + 模板管理」（127 号窗口在做，PR #3334 设计稿）；本稿建在它之上，只加「决策层」和「AI 只填两个空格」。
- **不另建发送通道、不另建回执表**；Outlook 草稿箱投递只作第二期兜底（§4.4）。
- **第一期 AI 不自由写作**，只在模板里填两个空格（§3.3）。
- 不处理旅行社客人的报名表 / 付款 / 行前序列（SOP 缺口表里另有排期）。

## 2. 核心设计：账本 → 状态 → 下一步

### 2.1 一句话

> **把「第几天发第几封」换成「这个人现在处于什么状态、球在谁手里、他自己的时间线是什么 → 今天对他最值得做的一件事（可能是什么都不做）→ 做完核对有没有用 → 用结果改下次」。**

### 2.2 IMPACT 展开（复用什么、新增什么）

| 阶段 | 做什么 | 复用（已有） | 新增（最小） |
|---|---|---|---|
| **I** | 每个触点分类：谁说的（客人 / 员工 / 平台自动 / AI 草稿经人发出）、是不是真话（排除广告开场白、自动回复、退信）、时间可信度（精确 / 近似）；构造「事实包」 | `contact_touchpoints`、`conversation_messages`、`isFormTemplateMessage`、`isAutomatedTouch`、`dnc.ts`、`travel-date.ts` | `classifyTouch` 纯函数（一处判据，名单 / 汇总 / 新节奏共用）；事实包构造器 |
| **M** | 为每类动作定义结果阶梯、窗口、基线 | `me_sale_outcomes`（合格线索 75 / 成交 2）、`flywheel_outcomes` 的 verdict 词汇（confirmed / inconclusive / reversed）、审核报告基线 | 基线表 + 口径文档（本稿 §6） |

### 2.3 状态：「球在谁手里」+「他的时间线」

状态**由账本算出来**（派生），不读 `stage` 字段（它只被 AI 填一次，见审核 F4）。

| 状态 | 怎么算 | 默认下一步 |
|---|---|---|
| **欠他回复** | 客人最后一条**真话**晚于我们最后一次人工联系 | 24 小时内回（已有：邮件回复检测 / #3271 跟进名单接口；回信本身不被 7 天 2 封拦，但会被计入） |
| **刚进线、没人碰** | 没有任何人工联系 | 首次联系（电话 + 当天 1 封邮件） |
| **等他回（线索链）** | 我们联系过，客人没有新真话；记「第几次」 | 到期 → 第 k + 1 次 |
| **等他回（报价链）** | 「报价已发」之后 | 报价 + 3 个工作日跟进，再 3 天 |
| **等他的时间** | 三次触达用完，或客人自己说了时间 | 在他的窗口前约 90 天回来一次；或有「有理由的新信息」时 |
| **暂停** | 说过不要 / 退订嫌疑 / 推迟 / 旅行社客人付全款前 | 不动；旅行社客人只出「联系旅行社」待办 |
| **终态** | 已付定金 / 全款 / 非咨询 | 交给别的流程 |

派生字段：`ball`（ours / theirs / none）、`phase`、`touches_since_last_customer_signal`（我们在客人最后一次真话之后主动联系了几次）、`last_authentic_customer_signal_at`、`timeline`（客人自己的出行窗口，带来源和置信度）、`tier`（A / B / B+ / 旅行社）、`email_budget_168h`（近 7 天主动邮件封数）、`stop_flags`。**重复留资**（同一个人再填一次表，近 120 天约 71 次）当作「回头客」信号（已有 `returning-lead`），不当回复；新一轮从第 1 次数，额度照旧。

### 2.5 动作菜单与选择规则

|---|---|---|

| `nudge_alternatives_close` | 电话优先 / 邮件 | 第 3 次：替代选项 + 收尾 + 退出办法 |
| `quote_followup_1` / `_2` | 邮件 | 报价后 3 工作日 / 再 3 天 |
| `timeline_wake` | 邮件 | 他的出行窗口前约 90 天 |

| `ask_for_phone_or_email` | 邮件 / 私信 | 联系方式缺失 |
| `contact_agent` | — | 旅行社送来的客人：只出待办 |
| `wait`（**显式「不打扰」**） | — | 额度满 / 在他的时间线之外 / 刚联系过；写明原因和下次复查日 |
| `suspect_stop` | — | 疑似退订：暂停该人所有自动动作，由人确认 |

**第一期用规则选**（上面 §2.6 的节奏表），不用模型打分。**优先级**：欠他回复 > A 档到期 > B+ 档到期 > B 档到期；同档按「超期天数」；客人刚有新动作（点了团页、回了真话）加分。**产能切线**：按配置的每人每天动作数切，**超出的排队、不消失**（2026-08-02 的教训：人不能因为一个上限就从页面上消失）。**第二期**才用测得的结果（回信率、有效通话率）替换规则里的权重。

### 2.6 默认节奏（回答 PM 第 1 问）

分档：
- **A 主动来问的**：邮件 / 官网表单 / WhatsApp / 电话打进来的，或表单客人后来写了真话。
- **B+ 有互动的表单客人**：只填了表，但电话通过话 / 点了团页链接。
- **B 广告表单客人**：只填了表，还没跟我们说过话。
- **C 旅行社送来的**：不在此节奏内，只联系旅行社（R1）。

| | A | B+ | B |
|---|---|---|---|
| 首次联系 | 2 个工作小时内（电话 + 当天 1 封邮件） | 当天 / 次个工作日上午 | 同 B+ |
| 电话尝试 | ≤ 2 次 / 3 个工作日 | ≤ 2 次 | ≤ 2 次 |

> 7 天 2 封：口径按 PM 10-28「含群发与一对一」，回信也计入（127 号稿默认）。线索链按 0 / 3 / 7 天发，三个时点任何 7 天窗口都 ≤ 2 封——**前提是第 1 次当天只发 1 封**（审核 F10）；客人写信来的，你回他的那封**就是**这 1 封。额度不够时系统给出「最早可再发时间」，当天改打电话，不硬发。电话不占额度。
> 为什么不是固定天数：这些天数是**起点**，来自 PM + 销售已定规矩和上面的额度约束，**没有本地证据证明 3 天比 5 天更好**；所以从第 1 天起就量结果（§6），第 4 周据数据调。**下表的数字都是 CTS 的配置值**（现阶段只有 CTS 一家的证据，标「候选参考」，红线 7），旅游剧本只放结构。「第 3 个工作日」折成自然日是第 3～6 天，所以第 3 次以「距第 1 封满 168 小时」为准，不写"第 7 天"。

**「等他的时间」**（代替 14 天休眠）：
- 知道出行月份 → 出发前约 90 天回来联系 1 次（长线团提前数月到一年订，旅游剧本现有 60 天唤醒（`travel-date.ts` 的 `LEAD_DAYS`），本稿改成「可配置，默认 90」）；
- 不知道 → 只在**有理由**时联系：新出发日、价格变化、早鸟，且他曾看过 / 选过那个团；每季度最多 1 次；
- 不是删除：他一开口、一点团页，状态自动回到「等他回」。

### 2.8 诚实的边界（回应「这像传统营销公司做的事」）

魏征复审的原话是：第一期本质上还是「3 / 7 天 + 停」的传统序列，只是分了档。这个批评对一半。**第一期真正做得到、也确实是 ME 独有的有三样**：①把「欠他回复」和「该推他一把」放进同一个状态里，各有时钟；②新表单带来的结构化出行时间让「按客人时间线排节奏」对新线索可以提前做；③价格日期链接的核对闸（每句话有出处，读不到就不发）。**第一期做不到的**：按结果自动调节奏（约每周 56 个表单客人、约 1% 成交，定金层测不出，只能先记录和观察）、异议分类（58 / 1027）、官网浏览接到客人（0 条能对上）。这些在第二、三期的数据补齐之后才成立，本稿不假装现在有。

## 3. 内容怎么「千人千变」（回答 PM 第 2 问）

### 3.1 五条轴

| 轴 | 内容 | 来源 | 没有时怎么办 |
|---|---|---|---|
| **锚点** | 他自己说过的话（逐字、带日期和出处），或新表单的结构化回答（出行时间、想去的团、人均预算） | 员工备注原话、客人邮件 / 私信、留资表单 v6.1 | **不写**；只用「你在表单里选的那个团」 |
| **兴趣** | 他选 / 问 / 看的团 | 表单所选团（501 / 501）、对话、将来的点击 | 用通用开场 |
| **这一步要做的事** | 第 1 次：回答 + 1 个问题；第 2 次：1 条新信息 + 1 个问题；第 3 次：替代选项 + 收尾 | 节奏表 | — |
| **异议**（第二期） | 价格 / 签证 / 健康 / 日期 / 信任对应的内容积木 | 简报异议字段（先校准） | 不路由 |
| **声音** | 发件人名义（CTS：Baker Gu, China Specialist，默认英文）、中老年受众：短句、不催促 | 客户配置 + 员工修改分析（客户私有记忆） | 默认声音 |

### 3.2 事实包（草稿里每个数字 / 日期 / 团名 / 链接的唯一来源）

优先级从上到下，**冲突时官网为准**（NL-02）：
1. **已上架团目录**的价格 / 班期（PM 10-21：团价班期查 ME 团目录；#2977 做这件事，草稿，CTS 团目录目前**未上架**；读取直接用 127 号设计的只读函数 R2a 和 `facts/published-tours` 提供者，不另写）；
2. **官网团页**：title / h1 对得上团名、页面 From 价、下一个确认出发日、站点地图里存在（验链接**不能只看 200**）；
3. **员工确认过的**事实；
4. **客人原话**（带 `evidence_id`）。
缺任何一项 → 该句换成「我确认后给您准确的价格」，或不写。**不能用 `offerings.yaml`**（报价库没跟 10-19 涨价，会少报 500 纽币，审核 F14）。

### 3.3 AI 在第一期只填两个空格（不自由写作）

> 为什么：10-26 试跑里 AI 曾凭空写出「价格有有效期」；127 号稿把「AI 起草」列为本轮不做。所以第一期的「千人千变」靠**选**和**填空**，不靠自由写作。

每封建议信 = **模板骨架**（127 号的模板与渲染器）+ **两个空格**：
- **空格 1「锚点句」**：只在有可查证的出处时出现，格式固定、由程序拼。出处有两种：①**新表单的结构化回答**（10-26 起的留资表单 v6.1 会问出行时间、想去的团、人均预算——可查证，比"引用他说过的话"更可靠）：`You mentioned you're hoping to travel in {month}.`；②**逐字原话**（员工备注、客人邮件 / 私信）：`When we spoke on {date} you mentioned "{逐字片段}".`。AI 只负责从出处里**选**最相关的一条，选不出就不出这一句。
- **空格 2「具体问题」**：从一个**固定问题库**里选（几个人 / 大概哪个月 / 想看哪个团 / 有没有同行的人需要特别安排……，库在客户配置里）；AI 只负责**选**哪个问题最合适，不自由造问题。
- **价格、日期、团名、链接**：全部由渲染器从上架团目录和官网事实填，AI 碰不到。
- AI 还可以做的**选择**：用哪个模板（第 2 次的 `nudge-new-info` 还是第 3 次的 `nudge-alternatives-close`）、在候选团里选「他最可能关心的那个」。
- **本稿不做**「早鸟」「还剩几周」这类动作：价格优惠、倒计时类说法既是 CTS 红线，也过不了发送时的检查。「有理由的再联系」只用**团目录里的新出发日 / 价格变化**。

**第二期才放开自由润色**：把关员在 20 份对抗用例上全部拦住、第一期跑满一个月、结果核对显示没有出过事实错误之后，才允许 AI 在空格内写 1～2 句自由文字，仍过同一套把关。

### 3.4 引用规则

- 引用客人的话必须**逐字**出现在 `evidence` 里（同 `stage-from-conversation.ts` 的纪律：说不出原话就不算数）；人名、数字、「首次 / 第一次」这类判断**不由 AI 自由生成**（借 `call-summary-gate` 的四道检查：人名对档案、数字有依据、判断性描述有依据且未被客人推翻、长度）。
- 健康、年龄、财务这类敏感信息：**默认不引用**，除非客人在同一线程里写给我们且与这一步相关；拿不准交给人。
- 起草时**不送电话、邮箱、姓**给 AI，只送名字（称呼用）、所选团、证据片段。

### 3.5 示例骨架（占位符，不含真实客人信息）

```text
Subject: {团名} — a quick update            ← 来自表单所选团 / 对话
Hi {first_name},                             ← 只用名
{锚点：仅当有可查证的出处}                   ← "You mentioned you're hoping to travel in {month}." 或 "When we spoke on {date} you mentioned {quote}."
{新信息：仅来自事实包}                        ← "The next confirmed departure is {date}: {官网团页链接}"
{一个具体问题}                               ← "Roughly how many people would be travelling?"
{退出办法：仅第 2 / 3 次}                    ← "If you'd rather I didn't follow up, just let me know — no problem at all."
Baker Gu, China Specialist
```

其中**只有「锚点句」和「具体问题」两处由 AI 选 / 填**；标题、新信息、链接、退出办法、署名由模板和渲染器给。

### 3.6 不写什么

倒计时 / 销售截止 / 「只剩几席」；邮件里约电话或会议（让他回信）；「免签」；没出处的价格、日期、有效期、名额、退改规则；对旅行社送来的客人付全款前直接发信；对说过「不要」的人发任何东西。

## 5. 治理

- **7 天额度**：任何**滚动 168 小时**内，我们发给同一人的邮件 ≤ 2 封，所有类型合计（欢迎 / 报价 / 跟进 / newsletter）。口径按 **PM 2026-10-28 对 127 号说的「含群发与销售一对一」**；**回信算不算：127 号稿默认算**（与「合计」一致、不会违规），本稿同样按算设计，回信本身不被这道闸拦，但会被计入。第 1 次当天只发 1 封，替代自动欢迎信，不叠加（自动欢迎信的现状见 §10）。**数数函数只能有一个**：以 127 号的 `evaluateFrequency` 四来源并集为准（Outlook 已发送箱含密送、ME 审计行、邮件出站触点、Mailchimp 群发），它自己标出的盲区——欢迎旅程等自动流程发出的信数不到——用 #2363 已验证的 Mailchimp 成员活动记录法补上；Newsletter 手册的 NL-04 / PL-04 调同一个函数。**还差一件要 126 号确认**：占额度的类型谁先占——Newsletter 手册 PL-04 让群发提前预占额度，本稿建议「报价 > 跟进 > 欢迎 > newsletter」（额度紧张时 newsletter 让路）；两边合写一份口径，PM 只答一次。
- **渠道**：第 2 / 3 次只用**邮件 + 电话**。私信 / WhatsApp 只用于客人在平台允许的时间窗内说过话时的回复（具体窗口以 Meta 最新规定为准）；短信没有实现，不用。
- **直客 / 旅行社**：见 §4.3；旅行社送来的客人付全款前只出「联系旅行社」待办；付全款后只许发三样：须知、出发前 2 周行程、微信群邀请（R1 + Q-C1）；期待感 / 邀请朋友序列只发直客（Q-C2）。
- **退订与同意**：第 2、3 次邮件末尾带一句退出办法（第 1 封是回他的问题，不加；措辞见 SOP v1，**回「先不考虑」= 暂停主动跟进 90 天，回 stop / unsubscribe = 别再联系**）；单词 Unsubscribe / Please do not contact 立刻暂停该人所有自动动作，由人确认后在卡片上记一笔「客户说别再联系」；未处理的退订提示不再 30 天后悄悄过期；邮件渠道补「只提示」通道；同意证据缺失（`consent_basis`：近 120 天 787 条里 335 条没有，全时段 442 条）的人不进自动节奏，只走人工。AU《Spam Act 2003》/ NZ《Unsolicited Electronic Messages Act 2007》要求商业邮件有同意、有发件人标识、有退订办法——**我不是律师，请 CTS 的顾问确认**。
- **工作日 / 时区**：员工的**工作量**用工作日算（复用 NZ 假日表）；对客人的**承诺**用自然时间；清单每天 NZ 早上 06:30 生成，系统不在夜里发任何东西，什么时候点发送由同事定；缺年份的假日表返回 `table_missing`，不当工作日。
- **个人信息与 AI 供应商**：起草提示词不含电话、邮箱、姓；对话片段只在事实包里按需出现；使用现有 AI 路由（含 10-26 PM 知情后开的 DeepSeek 备援）；CTS 书面同意与供应商条款核对作为第一期上线前提（#3069 同样标了尚未核实）。

## 6. 结果验证与学习（Check / Tune）

### 6.1 结果阶梯（不是打开率）

| 层 | 含义 | 怎么判 | 窗口 |
|---|---|---|---|
| 0 Execution | 建议被发出 | 127 号回执表（发送时同步写，含 `outcome`）；本稿不靠邮箱同步 | 即时；状态不明的由 127 号的延迟对账收口，仍不明 → **UNKNOWN** |
| 1 Activation | 送达 / 通话接通 | 退信检测；电话结果 | T+1 |
| 2 Output | 客人**真话**回复；点了团页 | 排除自动回复 / 开场白 / 退信；点击要先补 | T+7 |
| 3 Marketing Outcome | 有效通话 / 要报价 / 合格线索 | 通话 ≥ 2 分钟（须有时间）；`me_sale_outcomes` 合格线索 | T+30 |
| 4 Business Outcome | 付定金 | `me_sale_outcomes` 成交 / 阶段 | T+120 |

> 打开率不算结果（苹果隐私保护会自动打开，且 Mailchimp 打开 ≠ 他读了）。电话没有时间之前，层 1～3 里涉及电话的部分一律写 UNKNOWN。

### 6.2 基线（审核报告取数，2026-10-28）

首封主动邮件 7 天内客人回信 22%（43 / 193）；之后的催信回信约 49%（18 / 37，**选择偏差**，不能当有效证据）；客人来信后员工回复，7 天内客人再回 70%；邮件主动来问的首次回复：15 分钟内 6%、24 小时内 57%、26% 没看到回信；邮件首触点客人成交约 10.8%、表单约 1.3%。

### 6.3 怎么知道第 2 / 3 次有没有用

- **观察**（第一期）：按档、按第几次、按间隔分组，看 7 天回信率和 30 天有效通话率；样本 < 20 不下结论（NL-09）。
- **对照组**（第二期，需 PM 同意）：对 **B+ 档**（有互动、会走第 2、3 次的表单客人）按客人代号哈希留 10% 不发第 3 次。表单客人当前约 56 个 / 周，10% ≈ 每周 5～6 人，**约 1.3% 的成交率下 3 个月内测不出定金层的差别**——所以定金层的结论一律写 UNKNOWN，先用回信和有效通话作先行指标。
- **存量实验**：约 330 个「没有后续动作」的客人是现成样本。随机分到 3 个间隔变体（3 / 5 / 7 个工作日），14 天后看回信率；每组约 110 人、基线回信率约 22%、80% 把握，**约 15 个百分点以上的差别才测得出**（子牙复算；原稿写的 12 偏乐观）。**需 PM 同意**，因为是对真实客人的不同对待（风险：低，对照组等于今天的现状——没人跟）。

### 6.4 学习怎么沉淀

- **客户私有记忆**（写进 `memory/service.ts` 读取的客户偏好 / 模式那组表，**不是** `memory/write-lesson`——它写的是跨客户经验池）：例如「选了某团的客人，第 2 次带『新出发日』比带『评价』回信更多」「员工总是删掉某类句子」。
- **向旅游行业 Playbook 晋升**：CTS 单客户证据只算「候选参考」；需要 ≥ 2 个同行业客户的可比证据才算行业手册（`lesson-shareability` 判据；红线 3 / 7）。
- **周调参**：复盘员每周出一张「建议卡」（改间隔 / 改内容积木 / 停某类动作），写明证据和样本量；**档 3，PM 批准才生效**，不自动改。
- **建议修改分析**：保存「预填 ↔ 实际发出」差异的类别（删句 / 加句 / 改口吻 / 改事实），不存全文到记忆；用来改起草提示词和事实包。

## 9. 分层与复用声明（me-platform-tier-gate · Full）

### 9.1 Platform Tier Classification（Full）

**被判定对象**：线索「下一步最佳动作」= 在**已有的 CRM 名单引擎**上加：①触点分类 ②派生状态 ③行业跟进节奏接口 ④起草 → 把关 → 投递链 ⑤结果核对与学习。

**建议层级**（拆开判）：

| 部分 | 层级 | 理由 |
|---|---|---|
| 触点分类函数、状态派生（`followupDue()`）、`IndustryPlaybook.cadence` **接口**、数数函数、事实包校验框架、结果核对框架 | **L1（既有能力的扩展，不新增能力名）** | `segments.ts` 本来就是「通用引擎 + `IndustryPlaybook`」（文件注释明确要求新增行业信号一律扩展这个接口）；**但现在所有调用方都不传剧本、默认用旅游剧本**（`today/route.ts:791`、`contacts/route.ts:948`、`contact-list-view.ts:118`），所以必须按 `clients.industry` 选剧本、默认中性、节奏按客户开关缺省关（子牙复审） |
| 旅游剧本的**结构**：两条链（线索链 / 报价链）、「等他的时间」、哪些信号能叫醒、内容积木的种类、异议类型表 | **L2（旅游行业 Playbook）** | 换行业测试不通过（地产是看房周，物流是报价时效日）；这些只是旅游的通用形状 |
| 所有**数字**（第 3 个工作日、再隔 4～5 天、出发前约 90 天、分档条件）、发件人（Baker Gu, China Specialist）、英文、销售名单、官网团页、R1 的 27 个域名、每人每天动作数、固定问题库、SOP v1 文本 | **L4（CTS 配置）**，旅游行业层只标「候选参考」 | 这些数字现阶段只有 CTS 一家的证据（红线 7：单客户事实一律下沉 L4）；放进 127 号的发信设置行，不进共享代码 |

**归属**：平台基础设施（Kernel / Governance + Measurement / Verification + Memory）。**不新增支柱，不新增版本。**

**换客户测试**：
- 反例客户 NAL（物流）：节奏起点是「报价 → 发货时效」，不是「进线 → 电话」；默认的 3 个工作日、旅行社 R1、英文口吻都不成立 → 这些必须在 Playbook / 配置里，不能在引擎里。
- 反例客户 Roman（地产）：状态集是看房 / 出价，且「等他的时间」是按贷款 / 搬家时间线，不是出行月份 → 同上；引擎只认「等待信号 + 节奏接口」。

**换行业测试**：旅游（月～年）→ 地产（周）→ 物流（日）：节奏数字全不同，引擎里没有任何一个只对旅游成立的默认值；`TOURISM_PLAYBOOK` 保持唯一的旅游常量出处。

**智能层 or 执行手**：选动作、验证、学习是智能层；执行手是员工 + 127 号的发信通道（Outlook Connector）。

**红线检查**：1（禁包装升级）✓ 不叫「跟进智能层」，称为既有名单引擎的扩展；2（客户 / 行业事实不进 shared runtime）✓ 天数 / 话术 / 发件人都在 Playbook / 配置；3（禁直建 L1）✓ 不新增能力名；4 / 5（语义级换客户 / 行业）✓ 见上；6 N/A；7（L2 只装行业级判断）✓ CTS 单客户事实一律下沉 L4。

**PM 待拍板项**：无新支柱 / 新版本；商业口径是分档力度和存量客人的分批顺序（§8）。

**结论**：原想法「新做一个跟进引擎」→ Skill 判定「既有 L1 的扩展 + L2 旅游 Playbook + L4 CTS 配置」。**不登记新的 L1 候选**——理由：没有新的能力名；发送治理 / 数数函数的 L1 候选性质已在 #2363 判过（「待第二个客户有同类需求再评估」），本稿沿用；若 PM 想登记，回 `记`。已过子牙 + 魏征各一轮（§12）。

## 附录 B：验收口径摘要（给实现窗口）

1. 线上同一批数据干跑，审核报告里的每个数字能复现（±10%）。
2. 反例用**客人实际使用的语言和写法**造（英文原句 + 变体；中文价格 / 日期写法）。
3. 变异测试：把「额度」「别再联系」「旅行社」「事实核对」四处的判断删掉，测试必须变红。
4. 不用手拨假时钟测额度 / 窗口 / 冷却，用真时钟 + 变异检验（记忆 10-26）。
5. **快照测试**：非旅游客户（地产、物流、美容等）的名单在改动前后逐人不变；引擎代码里 grep 不到 `Baker` / `CTS` / `3 个工作日` / 英文话术（grep 只是辅助，快照才是验收）。
6. 每个定时 / 事件函数交付前当场手动触发一次完整链路，PR 有「## 当场试跑」。
7. **重跑不重复出建议**；状态一变（客人回信 / 标了别再联系 / 已有人发过）建议当场作废。
8. 加一条测试：跟进模块（决策层）**不引用任何发送函数**；`used_ai_draft` 在 AI 填空后如实记录。
9. 送给模型的提示词里没有电话、邮箱、姓；固定问题库、空格出处核对各有变异测试。
