## 1. 流程（逐步，含失败路径）
```
PM 点「批准处方」→ PATCH 批准路由（只给 requirePaidClientAccess）
  1) 落地（写 approved）成功
  2) 【在路由里、紧接着落地成功之后】发事件 prescription.approved.plan_draft.requested，等结果但限 2–3 秒；
     超时或发送失败 → 写 failed 回执（reason_code=event_not_sent），批准照样返回成功
     （不放进落地函数里：以后周更若恢复自动落地也会跟着触发；「发了不管」与「失败后写回执」矛盾，所以必须等结果）
  3) 才做原有的回读；回读失败照旧返回 500（事件已发出，不丢）
Inngest 函数 plan-draft-from-prescription（concurrency limit 1，key = prescription_id；onFailure 兜底写 failed 回执，写法照 ad-heartbeat.ts:137）
  步骤 A（单步）：门 + 构建 + 映射 + 校验 + 以固定 id 插入 marketing_plans（status='draft'）
        - 门：处方 approved、广告类、有 ad_plays、目标有周期、该客户在白名单（§5）；任一不满足 → 回执 skipped + 原因
        - 插入撞主键 → 回执 already_exists（不看现有草稿的状态，§2）
  步骤 B：写回执（§3）
```
- **事件名**业务可读；事件 data 只放 id：`{ request_id, attempt, client_id, prescription_id, version }`。
- **事件编号每次不同**（必改 1）：`plan_draft:<prescription_id>:<version>:<attempt>`（`attempt` 为首次 0、重试各自递增或 UUID）。依据：Inngest 事件 `id` 在 24 小时内同编号的第二个事件**直接丢弃、不触发任何函数**（官方文档 [Handling idempotency](https://www.inngest.com/docs/guides/handling-idempotency)、[Sending events](https://inngest.com/docs/events)；本仓未实测，实现时用 Inngest dev server 实测一次重复编号）。若重试沿用同编号，PM 点「重试」会被静默吞掉、页面永远显示失败。**防重复完全交给数据库主键（§2），不靠事件去重**。
- **重试走新路由**（必改 1）：`POST /api/clients/[id]/prescription/[pId]/plan-draft/retry`，**权限只给内部账号**（`requirePlanApproverAccess`），原批准路由对已批准处方返回 409，不能复用。
- **批准成功但没有回执**（必改 4）的三种成因（回读失败 500 之前已发事件则不算；进程在提交后发事件前被重启；函数超时/重试耗尽）：统一由页面规则兜住（§3 第 4 条）+ `onFailure` 写 failed。

## 2. 「只生成一份」（必改 2）
- **固定主键**：`marketing_plans.id = uuidv5(NAMESPACE, "<prescription_id>:<version>")`。已核（2026-10-27 查生产库）：`marketing_plans.id` 是 uuid 主键、插入时可自己指定。重复插入撞主键 → 数据库原子拒绝；**不需要部分唯一索引、不需要迁移**；v0.7 写的「已知限制」随之消失。（v0.7 担心的「两个 Inngest 区域同时认领」不是真风险：并发限制是全局的。）
- **查重与插入必须在同一个 Inngest 步骤**：Inngest 每步成功后结果被记住、重试不重跑；若「查有没有」与「插入」分成两步，插入遇到「库已写入但返回超时」会单独重跑而前一步不重跑 → 插两份。本稿合成单步，插入本身带固定 id，重跑也只会撞主键。
- **判重不看状态**：PM 批了自动草稿，或删了它（DELETE 实际是把状态改成 `archived`），之后再来的同键事件仍判 `already_exists`，**PM 删过的也算已存在**。要重新生成走明确的「重新生成」动作（用 `<prescription_id>:<version>:regen:<n>` 算新 id，回执记 regen 次数）。
- **度量**：不数 `already_exists` 占比（真重复时两次都记 `created`，量不出）；数「同一个 `generation_meta.from_prescription` 键下有几份计划」，应恒为 1（regen 例外，单独计数）。
- 处方改版（version+1）：新键 → 新草稿；旧版本那份「自动生成、没人改过、没批准」的草稿由生成 v+1 时**归档并写明原因**（建议 2：否则 v1 的草稿天天被每日巡检提醒批准，PM 还可能误批基于已被替代的处方的计划）。已批准的计划绝不动。

## 3. 回执与失败可见（必改 3、4）
- **回执不写 `flywheel_actions`**（必改 3）：那张表的定位是「每次已执行的动作一行」，已核至少三处读的时候不按类型过滤——执行看板「自动动作」（`execution/route.ts:480`）会把 `created` 显示成「状态未识别」、`failed` 显示成「待人工核对」；广告操作历史（`meta-ads/actions/route.ts:72`，带撤销按钮）会混进起草回执；后台首页 7 天动作计数（`dashboard/page.tsx:147`）会被灌水。
- **落点**：`prescriptions.generation_meta.plan_draft`（已核：`prescriptions` 有 `generation_meta jsonb` 列、`updated_at`）。字段：`{ request_id, attempt, status('created'|'skipped'|'already_exists'|'failed'), reason_code, reason_text, plan_id?, graph_reads, no_publish: true, authorization: 'none', triggered_by(触发人：邮箱或用户 id), actor_tier('internal'|'paid_client_member'), at }`。**为什么要记触发人和权限档**：处方批准只要求 `requirePaidClientAccess`，客户自己的员工也能点批准、也会触发自动生成草稿；将来出了「是谁让系统建的这份草稿」的疑问要能一行查到；这也是以后做方案 B 时「合并按钮只给内部账号」的数据基础；**只存最近一次**，历史靠 Inngest 运行记录。写入用「读 → 合并 → 带 `updated_at` 比对的更新」，冲突重读重写；**写前 grep 一遍确认没有任何地方把 `prescriptions.updated_at` 当内容指纹用**（2026-10-27 grep：生产代码无此用法，仅一个只读接口测试比对 `updated_at` 不变）。**无回执时的状态推断**：「草稿存在（按固定 id 查）」= 已生成。
- **页面规则（四态 + 一态兜底）**：
  1. 生成中 / 2. 已生成（链接 + 「系统根据处方第 N 版于某时自动起草，你改过/没改过」，建议 1）/ 3. 跳过（原因，区分「处方里没有广告打法」和「这份处方生成时系统还不会产出广告打法」，建议 4）/ 4. 失败（人话原因 + 「不影响这份处方已批准」+ **[重试]**）；
  5. **已批准 + 有广告打法 + 没有任何回执 + 没有草稿** → 「没有生成记录 + **[生成]**」（回执可能根本没写上，比如库也挂了，所以**不能显示『生成中』也不能空着**；超过 5 分钟才从『生成中』转入这一态）。上线前已批准的处方（含 CTS 的 89cb61eb）正落在这个状态；这个按钮同时就是 v0.6 的显式按钮，永远可用。
- **范围**：S4 只做「函数 + 一个状态块 + 一个『生成/重试』按钮」；执行看板抽屉（`InlinePrescriptionDrawer.tsx:173`）也能批准处方，给一条链接即可（建议 6）；不做两个界面、不做多余状态（建议 7，过度开发检查：现阶段带广告打法的处方基本只有 CTS 手工导入的几份，频率低）。

## 4. 草稿内容：留空与校验（魏征必改 5 + 子牙 M2/M5）
`parsePromoSpec` 硬要求 `daily_budget_cents` 正整数、`ad_account_id` ≥1 字符、受众编号与投放地区至少一个（`spec.ts:54/56/282`）。所以「留空 + 原因」与「草稿必须被 PUT 原样接受」不能同时成立；**写代码的人若为了过校验填默认值（最小预算、客户默认国家）就是「读不到悄悄填默认值」的事故形状**。逐字段写死：
- **账户或日预算读不到 → 这一步广告不进草稿**；原因写进 `generation_meta`（计划行的，**不入内容指纹**）；全部步骤都读不到 → 回执 `skipped` 并写原因。
- **禁止任何占位值**（预算、国家、受众、素材）。测试「所有依赖都读失败时，草稿里没有数字、没有国家」。
- **预算沿用第一刀口径并重申：读数失败只能让建议变小或留空，不能变大**（含 3195 审计 P1 修的那条：别的候选账户读不到也要让建议变小）。
- **「过同一个校验」要名副其实（子牙 M2）**：`PUT /promo`（`promo/route.ts:85-112`）在结构校验之外还会剔 `checks`/`gate_snapshot`、核目标属于这个客户、核广告账户属于这个客户、用 `checkAdsBudget` 判是否确定超上限。v0.7 只写了 `parsePromoSpec`，「草稿能被 PUT 原样接受」的单测也只证明结构合法。**把这一串检查抽成一个共享函数，PUT 和生成函数都调它**；另加反向测试：生成函数**永远不写** `checks`、`gate_snapshot`、`approval_receipt`、`promo_checks`。
- **草稿用哪份种子（子牙 M5，事实更正）**：`content.plan_seed` **不是**「自动生成后才存档」——主干上写处方时就在存（`prescription/generate/route.ts:427`、`prescriptions/manual/route.ts:125`、`refine/route.ts:202`）。而生成函数第一步是**现算**一份新种子；若处方页面板显示存档那份，会造出「页面 $25、草稿里 $50」，存档可能是几天前的数据，又落进「拿旧数据回答还能花多少」。**定**：草稿用现算的种子并带「按 X 点数据」+ 指纹；草稿生成后，面板改显示**草稿里那份**；**不回写已批准处方的 content**。
- **国家只能来自客户配置（子牙，平台化违规）**：v0.6 §3 受众兜底写过 `countries:['NZ']`，违反 `spec.ts:32`「不设任何默认国家」——国家必须来自客户配置，**不能写进共享代码**；读不到客户配置里的国家 → 这一步广告不进草稿（同「禁止占位值」）。
- 受众（建议 5，与 3190 对齐；子牙 M8）：spec 每步只有一个 `audience_ref` 字符串加排除列表，3190 的 `AdDraft` 用 `audienceIds` 数组（≤10）；CTS 新客/老客在 spec 里要**拆成两步**；**排除名单只能引用已有受众，不能新建/上传**（上传个人信息要 PM 本人授权，3190 已写明）。**受众依赖 3190**：`fetchCustomAudienceById` 只在 3190（OPEN 草稿）里，主干找不到。**S1 不做人数硬过滤**（与 v0.6 §3 一致；v0.7 写的「硬过滤」与之冲突，删除）：受众三态（读到/读到但不可用/读不到）+ 读不到留空；人数只在依据里显示。
- 素材：只取 `creative_pool` 里 `approved` 且推广期覆盖的；**取不到留空 + 原因，不许把「素材待批」当通过**。
