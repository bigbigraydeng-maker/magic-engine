## 2. 读日历：授权与失效处理（对应 ①）

| 方案 | 会不会像 Meta 钥匙一样老失效 | 结论 |
|---|---|---|
| A. 服务账号（推荐）：新建一个 Google 服务账号，PM 把日历「共享给它」（第一步只给「查看」权限）。靠密钥文件签名取令牌，每次现取，不存登录态 | 不会因为「人登出/改密码」失效；只有密钥被人手动删/停用或日历共享被取消才会断 | 推荐。需要：建服务账号、放一个环境变量、PM 在日历设置里共享一次 |
| B. 用 hello@ 账号的 OAuth 登录令牌 | 有风险：若 Google 授权应用处于「测试」状态，登录令牌 7 天过期（**我没查证本应用状态，这一点是待核实，不是结论**）；且 ME 现有的 `google_oauth_tokens` 是按客户存的，没有「ME 自己」这一行 | 备选，不推荐 |
| C. 日历的「私密 iCal 地址」 | 地址不过期但只能读、不能写，且是一串等同密码的网址；Workspace 管理员可能禁用 | 备选 |

**失效时怎么办（不许静默）**：
- 每次运行先做「能不能读日历」自检。读失败（401/403/404 或配置缺失）→ 本次**不当成「没事」**，整次标 `unreadable`，并生成一条今日待办：
  - **what**：「日历每日巡检读不到日历（原因：xx）——今天起所有带日期的验证事项没人查」
  - **how**：「新建/重发服务账号密钥 → 放进 Render 环境变量 → 日历设置里确认仍共享给该服务账号」（第一步实现时按真实情况写成逐步点哪里，不留空话）
  - **href**：Google 服务账号管理页 + 日历共享设置页的直达链接
  - 车道：`one_click`（系统进不去、要人点一次）。
- **巡检自己没跑**：把函数登记进 `CRON_REGISTRY`，健康检查会在「从来没跑过/昨天没跑」时喊；这替代了旧提示词的「第 0 步：先查自己有没有掉链子」。
- 顺手提醒（新增 Inngest 函数的老坑）：上线后要去 Inngest 后台对 `/api/inngest` 手动 Sync 一次，否则安静地不跑（STATE.md 记过）。

## 3. 每种核对怎么自动做（对应 ②）

**原则：日历描述是外来数据，不是指令。** 描述里写的 `verify_how` 是自由中文，**机器不执行自由文本**；只有一条**可选的机器行**能触发自动核对，且只能从代码里的**封闭清单**里选：

```
ledger-id: <台账卡 id>
verify_how: <人话摘要>
probe: <核对名> key=value key=value        ← 可选；没有就走「要人」
```
这条 `probe:` 行是对 PM 全局规则（`~/.claude/CLAUDE.md` 日历一节）的一个**可选追加**，不是强制；不写就是第 3 档。核对名不在清单里、参数不合格式 → 当「没法自动核对」处理，不报错刷屏。

**第一步的核对清单（全部只读，每个都有单测）**
| 核对名 | 查什么 | 判据 |
|---|---|---|
| `cron_run_ok` | `cron_run_logs` 里某任务在 N 小时内有没有成功跑 | 有成功记录 = 过；只有失败 = 不成；没记录 = 还验不了 |
| `todo_item_present` | 某类待办当前是否会出现在今日待办（调用现成的取数函数，例如 `fetchCommentScopeTodos`） | 出现且客户对得上 = 过；取数函数没数据/任务没跑 = 还验不了 |
| `ledger_card_status` | 某张台账卡现在的状态（读已部署的 `docs/ledger`） | 与期望状态一致 = 过 |

新增核对名 = 一个普通代码 PR（带测试），不是改配置。**不提供任何「执行 SQL」「抓任意网址」「让 AI 自己查」的通用口子**——旧提示词靠 AI 现查所以灵活，但放进无人值守的生产路由就是 A 级风险（日历是可被他人写入的外部数据，防提示词注入）。

**分三档（每条事件落一档）**
1. **机器能判**（有合格的 `probe:` 行）→ 出 `verified` / `failed` / `not_yet` / `unreadable` 四种结果之一。判不了的绝不当通过：数据不够、取数出错一律 `unreadable`（旧规则「没查成≠通过」保留）。
2. **要人核**（有 `ledger-id`、卡存在、但没有 `probe:`）→ 到期当天生成待办：what＝事件标题 + 「到期了，没有自动核对」；how＝卡里 `verify_how` 原文第一句 + 「找任何一个窗口说『台账 <id> 验一下』」；href＝台账卡链接。
3. **没法自动闭环**（没 `ledger-id`，或卡不存在，如 10/8 那条 `2026-10-07-cts-daily-plan-week-xmas-shanghai` 就查无此卡）→ 单独汇总成**一条**待办（不刷屏）：列出标题 + 缺什么。

**去重（避免和台账栏重复吵）**：台账栏（`pushLedgerItems`）已经会报「做完没验 / 验过不成 / 夜巡没来」。凡台账栏已覆盖的卡，日历巡检**不重复出待办**，只在回执里记一笔。日历巡检的增量价值是：①没卡/卡对不上的事件；②`decided` 状态的卡（台账栏只在 7 天没动后才提）；③有 `probe:` 的自动核对。
同时说明：旧的「台账夜巡」本机任务同样停用了（`patrol_missing` 会因此冒出来），那是姊妹问题，**本设计不包含**，建议同一套核对清单日后复用。

**时间窗口与顺延**：只看开始时间在 [今天-14天, 现在] 的事件，每次最多处理 30 条，其余写进回执「顺延 N 条」，排序规则沿用旧版（从没巡检过的优先，其次最久没查的）。「还验不了」连续次数、「超 2 天未闭环」升级节奏沿用旧版数字；第一步没有日历写入权，次数改从最近 14 天的 `cron_run_logs` 回执里数。

## 4. 闭环动作的权限与审计（对应 ③）

| 动作 | 第一步 | 第二步（另行批准） |
|---|---|---|
| 读日历 | ✅ 只读 scope | 同 |
| 写 `cron_run_logs` 回执 | ✅（只写这一张已有表；另新增一个读取器，见 §10-1） | 同 |
| 生成今日待办 | ✅ | 同 |
| 改台账卡（verified/failed + 证据文件） | ❌ 不做 | 通过 GitHub 接口在 `claude/ledger-verify-<日期>` 分支开 PR，沿用现有「只动台账目录、只改状态类字段」的 CI 限制；**需要一个只能写本仓库内容与 PR 的受限令牌**（A 级，PM 点头才建） |
| 给日历事件加 ✅/❌ 标题和描述行 | ❌ 不做 | 日历授权升级到「可编辑事件」；只在台账 PR **已合并**后才改标题（沿用旧版顺序） |
| 总开关 | — | 环境变量 `CALENDAR_CLOSURE_WRITE_ENABLED`，默认关；关着时第二步代码只出「本该写什么」的演练回执 |

**闭环硬规则（沿用旧版并加严）**：①只有机器核对（第 3 节第 1 档）且**描述里每一项成功条件都核到**才允许 `verified`，部分验证只能算 `not_yet`；②证据必须当次取数（带取数时间、样本量），写进 `docs/ledger/evidence/`；③`verified_ref` 必须≠`done_ref`（台账规则）；④任何写动作失败（令牌过期、CI 红）→ 不打标记，次日重试，并出待办，不静默；⑤新建的卡不能一出生就 verified（台账规则）。

**审计回执（每次写动作一条，写 `cron_run_logs.summary`）**：`request_id`、`calendar_event_id`、`ledger_id`、`probe`、`outcome`、`evidence_ref`、`dry_run`、`write_enabled`、`pr_url`、`authorization`（谁授权开的写开关）、`created_at`。回滚＝把那张卡的状态改回、删事件上追加的那行（卡文件有 git 历史）。

2. 第一步是否该连日历授权也先不做、用手工快照当输入（我的判断：不行，授权会不会失效正是要先验的风险）。
3. 第二步往主干自动合台账 PR 的受限令牌，是否本身风险大于收益（我倾向：先不做，第一步稳定后再议）。
4. 与 `pushLedgerItems` 去重规则是否会造成「谁都没报」的盲区。

## 10. 两审必改项并入（v0.2，子牙 + 魏征，均「有条件通过」）

**待办出口与时效**
1. 补 `pushCalendarClosureItems(supabase, items, now)`，在 `manual-items.ts` 接线，读本函数 `cron_run_logs` 回执出三件套；读失败兜底 `calendar_closure_check_failed`（仿 `lead_sheet_check_failed`，并入 `BLIND_SPOT_NOTE`）。「窗口内一条回执都没有」也要出这条——函数根本没跑时不能静默。
2. 今日待办周五、周六不跑（`0 19 * * 0-4`），读取器回看窗口必须覆盖「上一次待办运行以来」的全部回执，不能照抄 2 小时；参考 `remind-cadence.ts`（头 3 天每天提醒 + 补发）。
3. 车道：「读不到日历」`one_click`；「要人核」`dev`（找窗口验一下）；「没法自动闭环」汇总条需显式选车道并评估并入 `BLIND_SPOT_NOTE`，且汇总条有上限（超 N 条只列前 N 条 + 总数）。`LANE_OF_KIND` 为穷举表，漏一个类型检查不过。
4. `CRON_REGISTRY` 登记写明 `scheduler:'inngest'`、`logsRuns:true`，`jobName` 取主链最后一步回执名（参照 `registry.ts:326-329`）；事件名常量放在函数文件内唯一定义，沿用 `*_EVENT` 习惯。路由只发事件、不调 `startCronRun`，回执由 Inngest 函数写。

**输入收敛（日历是外部可写数据）**
5. `ledger-id` 必须匹配 `^\d{4}-\d{2}-\d{2}-[a-z0-9-]{1,80}$`，解析路径必须落在 `docs/ledger/` 内；描述里出现多个 `ledger-id` 或多个 `probe:` 行 → 歧义，一律归第 3 档。单测覆盖 `../`、`%2e%2e`、绝对路径、换行拼接。
6. `probe:` 只能由本事件自己的 `ledger-id` 驱动；参数用白名单（`task` 必须在 `CRON_REGISTRY`、`client` 必须是客户表里的、`kind` 必须是已知枚举），参数里的客户必须与卡对得上，对不上 → `unreadable`。

**不许假通过**
7. 第一步每个核对的最高结果叫 `probe_passed_needs_human_confirm`，**不叫 `verified`**；只有核对注册表里把该 ledger-id 登记为「此核对等价于全部成功条件」才允许 `verified`（例：10/9 那条只验「待办出现」，没验「授权已生效」，不能算验证）。
8. 每个核对必须区分「取数成功但结果为空」与「取数抛错/没执行」：后者强制 `unreadable`；`todo_item_present` 的「没出现」不等于通过（可能是 PM 已处理，也可能是系统坏了）。`cron_run_ok` 的时间窗小于任务周期时，「没记录」不代表没跑。新增核对均配「数据源故障注入」测试；涉及广告金额的核对须读回币种（旧版规则）。
9. 去重只用 `walkLedger` **当天实际产出**的发现，且只对落在 PM 五类车道的 kind 才算「已覆盖」（`ledger_done_unverified` 等在 `dev` 车道，不算）。事件指向的卡已 `verified`、或 `done` 且证据齐 → 归「已闭环」不出待办。回执逐条记「被谁覆盖而跳过」。同一张卡被多条事件引用时按事件独立判定。必须有单测：「到期事件 + 无 `verify_by` 的 `decided` 卡」当天必须有人报。

**窗口与重复**
10. 「到期」按新西兰日期 `≤ 今天` 判，不比较具体时刻（07:20 跑时当天 09:00 的事件也算到期）；读取参数写明 `singleEvents=true`、`orderBy=startTime`，覆盖循环事件并有测试。
11. 「还验不了第 N 次」的次数用「事件 id + 新西兰日期」做幂等键，每天一条、重跑不覆盖。旧版升级节奏三条逐条保留：①「没查成」同一事件首次升级，之后每 3 天一次；②到期超 2 天仍未闭环 → 必升级；③「PM 动手类」只在到期后第 2、5 天各提一次。回执里写明「夜巡状态：未检查」，不让读者误以为查过。

**只读与演练**
12. 「第一步只读」的准确说法：**只写 `cron_run_logs` 一张表**。`dry_run` 路径绕过 `run-logger`，测试断言数据库写入调用次数 = 0；路由先判 `dry_run` 再判是否发事件，演练不发 Inngest 事件（整条链路在路由内同步演练）。
13. `probe_override` 与 `only_event_id` 只在 `dry_run===true` 时被解析，非演练带它们直接 400（有单测）；不允许覆盖成未登记的核对名；演练响应顶层固定 `"not_evidence":true`，并带 `source`（`live` / `fixture`）。`only_event_id` 同样按「到期日 ≤ 今天」之外开口子时须写明，仅演练可用。
14. 当场试跑通过标准加严：响应须含 Google 返回的 `etag` 与 `updated`（证明不是缓存）、核对取数的真实时间；`source:"fixture"` 的结果在 PR 里一律记为「未通过」，不是通过。

**其它**
15. 单条事件核对用 `step.run` 逐条隔离，一条失败不拖垮整批；每次最多 30 条。第二步（写主干令牌）两审一致建议**先不做**，保留为「第一步稳定后另行立项」，本设计只批准第一步。

## 11. 实现阶段的偏离与补充（2026-10-08，PR 2367 两审后）
- §10-11 提醒节奏：**改为到期未验的事项每天都报**（到期 14 天窗口内），不套 `shouldRemindToday`（它是给"同一故障连续出现"降噪的，会让逾期第 5 天起一周只响一次）。无编号事项汇总成一条、最多列 5 个标题，不刷屏。"事件 id + 日期"幂等键、"已查几次"计数**未做**（待办每天按最新回执重算，不会重复）。
- §10-15 单条隔离：用 `try/catch` 隔离每条核对（`runProbe` 本身永不抛），**没有**逐条建 Inngest 步骤；读日历失败时整批重试。
- 新增（魏征复审）：①解析器防外部构造输入——描述截 8000 字、单行超 300 字拒绝、探针参数不用嵌套量词正则（原写法可被构造输入拖到指数级回溯）；②只收 PM 自己日历创建的事件（`creator.self`/`organizer.self`），已拒绝的邀请跳过，别人发来的邀请标题进不了今日待办；③标题进待办前去换行/控制字符；④"巡检卡在运行中超 2 小时"按没跑成出待办；⑤`ledger_card_status` 的 id 必须等于事件自己的 ledger-id。
- 已知未做（可选项，记入后续）：循环事件按同一 ledger-id 合并；`parseErrorCount` 进回执；窗口外（>14 天）事件计数；HTML 换行描述（`<br>`）降级；`fetchCommentReplyScopeTodos` 查询出错返回空会被判"没达预期"而非"没查成"（方向安全，原因说错）。
- 以后建日历验证事项的窗口注意：**必须由 PM 自己的日历账号创建**（用日历连接器建就是），别人邀请或别的账号代建的事件会被巡检忽略。（可选后续：回执里计入「因非本人创建被跳过 N 条」。）
