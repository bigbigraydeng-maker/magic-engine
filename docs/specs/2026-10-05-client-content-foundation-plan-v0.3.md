# 第一部分：给 PM 的一页纸（大白话）

**要做什么**：给每个客户建一套「客户资料库」，视频、Reels、社媒、每日计划、SEO、网站、广告、邮件、口碑都从它取事实，各自只决定「长什么样」；发出去之前有一道统一的检查，资料对不上就不发。

**现状（5 句话）**
1. 品牌气质（名字、语气、颜色）多数渠道读 Master Brief；产品和价格没有统一来源，**7 份并存、互相对不上**。
2. Reels 读的品牌色那一列根本不存在，拿不到品牌色。
3. 禁忌词有三套，各渠道各读各的。
4. 价格检查只在少数地方有；而且现有检查**认不出 "NZD 4,999"、"¥3999"、"3999元"** 这类写法（我实测过），CTS 的价格恰恰是 NZD。
5. 每日计划里「有没有对官网核实」代码里直接写成「未知」，等于没做。

**做完后的样子**
- 一份资料库，产品价格团期每条都带「来源网址、哪天核实的、什么时候过期」。
- 价格以官网为准，**但「团在不在售」由客户确认的事实盖章**（CTS 官网至今挂着已下架的团，吃过亏）。
- 各渠道发内容前过同一道检查：**文案里没出现价格、日期、团期、折扣，就放行；出现了就必须对得上资料库；对不上、资料空了、过期了，就不发**。

**谁来维护（分工表）**
| 事 | 谁做 | 怎么做 |
|---|---|---|
| 抓官网价格团期 | ME 自动 | 每天一次，只抓客户官网（域名白名单），抓不到先自动重抓 |
| 价格过期提醒 | ME 自动发待办 | 同一客户同一原因合并成 1 条，给 PM/执行人员，带「是什么 / 怎么办 / 链接」 |

|---|---|---|
| 价格对不上资料库 | 「CTS 这条 Reel 写了 NZ$4,999，资料库里该团是 NZ$5,199（4 天前核实），没发」 | 点链接选：改文案 / 更新资料库 |

**分步（每步一个 PR，前一步好了才开下一步）**

| 1 客户资料包（先只读对比，不切换） | 一张对比表：新旧禁忌词、生效版本，会多拦/少拦多少条，你看过再切 |

# 第二部分：技术方案

## 1. 三层
事实层（只读聚合）→ 派生层（各渠道适配器）→ 闸门层（对外那一步）。**不新建权威源**；产品/价格 v1 **不建新表**，实时读 Connector（官网 feed + 最近一份 `market_snapshots`，已有 `source_url / captured_at / content_hash / page_role` 与行业 profile 钩子）；政策类放 `client_knowledge_facts`（人工批准、客户双签），**两者并排返回、互不写入**。要持久化的需求等第 2 个客户出现再说，先开卡。

## 2. 分层判定（me-platform-tier-gate）
- `getClientFacts()`：L1 平台基础设施（整合既有能力，不是新支柱）。通用容器 `{label, value, unit, source, observed_at, expires_at, status}`，**不含团期/出发地字段**；`FirstPartyTour` 是 L2 旅游形状，作为旅游 profile 的 Connector 经注入进来，**不写进聚合器**。地产（listings）、建材（SPC/Hybrid）各有自己的 profile。换客户（CTS→Roman→建材）聚合器不改。
- 客户事实只作数据；清理 `keyword-relevance.ts:18` 写死的建材词（先出前后差异，会改变 Oztop 现有关键词）。

## 3. 分步
**第 0 步：补洞（同批，A 级，先于一切）**
- 内容生成接口登录与客户归属校验 → **修复窗口已开**（route-a/b/c）。
- **发布层兜底闸**：闸装进底层发出函数（`schedulePost`、`publishPagePhotoPost`、`publishToFacebook` 等），不是路由；闸通过凭证绑定「最终文案+素材哈希」，发布时重算，改动即失效；加「所有发出函数调用点必经闸」的测试，没有这条测试不叫完成。Reels 发布路由的 `caption` 覆盖与 `account_id` 归属问题，归**统一发布窗口**收口，本规划只依赖其结果。
- 现有价格识别补币种与数字归一：`NZD`、`NZ$`、`¥`、`元`、`纽币`、`k`；日期补 `15 March`、`3月15日`；白名单改**绑 tour_id**（不再只比数字）。先补测试，再接渠道。

**第 1 步：客户资料包（影子对比，A 级）**
- `getClientFacts()` **只返回结构化对象，不返回 prompt 文本**；由现有 `formatBriefForPrompt` 做唯一渲染；Reels 自写序列化器随之删除。
- **出错返回 `ok:false`，不返回空包**（现状 `getActiveBrief` 吞错，空禁忌词等于闸全开）；`select` 改字段白名单，测试断言 `competitive_notes_md`、`semrush_snapshot`、`source_file_urls`、`competitor_domains` 不出现在任何渠道；`brand_story_md`/`style_guide_md` 扫描竞品备注。
- 禁忌词**分三级** `{redline_phrases（硬扫）, topics（SEO/博客话题）, tone_words（只提示）}`，不拍扁；合并前**只读统计近 90 天已发/待发内容命中数**；旧列 `avoid_words` 先统计再定。先查生产 `excluded_topics` 列是否存在（发布代码已在 `select` 它）。
- 「生效 brief」取法先只读统计两列不一致的客户，再定规则。
- 新增读取用途 `public_content`：只收 `customer_ok`，敏感类仍要双签，**不绑 Messenger 开关**；代码里禁止内容渠道用 `internal_brief`。
- 无进程级缓存；缓存键带 `client_id`；入口断言 `clientId` 与调用方身份一致；「A、B 两客户互取」测试。
- 先切 Reels、social-plan；影子对比表给 PM 看后才切换。事件 `client_facts.pack.shadow_compared`。

**第 2 步：品牌包进资料库（与第 3 步可并行）**
先定 **logo 存放位置**（存储桶引用 + 哈希，Master Brief 没有 logo 列）；品牌色、Slogan、端卡统一取；下发给各出片引擎（含 Remotion）。logo 只经 `client_id` 取，找不到就失败，绝不借别的客户的。

**第 3 步：产品/价格/团期（先 CTS，A 级）**
- 返回 `offers[]`，每条 `{amount, currency, tour_id, valid_from/to, source_url, observed_at, expires_at, status ∈ ok | stale | fetch_failed | not_measured}`；**只有 `ok` 放行**；`first-party-tours.ts` 出错返回 `[]` 的行为要改（现在分不清「没产品」和「抓失败」）。
- 价格存「金额+币种」，日期存 ISO，名称限长，**自由文本不进提示词**；官网内容以结构化字段进，不原样进 prompt。
- **新写官网下载函数**：逐跳校验、每跳限域名、限 2MB、限超时、检查内容类型；抓取域名取 env 白名单/已核验域名，**不取客户可编辑的 `clients.domain`**；不复用只做探活的 `safe-remote-fetch.ts`。
- 「团是否在售」由知识库客户双签事实盖章，官网只作价格对照；对不上拒用并出人工任务。快照是**缓存不是来源**：只读、不可手改、带 `source_url + fetched_at`、对不上官网即失效；快照写入只走内部人员 `requireGlobalAdmin`（不用会放行演示管理员的 `guardAdmin`），留版本与操作人，**改价需另一人确认**。
- `verified_offer` / `verified_cta` / Creatomate `offers` 是**删字段，不是并存**：过渡期手填值只能等于快照、对不上拒收；**砍掉信号级 `evidence.verified_offer` 覆盖**（`evaluate.ts:404`）；`group_tours` 与 `cts-tour-price.ts` 列入迁移顺序，上线前用两把钥匙实测 `group_tours` 的 RLS，新表一律 `FOR ALL TO service_role`。
- `master_brief.products` 降级为产品线索引，**不再优先于官网 feed**（现 `service.ts:53` 相反）。
- 「当场试跑」：每日抓取任务当场 `dry_run` 一次，拿到真实输出才算完成。事件 `client_facts.snapshot.refreshed`（request_id、client_id、source_url、content_hash、status、observed_at）；过期/失败进今日待办三件套。

**第 4 步：统一事实闸**
- 4a：共用函数 + `dry_run`。**三态 `pass / block / needs_source`**；只对「文案里真出现价格、日期、团期、折扣」的声明核对，没声明放行；比对**结构化事实**（产品+金额+币种+日期），不是只比数字；价格进画面时，出片模板的值只能来自快照，成片抽帧 OCR/视觉复核（视频线）。事件 `client_facts.gate.verdict`（渠道、client_id、source record id、通过/拦截、命中声明、快照 id、是否 dry_run）。
- 4b：逐渠道开硬闸，**每个渠道上线先 `dry_run` 统计「会拦多少、拦得对不对」**。分级：视频、广告硬拦；社媒、每日计划拦下转人工待办；其余先只标记两周再定。
- 价格闸的最终放行**装在发出函数里**（第 0 步），4 步提供的是判定函数，不再造第二个发布闸。

**第 5 步：其余渠道**：SEO 写作、邮件、GBP、GEO，以及已在读知识库/红线的私信（Messenger）与语音；TikTok、小红书、portal 自助向导、人工 FDE 手写内容、第三方素材——**人工来源标「人工」并过同一道闸**。

## 4. 与进行中工作的衔接
- **Remotion v0.3**：改为 v0.4——只做**引擎接入**（外部成片入口砍掉）；品牌包与产品事实读本规划，事实检查调用第 4 步，不再自建「声明清单与官网抓取」；发布许可闸保持装在发出函数入口。排在本规划第 2、3 步之后。
- **视频工厂统一**：同上，依赖第 2、3 步。
- **统一发布窗口**：负责收口所有发布口子并取代 Publer；与第 0 步发布层兜底闸合并设计，不重复做。
- **Tour 管理模块 P1**：并入第 3 步。
