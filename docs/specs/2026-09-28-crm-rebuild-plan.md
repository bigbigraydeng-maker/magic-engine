# CRM 重整计划：先做标准 CRM 底座，再叠 AI 层（三个工作包）

**状态**：PM 2026-09-28 拍板方向，待新窗口认领
**来源**：PM 2026-09-28 凌晨原话（整理）——
> 「今天要联系」有点鸡肋，底座没做好就先把 AI 排序做出来了，太超前。先把客户列表的信息拉全，做成一个标准 CRM——该有的清单、功能、展示界面都有；再在这个基础上升级成 AI 版：不要那么多信息，只提炼精准的。散在外面的按钮合并进一个「CRM 管理」版面。只给 CTS 定制的功能（比如同行渠道）不该出现在 NAL 的后台——ME 后台要区分「基础功能」和「为客户定制的功能」。

**取代**：`docs/specs/2026-09-27-crm-contact-drawer-v0.md`（抽屉 v1 稿）。那份稿子的前提是「复用『今天要联系』页的抽屉去改『全部客人』」，而 PM 现在要删掉「今天要联系」、以「全部客人」为底座——方向反了，整份搁置。**但它的两轮复审查出的坑全部仍然成立**，已搬进下面 WP-B 的「已知坑」。

### 查证过的事实（2026-09-28，读代码得出，不是猜）

- 「同行工具」就是客户首页的 **「🤝 同行渠道」**卡片（`clients/[id]/page.tsx:718`），指向 `/agents`（旅行社同行送来的终端客户）。
- 那一排卡片里**只有行程单 / 楼盘 / 房子三张**按行业开关过滤（`page.tsx:677/685/693/711`，用 `industryFeatureFlags(client.industry)`）；**同行渠道没有任何过滤**。
- `/agents` 页面本身**也不检查**任何开关（对比 `/tailor-made/page.tsx:17` 有服务端检查 `clientHasIndustryFeature`）——所以只藏卡片不够，直接敲网址照样进得去。
- 侧边栏另有一处同类问题：PM 本人这种全权管理员走的是 `dashboard-shell.tsx:36` 的静态 `ADMIN_SECTIONS`，没有任何按客户过滤；只有受限演示账号（`buildScopedAdminSections`，`:184`）才按行业开关。ADMIN_SECTIONS 是跨客户的平台入口，本身不一定要过滤——**认领窗口先确认 PM 说的外漏是不是也发生在侧边栏，再决定要不要一起改**。

### 设计要先想清楚的一件事（认领窗口自己拍，拍完写进本节）

现有机制是**按行业推断**（旅游行业 → 有行程单）。PM 的说法是**按客户开通**（给 CTS 做的 → 只有 CTS 有）。两者不同：将来来第二家旅行社、没买同行渠道，按行业推断会给他开，按客户开通不会。建议：**客户开通为准，行业只当默认值**——这是 client configuration（L4）层的事，不是新能力线，不用走平台层级门的登记。

### 已知坑（抽屉 v1 稿两轮复审查出，每条已核实，新底座照样会踩）

1. 🔴 **换人时不重新挂载组件，会把 A 的笔记记到 B 头上（或 B 的笔记静默丢失）。** `ComposeNote.tsx:48` 的防重复键挂载时生成一次；`contact_touchpoints` 唯一键 `(client_id, source, source_ref)` 不含 contact_id；`crm/page.tsx:1780` 的 `<PersonDrawer>` 没有 `key`。任何「点下一个人」的交互，详情区外壳都要 `key={contactId}`。验收：连续给两个人各记一笔，两笔都在库里。
2. 🔴 **多人同时改同一个客人要防覆盖**（PM 2026-09-27 确认：跟进团队是一起翻同一份名单）。`advance-contact-stage.ts` 加**可选**参数 `expectedFromStage`，不传 = 老行为逐字不变（`nal-mark-won` 等老调用方不能受影响），要有这条回归测试。
3. **三条今日待办任务文案写死了「展开」「黄条下面」**（`manual-crm-items.ts:272/342`），版面一改就读不通，而且没有测试会报。同一个 PR 改掉，并加一条测试防漏改。
4. **缺一个「按 id 取单个客人」的接口**（`crm/contacts/[cid]/` 下没有裸 GET）。从待办链接直达某个人、或那个人不在当前页时要用到——是新增后端，不是「零后端改动」。
5. 同一套逻辑现在有两份：`ContactDetail.tsx` 和 `PersonDrawer.tsx` 各有一份 NAL 判断、各有一份 WhatsApp 回复框（发完一个刷新列表一个不刷）。底座只能留一份。
6. `viewerEmail` 是三条响应路径分别手写的，漏一条不会报错。放进响应的公共类型里、做成必填。
7. 预取下一个人的往来记录要能取消，否则快速连点会叠多份大请求、还可能显示错人的记录（参考 `all/page.tsx` 现有 `timelineReqRef` 防乱序写法）。
8. `contacts/route.ts` 的 `getPriority` 那行 `.order('id')` 只是稳定读取用、不影响展示顺序，**别跟 `getPaged` 的 `first_seen_at` 排序「统一」**——那是今晚刚修的随机排序 bug。
