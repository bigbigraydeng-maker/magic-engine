# 广告 ↔ 成片 关联行（ad_creative_links）补链设计 v0.1 · 只设计，未写代码 · 119 号 · 2026-10-21

> 来源：74 号指派（经 122 查库发现表几乎是空的）。三件事：①ME 内建广告路径建出广告那一刻写关联行；②手建广告用的「登记」受限入口；③现网存量回填方案（A 级、PM go，**不直接写库**）。
> 风险级：**A**（归因的真相源；回填会写生产库）。设计阶段需子牙+魏征复审。

## 0. 先说结论（读生产库与代码查出来的，改变了设计）

1. **现状**：`ad_creative_links` 全表 4 行，4 行全是 `unresolved`，只有 `winner_reel_sync` 一个调用点（`engine.ts:288`）；`boost_post_api` 在类型里登记了、`meta-ads/boost-post` 路由也存在，但**全仓没有调用 `linkAdToCreative`**。ME 自己的建广告路径 `ad-publisher.ts`（`publishDraftPaused`）没有登记路径、也没写。
2. **122 的硬约束在手建广告上永远满足不了**：约束是「`published_post_id`：广告创意的帖子 id 必须与工单 `published_ref.post_id` 精确命中」。我对 CTS 的 118 条工单只读核对：
   - A2 工单 `6149a614…`、B3 工单 `812221fd…` 的 `published_ref` 是**脸书主页上的 Reel 草稿**（`post_id = video_id = 1125525413247106 / 1629174608913506`，`video_state=DRAFT`）；
   - 而在广告里实际引用的，是 74 号上传到**广告账户视频库**的另一个视频对象（素材池里的 `28843889985273791`(A2)、`3626096160888481`(B3)，标题带工单 8 位前缀，如「CTS Natural China A2 15s price-suspense (6149a614) · 素材候选」），广告创意再把它转成主页帖子时 Meta 又生成**衍生副本**（`2052942792039743` 等，别名已登记）；
   - 我把素材池 5 个 id、衍生视频 id 一共 10 个，在 118 条工单的 `published_ref`/`output` 里全文搜索：**0 命中**。
   - 所以「一条内容」在系统里有三个互不相同的 id：①工单发布的主页 Reel 草稿 ②广告库里的素材视频（素材池 ref）③广告创意里的衍生视频/帖子（别名）。**帖子 id 精确命中永远对不上**。
3. **能用来做「内容绑定」的是素材池这条链**（PR 2964/2967 已有的 `ref` + `alias_refs`）：广告创意视频 id ∈ {ref}∪alias_refs → 素材池条目 → 条目对应的工单。缺的只有最后一跳：**素材池条目 → 工单** 现在没有任何字段、也没有写入方（标题里的 8 位前缀是人填的，不是系统记录）。

## 1. 绑定模型（不新增表）

```
广告(ad_id) ──创意里的 video_id / 帖子id──► 素材池条目(ref+alias_refs) ──work_order_ref──► 工单(content_work_orders.id)
                │                                         ▲
                └── 路1：帖子 id ∈ 已发布工单的 published_ref.post_id（现有 decideCreativeLink）
```

- **素材池条目新增可选字段 `work_order_ref`**（工单 id）。解析器保留它；**只能由受限入口写**（和 `promo_window` 同一套：内部员工、记录谁何时设、通用保存接口不接受也不抹掉）。
- `ad_creative_links.link_method` 新增取值 `asset_binding`（素材库绑定）：广告的视频经素材池条目、再经 `work_order_ref` 到工单。**`creative_ref` 仍是工单 id，`creative_source` 仍是 `content_work_order`**，下游归因不用改。
- 判定顺序（纯函数 `decideCreativeLink` 扩展，仍然「绝不猜」）：
  1. 路 1（现有）：帖子 id 精确命中唯一一条已发布工单 → `published_post_id`；
  2. 路 2（新）：创意的视频 id 精确命中唯一一个素材池条目（ref 或别名），该条目有 `work_order_ref` 且通过核验 → `asset_binding`；
  3. 都不行 → `unresolved` + 具体原因（没有视频 id / 视频不在素材池 / 条目没绑工单 / 命中多条）。
  - 两路结论冲突（命中不同工单）→ `unresolved`（冲突原因写明），不择一。

## 2. 「素材池条目 → 工单」怎么写入才不是「谁说了算」

`POST /api/clients/[id]/ad-strategy-config/creative-pool/work-order-ref`（仅内部员工，body 只收 `{ ref, work_order_id }`，写入人由会话派生）。服务端**读 Meta 与库核验后才写**，核验不过 → 422 不写：
- 该工单属于同一客户、状态为 `published` 或 `in_review/approved` 之后（不接 `failed/archived`）；
- 读 Meta 的广告账户视频库：该 `ref` 的视频存在、`ready`、标题**包含工单 id 的前 8 位**、创建时间晚于工单创建时间；
- 同一工单不得被两个不同素材池条目绑定（防止一条片子对应多个素材视频时随便挑一个；确有多个版本的，用别名而不是绑多条）；
- 条目已绑定别的工单 → 409（要改必须先走审计的「解绑」，本期不做，写进后续）。
- 局限（写明）：标题前缀仍是人写的字符串。这比「人直接说是哪条」多了两道客观核对（Meta 读到的视频确实存在且带该前缀、时间顺序），但**不是内容哈希**。要做到内容哈希（下载素材视频与工单 `final.mp4` 比对）成本大，列入后续，由子牙魏征判断是否必须。

## 3. 交付一：ME 内建广告路径建出广告那一刻写关联行

- `AdCreationPath` 新增 `me_ad_launch`（`ad-publisher.ts` 的 `publishDraftPaused`，草稿建成暂停广告，**创意里本来就有 `videoId`**）；`boost_post_api`（已登记、没接线）接上调用。按该文件自己的规矩：新增路径同时在 `AD_CREATION_PATHS` 登记（类型穷举逼出遗漏）。
- 写入点：广告建出来之后立刻 `linkAdToCreative`（永不抛异常，失败吞掉 + 记日志；与现有一致）。输入除原来的帖子 id，新增创意视频 id 列表，调用 §1 的判定。
- 草稿阶段的广告是暂停状态，仍然写关联行（归因要的是「这条广告是哪条片」，与是否在投无关）。

## 4. 交付二：手建广告的「登记」受限入口

`POST /api/clients/[id]/ad-creative-links/register`（仅内部员工）。**请求体只收 `{ ad_id }`**——不收工单号、不收素材 id：
1. 服务端读 Meta：该广告所属账户必须在该客户登记的账户里（复用 `campaign-ownership` 判据）；取创意 id、`video_id`（可能多个）、`effective_object_story_id`；
2. 按 §1 的判定顺序算出结果，**写入 `ad_creative_links`（幂等：同 `(client_id, platform, ad_id)` 只更新；已 resolved 的行不会被 unresolved 覆盖，只会在出现更强证据时更新）**；
3. 响应把判定和证据（用了哪一路、命中哪个素材池条目/工单）回给调用者；`unresolved` 也写行并说明缺什么（比如「视频 X 不在素材池」「条目 Y 没绑工单」）。
- 这样 74 号手建广告后只需调一次入口，**绑定由系统读 Meta + 核验素材池得出，不由人填**。
- 调用方：这是个 API 路由，需要内部员工会话；74 号窗口没有浏览器会话时由我代调（沿用「受限入口」那次的做法），不为此新建机器身份。

## 5. 交付三：现网存量回填方案（只出方案，不写库）

**对象**：客户登记账户里现在在投的广告（以 Meta 实时读为准，不用滞后的快照）。我 10-21 对广告级快照的只读统计：CTS 最新轮 ACTIVE 18 条（官方户 4、个人号 14；个人号已欠款停用，不会投放）。74 号/122 报的「21 条」与此口径不同（时间窗），回填前以实时读取的清单为准，并把清单贴给 PM。
**步骤**：
1. **只读试跑（dry-run）**：脚本对每条广告调 §4 同一个判定函数（不写库），输出一张表：广告 id、账户、创意视频 id/帖子 id、命中的素材池条目、将写入的 `creative_ref`/`link_method`，或 `unresolved` 原因。附汇总：可解析几条、不可解析几条及原因分布。
2. **先补素材池绑定（单独一步、各自核验）**：官方户 4 条在投广告用的视频，别名已登记到 A2/B3 两个条目（`2052942792039743`/`2324048611775779` → A2，`1126238526529263`/`1110954791640892` → B3）。要让它们解析成功，需要对两个条目各调一次 §2 的入口：A2 → 工单 `6149a614…`，B3 → 工单 `812221fd…`（两条工单状态均为 `published`，标题前缀与之吻合）。SH5 的素材视频 `2126654807950354`（工单 `164a29c1…`，目前 `in_review`）等其通过质检再绑。
3. **预期结果（以 10-21 读到的为准，实际以 dry-run 为准）**：官方户 4 条 → 全部可解析到工单（`asset_binding`）；个人号 14 条 → 绝大多数是 9 月的老广告，创意视频不在素材池、也不对应已发布工单 → `unresolved`（如实留白，不回填猜测）；现有 4 行（`winner_reel_sync` 的 unresolved）保持原样，除非新证据能给出确定结果。
4. **写库**：PM 点头（A 级，每次钉 SHA/清单）后才执行；只写 dry-run 表里「可解析」的行；`created_by='backfill_2026_10'`；用同一个幂等写入；**绝不覆盖已 resolved 的行，不写任何猜出来的行**。
5. **回读核对**：写完后按广告 id 回读，行数与 dry-run 一致；贴给 PM。
6. 回滚：因为只新增/升级行且 `created_by` 可区分，回滚 = 按 `created_by='backfill_2026_10'` 删除（需 PM 授权）。

## 6. 与 122 的对齐点（要回 122）

- 122 硬约束「observed_live 只认 `published_post_id`」对手建广告**永远无法满足**（见 §0.2）。建议改为：认「内容绑定」类 link_method —— `published_post_id` 与 `asset_binding` 两种（都是系统读 Meta/库核验得出，不是人填工单号）；`unresolved` 一律不放行。如果 122 坚持只认 `published_post_id`，则手建广告永远不会 observed_live，只有 ME 自己发布并建广告（winner_reel_sync / 将来的 me_ad_launch 且创意取自 ME 发布的帖子）的才行。
- `created_at` 晚于请求这一条：回填的行 `created_at` 是回填时间，需要 122 说明对「先有广告后有请求」的情形怎么处理（建议比较广告的 `created_time` 而不是关联行的 `created_at`）。
