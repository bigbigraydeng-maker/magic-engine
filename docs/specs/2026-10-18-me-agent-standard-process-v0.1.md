## 0. 给 PM 的一页（大白话）

**以后来一个 Agent 需求，固定走五关，每关有「过关凭证」，没有凭证不进下一关：**

| 关 | 一句话 | 过关凭证 | 你要做什么 |
|---|---|---|---|
| **第 1 关 立项卡** | 先回答 7 个问题，尤其「它吃什么数据、现在生产里有几条」 | 一张填满的立项卡 | **只拍一件事：做不做、排第几** |
| **第 2 关 规则先行** | 先把「什么情况做什么、谁批」写成规则表，再写代码 | 一张规则表（平台 / 行业 / 客户三层） | 规则里凡是「花钱、发布」的，**由你定档** |
| **第 3 关 接零件** | 按清单接现成的零件，不许自己另造 | 零件对照表 | 不用管 |
| **第 4 关 当场试跑** | 用演示客户真跑一遍，两个审查角色审过 | 试跑回执 + 审查结论 | 不用管 |
| **第 5 关 上线体检** | 每个 Agent 有一张体检卡：跑没跑、产出几条、判不了占多少、效果验了没 | 每周自动体检 | **只看红灯** |

**你问的「遇到问题能不能优化」，答案在第 5 关**：每个 Agent 跑一次必须留一条回执；回执里写不出「做了什么、结果怎样」的，自动变成一张记录卡，按期被人看到，不靠谁记得。连续 30 天零产出的，自动提议撤掉。

**你只需要做两种决定**：①第 1 关「做不做、排第几」；②第 2 关里「花钱 / 发布」类规则归哪一档。其余全部由开发窗口自己按流程走。

**为什么这次要定这个流程**：这个会话里编排层走了四轮审查才发现「它要调度的东西今天一条都不存在」。如果第 1 关先问了「生产里有几条」，第一天就会停下来。

## 1. 先把「Agent」分清楚——现在凌乱的根子

调研发现，`docs/agents/` 里的「Agent」其实是三种完全不同的东西，混在一张表里（四份文档对数量有四种说法）。**以后一律按三类登记，不许混：**

| 类 | 定义 | 例子（调研快照） | 本流程管不管 |
|---|---|---|---|
| **A 类 · 运行时 Agent** | 产品里真在跑的代码：会被叫醒、读数据、出判断或动手 | 诸葛亮（`src/lib/zhuge/`）、张骞（`src/lib/zhangqian/`）、华佗（`src/lib/huatuo/`）、鲁班（`src/lib/luban/`）、马良的出片检查（`src/lib/maliang/render-check.ts`） | **管，全部五关** |
| **B 类 · 引擎人格** | 一组规则引擎被起了人名，方便称呼；不一定调大模型 | 卫青（`src/lib/ads-strategy/`，纯规则、零个文件调模型）、孔子（SEO 巡检）、孟子（AI 可见度）、苏东坡（社媒） | **管，按 A 类走**（它们会被叫醒、会动手，风险一样） |
| **C 类 · 审查人设** | 开发窗口里用的审查角色，**产品里没有代码** | 子牙、魏征、板桥、狄仁杰 | **不管**（它们属于开发流程，登记在 §6 名册的单独一栏，不叫「待建」） |

> 例：`00-architecture.md` 现在把子牙、魏征标成「待建」。按本分类，它们是 C 类，**本来就不该有产品代码**，「待建」这个状态是错位。

**命名规矩**（以后新增一律遵守）：
- 一个名字只指一样东西。现在「孔明」（诸葛亮的字）被拿去指广告预检那一步（`kernel/autonomy-envelope.ts:6` 注释）——这类借用以后不许。
- 名字登记在 §6 名册，**名册是唯一权威**；手册、CLAUDE.md、代码注释里的名字以名册为准。

### 第 2 关 · 规则先行（Playbook first）

**凭证**：一张规则表。PM 10-10 拍板「所有支柱 agent 一律平台—行业—客户三层，先写 playbook 和规则，再排代码」（出处 `docs/sops/2026-10-11-seo-agent-playbook-and-rules-v1.0.md:4`）——本关就是把这条变成每个 Agent 的必经关。

**规则格式直接沿用广告手册**（`docs/sops/2026-10-10-ads-agent-playbook-and-rules-v1.0.md` §2.1，已是范本，不另起）：

`编号` ｜ **条件 → 动作** ｜ **谁做（档 1–4）** ｜ **证据来源（哪张表 / 哪个口径）** ｜ **样本门槛** ｜ **代码（已有 = 路径；缺 = 「尚无代码」；写好没人调 = 「零调用方」）**

- 每个数字带来源和样本量。没有证据写「待验证」，**不许编阈值**。

**授权四档直接沿用广告手册 §2.2**，推广到所有支柱：

| 档 | 意思 | 判档原则（拿不准一律往高档放） |
|---|---|---|
| 1 | 系统自动：只读、只记录、只出建议、只发待办 | 只读 → 档 1 |
| 2 | 出建议，任一授权的人点头才执行 | 只让花费变少 / 只会收、可撤回 → 档 2 |
| 3 | **必须 PM 本人**在执行这个动作的对话里点名说才算 | 花新钱、对外发布、会重置学习期 → 档 3 起 |
| 4 | 绝不自动，连 PM 点头也不开自动通道 | 见各支柱红线 |

**三层放哪**（不新造位置，按现状归位）：

| 层 | 放什么 | 放在哪（现成） |
|---|---|---|
| 平台层 | 换客户、换行业都成立的规则 | 支柱手册的「通用」部分 + 代码里的纯函数规则（`src/lib/<域>/`） |
| 行业层 | 只对一个行业成立的权重、阈值、模板 | 代码：`src/lib/ads-strategy/playbooks/`（5 个行业文件，已有）；文档：支柱手册的行业版 |

### 第 3 关 · 接零件（Reuse）

**凭证**：一张「零件对照表」——每个零件写「接的是哪个现成件 + 文件路径」，或「不需要，因为…」。**不许出现「新建一套 xxx 框架」**（119 号派工单已写明「不新建第二套工作流框架」）。

零件划分沿用 9 月自治计划的「五个零件 + 一个通道」（`docs/specs/2026-09-24-agent-autonomy-operating-plan-v1.md` §2，我已核对原文），每个零件对应的现成件：

| 零件 | 人话 | 必须接的现成件 | 关键约束（每条都是查实的坑） |
|---|---|---|---|
| **闹钟** | 自己醒 | 定时型：`src/app/api/cron/*` + `render.yaml`，**或** Inngest 定时；**都要登记进** `src/lib/cron/registry.ts` 的 `CRON_REGISTRY`（`:104`）；故意不排班的写进 `UNSCHEDULED_CRON_ROUTES`（`:412`）。事件型：Inngest，注册进 `src/lib/inngest/functions/index.ts` 的 `cloudFunctions` | 事件只当叫醒铃，payload 只带 `client_id`，消费者回库读当前值（`ads-events.ts:1-25`）；发送必须带幂等 id（`workflows/inngest-event.ts`）；`concurrency: { limit: 1, key: client_id }`；依赖在 handler 内创建；`step.sleep` 不许 `setTimeout`（PITFALLS F10）；**新函数上线后要去后台对 `/api/inngest` 手动 Sync 一次**（`docs/STATE.md:174`） |
| **眼睛** | 醒来能读到数据，且知道全不全 | 各域数据脊柱表（如 `ad_daily_insights`）+ 完整性判定（如 `ads_growth_states`） | 读失败 ≠ 没有；截断 ≠ 完整；**判不了必须标「判不了」并写原因码**，不许当 0 或当 false |
| **脑子** | 写死的判断规则 | 纯函数，放 `src/lib/<域>/`；需要大模型判断时**只走** `src/lib/anthropic/client.ts`（`callClaudeChat` 等，模型常量 `MODEL_SONNET` / `MODEL_HAIKU` 在 `:13-14`）或 `src/lib/ai/openai-client.ts` | **不许在业务文件里 `new Anthropic(` / `new OpenAI(`**（调研发现已有 7 + 3 个文件违反）；不许写死模型名字符串；prompt 放代码里的 `prompts.ts`，并在 `docs/agents/prompt-library/` 登记副本 |
| **手 + 笼子** | 能碰外部系统，但只在授权范围内 | **会花钱 / 发布的 Agent 必须五样都接**：①`kernel/types.ts` 的 ActionKey 枚举 + `registry*.ts` 的 `ActionDefinition`；②`src/lib/capabilities/<域>/` 的能力实现（含撤回函数）；③`src/lib/action-submission/` 的提交函数；④客户策略表 `client_automation_policies` 的一行；⑤批准入口（`human_only` 的动作要自建「批准 + 执行」入口并登记 `kernel/dedicated-approval-entries.ts`） | 对外写只许在 `capabilities/` 里（`boundaries.ts` 的 `PROVIDER_WRITE_MODULES`）；推进函数只许在白名单目录调（`KERNEL_RUNNER_ALLOWED_CALLER_DIRS`）；这些由 `kernel/__tests__/architecture.test.ts` 钉死。**通用审批页只签不执行**（`kernel-approval/service.ts`），所以档 2/3 的动作若没有专属入口，批了也不会动。**只读 / 档 1 的 Agent 一样都不接** |
| **记性** | 做完过几天回看效果 | 动作记 `flywheel_actions`；效果回写 `flywheel_outcomes`（`attribution/job.ts`）；学习进 `src/lib/memory/`（客户私有四张表 + `global_learned_lessons` 的 global / channel / industry 三层，共享层唯一写入口 `memory/write-lesson.ts`） | 验证四态不混用：pass / fail / pending / not_measured（范本 `seo-weekly-list/verify.ts`）；「没测到」不是「零」 |
| **（通道）** | 需要人动手的事，写成三件套 | `src/lib/pm-todo/` 写一个 `push<X>Items`，产出 `ManualItem{kind, what, how, href}`（`manual-item-types.ts:331-347`，href 必须是绝对网址）；在 `five-kinds.ts` 的 `LANE_OF_KIND` 给新 kind 分车道 | **车道决定 PM 看不看得到**（已核：decide / one_click / client_side / review / truth 进 PM 视野；dev 进开发欠账页；weekly 进周报）。**`how` 写「需要你去点」的，不许放 dev 车道**（调研发现已有这种错位）；检查自己挂了要用 `BLIND_SPOT_NOTE` 留一句「今天没查成」，不许只 `console.warn` |

**本关的两条结构性规定**：
1. **「只看不动」的阶段，代码里就不要有「动」那一行**（不靠开关拦）。用架构测试钉死「这个模块及其依赖不 import Kernel 推进符号」。本会话两轮审查的共同结论：开关是运行时的，靠开关拦的「演练」，哪天为别的原因翻开关就瞬间变成真动手。
2. **会动手的 Agent，必须自己守客户的总开关和演练开关**。已核：`autopilot_enabled` / `autopilot_dry_run` 只有 `ads-d3-auto-pause.ts` 一处在读，**Kernel 本身不读**。守法：复用 `loadAdStrategyConfigWithSource`（读失败与无配置行都会 fail-closed），**读和提交在同一个 step 里**。

### 第 5 关 · 上线体检与改进（Operate & improve）

**凭证**：名册（§6）里这个 Agent 的「体检」一栏有数，且每周自动刷新。

**体检四问**（每个 A / B 类 Agent 每周自动回答一次）：

| 问 | 从哪读（现成） | 红灯条件 |
|---|---|---|
| 跑没跑？ | 定时型：`src/lib/cron/health.ts` 的 `judgeJob`（blind / never_ran / overdue / stuck / silent_success）；事件型：**现在没有通用检测**（见 §5 缺口 1） | 该跑没跑 |
| 产出几条？ | 回执（§4）里的 `produced` 计数 | 连续 N 天为 0 |
| 判不了占多少？ | 回执里的 `undeterminable` 计数 + 原因码分布 | 判不了占比持续过半 → 缺的是数据，不是规则 |
| 效果验了没？ | `flywheel_outcomes` 的四态 | 到期未验 / 一直 not_measured |

**改进怎么发生（回答 PM「遇到问题能否优化」）**：
1. **出问题 → 自动变卡**：体检红灯自动生成台账卡（沿用 `docs/ledger/` + 现成的「决定了没做 / 做了没验」判定，`src/lib/ledger/walk.ts`），不靠谁记得。
2. **卡分两种去向**：数据 / 接线问题 → 开发窗口修（dev 车道）；规则不对（阈值、档位） → **回第 2 关改规则表**，不在代码里偷改。
3. **规则改动留痕**：规则表每条带编号，改动在规则表里写「旧值 → 新值 + 证据 + 日期」，这就是 Tune 段的落地（IMPACT 的 T：必须改变下一次决策才算学习）。
4. **退役**：连续 30 天零产出且无人认领 → 自动提议退役（**退不退由 PM 定**）；退役的在名册标「已撤」，代码按 Git 规矩不删分支、只停调度。

## 4. 回执最小契约（调研发现的最大空白，先定在文档里，不写代码）

**现状**：仓库有 7 张以上「每跑一次落一行」的回执表（`ads_autonomy_sync_receipts`、`youtube_publish_receipts`、`social_post_measurement_receipts`、`gsc_page_fetch_receipts`、`daily_plan_auto_publish_attempts`、`flywheel_actions`、`action_runs`），**我已核：全仓没有一个共享的回执类型**，每个函数各写一套。这让第 5 关的体检没法统一读。

**规定（只定字段，不建新表）**：今后新 Agent 的每一次运行，回执里**至少**要有：

| 字段 | 意思 | 为什么必须 |
|---|---|---|
| `agent` | 名册里的名字 | 体检按它汇总 |
| `client_id` | 哪个客户 | 隔离与汇总 |
| `run_key` | 幂等键（同一次运行重跑不重复） | 防重复动作 |
| `trigger` | 定时 / 事件 / 人按 | 区分「谁叫醒的」 |
| `inputs_complete` | 输入全 / 不全 / 读失败 | 「眼睛」那关 |
| `produced` | 本次产出几条（建议 / 动作 / 待办） | 体检「产出几条」 |
| `undeterminable` + `reasons` | 判不了几条、原因码 | 体检「判不了占多少」 |
| `side_effects` | 对外动作清单 + 授权凭据（无则空） | 审计 |
| `cost_usd` | 本次大模型 / 外部接口花费 | 现在**没有统一成本账本**，至少回执里有 |
| `status` | ok / partial / skipped(原因) / failed | 失败邮件与待办 |
| `created_at` | 时间 | — |

**落点规定（不新建表）**：
- **定时型、只读的 Agent**：写进现成的 `cron_run_logs.summary`（经 `src/lib/cron/run-logger.ts` 的 `startCronRun` / `finish`）。⚠️ 失败计数的键名要含 `fail` / `error` / `skip`，否则每日失败邮件读不到（`daily-cron-digest` 只挑这类键，调研报告 `digest-cells.ts:91`，未核）。⚠️ `cron_run_logs` 180 天后硬删，**需要长期证据的不能只放这里**。
- **会动手的 Agent**：动作本身已有 `action_runs`（Kernel 自带状态机）；运行回执另放该域现成回执表，没有就**在立项卡里提出、由 PM 批准**才新建（「新表一律先问 PM」，闭环骨架卡 10-18 原话）。
- **重跑首次为准**：回执用「插入，冲突不覆盖」，重跑只另记 `already_ran`。调研已发现覆盖式写法会让回执只剩最后一次（记忆 `feedback-receipt-overwritten-shows-last-attempt-not-first`）。

## 7. 手册模板（`docs/agents/<编号>-<名字>.md`）

现有手册格式各异。以后新写或重写一律用这几节，**不多不少**：

1. **一句话**：它负责哪个决定或动作（= 立项卡第 1 问）
2. **类与名册行**：A / B / C 类，IMPACT 段，支柱
3. **叫醒**：定时 / 事件 / 人按；登记在哪（`CRON_REGISTRY` 或 Inngest 事件名）
4. **吃什么**：数据表 + 完整性判定 + 「判不了」时怎么办
5. **规则表**：链接到第 2 关的规则表（不在手册里重抄）
6. **能动手的范围**：ActionKey 清单 + 每个的档位；不能动手的写「只读，档 1」
7. **留什么回执**：落点 + §4 字段
8. **怎么停**：开关在哪、谁能关
9. **体检**：四问各从哪读
10. **记忆**：写哪一层（客户私有 / 行业 / 全局），谁有权写
