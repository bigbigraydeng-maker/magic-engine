# 电话接进 CRM（3CX）

**状态**：判断层已完成并上线；取数层等对方开分机
**DAPE**：E 执行（回流）· **支柱**：口碑 / 广告归因（电话是 CTS 最主要的成交渠道）
**轨**：FDE

## 为什么要做

CTS 的生意大部分在电话上成交，而电话现在**在系统里完全不存在**：

- 客人打进来没人接 —— 这是「有人想订、我们错过了」的直接证据，今天没有任何地方记录
- 销售打出去聊了什么 —— 只在他自己脑子里
- 广告 / SEO 带来的电话 —— 归因链在响铃那一刻断掉，投放效果被系统性低估

## 架构：取数 / 判断分成两半

跟邮件那条线同一个分法（`src/lib/microsoft/mail-graph.ts` ↔ `mail-ingest.ts`）：

| 层 | 文件 | 职责 | 依赖 3CX 吗 |
|---|---|---|---|
| 判断 | `src/lib/threecx/call-plan.ts` | 一通电话在 CRM 里意味着什么 | **不依赖** |
| 取数 | 待建 `src/lib/threecx/landing.ts` | 从落地库读新行，翻译成 `CallRecord` | 依赖 |
| 落库 | 待建 `src/lib/threecx/call-ingest.ts` | 认人、写对话、写触点 | 间接 |
| 调度 | 待建 `/api/cron/call-sync` + `render.yaml` | 每 15 分钟跑一次 | 间接 |

**这样分的理由**：判断错了会安静地毁掉销售的名单，所以判断必须能被单测一条条钉住、
不能跟网络调用绑在一起。而且判断层不依赖对方怎么给数据，对方那边还没开通也照样能先做完、
先审完 —— 事实上就是这么做的。

**2026-08-05 这个分法当场兑现了一次。** 原计划的取数层是「调 3CX 的 REST 接口读通话记录」，
结果对方明确答复：**那些 endpoint 官方不提供、没有文档、不保证长期可用，不建议用在生产环境**。
整个取数层作废重来 —— 而**判断层一行没改**，因为它从来只认 `CallRecord`，不认数据从哪来。

## 判断层的六条（已实现，`call-plan.ts`）

| # | 判断 | 在防什么 |
|---|---|---|
| ① | 内部通话整条丢 | 同事互打分机变成客人 —— 客户 8/4 刚在邮件那边反馈过一次 |
| ② | 号码认不出来就丢，绝不猜 | 存错号 → 将来销售照着它打给陌生人 |
| ③ | 未接来电必须建人 | 「有人想订而我们错过了」，等同于邮件的「客人自己开过口」 |
| ④ | 纯外呼不建人 | 打给供应商 / 同行 / 打错号，不配变成一张「今天该联系谁」的卡 |
| ⑤ | 没接通 / 秒挂的外呼不算「跟过」 | 一片灰卡，而那些人一个电话都没接到（`automated-touch.ts` 踩过两次的不对称） |
| ⑥ | 一通电话只算一次，哪怕转接过 | 逐段记 → 一通电话在时间线上变成三次联系，时长还被重复计算 |

录音**只存编号，绝不存能直接打开的链接** —— 那是客人的通话内容，链接落库等于把它
复制到一个没人管权限的地方。要听的时候拿编号带凭证去换。

## 取数怎么做（2026-08-05 改定：Data Connector 推送，不是我们去拉）

### 对方给的方案

3CX 官方支持的对接方式叫 **Data Connector**：**我们提供一个数据库**（支持
MySQL / PostgreSQL / SQL Server / BigQuery），把地址、账号、密码给他们，
3CX **最短每 15 分钟**把通话记录 + 录音文件的下载链接推进来。

对方对六个问题的答复（2026-08-05）：

| 问 | 答 |
|---|---|
| 这个功能要另外买吗 | 包含在 $30/分机里 |
| 账号密码谁开 | **使用方提供** —— 我们开库、给凭证 |
| 有没有对方号码/方向/时长/接没接/谁接的 | 都有 |
| 没人接的来电有吗 | **有**（判断③要的就是这个） |
| 录音默认开吗、存多久、能下载吗 | 默认开，存 **3 个月**，推送数据里带下载链接 |
| 能主动通知吗 | 能，最短每 15 分钟推一次 |

### 方向反过来带来的第一件事：**绝不能把生产库的凭证给出去**

原方案是我们拿他们的凭证去读；现在是**他们拿我们的凭证来写**。这一颠倒，
风险的性质完全变了 —— 凭证一旦泄露或被滥用，代价不是「读不到通话记录」，
是**我们所有客户的数据**。

所以落地库必须是一个**单独的、除了接这一件事什么都没有的数据库**：

- 3CX 那个账号只能往落地库写，**碰不到主库一个字节**
- 落地库里没有任何别的客户数据 —— 就算整个被拿走，丢的也只是通话记录本身
- 我们的 cron 从落地库读出来，跑判断层，写进主库

（同一个实例上开个只能写一张表的角色理论上也行，但那是「配置对了才安全」；
单独一个库是「配置错了也还安全」。这类事只选后者。）

### 一个客户一张表 / 一个账号

3CX 是从**每个客户自己的话机系统**推过来的，它不知道我们的客户编号。
所以每个客户给一套独立的落地表 + 独立的库账号，映射关系存在我们这边。
混在一张表里靠某个字段区分 = 一旦对方配错，A 客户的通话记录会落进 B 客户的 CRM。

### 剩下的步骤

1. **落地库**：单独开一个 Postgres，建表（字段按对方推送的实际列定），
   给 3CX 一个只能 INSERT 的账号
2. **取数层** `lib/threecx/landing.ts`：按水位线读新行 → 翻译成 `CallRecord`。
   水位线要留重叠窗口，跟邮件那边同一个道理（不留重叠，一次失败就在时间线上留个永久的洞）
3. **落库层**：复用 `resolveContact`（电话身份）+ `contact_touchpoints`（`channel: 'phone'`、
   `source: 'threecx'`、`source_ref` = 通话编号）。`countsAsReached=false` 写成
   `metadata.automated = true` —— 那是读路径（今天该联系谁）现有的「这一笔不算有人跟过他」标记
4. **`/api/cron/call-sync`** 每 15 分钟，同一个 PR 内加 `render.yaml` 调度条目
5. **归因**：来电号码接上已有的人 → 电话计入原本的首次来源

### ⚠️ 录音只存 3 个月 —— 有个到期日要 PM 拍板

推过来的是**下载链接**，而录音本身在 3CX 那边 3 个月后就没了。所以：

- **默认做法**：只存链接，不复制音频。数据最少、风险最小、不花存储钱
- **代价**：3 个月前的通话，将来谁也听不回来了

要不要把音频复制进我们自己的存储，是**业务 + 隐私**决策（客户的通话内容、
录音告知义务、存储成本），PM 拍。**但它有到期日** —— 接通之后第一个 3 个月内必须定，
过了就不是「改主意」而是「已经丢了」。

### 还卡在对方的

- 开**一个分机**（$30/月），并让 3CX 那边把 Data Connector 指向我们的落地库
- 推送表的**实际列名**要拿到第一批真实数据才能确定
