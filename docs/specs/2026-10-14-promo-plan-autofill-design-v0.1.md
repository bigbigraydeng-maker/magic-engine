# 推广计划「帮你填好」· 设计稿 v0.1（只是设计，没写代码）

- 日期：2026-10-14 · 窗口：115 号 · 起因：PM 10-14 反馈「页面没错，但太复杂；里面的东西不该我来填，应该你主动帮我填好」
- 风险级别：**A**（新增一个写计划内容的接口 + 批准前多一道硬检查）· 状态：待 PM 一个决定 + 子牙/魏征设计审
- 平台层级门（Inline）：这是把**既有**「营销计划生成器」的产出自动翻成推广计划结构（L1 扩展既有 Marketing Plan，不新增能力线）；阶段默认分法是 L2 剧本默认数据（标未验证）；目标 / 预算 / 账户 / 主题来自客户自己的记录（L4）。共享代码不写客户名 / 行业词，换客户或换行业不用改代码。

## 0. PM 版（先看这里）

**你说得对。** 现在的页面要你一项项填目标、阶段、预算、主题——这是我把「系统已经会做的事」做成了表格让你做。系统其实已经有一个计划生成器：它读品牌资料、活动资料和搜索量建议词，自己排出每周发几条帖子、写哪些博客（带真实搜索量）、发哪些邮件。我之前没把它和推广计划页接上。

**新做法：一键帮你填好。页面变成三块，别的都收起来：**
1. **「我替你填好的计划」**：阶段卡片 + 每天做什么的排期（现在已有）。
2. **「需要你拍板的 N 件事」**：只列系统不能替你决定的——**钱**（广告每天花多少）和**没有依据的事**（还没绑广告账户、没选受众、没有进行中的目标）。每条写清「是什么、为什么要你定、点哪里去定」。
3. **「批准」按钮**：这 N 件事没处理完，按钮是灰的，并写明还差哪几件。
- 原来的填表区折叠成一行「想自己改？展开」，平时不出现。

**系统怎么填（全部来自库里已有的真实数据，不凭空写）：**
| 填什么 | 从哪来 |
|---|---|
| 计划起止日期、服务哪个目标 | 这个客户当前**唯一进行中**的目标（周期、预算都在目标里）；有多个或没有 → 列进「需要你拍板」 |
| 每周几条帖子 / 快拍 / 短视频 | 现有计划生成器的输出（它按品牌资料和活动资料排的），把各平台加总 |
| 博客主题和日期 | 现有计划生成器的输出（关键词和搜索量来自 DataForSEO，不是我编的） |
| 邮件主题和日期 | 现有计划生成器的输出（只有开通了邮件渠道的客户才有） |
| 阶段怎么分 | **系统默认分法**：预热 25% / 主推 50% / 收尾 25%，页面标「系统默认分法，可改」。没有任何行业证据，所以只当起点 |
| 广告 | 客户有**绑定的广告账户** + 目标里**写了预算**才放广告步骤；每天预算 = 目标预算 ÷ 目标天数，**标「建议值，需你确认」**；受众系统不知道，留空并列进「需要你拍板」 |

**没有计划可用时**：页面只剩一个按钮「帮我生成并填好」——用目标的周期当日期、自动起名，调用一次现有计划生成器（会产生一次生成费用，和以前生成计划一样），生成完自动填好。

**你要定一件事（回「同意」或说怎么改）：** 广告每天预算由系统按「目标预算 ÷ 目标天数」给出**建议值**，标「需你确认」，**你不点确认就不能批准**。同意这样出建议吗？（钱是你的决定，所以我不替你默认。）

## 1. 现状（我核了代码）

- `POST /marketing-plan/generate`：读 Master Brief（必需）+ Campaign Brief + SEO 建议词 + 爆款参考 + 邮件渠道表现 → Claude Strategy Engine 出 `plan_data`（`social` 各平台每周 / 每月条数、`blog.topics`、`email.topics`、`tasks`）。需要 `title / start_date / end_date`。
- 推广结构 `plan_data.promo`（阶段 + 四类步骤）和上面是两套并行数据，现在靠人手填 `promo`。
- 目标：`goals` 有 `period_start / period_end / budget_amount / budget_currency / status`；每客户只允许一个 active。
- 广告账户：`client_meta_ad_accounts`（含账户日预算上限）。受众：计划里的 `audience_ref` 目前是自由文本，没有可核对的受众表。
- 批准前检查清单（`gates.ts`）目前没有「占位未处理」这一项，所以空受众 / 未确认预算不会拦住批准。

## 2. 设计

### 2.1 纯函数 `buildPromoDraft(input)` → `{ spec, decisions[] }`

输入：已生成的 `plan_data`（social / blog / email）、目标、客户名下广告账户、计划起止日。**不读库、不调 AI、不花钱**，同输入同输出。

- 阶段：把起止日按默认比例（25/50/25，进 `playbooks.ts`，标 `unvalidated_default`）切成预热 / 主推 / 收尾；总天数 < 14 时只出 1 个阶段。
- 社媒：每个阶段一个 `social_cadence` 步骤，条数 = 各平台加总（posts / stories / reels）。
- 博客：生成器的 `due_week`（1–4）换算成具体日期，落在所属阶段内，不在阶段内就放该阶段最后一天并写进说明；邮件用生成器给的 `due_date`，同样夹进阶段。
- 广告：账户 = 客户唯一绑定的账户（多个 → 进「需要你拍板」让选）；日预算 = `budget_amount ÷ 目标天数` 取整到分，币种以账户快照为准、解析不到就不显示币种；超过账户上限时取上限并写进说明。**主推阶段放广告步骤，预热 / 收尾不放**（默认摆法，标未验证）。
- `decisions[]`：每条 = `{ key, what, why, how, href, blocking }`。包括：没有 / 多个进行中目标、没绑广告账户、广告预算待确认、广告受众待选、阶段分法待确认（非阻塞）、生成器某类内容为空（如没有邮件渠道，非阻塞，只说明）。

### 2.2 接口：`POST /api/clients/[id]/marketing-plan/[planId]/promo/autofill`

- 只对**草稿**计划；读该计划的 `plan_data`、该客户的目标和广告账户（都按路径里的客户读取），调 `buildPromoDraft`，用现有 `PUT /promo` 同一套校验（目标归属、账户归属、预算上限）后写入 `plan_data.promo`，并写入 `promo.autofill = { version, filled_at, notes[] }`（schema 加这个**可选**字段，旧计划不受影响）。
- 已有 `promo` 时默认拒绝（409，说明「已经有推广结构，要重新填请先点『重新帮我填』」）；`{ replace: true }` 才覆盖，且覆盖前把旧结构留底到 `generation_meta.previous_promo`（最多 3 条）。
- 不调用任何 AI、不对外、不花钱；回执：写入时间、操作者、规则版本。

### 2.3 接口：没有计划时的「帮我生成并填好」

页面按钮调用**现有** `generate`（标题 = 自动、日期 = 目标周期、强度 = standard），成功后再调 `autofill`。生成费用与现在一样，按钮旁明写「会调用一次内容引擎生成计划」。失败（没有 Master Brief 等）把原因翻成人话列进「需要你拍板」。

### 2.4 批准前新增一道硬检查：`plan.no_open_decisions`

- 草稿带 `autofill` 且仍有 `blocking` 的待决事项（广告预算未确认、受众待选、没有目标等）→ 批准按钮灰着并逐条说明；PM 在页面上逐条「确认 / 修改」后才放行。
- 「确认」写成人工核实记录（沿用现有 `promo_checks` 机制：谁、什么时候、备注），不新增表。
- 没有 `autofill` 标记的计划（FDE 手填的）不受这道检查影响。

### 2.5 页面

- 新组件 `PlanAtAGlance`：顶部「我替你填好的计划」摘要（阶段卡片 + 排期表）+「需要你拍板的 N 件事」清单（每条带「去处理」或「确认」按钮）+ 批准按钮。
- 填表区（`PromoSpecForm`）+ 高级文本编辑器收进一个 `<details>`「想自己改？展开」。
- 示例计划按钮保留，只在没有任何计划时出现。

## 3. 不做（本步）

- 不替你定任何钱：预算只是建议值，必须你确认；系统不会批准、不会开投、不会派待办。
- 不编受众：库里没有可核对的受众，留给你选。
- 不自动改客户网站、不生成内容、不碰广告账户。
- 不做批准后写待办卡（S4b，前置条件见 S4 设计稿 §8）。
- 阶段默认分法没有行业证据，只当起点；行业剧本以后有证据再改。

## 4. 风险与应对

| 风险 | 应对 |
|---|---|
| 系统「建议的预算」被当成既定事实 | 页面标「建议值，需你确认」；不确认不能批准；确认动作留痕 |
| 用错目标（客户有多个进行中目标） | 多个 / 没有都不自动选，列进待决事项 |
| 生成器的数字被当成已核实（搜索量、主题） | 沿用生成器自带的数据来源；排期表固定提示「以上是计划原文，未经官网核实，发布前必须核对」 |
| 重复点「帮我填好」覆盖手改内容 | 已有 promo 默认拒绝；覆盖要显式确认并留底 |
| 阶段默认分法被当成专业建议 | 页面标「系统默认分法」；剧本里标 `unvalidated_default` |
| 并发（两人同时填） | 写入走 `updated_at` 乐观锁，没命中返回 409 提示刷新 |

## 5. 验收（当场试跑）

- 纯函数：阶段切分（含 < 14 天）、日期夹进阶段、预算取整与上限、多账户 / 无账户 / 无预算 / 多目标 / 无目标、邮件为空、同输入同输出；换客户 / 换行业用两套合成数据证明共享代码不改。
- 接口（假数据库）：草稿能填；非草稿 409；已有 promo 409；`replace` 留底；越权客户的目标 / 账户被拒；并发 409；没有任何 AI 调用。
- 批准：有未确认的阻塞待决事项 → 按钮灰、接口 409；确认后放行；手填计划不受影响。
- 页面：本地页面 + 模拟接口截图「待你拍板」清单、全部确认后的批准按钮、折叠的填表区。生产库写入需 PM 点头，不对真实客户试跑。

## 6. Reuse Statement（设计阶段）

- 复用：`generate` 路由与计划生成器（不改）、`PromoSpec` 校验与 `PUT /promo` 的归属 / 预算核对、`promo_checks` 人工核实记录、`loadOwnedAccounts / listActiveGoals`、排期表、阶段卡片、批准乐观锁。
- 平台共享：`buildPromoDraft`、`autofill` 接口、`PlanAtAGlance`、新硬检查。行业特有：无（默认分法标未验证）。客户特有：无。
- 与 tier-gate Inline 判定一致：L1 扩展既有 Marketing Plan，不新增能力线。
