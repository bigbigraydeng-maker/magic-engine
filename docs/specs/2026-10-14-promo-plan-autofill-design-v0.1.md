## 0. PM 版（先看这里）

**你说得对：** 现在的页面要你一项项填，是我把「系统已经会做的事」做成了表格让你做。系统有个计划生成器，会读品牌资料、活动资料、搜索量建议词，排出每周发几条、写哪些博客、发哪些邮件。我没把它和推广计划页接上。

**新做法：一键帮你填好。页面只剩三块，别的都收起来：**
1. **「系统起草的计划（待你确认）」**：阶段卡片 + 每天做什么的排期，每一块标明来源：「来自你的记录」/「系统默认」/「AI 生成，未核实」。
2. **「需要你处理的事」**：只列系统不能替你决定的。**钱的部分只有一件：广告每天花多少、投给谁——你自己填这一个数和一个受众，系统不替你猜。**
3. **「批准」按钮**：还有没处理的必需项就是灰的，并写明差哪几件；旁边固定一句「批准只是确定计划，不会开始花钱、不会发布；开投要另外在广告审批页批」。

原来的填表区折叠成一行「想自己改？展开」。

**系统怎么起草（全部来自库里已有的数据，不凭空写）：**
| 填什么 | 从哪来 | 标签 |
|---|---|---|
| 服务哪个目标 | 这个客户**唯一一个**进行中的目标；有多个 → 你在下拉里选；没有 → 页面让你先建 | 来自你的记录 |
| 计划起止日期 | 已有计划就用它的；没有计划就从今天起排 4 周（不超过目标结束日） | 来自你的记录 / 系统默认 |
| 每周几条帖子 / 快拍 / 短视频 | 现有计划生成器的输出，各平台加总 | AI 生成，未核实 |
| 博客、邮件的主题和日期 | 现有计划生成器的输出。**只搬主题和日期，不搬它估的搜索量**（那是 AI 估的数，不是 DataForSEO 的；关键词留空，要写等有真实搜索数据再填） | AI 生成，未核实 |
| 阶段怎么分 | **系统默认分法**：预热 25% / 主推 50% / 收尾 25%（总天数不足 14 天就只出 1 个阶段） | 系统默认，可改 |
| 广告 | **不自动填。** 页面上有一个小表：选广告账户、填每天预算、填受众——三项填完才出现广告步骤。目标里写的预算只当参考显示，并注明「可能含非广告费用」 | 你填的 |

**为什么钱不由系统建议（审查查出来的）：** 目标里的「预算」是总盘子（可能含内容、视频、人力），币种默认值也只是 AUD；「总预算 ÷ 天数」可能把广告费放大十倍以上。所以我收回了上一条问你的「建议值」做法：钱只由你填一个数，填了就是你的决定，不需要再「确认」，也就没有「确认后又被改掉」的漏洞。

**一键起手（没有计划时）：** 页面按钮「帮我生成计划」调用一次现有计划生成器（有生成费用，和以前一样，按钮旁写明、点后立刻变灰、最多约 3 分钟）。生成完页面变成「继续填好」；**中途断了也只会续填，不会再生成第二份、不会再收一次费**。

**这一步之后系统仍然不会替你做的：** 不批准、不开投、不发布、不派待办、不生成内容、不碰广告账户。

**你要定的事：** 没有新的要你定的了（预算建议值那件事已作废）。你回「可以」，我就先做第二轮设计审，通过后分两个小步骤做（见 §7），每步你都能在页面上看到。

## 1. 现状（我核了代码；标 ⚠ 的是审查纠正了我 v0.1 的地方）

- ⚠ **目标不是「每客户只有一个进行中」**：唯一索引已在 `20260620000001_phase32_goal_subtypes_multi_active.sql` 删除，可以有多个进行中目标。
- 生成器输出（`MarketingPlanData`）：`social` 各平台 `posts_per_week / stories_per_week / reels_per_month`；`blog.topics[]`（`title / primary_keyword / keyword_volume / keyword_kd / due_week(1–4)`）；`email.topics[]`（`title / due_date`）；`tasks[]`；`generation_meta.truncated`。⚠ 搜索量和难度是 LLM 吐出的整数，**不保证来自 DataForSEO**；日期没有代码校验；被截断（`truncated`）时 tasks / email 可能不完整。
- ⚠ **`audience_ref` 是自由文本、必填（`min(1)`）**，没有可核对的受众来源，门里也没有任何受众检查——所以「受众留空」会让保存校验失败，必须在设计里处理（§2.4）。
- ⚠ **批准前检查清单只评估「时间最早的阶段」**（`gates.ts` `evaluateApproval`）。广告若在第二阶段，账户可用、上限、素材、落地页核实这些钱相关硬门**一项都不会被检查**——这是 v0.1 漏掉的、最严重的一条（§2.5）。
- ⚠ **`PUT /promo` 没有 `updated_at` 乐观锁**（只有 `status='draft'`）；有锁的是 PATCH 和批准。
- ⚠ 人工核实记录（`promo_checks`）只认两个固定 key，且**不绑定被确认的值**——所以 v0.1 的「确认预算」做法不成立；v0.2 改为「你填数」，不再需要确认记录。
- ⚠ 带推广结构的计划批准时**不派发** `plan_data.tasks`（只写回执）。对已有草稿跑「帮我填好」后，批准也不再派那批旧待办——页面要明说。
- `goals.budget_amount` 可空、语义不明；库里 CTS / Oztop 全部进行中目标的预算都是空——所以大多数客户本来就走「没填预算，不放广告」。
- `generate` 路由无幂等：每次 POST 新建一份计划并调用一次 Claude（可到 180 秒）。

## 2. 设计

### 2.1 纯函数 `buildPromoDraft(input)` → `{ spec, notes[], decisions[] }`

输入：已生成的 `plan_data`（social / blog / email / tasks）、`generation_meta.truncated`、进行中目标、计划起止日、今天。**不读库、不调 AI、不花钱**，同输入同输出。

- **阶段**：总天数 N；N < 14 → 1 个阶段（名称「计划期」）；否则 `n1 = n3 = round(0.25N)`、`n2 = N − n1 − n3`（每段至少 1 天），相邻阶段首尾衔接（end+1 = 下一段 start），保证不重叠。比例 / 14 / 阶段名称进 `playbooks.ts` 与 `labels.ts`（标 `unvalidated_default`）。起始日已过去 → 从今天起排并写进说明（不静默生成已过去的阶段）。
- **社媒**：每个阶段一个 `social_cadence` 步骤；posts / stories 各平台加总，reels 先跨平台加总再折算（与每周对账口径一致）。
- **博客 / 邮件**：先清洗：主题去空去重、截 80 字；`due_week` 不在 1–4 / 非整数 / null、邮件 `due_date` 不是真实日期 → **丢弃并写进 `notes`**（页面显示「系统丢掉了 N 条不合格的」，不悄悄少）。博客日期优先取生成器 `tasks[]` 里对应条目的真实 `due_date`（用 `source_blog_topic_index` 对上），否则 = 计划起始日 + (week−1)×7，再夹进计划范围；然后按日期归入所属阶段。`primary_keyword` 一律留空，**不搬 LLM 自带的搜索量 / 难度**。
- **步骤编号**：稳定可预测（`soc-<阶段序号>`、`blog-<序号>`、`mail-<序号>`），全局唯一。
- **不放广告步骤**（见 2.4）。
- **`decisions[]`**：每条 `{ key, what, why, how, href, level: 'required' | 'info' }`。例：没有进行中目标（required）；多个进行中目标要选（required）；生成可能没生成完 `truncated`（info，强提示）；起始日已过去（info）；生成器某类内容为空，如没邮件渠道（info）；还没有广告步骤（info：「要投广告请填每天预算和受众」）；批准后不会自动派待办（info）。
- **所有「待处理事项」每次都按当前内容重新算**，不依赖任何存起来的标记（§2.3）。

### 2.2 接口：`POST /api/clients/[id]/marketing-plan/[planId]/promo/autofill`

- 鉴权同目录其它路由（`requirePaidClientAccess`）。只对**草稿**；读该计划的 `plan_data`，目标 / 账户**按路径里的客户**读取。请求体只允许 `{ replace?: boolean, goal_id?: string }`；`goal_id` 仅在有多个进行中目标时用，**服务端照样用 `loadGoal(路径客户, goal_id)` 重新校验归属**，不信前端。
- 写入走与 `PUT /promo` 同一套校验（目标归属、账户归属、预算上限、结构校验）。**UPDATE 同时带 `status='draft'` 和 `updated_at`**，没命中返回 409「刚被别处改过，请刷新」。同时**给 `PUT /promo` 补上同样的 `updated_at` 锁**（审查指出 PUT 与 PATCH 会互相覆盖）。
- 已有 `promo` 默认拒绝（409）；`replace: true` 才覆盖，覆盖时：旧结构只留**一份摘要**到 `generation_meta.previous_promo`（阶段数、步骤数、哈希、`replaced_at`、`replaced_by`，不存完整结构，避免撑大计划行），并清空 `generation_meta.promo_checks`（旧核实记录不沿用到新结构）。
- 来源记录写在**服务端字段 `generation_meta.autofill`**（不在客户端可写的 `plan_data.promo` 里，PUT 不能剥掉或伪造）：`{ request_id, version, filled_at, filled_by, rule_version, notes[], no_publish: true, external_effect: 'none', cost_usd: 0 }`——即机器可读回执。
- 同步、无外部副作用、不花钱，不需要上 Inngest（依据 CLAUDE.md §3 例外，PR 写明）。

### 2.3 批准前的检查（A 级改动，两处）

1. **花钱相关硬门不再只看最早阶段**：`evaluateApproval` 除了评估时间最早的阶段，还要对**第一个含广告步骤的阶段**求值（账户可用、上限已设、结果口径、素材已批准、预算不超上限、落地页真实存在等）。这一条**与「帮我填好」无关，是既有漏洞**——只是「广告放在第二阶段」的计划（含手填的）一直绕得过。改 `gates.ts` + 测试 + 回归。
2. **待处理事项不新增「确认」机制**：因为钱和受众由 PM 直接填进计划，没有需要「确认」的建议值，所以**不新增 `plan.no_open_decisions` 硬门、不扩 `promo_checks`**（v0.1 的这两项作废）。`level: 'required'` 的事项（没目标等）本来就由现有门 / 保存校验挡住；页面把现有硬门的阻塞项和 `decisions[]` **合并成一份清单**展示，不两处各报一遍。

### 2.4 广告：小表，不自动填

- 页面「需要你处理的事」里有一项「还没有广告」，展开是一个小表：**广告账户**（下拉，来自该客户名下账户，无账户时写「这个客户还没绑广告账户」）、**每天预算**（你输入，单位元；旁边只读显示「目标里写的总预算 X（可能含非广告费用，仅供参考）」）、**受众**（填现有受众的名称或编号）。三项都填完才保存，一次写入含该广告步骤的完整结构（**保存校验与现有 `PUT /promo` 完全一致**：账户归属、日预算上限、必填项），所以没有「空受众占位」的半成品。
- 广告步骤放进哪个阶段：默认放「主推」阶段（只有 1 个阶段时就是它），下拉可改。步骤编号 `ads-1`。
- 币种：只显示数字并注明「按广告账户的币种」，不做换算、不臆断币种（与 `budget-caps` 的「不换算」一致）；账户或客户上限读不到时，现有校验已按「未核实」处理，不静默改数。

### 2.5 一键起手（没有计划时）：两步，可续、防重复

- 页面按钮「帮我生成计划」→ 调用**现有** `generate`（标题自动、起止日 = 从今天起 4 周且不超过目标结束日、强度 standard）。**`generate` 增加幂等小改**：同一客户、同标题、10 分钟内已有草稿 → 直接返回它，不新建、不再调用 Claude。
- 点击后按钮立即变灰并写明「生成中，最多约 3 分钟，请勿重复点击」；拿到计划编号就存进页面状态（并写入 `sessionStorage`）；页面随时按「是否已有计划 / 是否已有推广结构」判断下一步：**有计划没推广结构 → 按钮变成「继续填好」，只调 `autofill`，绝不再调 `generate`**。
- 失败原因逐类翻成人话（没有品牌资料、AI 超时、AI 返回无法解析、额度不足……各一条文案，不显示原始报错）。
- 4 周窗口的原因：生成器的 `due_week` 只有 1–4，长周期一次生成会被截断。目标更长时页面写「这一份只排了 4 周，后面等这份做完再续」。

### 2.6 页面

- 新组件 `PlanAtAGlance`：①「系统起草的计划（待你确认）」摘要（阶段卡片 + 排期表，每块带来源标签）；②「需要你处理的事」清单（现有硬门阻塞项 + `decisions[]` 合并去重；每条有「去处理」）；③ 批准按钮 + 固定提示「批准只是确定计划，不会开始花钱、不会发布；开投要另外在广告审批页批」。
- 填表区（`PromoSpecForm`）+ 高级文本编辑器收进 `<details>`「想自己改？展开」；示例计划按钮只在没有任何计划时出现。
- 「系统起草」标题和三种来源标签，防止「已填好」被误读成「系统已核实」。

## 3. 不做（本步）

- 不做批准后写待办卡（S4b，前置条件见 S4 设计稿 §8）。

## 4. 风险与应对（含审查查出的）

| 风险 | 应对 |
|---|---|
| 把「总预算 ÷ 天数」当广告日预算，放大十倍 | **不自动推导**；PM 自己填，目标预算只当参考并注明可能含非广告费用 |
| 「确认」一键放行 / 确认后值被改 | 没有确认按钮；值直接写在计划里，改了就是改了 |
| 广告放第二阶段，钱相关硬门被跳过 | 批准检查对「第一个含广告的阶段」也求值（§2.3，既有漏洞一并修） |
| AI 估的搜索量被当成真数据 | 只搬主题和日期，关键词留空，不搬任何 LLM 数字 |
| 生成器垃圾输出（日期错位、重复、空主题） | 先清洗，丢弃的逐条记入说明，页面显示「丢掉了 N 条」 |
| 标记被 PUT 剥掉 / 伪造 | 来源记录放服务端字段 `generation_meta.autofill`；待处理事项每次按当前内容重算，不依赖标记 |
| 并发（autofill / PUT / PATCH / 批准互相覆盖） | 全部带 `updated_at` + `status='draft'`；PUT 补锁 |
| 重复点击重复生成、重复收费、半途失败留半成品 | 按钮立即变灰；`generate` 幂等；可续填；不会二次生成 |
| 「已填好」被读成「系统已核实 / 已替我决定」 | 标题「系统起草（待你确认）」+ 三种来源标签 + 批准 ≠ 开投 固定提示 |
| 对已有草稿跑填好后批准不再派旧待办 | 页面明写「批准后不会自动生成待办」（已有批准记录同款提示） |
| 阶段名「预热 / 主推 / 收尾」不适合常青型客户 | 阶段名进 `labels.ts`、比例进剧本，标未验证；以后按目标类型选模板，没有模板就只出 1 个阶段 |

## 5. 验收（当场试跑）

- 纯函数：阶段切分（含 < 14 天、取整、衔接不重叠）、日期夹进阶段、`due_week` 异常值、邮件日期非法、主题去重截断、`truncated`、起始日已过去、同输入同输出；**换客户 / 换行业各用一套合成数据证明共享代码不改**。
- 接口（假数据库）：草稿能填；非草稿 409；已有 promo 409；`replace` 留摘要并清 `promo_checks`；越权客户的目标 / 账户被拒；`goal_id` 重新校验；并发 409；`PUT` 补锁；全程零 AI 调用。
- 批准：广告在第二阶段时钱相关硬门被评估（手填 / 填好都一样）；手填旧计划与已批准计划行为不变（回归）。
- 页面：本地页面 + 模拟接口截图「系统起草」摘要、需要你处理的事、广告小表、折叠的填表区、「继续填好」状态；生产库写入需 PM 点头，不对真实客户试跑。
