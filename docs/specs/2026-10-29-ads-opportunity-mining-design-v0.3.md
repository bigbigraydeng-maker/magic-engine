## 1. 平台 / 行业 / 客户三层（PM 2026-10-29）

跟 2026-10-10 PM 定的「所有支柱 agent 一律平台-行业-客户三层」同一个原则。

| 层 | 装什么 | 不许装什么 |
|---|---|---|
| **平台层** | 方法：抓取、切格子、统计筛选、AI 解读护栏、对照测试判定；默认阈值 | 任何客户事实、任何行业结论 |
| **行业层** | 同行业多个客户合起来的"基准线"（例：旅游业各时段的相对进线成本）；经 ≥2 个客户验证过、方向一致的结论 | 单个客户的原始数字、客户名 |
| **客户层** | 这个客户自己的格子、发现、测试结果；客户配置（阶段映射、阈值覆盖） | — |

### 1.1 行业从哪来

- `clients.industry` 已有，但是自由文本（生产实查：`travel`、`logistics`×2、`beauty_spa`、`flooring`，以及一条整句描述的电商）。
- 平台层加一个**行业归一函数**：自由文本 → 固定行业键（`travel` / `logistics` / `beauty_spa` / `flooring` / `ecommerce` / `real_estate` …），映射表写在配置里；认不出的归 `unclassified`，**不进任何行业池**。
- 行业**不写进数据行**（客户可能改行业），分析时现查现归一。

### 1.2 行业层怎么用

1. **分层收缩**：一个格子的进线率，小样本时依次往"这个客户整体 → 同行业 → 全平台"拉。这样一个新客户数据少时，能先借同行业的经验，而不是借全平台的平均。
2. **行业基准线**：发现里多一行"同行业对比"（例："这个时段比同行业平均便宜 30%"），只用相对指数，**不展示其他客户的原始数字**。
3. **行业池门槛**：同行业 ≥2 个客户、每个客户在窗口内预期进线 ≥ 门槛才启用；单个客户在行业池里的权重封顶 60%，防止一个大客户把"行业"变成"这个客户"。
4. **升级到行业手册**：某条结论在同行业 ≥2 个客户的对照测试里都验证成立、方向一致，才生成"行业手册候选"，写进 `playbook-ads-industry-<行业>` 前要人审。**不自动升级，不自动套用到新客户。**

### 1.3 现在各行业的数据够不够（2026-10-29 实查）

| 行业 | 绑定了广告账户的客户 | 行业层能不能用 |
|---|---|---|
| 旅游 | CTS（2 个账户） | 不能：只有 1 个客户 |
| 物流 | NAL、East International | 账户数够，但表单进线极少（NAL 90 天 3 条），预期进线不够 → 暂不能 |
| 美容 / 地板 / 电商 | 各 1 个 | 不能 |

**结论：底座按三层建，但现在实际只有客户层在工作。** 行业层要等同行业第二个有量的客户进来才会自动亮起。

### 1.4 存储上的落点

`ad_opportunity_findings` 加两列：`layer`（`client` / `industry`）与 `industry_key`。行业层的行 `client_id` 为空、**不存任何客户编号以外的客户信息**，只存参与的客户数和相对指数。

## 2. 继续挖到的数据（2026-10-29，只读）

### 2.1 年龄 × 性别（主账户 90 天，Meta 自报留资，**有留资数**）

- 花费 ~80% 在 55 岁以上；进线成本各组接近（约 NZ$9–12/条）。
- 65 岁以上：男性约 NZ$9.2/条（花 1,054、115 条），女性约 NZ$11.5/条（花 1,407、122 条）。系统把更多钱给了略贵的那一组。
- 55–64 岁同方向：男约 NZ$10.1、女约 NZ$11.9。
- **未过统计，只是线索**；而且 Meta 按性别优化本来就会这样分钱，要对照测试才能判。

### 2.2 能往回拉多久

- 主账户 2026-04 才开始有花费（4、5 月各约 NZ$60–70，6 月起每月约 NZ$1,600–2,900）。
- 按小时拆分拉 2026-07 整月成功 → **至少能回拉 4 个月**；对这个账户等于全部历史都拉得到。
- 阶段 1 回填上限定 **120 天**，够覆盖现有全部有效历史。

### 2.3 二号账户不收表单，指标必须按"系列目标"分开

二号账户 30 天在投 4 个系列：WhatsApp 私信（NZ$298，9 次开聊）、私信（几乎没花）、播放量养池（NZ$156）、官网点击（NZ$167，129 次点击）。

→ **格子只在"同一种系列目标"内部比**，不同目标的花费不能混在一个分母里（v0.1 正是错在这里，手册 §四十一）。
→ 抓取时同时存 Meta 自报的**私信开聊数**，私信类系列才有自己的成绩可比。

## 3. 阶段 1 落地决定（改 v0.2 §4.2–§4.3、§5）

1. **数据库只建两张表**：`ad_breakdown_stats`、`ad_opportunity_findings`。v0.2 里的视图 `ad_lead_events_v` **取消**，进线层改成程序里的读取函数（阶段 2，B 级，不改数据库结构）。理由：按"广告所属账户的时区"换算要连两三张表取最新快照，写成视图既慢又难测。
2. `ad_breakdown_stats` 加三列：`campaign_id`、`adset_id`（按系列目标分组要用）、`meta_messaging`（私信开聊数，按 `MESSAGING_ACTION_PRIORITY` 取第一个出现的，不相加）。
3. 阶段 1 抓四种切法：`hour_account_tz`、`placement_device`、`age_gender`、`region`。前两种 + 年龄性别带 Meta 留资；小时、地区的 `meta_leads` / `meta_messaging` 一律存空，不存 0。
4. **调度**：Inngest 每天新西兰时间 06:30 跑一次（在 Meta 昨日报表稳定之后、PM 早上看待办之前）。
5. **默认什么都不写**：模式 `dry` / `live`，客户名单由环境变量给，默认空名单、默认 `dry`。`dry` 照样去 Meta 读、照样做对账，只是不写表，回执写进运行记录——这正是"当场试跑"的方式。改成 `live` 要在数据库表建好之后。
6. **对账是验收的一部分**：每次运行，每个账户每天、每种切法的花费合计跟同一天的账户总花费比，误差 > 1% 记进回执。
7. 回填：账户在表里没有足够深的历史时拉 120 天，否则拉昨天 + 前 7 天（复用 `daily-insights.ts` 的窗口思路与账户时区）。
