# 第二部分：技术方案

## 0. 目标与不做
目标、不做：同 v0.2。**不新增发布通道**（Publer 适配器另立项）；不替换 make_promo（并存）；不上云渲染。

## 1. 现状要点（已对照代码）
同 v0.2 §1，补充：外部单若停在 `claimed` 会被清扫任务收回成 `queued` 再被真出片机领走（`factory-worker-sweeper/route.ts:36-45`），所以**外部单不经过 claimed**；`master_brief_id` 现在没有校验属于该客户（`complete-work-order.ts:160-165`）；`guardAdmin` 放行受限演示管理员（`require-admin.ts:50-62`）。

## 2. 分层判定
同 v0.2 §2（L3 适配器 / generic 与 travel 模板 / L4 props，注册表带 `industries`，CI 扫描禁 CTS 词）。新增：**props 必须过 schema 校验（zod，限长），不得含 URL 或本地路径（素材由出片机预先下载），禁 `dangerouslySetInnerHTML`、不开 `disableWebSecurity`，Master Brief 文字一律当不可信文本**。

## 3. 方案分步

**0 备份（已做）· 0.5 授权核查（已查；PM 2026-10-05 确认 3 人以内，免费档可用；音乐来源待确认）**

**1a 外部成片入口（默认锁死）**
- 入口只给 `requireGlobalAdmin`（不是 `guardAdmin`），校验 `client_id`；登记账号与授权账号分开（agent 可登记，**不能授权**）。不用 worker 令牌，不用 Mac 共享密钥。
- **一步建成 `in_review`，不经过 `claimed`**；认领函数加条件排除外部单；外部单以**服务端算出的成片哈希**识别，不靠 `brief.source` 标签（标签可被省略）。
- 红线只按 `client_id` 取 Master Brief，并校验 `brief.client_id = wo.client_id`。
- 新表：外部成片登记表，**`sha256` 唯一约束**防重复登记，RLS 写 `FOR ALL TO service_role`；状态以此表为准，Inngest 事件只做通知。
- 声明文字（成片里每一句 + 首评 `endcard.offer/cta/url` + `caption`）进入声明清单：只收固定字段，**不允许带 `src` 之类的键展开进渲染配置**；每句来源必须是该客户已登记官网域名下的 URL 或 Master Brief 字段路径；服务端用**新写的受限抓取**（仅该客户官网域名、限大小限超时、比对原文片段，不是只查链接存在；不复用 `safe-remote-fetch.ts` 的 HEAD 探活）。
- 核对范围：价格、**团期、优惠、「限时/最后几位」类词**；官网快照新鲜度 ≤ 14 天，团期已过拒收。
- **外部单的红线命中和品控标记硬拦，不是标红不打回**；声明文字进 AI 品控前先清洗，防「忽略上文」类注入。
- 服务端多帧 OCR 与声明比对（新交付物）；不一致、或没读出来（NOT_MEASURED）一律不通过。**不在 Next 服务进程里解码不可信 MP4**：先限大小/分辨率/时长，再交给 Mac 出片机的子进程（有超时）；存储桶加 `file_size_limit` 与 mime 限制。
- `media_evidence` 由出片机（受信）计算，服务端不信调用方自报；复核不过按 NOT_MEASURED。
- 上传链接对外部单 `upsert:false`，同一路径不可覆盖。
- 事件与回执：`factory.external_reel.registered`（request_id、client_id、work_order_id、source_sha256、no_publish、created_at）。

**1b 发布许可（样片能不能发）**
- **许可对象 = 客户 + 模板（含版本）+ 有效期**，一次批；每条成片的发布资格 = 许可有效 **并且** 机器核对全过 **并且** 马良/苏东坡审过 **并且** 发布前哈希一致。今天手工做、没有模板的片子，才逐条批（例外，预计很少）。
- 存在**独立的只追加表**（触发器禁改禁删，RLS `TO service_role`），记：谁、何时、批了什么、到期、撤销。**不放台账，不放 `review_ref` 里**（那里是整体读改写，会把撤销覆盖掉）。
- **撤销与发布领取放进同一条带条件的 UPDATE**；`adapter.publish()` 前**重读一次许可**；到期、重试同走这一处。
- 发布前服务端取文件**重算 sha256**，拷到**按哈希命名、不可覆盖**的路径再发（Facebook 现在是自己去拉公开地址）。
- **闸装在适配器 `publish()` 入口**（`facebookReelAdapter`），按哈希/路径反查，覆盖 `processOne`、`applyApprove`、`lecture-publish.ts:192` 与旧 Airtable 同步 `review-sync.ts:222`，不只两处。
- 广告线：`/meta-ads/draft` 对「已登记的外部成片」的 video_id 同样要许可。**如实说明做不到的部分**：广告线收到的是裸 video_id，别的视频 id 拦不住；脚本直调 Meta/Publer 没有技术闸（这是 D14 本体）。**Publer 直发的三个口子（`create-post`/`schedule`/`quick-post`/`reels/[draftId]/publish`）已由 9/29 社媒发布治理设计另行处理，PM 已接受风险**；在它们收口前，纪律是 CTS 成片不经 Publer 发布。
- 事件：`factory.external_reel.exception_authorized`（授权人、范围、到期）；撤销、到期各有事件，进今日待办（见第一部分表）。

**2a / 2b / 2c** 同 v0.2，并按审查补充：
- 2b：`brief.engine` 工单级；claim 带 `engines` 只是调度提示（自报），**真正边界是人审 + 哈希校验**；`complete` 按 brief 重算 `props_hash` 比对；`engine=remotion` 不得带 `creative_recipe`；缺模板编号/对账表引用拒收；渲染期间定时心跳 + 超时 + 单次重试上限；出片机健康检查加 Chromium 与 Remotion；验证「掉线待办」对 remotion 单同样生效，文案改成人话；开机自启仍没有（PM 接受风险）。
- 2a 的 CI 扫描：模板里不得出现 CTS、团价、logo 文件名。

**3、4 另立方案。** 前置依赖：「发布凭证收口」（D14 未做的技术闸）；Publer 适配器只在要发 Instagram 等其它平台时才需要（CTS 的 Facebook 发布工厂已能做）。
