## 1 目的与不做什么

**目的**：让员工在一页里看到两件事——① 每个团的每个出发日期，订了几单、定金收了几单、尾款收了几单、还差几单；② 全部订单一张清单，可以按团、按状态筛。今天已经上线的只有「一个客人的抽屉里看他自己的付款」和「付款要催」名单，没有任何汇总页，这一页补的就是汇总。

**一句话必须看清楚**：这套系统**一个金额都不存**，所以「收款情况」从头到尾只是**数人数和数订单数**，不是钱。页面上不会出现、也不允许出现任何金额、营收、回款率之类的数字。

**明确不做**：不记金额、不开发票、不算营收、不做财务对账、不预测现金流、不对客人外发催款邮件（外发是另一条线，且受「同一客人 7 天不超 2 封」约束）、不碰团目录的任何写操作。

### 2.3「人数」这一列的诚实结论
`party_size` 可空，在加订单表单的「更多」里，不填也能提交。生产里目前 0 单，**无法用数据证明填不填**，所以这是【假设】：**多数订单不会填**。
处理方式：**订单数是主数字**，任何地方说「几单」都以订单数为准；人数只在旁边用小字写「已知人数合计 N 人（M 单没填人数）」。**空的人数绝不当 1 算**，也不拿平均值补。若 PM 回「不留」，这一列直接不做（§8-3）。

### 2.4 团目录的红线（必须照这条写）
团目录文件夹以外的代码**不许提 `tour_catalog_*` 表名，也不许引可能碰到草稿的团目录模块** —— 由 `src/lib/tour-catalog/__tests__/boundary.test.ts` 和 CI 任务 `.github/workflows/tour-catalog-boundary.yml` 两道闸守着。唯一许可的读口是 `src/lib/tour-catalog/booking-facts.ts`（只读、固定列）。
**本页要的团名、出发日期、出发日期状态，全部只能走这个模块拿**。好消息是它现在返回的列已经够用（团：`id, name, duration_text`；出发日期：`id, tour_id, depart_on, return_on, status`），**所以这一轮不需要加列**。万一以后要多一列，必须在团目录文件夹**里面**改 `booking-facts.ts`，并同步改它钉列名的自检用例，不能在 CRM 这边绕。

## 3 页面长什么样

### 3.1 放在哪（决定 + 理由两句）
**新开一个页签「付款总览」**，地址 `/dashboard/clients/<id>/crm/payments`，挂进 `CrmTabs`（`active` 从 `'all' | 'decisions'` 扩成三个值）。
理由一：这是**整个客户层面的汇总**，不属于某一个客人，塞进客人抽屉逻辑上不成立。理由二：「全部客人」那一页已经很重（横表 + 抽屉 + 批量发信 + 要催名单），再加一张汇总表会让它更慢、更挤；单独一页可以独立取数、独立显示空状态，门禁沿用同一道闸不额外开口。

### 3.2 上半：按出发日期（文字草图）

┌──────────────────────────────────────────────────────────────────────┐

│ 新西兰南北岛 12 天                                                   │

每个数字一句话说明：
- **订单** = 这个出发日期下、没取消的订单张数。
- **定金已收** = 其中定金这一项已经收到款的张数。

- **收齐** = 定金和尾款两样都收到了的张数。
- **还差** = 至少有一样没收到的张数（= 订单 − 收齐）。
- **逾期** = 「还差」里面，已经过了到期日的张数。

禁止出现：节点、里程碑、班期、departure id、milestone。

## 4 数字怎么算（逐条定死）

1. **订单数 vs 人数**：订单数 = 行数，永远是主数字。人数 = `party_size` 不为空的那些相加，另外报「几单没填」。**空值不补 1、不补平均**。
2. **定金已收 / 尾款已收**：对应那条付款记录 `state = 'paid'`。
3. **两样都收齐**：两条记录都 `paid`。
4. **逾期几单**：**必须复用现成的到期日逻辑**，即 `src/lib/crm/booking-schedule.ts` 的 `computeMilestoneDueDates`，经由 `booking-view.ts` 的 `buildBookingView` 调用——跟客人抽屉、「付款要催」名单走的是同一条路径，**不许在这一页另写一遍、更不许写成 SQL 里的日期计算**。逾期 = 该项未收款且算出来的到期日早于今天（今天按 Pacific/Auckland 算，复用 `nzTodayIso`）。员工手改过的到期日（`due_override_on`）优先，与抽屉同一规则。
5. **「线下已处理」的款**（`quiet = true`）：「还差」里算（钱确实还没收到），但**逾期里不算**，与「付款要催」名单的口径一致（名单会把 `quiet` 排除）。表格下方用小字写「其中 N 单标了线下已处理」。待 PM 确认（§8-5）。
6. **取消的单**：所有列一律排除，但**单独数出来**显示一行「另有 N 单已取消」，下半清单里也能用状态筛选看到。
7. **没选出发日期的单**：不按团分组，统一归到上半表最后一行「出发日期还没定」；它们算订单数、算定金，**不算尾款到期也不算逾期**（没有出发日就算不出尾款到期日，抽屉里现在就是这个行为）。
8. **团目录里出发日期被删了**：用订单上存的 `departure_depart_on` 快照显示日期，并在那一行标「目录里已找不到这个出发日期」。不因为读不到就让这单消失。
9. **出发日期被改过**：按团目录现在的日期归组和算到期日，与抽屉一致；该行带现有的「出发日变了，请确认」提示标记（复用 `BookingWarningCode`，不新造文案）。
10. **过去 vs 未来，默认筛选**：上半表**默认只显示今天及以后出发的**（含「出发日期还没定」那一行），过去的收起来，一个开关可以打开。理由：出发都已经过去了，付款追踪的意义不大，而且 CTS 的 34 个出发日期里只有 2 个是过去的。待 PM 确认（§8-1）。

## 5 怎么取数、快不快

两种做法比过：

**(a) 把该客户的有效订单和付款记录全读出来，在 TypeScript 里汇总。** 查询固定几条：订单一条（分页读，用现成的 `fetchAll`，不受 1000 行上限影响）、付款记录一条、客人姓名一条（按 100 一批）、团与出发日期走 `booking-facts.ts`（也按 100 一批）。**不存在 N+1**——不会每单再查一次团。然后对每单调一次 `buildBookingView`，汇总。
**(b) 在数据库里做一个只读的汇总函数或视图。**

**推荐 (a)**，三个理由：① 到期日和逾期必须用 `computeMilestoneDueDates`，这是 TypeScript 的纯函数，照 (b) 做就得在 SQL 里把工作日、假日顺延、90/120 分档、邮轮、快照规则**再写一遍**，两份实现迟早对不上，而这正是算错到期日最容易出事的地方；② (b) 要加数据库对象 = 一次 A 级迁移，还要照规矩写 RLS 和执行权（`FOR ALL TO service_role USING (true)`、`revoke execute from public, anon, authenticated`），为一个只读汇总付这个代价不值；③ 量太小，(a) 完全撑得住。

**预计行数**：CTS 最多 32 个未来出发日期，一单两条付款记录。就算哪天到 500 单，也就是 500 行订单 + 1000 行付款记录 + 最多 33 个团 + 34 个出发日期，一次请求里几条查询搞定。

**上限与截断**：沿用「付款要催」名单的做法，给候选订单一个硬上限（它那边是 `NUDGE_CANDIDATE_CAP = 500`，本页按同一常量族另设一个，初值 2000 单），**超了就老实说**：页面顶部显示「订单太多，这页只统计了最近 2000 单，数字可能偏小」，不悄悄截断、不假装完整。注意「付款要催」踩过的坑不是 1000 行分页上限（那边已经用 `fetchAll` 绕过了），而是这个**候选上限会让数字偏小**——所以截断标记必须一路传到界面，不能只留在后端。
下半清单分页：每页 50 行，服务端分页，按出发日期近的在前。

## 6 权限

- 沿用 `requireBookingAccess(clientId, 'view')`，不新建闸、不放宽。不在名单上的人（也不是 ME 全局管理员）**这一页什么都不渲染**，页签也不显示；客户没配 `booking_schedule` 或配成关闭 → 404，与现有接口一致。
- 操作人只取登录会话邮箱，不读请求体。所有查询都带 `client_id`。
- **多暴露了什么？核实后的结论：多了一点，不是零。** 今天「付款要催」名单已经会把**全客户所有未收款**的客人姓名、团名、到期日一次性返回（`NudgeRow` 就是这些字段），所以「谁还没付」本来就能汇总看到。这一页新增的是**「谁已经付了」也被汇总出来**——抽屉里一次只能看一个人。性质上仍是同一批数据、同一批人（同一份名单），没有新字段、没有金额、没有新的人能看；但「一屏看完所有人的付款状态」这个方便程度是新的。如实记在这里，不说「零新增暴露面」。
- 这一页只读，不提供任何写入口，所以不需要 `edit` 能力。

## 9 Reuse Statement

**复用了什么**：`requireBookingAccess`（门禁、fail-closed、名单）；`booking-store-reads.ts` 的分页与分批读法和 `fetchAll`；`booking-view.ts` 的 `buildBookingView` / `nzTodayIso`；`booking-schedule.ts` 的 `computeMilestoneDueDates`（**不另写一份到期日逻辑**）；`booking-nudge.ts` 的候选上限 + 截断标记这个模式；`booking-types.ts` 的 `BookingWarningCode` 与「定金 / 尾款」文案常量；`booking-http.ts` 的响应与 Server-Timing 写法；`CrmTabs` 页签导航；`useOpenContactFromNudge` 的 `?contact=` 跳转；团目录唯一读口 `src/lib/tour-catalog/booking-facts.ts`。

**平台共享（L1）**：汇总的纯函数（一组订单 + 付款记录 → 每个出发日期的六个计数）、只读汇总接口、这两张表的界面。里面没有客户名、客户 ID、金额，也没有任何行业词。

**行业专属（L2 旅游）**：「按出发日期分组」「定金 + 尾款两段」这个形状，沿用已有的 `industry/travel-booking-rule.ts`，本稿不改它。

**客户专属（L4 CTS）**：只有 `clients.leads_config.booking_schedule` 里的数字和开关，以及 `crm_booking_members` 里的两个邮箱。**共享代码里没有 CTS 的名字、ID 或数字**；没配这块的客户整个页签不出现。

**团目录边界**：本页**不提任何 `tour_catalog_*` 表名、不引团目录的其它模块**，团名与出发日期一律经 `booking-facts.ts` 取；它现有的列已够用，这一轮**不加列**。若将来要加，必须在团目录文件夹里面改该模块并同步改它钉列名的自检用例。

**学习沉淀**：不产生跨客户学习，订单与付款是该客户私有记录。等有第二家旅游客户用上，再判断「按出发日期汇总」这个形状能不能升到行业手册。

**快速自检**：把 CTS 换成另一家旅行社，只改 `booking_schedule` 的数字和名单；换成悉尼地产客户，只换行业规则（定金 + 交割），这两张表和汇总函数不动。
