## 0. 给 PM 的一页话

**它是什么。** 每次写月信之前，先做一份「今天的情境包」：今天几号、这位客人离出发多久、他这条路线这几天每座城市是什么季节什么天气、官方最新说法是什么、当下有没有真正值得说的事。包里每一条都带来源链接和查到的日期，查不到的写「没查到」。写信的人只准用包里的条目；写完由另一个角色逐句对账；最后还是你点头才发。

**它不是什么。** 不是新养一个 agent：藏经阁第十六部要求「先问现有的能不能加个工具」，答案是能——采集交给现有的侦察员张骞多一个「看当下」的数据源，写信前的取舍归邮件策划层，写后对账由文案质检李白多一项检查。它不发信、不改名单、不花钱；碰到敏感话题（政治、灾害、疫情、治安事件）一律不写进信，只报给你。

**今天试跑的结果。** 12 月初那两篇信已经按它手工重写：每位客人多了「他这条路线、这几天」的真实气候（来自中国气象局平均值）和「截至发送日」的官方说法（新西兰外交贸易部的出行建议，更新日 8 月 27 日）。热点查了 10 条，**一条都没用**——全是对这批客人没用、或查不到官方出处、或对品牌不安全。「当下没有值得说的」是它的正确输出，不硬凑。

**还有三个意外收获**（都是不跑这一遍就看不见的）：官网两页对 3 月气温说法互相矛盾；团目录里两个团的「城市」字段是空的；新西兰官方对中国的出行建议级别其实是「Exercise increased caution」（8 月 27 日更新），v0.3 没写——要不要写进信是「黄区」话题（§7），先按原话平静转述，你可以随时让我删。免签只到 12/31 这件事仍按你的话先不写，发信前照样重查。

**要你定的只有一件**：设计方向和新两篇信是否按这样走（见 §19）。

## 1. 层级判定与「少即是多」（me-platform-tier-gate · Inline）

- **[跟班 · Tier]** 不新增能力线 / 支柱 / 智能层：①采集 → 既有 L1「采集」下的侦察员张骞（`docs/agents/30-zhangqian.md`，职责＝只采集、交付事实不交结论）新增一类数据源；②取舍 → [Newsletter Agent 手册](../sops/2026-10-28-newsletter-agent-playbook-and-rules-v0.1.md) §2A 策划层在「已批准计划 + CRM 进线」两个输入之外加第三个输入「实时情境包」；③对账 → 李白（文案质检）加一项「句子 ↔ 情境包」；④季节 / 目的地 / 节庆规则 → **L2 旅游行业规则（候选，证据仅 CTS 一家）**；⑤路线映射、话题开关、品牌词 → **L4 CTS 配置**；⑥外部连接全部复用现有（见 §18），不新增供应商。
- **[跟班 · 红线]** 红线 1 ✓（没有用「智能层」包装新能力线）；红线 2 ✓（季节表、来源清单、客户名都不进共享代码，进行业手册 / 客户配置）；红线 3 ✓（不直建 L1）；换客户测试：换成另一家新西兰旅游公司，共享部分（情境包字段、保鲜、对账）不用改，只换路线映射与品牌词；换行业测试：旅游 → 地产时「季节 / 气候」整块不适用，但「带日期带来源的事实包 + 保鲜 + 红区」骨架可复用，差异进行业层。
- **[跟班 · 继续吗？]** 归位既有能力、无红线冲突、**本稿不建议登记候选**（理由：目前只有邮件这一个使用方，达不到「第二个使用方」的升级门槛；若社媒 agent 也要同一机制，再升 L1 候选）→ 不停等，继续。
- **开工十问之十（藏经阁）**：「现有 agent 加一个工具能不能做？」→ 能，所以这里没有新 agent 名字。内部称呼「时令线」，PM 可改。

## 2. 要解决的问题：v0.3 为什么「不够好」

1. **任何季节、任何路线收到的都一样**（护照、保险、软件）。客人 3 个月后去的是北京的三月还是桂林的五月，信里看不出来。
2. **没有「此刻」**：没有任何一句是「截至某月某日」的。官方说法、日历上的事，都是写信那天的脑子里有什么就写什么。
3. **没有来源和日期的保鲜管理**：写完一个月后发出去，里面的事实可能已经变了，没有人知道哪句有保质期。
4. **拿不到证据时会硬写**：这一点是 11-04 试跑才暴露的——官网自己的页面互相矛盾，团目录有空字段，官方公告还没出，这些都需要机制处理，而不是写信的人凭印象。

## 3. 流水线：五步，谁做什么，哪些是代码、哪些才是模型

| 步 | 做什么 | 谁 | 代码还是模型（藏经阁第三部） | 输出 | 现状 |
|---|---|---|---|---|---|
| 1 定题 | 这封信发给哪组人、哪个团、哪天发；算离出发几个月；把行程按日期展开成「哪天在哪座城市」 | 邮件策划层（手册 ① 策划） | **全部代码**：日期运算、取整、行程展开 | 信件任务单 | 手册有，代码无；团目录与出发日现成可读 |
| 2 采集 | 读官方页面（出行建议、使馆通知、国务院放假通知）、气候表、新闻源、搜索热度，**只交事实** | 张骞（新数据源） | 抓取与比对＝代码；把乱七八糟的网页读成「候选事实」＝模型（只许提候选） | 情境包（§4） | 张骞现在只采集客户站点与搜索数据；新源为新写 |
| 3 筛选 | 三道关（相关 / 可核 / 品牌安全）+ 红区 + PM 话题开关 + 已讲过账本 | 策划层 | 相关性、红区词表、开关、去重＝**代码**；语义归类＝模型，只出建议 | 入选清单 + 丢弃清单（带原因） | 无 |

## 4. 情境包：每一条事实长什么样

```
fact {
  id                // F01…
  topic             // season | official_advisory | calendar | policy | payment | news | trend
  statement         // 一句话，读到什么写什么
  value             // 数字类放结构化字段
  applies_to        // 哪个团 / 城市 / 日期段
  source_url, source_class   // official | first_party | secondary | derived
  anchor            // 出处原文 ≤ 15 词
  fetched_at, as_of // 我们读到的时间；出处自己标的日期
  ttl_days, recheck_by
  state             // candidate | verified | pm_asserted | expired | absent_confirmed | unreachable
  verified_by       // code | second_source | human（模型读到的东西，模型自己不能标 verified）
  conflicts_with[]  // 与哪些条目矛盾
  safety_class      // green | amber | red
}
```

**状态怎么用（藏经阁第八、十一部）**
- `candidate`：读到了，没独立确认。信里只许用 `verified` 或 `pm_asserted`；v0.4 里所有条目现在都是 candidate，要等独立复核（v0.4 §8）。
- `verified`：由程序（官方原文 + 日期在保鲜期内；或两个独立来源在容差内一致）或人确认。**读它的模型不能自己升级。**
- `pm_asserted`：PM 的决定（例：「免签话题＝关，2026-11-04 先不说」），单独存，覆盖其它一切，带时间和原话。
- `absent_confirmed`：**去官方的地方查过，确实没有**（例：「国务院 2027 年放假通知，2026-11-04 未见」）。这是一条有日期的发现，不是空白。
- `unreachable`：**没读成**（网站打不开、被拦）。**不等于没有**——对应的句子槽位丢掉并出待办，不能写成「没有新消息」。
- `expired`：过了保鲜期，发信前必须刷新或删句。

**保鲜期（初值，候选）**：官方出行建议 7 天；使馆 / 政府政策通知 7 天；放假通知——出之前每次重查；支付 / 软件条款 30 天；新闻 7 天；搜索热度 3 天；气候平均值 365 天；路线 × 日期映射——团目录一变就重算。

## 5. 「判断什么季节去中国」：确定性的部分（全是代码，没有 AI 猜测）

**A. 路线 × 日期展开**：（团、出发日）→ 逐日行程 → 每个停靠城市的日期段。第 N 天 = 出发日 + N − 1。**数据缺口处理（11-04 实测）**：团目录里 Best of China 与 China Panorama 的 `tour_cities` 为空数组，城市只在行程文字里；规则是「字段为空 → 改读行程标题，并出一条『字段为空』待办」，**不许把空当成『没有城市』**。

**B. 城市 × 月份 → 气候行**：查一张带来源和版本的静态表（现为：中国气象局 1991–2020 平均值，经维基百科表格转录；表里没有的城市 → 信里不写这个城市，并出『补表』待办）。v0.4 里用到北京、西安、杭州、上海（3 月、5 月）和成都、昆明、桂林（5 月）。

**C. 冲突检测**：同一项事实有两个来源数字对不上，就不引用并报警。11-04 抓到的例子：官网「最佳旅行时间」页写 3–4 月 15–25 °C，气象局平均值显示 3 月城市日最高只有 13–16 °C、北京和西安清晨 2–4 °C。

**D. 「什么季节最适合去」（给潜在客人的版本，P3 才做；这里只写判断怎么做，不建）**：同样的数据，换一个读者。做法是一张**规则表**，不是 AI 凭感觉：每个（城市，出发月）按「舒适带」打勾——日最高 / 清晨最低在不在舒适范围、降水日多不多、是否撞上国定假日（人多）。再叠三样输入：①今天是几月、新西兰人这个月在搜哪个季节的团（`gtrends`，新西兰地域）；②CTS 在售的出发月份与余位（客户配置 / 销售数据）；③官网「最佳旅行时间」页（CTS 自己的说法，先修好 C 抓到的矛盾）。输出是「这个月该推哪个季节的团、为什么」，模型只负责把结果讲成人话。
示意（阈值只是占位，**「什么算好季节」是产品判断，要 Baker / PM 定一次**）：假设舒适带＝日最高 15–28 °C、清晨最低不低于 5 °C、降水日 ≤ 12 天。按 v0.4 文件 §2 的气候表（F03）：北京 3 月（13 / 2 °C，降水日 3）清晨不达标；北京 5 月（27 / 15 °C，降水日 6）达标；桂林 5 月（28 / 21 °C，降水日 18）降水日不达标。

**E. 月数规则（沿用 v0.3）**：月数＝（出发日 − 发送日）天数 ÷ 30.4 四舍五入；少于 4 周不发；多于 5 个月先等；发送日固定每月第一个周三（12/1 会让 3/18 出发的人被算成 4 个月，发错篇）。

## 6. 「当下是什么时候」：由代码给，不由模型「觉得」

- **时钟**：用系统日期，新西兰时区（复用 `nzDateString`）；日期作为输入传给模型，模型不许凭记忆说「现在是 X 月」。
- **新西兰公共假日**：发送日若落在新西兰公共假日，顺延；表里没有的年份 **fail-closed**，不当成工作日（复用 `nz-public-holidays.ts` 的 `table_missing` 做法）。
- **跑的节奏（以 12/2 为例）**：T-14（11/18）第一次出包 + 出草稿，交 PM；T-2（11/30，周一）**重核**所有标「发前重核」的条目，变了就改信、改「截至」日期；T-0 发送当天早上看一眼红区；发后 T+1 / 3 / 7 沿用手册 NL-07 / 08。
- **「截至某日」只在重核过的情况下写**：信里出现「as at 2 December」，必须所有易变事实都在发送前 48 小时内重查过。

## 7. 「当下的社会热点」：三道关 + 红区 + PM 开关

**来源（第一期只复用现成件，见 §18）**：官方页面（新西兰 SafeTravel、中国驻新西兰使馆 / 总领馆、国务院、文旅部、国家移民管理局）；新闻源（复用 `market-intel` 的 RSS 抓取、去重、事实对照；需新增一份旅游源清单，并把现在写死的 AI 类分类扩一项——小改动，落在 P2）；搜索热度（`gtrends`，新西兰地域）。社交平台抓取（Apify）等 P1 跑出「确实缺」再说，不预先接。

**三道关（缺一不入选）**：①和这位客人的路线、日期有关吗（城市 / 日期 / 季节命中）；②官方或主流来源能核实吗（单一博客不算）；③对品牌安全吗。11-04 试跑：10 条候选 0 条入选，详见 v0.4 §6。

**红区（一律不写进给客人的信；只出「需要你定」待办：什么事 / 可能影响哪个团 / 建议怎么做 / 链接）**：选举与政治、抗议、外交争端与制裁、造成伤亡的灾害、疫情与健康恐慌、恐袭与治安事件、军事。
**黄区（要 PM 对这类话题点一次头，之后记住）**：官方出行建议的级别措辞、签证 / 入境规则、带数字的支付限额、任何「安全」表述。
**绿区（默认可用）**：气候平均值、节庆日期、打包建议、官网已有的软件 / 支付软话。
**PM 话题开关**：存成 `pm_asserted`。现有一条：免签＝关（2026-11-04）。

## 8. 写信约束

- **槽位**：①阶段任务（最多 3 条，5 个月＝证件 / 保险 / 登记；3 个月＝软件与支付；其余月份待定）②季节段（路线 × 日期 × 气候）③「截至某日」段（最多 2 条，来自入选清单）④结尾。全文约 400 词以内（不含网址），每句尽量不超过 30 词，新西兰英语，口气平静（受众偏中老年，PM 10 月定）。11-04 实测：3 月团那封 405 词、5 月团那封 415 词。
- **每个事实句带出处编号**；没有编号的句子只许是建议（比如「带围巾手套」），并在出处表里标 `advice`。
- **不重复**：每位客人收过的事实编号记一本「已讲过账本」；同一条没变就不再讲。每位客人 7 天内群发不超过 2 封（NL-04）。
- **品牌词**：不许倒计时 / 截止 / 只剩几个位 / 价格（NL-17、PM 10-14）；任何价格要带「每人 · 双人同住」（PM 11-03）。

## 9. 谁来验证谁（藏经阁第五部：生产者不审自己）

1. **机器闸（代码）**：每个事实句有编号；编号对应条目是 `verified` 或 `pm_asserted` 且在保鲜期内；`scanOutboundClaims` 扫出的价格 / 日期 / 时长 / 承诺 / 签证 / 名额 / 折扣每一处都对得上一条事实；红线词；链接可打开且标题对。
2. **独立复核（另一个角色，最好另一个模型）**：只拿到信和情境包，自己重新打开每个出处、重算日期和取整、交叉核数字（11-04 已用这个方式审了 v0.4，结果见 v0.4 §8）。
3. **PM 点头**：你看信。
4. **发后回读**：手册 NL-07 / 08（收件人对不对、退订、退信）。
写信的、复核的、批准的是三个角色。

## 15. Phase 0 试跑记录（诚实版）

- **方式**：我（126 号窗口）手工按本设计走了一遍，**没有任何新代码运行**。
- **工具与量**：网上搜索 9 次、读网页 15 次（含 8 次读维基百科气候表——7 个城市页，北京页第一次被截断、带偏移重读；SafeTravel 读了两次）、只读查线上团目录 4 次（表结构 1 次、团与出发日 1 次、两个团的行程 1 次、第三个团的行程 1 次）；没碰客人名单明细，没发任何信。
- **结果**：4 个变体的信 + 情境包 9 条 + 被丢掉的热点 10 条（v0.4）。
- **机器闸真实试用（离线，不联网）**：把现成的文案扫描器 `scanOutboundClaims`（`src/lib/social/outbound-claims.ts`）跑在润色并按审查意见修改后的变体 A（2635 字，含网址）上，共 18 条命中：**真日期 8 条**（11 March、2 December、27 August 2026、4 April 2027，以及行程日期区间里的 16 / 19 / 21 / 24 March——扫描器对「12–16 March」这种区间只认最后一天）、**真时长 2 条**（three months、5 hours），都能对上情境包 F01 / F02 / F04 / F10；**8 条是误报**——把「about 3 days」「about 15 days」这类下雨天数当成了价格（4 条）或时长（4 条），信里其实没有任何价格。气温、电话号码、网址没有被误扫。对设计的影响：①命中只当成「必须对上一条事实」，不能当成「违规」；②气候统计句要加豁免并写进考卷；③日期区间要自己解析；④扫描器有 3000 字上限（润色中间稿含网址时是 3065 字，直接返回「输入太长」；现在 2635 字离上限只差一点），**要按段落扫**。
- **试跑暴露的问题（这就是跑一遍的价值）**：①官网「最佳旅行时间」页与气象局数字、另一官网页互相矛盾；②`tour_cities` 两个团为空；③上一轮「China Panorama 官网没页面」是代号不同（团目录里叫 `grand-tour`）造成的误判；④维基百科北京页太长，首次读取被截断，要带偏移再读；⑤支付限额只有第三方商业指南、没有官方出处；⑥故宫 / 兵马俑规则只有旅游博客；⑦国务院 2027 放假通知今天（去年同一天发布）还没出。 **独立复核（第五部「生产者不审自己」）又挑出写信的人自己没看见的：**⑧官网首页写 Baker 是 Founder，「关于我们」页写创始人是 Lisa Li——写信的人只核了首页就标「官网可溯」，**一个事实至少要看两个页面**；⑨「wet days」按降水 ≥ 0.1 mm 算，新西兰读者习惯 ≥ 1 mm，口径词不能直接借；⑩北京一行气候数字对不上引用页（维基百科换过表），要有第二来源并取保守区间；⑪信里链接的所有官网页顶部都挂着免签横幅，绕过了「免签＝关」的话题开关——开关要连链接落地页一起管；⑫SafeTravel 对中国页的「相关新闻」里有一条中东冲突通知提到燃油短缺可致航班延误或取消，没提中国——这是「红区」走报警通道（不进信、报 PM / 运营）的一个真例子。
- **证明了**：确定性部分算得出（日期、月数、气候）；筛选器管用（10 → 0，且每条有原因）；冲突检测、数据缺口检测、「查无」状态各有一个真例子。
- **没证明**：采集器写成代码后能不能稳定跑；定时；Mailchimp 里的实际发送；信对客人有没有用（要看发后回读）。
