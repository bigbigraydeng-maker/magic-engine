> 在 v0.1 之上：冲突处以本稿为准。吸收子牙+魏征对 v0.1 的审查（经 74 转）。风险级 A。只读 Meta，不改广告、不碰内核授权；**不构成对任何自动花钱的授权。** 标「审查员所述」的是我没独立复核的事实，实现第一步核实。

## 1. 监控的监控（心跳自己死了怎么办）
- **「最近一次样本」新鲜度检查**：心跳自己写一个高水位（最近一次成功采样时间，每账户）；**超过 N 小时没有新样本 → 出「心跳停了」待办（dev 车道）**。小时级任务的阈值 **N = 3 小时**（不用日任务的 26h 口径），写进配置。
- 同 PR 必须登记 `src/lib/cron/registry.ts`（新增写运行记录的定时函数不登记，机器判 A 且与 `render.yaml` 对不上）。审查员所述：登记表已有 7 处与 render.yaml 不一致、`registry.test.ts` 主干 2 条红（台账 `2026-10-21-cron-registry-drift…`）——**实现要等 122 修，或同 PR 处理**。每小时写 `cron_run_logs` 要**先确认保留期**（实现第一步）。

## 2. 读失败的方向（fail 方向写死）
- **读成功但返回空列表不等于「没在投」**：账户有激活系列但读到 0 个广告组 → 算**读失败**（分页/状态过滤可能吃掉）。
- `readList` 中途失败（`complete:false`，`entity-settings.ts` 约 150 行）**一律当读失败**，不用半份数据判断。
- 「连续 2 次才报」会让停止方向静默最长约 2 小时：**钱类（账户状态/超限）改为 1 次读失败就报「读不到」**；其他类仍 2 次。
- **令牌过期（Graph 错误码 190）不当限流退避**，走现有 `meta-token-health-items`（令牌健康）出待办。

## 3. 零消耗判据（单一属主，纯函数）
- 判据纯函数放 **`src/lib/ads-strategy/` 单一属主**（**由心跳 PR 实现**，带版本号与夹具）；**3017 的 3 小时升级读心跳的报警状态，不自己再读 Graph 重判**，并在 3017 标注「判据以心跳实现为准」。
- **扣 Meta 报表延迟**：沿用 D1 的口径（`d1-delivery-stall.ts` 的 `D1_REPORT_LAG_HOURS`，「缺口结束距评估 ≥2h」才下结论），并**只在「有效投放小时」内判**。
- **起算点**：「审核通过且 ACTIVE 之后」（不是创建、不是激活请求时刻）。
- **明确不报的条件（各配夹具）**：审核中；预算极小（预期曝光 < 1）；有投放时段限制；夜间低流量；刚激活（未满 2 个有效小时）。

## 4. 待办出口与车道
- 每个新 kind 必须在 `src/lib/pm-todo/five-kinds.ts` 的 `LANE_OF_KIND` 穷举表给车道（否则类型检查过不了）。建议：**零消耗/拒审 → `dev`；超限 → `decide`；账户状态 → 只有「要 PM 结款」才 `one_click`；「读不到」→ `dev`**（同 `ads_account_status_unreadable`）。
- **与已有 `ads_account_not_active`**（`ads-account-status-items.ts`，24h 门槛、不存标记）**并入同一 kind**，避免同一件事两条待办：心跳的「账户状态变化」只做**更快发现**（小时级写回执），待办仍由该 kind 出。
- **模式对齐现有做法**：「**检查函数写回执，pm-todo 读回执出待办**」（`promo-plan-daily-watch.ts` 头部所述），不是心跳直接写待办。
- **实时性如实写清**：今日待办每天 07:10 才生成，小时级报警 PM 次日才看到；**本稿不承诺实时推送**。若要小时级可见，另设出口（例如广告健康页的「心跳」小卡，读最新回执），**待 PM 决定**；v0.1 里「额外一次站内提醒」**没有对应通道，删除**。
- **防淹没**：每账户每天报警条数上限（初值 5），超出合并成一条「账户 X 有 N 个问题」。

## 5. 去重键与 3017 联动
去重键对**重建后的新对象失效**（新组 ID 变，再零消耗=新键=再报警→循环）。改为：**零消耗类键上提到「账户 + 类型 + 日」**，并带**重建次数闸**（与 3017 联动：同账户当天已有 1 次重建后仍零消耗 → 只出红色待办，不再产生新的零消耗子报警）。「报警解除后可重开」语义：拒审→恢复→再拒算**两次**（各有回执）。

## 6. 隐藏账户口径（对齐 D 系列）
- **不整体排除隐藏账户**：D 系列口径是「hidden 只压数据新鲜度噪音，钱相关照跑」，心跳同理。仅对「**没有在投广告组的隐藏账户**」跳过。
- 旧个人账户仍有开着的系列（日预算合计 115，还款后恢复花钱，审查员/74 所述）：**每天低频读一次，只报「有钱风险」一条**，与 122 的发布前检查分工（122 管发布前，心跳管持续存在的钱风险）。
- **不抽共用过滤函数去动 3012/3018 已合并的 A 级读路径**：本 PR 直接复用 `getClientAdAccounts` 加过滤；若要抽共用函数，**单列一步**。
- **依赖说明**：`hidden_from_ad_health` 列已随 3012 应用到生产并合并；本心跳实现顺序在 3012/3018/3025 之后，无未合并依赖。

## 7. 超限口径
- 账户日上限来源是 **`client_meta_ad_accounts.daily_budget_cap_cents`**（单账户），客户总闸在 **`ad_strategy_configs`**；**不同币种不能直接相加**，按账户币种各自比较。
- **CBO**（预算在 campaign 层，广告组 `daily_budget` 为空）时「广告组花费 > 日预算 ×1.25」**不适用**：用快照 `budget_level` 区分，CBO 改在系列层比。
- **×1.25 先读 2–3 周样本再定阈值**；**初值只出黄色回执，不上待办**。

## 8. 时区与「当日」
统一用**账户时区**（`fetchAccountSettings` 的 `timezone_name`）定义「当日」和去重键的日；**insights 用 `date_preset=today` 还是自算 `time_range` 要写明**：选**自算 `time_range`（账户时区的今天）**，避免 `today` 随接口时区漂移；实现第一步核实 Meta 对该账户 `today` 的口径。

## 9. 表（缩减）
- 采纳子牙建议：**只新增 `ad_heartbeat_alarms`**（`jsonb` 存上次状态、去重键、首次/最近命中、级别、是否解除）；**samples 不另建表**：小时花费用已有 `fetchHourlyAdsetSpend`（`entity-settings.ts:233`）按需读 + `ad_entity_snapshots` 作基线。**如实现中证明 samples 不可替代，须论证后再建**。
- **7 天清理放进心跳函数每轮顺手删**（不另起清理任务）。
- 表必须 `FOR ALL TO service_role USING (true) WITH CHECK (true)`；若建 samples，唯一键 `(账户, 对象, 采样小时)`。**3002 的受保护窄函数不适用心跳表**（心跳写的是监控数据，不是授权证据）。

## 10. 读调用精简
`fetchAdsetSettings` 缺 `delivery`/`created_time`/`start_time`，`fetchAdSettings` 带 `ad_studies` 与 creative 展开——**新增精简字段版**；「复用」的是**连接器与令牌**，不是整函数。**调用数设上限**（每账户每小时 ≤ 6 次），超了自动降频并记回执。

## 11. 回执与上线
- 回执字段补 **`cost`**（0）与 **`no_publish`**（true）；事件发送用 **receipt id 幂等**（同 `promo-plan-daily-watch`）。
- **定时触发默认 dry**；打开「写待办」需显式开关；上线后「**立即运行**」一次并回读。
- `dry_run` 证明力有限：加台账 `verify_by`：**次日核对「当天已采样 ≥ 20 次」**。

## 12. 措辞更正
v0.1 §6 里说「补 D 系列看不到小时级的洞」不准：**D1 本来就用小时拆分**；心跳的价值是**把发现延迟从「次日」降到「约 1 小时」**，并补上 D 系列没有的账户状态/拒审类变化。
