## 0. 给 PM 的一页

**以后来一个 Agent 需求，走五关。每关要交一样「过关凭证」，交不出就不进下一关。**

| 关 | 一句话 | 凭证 |
|---|---|---|
| 1 立项 | 先查清：它要用的数据，正式系统里**最近**到底有几条能用的 | 立项卡 |
| 2 写规则 | 先写清「什么情况做什么、谁批」，再写代码 | 规则表 |
| 3 接零件 | 只用现成零件，不许另造 | 零件对照表 |
| 4 试跑 | 用演示客户真跑一遍，两个审查角色审过 | 试跑留底记录 |
| 5 体检 | 每周看：跑没跑、出了几条、判不了多少、效果验了没 | 并进现有的每周闭环巡检 |

**你在这套流程里只出现在三处**（跟 10-18 闭环骨架定的「真人只在预算、审核、授权三处出现」一致）：

| 处 | 具体是哪几件事 | 多久一次 |
|---|---|---|
| **预算** | 一个 Agent 需求做不做、排第几 | 每个新需求一次 |
| **审核** | ①规则里会花钱、对外发布的条目，归哪一档；②名单上加谁、撤谁、改名 | 写规则时；偶尔 |
| **授权** | ①要新建数据库表；②改仓库总规矩（CLAUDE.md）和合并碰钱 / 安全的改动；③一个 Agent 长期没产出，撤不撤 | 偶尔 |

## 1. 什么算一个 Agent

**名单只有一份：9 月自治计划里你已认可的那份**（`docs/specs/2026-09-24-agent-autonomy-operating-plan-v1.md` §4）。v0.1 另起了一张名册，**撤回**。本流程只在那份名单上**加列**（§7）。

两类，不再分三类：

| 类 | 是什么 | 名单里的位置 |
|---|---|---|
| **运行时 Agent** | 产品里真在跑的代码：会被叫醒、读数据、出判断或动手。**调不调大模型都算**（卫青是纯规则，一样算） | 9-24 §4.1「支柱与运营」 |
| **审查团** | 开发流程里的审查角色，产品里本来就没有代码 | 9-24 §4.2「审查团」+ §4.3 常驻 |

> v0.1 的「引擎人格」那一类没有实际后果（我自己写了「按运行时走」），合并掉。马良、苏东坡既有运行代码又兼审查角色，用名单里的「兼审查」一列标出来，不硬塞进某一类。

**命名规矩**：一个名字只指一样东西（例：「孔明」现在被借去指广告的预检那一步，`kernel/autonomy-envelope.ts:6` 注释——以后不许）。名单是唯一权威，手册、CLAUDE.md、代码注释以名单为准。

## 3. 第 2 关 · 写规则

PM 10-10 拍板「所有支柱 Agent 一律平台—行业—客户三层，先写规则再排代码」（`docs/sops/2026-10-11-seo-agent-playbook-and-rules-v1.0.md:4`）。本关就是把它变成每个 Agent 的必经关。

**规则格式用 SEO 手册 §2.1**（它有「层」这一列，广告手册 §2.1 没有——v0.1 选错了范本，子牙指出）：

`编号` ｜ **条件 → 动作** ｜ **层**（通用 / 行业·候选 / 客户）｜ **谁做**（档 1–4）｜ **证据来源**（哪张表 / 哪个口径）｜ **样本门槛** ｜ **代码**（已有 = 路径；缺 = 「尚无代码」；写好没人调 = 「零调用方」）

- 每个数字带来源和样本量；没有证据写「待验证」，**不许编阈值**。

**授权四档是平台规则；判档原则留在各支柱自己的手册里。**

| 档 | 意思 |
|---|---|
| 1 | 系统自动：只读、只记录、只出建议、只发待办 |
| 2 | 出建议，任一授权的人点头才执行 |
| 3 | 必须 PM 本人在执行这个动作的对话里点名说才算 |
| 4 | 绝不自动，连 PM 点头也不开自动通道 |

> v0.1 把广告的判档原则（「只让花费变少」「会重置学习期」）当成了平台规则——那是广告专用的。SEO 手册 §2.2（`:60-75`）有自己的判档原则，还有「受控自动」这个例外。各支柱各写各的判档原则，**四档本身统一**。

**规则表改动算 A 级**：支柱手册正文是规则书，合并门槛一律 A 级，子牙签字 + PM 合；学习任务只写候选区（`inbox.md`，B 级可自动合），由子牙每周挑站得住的升进正文（`docs/specs/2026-09-28-pillar-agents-capability-memory-kernel-v0.1.md` §3.4）。

## 4. 第 3 关 · 接零件

| 零件 | 必须接的现成件 | 关键约束（每条都是查实的坑） |
|---|---|---|
| **闹钟** | 定时型：`src/app/api/cron/*` + `render.yaml`，或 Inngest 定时；都要登记进 `src/lib/cron/registry.ts` 的 `CRON_REGISTRY`（`:104`），故意不排班的写进 `UNSCHEDULED_CRON_ROUTES`（`:412`）。事件型：Inngest，追加进 `src/lib/inngest/functions/index.ts` 的 `cloudFunctions` | 函数编号必须以 `cloud-` 开头（`index.ts:104-108`）；事件只当叫醒铃，只带 `client_id`，消费者回库读当前值（`ads-events.ts:1-25`）；幂等编号由各域自己生成（如 `ads-events.ts:23`），`workflows/inngest-event.ts` 只要求有 `id`；`concurrency: { limit: 1, key: client_id }`；依赖在 handler 内创建；`step.sleep` 不许 `setTimeout`（PITFALLS F10）；**新函数上线后去后台对 `/api/inngest` 手动 Sync 一次**（`docs/STATE.md:174`）；闹钟避开周五、周六，不用 7 的倍数天（9-24 §4.1 末） |
| **眼睛** | 各域数据脊柱表 + 完整性判定 | 读失败 ≠ 没有；截断 ≠ 完整；判不了标「判不了」并写原因码，不许当 0 / false；**数据不全的轮次只观察不执行，并留痕**（9-28 §4.4） |

| 场景 | 现成的词 | 出处 |
|---|---|---|
| 单次核对 | pass / pending / not_measured | `seo-weekly-list/verify.ts:20` |

## 6. 第 5 关 · 体检与改进

**不另起巡检。** 每个 Agent 都是 10-18 闭环骨架（`docs/specs/2026-10-18-me-closed-loop-skeleton-min-cost.md`）里**某条线某个环节的执行者**。体检结果**回填骨架的闭环登记表**，只留**一套**每周巡检（骨架通用规则第 3 条：复用 `calendar-closure-audit` 的模式）。

**每次运行留什么记录**——**不新造回执表**，用现成的 `cron_run_logs`：

| 要记的 | 放哪 |
|---|---|
| 处理了几条 | 正式列 `processed`（体检已经在读，`cron/health.ts:353`） |
| 失败几条 | 正式列 `failed_count`，**必须经 `finish({ failed })` 传进去**——每日失败邮件看的是 `failed_count > 0 \|\| status === 'failed'`（`digest-cells.ts:72-74`） |
| 产出几条、判不了几条、原因码、花了多少钱 | `summary` 里**统一键名**：`agent`、`produced`、`undeterminable`、`reasons`、`cost_usd` |
| 事件型 Agent | 也能写这张表：`cronRunIdFromInngestRun`（`run-logger.ts:196-208`） |

- ⚠️ `processed = 0` 在不同任务里意思不一样（`health.ts:430` 已警告），所以体检看「产出」时读 `summary.produced`，不读 `processed`。
- ⚠️ 这张表按**任务名**记，不按 Agent 名记 → 名单要加一列「任务名」（§7）。
- ⚠️ 这张表 180 天后硬删，需要长期证据的另放该域现成回执表；没有现成的、确实要新表的，**先问 PM**。
- 重跑以首次为准，不覆盖（记忆 `feedback-receipt-overwritten-shows-last-attempt-not-first`）。
- 会动手的 Agent，动作本身另有内核自带的 `action_runs` 状态机。

**体检四问**：

| 问 | 从哪读 | 红灯 |
|---|---|---|
