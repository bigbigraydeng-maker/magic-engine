# 「把客户系统里的客人进展告诉 Meta」设计 · v0.2 · 只设计，未写代码 · 2026-10-29

> **一句话**：让 Meta 照着「真的报价 / 付钱的客人」去找人，而不是照着「填过表的人」。两条路：
> **A. 相似受众换种子**（按阶段挑客人名单定期同步给 Meta）；**B. 客人阶段回传**（Meta 官方「转化线索」优化）。
> **实测结论：两条路现在都缺可靠信号；最该先做、最便宜的一步，是让人确认 AI 判出来的「已报价」（§5）。**
>
> **风险级**：本文档 C；实现全部 **A**（把客人信息哈希后发给 Meta、影响广告学习，发出去撤不回）；A1 只算人数不上传可按 B。
> **本稿不构成任何对外发送、上传名单、改在投广告的授权。** 每一步首次对外都要 PM 本人点头。
> v0.1 → v0.2：吸收子牙、魏征两审（均「改后放行」）并补实测数字，见 §11。v0.1 未提交，已由本稿替代。

---

## 0. 给 PM 的三句话

1. **Meta 现在学的是「谁会填表」，不是「谁会买」。** 在投的相似受众，种子是「留过资料 + 订阅邮件的人」；回传通道只发成交、每条要人批。
2. **Meta 已经把「按客人质量优化」锁在客户系统回传后面**：官方说 2026 年 4 月起新建广告系列不接客户系统回传就选不了「优质线索」这个目标，8 月起老系列也受影响（[About performance goals for lead ads](https://www.facebook.com/business/help/782657799338685)）。
3. **但我们手上的「优质」信号现在不可靠**：系统里所有「已报价」记录 84 条，**75 条是 AI 自己判的、只有 9 条是人改的**；付过钱的只有约 36 人。拿这些去训练 Meta 或当种子，量不够、也不够准。先让人确认 AI 判的「已报价」，两条路才有料。

## 1. 为什么做（PM 原话，2026-10-29）

> 「ME 当前的 CRM 里的 enquiry 状态，是否可以通过 CAPI 回传给 Meta，从而自动触发 lookalike，然后找到更多精准客户？」→ PM 回「开」。

## 2. 现状实测（2026-10-29，只读，未改任何东西）

### 2.1 已有的能力（复用，不另写）

| 已有 | 在哪 | 本设计怎么用 |
|---|---|---|
| Meta 回传连接器 | `src/lib/meta/capi/writer.ts` | 已发 `Purchase`（定金 = 成交）、`BalancePaid`、`Lead`，匹配键含哈希邮箱 / 电话 / 姓名、私信身份、表单线索编号。注释写明「转化线索」那套没做。B 要扩：来源需支持「客户系统」（`destination-writer.ts` 目前只允许邮件 / 私信两种） |
| 回传防重三道闸 | `src/lib/conversions/writeback-service.ts` | 唯一约束、按状态条件更新、发之前先占位——B 照搬 |
| 一次授权 + 自动审 + 熔断 | `ai-auto-review.ts`、`ai-auto-review-circuit-breaker.ts` | B 的授权模型直接复用，不新造 |
| **客人名单导出** | `src/lib/conversions/audience-export.ts`（名单 A 口径） | 已定四条：只要游客、**只要广告来源（算有同意）**、排除拒联、必须有邮箱或电话。A1 在它上面加「按阶段筛」 |
| 阶段流水 | `contact_stage_events`，`changed_by` 记谁改的（`src/lib/crm/actors.ts`） | 用它区分人改 / AI 改 |
| 每日回传流水线 | `src/lib/inngest/functions/conversion-daily-pipeline.ts` | B 挂进去当新的一段，不另开定时任务 |
| 成交回传设计 | `docs/specs/2026-09-07-me-conversion-truth-uplink-spec.md` | 「7 天硬顶 / 服务端不去重 / 没有删除」三条官方事实同样约束本设计 |

### 2.2 两个广告账户里现有的受众

- 主账户：在投的只有「类似受众 1% · 填过表单 · 90 天」；其余相似受众都没在投。
- 官方账户：**「客人名单 · fb+newsletter · 2026-09-07」**（手工上传）及其 1% 相似受众（在投，约 3.5–4.2 万人）；**「排除 · 已付定金+不再联系+即将出行 · 2026-10-20」**（手工上传，在用）。

→ 从客户系统导名单上传已手工做过两次，没有自动化；在投相似受众的种子是上千人的「留过资料的人」。

### 2.3 客人阶段实测（CTS）

- **表单进线量**（按月，人）：7 月 259、8 月 127、9 月 292、10 月 97（中间停投两周）。7/25–9/30 平均约 197 条/月。**只有花钱多的月份够 Meta 要求的每月 200 条，不是「接近」。**
- **28 天内走到「已报价」**（7/25–9/30 的 440 条表单进线，都已满 28 天）：22 条，**5.0%**，落在 Meta 要求的 1%–40% 区间；每月约 10 条。
- **14 天内离开「已联系」**：32 条，7%。
- **谁改的阶段**（全部历史）：「已报价」84 次——**AI 75 次、人 9 次**；「即将出行」AI 11、人 1；「已付定金」人 16、「已付全款」人 5、「已出行归来」人 14。
- **付过钱的人**（定金 / 全款 / 即将出行 / 已出行）约 36–42 人，全部由人或订单确认。

### 2.4 Meta 官方门槛（2026-10-29 查 Meta 官方文档）

- 「转化线索」适合条件：即时表单广告；每个事件带 15–17 位线索编号（我们已存）；**每月至少约 200 条线索**；**至少每天上传一次**；优化的阶段**在线索产生后 28 天内发生**，**转化率 1%–40%**；集成约 3–4 周，之后学习期 2–4 周。来源：[Conversions API for CRM integration](https://developers.facebook.com/docs/marketing-api/conversions-api/conversion-leads-integration)。
- 改客人名单受众「不会重置在投广告的学习期」，但会同步影响用它的广告组和相似受众：[Edit a customer list custom audience](https://www.facebook.com/business/help/403733729689975)。
- 名单可带「客人价值」列做按价值的相似受众：[Create a customer value custom audience](https://www.facebook.com/business/help/185705781836755)。
- 相似受众种子人数下限：这次查到的文档没写，常见说法「单一国家至少 100 人」，**实现前核实原文**。

## 3. 方案 A：相似受众换种子 + 名单自动同步

### 3.1 做什么

1. 在 `audience-export.ts` 名单 A 口径上加「按阶段筛」，生成三份名单，**哈希后**同步到 Meta 客人名单受众：
   - **买家**：人确认的「已付定金 / 已付全款 / 即将出行 / 已出行归来」；
   - **高意向**：买家 + **人确认的**「已报价」（AI 判的不算，见 §5）；
   - **排除**：拒联、不感兴趣、非咨询、已付定金之后的人（列清 `stage_key`，不按营销动作或排序号推断）。
2. 阶段映射放在客户配置 `clients.leads_config`，按 `stage_key` 逐个列出，不改表结构；**不用 `marketing_action` 推断**（CTS 的「已报价」和「已联系」都是培育，「已付定金」和「不感兴趣」都是不再营销，推断会挑错）。
3. 只同步到**新建的**受众，每天增删，并回读 Meta 上的人数与应有人数对账。

### 3.2 硬停条件

- **种子匹配后单一国家不足 100 人（门槛待核实原文）就不建相似受众**，回执写「人数不够」。按现状：人确认的买家约 36 人、人确认的已报价 9 人，**现在不够**；AI 判的 75 条确认后才可能够。
- **换种子不一定比现在好**：现在的种子是上千人的留资名单，量大但不准；换成几十人的买家名单，准但可能太小。必须用对照测试比（§6），不能默认更好。

### 3.3 边界

- 「哈希」不是「匿名」：Meta 正是靠这串值认出这个人是谁。名单只发哈希后的邮箱 / 电话 / 姓名，明文只在系统内部。
- **接管现在在用的两份手工名单 = 每天自动改在投广告的受众**，需要 PM 单独授权「同意每天自动更新这几个在投受众」；没有这条授权，只写新受众。
- 新建相似受众、把它挂到广告组 = 改在投广告，每次 PM 本人授权；本模块不向内核提交任何广告动作。

## 4. 方案 B：客人阶段回传（Meta「转化线索」）

### 4.1 做什么

- 每天一次（挂在 `conversion-daily-pipeline` 里），把**表单线索**的阶段变化按「转化线索」格式发给官方数据集：带线索编号、来源标为客户系统、事件名用**自定义阶段名**（不用标准 `Lead`，避免和官网镜像重复计数）。
- **只认人改的阶段**：`changed_by` 为 `ai:` 或 `system:` 开头的一律跳过并记原因；AI 判的要经 §5 的人工确认后才算。
- 阶段映射同 §3.1，放客户配置；CTS 初稿：人确认的已报价 → 合格（优化目标）；不感兴趣 / 非咨询 → 不合格。

### 4.2 防重复（撤不回，必须一次对）

- 新建**发送记录表**，唯一键 =（客户、线索编号、Meta 漏斗阶段）：**每条线索每个阶段终身只发一次**，阶段来回改（报价 → 已联系 → 报价）、AI 撤回都不会重发。改表结构 → **留给 Ray 亲手合**。
- 照搬回传三道闸：唯一约束、按状态条件更新、发之前先占位。
- 发之前核对线索编号属于官方账户主页下的表单，不属于就拒发。
- 事件发生超过 7 天 Meta 整批拒收：积压超过 6 天的直接标「过期不发」并报警。

### 4.3 成交怎么处理（二选一，不并存）

现在的 `Purchase` 已经在按「收到定金」发成交。实现第一步先核实 Meta「转化线索」是否要求成交阶段也走客户系统这条流：
- 不要求 → B 只发「合格 / 不合格」，成交仍走现有 `Purchase`；
- 要求 → 成交改由客户系统这条流发，现有 `Purchase` 对表单线索停发。**绝不两边都发**（会把一笔成交记成两笔）。

### 4.4 授权与熔断

- 以 2026-10-21 台账卡「CTS 自动审核在发送闸上线前保持关闭」为前置；复用现有「一次授权 + 自动审 + 熔断」机制，**PM 对「某客户开启阶段回传」本人授权一次**。
- 熔断（任一触发即停发、出待办）：单日条数超过近 14 天日均 3 倍；同一线索当天出现阶段倒退；线索编号不属于官方表单；回执失败率超过 10%。
- 回传令牌换成系统用户令牌（现在是 PM 个人的用户令牌，过期会让每日自动发静默失败）。

### 4.5 投放侧

回传通过 Meta 数据验证后，新建一个「优质线索」广告组，与现有「留资数」广告组用 Meta 自带对照测试比 3–4 周。开测试 = 改在投广告，PM 本人授权。

## 5. 最该先做的一步：让人确认 AI 判出来的「已报价」

- 现状：AI 读通话 / 邮件 / 私信会直接把客人改成「已报价」（`src/lib/crm/stage-from-conversation.ts`，身份 `ai:conversation-read`），没有人确认。全部 84 条「已报价」里 75 条是这样来的。
- 做法：今日待办里给销售一个「这些客人 AI 判成已报价，对吗？」的一键确认 / 驳回；确认后写一条人确认的流水。**不改 AI 的判断逻辑，只加确认。**
- 为什么最划算：一次确认同时喂饱三件事——相似受众的种子（§3）、阶段回传（§4）、广告机会挖掘里「哪条广告带来的客人更会成交」。
- 归 CRM 那条线做（台账卡 `2026-10-29-crm-stage-hygiene-for-meta-signal`）；验收口径改为：**每月「人确认的已报价」绝对条数**（目标 ≥ 10，接近现在 AI 判的量），并每月抽 10 条核对有没有标错。不用「离开已联系的比例」——改成「无下文」也算离开，凑数没意义。

## 6. 怎么验证有没有用（Check）

- A：新旧两个相似受众在同一系列里用 Meta 对照测试比**每条「人确认的已报价」成本**。
- B：「优质线索」组 vs「留资数」组，3–4 周，同一指标；样本按点击数判够不够（手册 §十九）。
- 数据：广告机会挖掘的 `ad_breakdown_stats` + 阶段流水（连 `contacts` 取表单线索编号，只算人确认的）。
- 信号不够时结论记「证据不足」，不判成功或失败。

## 7. 隐私：PM / CTS 要分别确认的三种来源

| 来源 | 现有依据 | 要确认什么 |
|---|---|---|
| 广告表单进线 | 表单提交前展示了披露（现有成交回传的依据；`audience-export.ts` 也只认这一类） | 披露文字是否覆盖「用于广告受众与优化」 |
| 邮件订阅者 | 只同意过收邮件 | 能否进名单（现在官方账户那份手工名单已含订阅者） |
| 老客人（非广告来源） | 没看过表单披露 | 能否进名单 |
| 排除名单里的拒联客人 | — | 上传排除名单本身也是把资料交给 Meta，是否可接受 |

另：CTS 是否接受 Meta 客人名单条款；新西兰《隐私法》第 10、11 条与澳洲《隐私法》第 6、7 条关于「用于其他目的 / 披露给第三方」的要求由 PM 与 CTS 判断，本设计不替他们下结论。**回执、日志、待办里不许出现原始或哈希后的邮箱 / 电话 / 姓名**，只记联系人编号和计数。

## 8. 要 PM 决定的

1. **§7 的三种来源**分别能不能用（可先只用广告表单进线，最保守）。
2. **阶段回传的授权方式**：按客户一次授权 + 自动发 + 熔断（§4.4），还是维持逐条人批。
3. **先后**：建议 **§5 人工确认 → A1 演练算人数 → 人数够了再 A2/A3 → 信号够了再 B**。

## 9. 分阶段与验收（每阶段交付前当场试跑，默认演练不发）

| 阶段 | 内容 | 风险级 | 验收 |
|---|---|---|---|
| 0 | AI 判「已报价」的人工确认（CRM 线） | B | 每月人确认的已报价 ≥ 10，抽查标错率可接受 |
| A1 | 三份名单按阶段挑人 + 哈希（演练：只算人数，不上传） | B | 三份名单人数与客户系统按 `stage_key` 计数一致；AI 判的不进 |
| A2 | 首次上传 + 每日增删 + 回读对账 | A，PM 授权 | Meta 回读人数 / 匹配率；增删按天生效 |
| A3 | 相似受众 + 对照测试 | A，PM 授权 | 匹配后不足门槛就停；§6 指标 |
| B1 | 发送记录表 + 事件生成（演练：只生成不发） | A（改表结构，Ray 亲手合） | 事件格式与 Meta 文档逐项对齐；阶段来回改不重复生成；AI 改的被跳过 |
| B2 | 正式回传 + Meta 数据验证 | A，PM 授权 | Meta 事件管理看到阶段事件与匹配率；回执每日完整；熔断可触发 |
| B3 | 「优质线索」对照测试 | A，PM 授权 | §6 |

每一段的回执：业务事件名（如 `crm_signal.audience_synced`、`crm_signal.stage_events_sent`）、客户、来源记录编号、状态、花费影响、`no_publish`、授权记录编号、Meta 回执；定时部分挂进现有流水线，不另开任务。

## 10. 平台 / 行业 / 客户三层 与 层级判定

| 层 | 装什么 |
|---|---|
| 平台 | 按阶段挑人、哈希、每日增删与对账、阶段回传格式、发送记录与熔断（扩展现有 Meta 回传连接器与名单导出） |
| 行业 | 「哪个阶段算优质」的默认建议写进行业手册（旅游 = 已报价；物流 = 已报价或已下单；地产 = 已看房），**不写进共享代码** |
| 客户 | `clients.leads_config` 里的阶段映射、开关、授权记录 |

层级（Inline）：**L3 连接器扩展**，挂在「广告」支柱下；用 Meta 自带能力（相似受众、转化线索），**Connect 不 Build**；不新增支柱、不造找人算法；不需登记平台候选。
