## 0. 一句话结论

**不建新引擎，也不新建定时读取函数。** 把已经在的社媒零件按 **Inspect → Measure → Prescribe → Act → Check → Tune** 接成一条有目标的链，只补三处缺口：**目标契约、读回链接通并补齐（Reel 状态、Story、助推标记）、验证结果回流下一轮处方**。

和广告闭环的**最大区别**（决定了本稿比广告稿保守）：
1. Facebook **观看数 / 触达读不到**（缺洞察权限），Check 靠互动数 + 私信数，样本小、结论慢，**很长一段时间里大概率是「样本不足」，本稿如实面对而不掩盖**；
2. 广告动作可撤回，**发出去的帖子撤不回**（只能下架，下架也是对外动作）；
3. 因此 v1 **不开「信封内自动发布」**，沿用「PM 授权一周的包、授权绑内容指纹」；是否并入 Kernel 放到 WP5 由子牙裁。

## 3. 逐段设计

### 3.1 Inspect（发现）—— 从 master brief 开始

每个客户每天一次，**固定先读两样**，再读运行数据：

| 顺序 | 读什么 | 用来干什么 | 规则 |
|---|---|---|---|
| **I0** | 客户 **master brief**（方向、受众、支柱配比、品牌 VI）+ **官网当下内容** | 校准客户层：发什么、不能说什么、受众是谁 | brief 只给方向，**不当事实来源**；事实以官网为准，冲突选官网；官网读取**复用现有 Site Analyzer 封装**，不另写；读不到就标缺口，不猜 |
| **I1** | 目标契约（`goals` 一行）+ 名额配置 + 素材池 | 知道「要什么、能发多少、能用什么」| 无 active goal → 只巡察不出处方 |
| **I2** | 运行数据：近期帖子互动 / 私信、评论分类、页面指标、连接状态、未接入平台状态 | 发现问题 | 「读不到」与「0」永远分开 |
| **I3** | 机会信号（§3.1.1）| 发现机会 | 每条带 evidence / sample / not_comparable，与广告 `Diagnosis` 同形 |

#### 3.1.1 机会发现（纯函数，第一版只做有数据支撑的几条）
| 码 | 判据 | 输出处方候选 |
|---|---|---|
| **SO1 名额缺口** | 本周已排候选数 < 名额 | `social.plan_week` |
| **SO2 事实沉睡** | 事实库里已核实、近 N 天（客户配置）没用过的事实 | `social.make_post` / `social.make_story` |
| **SO3 评论 / 私信高频问** | 同类问题连续出现 ≥ 阈值（客户配置）| 选题建议。**不自动回复** |
| **SO4 真实素材未用** | 素材池 approved 的客户实拍久未被使用 | `social.make_reel` / `social.make_post` |
| **SO5 平台缺位** | 客户有该平台账号但 ME 未接入 | 只出一条待办 |

「哪种开头 / 栏目更好」不在第一版：要等标签与单条表现凑够样本（§3.5 门槛表）。

### 3.2 Measure（量）—— 接通并补齐现有读回链，**不新建定时函数**

- **M1 读取时点**：**保留主干的 T+4 / T+72**（共享代码里四处写死：`daily-plan-publish.ts`、`daily-plan-post-measurement.ts` 的 `MeasureDueSchema`、`post-measurement-store.ts`、`factory-reel-measurement-adapter.ts`；`social-post-cohort.ts` 只读 T+72）。要加时点只能**追加**，且列出全部要改的位置后按 A 级走；**不替换**，否则现有复盘读到空集。
- **M2 补齐三处断点（WP1 的内容）**：①让 Reel 的「已发布」状态能被读回链收到；②给 Story-lite 补一个能挂读回记录的发布动作（现状 Story 不写发布动作行，读回记录连一行都插不进去）；③助推标记（M4）。三者都动「已有读回函数与发布动作的写入」，A 级。
- **M3 回执落点（定论，不再留条件句）**：`social_post_measurement_receipts` 只放**原始读数**（`action_id` 必填且绑发布动作；`status` 只有 `ok/partial/unmeasurable`；`values` 的每个键会被转成数字写进指标表，**不许往里塞判定结果或标记**；同窗口读数内容变了会被拒绝重写）。**C1/C2/C3 判定与助推标记**由 WP1 设计阶段与子牙一起选落点：默认 `flywheel_outcomes`；放不下才**新建表（A 级，先问 PM）**。判定回执**只追加、不覆盖**，保留第一次结果（防「回执被重跑覆盖」）。
- **M4 付费助推隔离**：能识别的（工厂建广告，对应关系已在 `ads/creative-link.ts`）标 `boosted`；**识别不了的**（员工在 Business Suite 里手动加推）——只要该客户在该帖发出后窗口内有广告花费，一律标 `boost_unknown`，**不当作「没被助推」**。`boosted` 与 `boost_unknown` 都不进自然效果对比。
- **M5 口径只承诺拿得到的**：点赞 / 表情、评论、分享；Story 用「客户配置的『邀请私信』槽位发出后 X 小时内新开私信会话数」（**客户层示例：CTS 为 20:00 那条、12 小时**，2026-10-14 定，需连续两周再下结论）；观看 / 完播等在洞察权限未开前一律 `not_readable`，不进验收。
- **M6 归因**：首评链接带追踪后缀（沿用**客户层** utm 约定，CTS 示例见日常 Agent 设计稿），点击与留资走既有 CRM / 归因。按单条内容拆分的点击能力地图标「未验证」。
- **M7 Check 只覆盖系统发的帖子**：员工手动发的帖子（CTS 图文目前基本如此）没有发布动作，**不进 C2**，目标进度（C3）另标「含手动发布」口径说明，避免分子分母对不上。
- **M8 「读数不全」的定义**：只算**本来应该读得到**的指标缺失；观看数这类永远读不到的不算缺，否则会天天冻结。

### 3.3 Prescribe（开处方）

**处方 = 封闭词表里的一条，固定格式记录。记录与广告 `action_runs` 同形**（动作键 / 防重复键含日期 + 内容 id + 参数 hash / 证据 / why），不接 Kernel，但给 WP5 留接口，避免以后回头补历史。

| 词 | 含义 | 是否对外 | 谁批 |
|---|---|---|---|
| `social.plan_week` | 写一周候选 | 否（草稿）| 苏东坡签字 |
| `social.make_reel` | 向视频工厂下工单（带 `platform` 与创意标签）| 否 | 工厂审查 + PM 点通过 |
| `social.make_post` / `social.make_story` | 做图文 / Story 草稿 | 否 | 苏东坡（字）+ 马良（新增图）|
| `social.reslot` | 在客户配置内微调时段（±30 分钟，每期一个槽位）| 否（改排期）| 复盘 R1：第一次只建议，PM 看过后同类才自动 |
| `social.swap_asset` | 换同角色内已审图 | 否 | agent 自己 |
| `social.takedown` | 下架已发内容（5A）| **是** | 设计已批，**实现未开**，不在 v1；是否先注册为 Kernel「必须人工批准」动作，WP5 开工前单独裁 |
| `social.escalate_to_pm` | 三件套待办（what / how / href）| — | — |

**授权边界（硬规定）**：`social.reslot` 与 `social.swap_asset` **只能作用于授权之前的草稿**。授权绑内容指纹（含发布时间与图的哈希），授权后要改必须**作废原授权、请 PM 重新授权**；agent **永远不能重算指纹、不能放宽指纹**。

每条处方必带：`why`、`not_this_because`、`expected_impact`、`confidence`、`verification_definition`。**读上一轮验证结果**依赖 Check 产出，放在 WP4（见 §7）。**Day-0 默认处方**来自冷启动 v0.1，数量与钟点是「建议 / 候选」，由 PM 在目标契约里确认。

### 3.4 Act（做）—— 受控执行，v1 不改任何现有发布开关

```
处方 → 生产（视频工厂 / 图文 / Story 草稿）
     → 发前检查（硬规则 + 苏东坡 + 马良 + 值不值得发 + 事实出处 + 价格闸）
     → PM 授权一周的包（授权绑内容指纹，改了就拦）
     → 现有发布路径在发送窗口内发出 → 首评写入
     → 发布回执（授权人、指纹、平台返回 id、发布时间、是否被助推）
```
- **四条现有发布路径保持原样**（§2 A 行），v1 **不并入**新的串行队列，**不改**其开关；每日计划图文自动发布**仍默认只演练**，本稿不碰它的开关。
- **熔断必须真正能停发**：C1 判定 `mismatch`（校准完成后，见 §3.5）时，**撤销该包尚未发出条目的授权**（参照日常 Agent 设计稿 5.4 档一），而不是只停出新处方——Story / Post 的发布扫描自己跑，不经过新队列，只有撤授权才拦得住。
- **新增只有一处**：把各处回执**归一**成同一种「发布回执」读法（读取函数，不新建表）。草稿永远不记成「已发布」。
- fail-closed：没有授权事件和平台回执，不判完成。

### 3.5 Check（查）—— 三个独立判定，不合成一个分数

| 判定 | 看什么 | 方法 | 结果 |
|---|---|---|---|
| **C1 保真** | 发出去的 = 批准的 | 下载平台返回的图 / 视频帧与批准原件比对；文字、首评链接核对 | `match` / `mismatch`。**阈值未校准**：Facebook 会重压缩、缩放，视频还要抽帧；**先拿 CTS 历史帖校准，阈值标「候选」，校准前 mismatch 只开待办、不撤授权** |
| **C2 表现** | 这条内容在同类里怎么样 | **扩展现有 `social-post-cohort` / `social-post-evaluator`**（同客户同期对照），不另写第二套比法；「同类」的角色分类来自行业剧本枚举 | `above` / `within` / `below` / `insufficient_sample` / `not_comparable` |
| **C3 目标节奏** | 对 PM 目标走到哪了 | **复用广告 `goal-pace` 的线性节奏部分**（`null ≠ 0`），抽成两个支柱共用的模块；社媒另加「名额可达性」判断 | `on_track / behind / unreachable_within_quota / insufficient_sample` |

**样本门槛（全稿唯一一张，每条标出处）**
| 用途 | 门槛 | 出处 |
|---|---|---|
| 现有复盘方向提示 | 每组 ≥3 | 主干 `social-post-evaluator`（`minSampleSize: 3`）|
| 创意标签 × 表现出「候选结论」 | 每组 ≥5 | 日常 Agent 设计稿 SO-09 |
| 调发布时段（R1）| 连续 2 期、每组每期 ≥10 | 日常 Agent 设计稿 7.2 |
| 其余（如事件冻结天数、30 天冻结）| 〔候选〕无社媒证据，沿用广告数字作占位 | 广告 G8 |

- **`not_comparable`**：被助推 / `boost_unknown`；窗口内客户做过非 ME 改动；节假日或活动周（客户配置）；读不全（按 M8 定义）；手动发布的帖子。
- **「请示 PM」的触发**：①目标 `unreachable_within_quota`；②素材池耗尽；③熔断。其中①依赖每条帖子平均带来多少私信，**小样本下算不出来时它不会响——这是已知局限，日报如实写「样本不足，无法判断是否完得成」**，不假装在监控。
- **诚实预期**：按现有发布量，C2 / C3 在 CTS 上很可能**数月都只给「样本不足」**；这条链的前期价值是**把数据管道接通、让数据开始积累**，不是马上出结论。
- 每次判定落回执：request id / client id / 内容 id / 平台 / 读取时点 / 状态 / 助推标记 / 创建时间；只追加不覆盖。

### 3.6 Tune（调）
