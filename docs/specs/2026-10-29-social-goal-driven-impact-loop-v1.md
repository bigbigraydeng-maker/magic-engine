## 0. 一句话结论

**不建新引擎，也不新建定时读取函数。** 把已有社媒零件按 **Inspect → Measure → Prescribe → Act → Check → Tune** 接成一条有目标的链，只补四处缺口：**目标契约、读回链补齐（Reel 状态、Story、助推标记）、判定结果的专用落点、发布暂停标记**，再把验证结果回流下一轮处方。

和广告闭环的**最大区别**（决定了本稿比广告稿保守）：
1. Facebook **观看数 / 触达读不到**（缺洞察权限），Check 靠互动数 + 私信数，样本小、结论慢，**很长一段时间里大概率是「样本不足」，本稿如实面对**；
2. 广告动作可撤回，**发出去的帖子撤不回**（只能下架，下架也是对外动作）；
3. 因此 v1 **不开「信封内自动发布」**，沿用「PM 授权一周的包、授权绑内容指纹」；是否并入 Kernel 放到 WP5 由子牙裁。

**素材池**：「能不能用于价格 / 产品承诺」**只看素材的来源记录**（是否客户自己上传的实拍），**不看任何人或 agent 打的「已批准」标记**——状态字段当授权会漏闸（历史教训）。**沿用价格闸现有的来源规则**（`assets/provenance.ts`）：只有「客户实拍（已确认）」`client_verified` 与「FDE 自己拍的」`fde_shot` 能撑起真实价格；前者只能通过现有确认入口升级，并记下谁、何时。**agent 与任何系统模块都不能把来源写成这两种**。WP0 只核查该确认入口与素材页上能改来源的权限，**不改价格闸判定本身**。入库时系统另记上传人、时间、原始出处凭据作审计，不替代人工确认。马良审的是**画面质量与真实性**，结论只作审查记录，不改变来源。PM 只看结果，不逐条批。

**不变的审批矩阵**：沿用日常 Agent 设计稿 3.1；「授权自动发布」永远只有管理员本人能点。

### 3.2 Measure（量）—— 接通并补齐现有读回链，**不新建定时函数**

- **M1 读取时点**：**保留主干的 T+4 / T+72**（共享代码里四处写死：`daily-plan-publish.ts`、`daily-plan-post-measurement.ts` 的 `MeasureDueSchema`、`post-measurement-store.ts`、`factory-reel-measurement-adapter.ts`；`social-post-cohort.ts` 只读 T+72）。加时点只能**追加**并按 A 级列出全部改动位置；**不替换**。
- **M2 补齐三处断点（WP1）**：①Reel「已发布」状态能被读回链收到；②**Story**：**不套用每日计划的发布事件**（该事件格式要求推广活动编号和计划编号，Story 没有；读数函数读点赞 / 评论 / 分享，也读不了私信）。照 Reel 的做法**直接写发布动作行**，且用**单独的动作类型 `social.publish_story` 与它自己的防重复唯一键**（现有 S2 会同时读 `story_items` 和 `social.publish_post` 动作行，Story 若也记成后者会被算两次、还可能当成图文）；另写**单独的私信会话读取函数**，明确不走现有读数链，其读数存放在 M3 的新表里（`story_dm_count` 一类记录），**不进回执表**；③助推标记（M4）。
- **M3 回执落点（定论）**：
  - `social_post_measurement_receipts` **只放原始读数**（`action_id` 必填且绑发布动作；`status` 只有 `ok/partial/unmeasurable`；`values` 每个键会被转成数字写进指标表，**不许塞判定或标记**；同窗口内容变了会被拒绝重写）。
  - **判定结果不放 `flywheel_outcomes`**（复审核实 6 处放不下：`verdict` 只有 confirmed/inconclusive/reversed；`evaluator_key` 只允许 `flywheel_metrics / gsc_snapshots`；归因任务会按 `evaluator_key` 删"非预期指标"的行；唯一键 `(action_id, metric_key, window_days)` 撞键覆盖，违反"只追加"；`window_days` 按天存装不下小时；`action_id` 必填而目标节奏是每客户每期一条）。该表的语义是归因结论，当年另建回执表就是为了不混。
  - **定论：新建一张社媒验证判定表（暂名 `social_verification_verdicts`），A 级，先问 PM、合并后需 PM 回 `go apply` 才建**。字段至少含：request id、client id（外键指向 clients）、内容 id（可空）、周期（C3 用）、平台、记录类型（C1 / C2 / C3 / `story_dm_count`）、判定值、读取时点、助推标记、样本数、**依据的原始读数回执编号、对照组定义与基线值、不可比原因、判定逻辑版本号**、创建时间。**约束写进数据库，不靠自觉**：记录类型决定必填 / 禁填列（C1、C2 必须有内容 id 不能有周期；C3 必须有周期不能有内容 id）并限定判定值域（C1 只能 `match/mismatch`；C2、C3 只能 §3.5 列出的值）；**同一判定输入的同一次尝试只能写一条**（唯一键，防 Inngest 重跑出重复）；**拒绝修改和删除的触发器保证只追加**；RLS 一律 `FOR ALL TO service_role USING (true) WITH CHECK (true)`。**删客户冲突**：`client_id` 外键指向 clients 时，「拒绝修改和删除」触发器会拦住客户的连带删除；明确选定：**有判定记录的客户不许直接删，删客户另走有授权的流程**（内容 id 若外键指向 `flywheel_actions` 同理），WP1 实施前复审重点核。`story_dm_count` 类记录：内容 id 必填、周期禁填；唯一键 = 记录类型 + 内容 id 或周期 + 读取时点 + 判定逻辑版本 + 尝试序号。判定值域写成数据库约束，所以 §3.5 的〔候选〕值日后改动 = 再改一次表结构（A 级）。
- **M4 付费助推识别（精确，且读不全不当没助推）**：比对该客户广告里所有广告的 `effective_object_story_id` 与帖子编号，命中标 `boosted`（员工在 Business Suite 手动加推也会生成广告）。现成的 `fetchAdStoryIds` **不能直接用**：它出错返回空列表、最多读 200 条 / 8 页，会把「读失败 / 被截断」悄悄变成「没被助推」（正是「读不到当 0」的老问题）。所以：①**新写一个函数**（不改旧的，旧函数被评论自动回复依赖「出错返回空列表」的行为），读失败、读到上限被截断都**明确返回「读不全」**；②读不全 → 标 `boost_unknown`；**「ME 没接入的广告账户」无法靠逐账户读发现**：WP1 先实测「按主页反查被推广帖子」的读取入口能否用；**实测不可用，就按「没有被证明该主页只有已接入账户 → 一律标 `boost_unknown`」处理，并如实接受这会让很多帖子不可比**（§3.5 诚实预期）；③读取时**必须显式指定要读已暂停 / 归档 / 删除的广告状态**（Meta 默认会滤掉归档和删除的）；④`boosted` / `boost_unknown` 都不进自然效果对比。**不使用「窗口内有广告花费就标」的宽规则**。这个新函数列入 WP1 的 A 级改动清单。
- **M5 口径只承诺拿得到的**：点赞 / 表情、评论、分享；观看 / 完播等在洞察权限未开前一律 `not_readable`，不进验收。**Story** 用「客户配置的『邀请私信』槽位发出后 X 小时内新开私信会话数」（**客户层示例：CTS 为 20:00 那条、12 小时**，2026-10-14 定，需连续两周再下结论）。**私信会话读取在日常运营稿里仍标「未验证」，X 的上下限与是否可读都在 WP0 实测后定**。
- **M6 归因**：首评链接带追踪后缀（沿用**客户层** utm 约定），点击与留资走既有 CRM / 归因。按单条内容拆分的点击能力地图标「未验证」。
- **M7 Check 只覆盖系统发的帖子**：员工手动发的帖子不进 C2。**系统发的图文近乎为 0**（见 §2 A 行），所以 **Post 的 C2 现在基本是空的**；要有数据，需先由 **PM 本人**决定图文发布路径（把每日计划图文自动发布从演练转真发 = 发布授权；或做 Post 最小版），见 §10 第 6 条；本稿不假装解决。
- **M8 「读数不全」的定义**：只算**本来应该读得到**的指标缺失；观看数永远读不到不算缺；**Story 私信数在 WP0 验证可读之前不算「应读到」**（否则天天冻结），验证后才纳入。
- **M9 私信防重复计数**：社媒目标用独立指标键；同一个私信会话若被广告目标 `messaging_started` 计过，社媒口径要剔除（靠会话来源里的广告标识）。**能否可靠识别在 WP0 实测**；识别不了，该指标不得作为社媒目标，改选别的。**已知局限**：客人看过广告、却从主页直接点私信进来的会话没有广告标识，仍会算给社媒。

### 3.3 Prescribe（开处方）

**处方 = 封闭词表里的一条，固定格式记录**（动作键 / 防重复键含日期 + 内容 id + 参数 hash / 证据 / why，与广告 `action_runs` 同形，给 WP5 留接口）。**记录存在哪还没定**：写进 Kernel 的 `action_runs` 算 A，另建表也是 A，只有塞进现有工单表字段才可能是 B——**落点在 WP3 设计时与子牙定，定之前 WP3 按 A 级**。

| 词 | 含义 | 是否对外 | 谁批 |
|---|---|---|---|
| `social.plan_week` | 写一周候选 | 否（草稿）| 苏东坡签字 |
| `social.make_reel` | 向视频工厂下工单（带 `platform` 与创意标签）| 否 | 工厂审查 + PM 点通过 |
| `social.make_post` / `social.make_story` | 做图文 / Story 草稿 | 否 | 苏东坡（字）+ 马良（新增图）|
| `social.reslot` | 在客户配置内微调时段（±30 分钟，每期一个槽位）| 否（改排期）| 复盘 R1：第一次只建议，PM 看过后同类才自动 |
| `social.swap_asset` | 换同角色内已审图 | 否 | agent 自己；**每个包的换图次数上限和冷却期〔候选〕，WP3 设计时定**，目前这两个动作没有冷却、不进统一授权核查，是已知缺口 |
| `social.takedown` | 下架已发内容（5A）| **是** | 设计已批，**实现未开**，不在 v1；是否先注册为 Kernel「必须人工批准」动作，WP5 开工前单独裁 |
| `social.escalate_to_pm` | 三件套待办（what / how / href）| — | — |

**授权边界（硬规定）**：`social.reslot` 与 `social.swap_asset` **只能作用于授权之前的草稿**。授权绑内容指纹（含发布时间与图的哈希），授权后要改必须**作废原授权、请 PM 重新授权**；agent **永远不能重算、不能放宽指纹**。

每条处方必带：`why`、`not_this_because`、`expected_impact`、`confidence`、`verification_definition`。**读上一轮验证结果**依赖 Check，放在 WP4。**Day-0 默认处方**来自冷启动 v0.2。

#### 3.3.1 四层叠起来（v1.5）

不另造处方引擎。华佗处方、品牌总纲、发布名额、评论自动回复开关、目标卡都已有。缺的是把下面四层叠成「本周方子」的合成，加一张给人点的社媒方案确认卡。周包和目标卡继续读客户配置。

```
平台规则（硬规则，谁也改不了）
  ↓ 行业模板（默认值，没填才用）
  ↓ 阶段调整（在行业默认上加减，也只在没填的地方生效）
  ↓ 客户自己的配置（人填过的永远优先）
  = 本周社媒方子 → 周包照它出稿
```

- **平台层**：写死，所有客户一样。例如 Facebook 正文不放链接、链接放首评；读不到的指标不进验收；Story 不卖货；问价、投诉、退款永远不自动回；小组只能「ME 写、人去发」；Marketplace 不挂团。出处：Facebook 运营思路、社媒规则手册。
- **行业层**：每个行业一份默认（内容比例、三种形式各管什么、哪些话题要人回、禁说什么、旺季）。键用 `clients.industry` 那套词（经验记忆已按它取）。三套行业词现在对不上，要另写一个小映射，不把三套并成一个新词表：①设置页受控词（`src/lib/clients/industries.ts`，如 `travel`；这份词表里还没有物流）；②华佗基准代码（`src/lib/huatuo/industry-mapper.ts`，如 `tourism_operator`）；③口碑平台表（`src/lib/apify/industry-platform-map.ts`，如 `tourism_travel`）。另有爆款参考库按行业存，但没有「这个行业社媒该怎么做」的模板。**首批只写旅游、物流两份**（2026-11-02 已定），起点在冷启动 v0.2，比例和节奏仍标〔建议〕。建材、通用不进首批。物流在设置页词表里还没有对应项，模板先写在文档里，不在这次改词表。
- **阶段层**：每次用**这个客户、这个平台自己的账号数据**现算，**不入库**，也不拿别的客户或别的平台的数来套。现在只算 Facebook；以后接上的平台各自单独算。只调量、比例、平台、互动、目标五样。人看到的是一句话加依据。判据数字仍是〔建议〕，2026-11-02 **没有确认**。
- **客户层**（2026-11-02 已定）：总纲 `content_pillars`、发布名额、自动回复开关、目标卡里**人填过的永远压过上面三层**。阶段变了也不自动改人填的数。行业模板和阶段只出「建议改」卡。

**阶段四档**（判据数字仍是〔建议〕，§10 第 8 条未确认。按每个客户、每个平台、用该客户自己的账号数据现算；现在只有 Facebook）：

| 阶段 | 判据 | 意思 |
|---|---|---|
| **起步** | 下面任一条：没有主页发布授权；事实库 < 20 条；真实素材 < 15 件（来源为 `client_verified` / `fde_shot`）；系统连续按时发出 < 4 周 | 先攒内容库和第一批能比的数据 |
| **成长** | 起步都过了；但每种形式能比的读数回执 < 每组 10 条（复用复盘 R1 的门槛） | 量稳住，开始看哪类内容有互动 |
| **成熟** | 连续 12 周按时发出，且至少一种形式回执 ≥ 每组 10 条、连续 2 期 | 节奏已经稳住。可以建议调比例、调时段，仍只出卡。不挂数字目标 |
| **暂停** | 发布授权断了、熔断触发、或投诉明显变多 | 只出待办，不出新稿 |

「按时发出」= 周包里批过的条目真发出去了（读周包和发布记录）。两个轴取慢的那个：内容够了但数据不够，算成长，不算成熟。**个人 IP**（`clients.client_kind`）不另写一套，复用 `src/lib/huatuo/personal-ip.ts` 已有的 12 周三阶段（立人设 / 放大攒人 / 变现）：起步≈立人设，成长≈放大，成熟≈变现。

**阶段调什么**（客户填过的格子不动，只出现在建议卡上）：

| | 起步 | 成长 | 成熟 |
|---|---|---|---|
| **量** | 冷启动：Reel 1–2 / 图文 3 / Story 每天 1（晚上邀请私信） | 行业模板的标准量（素材够再加） | 按数据加减，每次加量出卡 |
| **比例** | 偏「讲清楚是什么」 | 行业模板默认比例 | 按回执调，每次只动一类、不超过 10 个百分点，出卡 |
| **平台** | 只 Facebook | Facebook；其他平台连接好了才出「要不要开」的卡 | 同左 |
| **互动** | 只问候 + 常见问题；问价 / 投诉 / 退款进待办 | 同左；高频问题出「加一条 FAQ 模板」的卡 | 同左；投诉永远不自动回 |
| **目标** | **不挂数字目标**。主信号是按时、按节奏发出（动态常态化更新），不看粉丝数、触达数 | 同左 | 同左。可以建议调比例，仍不挂粉丝、触达或私信条数 |

社媒不设数字目标（2026-11-02 已定）。§3.1 I1「没有 active goal 就只巡察、不出处方」**不挡住周包**：周包仍按客户名额和冷启动出稿。处方卡上的主健康信号是「这一周有没有按时、按节奏发出」，不是粉丝数或触达数。

**社媒方案卡**：第一次开方、阶段变了、或要建议调比例 / 加量时出卡。卡上写阶段和依据（哪个平台、用的是这个客户自己的哪几项账号数据），**只列和现在不一样的几项**，每项标明来自平台 / 行业 / 阶段哪一层。卡的主行是按时、按节奏发出，不把粉丝数或触达数列成目标。一张卡点一次（采用 / 不改 / 改一下再用），同一周不重复出卡。点「采用」才写回 `master_briefs.content_pillars` 和发布名额，写之前留一条记录：谁、何时、改前、改后。行业模板和阶段给的数，人没点采用就不写进去。

**两处配置对不上（先记在设计里，施工见 §7.1 第 1、2 步，都是 A 级）**：

1. `clients.publishing_calendar_config` 是线上直接加的列，仓库 `supabase/migrations/` 里没有对应迁移，新环境建不出这列。
2. 名额现在按天存（每天几条图文、每天几条 Story、每周几条 Reel）。CTS 已确认的业务量是**每周 18 条 Story + 4 条图文 + 3 条 Reel**（高频客户，2026-11-02）。按天的格子写不出「每周 4 条图文」。把名额改成按周读写是**另一次 A 级代码改动**（§7.1 第 2 步），本稿不改代码，也不把这个每周量写成全行业默认。

CTS 是在新西兰卖中国团的旅游公司，客人是所有新西兰人。上面的每周量只属于这一家的客户层，压过旅游行业模板，不写成平台规则，也不套到别的客户。

### 3.4 Act（做）—— 受控执行，v1 不改任何现有发布开关

```
Story:  处方 → 草稿 → 发前检查 → PM 授权一周的包（绑内容指纹）→ Story-lite 在发送窗口发出
Reel:   处方 → 视频工厂工单 → 苏东坡 + 马良审 → PM 点「通过」（工单状态 approved + 批准清单；没有包授权）→ 工厂发布器发出
图文:   目前没有在跑的系统发布路径（每日计划图文自动发布默认只演练）→ 由 PM 决定（§10 第 6 条）
共同:   每条发布路径在调平台接口之前的最后一步都要再读一次「发布暂停标记」（读不到一律不发）
        → 首评写入 → 发布回执（授权人、指纹、平台返回 id、发布时间、是否被助推）
```
- **四条现有发布路径保持原样**，**不并入**新的串行队列，**不改**其开关；每日计划图文自动发布**仍默认只演练**。
- **发布暂停标记（新，WP1b，A 级）**：每个客户一个标记；**所有发布路径（含工厂路径，它没有包授权，只能靠这个停）必须读它，读不到按暂停处理（fail-closed）**。设置暂停**不需要管理员身份**（机器可设），但**只有系统内部模块（验证模块、发布器）能设**，客户侧账号与外部接口不能设；**恢复发布只有管理员本人能做**。理由：撤授权要求管理员身份（Story 的撤销入口与每日计划的撤销接口都要管理员），机器没有这个身份，造一个"系统身份"等于在授权闸上开新口子。
  - **「没暂停 ≠ 有授权」**：暂停标记只会让发布停下，不是许可；四条路径原有的授权核查一个都不能省，防止以后有人把「没暂停」当发布许可（历史上状态字段当授权漏过闸）。
  - **最后一刻再读一次**：工厂发布先把工单改成「发布中」再调平台接口，最后一道服务端检查在发出前重核批准清单——暂停标记必须读在这同一位置，不能只在扫描开头读，否则已被领走的条目拦不住。Story 与每日计划自动发布同理，读在调平台接口之前那一步。
  - **存在哪**：必须放数据库（新表或新字段），**需要 PM 回 `go apply`**；**上线顺序：先建表并预置数据，再上读取代码**，否则「读不到就不发」会让所有路径全停；**上线之后新建的客户：由建客户流程写入默认行，并加测试保证一建好就有这一行**；读取出错 = 按暂停处理，缺行 = 按暂停处理并进待办（不静默放行）。**只通过一个写入函数改这张表，并加检查防止别处直接写**。
  - **每次设置与恢复都留记录**：谁、为什么、触发哪条规则、时间。
  - **覆盖范围**：首评写入属于发帖的一部分，被拦；每小时跑的评论自动回复也是对外动作，**纳入暂停范围**——它是 Render 上的定时接口（`/api/cron/social-comment-autoreply`，不是 Inngest），要在它调平台接口之前读暂停标记，并在它自己的运行记录里记「因暂停未发」；管理员手动点发布在暂停期间同样被拦（先恢复再发）。
- 新增读取函数：把各处回执归一成同一种「发布回执」读法（不新建表）。草稿永远不记成「已发布」；无授权事件 + 无平台回执，不判完成。

### 3.5 Check（查）—— 三个独立判定，不合成一个分数

| 判定 | 看什么 | 方法 | 结果 |
|---|---|---|---|
| **C1 保真** | 发出去的 = 批准的 | 下载平台返回的图 / 视频帧与批准原件比对；文字、首评链接核对 | `match` / `mismatch`。**阈值未校准**（Facebook 会重压缩缩放，视频要抽帧）。**阈值按平台、按素材类型（图 / 视频）分别标〔候选〕，不用单客户校准出的常数当全体默认**；校准的通过标准（误报率 / 漏报率上限）在 WP4 设计时与子牙定。**校准前只开待办，不触发暂停** |
| **C2 表现** | 这条内容在同类里怎么样 | **扩展现有 `social-post-cohort` / `social-post-evaluator`**。要扩的限制：现在只收每日计划发的帖、只在同一推广活动内比、工厂 Reel 被排除、只读 T+72——WP4 设计时逐项写明去掉哪些。分档沿用现有的 **±30%**〔候选，来自现有模块〕。「同类」的角色分类来自行业剧本枚举。**Story 不做逐条 C2**（没有单条表现），只看客户层「邀请私信」私信量 | `above` / `within` / `below` / `insufficient_sample` / `not_comparable` |
| **C3 目标节奏** | 对 PM 目标走到哪了 | **复用广告 `goal-pace` 的线性节奏部分**（`null ≠ 0`），抽成两个支柱共用模块；社媒另加「名额可达性」：剩余名额 × 系统发帖近期每条中位结果 vs 剩余目标〔候选公式；「近期」的长度也是候选，WP4 与子牙定〕；系统发帖样本不够门槛时输出 `insufficient_sample` | `on_track / behind / unreachable_within_quota / insufficient_sample` |

**样本门槛（全稿唯一一张，每条标出处）**
| 用途 | 门槛 | 出处 |
|---|---|---|
| 现有复盘方向提示（相差 ±30% 才建议）| 每组 ≥3 | 主干 `social-post-evaluator` |
| 创意标签 × 表现出「候选结论」 | 每组 ≥5 | 日常 Agent 设计稿 SO-09 |
| 调发布时段（R1）| 连续 2 期、每组每期 ≥10 | 日常 Agent 设计稿 7.2 |
| R2 | 每组 ≥8 | 日常 Agent 设计稿 7.2 |
| Story 替代量法 | 连续两周再下结论 | 74 号 2026-10-14 |
| 其余（「连续 `below`」几次、冻结天数）| 〔候选〕2 个连续周期 / 30 天，社媒无证据，沿用广告与 R1 作占位 | 广告 G8 |

- **`not_comparable`**：被助推 / `boost_unknown`；窗口内客户做过非 ME 改动；节假日或活动周（客户配置）；读不全（按 M8）；手动发布的帖子。
- **「请示 PM」触发**：①`unreachable_within_quota`；②素材池耗尽；③熔断。①依赖每条帖子平均带来多少私信，**小样本下算不出来时它不会响——已知局限，日报如实写**。
- **C3 分子分母口径**：目标进度的分子是主页层的自然私信 / 点击（含手动发布、剔除广告来源，见 M9），而"名额可达性"只能用系统发的帖子估每条结果——**两者口径不同，日报并列显示并标注，不拿其一去判另一个**；在 WP0 证明可剔除广告重复之前，C3 不用于请示 PM。
- **诚实预期**：按现有量，C2 / C3 在 CTS 上很可能**数月都只给「样本不足」**；Post 的 C2 现在基本是空的（系统发图文近乎为 0）；这条链前期价值是**把管道接通、让数据开始积累**，不是马上出结论。
- 每次判定写入 M3 的新表，只追加不覆盖。

### 3.6 Tune（调）
