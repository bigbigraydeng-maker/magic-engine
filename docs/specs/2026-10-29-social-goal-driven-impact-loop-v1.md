## 0. 一句话结论

**不建新引擎。** 把已经在的社媒零件（视频工厂、Story/Post 周包与授权、Facebook 发布、评论分类、页面指标同步、单条表现读取、创意标签）按 **Inspect → Measure → Prescribe → Act → Check → Tune** 接成一条有目标的链，只补三处缺口：**目标契约、发布后自动回读与验证、验证结果回流下一轮处方**。

和广告闭环的**最大区别**（决定了本稿比广告稿保守）：
1. 广告能按天读到花费、结果，社媒的 **Facebook 观看数 / 触达读不到**（缺洞察权限），所以 Check 靠互动数 + 私信数，样本小、结论慢；
2. 广告动作可撤回（暂停、改预算），**发出去的帖子撤不回**（只能下架，下架也是对外动作）；
3. 因此 v1 的 Act **不开「信封内自动发布」**，沿用现有「PM 授权一周的包、授权绑内容指纹」；自动发布放到 WP5，且需 PM 本人另行拍板。

## 1. 分工边界（提议，待 PM 确认；依据：PM 10-13「发什么、几点发、怎么发、发了数据怎么样、怎么调整，都是 agent 要考虑的」与 10-16「真人只管预算、审核与授权」）

| PM 管 | AI 管 | AI 只在这些情况找 PM |
|---|---|---|
| **目标**（例：每月多少条私信咨询 / 多少次首评链接点击，带期限） | 发什么（选题、角色、形式）、写候选、做内容、排时段（在客户配置范围内）、读数据、验证、复盘、写学习卡 | 按当前目标 + 名额 + 素材池，**目标完不成**——请示「加量 / 补素材 / 下调目标」三选一 |
| **每周发布量（名额）** | 在名额内安排角色比例与时段 | 熔断触发（§6） |

## 3. 逐段设计

### 3.1 Inspect（发现）—— 从 master brief 开始

每个客户每天一次（后台任务），**固定先读两样**，再读运行数据：

| 顺序 | 读什么 | 用来干什么 | 规则 |
|---|---|---|---|
| **I0** | 客户 **master brief**（方向、受众、支柱配比、品牌 VI）+ **官网当下内容**（事实） | 校准整个客户层：该发什么、不能说什么、受众是谁 | brief 只给方向，**不当事实来源**；事实以官网为准，冲突选官网（客户数据红线）；读不到就标缺口，不猜 |
| **I1** | 目标契约（`goals` 一行）+ 名额配置 + 素材池 | 知道「要什么、能发多少、能用什么」| 无 active goal → 只巡察不出处方（对应广告 K5）|
| **I2** | 运行数据：近期帖子的互动 / 私信、评论分类结果、页面指标、连接状态、**Instagram 等未接入平台的状态** | 发现问题 | 「读不到」与「0」永远分开 |
| **I3** | 机会信号（§3.1.1）| 发现机会 | 每条带 evidence / sample / not_comparable，格式与广告 `Diagnosis` 同形 |

#### 3.1.1 机会发现（纯函数，第一版只做有数据支撑的几条）
| 码 | 判据 | 输出处方候选 |
|---|---|---|
| **SO1 名额缺口** | 本周已排候选数 < 名额 | `social.plan_week`（补候选，缺口标原因：缺事实 / 缺素材 / 缺审）|
| **SO2 事实沉睡** | 事实库里已核实、近 N 天（客户配置）没用过的事实 | `social.make_post` / `social.make_story` |
| **SO3 评论 / 私信高频问** | 同一类问题在评论分类或私信里连续出现 ≥ 阈值（阈值客户配置）| 选题建议（选题回答该问题）。**不自动回复**，评论自动回复另有设计和闸 |
| **SO4 真实素材未用** | 素材池里 approved 的客户实拍久未被任何内容使用 | `social.make_reel` / `social.make_post` |
| **SO5 平台缺位** | 客户有该平台账号但 ME 未接入 | 只出一条待办（不出内容）|

“哪种开头 / 栏目更好”这类机会（原 v0.3 创意层的核心）**不在第一版**：要等标签与单条表现凑出每组 n≥5（设计稿 SO-09）的样本，见 §3.6。

### 3.2 Measure（量）

- **M1 单条表现读取定时化**：每条已发内容，在固定「年龄」读一次并落回执（候选年龄：Story 12 小时；Post / Reel 1 天、3 天、7 天——**〔候选〕，没有平台证据，沿用「基础权限可读」的三项 + 后续可调**）。复用 `post-performance`（S2）与现有回执表，**不新建表**（沿用 v0.3 §5.6 落点；若回执放不下再另开，按 A 级走）。
- **M2 口径只承诺拿得到的**：点赞 / 表情、评论、分享；Story 用「20:00 邀请私信那条发出后 12 小时内新开私信会话数」；观看 / 完播等在洞察权限未开前一律 `not_readable`，不进验收。
- **M3 归因**：首评链接带追踪后缀（沿用日常 Agent 设计稿 utm 约定），点击与留资走既有 CRM / 归因，不另造。
- **M4 付费助推隔离**：同一条内容若被广告助推，其互动 / 私信标 `boosted`，**不计入自然效果、不进验证对比**（对应广告 K12 的「有其他变动 → not_comparable」）。

### 3.3 Prescribe（开处方）

**处方 = 封闭词表里的一条，固定格式记录**（对应广告 `ads.*` 词表 + `action_runs` 一行）：

| 词 | 含义 | 是否对外 | 谁批 |
|---|---|---|---|
| `social.plan_week` | 写一周候选（角色、希望哪天、事实编号、素材指纹）| 否（草稿）| 苏东坡签字 |
| `social.make_reel` | 向视频工厂下工单（带 `platform` 与创意标签）| 否（成片是草稿）| 工厂审查 + PM 点通过 |
| `social.make_post` / `social.make_story` | 做图文 / Story 草稿 | 否 | 苏东坡（字）+ 马良（新增图）|
| `social.reslot` | 在客户配置内微调时段（±30 分钟，每期一个槽位）| 否（改排期）| 按复盘 R1：第一次只建议，PM 看过后同类才自动 |
| `social.swap_asset` | 换同角色内已审图 | 否 | agent 自己（沿用审批矩阵）|
| `social.takedown` | 下架已发内容（5A）| **是** | 设计已批，**实现未开**，不在 v1 |
| `social.escalate_to_pm` | 不是动作，是三件套待办（what / how / href）| — | — |

每条处方必带：`why`（证据）、`not_this_because`、`expected_impact`、`confidence`、`verification_definition`（几天后看什么、怎么算成）。**处方记录落点**：沿用现有工单 / 候选表的字段，其余写入回执；不新建 prescriptions 表（与广告同）。

**读上一轮验证结果**：同类处方上次 `reversed` → 降一档；两次 → 对该客户冻结 30 天（对应广告 G8）。

**Day-0 默认处方**：新客户没有任何历史时，处方来自 [冷启动策略 v0.1](../sops/2026-10-29-social-new-client-cold-start-v0.1.md)，其数量与钟点是「建议 / 候选」，由 PM 在目标契约里确认。

### 3.4 Act（做）—— 受控执行，v1 不开自动发布

```
处方 → 生产（视频工厂 / 图文 / Story 草稿）
     → 发前检查（硬规则 + 苏东坡 + 马良 + 值不值得发 + 事实出处 + 价格闸）
     → PM 授权一周的包（授权绑内容指纹，改了就拦）
     → 发送窗口内由发布器发出 → 首评写入
     → 发布回执（授权人、指纹、平台返回 id、发布时间、是否被助推）
```

- **沿用**：Story-lite / Post-lite 的授权、指纹、发送窗口（早于 5 分钟不动、晚于 20 分钟 MISSED 不补发）、Reel 在工厂点通过。
- **新增只有一处**：把以上各处回执**归一**成同一种「发布回执」读法（不新建表，查询视图或读取函数），供 Check 使用。草稿永远不能记成「已发布」（v0.3 硬规则）。
- **fail-closed**：没有授权事件和平台回执，不许伪造完成（CLAUDE.md Inngest 硬约束）。
- **Kernel**：广告走 Kernel 的「受限自治信封」，社媒 v1 **不接**。接不接、怎么接（是否把发布注册为 Kernel 动作）列为 **WP5 的架构问题交子牙裁**，不在本稿定。

### 3.5 Check（查）—— 本稿最重要的新增

Check 有三个独立判定，**不合成一个分数**：

| 判定 | 看什么 | 方法 | 结果 |
|---|---|---|---|
| **C1 保真** | 发出去的 = 批准的 | 下载平台返回的图 / 视频帧，与批准原件比对（同尺寸时平均差个位数＝同一张）；文字、首评链接核对 | `match` / `mismatch`（mismatch → 熔断 + 待办）|
| **C2 表现** | 这条内容在同类里怎么样 | 与**同客户同角色同平台近 N 条的中位数**比；每组 n≥5 才下结论，否则 `insufficient_sample` | `above` / `within` / `below` / `insufficient_sample` / `not_comparable` |
| **C3 目标节奏** | 对 PM 的目标走到哪了 | 纯函数 `goal-pace`：当期累计、预期、差距、`on_track / behind / unreachable_within_quota / insufficient_sample` | `unreachable_within_quota` 是请示 PM 的**唯一触发器** |

- **`not_comparable` 条件**：被助推；窗口内客户做过非 ME 的改动（改主页资料、换封面）；节假日或活动周（客户配置）；读不全（`partial`）。
- **样本诚实**：起步量下 Post 每期每组远不到 n≥10（冷启动 v0.1 §三：约第 14 周才可能第一次触发 R1）。**宁可长期 `insufficient_sample`，不拿小样本下结论。**
- **读不到 ≠ 0**：回执里 `not_readable(原因)` 与 `0` 分开，报告标样本量。
- 每次判定落回执：request id / client id / 内容 id / 平台 / 读取年龄 / 状态 / 是否被助推 / 创建时间。

### 3.6 Tune（调）

- **T1 标签 × 表现**：创意标签（S1）与 C2 结果凑够每组 n≥5 后，才出「哪种开头 / 栏目 / BGM 更好」的**候选结论**。标签是建单方自报，苏东坡 / 马良审时顺带核对，核过的才进对比。
- **T2 写学习**：`above`/`below` 稳定且无混杂 → `saveProvenPattern` / `saveFailedExperiment`（客户层）；`insufficient_sample` / `not_comparable` → 只更新决策记录，**不写经验**。
- **T3 升层**：客户层 → 平台 / 行业层，需 ≥2 个客户同结论（红线 7）+ `checkShareable` + 该平台自己的样本（Facebook 验证的规则**不自动**适用 Instagram）。v1 只写客户层。
- **T4 调时间**：只走复盘 R1（连续 2 期、每组 n≥10、±30 分钟、一次一槽位、第一次只建议）。
- **T5 回流**：验证结果下一轮 Inspect 读到，进入 §3.3「读上一轮验证结果」。
- **手册更新**：被验证的平台打法，由 97 号 / 苏东坡提改动更新对应平台运营思路，标出处和日期，PM 逐条确认——**学习不会自己改手册**。

## 4. 三个角色（确定性模块 + 现有 agent，不新增聊天机器人）

| 角色 | 落点 | IMPACT 段 | 说明 |
|---|---|---|---|
| **巡察**（暂名，同广告「卫青」位）| `src/lib/social/agents/patrol.ts`（新）| I + M | 读 brief / 目标 / 运行数据，写出一行「社媒成长状态」（问题、机会、目标节奏、各客户当日读数完整度）；合并并**收编**现有零散的指标同步调用，不双跑 |
| **苏东坡**（军师，已有）| 规则手册 + 创意层（S5，后期）| P + T | 判断全是纯函数 / 规则；LLM **只**把结构化结论写成人话 |
| **执行**（工厂 + 发布器，已有）| 视频工厂、Story/Post-lite、Facebook 发布器 | A + C | Check 的读回、比对、判定由新增的**验证模块**做，生产方不得自评 |

“生产方与质检方必须是两个不同的角色”（2026-09-28 事故铁律）在本链的位置：**工厂产出 → 苏东坡 / 马良审 → PM 授权 → 发布 → 验证模块读回（不是生产方）**。

## 5. 事件链与节奏（Inngest，事件名业务可读，函数 id 一律 `cloud-social-*`）

```
social/impact.cycle.due         每客户每天一条（并发键 client_id，串行）
social/growth_state.built       巡察：I0–I3 + M → 当日状态
social/prescription.proposed    处方候选（词表内）+ memory 过滤
social/content.produced         工厂 / 草稿完成
social/publish.authorized       PM 授权（人，不是 agent）
social/post.published           发布回执
social/readback.due             按读取年龄 sleepUntil（Story 12h；Post/Reel 1d/3d/7d〔候选〕）
social/verification.completed   C1/C2/C3 判定回执
social/memory.recorded          T2 写学习
social/pm_digest.ready          日检报告
```
- 数据不完整（某客户当日读数缺）：**诊断照跑，处方与候选当日冻结**，日报写「今天读数没拉全，不动」；次日自动恢复。
- 所有会触达发布的路径一律经 `social/impact.cycle.due` 串行，不留旁路（对应广告 G11 串行化）。
- 新增写运行记录的定时函数 → **改 cron 登记表 → 机器判 A**；上线后须手动 Sync `/api/inngest`。

## 6. 安全底线与熔断（写死在代码，不靠人）

1. 内容只取自已核实来源池（事实库 → 真实素材库 → 工厂产出），没有就记缺口，**不编**。
2. 客户实拍才能做「价格 / 产品承诺」；图库图与 AI 图只做氛围，来源看**来源记录**，不看文件名。
3. 视频一律走视频工厂（`src/lib/factory/`），**禁止**旁路脚本直调生成接口加平台发布接口。
4. 所有视频默认带 logo；结尾带不带由工厂按模板定（PM 2026-10-29）。
5. Reel 封面与 Story 第一帧必须各不相同；干巴巴的纯数字卡不单独成一条。
6. 草稿永远不记成「已发布」；无授权事件 + 无平台回执，不判完成。
7. **熔断**（任一触发 → 当日冻结处方 + 三件套待办，不等 PM）：C1 `mismatch`；发布器连续失败；连接 / 令牌将过期或已断；负面评论 / 硬错误在短时间内集中出现（沿用 5A 阈值设计）；读数不完整（只冻结当天）。
8. **自动下架**：5A 设计已批（PM 10-13 授权先记后做），**实现与开关均未就绪，v1 不开**。
