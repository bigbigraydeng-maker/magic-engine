# CRM「同一个人被拆成两个联系人」：合并提示 + 合并操作 + 来源文案（设计稿 v0.1）

状态：**设计稿，待 PM 看，未写任何代码**。起因：CTS 客人 Scott Baker 同时用 Facebook 私信和 info 邮箱联系，系统建了两个联系人，销售看不到员工的邮件回复（已手工合并，不回滚）。
风险级别：**A**（要加数据库表和函数，合并会改生产数据）。来源文案那一条单独拆出来是 **C**。

## 三、合并提示（只提示，不自动合）

**位置：** 客人抽屉顶部加一条灰色提示：「他可能也是 ○○（私信/邮件），看一眼再决定」，旁边两个按钮「是同一个人（去合并）」「不是」。「不是」要记住，以后不再提示这一对。

**信号（打分相加，达到阈值才提示，宁漏勿错）：**
- 名字规范化后相同（去标点、大小写、单个字母缩写）：强
- 一边的邮箱前缀包含另一边的全名：强
- 两边首次进线时间相差 ≤ 72 小时：弱，只能加分
- 渠道不同（一个私信、一个邮件/表单）：弱
- 第一条来信正文相同：弱（上面看到会被诈骗私信污染，必须先去掉出现过 4 次以上的模板句）
- **不提示的情况：** 已有共同的邮箱/电话/私信号（那本来就是同一人，系统会自己合）；任何一边是「别再联系」时仍然提示，但不允许把「别再联系」合没了（见第四节）。

**什么时候算：** 新联系人建出来时，只跟同客户最近 30 天的联系人比（按规范化名字和邮箱前缀建索引，不做全表两两比较）。另跑一次历史回填。

**存哪：** 新表 `contact_merge_suggestions`（客户、联系人 A、联系人 B、命中的信号、分数、状态：待处理/已忽略/已合并、处理人、时间）。唯一约束保证同一对只出现一次。

## 四、合并操作（现在不存在，需要新做）

### 4.1 要挪哪些表（从迁移文件整理，**线上实际外键没有逐一核对，开工前必须用数据库元数据再查一遍**）

| 表 | 怎么处理 |
|---|---|
| `contact_identities` | 全部指向保留的联系人；撞上唯一约束（同客户同种同值）的丢掉重复行 |
| `contact_touchpoints` | 全部指向保留的联系人 |
| `contact_stage_events` | 全部指向保留的联系人（阶段变更历史保留） |
| `conversations`（`contact_id`） | 全部指向保留的联系人（私信/邮件会话归到一处） |
| `crm_segment_feedback` | 指向保留的联系人；撞唯一约束的保留较新的一条 |
| `me_sale_outcomes` | 指向保留的联系人（成交回写不能丢） |
| `crm_bookings`（及其成员/里程碑/事件） | 预订挂在联系人上，指向保留的联系人；数据库里有「不得跨客户引用」的触发器，同客户合并不受影响 |
| `telephony_calls` | 通话记录指向保留的联系人 |
| `agent_customers.agent_contact_id` | 同行代理的联系人；合并同行时才会碰，普通合并不动，但要查有没有指向被合掉的人 |
| `conversation_health_alerts.contact_id` | 无外键，也要改指向 |
| 通话分析、攻略等其它引用 | **未查清，开工前必须扫全（按 `contact_id` 列名扫线上全部表）** |

### 4.2 联系人自身字段怎么合（保守规则）
- 「别再联系」：**任一边是就保留为是**，原因拼接。绝不能因为合并把客人说过不要联系的话抹掉。
- 阶段：取阶段更新时间较新的；置顶：任一边置顶就置顶；重要备注：两条拼接；推迟到期：取较晚的。
- 首次进线时间取较早的；显示名取更完整（非空、非缩写）的；邮箱电话取非空的。
- 广告归因（`attr_*`）：取 `first_attributed_at` 较早的那一份整组带走，不拼凑。

### 4.3 可撤销 + 回执
- 合并写成**一个数据库函数，单事务**：要么全部挪完，要么全部不动。
- 合并前先把「被合掉的联系人整行 + 这一次挪动过的每张表的行 id 清单」存成快照，写进新表 `contact_merge_log`（谁、何时、保留谁、合掉谁、快照）。这就是回执。
- 被合掉的联系人**不真删**，加 `merged_into` 标记并从所有名单排除。
- **撤销**：按快照把挪过的行指回原联系人、恢复被合掉的联系人。撤销窗口 30 天；合并之后在保留的联系人名下新产生的行不动，只回滚快照里的行。
- 只允许同一个客户内合并；合并只能由登录员工在页面上点，**不会自动触发**。点之前先显示「合并后长这样」让人确认。

### 4.4 要不要接 Inngest
合并是员工在页面上点一下、同步完成的单个动作，没有跨步骤的异步接力，也不对外发任何东西，**不接 Inngest**。回执存在 `contact_merge_log`。提示的历史回填是一次性任务，同样不接。

## 五、「来源」那一行的文案（C 级，可以单独先做）

- 现状：列表里的「来源」是**第一条客人来信的渠道**（私信/邮件/WhatsApp/电话/FB 表单/网站表单），PM 读成了广告来源。
- 改成：**「首次联系渠道」**。
- 另外：有广告归因的另起一行显示**「广告来源：平台 · 广告名」**。CTS 现有 1187 个联系人里 522 个带广告归因。
- 注意：私信会话上的「从哪条广告点进来」只有 1470 个会话里的 9 个有，所以私信的广告来源多数还是空的（这是另一件事，Messenger 广告来源捕获，不在本稿）。**没有广告归因的人不显示「广告来源」这一行**，不写「自然流量」，因为我们并不知道。

## 七、复用声明

- 复用：现有联系人/身份模型、`contact-kind` 的域名与系统账号规则、`contact-enrichment` 的来源计算。

## 八、没验证的、会影响设计的

1. 线上所有指向联系人的表（见 4.1，只查了迁移文件）。
2. 邮件正文是否全部入库（影响「正文相同」这类信号能抓到多少）。
3. 阈值：28 对里有的可能是同名不同人（例：同名但两个完全不同的邮箱），需要 PM 看那 20 对名单后判断提示该多松还是多紧。
