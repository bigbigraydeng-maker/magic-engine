## 0. PM 版
**这一段能做到的（说小一点，不夸大）：** 推广计划每天数一遍——「计划要求未来 7 天发几条帖子 / 快拍 / 短视频」，对照每日计划里**真的排好草稿**的条数，不够就推一条待办提醒你。它**不会替你排、不会写任何内容、不会发任何东西**，也不「指挥」每日计划——叫「盯着」，不叫「指挥」。真正让每日计划按计划补出来，要 97 号那边的代理去做（内容要对着官网核实，是它的活）。
**缺口为零只表示条数够，不代表排得对**（价格屏限制、相邻 Reel 不同曲这些放行规则在 97 那一层，本检查不判）。

**数据看起来很少有人用（原因没证明）：** 营销计划表按建表日期统计（含所有状态）：2026-05 建了 12 份，06 建了 18 份，08 建了 1 份，09、10 月 0 份。CTS 的每日计划是 4 个不同活动、各 1 份快照（08-24、09-14、10-06 ×2）；最新两份只排到 10-14，**今天（10-15）起未来 7 天一天都没覆盖**。原因只有三个没验证的猜测：①计划页要人填表（第一刀已改 AI 起草）；②批了没东西动（本稿开始让它盯每日计划，但**仍不会动手**）；③社媒日常转到每日计划页去做了。本稿只回应②的一半。PR 前复跑这两条查询并贴语句。

## 1. 设计
### 1.1 期望：只数条数，不比星期几
- 复用 `expandPromoSchedule`（已上线）展开计划，取窗口内 `post / story / reel` 三类的**条数**（窗口 = 计划账户时区的 `今天+1 … 今天+7`，不含今天；时区未知 → 不检测，只出「读不到时区」）。
- 每周 N 条，任意连续 7 天恰好含 N 条（星期表每个星期几出现一次），所以条数不受默认星期表的影响；缺口文案**不出现星期几**。

### 1.2 实际：每日计划里「真的排好草稿」的条数
- 读 `social_plans` 里该客户全部 `campaign_daily_v1`：**按 campaign_id 各取 created_at 最新一份，再把各活动 PLANNED 的日子取并集**（计划本身没有 campaign 归属）。不复用 `loadDailyPlanCoverage`（它是所有历史快照的并集，会漏报）。只在 `promo/` 里新建读函数，**只 `import type`** 每日计划的类型，不 import 它的运行时代码。
- 「排好」= 槽位 PLANNED **且** bundle 内容齐全：Post 的 hook / body / cta / 图编号非空；Story 4 帧；Reel 的 brief / script / caption 非空。**Reel 的 media_status 不比**（写入契约下恒为 NO_MEDIA / DRAFT_MEDIA，没有成片是常态）。
- PLANNED 但没有 bundle / 内容缺 → 不算排好，并在文案里单独说「N 天数据形状有问题」。

### 1.3 读不到的三种情形，分开说
1. **读库失败** → `daily_plan_unreadable`（只对已批准且已开始的计划出，走现有降频）。
2. **一份每日计划都没有 / 最新一份已全部过期** → 按「实际 = 0」处理，出缺口，并写「每日计划最新只排到 X 日 / 还没有建过每日计划」。这是确定状态，**不是读不到**。
3. 读到了、没排够 → 缺口。
四种结果（够 / 不够 / 读不到 / 形状错）绝不混说。读到 0 ≠ 读不到。

### 1.4 接到现有管道
- `WatchCode` 加 `daily_plan_gap`、`daily_plan_unreadable`；`runPromoPlanWatch` 对「已批准 + 已开始（board.reconcile.week_index 不为空）+ 时区已知」的计划追加（同客户一轮只读一次）；纯函数 `detectSlotGaps`，**`detectWatchFindings` 保持纯**。回执、今日待办合并（一份计划一条）、降频全部沿用 #2701，不新建管道。
- 与「检查清单」里的软门「社媒节奏已排」（批准前、只亮黄灯）不重复：那条只管批准前、不进待办。

### 1.5 不做的
- **不做 slot-proposal 接口**（没有消费者；逐日清单形状又像 POST 骨架，97 的代理可能直接拿去覆盖已审核的每日计划）。97 要读再另设计，且只会给条数、不给逐日、不带 `slots` 形状、不带 phase/step 编号。
- 不写每日计划、不生成内容、不碰视频工厂、不碰 97 的文件（`campaign-daily-plan/route.ts`、`lib/campaign/daily-plan.ts`、`WeekOverviewPanel` 等）。
- 邮件 / 广告两段不在本稿；S4b 仍不做（以后若做，会和本检查重复提醒，要先排先后）。

## 2. 测试（用真实排期函数，只 mock 数据库客户端）
条数相等星期不同不报；3 条要求只排 1 条报缺口且文案无星期；整份已过期报「没覆盖」而不是 N 个缺口；零份每日计划 ≠ 读失败（文案不同）；读失败只一条；草稿 / 未开始计划不检测；Reel 无成片仍算排好；多活动并集；PLANNED 无 bundle 算缺口并标形状错；同一缺口连续两天走降频；换一个客户 / 计划形状函数不用改；故意把检测改成「永不报」，缺口用例必须变红。

## 3. 当场试跑（no_publish，只读）
对 CTS 真实每日计划（4 个活动，最新只排到 10-14）+ 内存里一份已批准计划：期望得到「未来 7 天完全没覆盖」缺口待办；再各跑一次「读失败」「一份都没有」两个分支（假库）。
