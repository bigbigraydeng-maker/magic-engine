## 1 目的与不做什么

**目的**：一页看清两件事 —— ① 每个团的每个出发日期，订了几单、定金收了几单、尾款收了几单、还有几单没收齐、最近哪天该收；② 全部订单一张清单，按团和状态筛。今天只有「一个客人抽屉里看他自己的付款」和「付款要催」名单，没有汇总页。

**一句话必须看清楚**：这套系统**一个金额都不存**，所以「收款情况」从头到尾只是**数订单**，不是数钱。页面上不会出现、也不允许出现任何金额、营收、回款率。

**明确不做**：不记金额、不开发票、不算营收、不做财务对账、不预测现金流、不对客人外发催款、不碰团目录的任何写操作。

### 2.2 代码核对过的五条事实（本稿据此改写 v0.1）
1. **没选出发日期的单，定金仍有到期日**：`booking-view.ts` 的 `noDepartureOutcome` → `computeDepositDueOnly(rule, bookedOn)`（预订日 + 3 个工作日），尾款才是 null + 备注「出发日期未定」。逾期是**逐项**判的（`state==='unpaid' && dueInDays < 0`），所以这类单的定金会逾期。
2. **到期日用的是现值出发日**：`buildBookingView` 的 `effectiveDepartOn = 线上现值 ?? 快照`。所以分组键只能用 `departure_id`。
3. **`fetchAll` 顶到天花板是抛错，不是返回半份**（`src/lib/supabase-paginate.ts` 结尾那段）。所以「拒绝渲染」是现成行为，不用新写保护。
4. **nudge 的两个读取算不出本页要的数**：`listUnpaidMilestonesForClient` 写死 `state='unpaid'` + `quiet=false`；`listActiveBookingsByIds` 写死 `status='active'`。`listContactsForNudge` 会连带 `listDncTouches` 把 `contact_touchpoints` 按 100 人一批全量分页读出来。
5. **`nudged_on` 字段确实存在**（`crm_booking_milestones`，映射成 `MilestoneRow.nudgedOn`），B7 这一列有数据来源。

另外两条小更正：`fetchContactRowsForNudge` 目前**没有导出**；`useOpenContactFromNudge` 是「同一页内点要催名单开抽屉」的钩子，**跨页直达靠的是 `crm/all/page.tsx` 读 `?contact=`**，v0.1 把两者说成一回事了。

## 3 页面长什么样

### 3.1 放在哪
新开页签「付款总览」，地址 `/dashboard/clients/<id>/crm/payments`，`CrmTabs` 的 `active` 从两个值扩成三个。理由：这是整个客户层面的汇总，塞进客人抽屉逻辑上不成立；「全部客人」那页已经很重，单独一页可以独立取数、独立显示空状态，门禁沿用同一道闸。

## 4 数字怎么算（逐条定死）

1. **订单** = 这一组里没取消的订单张数。订单数永远是主数字，这一轮**不做人数列**（§8）。
2. **定金已收 / 尾款已收** = 对应那条付款记录 `state = 'paid'` 的订单张数。
3. **未收齐** = 至少有一项「未收款、且没标线下已处理」的订单张数。括号里的「其中 M 单已过期」= 这些单里，那类项目算出来的到期日早于今天的张数。
4. **线下已处理** = 至少有一项「**未收款**且标了 `quiet`」的订单张数（已经收到款的项就算标过 `quiet` 也不数——SQL 的 quiet 动作没有检查付款状态，所以必须在统计里自己加这个条件）。**不计入未收齐**。这一列和「未收齐」可能数到同一张订单（一项线下处理、另一项还真欠着），所以**两列不互斥、不能相加**。
5. **最近到期日** = 这一组里所有「未收款、没标线下已处理」项目的到期日取最早的一个；一个都算不出来或全收齐 → 显示「—」。
6. **已收齐不单独显示一列**（与未收齐重复）。但测试里仍单独算出来做交叉验算（§7.2）。
7. **没选出发日期的单**：归到最后一行「出发日期还没定」，算订单数、算定金已收、**定金照算到期日和过期**（预订日 + 3 个工作日，`computeDepositDueOnly`）；只有**尾款**不算到期也不算过期。**有出发日期但「到期日算不出来」的订单**（`buildBookingView` 的 `unavailableWithFallback` 分支：尾款到期日为 null，定金退回自己的日期）与没选出发日期**同一待遇**：算「未收齐」，定金照算过期，尾款不算过期。
8. **到期日一律复用现成逻辑**：`booking-schedule.ts` 的 `computeMilestoneDueDates`，经 `booking-view.ts` 的 `buildBookingView` 调用 —— 跟客人抽屉、「付款要催」走同一条路径，**不许在这一页另写一遍，更不许写成 SQL 里的日期计算**。今天按 Pacific/Auckland 算（`nzTodayIso`）。员工手改过的到期日（`due_override_on`）优先。
9. **分组键是 `departure_id`，不是日期**（`departure_id` 为空的自成一组）。显示的日期用**线上现值，取不到才用快照**并在那行标「目录里已找不到这个出发日期」；团名取不到标「团目录里已找不到这个团」。出发日改过的行带现有的「出发日变了，请确认」标记（复用 `BookingWarningCode`，不新造文案）。
10. **「已出发」与「看不到日期」怎么判**：过去/未来**只看 `effectiveDepartOn`**（线上现值，取不到才用订单上存的快照 `departure_depart_on`）。出发日期被从团目录删掉、但快照还在 → 用快照判过去/未来，并标「目录里已找不到这个出发日期」。**`departure_id` 还在、但现值和快照都没有日期** → 这种行叫「日期不明的出发」，只要还有未收款就**一律留在默认视图里**（不能因为判断不了是不是过去就把欠钱的单藏起来），排在「出发日期还没定」前面。
11. **默认看哪些行**：未来出发的全部 + **任何还有未收款的过去出发**（那种行标「已出发」）+「出发日期还没定」那一行。已经出发且已经收齐的才收起来，一个开关可以打开。理由：已出发但尾款没收是最该追的钱，默认藏起来就看不见了（「付款要催」名单对过期超过 14 天的只折叠成一个数字，所以它也补不上这个洞）。
12. **取消的单**：所有列一律排除，但单独数出来显示「另有 N 单已取消」，下半清单的状态筛选里能看到。

## 5 怎么取数、快不快

做法定为**全部读出来、在 TypeScript 里汇总**，不做数据库视图或汇总函数。理由：① 到期日必须用 `computeMilestoneDueDates`，照数据库那条路要在 SQL 里把工作日、假日顺延、90/120 分档、邮轮、快照规则再写一遍，两份实现迟早对不上；② 加数据库对象 = 一次 A 级迁移，为一个只读汇总不值；③ 量太小。

### 5.1 必须新增的四个读取函数（点名，免得以后有人硬套 nudge 的读取）
| 新函数 | 确切语义 | 为什么不能用现成的 |
|---|---|---|
| `listBookingsForOverview(db, clientId)` | 该客户**全部**订单，`active` 和 `cancelled` 都要，用 `fetchAll` + `order('id')` 分页读全 | `listActiveBookingsByIds` 写死 `status='active'`，数不出取消单 |
| `listMilestonesForClient(db, clientId)` | 该客户**全部**付款记录，`paid` / `unpaid` / `quiet` 全要 | `listUnpaidMilestonesForClient` 写死 `state='unpaid'` + `quiet=false`，算不出「定金已收/尾款已收」和 quiet 数 |
| `listContactNamesForClient(db, clientId, ids)` | **只读姓名**：`contacts` 的 `id, display_name`，按 100 一批 | `listContactsForNudge` 连带全量读 `contact_touchpoints` 判拒联，与本页无关且 CTS 已 1271+ 行在涨（也可改为导出现有的 `fetchContactRowsForNudge`，但它现在没导出，且仍带 `do_not_contact` 列） |
| `listPaidStageContactsWithoutBooking(db, clientId)` | W8 那份「付过钱但没订单」的名单：该客户 `contacts` 里 **`stage IN ('deposit_paid','paid_full','traveling_soon')`**（线上实数 16 + 5 + 8 = **29** 位）。🔴 注意 `src/lib/crm/agent-customer-stages.ts` **只认识** `deposit_paid`，不认识 `paid_full`（由 `payment-email-detect-run.ts` 与 `stage-from-conversation.ts` 写入）和 `traveling_soon`，所以这三个值必须写成本函数自己的常量并注明来源，**不许**从那个文件推导（照做会只数到 16）。`completed`（已出行）线上 0 人、且出行已结束，不纳入；以后出现再说。并且在 `crm_bookings` 里**一张订单都没有**（含已取消的也算「有」，避免取消过的人被反复提醒）的客人，只返回 `id, display_name, stage`，上限 200 行（超了显示「还有更多」，**不**悄悄截断数字：顶部的「29 位」用 count，名单才分页） | 页面上的「看名单」和空状态提示都靠它；现成读取里没有任何一个按「阶段 + 没订单」查 |

团与出发日期继续走 `loadCatalogFacts` → `booking-facts.ts`（按 100 一批）。然后对每单调一次 `buildBookingView` 再汇总，**不存在 N+1**。

### 5.2 顶到天花板怎么办（Z1/W3）
汇总**不设候选上限**。`fetchAll` 的 `hardCap` 沿用现有读取的 20000，顶到就抛错 —— 接口把它变成一个明确的失败响应，页面**拒绝渲染汇总**，只显示「订单太多，这页的数字暂时算不出来，已经报给开发」。**绝不显示偏小的数字**：汇总被截断会让每一列都悄悄变小，一条页面级提示也说不清哪一行错了。下半清单仍然服务端分页，每页 50 行，按出发日期近的在前。

**预计规模**：CTS 最多 32 个未来出发日期；就算哪天到 500 单，也就是 500 行订单 + 1000 行付款记录 + 33 个团 + 34 个出发日期。

## 6 权限与暴露面

- 沿用 `requireBookingAccess(clientId, 'view')`，不新建闸、不放宽。不在名单上的人（也不是 ME 全局管理员）这一页什么都不渲染，**页签也不显示**——机制：新增一个极小的只读接口 `GET /api/clients/[id]/crm/bookings/access`（只过一遍 `requireBookingAccess('view')`，通过返回 `{ok:true}`，不查任何别的表），`CrmTabs` 挂载时探一次，**200 才显示页签，403/404/网络出错一律不显示**（出错不显示比误显示安全，也不暴露「这个功能存在」）；客户没配 `booking_schedule` 或配成关闭 → 404。操作人只取登录会话邮箱，不读请求体；所有查询都带 `client_id`。这一页只读，不需要 `edit`。
- **本页新暴露了什么（照实写）**：「付款要催」名单只返回到期日在前后 14 天内或没有日期的项，而且**丢掉线下已处理、丢掉已暂停提醒（`remind_after` 在今天之后）、丢掉拒联客人**，行数还受上限（默认 10、最多 100）和 50 条折叠限制。所以这一页新摊开的是四类：**远期未收款**、**线下已处理**、**已暂停提醒**、**拒联客人的付款状态**；外加「谁已经付了」从一次看一个人变成一屏看完。仍然是同一批数据、同一批人、没有新字段、没有金额、没有新的人能看。

## 9 Reuse Statement

**复用了什么**：`requireBookingAccess`（门禁、fail-closed、名单）；`fetchAll` 的分页与抛错行为；`buildBookingView` / `nzTodayIso`；`computeMilestoneDueDates` / `computeDepositDueOnly`（**不另写一份到期日逻辑**）；`BookingWarningCode` 与「定金 / 尾款」文案常量；`booking-http.ts` 的响应与 Server-Timing 写法；`CrmTabs` 页签导航；`all/page.tsx` 现有的 `?contact=` 直达机制；`booking-options.ts` 的未来出发日期口径（空状态那个数字）；团目录唯一读口 `booking-facts.ts`。

**没复用、且说明了为什么**：`listUnpaidMilestonesForClient`、`listActiveBookingsByIds`、`listContactsForNudge` 三个 nudge 读取，语义对不上（§5.1），改为新增三个读取函数；`booking-nudge.ts` 的候选上限 + 截断标记这个模式**明确不沿用**（汇总页截断等于每列都变小，§5.2）。

**平台共享（L1）**：汇总的纯函数（一组订单 + 付款记录 → 每个出发日期的几个计数）、只读汇总接口、这两张表的界面。里面没有客户名、客户 ID、金额，也没有行业词。
**行业专属（L2 旅游）**：「按出发日期分组」「定金 + 尾款两段」这个形状，沿用已有的 `industry/travel-booking-rule.ts`，本稿不改它。
**客户专属（L4 CTS）**：只有 `clients.leads_config.booking_schedule` 里的数字和开关，以及 `crm_booking_members` 里的两个邮箱。共享代码里没有 CTS 的名字、ID 或数字；没配这块的客户整个页签不出现。
**团目录边界**：本页不提任何 `tour_catalog_*` 表名、不引团目录的其它模块，团名与出发日期一律经 `booking-facts.ts` 取，这一轮不加列。
**学习沉淀**：不产生跨客户学习。等有第二家旅游客户用上，再判断「按出发日期汇总」能不能升到行业手册。
**快速自检**：把 CTS 换成另一家旅行社，只改 `booking_schedule` 的数字和名单；换成悉尼地产客户，只换行业规则（定金 + 交割），这两张表和汇总函数不动。
