## 0. 先说结论：大半已经有了，真缺口只有四块

查了现有代码（不是凭印象），**以下已经存在，本设计不重做**：

| 已有 | 位置 | 做了什么 |
|---|---|---|
| 改主账户 + 三道闸 | `src/lib/meta/ad-account-binding.ts` / `ad-account-binding-service.ts` | 仅内部员工；同一账户已绑别的客户则拒绝（除非员工写原因覆盖）；用 Graph 核实账户读得到；写审计 |
| 旧账户去留 | `src/lib/meta/ad-account-registry-write.ts` + `MetaAdAccountPanel.tsx` | 改主账户时可勾选「保留为第二账户」；两张表一起写、失败回滚 |
| 账户级日上限 | `src/app/api/clients/[id]/ad-accounts/[accountId]/daily-cap/route.ts` | 仅内部员工；各账户上限之和 ≤ 客户总上限；币种一致；账户必须已绑 |
| 欠款/停用显示 | 作战地图（PR 2935） | 账户状态异常标「不可用」，不计入判断 |

**真缺口（本设计只做这四块）：**
1. **没有候选清单**：FDE 只能手输 `act_数字`，输错或不知道该选哪个。Graph 读取白名单已允许 `me/adaccounts`（`graph-read.ts:13`），但没有任何入口用它列出「这个客户授权的商务管理平台下有哪些账户」。
2. **不能直接加第二账户**：只能走「改主账户 + 勾保留旧的」绕一圈。想给已有主账户的客户再加一个，必须先假装换主账户。
3. **不能单独解绑一个非主账户**：解绑只发生在「改主/清空主」的副作用里。
4. **标签、主账户标记不能单独改**：`label`、`is_primary` 只能在改绑时顺带写。

## 1. 要做什么（用户视角）

在客户设置页现有的「Meta 广告账户」面板（`MetaAdAccountPanel.tsx`）里加一块「已绑定的广告账户」：

1. **列表**：每个已绑账户一行 —— 名称（取自 Meta）、账户号、标签、主/副、状态（正常/欠款停用/其他异常，与作战地图同一套文案）、币种、日上限。
2. **「添加账户」**：点开后列出「该客户授权的商务管理平台下、尚未绑到任何客户」的账户供选择；选中后填标签、币种（只读，取自 Meta）、日上限（可稍后填），确认绑定。
3. **「解绑」**：仅非主账户；主账户要换主账户才能动（走现有流程）。
4. **「设为主账户」/ 改标签**：不改归属，只改标记。

全部仅内部员工（`requireGlobalAdmin`）。客户成员只读或看不到。

## 2. 接口设计（全部新增，挂在现有 `ad-accounts` 路由下）

不新建能力线，不新建表。**表仍是 `client_meta_ad_accounts`**，写入走现有 `ad-account-registry-write.ts` 的回滚思路。

| 方法 路径 | 作用 |
|---|---|
| `GET /api/clients/[id]/ad-accounts/candidates` | 读 `me/adaccounts`（用该客户授权的令牌，沿用 `token-manager` 取令牌规则），返回候选：账户号、名称、状态码、币种、`already_bound_to`（绑在哪个客户名下，没有则空） |
| `POST /api/clients/[id]/ad-accounts` | 绑一个账户为**副账户**（body：`ad_account_id`、`label`、`preview?`）。复用 `bindAdAccount` 里的三道闸，不重写 |
| `DELETE /api/clients/[id]/ad-accounts/[accountId]` | 解绑非主账户；写审计 |
| `PATCH /api/clients/[id]/ad-accounts/[accountId]` | 只改 `label` / 设为主账户（设主账户 = 同时更新 `clients.meta_ad_account_id`，沿用现有双写+回滚） |

`daily-cap` 的 PATCH 不动，仍是上限的唯一入口。

## 3. 校验（每一条都要有机器闸，不靠界面）

1. **只有内部员工**：`requireGlobalAdmin`，与现有一致。
2. **账户必须属于该客户授权的商务管理平台**：候选清单来自 Graph；POST 时**服务端重新读一次**确认该账户在清单里，**不信前端传来的"它在清单里"**。读不到 → 拒绝，fail closed。
3. **不能抢别的客户的账户**：沿用 `findOtherClientRegistrations`；已绑他人 → 拒，除非员工写覆盖原因（现有机制，写审计）。
4. **币种**：新账户币种必须与该客户已绑账户一致，否则拒（理由同 daily-cap 的币种闸：不同币种的上限不能相加）。读不到币种 → 拒，不猜。
5. **日上限合计 ≤ 客户总上限**：绑定时**不强制填上限**，但沿用现有规则「客户绑了 ≥2 个账户而某账户没配上限 → 该账户的自治动作被拒」（`envelope-facts.ts`），所以新加的账户在填上限前**不会被自治动**。这是故意的安全默认。
6. **账户状态**：欠款/停用账户**允许绑定**（要能先绑再排查），但界面显示「不可用」，且作战地图/自治判断已经排除它。
7. **解绑**：主账户拒绝；有在跑广告的账户（最新快照里有 ACTIVE 广告组）拒绝，并说明「先停掉里面在跑的广告」——避免解绑后归属校验失效、广告变成"没人管的在跑广告"。
8. **并发/回滚**：两张表（`clients` + `client_meta_ad_accounts`）双写失败按写前快照恢复，沿用 `ad-account-registry-write.ts`。

## 4. 回执（谁、什么时候、改了什么）

每次绑定/解绑/改主/改标签写一条审计（沿用现有绑定审计表与格式）：操作人、客户、账户号、动作、前后值、令牌来源（`token_source`）、覆盖原因（如有）、结果。**先写审计、再改数据**（现有 AD-SEC-3 的顺序）。不涉及外发、扣费、发布，**不需要 Inngest**（纯同步管理写入，已有审计回执），PR 里写明这条原因。

## 5. 不做什么

- 不做客户自助绑定（客户自己提交仍走现有"待处理请求"→ FDE 处理）。
- 不改运行时跨账户日上限强制（已是 ROADMAP 欠账，另一件事）。
- 不动 `clients.meta_ad_account_id` 的单值语义，不新增列。
- 不改作战地图、不改自治信封。

## 7. 验证计划（实现后）

1. 单测：每条校验各一个"应该拒"的用例 + 变异（去掉该校验，对应用例必须变红）。
2. 用测试数据演练：绑定→填上限→解绑全链路，**不碰真广告**；账户用夹具，不对真实 Graph 写。
3. 当场试跑：候选清单读取是只读 Graph 调用，可对 CTS 真实授权实读一次（只读，PM 已一次性授权只读 API 调查）。
4. 审：子牙 + 魏征设计审（动手前）+ 实施审（动手后）；碰账户归属 → 加狄仁杰攻击验证（尝试绑别客户账户、绕过前端直接 POST）。

## 8. 待审重点（请审的人特别看）

1. 候选清单用哪个令牌：客户授权令牌 vs 共享回落令牌。共享令牌能看到多家客户账户，清单会混入别人的账户（现有代码注释已点出）。建议：**清单只用客户自己授权的令牌，没有则返回空并提示去授权**，不回落共享令牌。
2. "有在跑广告则拒绝解绑"的判据读快照有延迟，是否需要实时读 Graph 再确认。
3. 币种读不到时直接拒，会不会让新客户第一个账户也绑不上（第一个账户没有"已绑账户"可比，应放行并记下币种）。
