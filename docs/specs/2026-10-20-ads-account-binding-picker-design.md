# 广告户绑定：从授权商务管理平台选账户（设计稿 v2，仅设计，未写代码）

- 日期：2026-10-20　窗口：119　风险级别：**A**（账户归属 = 谁能被停广告/改预算；碰钱的上限；要加数据库迁移）
- 状态：v2，吸收子牙+魏征第一轮意见（均为「改设计再审」）；审完前不写代码
- v1 → v2 主要变化：POST 不再调 `bindAdAccount`、去掉覆盖开关；账户号全局唯一改由数据库保证；单事务；审计迁移；钱闸连锁（先配上限、绑后立刻抓快照）；欠款账户实时读状态；候选清单只用客户专属令牌；复用 `ai/manage.ts` 的 discover。

## 0. 现状与真缺口（已核对代码）

已有，不重做：
- 改主账户三道闸 + 审计：`src/lib/meta/ad-account-binding.ts`、`ad-account-binding-service.ts`
- 改主账户时「保留旧的为第二账户」：`ad-account-registry-write.ts` + `MetaAdAccountPanel.tsx`
- 日上限唯一入口（合计 ≤ 总上限、币种一致）：`ad-accounts/[accountId]/daily-cap/route.ts`
- 账户列举：`src/lib/meta/ai/manage.ts` 已有 `discover(...)`（读 `adaccounts`）—— **候选清单复用它**，不另写 Graph 调用（v1 说「没有 discover 入口」不实，已更正）
- 作战地图的账户状态文案：PR 2935 合并后复用 `account-status.ts`

真缺口：①没有候选清单入口 ②不能直接加副账户 ③不能单独解绑非主账户 ④标签/主账户标记不能单独改。

## 1. 为什么这件事比看上去危险（来自两审，写进设计前提）

1. **读取方一旦登记表有行就不再回落旧列**（`client-ad-accounts.ts:49`、`campaign-ownership.ts:58`、`common.ts:54`）。对「零行 / 只有旧列」的客户直接加一条副账户，主账户会从归属闸、数据同步、上限里**静默消失**。
2. **绑第 2 个账户的瞬间，原账户也变成「日上限未配置」**（`envelope-facts.ts:696`：已登记 ≥2 个且本账户没配上限 → 拒，含暂停类动作），整客户加预算被拒。
3. 内核**没有**账户状态判断；欠款账户不会被内核自动排除（v1 §3.6「已排除」不实）。
4. 跨客户唯一性目前只在应用层，并发可双绑。

## 2. 要做什么（用户视角）

客户设置页 `MetaAdAccountPanel` 里「已绑定的广告账户」区（**扩展现有 `GET ad-accounts`，不另建列表接口**）：
1. 列表：名称（取自 Meta）、**脱敏账户号**、标签、主/副、状态（复用 `account-status.ts` 文案）、币种、日上限。**不显示商务管理平台号，不显示他客户名**（见 §6）。
2. 「添加账户」：候选清单 → 选 → 标签 → 在同一流程里把**所有账户（含现有的）的日上限补齐** → 确认。
3. 「解绑」：仅非主账户。
4. 「设为主账户」/ 改标签。

全部仅内部员工（`requireGlobalAdmin`）。

## 3. 接口

| 方法 路径 | 作用 |
|---|---|
| `GET /api/clients/[id]/ad-accounts` | 扩展：已绑账户的状态/币种/上限（实时读 Graph 状态，读不到标「未知」） |
| `GET /api/clients/[id]/ad-accounts/candidates` | 候选清单，规则见 §4 |
| `POST /api/clients/[id]/ad-accounts` | 绑一个账户。**不调 `bindAdAccount`**（它会改主账户）；**无覆盖开关** |
| `DELETE /api/clients/[id]/ad-accounts/[accountId]` | 解绑非主账户（条件删除） |
| `PATCH /api/clients/[id]/ad-accounts/[accountId]` | 改标签 / 设为主账户 |

`daily-cap` PATCH 不动，仍是上限唯一入口；绑定流程在前端按顺序调用它，**后端以 PATCH 的返回为准**（沿用「界面不自己算校验」）。

## 4. 候选清单与令牌（裁决 B①）

- 令牌 = 数据管道实际在用的那把：`resolveMetaTokenDetailed`（与 `snapshot-sync.ts:242` 同源）。
- **客户必须存在，且令牌来源是客户专属**；来源是 `shared_fallback`（共享令牌）、`ownership_unknown`、或无令牌 → **清单返回空 + 提示「该客户没有专属授权，请先授权」**，不回落共享令牌，不用客户 OAuth 另找。
- 复用 `ai/manage.ts` `discover`；候选只含：账户号、名称、状态码、币种。**不含**商务管理平台号；「已绑他人」只返回布尔 `bound_elsewhere`，不返回客户名。
- **清单只是便利，不是授权证据**：同一把令牌读出的清单证明不了归属（`ad-account-binding.ts:15` 已写「读到 ≠ 属于」）。因此**删除 v1 §3.2「必须在清单里」这条校验**，不做循环验证；归属的真防线是 §5 的数据库唯一约束 + 内部员工人工选择 + 审计。

## 5. 校验与数据库约束（A 级迁移）

**迁移 1：账户号全局唯一。** 在 `client_meta_ad_accounts` 上加按规范化账户号（去 `act_`、去前导零，同 `canonicalAccountDigits`）的**全局唯一索引**。上线前先查生产是否已有重复（有则先清，迁移前置检查，**不自动合并**）。覆盖「并发双绑」「`123` 与 `act_123` 异形重复」；**同一客户内的异形重复**也由它挡住（v1 的 `findOtherClientRegistrations` 排除了本客户，不够）。

**迁移 2：审计表 action 扩值。** `meta_ads_registry_audit.action` 的 CHECK 现只有 `bind / clear / request / dismiss_request`（`20260913120000:29`）；新增 `add_secondary / unbind / relabel / set_primary`。RLS 不变，**仍写 `FOR ALL TO service_role`**。数据库触发器 `meta_ads_registry_guard` 抛 23514 时，路由映射成 **409**，不报 500。

POST 校验（服务端，全部 fail closed）：
1. 仅内部员工。
2. 规范化账户号（`parseAdAccountInput`）；与本客户已有行比对（含异形）。
3. **零账户 / 只有旧列的客户**：POST 副账户**拒绝**，提示走「设主账户」流程（避免 §1.1 的静默丢主账户）。设主账户时同步写旧列，沿用现有双写。
4. **币种（裁决 B③）**：客户第一个账户放行并记币种；第 2 个起必须与现有账户币种一致；读不到币种 → 拒。结论写入审计。
5. **日上限先行**：新增前，**现有每个账户必须已配日上限**，否则拒并提示先补（见 §1.2）；流程内把「给两个账户补上限」并入同一向导。
6. **绑后立刻抓一次该账户快照**（否则新账户没有账户级快照，上限 PATCH 读不到币种会 409：`daily-cap:165`）。抓不到 → 绑定回滚并报错，不留半成品。
7. 欠款/停用账户允许作为**副账户**绑定（便于排查），界面标「不可用」；但**设为主账户必须实时读状态 = 1**，否则拒。

## 6. 事务、竞态、回滚

- 全部写入改为**单个数据库事务函数**（一个 RPC / SQL 函数，内含登记表 + `clients` 旧列 + 审计），**取消**应用层「写前快照→失败恢复」（它在并发时会删掉别人刚加的行：`registry-write:100`）。
- DELETE：**条件删除**（`is_primary = false` 且命中恰好 1 行），0 行 → 409；防与「设主」竞态。
- 「换主账户默认删旧户」（`registry-write:77`）改为**明确选项**，界面必须让员工选「保留为副账户 / 移除」，不再默认删。
- 继承缺陷一并修：现有回滚快照漏了 `daily_budget_cap_cents`（`registry-write:46/105`）；改单事务后此问题随之消失，迁移 PR 里补测试证明。
- **无主账户的客户加副户**：日同步会跳过它（`pullback:35`）→ §5.3 已禁止。

## 7. 解绑（裁决 B②）与解绑后的钱闸

- 主账户拒绝解绑。
- 账户状态 ≠ 1（欠款/停用）→ **直接放行**（旧快照里的 ACTIVE 会永久拦住它，不能作依据）。
- 状态 = 1 → **实时查 Graph** 是否仍有在投广告；活跃判定取**四态**（`DELIVERING_STATUSES`，`context:48`，不只 ACTIVE）；**读不到 → 拒**；账户与别的客户共用时，只能由员工写原因覆盖，并记审计。
- 解绑后后果必须写进界面确认语并记审计：归属闸**会拒绝**对该账户内广告的止损；总闸**不再计入**其花费。因此解绑前界面显示「该账户内仍有 N 个广告，解绑后系统无法替你止损」。

## 8. 敏感信息

响应与审计**不得**含：商务管理平台号、其他客户的名字、完整令牌来源细节（只记 `token_source` 枚举）。跨客户冲突只回「该账户已被占用」。现有 `binding-service.ts:133` 的写法要改，作为本 PR 的一部分。

## 9. 复用与小项

- `runChecks`（`binding-service:74`）未导出：先抽出为可复用函数，POST/PATCH 共用，不复制。
- `label` 纯展示，**不参与任何逻辑**；代码里写死的「主账户」标签，换主后旧主仍带该标签 → 换主时一并改标签。
- 不新增表、不改能力线；L3 Connector 管理面，挂在广告支柱账户登记下。换客户 / 换行业代码均不用改。
- 不需要 Inngest：纯同步管理写入，已有审计回执；PR 里写明原因。

## 10. 不做什么

客户自助绑定；运行时跨账户日上限强制（ROADMAP 欠账）；改作战地图；改自治信封；自动合并重复账户。
