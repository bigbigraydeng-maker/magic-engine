## 2. 为什么危险（设计前提）

1. 读取方只要登记表有行就不再回落旧列（`client-ad-accounts.ts:49`、`campaign-ownership.ts:58`、`common.ts:54`）。对「零行 / 只有旧列」的客户直接加副账户，主账户会从归属闸、同步、上限里静默消失。
2. 绑第 2 个账户的瞬间，原账户也变成「日上限未配置」（`envelope-facts.ts:696`），整客户加预算被拒。
3. 内核没有账户状态判断。
4. 跨客户唯一性目前只在应用层，并发可双绑。
5. 共享令牌能看到多家客户账户：「读得到 ≠ 属于」（`ad-account-binding.ts:15`）。

## 3. 令牌来源（裁决，**候选清单与 POST 同一规则**）

- 令牌 = 数据管道实际在用的那把：`resolveMetaTokenDetailed`（与 `snapshot-sync.ts:242` 同源）。
- 客户必须存在且令牌来源是**客户专属**；`shared_fallback`、`ownership_unknown`、无令牌 → **候选清单返回空 + 提示先授权；POST 一律拒绝**。这样绕开清单直接 POST 也绑不了共享令牌能看到的账户（v2 漏洞：`runChecks` 放行共享令牌，`service:78`）。
- **读取账户列表的方式（二选一，已定：抽 helper）**：`ai/manage.ts` 的 `discover` 只吃客户 OAuth 连接、要求授权人本人且试点已开通（`manage:54`、`store:27`），还占 Ads-AI 限流（`reserveRead`），与「用专属令牌」互斥，**不直接调用**。做法：从 `discover` 里**抽出一个只管分页读 `adaccounts` 的纯读取函数**（入参=令牌，不含限流/连接逻辑），`discover` 改为调用它（行为不变，原测试保持绿），候选清单用同一函数 + 专属令牌。
- 候选字段只含：账户号（脱敏显示）、名称、状态码、币种、`bound_elsewhere`（布尔）。**不含**商务管理平台号，不含他客户名。
- 清单只是便利，不是归属证据；归属的真防线是 §5 唯一索引 + 内部员工人工选择 + 审计。**不设「必须在清单里」校验**（循环验证）。

## 4. 接口（第一刀）

| 方法 路径 | 作用 |
|---|---|
| `GET /api/clients/[id]/ad-accounts` | 扩展现有：已绑账户的名称/脱敏号/标签/主副/实时状态/币种/日上限；状态读不到显示「未知」 |
| `GET /api/clients/[id]/ad-accounts/candidates` | 候选清单，规则见 §3 |
| `POST /api/clients/[id]/ad-accounts` | 加一个副账户。**不调 `bindAdAccount`**；**无覆盖开关**；请求体只接受 `ad_account_id`、`label`、`daily_budget_cap_cents` |
| `PATCH /api/clients/[id]/ad-accounts/[accountId]` | **只改 `label`**；请求体出现其他字段 → 400；路径 `accountId` 必须属于该客户，否则 404 |

仅内部员工（`requireGlobalAdmin`）。`daily-cap` PATCH 仍是上限唯一入口，POST 内部按顺序调用其逻辑，**以它的返回为准**。

## 5. POST 校验（服务端，全部 fail closed）

1. 内部员工；令牌来源见 §3。
2. 规范化 `parseAdAccountInput`；**该客户必须已有主账户且登记表里有行**。零行 / 只有旧列 → 拒，提示见 §6。
3. **币种**：读不到 → 拒；与现有账户币种不一致 → 拒（理由同 daily-cap 币种闸）。结果写审计。
4. **日上限先行**：现有每个账户必须已配日上限，否则拒并提示先补（§2.2）；新账户本次必须同时给上限；各账户上限之和 ≤ 客户总上限（沿用 daily-cap 规则）。
5. **状态**：欠款/停用账户允许作为副账户绑定（便于排查），界面标「不可用」。
6. **重复**：规范化后与本客户已有行比较（含 `123` vs `act_123`）；跨客户由数据库唯一索引兜底，冲突只回「该账户已被占用」，不泄露客户名。
7. **绑后立即抓快照，必须一次抓全部账户**（不是只抓新账户），否则 `envelope-facts.ts:165` 判「非同一轮」，加预算被拒。快照是外部读，**不能进数据库事务**：流程是「先写库（事务）→ 再抓快照；抓取失败则执行**补偿删除**（条件：该行刚创建、非主账户）并报错」。补偿本身失败 → 记审计并在待办里挂一条人工任务（what/how/href 三件套），不假装成功。
8. 审计先于数据变更写入；审计写失败 → 不写数据。

## 6. 只有旧列的客户（本期临时处理）

面板 dirty 判断（`MetaAdAccountPanel:179`）不允许原值重存，新列表又读不到这类客户的行，指引会成死路。**本期不做迁移入口**，临时办法：POST 对这类客户返回明确错误「该客户尚未迁入账户登记表，请联系开发处理」，并在审计里记一条 `blocked_legacy_only`；同时把这类客户数量列入验证计划（§10.2）——若第一刀要服务的客户（CTS）已有登记行则无影响。迁移入口作为「后续」另设计。

## 7. 数据库（A 级迁移，第一刀）

1. **唯一索引**：不重造归一化。用「格式 CHECK + 普通唯一索引」：存储前统一为 `act_<数字>`（应用层 `parseAdAccountInput` 已保证），数据库加格式 CHECK（`^act_[1-9][0-9]{9,24}$`）+ 对 `ad_account_id` 的普通唯一索引。存量行不符合格式的，迁移前置检查并列出，**不自动改**。注意：该索引管不到 `clients.meta_ad_account_id` 旧列（旧列漂移仍可能与别的客户重复），这是已知范围，另由旧 PATCH 的现有重复检查负责。全局唯一与「共用账户可由员工覆盖」（`service:46`）互斥：**第一刀 POST 不提供覆盖**；旧 PATCH 的共用覆盖流不受影响，但需先过 §8 的收紧。现成函数 `meta_ads_registered_match`（`20260920064556:93`）仅作存量查重参考。
2. **审计扩值**：表是 **`client_binding_audit`**（`20260913120000:29`），其 `action` CHECK 现只有 `bind / clear / request / dismiss_request`。第一刀新增 `add_secondary`、`relabel`、`blocked_legacy_only`。RLS 不变，仍 `FOR ALL TO service_role`。
3. **错误码映射**：23514 **不一律转 409**——审计 CHECK 尚未 apply 时同样报 23514。路由按触发来源区分：来自 `meta_ads_registry_guard` 触发器 → 409；来自 CHECK 约束名 → 500 并报「迁移未应用」。
4. **新 RPC（单事务：登记表行 + 审计）** 的权限：`REVOKE ALL FROM PUBLIC/anon/authenticated`，仅 `GRANT EXECUTE TO service_role`，仿 `20260920064556:193`。事务内不含外部读写。

## 8. 旧 PATCH（`meta-ad-account/route.ts:133`）先收紧（第一刀包含）

旧 PATCH 目前可把死户设为主、可覆盖共用、可移除在投旧主，不受本设计校验约束。第一刀内：
- 设主 / 清空主 / 移除旧主：**加两道闸**——目标账户状态必须实时读到 = 1；被移除的旧主账户若状态 = 1 须实时确认无在投广告（四态 `DELIVERING_STATUSES`，`context:48`；读不到即拒）。
- 状态不在上述条件内 → 400 并说明原因。
- 覆盖共用保持现状（员工写原因，有审计），本期不扩大。
- 对「只有旧列」客户的改主行为保持不变（仍可用），不借本期改动。
