## 1. 这份契约要解决的那一个问题

**「这次和上次能不能比」这个问题，今天在仓库里没有任何地方回答得了。**

AI 引擎的答案会因为换模型、换语言、换市场、换问法、换采样数而变。任何一项变了而系统不知道，「排名提升了」就是一句不能证伪的话。测量层唯一的职责就是：**把「能不能比」变成一个可以被机器判定的问题，判不了就明说判不了。**

**测量层拥有**：观测身份 · 证据保全 · 可比性判定 · 覆盖率与成本的如实记录。
**测量层不拥有**：处方 · 执行 · 归因结论。

---

## 2. 范围

**在范围内**：GEO / AI 可见度的观测身份、不可变证据模型、指标定义、可比性判据、成本与覆盖率的诚实表达、对既有两套系统的保守映射。

**不在范围内**：处方生成（Domain Module 的事）· 页面改动（Page 能力的事）· 归因结论（Flywheel 的事）· 具体列名与索引（WP03 的事）· 真实外部调用（WP04 的事）· 引入新 Agent（永久禁止）。

## 3. 观测身份

身份分两层，**职责不同，不许混为一谈**：

- **采集身份（acquisition identity）** —— 我们**当时是怎么问出来的**。它决定「这两次问的是不是同一件事」。
- **解释身份（interpretation identity）** —— 我们**是怎么把原始回答读成结构化指标的**。它决定「这两个数字是不是用同一把尺子量出来的」。

### 3.1 采集身份（七项）

**一次观测的采集身份 = 下面七项的组合。任何一项不同，就是另一次采集，不能直接对比。**

| # | 维度 | 含义 | 为什么少不了 |
|---|---|---|---|
| 1 | **QuerySetVersion** | 这一批问题的不可变版本 | 问题集改了却沿用同一条时间线 = 拿两套题的成绩比高低 |
| 2 | **query_key** | 单个问题的稳定语义键 | 只有行 id 的话，问题被原地改写就无声断链 |
| 3 | **engine family** | 引擎族（跨模型升级保持稳定） | 模型天天变，族级才是可长期追踪的轴 |
| 4 | **model / version** | 具体模型与版本 | 同一族换代会整体平移结果，必须能分开看 |
| 5 | **locale** | 提问语言 | 中文问和英文问是两件事 |
| 6 | **market** | 地域上下文（AU / NZ 等） | ME 的定位是 AU/NZ；不带市场的答案不代表客户的真实处境 |
| 7 | **sample** | 见 §3.2 —— 它本身要拆成三件事 | LLM 有随机性，样本安排不同的两个数不该直接比 |

### 3.2 `sample` 必须拆成三件事

「sample」这个词同时被用来指「问了几次」和「这一行是第几次」，混用会让可比性判定失去依据。**概念上分开**（WP00 不定最终列名，那是 WP03 的事）：

| 概念 | 属于哪一层 | 说明 |
|---|---|---|
| **样本计划 / 数量**（sample plan / count） | **队列或批次**层 | 这一轮打算对每个（问题 × 引擎 / 模型）问几次 |
| **样本序号 / 复本身份**（sample index / replicate identity） | **单条观测**层 | 这一行是这组复本里的第几次；两侧要能各自重建出来 |
| **影响输出的采样参数**（sampling parameters） | 观测层，**可控且可得时**才记 | 例如温度、随机种子一类会实质改变输出的设置。**拿不到就记「未知」，不许编** |

**冻结**：**任一侧的样本计划不同，或任一侧无法重建样本序号身份，这次比较就不算 matched，必须产出 `not_comparable`。**

### 3.3 解释身份（interpretation identity）

结构化 GEO 指标不是原始回答本身，是**读出来的**。所以它另有一层身份：

| 项 | 含义 |
|---|---|
| **parser version** | 把原始回答读成结构的那套解析逻辑的版本 |
| **metric / taxonomy rules version**（适用时） | 指标判据与品牌 / 实体归类规则的版本。比如 `qualified mention` 的判据一改，同一份回答的指标值就会变 |

**parser 置信度不是身份维度。** 它是**质量信号与阈值**：用来决定这条观测够不够格进入统计（见 §6.1 第 3 条），不用来决定「这是不是同一次观测」。

### 3.4 三条附加规则

1. **身份写在观测行上，不是写在问题上。** 只把 `market` 挂在问题上，重跑时换了市场就查不出来。
2. **解析逻辑改了不覆盖历史。** 重新解析产生新的结构化结果 + 新的解释身份，原始回答与旧解析都原样保留（§4.4）。
3. **缺失的维度必须显式记成「未知」，不许省略、不许填默认值。** 省略会让下游把「不知道」误读成「一样」。

## 4. 不可变证据模型

四层，各自的可变性规则不同：

```
QuerySet (versioned, immutable once locked)
   └─ Batch (一次采集执行；append-only)
        └─ Observation (一个问题 × 一个引擎/模型 × 一次样本；immutable)
             └─ Evidence (原始响应 / 引用来源 / 页面关联；immutable)
```

### 4.1 QuerySet

- **版本化**。一旦这个版本被用于采集，它的问题文本**永不可改**。
- 改问题 = 新增问题或发新版本，不是原地编辑。
- 弃用靠停用标记，不靠删除。
- 仓库里已有可直接借鉴的先例：行业级归档用 `question_hash`（问题文本的哈希，UNIQUE）+ `locked_at`（非空即锁死文本）来强制这一点。**客户级现有系统没有这道锁**（§8）。

### 4.2 Batch

- 一次采集执行 = 一个批次。**重跑创建新批次，绝不覆盖旧批次。**
- 批次要记：覆盖了哪些引擎 / 模型 / 语言 / 市场、尝试了多少、成功多少、失败多少、花了多少钱、被谁触发、什么时候开始与结束。
- 批次自己有状态：完成 / 部分完成 / 失败。**「部分完成」是一等结论，不许四舍五入成完成。**

### 4.3 Observation

- **不可变。** 已落库的观测行任何情况下都不修改。
- 重跑产生新的观测行，不是更新旧行。
- 每一条观测都带完整的 §3.1 采集身份七项（含 §3.2 的样本序号），以及产出其结构化字段时所用的 §3.3 解释身份。
- 失败也是观测：调用报错、超时、被限流，都要落一条**明确标为失败**的观测，而不是不落行。**不落行会让「问了但失败了」和「根本没问」在库里长得一模一样**，覆盖率就永远算不准。

### 4.4 Evidence

- 原始响应**逐字保留**，供解析逻辑改进后重新解析。**这是解释身份能起作用的物质前提** —— 只有原始回答还在，两侧才可能「用同一个 parser / 规则版本重新解析一遍」再比（§6.1 第 2 条）。
- 引用来源（AI 答案里引用的 URL）单独结构化保存，因为「有没有引用到客户自己控制的域名」以及「引用的是哪一页」是 §5 里两件不同的事。
- **域名归属**（这个 URL 是不是客户自己控制的域名 / 别名）与**规范页面关联**（它对应客户的哪一个受管页面）**分开记**。前者只需要一份经核实的自有域名与别名清单；后者需要可信的页面台账或确定性的规范化规则。
- 两者都是「能确定才记，不能确定就留空」，**留空绝不等于 0**。
- **重新解析产生新的结构化结果 + 新的解释身份标记，绝不覆盖历史解析。** 历史结论必须能被原样复现。

## 5. 指标定义

七个指标，全部按 §3.1 的采集身份分组统计，并带上产出它们时的 §3.3 解释身份。**每个指标都必须能回答「这个数是从多少次成功观测里算出来的」。**

| 指标 | 定义 | 判定要点 |
|---|---|---|
| **qualified mention**（合格提及） | 客户品牌在答案中被提到，且**是作为该问题的相关答案**被提到 | 顺带出现、否定语境出现、同名异实体出现，都**不算**。判据必须写死，不能靠人看。判据本身有版本（§3.3 的 rules version） |
| **recommendation**（推荐） | 答案把客户**作为建议选项**给出，不只是提到 | 比 mention 强一档；混在一起统计会系统性高估 |
| **citation**（引用） | 答案带出了可点击的来源链接 | 记录来源域名与 URL |
| **owned-domain citation**（自有域名被引用） | 引用的 URL 属于客户**自己控制的域名或别名** | 只需要一份**经核实的自有域名 / 别名清单**就能判。**不需要页面台账** |
| **direct owned-page citation**（具体自有页面被引用） | 上一条成立，**且**该 URL 能被关联到客户的某一个受管页面 | ⚠️ 这一档才需要**可信的页面台账或确定性规范化规则** —— 用来消解重定向 / 别名 / 追踪参数，并支撑页面级 lineage |
| **conditional rank**（条件排名） | **在被提及的前提下**，客户排第几 | 🔴 只在 mention 成立时才有值。把「没提到」当成「排名很靠后的一个数」是最常见的造假形状 —— 那会让一次提及率下降看起来像排名改善 |
| **engine coverage**（引擎覆盖） | 这一批次里，有多少个引擎 / 模型真的成功返回了 | 它是**所有其它指标的分母修正项**，不是一个附属统计 |

三条冻结：

1. **`conditional rank` 永远与 mention 分开报，永远不与「未提及」混算。**
2. **域名归属与页面归属是两档，不是一档。** 域名归属可核实时就能报 owned-domain citation；页面级归属另需页面台账。
3. **没有页面台账时，`direct owned-page citation` 的结论是「不可算」，绝不是 0。** 报 0 会被读成「一次都没被引用」，那是一个不同的、而且是错的事实。

仓库既有的 GEO 指标词汇（`src/lib/flywheel/vocabulary.ts` 的 `geo.query.mention_rate` / `geo.query.avg_rank` / `geo.engine.coverage` 等）在**归因层**继续使用；本契约的七个指标是**测量层**的定义。两者的映射由 WP05 / WP10 显式声明，**不许假定同名即同义**。

## 6. 可比性（matched cohort）与 `not_comparable`

### 6.1 判据（三条，缺一不可）

两组**结构化指标**可比，当且仅当下面三条同时成立：

1. **采集身份匹配** —— §3.1 的七项在两侧逐项一致，且 §3.2 的样本计划一致、两侧都能重建样本序号身份。
2. **解释身份一致** —— 两侧的 parser 版本与指标 / 归类规则版本相同；**或者**两侧都从各自**不可变的原始回答**用**同一个** parser / 规则版本重新解析了一遍。
   > 这就是 §4.4 坚持逐字保留原始回答的用处：解析器升级不会让历史数据作废，只要能用新版本把两边都重跑一遍。
3. **质量阈值达标** —— 两侧的 parser 置信度、引擎覆盖率与失败率都在可接受范围内（阈值由 WP02 定义并写死，**不许每次运行时现算**）。

三条里任何一条不成立 → 结果是 **`not_comparable`**，并且必须带上**是哪一条、哪一项不成立**。

**置信度的角色要说清楚**：它是第 3 条的**质量信号 / 阈值**，**不是**第 1、2 条里的身份维度。置信度低不会让一条观测变成「另一次观测」，只会让它够不够格进统计。

### 6.2 `not_comparable` 是一等结论

- 它**不是错误**，不是数据缺失，不是「暂时先按可比处理」。
- 它必须能被下游读到并如实展示。
- **上游拿到 `not_comparable` 时，不许退化成一个数字继续往下算。**
- 归因（#885 WP10）在拿到 `not_comparable` 时**必须停在可比性闸前**，不许出具任何「提升 / 下降」的结论。

### 6.3 不许做的四件事

1. 不许为了让两侧可比而**丢掉一侧的失败观测**（那会同时抬高两侧的成功率，且抬得不一样多）。
2. 不许把不同模型版本的结果**合并成一个引擎族的平均数**然后声称可比。
3. 不许在样本计划不同时**只比均值**。
4. 不许用「趋势看起来是这样」替代可比性判定。
5. 不许**只升级 parser 就直接对比新旧数字** —— 要么两侧同版本，要么两侧都用新版本重跑一遍原始回答。
6. 不许把**置信度当身份**（「这次置信度高所以是更好的一次观测」），也不许把**置信度低的行悄悄剔掉**而不报覆盖率变化。

## 7. 成本与部分覆盖的诚实性

### 7.1 三条硬规则

1. **预算是硬上限，不是预测值。** 每一步在调用外部服务**之前**就要判「剩下的钱够不够这一步最多花的」，不够就不开跑。跑完之后再判一次实际是否超出声明上限。（两端判据与 Kernel 的成本模型一致，见 [执行内核 v1](./2026-08-08-me2-execution-kernel-v1.md) §5。）
2. **成本 / 覆盖失败必须显式，不许静默转成功。** 预算耗尽导致只跑了一半，结论就是「部分覆盖」，不是「完成」。
3. **外部调用不许超出已授权的额度。** 说不出成本上界的付费步骤一律 fail closed。

### 7.2 部分覆盖结果的最低表达

一个部分覆盖的批次结果必须能回答：

- 计划覆盖哪些引擎 / 模型 / 语言 / 市场 / 问题
- **实际成功**覆盖了哪些
- 差在哪、为什么（预算 / 限流 / 报错 / 超时）
- 在这个覆盖度下，哪些指标**仍然可算**，哪些**不可算**

**冻结：一个部分覆盖的批次不许在任何界面上被呈现成一次完整基线。**

### 7.3 为什么这一条不是洁癖

2026-08-10 只读实测：Roman 名下 252 次客户级 AI 可见度调用中，**36 次报错（约 14%）**。不做覆盖率核算直接把成功那批的比例当基线，会系统性高估 —— 而且高估的幅度会随着下一次的错误率变化而变化，于是「改善」和「这次报错少了点」在数字上完全无法区分。

## 8. 对既有系统的保守映射

仓库里有**两套彼此独立**的 AI 可见度系统，都早于本契约：

| 系统 | 代码 | 表 | 采集 |
|---|---|---|---|
| **客户级 AI Tracker** | `src/lib/ai-tracker/*`（openai / claude / perplexity / gemini 四个 runner + parser + orchestrator） | `ai_visibility_queries` / `ai_visibility_runs` / `ai_visibility_snapshots` | Render cron `ai-tracker-weekly`，周一 01:00 UTC |
| **行业级归档** | `src/lib/industry-ai-visibility/*` | `industry_ai_visibility_questions` / `_snapshots` / `_runs` | Render cron `industry-ai-visibility-daily`，每日 02:30 UTC（路由名仍叫 `ai-visibility-weekly`，是历史遗留） |

### 8.1 映射矩阵（逐维度）

| 本契约要求 | 客户级现状 | 行业级现状 | 保守处置 |
|---|---|---|---|
| **QuerySetVersion** | ❌ 无版本概念，问题可原地改写 | ⚠️ 有 `locked_at`（锁死文本）但**没有集合版本** | 一律映射为 **未知**。禁止用「采集日期」冒充版本 |
| **query_key** | ❌ 只有行 id | ✅ 有 `question_hash`（文本哈希，UNIQUE） | 客户级 → 未知；行业级 → 可映射 |
| **engine family** | ✅ 有引擎字段（封闭 CHECK） | ✅ 有平台字段 | 可映射 |
| **model / version** | ⚠️ 有模型名，但是**自由文本** | ⚠️ 同上 | 可映射，但必须标注「自由文本、未受控词汇表」 |
| **locale** | ❌ 观测行上没有 | ✅ 问题上有语言字段 | 客户级 → 未知；行业级 → **只能推断到问题层，不是观测层**，仍标降级 |
| **market** | ⚠️ 只在**问题**上有市场标签，观测行上没有 | ✅ 问题上有国家 / 城市 | 一律标注「来自问题层，非观测层」 |
| **sample plan / count**（§3.2） | ❌ 无 | ❌ 无 | 一律 **未知** |
| **sample index / replicate**（§3.2） | ❌ 无 | ❌ 无 | 一律 **未知** —— 因此 §6.1 第 1 条在 legacy 上永远成立不了 |
| **sampling parameters**（§3.2） | ❌ 无 | ❌ 无 | 一律 **未知** |
| **parser version**（§3.3） | ❌ 无 | ❌ 无 | 一律 **未知** —— 因此 §6.1 第 2 条也成立不了 |
| **metric / taxonomy rules version**（§3.3） | ❌ 无 | ❌ 无 | 一律 **未知** |
| **parse confidence**（质量信号，非身份） | ❌ 无 | ✅ 有 | 客户级 → 未知，因此 §6.1 第 3 条无法判定 |
| **citation evidence** | ❌ 客户级观测不保存引用来源 | ✅ 有 AI 引用来源数组 | 客户级 → **不可映射**，`citation` / `owned-domain citation` / `direct owned-page citation` 在客户级历史数据上**无法回算** |
| **raw response** | ⚠️ 有原始文本 | ✅ 有原始响应（jsonb）+ 明确的「留着重新解析」设计意图 | 都可映射。**这是将来「用同一 parser 版本两侧重跑」唯一的物质基础** |
| **失败观测是否落行** | ⚠️ 有错误字段，能区分 | ✅ 有错误码 / 错误消息 | 可映射 |

### 8.2 映射规则（冻结）

1. **legacy 映射的产物相对 ME2 的新观测一律标记为 `not_comparable`。** 理由现在是**双重**的：采集侧缺 QuerySetVersion 与全部三项 sample 概念（§6.1 第 1 条不成立），解释侧缺 parser / 规则版本（§6.1 第 2 条也不成立）。
2. **历史真相不许改写。** 映射是**只读投影**，不回写、不补齐、不「修正」任何历史行。
3. **缺失维度标「未知」，不填默认值。** 尤其禁止用采集日期冒充查询集版本、用问题层的市场冒充观测层的市场、用「当前 parser」冒充历史 parser。
4. **客户级历史数据不能用来算任何一档 citation 指标。** 数据根本不在，算出来的一定是 0，而 0 会被读成「一次都没被引用」这个错误结论。
5. legacy 投影**可以**用于「大致趋势」的人工参考，**不可以**用于任何自动化的归因、学习或客户可见的成效声明。
6. **未来若要让某批 legacy 数据参与比较，唯一合法的路径是**：用一个确定的 parser / 规则版本，把两侧的**不可变原始回答**各自重新解析一遍，并且采集侧的缺口（尤其 sample）已被独立补齐或明确接受为不可比。**不许靠给历史行补一个假的版本号来"打平"。**
