# 「开投/启用」那一步的日预算上限检查 · 设计 v0.3（增量稿）· 只设计，未写代码 · 119 号 · 2026-10-21

> 在 `…-v0.2.md` 之上的增量：**冲突处以本稿为准**。吸收子牙+魏征对 v0.2 的复审。风险级 **A**（碰钱）。

## 1. 取数口径还有两处错（改正）

1. **新鲜度看抓取记录，不看实体行的时间**：v0.2 要求复用 `coverageProblem`，但它用「最新一行的时间」判新鲜度（阈值 2 天，`promo-draft-facts.ts:160/182`）。快照**只在变化时写行**，稳定账户几天没有新行是正常的，会被误判为「不新鲜」而永久拒绝。改为：**新鲜度只看 `ad_snapshot_captures`**——每个相关账户、每个层级（campaign/adset）最近一次 `complete=true ∧ skipped_shared=false` 的抓取，其 `captured_at` 距今不超过阈值（建议 6 小时；因为启用前我们会同步抓一次，实际是「这次抓取是否完整」）。`coverageProblem` 只保留其「覆盖面」判断部分，不用它的新鲜度判断；实现设计里抽出一个只含覆盖面判断的共用函数。
2. **不设回看窗口**：草稿路径读快照只回看 35 天（`promo-draft-facts.ts:426`），超过 35 天没变的广告组读不到、会被漏算。启用闸对每个实体**取最新一行，不设回看窗口**（自己的查询：按实体取 `captured_at` 最大的一行，排除 `disappeared`；实体数量级是几百，可接受）。
3. **排除账户的判断要先于「每个账户都抓全」的检查**：个人号（欠款停用）永远抓不全，若先要求所有账户 `complete`，闸会永久拒绝。顺序改为：先按账户状态确定**参与合计的账户集合**（§2），再只对这个集合要求抓取完整。

## 2. 账户排除：方向要安全（改正 v0.2 的「状态≠1」）

- v0.2 写「复用 `account-status.ts`」不成立：该文件只有 `isClosedAccountStatus`（2/100/101，不含 3），且「≠1 即排除」方向不安全——Meta 账户状态 **9（宽限期）仍在投放**，被排除会让合计偏低、**误放行**。
- 改为**只排除明确不投放的状态集合**：初稿 = `{2 已停用, 3 欠款/未结算, 7 风控审核中, 100 待关闭, 101 已关闭}`（**具体清单必须对照 Meta 官方账户状态文档核对后写死，实施前核实；我现在不能证明 7 一定不投放**——若不确定，宁可不排除，使合计偏高、方向安全）。8（待结算）、9（宽限期）与状态 1 一律**计入**。
- **状态读不到 / 过旧 → `cap_unreadable`**（既不当可用也不当不可用）。新增判断函数（新写，不假装复用）：`isNonDeliveringAccountStatus(code)`，放 `account-status.ts` 并配测试，口径变更必须同步改测试。
- **账户从排除集恢复正常**（例如旧主账户充值后状态变回 1，4 个老系列恢复花钱）：闸每次都**现场按当前账户状态重算**，恢复后的账户会自然计入合计，**启用会被拦到合计回到上限以内**（无需额外机制）；残余风险是恢复后「已在投」的广告在被发现前继续花钱——由每日审计兜底（审计在账户状态由排除变为计入的当天出红待办）。

## 3. 并发：采用「备选」，撤回预留表（两位）

魏征指出预留表方案有**硬反例**：公式 `传入的在投合计 + 未过期 reserved + 本次`，A 提交后标 `consumed` 不再计入，而快照还没追上；B 此时进锁看到 `134 + 0 + 10 = 144`，实际已是 `154`。并且 15 分钟 TTL 到期时 Meta 调用可能还在跑或结果丢失、进程在标 `consumed` 前挂掉，预算既不在预留也不在快照里。要修就要「锁内重算、`consumed` 在快照追上前继续计入、TTL 过期且结果未知先读 Meta 核实再释放」——复杂度远超收益。
- **决定：撤回预留表方案**，采用 v0.2 的**备选**：把「同一客户并发启用可能穿越上限」**写成已知残余风险**，由 PM 确认接受。理由：目前**只有 PM 本人**能启用（`requireSpendActivationAuthority`），实际并发概率极低；穿越幅度最多是「同时启用的几条之和」，且每日审计会在一个周期内发现。
- 待 PM 确认（不替定）：接受此残余风险。

## 4. 「所有会让花钱预算变大或开始花钱的入口」全清单（魏征）

逐个标：**闸**（本设计加的检查）/ **内核**（已有信封硬拦）/ **残余风险**。**加测试**：用一个架构测试扫描全仓对 `setAdSetStatus(..., 'ACTIVE')`、`setCampaignStatus(..., 'ACTIVE')`、对 Meta 的 `status: 'ACTIVE'` 写入、以及提高 `daily_budget` 的调用点，**每个调用点必须登记在这张清单里**，未登记的新增入口 → 测试红（防止以后新增启用/加预算入口时漏掉闸）。

| 入口 | 位置 | 处理 |
|---|---|---|
| 草稿批准 → 激活三层 | `draft-and-gate.ts approveDraft` → `ad-publisher.activatePublished` | **闸**（block） |
| 重新启用系列 | `meta-ads/execute` `ads.reactivate_campaign` | **闸**（block） |
| 内核：加预算 | `ads.scale_unit_budget`、`ads.budget_move_plan` | **内核**（`isWithinEnvelope` 客户总上限硬拦） |
| 内核：新开再营销广告组 | `ads.add_retargeting_adset`（`new_spend`） | **内核**（同上） |
| 内核：换素材 | `ads.swap_creative`（`creative_only`） | 不增加预算；无需闸 |
| 降预算 | `meta-ads/execute` `ads.adjust_bid`（只允许降低，上调 422） | 无需闸；**测试断言上调仍被拒** |
| 内核暂停的**撤回**（回滚 = 写回 ACTIVE） | `pause-unit.ts`、`pause-campaign.ts` 的 rollback handler | **残余风险**：撤回恢复的是暂停前的状态，但暂停之后别处预算可能已变；写明，不加闸（撤回是失败路径，加闸会让撤回失败更危险） |
| 单个广告组/单条广告重新启用 | 目前代码里没有独立入口（实现前核实）；若有 → 同闸 | 待核实；未登记即测试红 |
| 自动加预算（自治） | 内核 | **内核** |
| 在 Meta 后台/Meta MCP 手建、手调 | 不经 ME | **残余风险** + 每日审计 + 登记入口 warn |
- **系列用 `lifetime_budget`（终身预算）时明确拒绝**：本闸只处理日预算；读到系列是终身预算 → `cap_unreadable`（原因「终身预算，本闸不支持」），不能当成「CBO 加 0」放行。

- §4 账户排除：改为明确不投放集合 + 新函数，状态读不到=拒绝；恢复时靠现场重算。
