# 中国手机号验证码登录 + 用户名密码登录 — 设计方案 v0.2

**状态**：v0.2，已过 子牙（架构）+ 魏征（挑刺）第一轮复审，BLOCKER 已改；进详细设计前建议再走一轮确认
**提出人**：PM（2026-09-28，聊天原话："我们的很多客户人在国内，邮件注册就是一个问题...能不能接入：1. 中国手机号动态验证码登录；2. 简单的用户名密码注册登录"）
**Tier 判定**：L3 Connector（新接一个短信服务商，挂在现有 Supabase Auth 这个平台底座上）+ 现有登录能力扩展一种方式；不新增支柱、不新增能力线，未登记 candidates。

## 1. 问题

`/portal/register` 目前只支持邮箱验证码登录（`signInWithOtp` + 6 位数字码，见 `src/app/api/auth/self-register/route.ts`）。国内客户大量用 QQ/163 邮箱（`register-form.tsx:238` 已经写了"QQ 和 163 邮箱最容易被拦"）或根本没有常用邮箱，注册这一步先天卡住一批潜在自助客户。

补充发现（2026-09-28 当场验证，见 `docs/ledger/`）：现有邮箱验证码本身在生产环境也有 bug——`signInWithOtp` 代码假设 Supabase 邮件模板已经改成显示 `{{ .Token }}`（六位数字），但生产库实际发出的邮件仍是旧版"点链接登录"模板，前端画的 6 个数字格子收不到对应的验证码。这个 bug 独立于本方案，已另外上报，**本方案的手机验证码走向不依赖这个邮箱 bug 修好与否**——手机验证码用自己的发码通道，不经过 Supabase 邮件系统。

## 2. 结论：两个需求是同一条改造线的两半，一起做

- **手机验证码** = 解决"怎么第一次证明这个手机号是你的"（替代邮箱验证码这一步）
- **用户名密码** = 解决"以后不想每次都等验证码"（验证过手机号之后，顺手让客户设一个密码，以后直接密码登录）

两者共用同一套"自助客户登录身份"模型，不是两个独立系统。

## 3. 为什么不能像邮箱验证码一样直接用"发短信"

查了阿里云、腾讯云 2026-09-28 当天的官方文档（不是凭旧印象）：

- **国内短信品牌签名**（短信上显示"来自 Magic Engine"这种）**只批给持有中国大陆营业执照的公司**去申请。魔力引擎是新西兰注册主体，这条路走不通，阿里云、腾讯云都一样卡在这条规则上。
- 腾讯云的"国际/港澳台短信"不需要资质，但那是发给国际/港澳台号码的通道，**发不到中国大陆手机号**，解决不了我们的问题。
- 阿里云有一个专门给"验证码"场景做的独立产品——**短信认证服务（号码认证服务 / PNVS）**：个人实名认证用户即可直接调 API 发送和校验验证码，**不需要企业资质、不需要申请签名和模板**，系统给一个统一的预置签名（类似"验证码：1234，来自云通信"这种通用文案，不会显示"Magic Engine"）和标准模板。

**推荐方案：接阿里云"短信认证服务"**，这是目前唯一一条在没有大陆营业执照的情况下，能把验证码送到中国大陆手机号的合规路线。

权衡（如实说清楚，不是"应该可以"）：
- 优点：不需要大陆公司资质、接入快、成功率高（阿里云官方定位就是"低成本、高成功率的验证码解决方案"）
- 缺点：短信显示的是阿里云统一签名，不是"Magic Engine"品牌名——对一次性验证码这个场景通常客户不会在意，但需要 PM 知道这个取舍
- 待确认：这个产品具体的按条单价，公开文档只查到"国内短信 OTP 类 0.045 元/条起"是**普通短信服务**的价格，短信认证服务（PNVS）是否同价或有自己的独立计费，需要真正开通账户那一步才能拿到准确数字（Sources: [短信服务定价](https://www.alibabacloud.com/product/short-message-service/pricing)、[短信认证服务介绍](https://help.aliyun.com/zh/pnvs/getting-started/sms-authentication-service-novice-guide)）

## 4.1 架构缺口：`resolveRedirectForSession` 假设一定有邮箱（子牙复审发现，BLOCKER，必须解决）

`client_portal_users.email` 是 `NOT NULL UNIQUE`，且登录后落地逻辑的唯一入口 `resolveRedirectForSession` 完全按 `user.email` 查这张表——手机号注册的用户如果没有邮箱，验证码能验成功、账号能建成功，但登录后会直接卡在落地逻辑里，走不到自己的客户主页。

**方案**（详细设计阶段拍板具体做法，这里先定方向）：给 `client_portal_users` 加一个可空的 `phone` 列，`resolveRedirectForSession` 增加"没有 email 就按 phone 查"的分支；`email` 字段的 `NOT NULL` 约束需要放宽为"email 和 phone 至少有一个非空"（数据库层用 `CHECK` 约束）。**不采用**"给手机号用户生成一个假邮箱"这种绕过办法（子牙复审明确指出这条路风险不可控，比如假邮箱意外撞到真实客户邮箱、或者以后这个假邮箱被当成真邮箱发信）。

## 5. 数据模型改动（草案，待复审确认）

- `auth.users`（Supabase 管的表）本身原生支持 `phone` 字段，不需要新建表存手机号身份本身
- 需要新建一张验证码暂存表（形状参考 `meta_ads_oauth_states` 的"发一个随机值、存哈希、带过期时间、验完即删"模式）。子牙复审指出原稿字段不够：不能只用 `phone_hash` 当主键（同一手机号连续请求会有更新/竞态问题），要有独立自增 `id` 主键，补 `created_at`、`consumed_at`（防止同一个验证码被重放使用），并参照 `meta_ads_oauth_states` 加一条 `service_role_full` 的 RLS 策略。定稿字段：`phone_otp_codes(id, phone_hash, code_hash, created_at, expires_at, consumed_at, attempt_count)`
- `clients` 表已有 `source='self_serve'` 字段，手机号注册的客户同样走这个字段，不新增字段
- `client_portal_users` 需要加 `phone`（可空）列，见 4.1
- 限流用的 `bucket_type` 命名子牙建议详细设计阶段再定——现在挂在"张骞"（公开扫描工具）名下的限流表里，核心登录安全和一个对外扫描工具共用同一张基础设施表，命名上容易让人误以为这是扫描工具的附属功能，不算 BLOCKER 但值得讨论要不要换个更中性的表/命名

## 5.1 身份去重与滥用防护（魏征复审发现，BLOCKER，必须在这里拍板方向）

现有 `self-register` 的去重逻辑按"公司名 + source=self_serve"查重，不是按"人"查重。如果不做任何处理，同一个人换一个手机号（国内一人多号很常见）、换一个公司名，就能重新注册一次、重新领一次自助客户的 90 天免费期——这不是细节问题，是要不要防、防到什么程度需要现在定方向：

- **本方案采用的方向**：不在这一版做"跨手机号/邮箱是否同一个人"的强校验（这类校验本身很难做准、容易误伤真实的"一个客户确实想用两个不同手机号"场景），**改为**在给自助客户发放的欢迎礼包（如现有的注册赠送 MTC）上做限制——按更难伪造的信号（如同一浏览器指纹/同一收款方式，具体机制沿用现有欺诈防护，不在本方案新造一套）限制重复领取，而不是完全不设防
- 这一条明确写成**已知限制**而不是回避：允许"新客户可以用不同手机号再注册一次工作区"这件事本身发生，只堵"重复领免费额度"这个真正花钱的口子
- 若 PM 认为这个风险接受不了、要做更强的跨身份查重，需要另外拍板，不在这次 1-2 个工作日的估时范围内

## 6. 安全考虑（红线自查）

- 验证码有效期短（对齐现有邮箱验证码的做法，具体分钟数详细设计时定）
- 每手机号每天发送上限 + 每 IP 每天发送上限（两条都要，缺一条就是开着口子）—— 复用第 4 节的限流器
- 验证码核对失败次数上限（防止对同一个验证码暴力试）
- 阿里云 AccessKey/Secret 走环境变量，不进代码、不进日志（对齐 `docs/ENV.md` 现有规矩）
- 密码存储：`signInWithPassword` 走 Supabase 自己的密码哈希机制，不需要我们自己实现哈希

## 7. 不在这次范围内

- 不做微信登录/小程序登录（PM 没提，不顺手加）
- 不做"发送国际短信"通道（问题只在国内号码收不到验证码，港澳台/国际本来就能用邮箱或已有验证码链路）
- 短信认证服务的预置签名文案由阿里云统一提供，不做定制（定制需要品牌资质，本方案明确放弃这条）
