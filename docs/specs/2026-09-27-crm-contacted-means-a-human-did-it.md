# 「已联系」只能算真人真的做了的（状态模型定稿，待 PM 拍板）

**状态**：待审 —— 送子牙（架构）+ 魏征（挑刺）+ 板桥（非技术视角），审完送 PM
**风险级别**：**A 级**（改的是全平台「谁该被联系」的判据 —— 判错会让热线索被埋，而且是静默的）
**提出人**：PM 2026-09-25。原话意思：
> Meta 广告会自动回复对话 —— FB 表单能拿到对方电话/邮件，系统自动回一封。但到这步真人什么都没做，**这不能算「已联系」**。真正的联系是打了电话、发了 email。所以客户状态模型必须区分「系统自动动作」vs「真人联系动作」。

**不做**：改 `client_pipeline_stages` 的档位（那是按客户配的业务模型，不动）· 电话接入（另一份稿）· 界面改动（抽屉那份稿）

## 一、先给数字：这件事有多大

全部实测，生产库 `glbdnayojixmexgofbsd`，2026-09-27。

### 1.1 「已联系」几乎全是机器推的

CTS 有 **451 人**标着「已联系」。推它的人是谁：

| 谁推的 | 次数 | 带理由 |
|---|---|---|
| `ai:conversation-read`（AI 读对话判的） | **447** | 447 |
| 真人（`info@ctstours.co.nz`） | **4** | 0 |

**99.1% 是机器推的。**

### 1.2 但「机器推的」≠「没人联系过」—— 这一步我差点报错

机器推之前是**真的读了往来记录**的，不是凭空标。所以我逐个人去查有没有真人动作：

| | 人数 |
|---|---|
| 有真人打过电话 / 发过非群发邮件 | 374 |
| 私信里判出真人回过 | 136 |
| **两者任一满足 → 真的被人联系过** | **389** |
| ❗ **一条真人动作都找不到** | **62（14%）** |

**所以 62 个人是真的「标着已联系但没人碰过」。** 不是 447 个 —— 把「机器记录的」当成「没发生过」会把问题夸大 7 倍。

### 1.3 🔴 我曾经报错过一次，更正在这里

我曾跟 PM 说「14% 只是下限，真实更高，因为**我们自己那条自动回复**看起来像真人」。**查了生产：那条自动回复一次都没跑过。**

| 查的 | 实际 |
|---|---|
| `conversation_outbound_log` 总行数 | **5** |
| 其中自动回复机器人发的 | **0** |
| 实际发件人 | `bigbigraydeng@gmail.com`、`info@ctstours.co.nz`（都是真人） |

代码路径确实存在、确实会分不清，但它没有污染任何数据。**拿一条 0 行的路径去论证，是错的。**

### 1.4 真正的原因（这条才成立，而且更严重）

**全库出站记录几乎全是没有标记的。** 2074 条出站触点：

| 来源 / 渠道 | 条数 | 标了「机器发的」 | 记了「谁做的」 |
|---|---|---|---|
| messenger | 698 | **0** | 0 |
| 邮件（microsoft_mail） | 689 | **0** | 0 |
| 电话（sheet_followup，真人打的） | 621 | **0** | 0 |
| 群发（mailchimp） | 25 | 0（靠来源认得出） | 0 |
| 电话（me_manual，ME 里手记的） | 22 | 0 | **20** |
| 其余 | 19 | 0 | 0 |

**全库 `automated=true` 的出站记录是 0 条。** 判据函数是好的，但它只认两件事：来源是群发，或者写库时标了 `automated` —— 后者一条都没有。所以今天它能认出来的只有那 25 条群发。

> **一句话：不是「判得不准」，是「没东西可判」。**

## 二、五个漏口（每条带代码位置）

| # | 漏在哪 | 位置 | 后果 |
|---|---|---|---|
| **A** | **自动回复和真人回复写的是同一行** —— 同 `source`、同 `source_ref`、同 `metadata {thread_id, sender:'page'}`。而 `send.ts` 手上**明明有** `sentByEmail`（它写进了 `conversation_messages.sender_name`），写触点那一步没带过去 | `lib/messenger/send.ts` 的 `markContactFollowedUp` · `lib/whatsapp/send.ts` 同形 | 写入侧根本没留下身份 |
| **B** | **算「有没有人跟过」那段结构上不读 `automated`** —— `lastOutbound` 不滤，而 `lastOutbound === 0` 是「还没人联系过」的唯一判据、`lastInbound > lastOutbound` 是「客人在等你」的唯一判据。代码自己在文件里承认了这个缺口 | `lib/crm/segments.ts` | **就算 A 补上它也不看。** 一封群发就能让刚询价的热线索掉出今天名单 |
| **C** | **认得出却不落库** —— `isAutomatedPageMessage` 有能力认出 Meta 的秒回 / instant reply / AI 接管，但结论只用来挑时间戳，**没写进 `metadata.automated`** | `lib/messenger/link-contacts.ts` 的 `advanceOutboundTouch` | 判断白做了 |
| **D** | **出站邮件硬编码 `automated: false`** —— 而 `sendMailReply` 同时是机器身份发信的通道 | `lib/microsoft/mail-send.ts` | 写下的是一句**主动的假话**，不是缺省值 |
| **E** | **共享判据会把机器判成人** —— `isHumanActor` 的规则是「含 `@` 就算人」，而自动回复的身份常量是 `governed-reply-agent@magicengine.cloud`，**含 `@` → 判成真人**。测试只锁了不带域名的那个字符串 | `lib/crm/human-actor.ts` · 常量在 `conversation-inbound-autoack.ts` | 今天还没有生产调用方所以没爆。**A 补完之后，它会让读侧照样认错** |

**反证 A–D 是漏做而不是设计如此**：AI 外呼那条路**明确标了** `automated: true`，注释还点名「跟 Mailchimp 群发、**Meta AI 秒回**同一条道理」（`lib/voice/crm-bridge.ts`）。同一个道理，Meta 那条没落实。

## 三、定义：什么算「真人联系过」

**判据只有一条，写死：这一笔出站动作，有一个我们认得出的真人身份。**

不是「有出站记录」，不是「状态字段写着已联系」。

| 情况 | 算不算真人联系 | 依据 |
|---|---|---|
| 销售在 ME 里记一笔电话 | ✅ 算 | `metadata.logged_by` = 登录邮箱 |
| 销售在 ME 里回私信 / 回邮件 | ✅ 算 | 发送记录里有 `sent_by_email` 且不在机器名单里 |
| 员工在 Google 表格里写了一句 | ⚠️ **算，但记不到人** | 表格**没有「谁跟的」这一列**，只有那句话 |
| 群发邮件 | ❌ 不算 | 来源是群发 |
| AI 外呼 | ❌ 不算 | 已标 `automated: true` |
| Meta 的 AI 秒回 / instant reply | ❌ 不算 | 有判据能认出（C），但今天没落库 |
| 我们自己的自动安抚回复 | ❌ 不算 | 发件身份是机器（E 要修完才认得出） |
| **AI 读对话把 stage 推成「已联系」** | ❌ **不算「有人联系过」** | 它是**对既有记录的判断**，不是一次新的联系动作 |

### 🔴 最后那一条是整份稿子的关键

AI 判阶段**没有错**——它读的是真的往来记录，971 次判断 971 次带理由和客人原话。错的是**把它的结论当成「有人联系过他」**。

> **`stage` 是「我们认为他到哪一步了」，不是「有人联系过他」。** 这两件事必须分开：
> - 前者可以由 AI 判，判错了改一下就行
> - 后者只能由「真人做过一个动作」这个事实决定，**不能由任何判断推导出来**

同一个道理记忆里已经有一条：**状态字段当授权用，闸必漏**。这里是同一个形状——把 `stage === 'contacted'` 当成「联系过」的证据，等于让一个可被 AI 写的字段去证明一件只有事实能证明的事。

## 四、怎么修（顺序不能反）

| 轮 | 做什么 | 为什么这个顺序 |
|---|---|---|
| **S1** | **修 E**（`isHumanActor` 认得出机器邮箱）+ 把两个机器发件身份常量合并成一份、改成按域名单 | **必须最先。** 不修它，后面写入侧补完了，读侧照样把自动回复认成真人 —— 稿子担心的后果照样发生，只是换了个原因 |
| **S2** | **修 A + C**：写触点时带上发件身份；把 `isAutomatedPageMessage` 已经算出来的结论**写进 `metadata.automated`** | 让库里开始有东西可判。C 几乎零成本 —— 判断已经在跑了，只是结论被丢掉 |
| **S3** | **修 D**：`mail-send.ts` 不再硬写 `automated: false`，按真实发件身份写 | 它现在写的是一句主动的假话 |
| **S4** | **修 B**：`segments.ts` 开始读 `automated` | **必须放在 A/C/D 之后。** 先让它读，而库里还是 0 条标记 → 什么都不会变，白改一轮 |
| **S5** | 回填：拿已有证据能判的历史记录补标（**判不出来的一律跳过并记原因，绝不按 0 兜底**） | 62 个人的名单要能重算 |
| **S6** | 界面：抽屉时间线做**三态**（机器 / 真人 / 不知道），不做二值开关 | 二值开关会骗人：今天 2049/2074 都是「不知道」 |

### 🔴 S4 的方向必须是「错杀」不是「错信」

`segments.ts` 开始读 `automated` 之后，判不准的那些**一律当成真人**（= 这个人不再出现在「还没人联系过」里）。

理由：**错杀一个真人，代价是这条线索多露一次面；错信机器是真人，代价是热线索被埋。** 后者是静默的、没人会发现。这跟 `automation.ts` 既有的 deny-list 原则一致。

## 五、验收：拿真数据验，不看测试绿

| 判据 | 现在 | 修完要变成 |
|---|---|---|
| 全库 `automated=true` 的出站记录 | **0 条** | messenger / 邮件里机器发的那些都带上标记 |
| 出站记录记到「谁做的」 | 20 / 2074 | 经 ME 发出的那些都带上 |
| `isHumanActor('governed-reply-agent@magicengine.cloud')` | **`true`（错的）** | `false` |
| 「一条真人动作都找不到」的人数 | 62（14%） | **数字会变，但必须能说清每一个人为什么被算进去** |
| `isAutomatedTouch` 能认出的比例 | 只有 25 条群发 | 覆盖群发 + AI 外呼 + Meta 秒回 + 我们的自动回复 |

**⚠️ 最后一项不是「数字要变小」。** 修完之后 62 可能变大（因为现在算成真人的那些被认出是机器了）。**变大是对的** —— 它说明我们终于看见了真相。**「数字变好」不是验收标准，「每个人为什么在名单上说得清」才是。**

## 六、Reuse Statement

- **复用了什么**：`isAutomatedTouch`（判据本身是好的，不用改）· `metadata.logged_by`（操作者字段早就有，`recordManualTouchpoint` 一直在写）· `isAutomatedPageMessage`（已能认出 Meta 秒回，只是结论没落库）· `lastHumanPageReplyAt` · `actors.ts`（2026-09-27 刚建，机器身份清单 + 翻译）。**不新造任何判据**，只是把已有的接上、把认出来的结论存下来。
- **platform-shared**：全部。机器身份、`ai:` / `system:` 前缀约定、三态显示都是平台级。
- **client-specific**：无。⚠️ 唯一沾客户的是「Google 表格没有『谁跟的』这一列」—— 那是 CTS 的一张表，属 client configuration，不进共享代码。
- **换客户测试**：换 NAL —— 它几乎只有私信，A/C/E 三条直接适用；它没有 Google 表格，所以那条不成立。判据一个字不用改。
- **换行业测试**：不含行业语义。
- **Memory 升级**：`stage` 不等于「有人联系过」这一条可升通用层（跟「状态字段当授权用，闸必漏」是同一形状，两条互为证据）。
