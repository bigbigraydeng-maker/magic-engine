## 1 目的与范围（P1 要做的 5 件事）

**目的。** CTS 员工打开一位客人，就看到「订了哪个团、哪天出发、定金收到没、尾款哪天要付」，并有一张「付款要催」名单。

**v1 只追踪进度，不碰钱：** 不存金额、不开发票、不对账、不退款；不给客人发催款邮件；不改 `contacts.stage` 的含义。

**P1 范围（只这 5 件）：**
1. 加订单：选团 + 出发日期；预订日默认今天；人数、邮轮放在「更多」里。
2. 勾「定金」「尾款」：点「已收到款」要再确认一步，收款日期可改；系统自动算出并显示尾款到期日。
3. 「付款要催」名单：默认前 10 条，每行有「今天已催」「推迟几天」。
4. 一行文字备注；订单可以改团/改出发日期（已勾的记录保留）；可以取消并写一句文字原因。
5. 出发日期被团目录改过时，明确提示并要员工确认（到期日绝不悄悄变）。

不在 P1：邮件自动勾选、历史记录界面、已付款没订单名单、今日待办条目、任何非必需字段。

## 2 本稿用到的现状（v0.1 §2 之外新核的）

- 邮件识别器（`src/lib/conversions/payment-email-detect-run.ts`）：在 `ex.status !== 'confirmed'` 检查之后紧接着就把 `balance`（约 520 行）和 `unknown`（约 524 行）丢掉；今天只往后传 `deposit | full`。真实常量：`DETECTOR_ACTOR = 'payment-email-detect'`、`AUTO_REVIEWER_IDENTITY = 'auto:payment-email-evidence'`（第 45–46 行）。**v0.1 写的 `auto:payment-detect` 不是这两个，作废。**
- 它扫三种渠道：`email | messenger | whatsapp`（`Channel` 类型）。
- 团目录的 `tour_catalog_tours` / `tour_catalog_departures` 都带 `client_id`（可做同客户核对）；现有并发报错写法是 `raise exception 'conflict:stale:%'`（`20261010150000_tour_catalog_edit.sql`）。
- `src/lib/locale/calendar.ts`：面向营销的静态假日表，只有原始日期、没有「周末顺延到周一」；Matariki 只有 2026-06-26 一年。例：2026-12-26 是周六，新西兰实际放假日是 12-28（周一），表里没有。

## 3 数据模型（提案）

三张新表。全部 service-role only：`for all to service_role using (true) with check (true)` + `revoke all ... from anon, authenticated`（照 `tour_catalog_members`）。P1 迁移是**新增表**，不改任何现有表。

### 3.1 `crm_bookings`（一位客人订了一个团）
| 列 | 类型 | 说明 |
|---|---|---|
| `id` | uuid pk | |
| `client_id` | uuid not null → `clients(id)` | 所有查询都带 |
| `contact_id` | uuid not null → `contacts(id)` **on delete cascade** | 一单只挂一个联系人；夫妻/家庭把同行人写进备注 |
| `tour_id` | uuid not null | 指向团目录，**不设外键**（团目录会硬删） |
| `departure_id` | uuid null | 同上；null = 出发日期还没定 |
| `departure_depart_on` | date null | **出发日期快照**：写入时由数据库函数从团目录读出并存下。两个用途：①团/班期被删后仍能显示原出发日；②记录「到期日是按哪个出发日确认的」（§5）。这是抄来的数据，如实承认 |
| `booked_on` | date not null | 预订日，员工填，默认今天（NZ 日期） |
| `party_size` | smallint null check (1..60) | 人数，在「更多」里；不是金额 |
| `is_cruise` | boolean not null default false | 员工勾选，在「更多」里（§4.2） |
| `status` | text check in (`active`,`cancelled`) | 取消不删行 |
| `cancel_note` | text null check (length ≤ 200) | 取消原因/定金处理，**纯文字，不写金额** |
| `note` | text null check (length ≤ 500) | 一行备注，可写同行人姓名；不放金额、证件号 |
| `created_by`, `created_at`, `updated_at` | | `updated_at` 供乐观并发 |

**防重复订单：**
```sql
unique (client_id, contact_id, tour_id,
        coalesce(departure_id, '00000000-0000-0000-0000-000000000000'))
  where status = 'active'
```
同一人同一团同一出发日只能有一张有效订单；同一人订两个不同团/日期没问题，各自单独勾。

### 3.2 `crm_booking_milestones`（一单两行：定金、尾款）
| 列 | 类型 | 说明 |
|---|---|---|
| `id`, `booking_id` → `crm_bookings(id)` on delete cascade, `client_id` | | |
| `kind` | text check in (`deposit`,`balance`) | `unique (booking_id, kind)` |
| `state` | text check in (`unpaid`,`paid`) | |
| `paid_on` | date null | 员工填，可改；自动勾选时取邮件发送时刻转成 Pacific/Auckland 的日期 |
| `paid_source` | text null check in (`staff`,`email`) | `email` **只能**由服务器端识别器那条路写（§6.2）；P1 的路由写死 `staff` |
| `paid_evidence_ref` | text null | 邮件内部引用，写成 `<message_id>:<kind>`；不存邮件原文、不存金额 |
| `due_override_on` | date null | 员工手改的到期日 |
| `due_override_depart_on` | date null | 手改时当时的出发日期；以后出发日变了就提醒（§5） |
| `remind_after` | date null | 「推迟几天」「今天已催」写这里 |
| `nudged_on` | date null | 最近一次「今天已催」 |
| `quiet` | boolean not null default false | 「线下已处理」：不再出现在催款名单，但不改已付状态 |
| `updated_at` | | 乐观并发 |

**不存 `due_on`。** 到期日不是一列，而是读的时候用当时的出发日期、预订日、规则现算（§4）。所以没有「缓存过期」问题，也不需要每日刷新任务。

**幂等：** `unique (client_id, paid_evidence_ref) where paid_evidence_ref is not null`——同一封邮件对同一个节点只能勾一次（P3/P4 用，P1 先建好）。

### 3.3 `crm_booking_events`（只增不改的审计表）
列：`id, client_id, booking_id`（**普通 uuid，不加外键**）`, milestone_kind null, action, detail jsonb, actor_email text null, source`（`staff | email | system`）`, created_at`。
- `action`：`created | edited | cancelled | milestone_paid | milestone_unpaid | due_overridden | departure_confirmed | auto_tick_proposed | auto_tick_rejected`（后两种 P3 才用）。
- 由数据库触发器在两张表变更时写入（应用层漏写不了）；再加「不许改、不许删」的触发器（照 `tour_catalog_change_log`）。
- **`detail` 里只放：改了哪些字段名、日期、状态**。备注（可能含同行人姓名）和取消原因**不写原文**，只记「备注已修改」。所以审计表本身不含客人个人信息。
- `actor_email`：员工 = 登录邮箱（小写）；系统 = 固定常量，**必须与 `payment-email-detect-run.ts` 的 `DETECTOR_ACTOR` / `AUTO_REVIEWER_IDENTITY` 一致**，不另造字符串。
- 订单 id 不加外键的原因：删除联系人会把订单级联删掉，审计表必须留着，不能被「不许删」触发器卡住，也不能因外键阻止删联系人。

### 3.4 写入走数据库函数（一个函数做一件事）
`crm_booking_create` · `crm_booking_update`（改团/改出发日期/预订日/人数/邮轮/备注）· `crm_booking_set_paid` / `crm_booking_unset_paid` · `crm_booking_override_due` · `crm_booking_confirm_departure` · `crm_booking_nudge`（今天已催/推迟/线下已处理）· `crm_booking_cancel`。
- 每个函数：核对 `tour_id`、`departure_id` 都属于**同一个 `client_id`**，且 `departure.tour_id = tour_id`（团目录两张表都带 `client_id`，可直接核）；联系人属于该客户；失败抛明确错误。
- 乐观并发：传 `p_expected_updated_at`，不一致抛 `conflict:stale:%`（与团目录一致，路由层统一翻成 409）。
- 沿用团目录函数同款：`revoke execute ... from public, anon, authenticated; grant execute ... to service_role`。
- 勾付款的函数里：`select ... for update` 锁行 + `on conflict do nothing`（P3 的自动勾复用同一个函数）。

## 4 到期日计算（读取时现算）

### 4.1 三层放哪
- **L1 通用**：纯函数 `computeMilestoneDueDates(rule, input)`（拟 `src/lib/crm/booking-schedule.ts`），只认规则对象，不认客户。
- **L2 行业**：旅游规则**形状**（定金 = 预订后 N 个工作日；尾款 = 出发前 M 天，M 分档），只给形状不含数字（拟 `src/lib/crm/industry/travel-booking-rule.ts`）。
- **L4 客户**：CTS 数字放 `clients.leads_config.booking_schedule`（与 `payment_email_detect` 同处）：
  `{ "enabled": true, "deposit_due_working_days": 3, "balance_lead_days": { "standard": 90, "long_or_cruise": 120 }, "long_tour_min_days": 16, "holiday_region": "NZ", "balance_roll_forward": false }`
  数字待 PM 回答 §9 后写入，不进代码。没配的客户整块不出现（fail-closed）。

### 4.2 规则（全部定死）
- **起算日：预订当天不算**。定金到期 = `booked_on` 之后的第 3 个工作日（周一至周五且不是假日）。例：周一预订 → 周四到期。
- **尾款到期** = 出发日期 − 90 或 120 个日历天。
- **团天数的唯一来源**：`return_on − depart_on + 1`（有 `return_on` 时）；没有才解析 `duration_text`；两者都有且不一致，界面显示「团天数对不上，请核对」。天数 ≥ 16 或勾了邮轮 → 120，其余 90。
- **邮轮**：团目录没有结构化标记，所以由员工在「更多」里勾。**没勾邮轮时，到期日下方始终显示一行小字「未勾邮轮按 90 天算」**，避免员工以为系统知道。
- **时区**：所有邮件时间戳先从 UTC 转成 Pacific/Auckland 再取日期。
- **周末/假日顺延**：由配置 `balance_roll_forward` 决定，默认 false（不顺延），等 PM 回答（§9-4）。
- **出发日期没定**（`departure_id` 为空）：不算到期日，显示「出发日期还没定，补上才有到期日」。
- **预订时已经太近**（算出的尾款日早于或等于预订日）：不报逾期；两个到期日合并成一个「全款」，与定金同日，界面写「这单离出发太近，需一次付清」。待 PM 确认（§9-3）。

### 4.3 假日表（P1 一并修，共享，带测试）
在 `src/lib/locale/calendar.ts` 或其旁新增 NZ 工作日用假日列表：
- 补**周末假日顺延到周一**（Christmas / Boxing Day / 新年 / 新年次日 / Waitangi / Anzac 等）。回归用例：2026-12-26（周六）→ 12-28（周一）也算假日。
- 补 **Matariki** 逐年官方日期（现在只有 2026 一年），写入时对官方公布日期核对。
- 表只覆盖到某一年；订单涉及的年份**超出表范围**时，不静默按「没有假日」算，而是显示「假日表缺失，到期日可能偏早」，并把这条订单排进名单、不隐藏。**测试**：预订日在 2028 的订单必须得到该提示。

## 5 界面与措辞（只用大白话）

### 5.1 客人抽屉里的「订单与付款」块（仅配了 `booking_schedule` 才显示）
```
订单与付款                                      [＋ 加订单]
┌────────────────────────────────────────────────────────┐
│ 新西兰南北岛 · 2027-03-12 出发                         │
│ ⚠ 出发日变了：原 2027-03-12 现 2027-03-19，到期日已重算，请确认  [确认]
│ 定金  ✅ 已收到款 10月08日                             │
│ 尾款  ⬜ 未收到 · 到期 2026-12-12（还有 61 天）  [已收到款]│
│       未勾邮轮按 90 天算                               │
│ 备注：同行：Li 夫妇                                    │
│ [改团/出发日期] [改到期日] [取消订单]                  │
└────────────────────────────────────────────────────────┘
```
- **加订单**：选团 → 选出发日期 → 提交（预订日默认今天；「更多」里才有人数、邮轮）。
- **已收到款**：点后弹一步确认（显示收款日期，可改），再提交。已勾的可以「撤销」。
- **自动勾的（P4）**会带标记「邮件自动」和按钮「撤销自动标记」。
- **出发日变了**：订单存的出发日期快照与团目录现在的不一致，就显示上面那行，并按**现在**的出发日期重算到期日；员工点「确认」才把快照更新（`crm_booking_confirm_departure`），确认前提示一直在，**到期日不会悄悄变**。
- **手改过的到期日**：若之后出发日期又变了，仍然提示「你手改的到期日是按原出发日 X 定的，现在出发日是 Y，请核对」。
- **出发日期/团被删或取消**：显示「团目录里已找不到这个出发日期（原为 2027-03-12）」/「这个出发日期已取消」，原出发日取自快照。
- **取消订单**：只写一句文字原因/定金怎么处理，**不写金额**；取消后不再提醒。
- 不出现的词：节点、里程碑、班期健康、departure id、班期（一律说「出发日期」）。

### 5.2 「付款要催」名单（在「全部客人」页段头旁；不混进现有名单，因为已付定金的人会被现有名单排除）
- **一单一行**，只显示最紧的那一项（不并排叠两条）；默认**前 10 条**，「展开更多」。
- 排序：已逾期 → 3 天内 → 14 天内。**逾期超过 14 天的折叠成一行「逾期很久（N 单）」**，不再逐条刷屏，升级而非堆叠。
- 每行三个按钮：「今天已催」（今天不再出现）· 「推迟几天」（选 3/7/14 天）· 「线下已处理」（该项不再提醒，不改已付状态）。
- 取数：读所有 `state='unpaid'`、订单 `active`、联系人未拒联的节点（单客户量级小，上限 500，超限显示提示），在服务端用现读的出发日期现算到期日；**没有定时任务、没有缓存**。
- 点一行打开该人抽屉（`?contact=`）。对客人群发「7 天不超 2 封」只管发给客人的邮件，v1 不外发，不适用。

## 6 邮件自动勾选（P3/P4，**手工版用满约 1 个月之前不排期**）

### 6.1 接入点
- 钩子必须在 `ex.status !== 'confirmed'` 检查**之后**、丢弃 `balance`/`unknown`（约 520–526 行）**之前**；或做成独立的 Inngest 步骤读同一批确认结果。放在丢弃之后就永远看不到尾款。
- 今天识别器只往后传 `deposit | full`，尾款与不明在钩子前就被计数后丢弃。P3 要把 `balance`、`unknown` **只读地**多交给钩子；**不改**「尾款不算成交、不发 Meta」的现有决定，两条支路互相独立。
- 钩子必须尊重 `dryRun`（不写）；邮件识别对 CTS 现已开启，试跑不得写库。

### 6.2 匹配与写入规则（全部满足才自动勾，否则只出「提案」）
1. 渠道必须是 `email`。`messenger` / `whatsapp` 一律只出提案（`paid_source` 只有 `staff|email`，不为此加第三个值）。
2. 收件邮箱只对应**一个**联系人；一个邮箱对应两个及以上联系人 → 转人工。
3. **邮件正文或标题必须写出团名或出发日期，并与该联系人名下某一张有效订单对上**。「这人恰好只有 1 张订单」**不能**单独作为依据（识别器认的是人，不是团）。
4. 邮件类型与节点对得上且节点未付（`full` = 两个都未付才勾；`unknown` 不勾）。
5. 该邮件引用没勾过（数据库唯一约束兜底）。
- 满足：调用同一个勾付款函数，`paid_source='email'`，事件 actor 用真实常量。**`paid_source='email'` 只允许这条服务器端路径写入；路由层只要见到该字段就直接拒（400）。**
- 不满足：写 `auto_tick_proposed` 事件（原因：`no_booking` / `multiple_bookings` / `tour_or_date_not_named` / `shared_mailbox` / `non_email_channel` / `already_paid` / `departure_changed`），并进今日待办（what/how/href 三件套）。
- **并发输了不丢证据**：乐观并发失败的一方也写一条 `auto_tick_proposed`，证据留在审计里。
- 撤销：「撤销自动标记」改回未付，记 `milestone_unpaid`，30 天内同一联系人同一邮件不再自动勾（沿用识别器的 `REJECTION_COOLDOWN_DAYS`）。

## 7 权限、隐私与回退

### 7.1 谁能看、谁能改（如实说）
- v0.1 说「订单块不增加新的暴露面」**不对**。订单与付款进度记录的是「某位具名客人订了哪个团、定金尾款付没付」，比现在的阶段标签（已付定金/已付全款）敏感得多。
- CRM 的闸是 `requirePaidClientAccess`：ME 管理员或该客户任意付费账号。若沿用，**CTS 所有付费账号**都能看到并修改每一位客人的付款进度，而且目前没有按字段区分。
- 备选：像团目录那样另建 `crm_booking_members` 名单。选哪个是业务问题，见 §9-1；默认先沿用 CRM 的闸，PM 回答后再收窄。
- 所有路由带 `client_id`；联系人归属校验照 `advanceContactStage` 的写法；操作人只取登录会话邮箱，不读请求体。

### 7.2 审计
§3.3 的触发器写入，只增不改不删；谁 / 什么时候 / 来源三要素齐全。

### 7.3 客人要求删除个人信息
- 订单、节点随联系人**级联删除**（`contact_id` 外键 `on delete cascade`），删联系人不会被审计表卡住。
- 审计表因设计上不含客人姓名、备注原文、金额，可以保留（2026-10-13：PM 本人曾说要金额，当天又改为「不要金额」，以后者为准；系统仍不存金额）；唯一可能的个人信息是员工邮箱，抹除流程 = 一个专用数据库函数，只允许把 `actor_email` 置空，其余列仍不可改。这条已决定，不再问 PM。

### 7.4 开关关掉时
把 `booking_schedule.enabled` 改 false：抽屉里的订单块隐藏、「付款要催」不显示、不再提醒；**已有订单和审计一条不删**，再打开原样回来。

**平台共享（L1）**：三张订单表；`computeMilestoneDueDates`；数据库函数；「订单与付款」块与「付款要催」名单；`matchEmailToBooking` 的匹配规则（只认联系人、渠道、节点类型、团名/日期是否写出、邮箱是否唯一）；补全后的 NZ 工作日假日表。表和函数里没有客户名、客户 ID、金额。

**行业专属（L2 旅游）**：「定金 + 尾款、按出发前天数分档」的规则形状与默认字段名。地产版（定金 + 交割）换另一份行业规则，复用同一套表。

**客户专属（L4 CTS）**：`leads_config.booking_schedule` 里的 3 / 90 / 120 / 16 与 `holiday_region`、`balance_roll_forward`、`auto_tick_from_email`。共享代码里**没有** CTS 的名字、ID、数字；没配置的客户整块不出现。

**学习沉淀**：不产生跨客户学习；订单事件是 CTS 私有记录。多个旅游客户证明「预订太近→全款」成立后，才升到行业 Playbook。

## 11 PM 决定与执行默认值（2026-10-12）

- **§9-1 谁能看和改：名单制。** 另建第 4 张表 `crm_booking_members(client_id, email, granted_by, created_at)`（照 `tour_catalog_members`：email 小写、service-role only、revoke anon/authenticated）。能用的人 = ME 全局管理员 + 名单里且是该客户付费账号的人；加/移名单只限 ME 全局管理员。初始名单：`info@ctstours.co.nz`、`ctstours1@chinatravel.co.nz`（由管理员上线后写入，P1 迁移本身不写数据）。所有订单路由与「付款要催」名单都走这道闸。
- §9-2 数字：3 个工作日 / 90 / 120 / 16 天分界，按 CTS 官网条款原样写进 `booking_schedule`（客户配置，不进代码）。
- §9-3：预订时已进尾款期 → 合并成「全款」，与定金同日（`一次付清`）。
- §9-4：到期日落在周末/假日 → 不顺延（`balance_roll_forward=false`）。
- §9-5：邮轮由员工在「更多」里手勾；暂无团被预先标成邮轮。

### 11.1 审查后的技术修订（2026-10-12，P1-a 三位审查：子牙 / 魏征 / 狄仁杰）

- **撤销自动标记后的重勾**：同一封邮件的引用**永久**只能勾一次（数据库唯一约束），不再是 §6.2 写的「30 天」；撤销后正确的订单由员工手动勾补上。P3/P4 另排期时按此执行。
- **尾款日排到定金日前面**：尾款日（按需顺延后，最晚出发前一天）不晚于定金日、或不晚于预订日，就合并成「一次付清」，到期日取定金日并夹在「预订日 ~ 出发前一天」之间。
- **直接写库也要同一客户**：订单的联系人/团/出发日期、付款记录的客户编号，由数据库触发器强制一致，不只靠函数。
- **审计补全**：付款记录的新增/删除、订单删除也写修改记录；清除操作人邮箱留一条清除记录，并同时抹掉订单创建人与名单加入人里的同一邮箱。
- **假日表**：订单用 `src/lib/locale/nz-public-holidays.ts`（含周末顺延）；`calendar.ts` 是营销日历，保持原样，不合并。
