## 0. 一段话结论
1. **不重造**：授权 / 执行 / 步骤 / 成本 / 校验的系统记录仍是**内核**（`action_runs`、`authorization_decisions`、`action_run_steps`、视图 `kernel_action_lineage`）；盯盘 / 体检的运行回执仍是 `cron_run_logs`；请求本身仍归 119 的 `ad_agent_requests`。这三样一个字都不搬。
2. **只新增一张追加式「请求回执台账」`agent_request_receipts`**（+ 一张事件发件箱 `ad_agent_event_outbox`）。W1 链路页读「119 的请求表 + 这张台账」就能画出“从发出到有回执”。
3. **防线在库里，不在自觉里**：两张新表对 `service_role` 没有写权限，写入只有一条路——SECURITY DEFINER 函数 `ad_agent_apply_receipt_v1`。函数在一个事务里：先锁请求行、再幂等、再按**函数体里的转移规则**算新状态、再在库内核验授权与下游、最后写回执 + 同事务更新请求行缓存 + 写发件箱。调用方给不了“结论”，只能给“阶段 + 证据”；**所有“人”的动作（驳回 / 撤回 / 指认 / 更正 / 结案 / 更换观察对象 / 确认标记）还要带一条一次性的人工动作凭据**，在库里核验并消费（§4 §5.6）——它防的是代码接线错 / 漏传、并留下可审计记录，**不防持有 `service_role` 钥匙的人**（§11）。
4. **两种模式**（函数体里按请求类型定，改它 = 改迁移 = A 级）：**观察型**（本期 `creative`）——台账只记“谁做了什么、人批了什么（指针当证据）、我们观察到了什么”，**从不声称授权或执行**，用 `observed_live` 收尾，终态词是 **`fulfilled_observed`，展示成“观察到在投”，不写“已上线”**；**创意上线不受内核授权覆盖、也没有任何阻断——已经被人手动上线的广告（成片须已在 ME 审核页批准、内容绑定对得上、且落在请求合同指定的目标——合同没给全系列 / 广告组时由人指认）同样会拿到 `fulfilled_observed`**；**执行型**（其余类型，等内核动作落地）——授权、执行、回读全按 §4 §6 核验，用 `executed → completed` 收尾，终态词 `fulfilled`。W2 的任何“启用前闸”只认执行型的 `fulfilled`，**永远不认 `fulfilled_observed`**。**批准之后合同写错 / 目标变了有两条受控的路**（v0.9.1）：人指认带凭据绑定的 `override_target`（只放开系列 / 广告组，不放开账户和预算上限），或人带凭据撤回 + 后继请求接手原工单一次——合同更正 = 撤回 + 新请求，不改旧合同（§4 §5.2 §6）。**`approver_scope = 'internal_staff'` 只是“内部员工的内容批准身份”**（`requireGlobalAdmin()`，`ADMIN_EMAILS` ∪ 整个 `ADMIN_EMAIL_DOMAIN`；v0.9 由 `global_admin` 改名——现有启用回执的 `basis = 'global_admin'` 指的是另一件事：`ADMIN_EMAILS` 精确名单），**不是花钱授权**：开投那一步另用 `requireSpendActivationAuthority()`（`ADMIN_EMAILS` 精确名单，名单上有几个人就放几个人）；`fulfilled_observed` 不等于“PM 授权花钱”，**也不代表过了任何预算闸**（台账合同上限只管单个请求，119 的 PR 2999 的客户日上限管全客户合计，两层互不替代，§4）。
5. **这套防线防什么、不防什么（写明白）**：防——其它窗口 / 脚本 / MCP 绕过函数直接改台账、代码或接线出错造成的假回执、重放与并发、倒退状态、抢先占位。**不防**——持有 `service_role` 钥匙、**又去伪造系统记录**的人：内核的 `action_runs`、`authorization_decisions`，以及观察型要读的盯盘快照行、广告↔成片关联行、审核记录、日数据，本来都是 `service_role` 可写的，我们核验时读的正是它们；也不防“人点了执行卡完成”这种可变状态被当成成功证据（§11）。收口那些表是各自的 A 级事项，另开卡由 PM 定（§12(b)）。也不防持钥者直接调用人工动作凭据的签发函数 `ad_agent_issue_human_grant_v1` 给自己签凭据（凭据只防代码接线错 / 漏传、留下可审计记录，不是会话绑定的证明）；持钥者还能把签发限额占满，让正常的人签不出——方向是拒绝服务，不是伪造（§11）。
6. **内核一行代码不改。** 请求编号借内核现成的 `triggered_by='agent'` + `triggered_by_ref` 带过去。
7. **“没回执 / 没对账 / 权限被改”有人管**：每小时的监督函数扫卡住、过期（仅限未上线的）、已完成但缺对账、对账不一致、发件箱漏发、**表权限被人改了 / 属主名下多了能写台账的函数**，推今日待办（what / how / href）；观察者（actor `ad_watch`，写 `observed_live`；候选——目标账户内绑定到本工单的广告——多于一条、或合同没给全系列 / 广告组时不自动选，出“指认”待办交人）与对账者（actor `reconciler`，写 `reconciled`）也是这个函数里的步骤；**异常批量的人工动作、认领之后又出现第二条候选**合并成每客户每天一条“台账异常汇总”（走开发欠账栏）；**观察后预算被调高超过合同上限、广告先于批准上线这两类高危信号不进汇总**，每个请求每天各单独出一条红待办，进 PM 的“要拍板”栏（仍在 PM 的五类之内，不新增待办类，v0.9.1）；**对账不一致（要人结案）与待人指认两类待办归值班同事**：开发欠账栏里可点的工作项，带链路页直达链接，不作为单条进 PM 邮件；`page` 请求交付之后不再出卡住 / 过期待办；没有快照的绑定广告不算候选，请求显示“待补快照”；其余台账来源的待办每客户每天有总量上限（§8）。

## 4. 模式、授权与对外动作
**模式（函数体里按请求类型定；本期 `creative` = 观察型，其余 = 执行型）**

> **观察型的一句话边界（spec 明写）：创意上线不受内核授权覆盖，也没有任何阻断。台账只观察——所以一条被人手动上线、没经过任何内核授权的广告，只要成片已在 ME 审核页被批准、它的内容绑定对得上、又落在请求合同指定的目标里（合同没给全系列 / 广告组、或实投的系列 / 广告组与合同不同时，由人带凭据指认），同样会拿到 `fulfilled_observed`。这个终态只表示“观察到在投”，不表示“授权过 / 安全 / 我们投的”，任何地方不得写成“已上线 / 已履约”，更不能当 W2 启用前闸的依据（§11）。**

| | 观察型（本期 `creative`）| 执行型（其余类型，等内核动作落地）|

| 收尾阶段 / 终态词 | `observed_live → fulfilled_observed`（展示“观察到在投”）| `executed → completed → fulfilled` |

**观察型 `observed_live` 的核验（全部在函数里做，任何一条不过整笔不写；共八条）**
1. **快照行**：`snapshot_ref = {table:'ad_entity_snapshots', id}`（别的表一律拒）；该行 `level = 'ad'`、`client_id` = 请求客户、`ad_account_id` 是该客户在 `client_meta_ad_accounts` 登记的账户；**`effective_status = 'ACTIVE'`**（“在投类”只此一个，常量写在函数体；其余——PAUSED、ADSET_PAUSED、CAMPAIGN_PAUSED、DISAPPROVED、PENDING_REVIEW 等——抛 `observation_not_live`）；`captured_at` 晚于本请求的 `approved` 回执、不晚于 now()+5 分钟。
2. **“现在还是”**：该行是此广告（同 `client_id + entity_id`）的**最新**一行快照，**且** `ad_snapshot_captures` 里同账户、`level = 'ad'`、`complete = true`、`skipped_shared = false` 的最近一轮在 **12 小时内**（抓取每 6 小时一轮，容忍漏一轮）。广告级行只在变化时才记，所以“没有更新的行 + 近期抓全”才等于“这之后没变”；否则抛 `observation_stale`。
3. **对上请求合同的目标与预算**（v0.7，复审高 3；v0.9 按追加 E3 分两步、按复审 3 / 4 / 9 定预算口径）：`creative` 合同写**目标** `target = {ad_account_id, campaign_id, adset_id}`——`ad_account_id` 创建时必填（须是该客户登记的账户），`campaign_id / adset_id` **可空**（新素材另建新广告组，发请求时往往还不存在；给了 `adset_id` 必须给 `campaign_id`；§12 第 12 条）。快照行的 `ad_account_id` 必须等于合同的；合同给了的 `campaign_id / adset_id` 必须逐项等于快照行上的，否则抛 `observation_target_mismatch`；**系列或广告组任一为空 → `actor = ad_watch` 不能认领（抛 `observation_target_unspecified`），只能由人带凭据指认**，被指认的广告照样过其余各条。**目标对不上的人工放行 `override_target`（v0.9.1，复审魏征 3）**：合同给了的系列 / 广告组与这条广告实际所在的不一致时，人指认（或更换观察对象，§6）的凭据可带 `override_target = {campaign_id, adset_id}`（两项必须齐全，凭据绑定），只放开这一项比对——声明值必须等于快照行上的实际值（防手误），**账户永远不能 override**（仍须等于合同账户），**预算上限不放开**（下面照旧按这条广告自己所在的系列 / 广告组比）；任一不符抛 `observation_target_mismatch`。合同没给的那项本来不比，不需要 override；`ad_watch` 永远不能 override。通过时 `provider_ref.target` 记 `{contract, snapshot, override}`、`provider_ref.override_target = true`。合同本身写错（含预算上限）不靠 override：走撤回 + 后继请求（§5.2 §6）。**预算**：合同必填日预算上限 `max_daily_budget_cents`（正整数，`currency` 的最小单位）与 `currency`（ISO 4217）；比的是这条广告自己所在的系列 / 广告组（合同给全且没 override 时就是合同目标）——口径照 PR 2999：系列行 `budget_level = 'cbo'` 取系列行、`'abo'` 取该广告组行的 `daily_budget_minor`，各取最新一行，且同账户该层级 12 小时内有一轮抓全（同第 2 条）；**只有该账户币种（账户级最新一行的 `currency`）= 合同 `currency` 时才比**。读不到（没有行 / 没抓全 / `budget_level` 为空 / 该层 `daily_budget_minor` 为空）、该层是终身预算（`lifetime_budget_minor` 非空）、币种读不到或不一致 → 抛 `observation_budget_unreadable`（与 2999 的 `cap_unreadable` 同口径：读不到就拒，不当 0）；超过上限 → `observation_target_mismatch`。这样别的广告组 / 别的系列里投的同一帖子（包括 1 美元的测试广告）认领不了本请求（除非人带凭据用 override 有意指认它）。
4. **广告 ↔ 成片绑定（内容绑定类；v0.9 词汇与核验按 PR 2990 最新，复审 2）**：`ad_creative_links` 有 (client_id = 请求客户, platform = 'meta', ad_id = 快照 `entity_id`) 的行（表现状只有 4 行，没有行是常态，按不过处理），且全部满足：①`link_method` 在**内容绑定类**内——`published_post_id`（帖子 id 精确命中已发布工单，`link_strength = 'post_id'`）或 `asset_binding`（广告创意的源视频 → 素材池条目 → 条目的 `work_order_ref` → 工单，根是 PM 的单独签字，`link_strength = 'pm_attested'`）；`asset_binding_provisional`（只过了标题核验）与 `unresolved` 一律不放行；`link_strength` 与 `link_method` 对得上；②**`pm_attested` 必带 `attestation_id`，且 2990 的唯一判定函数 `creative_binding_is_valid(attestation_id)` 为真**（签字哈希 = 工单此刻文件哈希 ∧ 签字未撤回，2990 s1 §1；台账只调它，不自己再写一遍）；③`creative_source = 'content_work_order'`，**`creative_ref` = `approved` 回执里批准的那个工单 id**（不是“当前下游”）；④`link_source` 在白名单内（`ad_creation_path` / `registration_entry`；回填 `backfill_*` 不放行）、`retracted_at` 为空、**`stale_at` 为空**、**没有未了结的换创意意图**（2990 s1 §3：`swap_pending` / 结果未知时读取方一律不采信；用 119 给的只读判定函数 `creative_link_has_pending_swap(link_id)`，§12 第 11 条）；⑤**创意复核新鲜**：关联行的最近一次创意复核时间（119 每日扫描读 Meta、`meta_creative_id` 对上后刷新；**119 已确认新增这一列 `creative_checked_at`（2990 实现设计 s1 §5，头 `4259b894a`），只经窄函数 `link_touch_checked_v1` 写**）距今 ≤ 30 小时（每日一扫 + 一个抓取周期；数值取自 `ad_agent_ledger_limits_v1()`，§3.3），且此后该广告的 ad 级快照没有出现 `creative_video_ids` 不同的行——快照里只有这一列能看出“换了视频”（它是 Meta 生成的投放用衍生视频 id，**不是**创意编号，也不等于关联行的 `source_video_id`）；**“`meta_creative_id` 等于广告当前创意编号”库里比不了**（快照没有创意编号列），归 119 每日扫描，对不上由它标 `stale_at`。任何一项不过 → 抛 `creative_link_missing`（错误详情写哪一项）。**“广告晚于请求”**：优先用关联行的 `meta_created_time`（2990 v0.5，登记入口读 Meta 写入），必须晚于请求的 `created_at`（后继请求以链首请求为准，§6）；该列为空时回退到该广告在 `ad_entity_snapshots` 里**最早一行**的 `captured_at`，`provider_ref.created_time_source` 如实标 `meta` / `first_snapshot`（先于请求就存在的广告不可能是本请求的产物）；否则抛 `ad_predates_request`——**不用关联行自己的 `created_at`**，因为回填 / 重写都会改它。通过时把 `link_id / link_method / link_source / link_strength / attestation_id / creative_ref / creative_checked_at` 冻进 `provider_ref`（§3.1）。这个绑定**不是成片内容哈希**：`pm_attested` 是“人认定”，比 `post_id` 弱（§11）。
5. **下游与批准对得上**（v0.7，复审高 1）：`downstream_ref.id` 必须等于 `approved` 回执 `source_ref.approval.id`，并对**当前**下游工单把批准人核验整套重做一遍：`review_ref.approved_by`（`lower()`）仍等于 `approved` 回执的邮箱、`approval_source / approver_scope` 仍合格、`approved_at` 与回执里抄下的一致（沿用批准的回执，邮箱取 `source_ref.approval.original_approved_by`）；对不上抛 `approval_downstream_mismatch`。（批准之后下游本来就锁死，§5.3 §6；这一条兜的是“库里被直接改写”的漏洞。）
6. **一条广告只能被一个请求认领**：函数把 `ad_id` 写进请求表 `observed_ad_id`（部分唯一索引）；已被别的请求认领抛 `ad_already_claimed`。同一请求本期只认领一条广告。
7. **不含糊**（v0.7，复审高 3；v0.9 改候选集合，复审子牙 3）：函数在同一事务里数候选——**目标账户（合同 `target.ad_account_id`）内所有绑定到本工单的广告**：`ad_creative_links` 里 `creative_ref` = 批准的工单、`retracted_at` 为空的行，**不论广告状态（在投 / 暂停 / 审核中）、不论在哪个系列 / 广告组、不论绑定是内容绑定类还是 `asset_binding_provisional`、不论是否 stale**（广告所在账户取它最新一行快照；**一行快照都没有的广告账户未知，不算候选**（v0.9.1，复审魏征 4）——请求在链路页显示“待补快照”（监督函数读模型里算，不写回执），关联行出现后 24 小时仍没被盯盘抓到 → 进当天“台账异常汇总”（§8 第 8 类⑤）。**只在合同目标账户内找**：CTS 官方户和个人号共用同一素材是真实情况，别的账户里绑同一工单的广告不算候选）。**候选不止一条：`actor = ad_watch` 的认领被拒，抛 `observation_ambiguous`**；`actor = human` 的指认只能指候选中通过其余各条的一条。所以：①1 美元测试广告投在**别的**系列 / 广告组——它自己过不了第 3 条，认领不了；真广告到了候选变两条，同样不自动认领 → 人指认；②测试广告投在**目标广告组里**、又是当时唯一的候选——会被如实认领（它确实是绑定了本工单、落在目标里、在投的广告，台账只说“观察到在投”）：台账**分不出正式广告和测试广告**，办法是事后发现——认领之后目标账户里又出现第二条候选，当天进“台账异常汇总”（§8 第 8 类④），由人用“更换观察对象”改认真广告（T+7 对账之前，§6）；③“同一成片被投了两次”不会被谁抢先认领，而是出待办让人定（§8）。**人为制造多候选（再登记一条绑同一工单）的后果是“多一次人工指认”，不是误放行——方向是拒绝服务，不是伪造通过**（v0.8 起，复审魏征 3；§11）；待办每请求每天一条，不刷屏。
8. **派生**：`provider_ref` 由函数写（§3.1），含两个先于批准的判断量——`first_active_at`（该广告最早一行 `ACTIVE` 快照的 `captured_at`）和 **`live_before_approval`**（`first_active_at` 早于 `approved` 回执的 `source_ref.approval.approved_at`，即审核页批准那一刻（抄自 `review_ref.approved_at`）；**v0.9 起不再比回执的 `created_at`**——回执可能晚写，复审子牙 4）；为真时照样盖章（`fulfilled_observed` 只表示“观察到在投”），但**单独出一条红待办**（§8 第 8 类③，进 PM 的“要拍板”栏，不藏进汇总；v0.9.1），由人经凭据 `acknowledge_flag` 确认后消失（v0.8，复审子牙 6）。用“最早 ACTIVE”而不是“最早快照”：ME 自己建的暂停草稿广告批准前就有快照行，不算“先上线”。**局限（v0.9 写实，复审魏征 7）：它只能发现“慢上线”——批准前已经被抓到过 ACTIVE 快照的广告；快照每 6 小时一轮，`first_active_at` 比真实上线最多晚一个抓取周期，批准前不到一个周期才上线的广告可能漏标。所以 `live_before_approval = false` 不是“没有先上线”的保证，PM 不得依赖它（§11）。**调用方传了非空的 `p_provider_ref` 抛 `evidence_invalid`。

**两档身份，别混（v0.8 写明，v0.9 改名）**：台账里的“人”一律是 **`requireGlobalAdmin()`** 通过的内部员工（`ADMIN_EMAILS` ∪ 整个 `ADMIN_EMAIL_DOMAIN`，不限定单个客户）——它回答“这是内部员工吗”，**不回答“这是 PM、可以花钱吗”**；台账把这一档记作 **`approver_scope = 'internal_staff'`**（v0.8 叫 `global_admin`；现有启用回执用 `basis = 'global_admin'` 指 `ADMIN_EMAILS` 精确名单，同名不同义，v0.9 改名）。开投（批准草案 / 恢复暂停系列）另用 `requireSpendActivationAuthority()`（`ADMIN_EMAILS` 精确名单，域名放行的人不行，名单上有几个人就放几个人，`src/lib/ads/spend-activation.ts`）。所以 `internal_staff` 只是“内部员工的内容批准身份”；`fulfilled_observed` 永远不等于“PM 授权花钱”；W2 的启用前闸只认执行型 `fulfilled`，且开投那一步另有自己的身份闸。人工动作凭据（驳回 / 撤回 / 指认 / 更正 / 结案 / 更换观察对象 / 确认标记）同样只要求 `requireGlobalAdmin`：这些动作不花钱，要求更严会让值班同事动不了。

**两层预算，别混（v0.9，复审子牙 4）**：台账合同的日预算上限只管**这一个请求**认领的那条广告（第 3 条认领时比、§5.2 对账时再比、§8 盯到 T+14）；119 的 PR 2999 的客户日上限管**全客户**在投设定预算合计（启用那一步现场检查 + 每日只读审计）。两层互不替代：`fulfilled_observed`、对账 `match` **都不代表过了任何预算闸**；2999 的闸也不读台账。

**执行型的授权来源（函数体里的白名单）——本稿只放行 `authorization_decisions`（内核）**。其它来源一律拒绝；创意上线的内核动作（暂名 `ads.attach_creative`，A 级）另开卡由 119 评估，落地后创意类请求才切到执行型（改一次迁移）。
- **`authorization_decisions` 的核验**（`approved` 与 `executed` 都做）：行存在 ∧ `client_id` = 请求的客户 ∧ `verdict = 'allow'` ∧ **决策所属的 `action_run` 满足 `triggered_by = 'agent'` 且 `triggered_by_ref = request_id::text`** ∧ **该决策的 `action_key` 在“该请求类型的白名单”内**（白名单写在函数体里，具体键名由 119 在合同里给；内核有 `action_key_mismatch` 校验，台账不能比内核更宽）；`approved` 阶段另要求决策**未过 `expires_at` 或已被兑换**；`executed` 阶段另要求 **`consumed_at` 非空** ∧ **run 的状态是 `running` 或 `succeeded`**。
- **`executed` ≠ 成功**：`consumed_at` 是 run 被领走时就写的，所以 `executed` 只证明“动作开始了”；**成功只认 `completed` 的库内回读**（`action_runs.status = 'succeeded'`，§6）。展示上 `executed` 一行写“已开始”，不写“已成功”。
- **不要求 `executed` 的授权与 `approved` 的是同一份**（`dead_letter` 恢复 / 接管会重签决策）；改成“两跳的决策都属于本请求的 run”。一次性由 `executed` 上的部分唯一索引保证。
- **`approved_by` 与授权记录里的“人”必须对得上**：`human:<邮箱>` 要求决策 `decided_by = 'human'` 且 `lower(decided_by_user)` = 该邮箱；`policy:` / `kernel:` 要求 `decided_by = 'policy'`。
- 先批准后上线、先上线后完成由转移规则保证。`human:` 的批准必须先有 `approval_requested`（走 `pending_pm_approval`）；**仅执行型**的 `policy:` / `kernel:` 可从 `accepted` 直接到 `executing`，观察型没有这条捷径。

**请求类型 × 模式 × 本期能不能进终态（v0.8，复审子牙 5；函数体里写成 `CLOSING_MODE` 表，合同目录以 119 为准）**
| 请求类型 | 模式 | 终态 | 本期状态 |
|---|---|---|---|
| `creative` | 观察型 | `observed_live → fulfilled_observed` | **本期唯一验收的一条** |
| `budget` | 执行型 | `executed → completed → fulfilled`，下游 `action_run`（内核已有 `ads.*` 预算类动作）| 设计已定；`action_key` 白名单由 119 的合同给，给出之前 `completed` 抛 `closing_not_enabled` |
| `audience` / `seo` | 执行型 | 同上 | **合同给出内核动作白名单和下游种类之前一律抛 `closing_not_enabled`** |
| `page` | 执行型（按已有机制）| **本期不许 `fulfilled`，也没有下游种类**：页面发布既没有内核动作也没有执行项 | 台账与页面就绪**解耦**（119 的 PR 2998 v0.3 起）：不挂翻转回执、不读她的 `landing_readiness_current`；开投闸只信 2998 在启用那一刻的现场重读。`page` 请求由生产者 `website_agent` 接单 / 交付 / 送审。**交付即收口（v0.9.1，复审魏征 2；不新增状态）**：写过 `delivered` 回执之后，监督函数不再出卡住待办、不按 `hard_deadline_at` 提醒；到 `valid_until` 照常追加 `expired`（函数拒绝条件不变）但不出待办；链路页显示“已交付（本期台账不再跟进）”。还没交付的照旧：到 `hard_deadline_at`（14 天）出卡住待办，之后只能 `failed`、（批准前）`rejected`，或到 `valid_until` 自然 `expired` |
| `launch` | — | **本期不许 `fulfilled`**（W2 再定）| 不写台账行 |
`closing_not_enabled` 是函数在 `completed / observed_live` 前按这张表挡的：表里没打开的类型（都是执行型），请求只能走 `rejected`（执行型只在批准前：人驳回带凭据，或生产者自己放弃；观察型批准后的撤回只属于 `creative`，§5.2）/ `failed`，或到 `valid_until` 自然 `expired`（`corrected` 不改状态）；它不会静默停在中间——`hard_deadline_at`（`page` 默认 14 天）到了照样出“卡住”待办，提醒人处理（`page` 交付之后例外，见上表）。


## 5. 唯一写入函数 `ad_agent_apply_receipt_v1`
### 5.1 签名与返回
`ad_agent_apply_receipt_v1(p_request_id uuid, p_stage text, p_occurrence text, p_expected_old_status text, p_actor text, p_waiting_on text, p_next_due_at timestamptz, p_approved_by text, p_authorization_source text, p_authorization_id uuid, p_cost_usd numeric DEFAULT NULL, p_provider_ref jsonb DEFAULT NULL, p_source_ref jsonb DEFAULT NULL, p_downstream_ref jsonb DEFAULT NULL, p_human_grant_id uuid DEFAULT NULL, p_note text DEFAULT NULL) returns jsonb`（`p_cost_usd` 缺省 NULL：非 `corrected` 阶段按 0 记，`corrected` 阶段 = 不替换）
返回 `{ outcome: 'inserted' | 'replayed', seq, status_before, status_after, receipt_key }`；失败抛带**机器可读码**的异常：`illegal_transition`、`stale_expected_status`、`receipt_key_conflict`、`actor_not_allowed`、`authorization_invalid`、`authorization_already_used`、`approver_invalid`、`approver_mismatch`、`approver_source_invalid`、`downstream_invalid`、`readback_failed`、`observation_not_live`、`observation_stale`、`creative_link_missing`、`ad_predates_request`、`observation_target_mismatch`、`observation_target_unspecified`、`observation_budget_unreadable`、`observation_ambiguous`、`approval_downstream_mismatch`、`ad_already_claimed`、`evidence_invalid`、`reconcile_not_due`、`reconcile_not_enabled`、`reconcile_chain_conflict`、`reconcile_chain_limit`、`request_expired`、`missing_next_due`、`correction_not_allowed`、`human_grant_invalid`、`closing_not_enabled`、`request_not_found`。**所有底层唯一冲突（SQLSTATE 23505）都在函数里翻成上面对应的码**，不让裸错误漏给调用方。
**没有 `p_status`、没有 `p_client_id`、没有 `p_seq`、没有调用方时间**：新状态由函数算，客户从请求行读，序号函数自己取，`created_at` 是库的 `now()`。

### 5.2 一个事务里依次做（锁后幂等）
1. 校验参数形状（阶段在清单内、`p_occurrence` 符合格式、`p_actor` 在清单内）。**再按本节末的“阶段 → 允许的 actor”表核 `p_actor` 是否被允许写这个阶段**（不允许抛 `actor_not_allowed`）。拼出 `receipt_key`，算出 `payload_hash`。
2. **锁请求行**（`SELECT … FOR UPDATE`）；不存在抛 `request_not_found`。读出请求类型，定**模式**；生产者类阶段（`accepted / linked / delivered / approval_requested`、不带凭据的 `rejected`）在这里按本节末“请求类型 → 生产者”表核 `p_actor`，对不上抛 `actor_not_allowed`（v0.9）。
3. **权威幂等检查（锁后）**：按 `receipt_key` 查已有回执。有 → 比 `payload_hash`：相同返回 `replayed`；不同抛 `receipt_key_conflict`。因为已经持锁，原调用若还没提交，重试会在第 2 步排队，等它提交后才走到这里，必然命中 `replayed`；INSERT 仍兜住唯一冲突。
4. 比 `p_expected_old_status` 与当前状态，不同抛 `stale_expected_status`。
5. **转移规则**（函数体里的 `VALUES` 表，按（模式, 当前状态, 阶段），见 §5.3）：没有这一行抛 `illegal_transition`。终态（`fulfilled / fulfilled_observed / rejected / expired / failed`）：`fulfilled*` 只留 `reconciled`、`corrected`，其余终态只留 `corrected`。附加守卫：
   - `approved`：请求未过 `valid_until`（否则抛 `request_expired`）；`accepted → executing` 只许**执行型**且 `approved_by` 是 `policy:` / `kernel:`，**观察型没有这条捷径**（必须经 `pending_pm_approval`）；
   - `expired`：**必须真过了 `valid_until`**；且该请求**没有 `executed` / `observed_live` 回执**、**没有已被兑换的授权决策**——否则拒绝；
   - `executed` / `completed` / `observed_live` / `failed`：**不因时间拒绝**（真实发生的事必须能记下来）；
   - `completed`（执行型）：必须已有 `executed` 回执；`launch` 类型本期不允许进入 `fulfilled`（§6）。
6. **阶段专属校验**（SQL 里做，不信调用方）：
   - `approved`：执行型按 §4 核验授权；观察型按 §4 表核验批准人（`human:`、先有 `approval_requested`、`review_ref` 对账，含 `approval_source / approver_scope` 标记）与工单指针；**后继请求接手前任工单的**（`supersedes_request_id` 非空，v0.9.1），其 `approved` 只能是“沿用批准”（`actor = system`、`approved_by = policy:carry_over`，核验见 §4 `approved` 行末）：批准不重新给，`review_ref` 的核验整套照做（`approved_by` 须等于 `original_approved_by`），引用的审核记录须与前任 `approved` 回执逐字相等，对不上抛 `approval_downstream_mismatch`（§6）；绑新工单的后继照常走人批；
   - `executed`：`no_publish = false`、`provider_ref` 非空对象、授权按 §4 核验（含 `action_key` 白名单、run 状态 running / succeeded）；
   - `observed_live`：观察型；按 §4“观察核验”八条逐条做（合同目标与预算、内容绑定类关联、下游与批准对得上、候选唯一都在内；合同没给全系列 / 广告组时只许 `human` 指认）；`authorization_*` 为空；`actor = ad_watch` 时 `approved_by` 必须为空，`actor = human`（指认）时必填 `human:<邮箱>` 且备注必填，并带人工动作凭据（kind = `designate_observation`，目标 = 被指认的广告与可选的 `override_target`，§4 第 3 条）；下游已绑定为 `work_order` 并核验（§6）；`p_provider_ref` 必须为空（由函数派生）；
   - `accepted` / `linked`：可带 `p_downstream_ref {kind, id}`，按 §6 核验后**同事务写入 `ad_agent_requests.downstream_ref`**（执行型：`executed` 之后不允许再改；**观察型：`approved` 之后不允许再绑，状态机上 `executing` 里没有 `linked`，§5.3**；后继请求接手前任工单的特例见 §6）；
   - `completed`：下游必须已绑定，库内回读（§6）；**回读失败整笔回滚**；
   - `reconciled`（对账）：①请求须在 `fulfilled` / `fulfilled_observed`；②**`actor` 只许 `reconciler`**；③`source_ref.window` ∈ `t7 / t14`（天数写在函数体：7 / 14），**窗口未到期拒写**（`reconcile_not_due`）——到期 = `now() ≥ 收尾回执的 created_at + 窗口天数`（收尾回执 = 把请求推进到 `fulfilled*` 的那条，或后来“更换观察对象”的 `corrected`；用库时间，调用方改不了），所以“刚收尾就抢先写一条 match 占位”不成立；④**`result` 与 `evidence` 由函数按证据行算，调用方不能给**：观察型（`creative`）的口径写在函数体——**窗口按广告账户的时区算**：窗口 = 收尾回执当天起的 N 个日历日，时区取该广告账户的账户级快照行（`ad_entity_snapshots`，`level = 'account'`）里最新一行的 `timezone_name`；**读不到时区 → `unmeasurable`，不猜、不退回 UTC**（ME 没有客户级时区配置，日数据的 `insight_date` 本来就按账户时区切，用别的时区会错位）。取 `ad_daily_insights` 里该广告（`level = 'ad'`，`entity_id` = `observed_ad_id`）在窗口内的行：**该客户 ad 级日数据已拉到窗口末**（该客户 ad 级行的最新 `insight_date` ≥ 窗口末那一天；没花钱的广告当天可能没有行，所以看客户整体的拉取进度，不看单条广告）时，**`match` 要求“窗口末仍在投”**——窗口**最后 2 个日历日**里这条广告至少有一天花费 > 0，**且**广告级快照里 `captured_at` 不晚于窗口末、离窗口末最近的那一行 `effective_status = 'ACTIVE'`，**且**这条广告所在系列（CBO）/ 广告组（ABO）窗口末前最近一行快照的 `daily_budget_minor` 不超过合同上限（口径同 §4 第 3 条，币种须一致；v0.8 起持续盯，复审魏征 3）；可判定的项有一项不满足 → `mismatch`（超预算时 `evidence.budget_over_contract = true`）；其余都满足、但预算这一项比不了（读不到 / 终身预算 / 账户币种 ≠ 合同币种）→ `unmeasurable`（**绝不给 `match`**，`evidence.budget_unmeasurable` 写原因；v0.9，复审魏征 9）（第一天花了 5 美元、第二天被停，窗口末没有花费，是 `mismatch`，不是 `match`）；没拉到窗口末（或该广告在窗口末之前没有任何快照行）→ `unmeasurable`；`evidence` = 用到的日数据行 id（最多 20 个）+ 汇总（窗口起止日与时区、最后 2 天各自的花费、窗口末前最近一行快照的 id / 状态 / 时间、客户 ad 级最新 `insight_date`、预算行的 id / 值 / 币种）。**其它请求类型的对账口径在启用该类型时补进函数体，补之前对它们的 `reconciled` 一律抛 `reconcile_not_enabled`**；⑤**对账是链，不是唯一占位，但只有 `unmeasurable` 能被接续**：每个窗口的第一条不带 `supersedes`；之后的每一条必须 `supersedes` = 该窗口当前链头的 `receipt_key`，**且链头的 `result` 必须是 `unmeasurable`**（`match / mismatch` 是终局，要接续抛 `reconcile_chain_conflict`——已得出的结论不会被后来的回执悄悄翻盘；错了只能由人 `corrected` 结案或新开请求）；同样走上面全部校验、重新算（数据晚到时 `unmeasurable` 可以接续成 `match` 或 `mismatch`；链不分叉，唯一索引兜底）。**接续的节奏也由函数管，不靠监督函数自觉**：距上一条**不足 24 小时**抛 `reconcile_not_due`，同一窗口**接续超过 5 次**抛 `reconcile_chain_limit`；⑥`result` 是 `mismatch` 或 `unmeasurable` 时回执照写，**监督函数据此出“对账不一致”的人工待办**（§8），直到链头变成 `match`（只有 `unmeasurable` 能变），或有人写 `corrected`（`case_closed: true`，人批，备注必填）结案；
   - `corrected`（更正）：**只能更正两类东西，外加三个受控的专用动作**——①`note`；②`cost_usd`（显式给才替换；带 `action_run_id` 的行不能改成 > 0）；以及——③**结案**：`source_ref.case_closed = true`，目标必须是某窗口当前链头且 `result` 是 `mismatch` 或 `unmeasurable`，备注必填；④**更换观察对象**（`source_ref.replace_observation = {snapshot_ref}`，可带 `override_target`，§6；此时 `provider_ref` 由函数从新快照派生，调用方仍不能给；整套观察核验重做）；⑤**确认先于批准上线的标记**（`source_ref.acknowledges = <该 observed_live 的 receipt_key>`，目标须 `live_before_approval = true`，备注至少 20 个字符（v0.9），只消掉待办、不改任何回执内容）。**v0.7 起删掉了 v0.6 的第③类“更正 `source_ref` 里的指针”**：它能事后改写 `approved / observed_live` 的证据指针（批准的工单、快照、下游快照）而不重核；现在这些指针一律不可更正，认错了只走“更换观察对象”这条整套重核的路。**授权、`no_publish`、阶段、各回执的 `provider_ref`（更换观察对象除外）、`reconciled` 的 `result / evidence` 都不可更正**（要换对账结论，只能由对账者写一条接续的 `reconciled`，且只有 `unmeasurable` 能被接续）；必须 `actor = human`、`approved_by = human:<邮箱>` **并带人工动作凭据**（kind 按动作，见下“人工动作凭据的核验”）；必带 `corrects`（同一请求下已存在的**非 `corrected`** 回执的 `receipt_key`）与 `note`；违反抛 `correction_not_allowed`。原行保留，展示与总成本以更正为准；
   - `rejected`（v0.9 收紧，复审魏征 6；v0.9.1 加撤回，复审魏征 3）：**生产者放弃**——`actor` 是该请求类型的生产者（本节末“请求类型 → 生产者”表）**且**该请求还没有 `approved` 回执——不需要凭据；**其余一律 `actor = human` + 人工动作凭据**，备注必填：批准前用 `reject_request`；**观察型批准后（`executing`、还没有 `observed_live`）用 `withdraw_request`，即“撤回”**。生产者与请求类型对不上、或已有 `approved` 回执（含生产者想撤回批准后的请求）→ `actor_not_allowed`（§5.3：执行型的 `rejected` 只在批准前三个状态合法；观察型另有 `executing → rejected`，只许人带 `withdraw_request`）；
   - **人工动作凭据的核验（v0.8；v0.9 补哈希与金额；所有 `actor = human` 且阶段 ≠ `approved` 的回执）**：必须带 `p_human_grant_id`（没带抛 `human_grant_invalid`；`actor` 不是 `human` 却带了也抛）；函数 `SELECT … FOR UPDATE` 读凭据行并逐条核对——①`request_id` 等于本请求；②`kind` 与本次动作对得上（`rejected` ↔ `reject_request`（批准前）/ `withdraw_request`（观察型 `executing`）；`observed_live` ↔ `designate_observation`；`corrected` 的 `case_closed` ↔ `close_case`、`replace_observation` ↔ `replace_observation`、确认 `live_before_approval` ↔ `acknowledge_flag`、其余（备注 / 成本）↔ `correct_note_cost`）；③`target` 与回执里的目标指针一致（指认的广告号 / `corrects` 的 `receipt_key` / `snapshot_ref` / `override_target`）；④**`target.note_sha256` = 本次回执备注的 SHA-256**（`encode(pg_catalog.sha256(convert_to(p_note, 'UTF8')), 'hex')`，原样不做规范化）；`correct_note_cost` 另要 `target.cost_usd` = `p_cost_usd` 按 4 位小数格式化的文本（`null` ↔ 不替换）；`acknowledge_flag` 另要 `target.evidence_sha256` = 函数此刻从回执重算的证据哈希（§5.6）；⑤`granted_by` = `p_approved_by`（`lower()`）；⑥`issued_at ≤ now() < expires_at`；⑦`consumed_at` 为空；⑧`approval_source = 'me_admin_route'` ∧ `approver_scope = 'internal_staff'`；全部过了才继续，并在**同一事务**里写 `consumed_at = now()`、`consumed_receipt_key`。不过抛 `human_grant_invalid`。**它防的是代码接线错 / 漏传——凭据签给 A 动作却用在 B 上、备注 / 金额 / 证据被换、过期或重用；不防持钥者，持钥者可以自己签（§5.6 §11）。**重放：`p_human_grant_id` 计入 `payload_hash`，同键同凭据重试 = `replayed`（凭据已被这条回执消费，不再核）；同键换了凭据 = `receipt_key_conflict`；
   - 非终态结果必须有 `waiting_on` 与 `next_due_at`（`completed / observed_live` 例外：带对账到期，§8）；`next_due_at` 超过 `hard_deadline_at` 时**截断**，不拒写。
7. `seq = 该请求当前最大 + 1`，写回执（含 `status_before / status_after`）。
8. 更新请求行：`status = status_after`、`updated_at = now()`（必要时 `downstream_ref`；`observed_live` 与“更换观察对象”时 `observed_ad_id`）。底层唯一冲突在这里捕获，翻成 §5.1 的码。
9. 写发件箱一行（同事务）。
10. 返回。

**阶段 → 允许的 `actor`（写死在函数体里；不允许抛 `actor_not_allowed`）**
| 阶段 | 允许的 `actor` |
|---|---|
| `issued` | `ad_agent`（只经 `ad_agent_create_request_v1`）|
| `accepted / linked / delivered / approval_requested` | 该请求类型的生产者（下面第二张表；`ad_agent / video_agent / website_agent / seo_agent` 之一）|
| `approved` | 观察型：`human`（后继请求接手前任工单后的“沿用批准”：`system`）；执行型：`human`，或 `ad_agent / kernel_sync`（`policy: / kernel:`）|
| `rejected` | `human`（带人工动作凭据：批准前 `reject_request`，观察型批准后 `withdraw_request`）/ 该请求类型的生产者（还没有 `approved` 回执时自己放弃，不需要凭据）|
| `executed / completed` | `kernel_sync / ad_agent`（执行型）|
| `observed_live` | `ad_watch`（候选恰好一条、且合同给全了系列 / 广告组时）；`human`（指认：候选多于一条或合同没给全时，带人工动作凭据）|
| `reconciled` | `reconciler`（对账者）|
| `failed` | 各生产者、`kernel_sync`、`system` |
| `expired` | `system` |
| `corrected` | `human`（带人工动作凭据）|

**请求类型 → 生产者 actor（v0.9 写进函数体规则表，复审魏征 6；以 119 的合同目录为准；`failed` 的写入者不变）**
| 请求类型 | 生产者 |
|---|---|
| `creative` | `video_agent` |
| `page` | `website_agent` |
| `seo` | `seo_agent` |
| `budget` / `audience` | `ad_agent` |
| `launch` | —（本期不写台账行）|

`actor` 只是标签，不是凭据：这两张表防的是代码接线出错，并让审计一眼读得懂“谁写的”，防不住持钥者冒名（§11）；**`human` 另要带库里核验的人工动作凭据（§4 §5.6）——同样只防代码接线错 / 漏传并留痕，不防持钥者（他能自己签，§11）**。

TS 外壳 `appendAgentRequestReceipt()`（`src/lib/agent-requests/ledger.ts`）只做三件事：整理参数调 RPC；用 `failClosedIfRpcMissing` 在函数缺失时**当场停**；调用成功后按发件箱发事件并调 `ad_agent_mark_event_emitted_v1`。**回读与核验都不在 TS 里做**。观察型 `approved` 的批准人入参是品牌类型 `VerifiedReviewer`（§4；**编译期的辅助层，不是防线**——库里的防线是函数对 `review_ref` 来源标记的核验），外壳不收字符串。

### 5.3 转移规则（写在函数体里；阶段清单与映射以 119 合同为准，单测展开成矩阵对照）
下表“同状态”= 不改状态。观察型 / 执行型的差别：`accepted` 行的 `approved`、`executing` 行的收尾阶段与 `linked / delivered`、观察型 `executing` 下的撤回，以及 `fulfilled*` 的终态词。
| 当前状态 \ 阶段 | 之后的状态 |
|---|---|
| `requested` | `issued`→requested（仅第一条回执）；`accepted`→accepted；`rejected`；`failed`；`expired` |
| `accepted` | `linked`、`delivered`→同状态；`approval_requested`→pending_pm_approval；`approved`→executing（**仅执行型**且 policy / kernel 批准；观察型没有这一行）；`rejected`；`failed`；`expired` |
| `pending_pm_approval` | `linked`、`delivered`→同状态；`approved`→executing；`rejected`；`failed`；`expired` |
| `executing` | `failed`；`expired`（仅在满足 §5.2 第 5 步的守卫时）。**观察型**：`observed_live`→**fulfilled_observed**；`rejected`→rejected（**撤回**：只许 `human` 带 `withdraw_request` 凭据，v0.9.1，复审魏征 3）；**`linked` / `delivered` 一律 `illegal_transition`**——批准之后下游锁死，要换片 / 改合同 = 撤回 + 后继请求（v0.7，复审高 1；后继接手原工单见 §6）。**执行型**：`linked`（仅在还没有 `executed` 时）、`delivered`→同状态；`executed`→executing；`completed`→fulfilled（须已有 `executed`）|
| `fulfilled` | `reconciled`→fulfilled（窗口到期后，对账链，§5.2）；`corrected`→fulfilled |
| `fulfilled_observed` | `reconciled`→fulfilled_observed（同上）；`corrected`→fulfilled_observed（含“更换观察对象”，仅在还没有任何 `reconciled` 时，§6）|
| `rejected / expired / failed` | 仅 `corrected`→同状态 |

另：**`corrected` 在任何状态下都合法**（不改状态；字段与批准人的限制见 §5.2）。**`rejected` 出现在批准前的三行**（`requested / accepted / pending_pm_approval`），**另加观察型 `executing` 的撤回**（v0.9.1）；谁能写见 §5.2——不带凭据的只限该请求类型的生产者且在批准前，其余要 `human` + 凭据（批准前 `reject_request`，批准后撤回 `withdraw_request`）。

### 5.4 静态扫描降为辅助
仍保留“只有 `ledger.ts` 调这个 RPC”的全仓扫描，但**它不再是防线**：库里没有写权限，直接被拒（属主身份 SQL 除外，§3.3）。

### 5.5 `ad_agent_create_request_v1`（请求创建；v0.6 补规格，归 122 写，与 119 对接）
`ad_agent_create_request_v1(p_client_id uuid, p_request_type text, p_contract jsonb, p_idempotency_key text, p_valid_until timestamptz, p_created_by text, p_supersedes_request_id uuid DEFAULT NULL) returns jsonb`
返回 `{ outcome: 'created' | 'replayed', request_id, receipt_key }`；失败抛带机器可读码：`request_type_invalid`、`contract_invalid`、`idempotency_conflict`、`valid_until_invalid`、`client_not_found`、`actor_not_allowed`、`supersedes_invalid`（v0.9.1）。**没有 `p_request_id`、没有 `p_status`、没有调用方时间**——请求号 `gen_random_uuid()`、`created_at = now()`、`status = 'requested'` 都是函数自己写的。
函数体，一个事务里依次做：
1. 形状：`p_request_type` 在封闭清单内（`budget / audience / creative / page / seo / launch`）；`p_created_by` 在 actor 清单内，且按 §5.2 末“阶段 → 允许的 actor”表允许写 `issued`（即 `ad_agent`）；`p_idempotency_key` 符合 `^[A-Za-z0-9._:-]{8,200}$`；`p_valid_until` 在 `(now(), now() + 30 天]`。
2. 客户存在（`clients`）。
3. **按 `p_request_type` 校验合同正文 schema**：每个类型的必填键 / 类型 / 取值范围 / **不允许多余的键**写在函数体里（键名与取值由 119 的合同目录给，函数体抄写，单测把函数的校验规则与合同 schema 常量逐类型对照，漂了就红）。不过抛 `contract_invalid`。`creative` 另核（v0.9）：`target.ad_account_id` 是该客户在 `client_meta_ad_accounts` 登记的账户；给了 `adset_id` 必须给 `campaign_id`；`max_daily_budget_cents`（正整数）与 `currency`（ISO 4217 三位大写）必填（§4 第 3 条、§12 第 12 条）。**后继请求**（给了 `p_supersedes_request_id`，v0.9.1）：锁前任行，核同客户、同 `request_type`、前任在终态 `failed / rejected / expired`、前任还没有别的后继（`unique(supersedes_request_id)`），幂等键按合同约定并入 `:r<n>`；不满足抛 `supersedes_invalid`。合同更正 = 撤回 + 这样的新请求，旧合同不改。
4. 锁 `(client_id, idempotency_key)`（对唯一索引做 `INSERT … ON CONFLICT`，或 `pg_advisory_xact_lock`），查已有请求：有 → 比规范化合同的 SHA-256：相同返回 `replayed`（连同已有的 `request_id`），不同抛 `idempotency_conflict`。
5. 写请求行；**同一事务**内走与 `apply_receipt_v1` 同一个内部写入例程写第一条 `issued` 回执（`seq = 1`，`status_before = status_after = requested`）和发件箱一行。
6. 返回。
请求表触发器的不可变列（§3.3）、`unique(client_id, idempotency_key)`（要 119 给，§12）与第 4 步互相兜底。

### 5.6 `ad_agent_issue_human_grant_v1`（人工动作凭据签发；v0.8 新增，v0.9 补限流与上下文，归 122 写）
`ad_agent_issue_human_grant_v1(p_request_id uuid, p_kind text, p_target jsonb, p_granted_by text, p_note text, p_issue_context jsonb) returns jsonb`；返回 `{ grant_id, expires_at }`；失败抛带机器可读码：`request_not_found`、`grant_kind_invalid`、`grant_precondition_failed`、`approver_invalid`、`grant_rate_limited`、`grant_context_invalid`。**没有 `p_approval_source`、`p_approver_scope`、没有调用方时间**——来源 `me_admin_route`、范围 `internal_staff`、`issued_at = now()`、`expires_at = issued_at + 15 分钟` 都是函数自己写的。
**谁调**：只有 ME 管理后台路由 `POST /api/admin/agent-requests/[request_id]/human-action`（新入口，A 级）。路由先过 `requireGlobalAdmin()`（内部员工；放行整个 `ADMIN_EMAIL_DOMAIN`，不是 PM 专属，§4），再用**会话邮箱**调签发函数（带 `issue_context`；`target` 里的哈希 / 金额由路由按将要写的回执算），随后在同一次请求里调 `appendAgentRequestReceipt`（带 `p_human_grant_id`，备注 / 金额与签发时一致）；浏览器端从不拿到凭据。
函数体，一个事务里依次做：
1. 形状：`p_kind` 在封闭清单内（七种）——`reject_request / withdraw_request / designate_observation / replace_observation / close_case / acknowledge_flag / correct_note_cost`；`p_target` 恰好是该 kind 规定的键（§3.2；`note_sha256 / evidence_sha256` 为 64 位小写十六进制，`cost_usd` 为 4 位小数文本或 `null`），否则抛 `grant_kind_invalid`；`p_granted_by` 匹配 `^human:[^@\s]+@[^@\s]+$`（比较一律 `lower()`，否则 `approver_invalid`）；`p_note` 至少 5 个字符（必须写理由；`acknowledge_flag` 至少 20 个）。
2. 锁请求行；不存在抛 `request_not_found`。
3. **签发时就核前置条件**（让凭据不能为“做不成的动作”签发）：
   · `reject_request`：请求在批准前的三个状态（`requested / accepted / pending_pm_approval`，§5.3）——`executing` 及之后不用它驳回，不为做不成的动作签凭据。**分工（v0.9.1）**：批准前用 `reject_request`，批准后（观察型）用 `withdraw_request`；
   · `withdraw_request`（撤回，v0.9.1，复审魏征 3）：观察型、状态 `executing`、已有 `approved` 回执、还没有 `observed_live`；`p_target = {note_sha256}`，备注必填；
   · `designate_observation`：观察型、状态 `executing`、已有 `approved` 回执、还没有 `observed_live`，`p_target.ad_id` 在 §4 第 7 条的候选集合内且过第 1–4 条（合同没给全系列 / 广告组时同样可指认）；带了 `override_target` 的，第 3 条按 override 核（两项齐全、等于该广告最新一行快照上的系列 / 广告组）；
   · `replace_observation`：状态 `fulfilled_observed`、还没有任何 `reconciled`，`p_target` 带 `corrects`（本请求的 `observed_live` 回执）与新的 `snapshot_ref`（可带 `override_target`，规则同指认）；
   · `close_case`：`p_target.corrects` 指向某窗口当前链头，`result` 是 `mismatch` 或 `unmeasurable`，且未结案；
   · `acknowledge_flag`（v0.9 加二次核对，复审魏征 7）：`p_target.corrects` 指向 `provider_ref.live_before_approval = true` 的 `observed_live` 回执、还没被确认，**且 `p_target.evidence_sha256` = 函数从回执重算的证据哈希**——规范文本 `<ad_id>|<first_active_at>|<approved_at>|<二者相差秒数>`（`ad_id / first_active_at` 取该回执的 `provider_ref`，`approved_at` 取 `approved` 回执的 `source_ref.approval.approved_at`，时间一律 UTC `YYYY-MM-DDTHH:MI:SSZ`），即人在链路页上看到的那组数；消费时再核一次（§5.2）；
   · `correct_note_cost`：`p_target.corrects` 指向本请求的一条非 `corrected` 回执。
   不满足抛 `grant_precondition_failed`。
4. **限流**（数值取自 `ad_agent_ledger_limits_v1()`，§3.3；计数前取事务级咨询锁 `pg_advisory_xact_lock`，签发是低频动作，串行化没有性能问题）：①同一请求同时**未过期且未消费**的凭据 ≤ 3 条（过期的不算，v0.9.1）；②**非确认类**（另外五类）：同一邮箱滚动 10 分钟 ≤ 5 条，**全局（所有邮箱合计）滚动 10 分钟 ≤ 20 条、滚动 24 小时 ≤ 100 条**（v0.9，复审魏征 5：随机邮箱能绕开单邮箱限额）；③**确认类**（`acknowledge_flag / close_case`：只消待办，不改任何证据）不计入单邮箱限额、也不占②的全局桶，单独一个更高的全局桶：滚动 10 分钟 ≤ 60 条、24 小时 ≤ 300 条（v0.9，复审魏征 8：清理积压时不撞限）。任一超限抛 `grant_rate_limited`。被拒的签发随事务回滚、库里不留行，所以监督函数看的是“满额”状态（§8 第 8 类①）。
5. **记签发上下文 `issue_context`**（v0.9，复审魏征 5）：调用方那半 = 路由传入的 `{route, server_request_id, session_email_hash}`（必须是恰好含这三个键的对象，否则抛 `grant_context_invalid`；内容调用方可伪造）；函数自取的那半 = `session_user`、`current_setting('application_name')`、`current_setting('request.headers', true)` 里的 `user-agent` / `x-forwarded-for`（有就记，没有记 null）。**只用于事后审计和异常发现（§8 第 8 类①），不是放行条件。**
6. 写凭据行，返回。
**孤儿凭据（v0.9.1，复审魏征 4）**：路由是先签发凭据、再写回执；写回执失败会留下一条没被消费的凭据。它 15 分钟自然过期，限额只数未过期的，过期后不占额度；路由失败时把错误告诉操作的人、请他等一会儿再试，**不自动重试**（自动重试会接连签出新凭据，把同请求 3 条的额度占满）。
**凭据防什么、不防什么（v0.9 统一口径，与 §0 §5.2 §11 一致）**：防的是**代码接线错 / 漏传**——忘了带凭据、凭据签给 A 动作却用在 B 上、目标 / 备注 / 金额 / 证据被换、过期或用第二次，库里都会拒；并给每个人工动作留下一条签发记录（邮箱、理由、目标、上下文、时间）和一条消费记录，事后可查。**不防持有 `service_role` 钥匙的人**：签发函数对 `service_role` 开放执行，`p_granted_by` 只按正则校验，没有员工名单、不绑定会话，持钥者可以用任意邮箱给自己签凭据再用掉；全局限流只限住他一次能做多少，`issue_context` 也有一半可伪造。凭据与 `approved` 的 `review_ref` 同级，区分的是“代码路径”而不是“会话”，不是密码学证明。持钥者还能把限额占满，让正常的人签不出（拒绝服务，§11）。可选的后续加固（本期不做）：签发要求一个只放在 Render 网站服务环境里的签名密钥（不在 `.env.local`），库里存一份核对用——它把“只拿到 `service_role` 钥匙就能签”变成“还得拿到网站服务的密钥”，仍不是会话证明。


## 6. 下游绑定、`fulfilled` 的回读（库内）
`ad_agent_requests.downstream_ref = {kind, id, terminal_status}`：
- **绑定**：`kind / id` 在 `accepted` 或 `linked` 回执里由函数写并核验；**执行型**在 `executed` 之前可以重绑（执行卡被批量删、绑错了），每次绑定都是一行回执，`executed` 之后锁死；**观察型在 `approved` 之前可以重绑（绑错了、换了新工单），`approved` 之后锁死——`executing` 状态下没有 `linked / delivered`（§5.3），要换片 / 改合同 = 撤回 + 后继请求（后继可接手原工单一次，见下）**（v0.7：v0.6 在 `executing` 下还允许 `linked`，批准的是工单 A、观察时下游已被换成工单 B，复审高 1）。**没绑定就 `completed` / `observed_live` 不了**（fail closed）。**观察型只许绑定 `kind = 'work_order'`，执行型只许 `action_run` / `execution_item`；`page` 本期一个都不许（带 `p_downstream_ref` 抛 `downstream_invalid`，§4 末表，v0.9）。`observed_live` 之后绑定锁死；认错广告的更正办法见下“更换观察对象”。**
- **绑定时的核验**：对象存在 ∧ 客户一致 ∧ 回链列等于本请求（`action_run` 看 `triggered_by_ref`）∧ **对象创建晚于请求** ∧ **绑定那一刻对象还不在成功终态**。`created_at` 之所以可信，是因为请求表的 `created_at` 由触发器强制为 `now()`（§3.3）。**交叉检查（v0.9.3，⓪ 第二位审查）**：对象自己的 `created_at` 在执行项被删后用同一个 id 重插时可以任写，回链列的触发器也拦不住这种换挂——所以绑定时函数还要查**台账里是否已有别的请求**（不含 `supersedes_request_id` 链上的前任）在回执 `source_ref.downstream` 里绑过同一个 `id`，有则抛 `downstream_invalid`；执行项的回读（下表）再要求 `executed` 授权所属 run 的 `execution_item_id` 等于该执行项。这两条独立于回链列触发器，不能只靠触发器。**后继请求接手前任的工单（v0.9.1，复审魏征 3）**：回链列此刻指向前任——函数核前任在终态 `rejected / failed / expired`、本请求的 `supersedes_request_id` = 回链列旧值、该工单 `agent_request_prev_id` 为空，然后同一事务里把回链列改成本请求、旧值写进 `agent_request_prev_id`（触发器只放行这一种改写，§3.3）；不满足抛 `downstream_invalid`。对后继另有三句：①“对象创建晚于请求”改为晚于**链首请求**（沿 `supersedes_request_id` 回溯到的第一个）；②“绑定那一刻不在成功终态”对后继接手原工单**不适用**：工单被前任绑定、批准、之后正常发布（`published / measuring / closed`）是常态，若仍按它挡，后继几乎永远接不了；改为要求工单状态在**批准后集合**内（`approved / publishing / published / measuring / closed`），且回链列此刻指向前任（上面已核）；③后继的 `approved` 是“沿用批准”（§4 `approved` 行末）：批准不重新给，`review_ref` 的来源标记、批准人等核验整套照做，引用的审核记录须与前任 `approved` 回执逐字相等，对不上抛 `approval_downstream_mismatch`。
- **工单状态的两个集合（v0.7 写明；此前 §4 与 §6 的说法对不上）**：**批准后集合** = `approved / publishing / published / measuring / closed`——观察型 `approved` 与 `observed_live` 核验“成片已被批准”用它；**成功终态** = `published / measuring / closed`——绑定那一刻对象已在成功终态 = 旧对象，不许绑。两个集合不同：批准后集合多了 `approved / publishing`（批准了、还没发出去），成功终态不含它们。
- **回链列只许从空写成一次**（触发器）——旧对象不能被改绑到新请求；错绑的对象就废在那儿，请求侧重绑另一个。**唯一例外**是上面的“后继请求接手前任的工单”，每个工单只一次（`agent_request_prev_id` 非空 = 用过了；执行项没有这个例外）。
- **`terminal_status` 只在 `completed`（执行型）或 `observed_live`（观察型）时由函数回读后写**，不接受调用方提供。

**执行型 `completed` 的回读**（按 `kind`；**只允许 `action_run` 与 `execution_item` 两类下游**——工单表没有和 run 对应的字段，无法把授权绑到工单；v0.8 预留的下游种类 `landing_readiness` v0.9 删除：PR 2998 v0.3 起页面就绪与台账解耦，§4 末表）：
| kind | 回读条件（全部满足才放行）|
|---|---|
| `action_run` | `action_runs.status = 'succeeded'` ∧ `client_id` = 请求客户 ∧ `triggered_by = 'agent'` ∧ `triggered_by_ref = request_id::text` ∧ `created_at ≥ 请求.created_at` ∧ **该 run 就是 `executed` 回执里授权决策所属的 run**（授权与下游动作绑在一起，子牙1）|
| `execution_item` | `status = 'completed'` ∧ `client_id` 一致 ∧ `agent_request_id` = request_id ∧ 创建晚于请求 ∧ **`executed` 授权所属 run 的 `execution_item_id` 等于该执行项** ∧ **该 run 的 `status = 'succeeded'`**（v0.6 补：此前只核了执行项自己的状态，而它是人可以点“完成”的；子牙 / 魏征 v0.5 复审中项 4）|
| 其它（含 `work_order`）| **拒绝**（fail closed）；新增 kind = 改迁移 |

**观察型 `observed_live` 的下游核验**：下游 `kind` 只许 `work_order`（成片工单；执行项接不上 `ad_creative_links`）；对象存在 ∧ 客户一致 ∧ 回链列 = 本请求 ∧ 创建晚于请求（后继请求：晚于链首请求）∧ `status` 在**批准后集合**内 ∧ **`id` = `approved` 回执批准的那个工单**（§4 第 5 条）。这只证明成片在流程里走到了批准；**“这条广告投的就是这条成片”由 §4“观察核验”第 4 条（`ad_creative_links`）负责，“广告现在在投”由第 1、2 条（快照）负责，“广告落在请求指定的目标、预算不超上限”由第 3 条负责（合同没给全系列 / 广告组、或实投与合同不同时只能由人指认，后者带 `override_target`）。**
- **更换观察对象（认错 / 写错广告的更正路径，v0.6）**：`observed_live` 之后绑定锁死，`observed_ad_id` 也不能随便改。认错了广告，由人写一条 `corrected`（`actor = human`，`approved_by = human:<邮箱>`，备注必填），`source_ref = {corrects: <observed_live 的 receipt_key>, replace_observation: {snapshot_ref}}`：函数对**新的快照指针**把 §4“观察核验”八条整套重做一遍（含合同目标与“不含糊”；实投系列 / 广告组与合同不同时凭据带 `override_target`，规则同指认，v0.9.1），通过后**同一事务**里把请求表 `observed_ad_id` 改成新广告（旧广告的认领随之释放，唯一索引重新判），新旧两行回执都保留；对账的到期基准改用这条更正回执的时间。**一旦已有任何 `reconciled`，不允许更换**（对账是对着旧广告做的；要换请新开请求）。

- `fulfilled` 的 CHECK（119 的表上）：`status <> 'fulfilled' OR (downstream_ref ? 'kind' AND downstream_ref ? 'id' AND downstream_ref->>'terminal_status' IS NOT NULL)`；`fulfilled_observed` 另有 §3.3 的 CHECK（要求 `observed_ad_id` 非空）。119 §8 的更强版（`terminal_status` 属于按 kind 约定的成功集合）兼容，建议用它（§12）。
- **`launch`**：本期不写、也不允许 `fulfilled`；W2 再定 `cron_run_log` 这个 kind 的库内核验。

## 7. `receipt_key`、重试与事件
- **出现编号由生产者给，是业务编号，不是重试次数**：`delivered` 用草稿版本号（如 `draft-2`）；`executed` 用授权 id 的后缀；`linked` 用被绑对象 id 的后缀；`observed_live` 用观察到的（或被人指认的）广告 id 的后缀；`reconciled` 用窗口名（`t7`），接续的用窗口名加链位（`t7-r2`、`t7-r3`）；其它一次性阶段用 `1`。重试 / 重放用同一个编号，所以幂等；合法的第二次 `delivered`（两版草稿）编号不同，所以不会被吞。
- 同键同载荷 → `replayed`（成本不会重复累计）；同键异载荷 → `receipt_key_conflict`；**错写了怎么办 → `corrected` 更正回执**（受限，§5.2），不改原行。
- **成本口径**：同一动作的成本只记一处（§1 规则⑥）。内核同步器写的行 `cost_usd = 0`（CHECK 强制），台账总成本视图 = 台账行（按“被更正者以更正为准”）之和，**内核成本单列展示、不与它相加**。
- **发件箱**：回执与待发事件在同一事务落库；TS 外壳随后发事件（事件 id = `receipt_key`）并标记已发；崩在中间，监督函数把 `emitted_at` 为空超过 10 分钟的补发。**发件箱不是安全边界**，且 Inngest 按事件 id 去重只有约 24 小时——**所有消费者必须按 `receipt_key` 幂等**。
- 119 的 `idempotency_key` 含“周期日”：周期日取 NZ 日期（写进合同）；`failed / rejected / expired` 之后同周期要能重发——带 `supersedes_request_id`（119 已同意，v0.9.1），幂等键并入 `:r<n>`（§5.5 §12）。

## 8. 监督函数 `ad-agent-request-watch`（每小时，新西兰 :35；`ad_agent.request_watch.requested` 可人手叫醒）
读 `agent_request_heads`，判八类（v0.9：v0.8 的第 8–10 类并成第 8 类“台账异常”；v0.9.1：其中预算越界、先于批准上线两种单独出红待办，其余进“台账异常汇总”），**并承担两个会写回执的步骤——观察者、对账者**（运行回执写 `cron_run_logs`；读不到请求表 = 函数自己失败，如实写 failed）：
1. **卡住**（非终态）：`next_due_at < now()`，**或** `now() > hard_deadline_at`。`hard_deadline_at = 请求.created_at + 该请求类型的最长全程`——**默认（74 号定）：budget 48 小时 / audience 7 天 / creative 14 天 / page 14 天 / seo 30 天 / launch 空**；可按请求覆盖但不得超过 30 天；函数写 `next_due_at` 时超过它就**截断**（不拒写），所以反复追加“草稿已出”之类的回执推迟不了“卡住”。**没有任何回执的请求**：发出后 2 小时仍无 `accepted` → 卡住。**`page` 请求写过 `delivered` 之后不再判卡住、不按 `hard_deadline_at` 提醒**（交付即收口，v0.9.1，§4 末表）。
2. **过期**：非终态且真过了 `valid_until`——没有 `executed` / `observed_live` 回执、也没有已兑换授权 → 经函数追加 `expired`；**已有 `executed` / `observed_live` 或授权已被兑换** → 不得转 `expired`（函数拒绝），改推红待办“已上线（或已兑换）但已过有效期，请人决定是否停”。**`page` 请求写过 `delivered` 的，到期照常追加 `expired`，但不出任何待办**（v0.9.1）。
3. **已完成但缺对账**：`fulfilled` / `fulfilled_observed` 且对账到期（T+7）已过、没有对应窗口的 `reconciled` → 先由下面的**对账者步骤**补写；日数据没拉到时对账者也会得到一条 `unmeasurable` 回执，所以这一类待办只剩“对账者自己没跑”的情形。
4. **对账不一致**：某窗口当前链头的 `result` 是 `mismatch` 或 `unmeasurable`、且还没结案 → **需人工的待办**（归值班同事，见下“待办写法”；`match / mismatch` 是终局；`unmeasurable` 接续满 5 次仍没结论也停在这里）（what：哪条请求、比对出什么不一致；how：谁去核；href：链路页）。人处理后写 `corrected`（`case_closed: true`，人批、备注必填）**结案**，或等对账者接续写出 `match`；**没结案每天推一条，结案后消失**——不静默，也不永远挂着。
5. **权限与属主名下函数核对**：调 `ad_agent_ledger_security_check_v1()`（§3.3；检查对象含人工动作凭据表与签发函数，v0.9 起含 2990 的关联 / 签字 / stale 原因 / 换创意意图表与写函数）——授权集合与期望不一致（含 PUBLIC、列级授权）、`search_path` 没钉、属主名下引用台账表的函数集合 / 函数体哈希变了、**本稿触发器被禁用 / 被删 / 被改成仅复制角色触发（`tgenabled ≠ 'O'`）** → 红待办（“台账或关联表的写保护被人改了”）。
6. **发件箱漏发**：补发（§7）。
7. **待人指认**：候选多于一条（`observation_ambiguous`，候选集合见 §4 第 7 条），或合同没给全系列 / 广告组而目标账户里已有绑定到本工单的广告（`observation_target_unspecified`）→ **需人工的待办**（归值班同事，见下“待办写法”；what：哪条请求、为什么要人指认、哪几条广告（广告号 + 在投状态 + 所在广告组 + 最早快照时间）；how：核对后在链路页点“指认”，由人写 `observed_live`（`actor = human`，`approved_by = human:<邮箱>`，备注必填，带凭据），函数同样整套核验；href：链路页）。没指认的每天推一条，指认后消失。

- **观察者步骤（actor `ad_watch`）**：对每个观察型、`executing`、已有 `approved` 回执的请求，按 §4 第 7 条算候选集合（目标账户内绑定到**批准的工单**的所有广告，不论状态；一行快照都没有的不算候选，请求在读模型里标“待补快照”、不写回执，v0.9.1）：**候选恰好一条、合同给全了系列 / 广告组、且它通过 §4“观察核验”八条 → 调 `apply_receipt_v1` 写 `observed_live`**（`p_occurrence` = 广告号后缀，`p_source_ref = {snapshot_ref}`）；**候选多于一条，或合同没给全而候选至少一条 → 什么都不写，出“指认”待办（第 7 类）**；没有候选、或唯一那条没通过 = 什么都不写，请求继续等（卡住 / 过期照常判）。**观察者不评价广告好不好，只记“看到在投”；它也不替函数做“第一条通过的就认领”的选择**（v0.6 按 `created_at` 升序取第一条，1 美元测试广告能抢先认领——复审高 3；v0.8 只数在投且过第 1–4 条的广告，测试广告先出现仍会被认领——复审子牙 3，v0.9 改为不论状态）。
- **对账者步骤（actor `reconciler`）**：对每个 `fulfilled_observed` 且某窗口已到期的请求：该窗口还没有链头 → 写第一条 `reconciled`（`p_occurrence` = 窗口名，`p_source_ref = {window}`）；链头是 `unmeasurable` → 尝试接续（`supersedes` = 链头）。**接续的间隔（距上一条 ≥ 24 小时）与次数（≤ 5）由函数把关（§5.2），这里只是按时叫它**，被拒（`reconcile_not_due` / `reconcile_chain_limit`）就等下一小时，或转人工待办。**结论由函数算（§5.2），对账者只负责按时叫它。**
- **沿用批准者步骤（actor `system`，v0.9.1）**：对每个观察型、`pending_pm_approval`、`supersedes_request_id` 非空且已接手前任工单（§6）的请求：前任的 `approved` 回执与工单 `review_ref` 都齐且一致 → 调 `apply_receipt_v1` 写“沿用批准”的 `approved`（`approved_by = policy:carry_over`，`p_source_ref.approval` 带 `carried_over_from / carried_over_receipt_key / original_approved_by`）；任一不一致 = 什么都不写，请求停在 `pending_pm_approval`，按卡住 / 过期照常判。它不评价内容，只做函数核验过的搬运。
- 待办写法：what / how / href 三件套；同一请求同一状态一天一条。**台账来源的待办每客户每天至多 `LEDGER_TODO_DAILY_CAP_PER_CLIENT = 5` 条（含第 8 类那条汇总；数值取自 TS 配置 `src/lib/agent-requests/limits.ts`，§3.3）**：超出的单条并进当天的汇总（计数 + 每行仍带 what / how / href），只折叠、不丢；第 5 类（写保护被改）是全局一条，不占客户额度、不折叠；第 8 类的两条高危红待办（②③）同样不占客户额度、不折叠（v0.9，复审魏征 8：v0.8 每多一类异常就多一类待办，总数没有上限）。**第 4 类（对账不一致，要人结案）与第 7 类（待人指认）归值班同事**（v0.9.1，复审魏征 1）：在 `LANE_OF_KIND` 里分到 `dev` 车道，是开发欠账栏里可点的工作项，带链路页直达链接（结案 / 指认就在链路页点），**不作为单条进 PM 邮件**（PM 邮件里只有开发欠账栏的总数那一行，five-kinds 现状）；钱的事不在这两类里——预算越界、先于批准上线是第 8 类②③的 `decide` 红待办（见上）。其它几类台账待办的车道实现时按 five-kinds 表分（新 kind 不分车道，类型检查过不了）。默认时限（写入者填 `next_due_at` 时用）：预算类批准后 2 小时 / 受众类 24 小时 / 素材类 72 小时出草稿、批准后 24 小时观察到上线 / 页面类 48 小时 / SEO 类 7 天，**都受 `hard_deadline_at` 约束**。
- **`actor` 不是凭据**：任何依赖链上回执的闸**只认库内核验通过的结果**（执行型：`completed` + 下游回读 = `fulfilled`；观察型：`fulfilled_observed` 只是观察线索，**永远不能**当“启用前闸”的依据，见 §11），不认 `actor` 文本。

## 9. W1 验收与测试
**W1 验收（唯一一条端到端链）**：诊断 → creative 请求（`issued`）→ 视频 Agent 接单（`accepted`，绑定成片工单）→ 出片并过质检（`delivered`，带成本）→ 送审（`approval_requested`）→ PM 在 ME 审核页批准（`approved`，记指针当证据）→ 观察者看到广告在投（`observed_live`）→ T+7 对账（`reconciled`，结论由函数按日数据算）。每一跳有回执（含成本、批准人、`mode`、`outside_kernel_authorization`、观察证据、下一步谁 / 最晚何时），链路页能画出来。没真实跑通不叫做好，单测绿不能代替。**创意上线的内核动作落地前，不验收 `executed / completed` 这条路。验收拆成 W1a（`issued … approved`，不依赖关联表和快照，先验）与 W1b（`observed_live … reconciled`，卡在 119 的 PR 2990，另开台账卡），见下。**
**验收拆成 W1a / W1b 两段，再加一张 T+7 的台账卡，不拿 T+7 当场验（v0.7，复审中 7）**：
1. **W1a（`issued → accepted → delivered → approval_requested → approved`；不依赖 `ad_creative_links`，也不依赖盯盘快照，先验）**：
   - **一次性测试库（合并前必做）**：按真实表结构造的**合成夹具**（虚构数据，不是生产数据的拷贝——生产里没有可解析的关联行，§2）：工单行与 `review_ref`（含 `approval_source / approver_scope`），经真函数把链路从 `issued` 跑到 `approved`；同时跑本节全部与批准有关的“被拒”用例。

2. **W1b（`observed_live → … → reconciled`；卡在 119 的 PR 2990，另开台账卡）**：
   - **合成夹具**（按真实表结构造的虚构数据：工单行与 `review_ref`、`ad_creative_links` 行（含 `asset_binding` + `pm_attested` 与签字记录）、广告级 / 系列 / 广告组 / 账户级快照行与抓取记录、日数据行）；**把时间排成“请求在前、广告在后”**——已存在的广告 / 工单 / 执行项不能事后绑到新请求，这是防抢认领的核验，不为验收放宽；沙盘里以属主身份可以改时间。经真函数跑到 `observed_live`；`reconciled` 在沙盘里同样以属主身份把收尾回执的 `created_at` 往前拨 7 天，走一次到期对账（生产里拨不动，这只是验证函数路径）。夹具要覆盖：目标广告组内唯一候选 / 两条候选（`observation_ambiguous`，之后由人带凭据指认）/ 同工单另有一条暂停的广告（同样 `observation_ambiguous`）/ 别的广告组的候选（`observation_target_mismatch`）/ 合同只给账户（`observation_target_unspecified` → 人指认）/ 实投广告组与合同不同（人指认带 `override_target`）/ 撤回 + 后继请求接手原工单 / 绑定的广告还没快照（“待补快照”）/ 窗口末被停（`mismatch`）。

## 11. 残余风险（诚实写明，库里管不到的）
- **持钥者伪造系统记录**：`service_role` 本来能直写 `action_runs`、`authorization_decisions`；观察型读的 `ad_entity_snapshots`、`ad_snapshot_captures`、`ad_creative_links`、`ad_daily_insights`、工单 `review_ref` 也都是 `service_role` 可写的（`ad_creative_links` 与签字表在 PR 2990 落地后撤销 `service_role` 的写权限，只剩 2990 的各写入角色与 DBA 通道，§12 第 11 条；其余几张仍可写）。有钥匙又会伪造的人，可以造一条成功的 run 和一份已兑换的“人批准”决策，把执行型放行到 `fulfilled`；也可以造一整套“广告在投 + 内容绑定对得上 + 落在目标广告组 + 日数据有花费”的证据，把观察型放行到 `fulfilled_observed`。本设计防不住这个；要防得收口那些表的写权限，是各自的 A 级事项（§12(b)）。**v0.7 加的批准来源标记（`review_ref.approval_source / approver_scope`）同理：它能区分“哪条代码路径写的”（路由与 Airtable 同步器写的值不同，库里终于分得出），防不住持钥者直接改写这个 jsonb——所以这里如实写“降级”，不写成“已强制”。**
- **`internal_staff` 不是 PM，人工动作凭据也只是内部员工级**（v0.8 起，复审魏征 4；v0.9 由 `global_admin` 改名，免得与启用回执的 `basis = 'global_admin'`（`ADMIN_EMAILS` 精确名单）同名不同义）：`requireGlobalAdmin()` 放行 `ADMIN_EMAILS` 和整个 `ADMIN_EMAIL_DOMAIN`；开投用的 `requireSpendActivationAuthority()` 要求 `ADMIN_EMAILS` 精确名单（名单上有几个人就放几个人，`src/lib/ads/spend-activation.ts`）。所以 `approved` 与人工动作凭据里的 `approver_scope = 'internal_staff'`，都**不能**读成“PM 批准了花钱”；`fulfilled_observed` 更不能。
- **人工动作凭据只防代码接线错 / 漏传，不防持钥者**（v0.8 起，复审魏征 1 / 5；v0.9 与 §0 §5.2 §5.6 统一口径）：签发函数对 `service_role` 开放执行，`p_granted_by` 只按正则校验，没有员工名单、不绑定会话，持钥者可以用任意邮箱给自己签凭据再用掉；凭据行的 `issue_context` 有一半是调用方给的、可伪造。凭据带来的是：接线错会被库拒、每个人工动作有签发与消费记录、批量滥用能被发现（§8 第 8 类①，检测不是预防）、全局限流限住一次能做多少——它与 `review_ref` 一样是“区分代码路径、留痕”，不是会话绑定的证明。**反方向是拒绝服务**：持钥者可以把“同一请求未过期且未消费 ≤ 3”和全局桶占满，让正常的人一段时间里签不出凭据（方向是拒绝服务，不是伪造通过）；缓解 = 监督函数从凭据表看到满额就进当天汇总待办（§8 第 8 类①），兜底 = PM 授权的 DBA 通道处理（查来源、清理、必要时换 `service_role` 钥匙）。后续加固选项见 §5.6。
- **批准后的两条人工路是有意放开的口子**（v0.9.1，复审魏征 3）：`override_target` 由人带凭据放开系列 / 广告组比对（账户与预算上限不放开），后继请求**有意沿用前任的批准**（批准针对的是成片，合同更正 = 撤回 + 新请求，不重新送审）；两者都依赖凭据与 `review_ref`——凭据只防代码接线错、不防持钥者（上一条），`review_ref` 仍是 `service_role` 可改的 jsonb（下面“批准人是有库内记录但可变”），所以它们留痕、可查，不是强证明。
- **观察后的越界不阻断，只记录和喊**（v0.8）：广告先于批准上线、观察后预算被调高，台账都**不会**让已盖的章倒退或停掉广告（创意上线不受内核授权覆盖，§4），只是在回执 / 待办里留下证据，由人处理；这与“台账从不声称授权或执行”是一回事。
- **PM 不能依赖的几件事（v0.9 汇总）**：①`live_before_approval = false` 不保证“没有先上线”——它只能发现慢上线（§4 第 8 条）；②`fulfilled_observed`、对账 `match` 不代表过了任何预算闸——台账合同上限只管单个请求，2999 的客户日上限管全客户合计（§4“两层预算”）；③收尾 T+14 之后预算再被调高，台账不盯——由 2999 的客户日上限（启用那一步现场检查 + 每日只读审计，事后最长约 24 小时发现）与内核信封（内核动作加预算硬拦）兜；④人工动作凭据不防持钥者（上面）；⑤台账分不出“正式那条广告”和“测试广告”——测试广告投在目标广告组里、又是当时唯一候选时会被如实认领（§4 第 7 条、§8 第 8 类④）。
- **成功终态信任的是可变状态或外部观察**：执行项 `completed` 是人可以点的；工单 `approved…closed` 是工厂流程里的状态；观察型的“广告在投”来自 Meta 的抓取，库里验不了真伪。因此**这些成功终态不单独撑 W2 的“启用前”闸**——闸只认执行型的 `action_run` 回读（`fulfilled`）；**`fulfilled_observed` 永远不当闸的依据**。（v0.5 曾写“或 T+7 对账 `match`”，已删：对账读的是同一批系统表，对持钥者不构成独立证据；它能发现的是漂移——广告被停 / 删 / 从没花钱——不是伪造。v0.7 把 `match` 收紧成“窗口末仍在投”（最后 2 天有花费 ∧ 窗口末前最近一行快照仍是 ACTIVE），“第一天花了钱第二天被停”现在是 `mismatch`。）
- **广告与成片的绑定不是内容哈希**：`published_post_id` 靠“建广告那一刻记下的帖子 id 精确命中已发布工单”；`asset_binding` 靠“广告创意的源视频 = 素材池条目 → 条目的 `work_order_ref`”，这一跳的根是 **PM 在签字页单独签的“这条视频就是工单 X 的成片”**（`creative_binding_attestations` 钉住签字时工单 `final.mp4` 的哈希；Meta 会重编码，哈希证明不了“Meta 上的视频就是这个文件”，2990 v0.4 §3）——所以 `provider_ref.link_strength` 如实标 `pm_attested`（人认定，弱于 `post_id`）；只过了标题前缀核验的是 `asset_binding_provisional`，台账不放行。“这条广告里跑的就是被批准的那个视频文件”没有字节级证据。**换创意**：库里只能从快照的 `creative_video_ids` 看出“换了视频”；换了创意但视频没变、或在 Meta 后台 / MCP 手换的，要等 119 的每日扫描（读 Meta 比 `meta_creative_id`，对不上标 stale）——空档最长到下一次扫描（台账要求复核不超过 30 小时，§4 第 4 条）。
- **批准人是“有库内记录但可变”**：观察型 `approved` 的 `human:` 邮箱来自已验证的内部员工会话，函数再核工单 `review_ref`；`review_ref` 是 jsonb，`service_role` 可改写；Airtable 路径写的批准人不是会话验证的，v0.7 起它在 `review_ref` 里带 `approval_source = 'airtable_sync'`，函数据此拒收（`approver_source_invalid`），该路径不产生台账 `approved`（§12(e)）。
- **平台回执号 / 观察线索的真伪库里验不了**（外部系统）：执行型靠授权真实且一次性 → 下游对象库内回读；观察型靠“最新快照 + 近期抓全 + 关联行 + 认领唯一 + T+7 对账（发现漂移）”。
- **“落在合同目标”防的是误认，不是伪造**：目标由 119 的合同给（账户必填，系列 / 广告组可空）；候选是“目标账户内所有绑定到本工单、已有快照的广告，不论状态”（一行快照都没有的先不算，显示“待补快照”）——多于一条、或合同没给全系列 / 广告组时不自动选，由人指认（实投与合同不同时带 `override_target`，§4 第 3、7 条）；人为制造多候选（再登记一条绑同一工单）只会让请求多出一次人工指认——方向是拒绝服务，不是误放行。**“广告晚于请求”**优先用关联行的 `meta_created_time`（登记入口读 Meta 写入）；为空时用最早一行快照的时间近似（盯盘表没有广告创建时间列），最坏误差一个抓取周期（6 小时）：请求发出前 6 小时内建的广告可能被当成之后建的；但它还得过“绑定到本请求批准的工单”那一关，而该工单创建晚于请求（§6），所以这条核验是兜底，不是唯一的防线。**分不出正式广告和测试广告**：测试广告投在目标广告组里、又是当时唯一候选时，会被如实认领（台账只说“观察到在投”）；之后出现第二条候选只会进当天汇总喊人（§8 第 8 类④），不会让已盖的章倒退；改认走“更换观察对象”（T+7 对账前，§6）。
- **属主身份 SQL 不受限**（迁移、SQL 编辑器、MCP 的 `execute_sql`）：DBA 通道，靠流程管；应用运行时不得用属主身份的直连连接串；常驻核对（§3.3 §8）只能发现“权限被改回去 / 属主名下函数集合或函数体变了”，发现不了变更当时的意图，也发现不了属主身份直接改数据。
- **回链列触发器的边界**（v0.9.2，⓪ 实现时独立审查实测）：①执行项**可以被删**（调度器会删待处理项），所以“先删再用同一个 id 重插”在执行项上拦不住，只靠“绑定那一刻对象创建晚于请求”、回链列只写一次和 §6 的台账交叉检查兜（`created_at` 在重插时可以任写，所以不能只靠触发器）；工单表已补 DELETE 和 TRUNCATE 守卫；②同一张表上的 BEFORE 触发器按名字顺序执行，守卫不保证排最后，排在它后面的触发器改了回链列它拦不住（只有属主能加触发器，常驻核对要覆盖）；③会话标记任何角色都能设，挡不住“属主名下、参数可控、会写这两列的 SECURITY DEFINER 函数”，靠常驻核对（§3.3 第三层）兜；④打回重开工单、撤回后重派执行项、诸葛的“作废 + 新插”都会生成**没有回链的新行**，它们也是“创建处”，写入点 PR（§10 ① ②）要一并覆盖；若以后批量 upsert 时带上回链列，只要有一行值不同或被补成空，整批都会失败。
- 阶段清单 / 转移规则 / 合同常量三处抄写（含九态、`actor` 矩阵、各请求类型的合同 schema），漂开只能靠矩阵对照单测发现；合同目录落地前本稿的映射是草案。
- 本稿所有规则在迁移 apply 之前都是纸面设计；A 级，apply 要 PM 显式 go，且先在一次性的测试库里把 §9 的用例跑一遍。

## 12. 给 119 的对齐项 与 剩余待办

1. 函数入参：119 稿是 `new_status` + `receipt_seq`；本稿改成 **`stage` + 函数体里的转移规则**（库里算，不信调用方，规则不放可改的表里）。保留的：`expected_old_status`、行锁、终态不可覆盖、乱序不倒退。`receipt_seq` 由函数在持锁时取。
2. **阶段词表 14 个**（不变，v0.5 起）；**状态词表由八态改九态：加 `fulfilled_observed`**（观察型终态，展示“观察到在投”；`fulfilled` 只留执行型）。请 119 回一句“同意”并写进合同常量与 `ad_agent_requests.status` 的 CHECK。**若她不愿加状态**，退一步：保持八态，请求表加一列 `closing_mode`（`executed / observed`），由函数在进入 `fulfilled` 时写，所有读 `fulfilled` 的地方必须同时读它——但“忘了读这一列”就会把观察型当成履约，是更弱的防线，我不推荐。
