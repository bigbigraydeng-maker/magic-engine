# 发布日历（Publishing Calendar）设计稿 v0.2

- **日期**：2026-10-14（新西兰）｜ **窗口**：74 号（CTS 广告总控）｜ **风险级**：A（最终会决定对外发布什么）
- **状态**：只出方案。没有代码、没有建表、没有改任何发布开关。
- **缘起**：PM 2026-10-13 问：「每日计划是按 campaign 走的，那 story 是按什么走的？还是说我们应该有一个像『每日发布日历』一样的汇总界面？这个界面应该包括多个 campaign 报名要发的 post、reels 和 story，然后用大模型分析鉴别选出最应该发的。因为每天不可能发无数条，应该有总量限制。还是你觉得这个界面就应该是开放式的，所有 campaign 都可以报名往出来发？」
- **v0.1 → v0.2**：PM 2026-10-14 拍板「按这个做，但是报名和挑选我希望都是自动化」。因此：报名由各内容来源按排程**自动写入**，不再靠人在窗口之间搬文件；挑选**从第一天起就是自动的**（硬规则 + 分配是程序，模型是其中一个零件，等真的有人抢名额才接上）。PM 保留的只有「每周看一眼 + 点一次授权」。
- **平台层级（Tier Gate · Inline）**：属于既有「社媒」支柱 Act 段的编排层，不新增支柱、不新增能力线；日历是平台通用机制，每天发几条与内容规则是行业/客户层配置。

---

## 0. 给 PM 的一页话

**要解决的事**：现在三类内容各走各的路——图文帖按「推广活动」走（一个活动一个官网链接一周 7 天），Story 按「客户一周 18 条」走，Reel 按「视频工厂工单」走。没有一个地方能回答「今天到底发什么、为什么是它」。

**做法**：建一本**发布日历**，它是唯一决定「哪天发哪条」的地方。

- **谁都可以报名，而且是自动报名。** 内容是谁做的，谁就按排程自己把成品写进日历——排期 agent 每周出完内容直接写进来，视频工厂的片子一过审也自己写进来。**没有人在窗口之间搬文件、搬图。**
- **但名额是封顶的。** 每天图文帖 2 条、Story 3 条，每周 Reel 3 条。报名多于名额时发不完，多的顺延或作废。
- **挑选也是自动的。** 先用硬规则筛掉不合格的（事实没出处、画面没过审、图和最近发过的重复、带价格但配图来源不明），再按「哪个团更急、别让同一个团刷屏、同一天三条 Story 角色要不同」自动排进每一个时段。每条为什么排在这里、为什么没被排上，日历上都写着。
- **你只做一件事**：每周看一次这张日历，点一次「授权这一周」。

**挑选里的「模型」是其中一个零件，不是全部**：硬规则和分配是程序做的，从第一天就自动。只有当同一个格子里**合格的候选多于名额**时，才需要模型来判「这几条里今天最该发哪条」。CTS 现在候选数正好等于名额（每周 12 条图文、18 条 Story、3 条 Reel），没有人在抢名额，所以这个零件**先留好接口、暂不接模型**，超额时先按「团更急 → 先提交的先上」这条明规则决定，并在日历上写明理由。真出现抢名额再把模型接上去。

**PM 保留的唯一人工环节是授权**，这是故意的：对外发布是撤不回的动作，必须有人点头。报名、挑选、排时间、发布、巡检、复盘，全部自动。

**分三步，每步你都能叫停**：① 日历页面（只读，看得见每天发什么、名额用了几个、谁被挡在外面）→ ② 候选表 + 自动报名 + 自动挑选 + 一处授权 → ③ 模型挑选零件（等报名多过名额再接）。

## 1. 先核实的事实（查的是生产库与代码，不是文档）

| 事实 | 出处 |
|---|---|
| CTS 现有 8 个 active 的推广活动，绝大多数是**主题**角度（圣诞、免签、品牌曝光、SEO 地基），只有 1 个是单团（上海周边团）；不是「一团一个活动」 | 生产库 `campaign_briefs`（2026-10-14 只读查询） |
| 每日计划 = 一个推广活动的 7 天，每天 Post+Story(4帧)+Reel 三格；自动发布只接了 Post，唯一键（计划，日期），发布时间写死新西兰 08:00 | `src/lib/campaign/daily-plan.ts`、`20261010100000_daily_plan_auto_publish.sql`、`daily-plan-publish.ts` |
| CTS 的每日计划一共 4 份，最近两份建于 2026-10-06；**这周的内容一条都没写进去** | 生产库 `social_plans`（`plan_kind = campaign_daily_v1`） |
| Story 周包不属于任何推广活动：表里只有客户、标题、授权、条目（渠道/时间/图/文字/状态/回执） | `src/lib/social/story-lite/types.ts`、生产库 `story_packs` / `story_items` |
| Reel 工单没有「计划发布日」字段 | 视频工厂工单（84 号 2026-10-13 核实） |

**结论**：三条线各有自己的「身份」，**没有共同的主键**。日历要成立，必须引入一个三者都能挂上去的东西——「候选」。

## 2. 核心模型：三层

```
候选（谁想发什么）  ──报名──►  日历（哪天发什么·名额封顶）  ──授权──►  发布器（Story/Post/工厂各自发）
   任何活动都能报                  挑选在这里发生                      已建好，不改
```

### 2.1 候选 candidate

一条候选 = 一件**可以发出去的成品**，不是创意点子。它带着：

| 字段 | 说明 |
|---|---|
| 客户 | 必填 |
| 格式 | 图文帖 / Story / Reel |
| 内容 | 图（公开存储地址 + 文件指纹）、正文、首评（带追踪参数的链接）、Reel 则是工单号 |
| **讲哪个团** | 自由标签，例如 `BOC-2027-03-11`。**与推广活动分开**——现有活动多是主题角度，不能当团用 |
| 来自哪个推广活动 | 可空（品牌类内容没有活动） |
| 角色 | 拉新 / 讲清行程 / 灵感 / 事实 / 邀请私信 |
| 想什么时候发 | 具体某天某时，或「这一周任意一天」 |
| 谁提交的 | 内容窗口、每日计划生成器、视频工厂 |
| 审查状态 | 事实（苏东坡）、画面（马良）各一个签字 |
| 事实出处 | 事实库编号，没有出处的不收 |

**开放报名，且自动报名**（PM 2026-10-14）：任何推广活动、任何来源都能提交，而且是各来源**按排程自己写进来**，不经人手。三个来源现在怎么变：

| 来源 | 今天 | 自动化之后 |
|---|---|---|
| Story / 图文帖 | 内容窗口做好图与文案放 Dropbox，由另一个窗口按文档手工导入 | 排期 agent 每周固定时间跑完，**直接写候选**（图先传公开存储、带指纹），导入脚本退役 |
| Reel | 视频工厂出片 → 审查 → PM 点通过 | 工单一通过**自动写候选**（带工单号与封面帧），日历决定哪天发 |
| 每日计划（主题活动） | 自己一条线，关着 | 它产出的 Post 也可以**自动报名**进日历；它仍不自己发 |

**报名是写入，不是请求**：候选写进来即存在，合格与否由日历的硬规则判，不需要谁批准「可以报名」。

### 2.2 日历 calendar

一本日历属于**一个客户**（不属于活动），按新西兰日期排。每一天每一种格式有**名额**：

| 格式 | 名额（CTS 当前） | 来源 |
|---|---|---|
| 图文帖 | 2 条/天 | PM 2026-10-12 拍板 |
| Story | 3 条/天（08:30 / 13:00 / 20:00） | 同上 |
| Reel | 3 条/周 | 同上 |

名额是**客户层配置**，不写死在代码里。另有两条分配上限（防刷屏）：
- 同一个团每天最多 1 条图文帖、最多 2 条 Story；
- 同一天的 3 条 Story 角色必须各不相同（灵感 / 事实 / 邀请）。

**封闭挑选**：名额满了就发不出去，多的顺延到下一个有空位的日子，或过期作废。这是 PM 问题的另一半答案——**挑选封闭**。

### 2.3 发布器

已经建好的三套：Story 最小版（在跑）、图文帖最小版（设计中）、视频工厂（在跑）。**日历不重写它们**，只把「这一天发这一条」写进各自的周包/工单。

## 3. 挑选怎么做（三道，顺序不能换，全程自动）

**三道都由程序触发，没有人工环节。** 每周排期 agent 写完候选后自动跑一次，之后每有新候选写入再跑一次（例如工厂新片过审）。结果写进日历，并对每条给出一行理由。

### 第一道：硬规则（程序判，不过就不能进日历）

1. 事实签字、画面签字都有；
2. 事实有出处（事实库编号或官网可溯）；
3. 图文件指纹与本周已排的、近 30 天已发的都不重复（**首帧不撞脸**的程序部分）；
4. 正文不含链接；首评链接四个追踪参数齐；
5. 带价格的，配图必须是确认过来源的客户实拍/官方素材（沿用现有两道价格闸）；
6. 标为「纯文字卡」的不收。

**「查不到」不等于「不合格」**：官网抓不到、接口报错时记「未核到」并交人判，不自动淘汰、也不自动放行。

### 第二道：分配（程序判，保证公平）

按**紧迫度**给每个团一个权重：离出发日越近、已订座位越少、销售窗口越短的团，这周拿到的名额越多。CTS 当前：3 月四个团（11/18/25/26 March）销售窗口到 11 月底，权重最高。

### 第三道：排进时段 + 超额时挑选（自动）

合格并配好额的候选，自动排进当天的时段：Story 按角色对号入座（灵感→08:30、事实→13:00、邀请→20:00），图文帖按团轮换，Reel 按工厂出片顺序隔天一条。**这一步永远自动，没有人工。**

同一个格子里合格候选**多于名额**时，才需要「挑」：

- **第一版（现在）**：按明规则——团更急的优先，同样急则先写进来的优先。规则是确定的，结果可复现，日历上写明「选它因为 X 团 3/11 出发、本周只排到 1 条」。
- **第二版（真的开始抢名额时）**：在同一个位置接上模型，输入是已合格、已配额的候选，输出是「选哪条 + 每条一行理由（选中的和没选中的都要）」。**接口第一版就留好**，换的只是这一个函数。

**为什么不一上来就接模型**：CTS 现在候选数 = 名额数，每一格都是「有几条就排几条」，模型没有可挑的东西，接上去只是空转和花钱。**这不是不做自动化——挑选从第一天就是自动的，只是超额分支先用明规则。** 一旦某一格出现超额，这条记录就是接模型的触发条件。

## 4. 授权

- **一周一次**，授权的是**日历这一周**，不是某一个包。
- 授权时记下这一周每条内容的指纹；**授权之后任何内容被改动，那一条自动变回未授权**，不会偷偷发出去。
- 授权覆盖日历后，由日历把「这一天这一条」写进 Story 周包 / 图文帖周包；Reel 仍在视频工厂点通过（过渡期），日历显示它的状态与跳转。
- **落差要如实告诉 PM**：第一版是「一次点击 + Reel 另有一处」，不是三类全在一个按钮里。

## 5. 页面长什么样

一页，按天排（本周 7 行），每行三栏：

```
10/14 周三    图文帖 2/2 ███  Story 3/3 ███   Reel —
  08:30  Story · 灵感 · Tale · 故宫红墙雪顶 ·「Discover imperial Beijing」· 已授权 · 待发
  10:00  图文帖 · 讲清行程 · BOC · [缩略图] ·「Day 12 ...」· 尚未接入
  13:00  Story · 事实 · BOC ·「Beihai Park」· 已授权 · 待发
  ...
10/15 周四    图文帖 0/2 ░░░  Story 3/3 ███   Reel 1/3（本周）
  ⚠ 图文帖今天没人报名
```

- 顶部一句话：**现在是演练模式 / 真发已开**，**这一周已授权 / 未授权**。
- 每天每格显示「用了几个 / 共几个」，空位显眼。
- 每条显示：时间、格式、角色、团、缩略图、一句话、状态。
- 被硬规则挡下的候选单独一栏「没能进日历」，写明被哪条规则挡的——**管道不许断头**，不能只留在日志里。
- 中文大白话，不出现「素材池 / 指纹 / 信封」这类词。
- 仅全局管理员可见，服务端按客户过滤。

## 6. 分三步做

| 步 | 做什么 | 验收 | 谁 |
|---|---|---|---|
| ① 日历页面（只读） | 读现有三处（Story 周包、图文帖周包、工厂工单）按天显示 + 名额用量 + 「没能进日历」栏 | PM 打开能看懂这一周发什么、还差几条 | 84 号（「本周总览」已交 PR #2548，按本稿补名额用量与被挡栏） |
| ② 候选表 + 自动报名 + 自动挑选 + 一处授权 | 候选表；各来源按排程自动写入；硬规则 + 分配 + 排时段（全自动）；日历写进各自周包；一次授权 | 一周内容从产出到授权**全程没有人搬文件**；日历上每条都有一行理由 | 待定，PM 批了再开 |
| ③ 模型挑选零件 | 只换超额分支那一个函数，逐条写理由 | 有一次真实的「挑了 A 没挑 B」并给出理由 | 等真的抢名额了再接 |

**明确不做**：跨客户看板、内容生成、改图、自动补发、Instagram、把每日计划那条线改造成日历（它保持关着，不删）、给日历做审批流（审查仍在苏东坡/马良那里）、**自动授权**（对外发布必须 PM 点头，见 §4）。

## 7. 对现有东西的影响

- **每日计划**：保持原样、保持关着。它仍是「一个推广活动的 7 天」，适合主题式活动；日历不取代它，**日历取代的是「谁决定今天发什么」这件事**。将来每日计划的产出也可以作为候选报名进日历。
- **Story 最小版 / 图文帖最小版**：不改，成为日历的「发布器」。
- **视频工厂**：不改，Reel 仍在那里点通过。
- **巡检员**：日历给它一张「这一周应该发什么」的对照表，它现在是拿周包文档对的。

## 9. Reuse Statement

- **复用**：Story 最小版的周包/条目/授权/指纹/扫描约定；图文帖最小版同构设计；视频工厂工单；现有事实与画面审查角色；现有价格闸与首评写入器。
- **平台共享**：日历、候选、名额、硬规则、分配、授权绑指纹——都不含客户名与行业判断。
- **行业层**：旅游版默认的角色分工（拉新 / 讲清 / 灵感 / 事实 / 邀请）与「按出发日紧迫度分配」。
- **客户层**：CTS 每天 2 帖 3 Story、每周 3 Reel、三个发布时刻、四个在推的团。
- **没有**客户私有事实写进共享代码。
