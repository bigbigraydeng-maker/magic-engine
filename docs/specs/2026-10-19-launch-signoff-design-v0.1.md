# 「重大功能上线签字」最小版设计稿 v0.1（只设计，不写代码）

日期 2026-10-19 · 作者 118 号 · 依据：PM 10-19 定的规矩（统筹 18 号转述）；`docs/specs/2026-10-19-ads-agent-test-checklist.md`（T1–T7）；读过的现有零件：内核人工审批（`lib/kernel/human-approval.ts`，按“动作运行”签的）、推广计划核实记录（`promo/types.ts` 的 `verified_by / verified_at / content_hash`，内容改了旧核实自动失效）、台账 `docs/ledger`、开关所在 `ad_strategy_configs.autopilot_dry_run`。**A 级（碰授权/签字）：须子牙+魏征审、PM 点头才开发。**

## 给 PM 的结论
1. 做法：新增一个后台页「上线签字」，列出测试清单每一项的 **目标 / 通过判据 / 状态（通过·失败·没测）/ 真实证据 / 18 号复核**；**全部通过**才出现「签字上线」按钮，点了记下 **谁、什么时候、对应哪个代码提交**。有一项没过按钮灰着并写差哪项。
2. **能不建表吗？不能，但只需要 1 张很小的表**（见第 4 节）。别的零件都不合适：台账是代码仓库里的文件，后台点一下没法写进去；内核审批是给“动作运行”签的，硬套会把内核搅复杂。需要你点头：**允许新增 1 张追加式小表 `launch_signoff_events`？**
3. 这一版**只签字，不翻开关**：签完字，“关演练开关”仍是单独一步（第 6 节写了以后怎么把两者锁在一起）。

## 1 入口
左栏 `ADMIN_SECTIONS` 第 1 组（和「等你点头的广告 / 动作」并列）加一项「上线签字」→ `/dashboard/launch-signoff`。仅管理员；沿用现有 admin 判断，不放宽。

## 2 页面内容
一页一个功能（这一版只有「广告 Agent 机器验证」）。页头：功能名 · 风险级 A · 被测代码提交号 · 当前线上提交号（Render 的 `RENDER_GIT_COMMIT`）。
表格 7 行（T1–T7），每行：目标 · 通过判据 · 状态 · 证据链接（库表+记录 id+时间，点开是只读详情）· 18 号复核结论（通过/退回 + 一句话 + 谁 + 何时）。
**状态规则**：一项只有在“执行方留了回执（119）”**并且**“复核方（18）另行确认”两步都有，才算「通过」；只有执行方的回执显示「待复核」，不算过。生产者≠质检者，沿用工厂规矩。

## 3 签字
- 按钮「签字上线」只在 **7 项全通过 + 被测提交号 = 当前线上提交号** 时可点；否则灰着并写原因（“差 T3、T6”或“测完之后代码又变过，需 18 号重新复核”）。
- 点后弹确认框（写清：签字不会翻任何开关）。服务端**重新核对**全部条件再写库，不信前端；签字人取自登录会话（不由页面传）。
- 记录：姓名/邮箱 · 时间 · 提交号 · 清单指纹 · 当时 7 项状态快照。只增不改；撤销也是新增一条“撤销”。

## 4 数据放哪
一张追加式表 `launch_signoff_events`：`id, feature_key, event_type（item_result | review | signature | revoke）, item_key, status, evidence_ref, actor, actor_role, commit_sha, checklist_hash, note, created_at`。
- 当前状态 = 每个 (feature, item) 取最新事件；全部只增（数据库触发器禁止 UPDATE/DELETE，同内核决策表做法）。
- RLS 按仓库铁律：`FOR ALL TO service_role USING (true)`，不放行匿名；读写全走服务端接口。
- 为什么不复用：台账（仓库文件）写不进；`kernel` 审批需要 ActionDefinition 和授权政策，签字不是“执行动作”；推广计划的 `verified_by` 挂在计划 JSON 上，没有“功能”这个对象。**风格上抄推广计划的两点**：记谁+何时、内容指纹变了旧签作废。
- 迁移属 A 级，另案、等你点头后再写。

## 5 清单从哪来、谁更新
- **清单内容**：仓库里一份结构化定义（`src/lib/launch-signoff/checklists/ads-agent.ts`：key、标题、目标、判据、负责人），手写一次，文件头写明对应的文档路径；**不从 markdown 表格解析**（自由文字，容易解析歪）。定义的指纹随事件一起记，清单改了旧签字自动失效。
- **状态谁写**：119 测完用一条命令写 `item_result`（附真实证据：表名+记录 id+时间）；18 号复核写 `review`（通过/退回）。命令走服务端接口，鉴权用现有管理员/服务钥匙，页面只读。
- 没人写 = 状态「没测」，按“没测完”处理。

## 6 最小范围与以后推广
- 最小：1 张表、1 个页面、1 个清单定义、3 个接口（读/写事件/签字），仅这一个功能。
- 推广要改：①清单登记表（多功能）②**闸**——给“翻开关”的服务端接口加一行 `requireSignoff(featureKey)`（例：把 `ad_strategy_configs.autopilot_dry_run` 改成 false 前必须有有效签字，否则 409）③今日待办加“待签字：X”提醒（用现有 manual-items 做法）④A 级 PR 模板要求写 feature_key。②是真正“才能翻开关进生产”的落点，**这一版不做**，因为它改的是广告执行链的开关接口（A 级，碰钱）。

## 7 风险与回滚
| 风险 | 对策 |
|---|---|
| 把签字当成“已上线” | 页面和确认框都写明“只签字，不翻开关”；开关仍是原来的单独一步 |
| 状态被写假（执行方自说自话） | 必须有 18 号另起的复核事件；证据必须是库表+记录 id，页面可点开核对 |
| 测完代码又变了 | 签字绑提交号，线上提交号不同按钮灰；清单指纹变了旧签作废 |
| 误签/要撤 | 撤销=新增一条事件，历史不删 |
| 页面或接口出问题 | 回滚=去掉左栏入口与接口；表里只有审计事件，留着无害。没有闸挂在上面，不会卡住别的功能 |
| 没验证的 | Render 的 `RENDER_GIT_COMMIT` 在本服务是否可用（需要上线时实测）；其余是设计，未实现 |
