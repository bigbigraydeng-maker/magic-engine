## 1. PM 版结论（先看这里）

**第一件事：手册写好了，分四块——策略、内容、效果、预算，预算只占其中一块。**
每条规则都写成同一个格式：条件 → 动作 → 谁做 → 证据从哪来 → 样本要多少 → 现在有没有代码。后面派代码，直接照着派。

**第二件事：一条授权分歧要你先定——这是本手册最大的一个坑。**
你 9-24 授权过广告「全权自治」（含自动加预算、自动开新广告）；你今天（10-10）又要求「开投、加预算、改受众必须你本人授权」（换素材已改为系统自己换、事后报）。两条冲突。**我按今天的写**，并发现现有代码里 CTS 已经处在「自动批准」档（见 §2.3）——所以这条放在 §10 第 1 位。

**第三件事：预算口径你还没想好，我没替你定。**
「每天 150」和「每月 5,000（谷歌 + Meta 合计）」两种口径下规则会分叉，§7.2 把两条路都写了，你定了再选。

**第四件事：现在这份手册还不能让系统「自己看懂数据就动手」。**
大约一半规则已经有代码（疲劳判定、版位漏检、结果口径），另一半写好了但没人调用（真实花费上限判据、付款告警），还有一部分完全没有（换素材前后对照、创意测试通道、命名校验）。§11 逐条列了。

## 1b. 工作流总图（PM 2026-10-10 要求重想：先把 agent 要干的活想清楚，再分平台 / 行业 / 客户三级）

> 本节是全手册的**骨架**，后面 §3–§7 的规则都挂在这张图上。本节不出现任何客户名和客户数字。
> 现状三档：**有** = 已自动在跑；**半** = 有零件但要人接 / 没连成一条线；**无** = 没有。

**一句话分工：平台定「做什么、什么时候做、谁批」；行业定「怎么判、看哪个结果、什么季节」；客户定「具体数字、具体的人、具体的素材」。**
行业级和客户级**不新增工作**，只往平台级的工作里**填空**。所以一个新客户接进来，agent 不用重新学「每天干什么」，只要把空填上。

### 1b.2 行业级：平台工作流里要行业来填的空

> 每个行业填同样的 7 个空。**两个以上客户验证过才算定论；只有一个客户的一律标「候选」。**

| # | 空 | 它影响平台级哪一步 | 旅游（候选，1 个客户） | 物流（候选，1 个客户） | 地产 / 电商 / 医美 |
|---|---|---|---|---|---|
| 1 | 「结果」认哪个、叫什么 | 每天判健康、出成本 | 表单留资，叫「咨询」 | 私信开聊（不看留资） | 未填 |
| 2 | 漏斗长什么样 | 每月结构体检、每周受众池 | 先用视频养人，再用表单收 | 直接私信收，池子小 | 未填 |

| 5 | 素材多久老化、多久补一批 | 每周素材库存 | 一两周就老，约两周补一条 | 未填 | 未填 |

### 1b.4 三层怎么配合（用一步举例，不带客户名）

平台级的「每周查素材库存」这一步：
- **平台**规定：每周一算一次「新素材还够几周」，不够就向内容团队下单；已过审素材的更换由系统自己换、事后报（§2.2 上方更新），加预算才要 PM 本人批。
- **行业**填：这个行业素材大约多久老化（第 5 个空）。
- **客户**填：这个客户素材库里现在有几条可用（第 8 个空）。

三个都有，这一步才能自动出结果；**缺任何一层的空，这一步就该明说「判不了，缺 XX」，而不是不做。**

### 1b.5 现在卡在哪（一句话版）

- **平台级**：「每天」基本齐；「每周」只有零件；「每月」「每季」和「事件触发后的跟进」几乎是空的。
- **行业级**：七个空里只有一个有地方放。
- **客户级**：十一个空里，多数客户只填了三四个，所以很多步骤即使做出来也会回答「判不了」。

**所以开发顺序应该是：先把平台级的每周 / 每月 / 事件跟进这几条线连起来 → 同时把客户级的空做成设置页让人能填 → 最后再扩行业剧本。** 具体分期见 §11。

## 1c. 多平台与 ROI（v2：2026-10-10 经卫青 / 魏征 / 子牙 / 诸葛亮评估 + 外部调研后重写）

> **自我纠正两次**：①v1.0 初稿实际只覆盖了 Meta；②本节第一版把三样「已有」的东西写成了「没有」（Google 广告的取数代码、成交金额的存放位置、成交回填通道），四位评估各自独立查出，已全部改正。**教训：说「缺」之前先查仓库。**
> 平台层级门（Inline）：仍归位既有**广告支柱（L1）**，「跨渠道一本账」是支柱内的总账层，不是新支柱；每个投放平台的取数与执行是**连接器（L3）**。不登记候选。

### 1c.1 四层，以及和 ME 既有分层怎么对上

| 层 | 管什么 | 对应 ME 既有分层 | 现状 |
|---|---|---|---|
| **平台级**（不分渠道、不分客户） | 工作日历、授权四档、留痕、统一的一本账 | 共享能力（L1） | §1b |
| **渠道级**（每个投放平台一份） | ①怎么取数、怎么执行 → **连接器（L3）**；②这个平台自己的判据（学习期、疲劳、受众池、搜索词……）→ **挂在共享能力下、按渠道分文件，不塞进连接器** | L3 + L1 下的渠道分支 | Meta 有；Google 只有取数零件；其他无 |
| **行业级** | 7 个空（§1b.2）+ 第 8 个：各渠道在这个行业里扮演什么角色（接「已经想买的人」/ 负责「让人知道」） | 行业剧本（L2） | 候选 |
| **客户级** | 11 个空（§1b.3）+ 见 §1c.6 新增的 6 个 | 客户配置（L4） | 少数已填 |

**规矩**
- **平台级的工作流里不许出现任何一个投放平台的名字。** 只对某一个平台成立的规则一律下沉到渠道级。
- **现在不做大抽象。** 现有代码里与 Meta 绑死的程度是「中等」（判据目录约 72 个文件里 9 个直接引用 Meta 封装；逐日数据表已有「平台」一列，只是写入处写死）。等第二个平台真有逐日数据，再把共用部分抽出来——先抽会抽错。
- **授权四档的闸要装在每一个渠道上。** Google 的执行口目前**没看到**走授权内核（子牙只查了一个文件，**未完全核实**），动作名还和 Meta 的撞名。只给 Meta 装闸等于留一个后门。

### 1c.2 统一的一本账：从花钱到 ROI 的六级台阶

| 级 | 是什么 | 数从哪来 | 现状（已按评估更正） |
|---|---|---|---|
| 1 | **花了多少钱**（同一币种、同一含税口径、按当地日期） | 各投放平台 | Meta **有**（逐日）；Google **半**（取数代码在，但只存「近 30 天合计」、不存币种，线上凭证也没配齐）；TikTok **半**（有读写零件，没接进来）；其他 **无** |
| 2 | **带来多少线索 / 开聊 / 下单** | 各投放平台自报 | Meta **有**；Google **半**（每日任务已把近 30 天的转化数和单次转化成本汇总写入 `flywheel_metrics`，缺逐日数据和转化动作明细，开发时复用、不重建）；其他 **无** |
| 3 | **其中多少是合格的** | 客户的销售 / CRM | **半**：成交事实表已能存「合格咨询」，已有回填通道；多数客户没在填 |
| 4 | **成交了多少单** | CRM / 付款记录 | **半**：同一张表，已有四条回填通道（客户表格同步、付款邮件识别、私信对话、人工标记）；多数客户没在填 |
| 5 | **成交值多少钱** | 客户 | **半**：同一张表**已有金额和币种两列**（成交必填）；没人回填 |
| 6 | **ROI = 成交收入 ÷ 广告费**（PM 2026-10-10 已定，不算毛利） | 算出来的 | **无** |

**真正的缺口不是「没地方存」，是两件：①多数客户没人回填；②成交连不回是哪个渠道、哪条广告带来的**（成交表没有渠道一列，只能经联系人的来源标记绕回去；来源标记在各客户填了多少，**未核实**）。**开发时一律复用这张已有的表和已有的结果阶梯，不许另建一套。**

**九条硬规矩（ROI 最容易算出骗人的数，这九条就是防骗的）**
1. **算到哪一级就说到哪一级。** 只到第 2 级只能说「每条线索多少钱」，不许叫 ROI。
2. **跨渠道比较只许用第 3 级及以上的数，裁判是客户自己的成交记录。** 各平台都把功劳往自己头上算，自报数加起来一定比真实多；官方也只保证同一个平台内去重，跨平台没有官方去重方案。
3. **来源不明的成交占比太高，就写「判不了」。** 站内表单、私信、电话天生带不上来源标记。「太高」的门槛**待验证**。
4. **按「线索进来的那个月」归账，不按「钱到账的那个月」。** 高单价生意成交滞后几周到几个月，按到账月算会系统性看低最近的月份和新渠道。还没走完成交周期的月份标「**未成熟，不可判**」。
5. **标明是「定金口径」还是「全款口径」。** 只收到定金就除，会严重看低。
6. **退款单列；没有退款数据就不许叫 ROI。** 现有成交表（`me_sale_outcomes`）只收成交 / 尾款 / 线索、金额必须为正、明确不记退款，W1 只是只读报表、W5 也不采退款——所以**退款事实及其与原成交的关联目前没有任何工作包承接**。在补上之前，凡没有退款数据的客户，一本账只能写「成交收入 ÷ 广告费（未扣退款，会偏高）」，不许称 ROI；补退款存储与采集须作为新工作包（A 级，动数据库）另批，排在 W9 之前。
7. **成交太少不下结论；剔掉最大一单再算一遍。** 两个数一起给。「太少」是几单**待 PM 定**。
8. **负责「让人知道」的渠道不按最后一次点击判 ROI**，单独看它给下游供了多少人。**这项豁免每季复核一次**，否则会变成免死金牌。「供了多少人」怎么量：目前只有 Meta 受众池增长这一种量法，其他渠道**尚无量法**。
9. **搜索自己品牌名的那部分单列，不参加比较。** 那批人多半是别的渠道养出来的。

**没有成交数据时怎么办（降级路径）**：只报到手里有的那一级并明说「只到第 N 级」；同时把「请客户回填成交」下发成一条人工待办（what：缺哪一级、对结果的影响；how：让谁填哪张表；href：直达回填页；缺口补上后自动关闭；由 W1 承接，见 §1d）。**不许因为没数据就什么都不报，也不许用估的数顶上。**

**不同类型的客户，现实中能走到第几级（行业·候选，诸葛亮按现有客户判断，未查库）**

| 客户类型 | 成交从哪来 | 现实能到第几级 |
|---|---|---|
| 电商 | 订单自带金额，可自动 | 第 6 级，**应是第一个算出 ROI 的** |
| 高单价旅游 | 付款邮件识别（还在草稿阶段），定金邮件常不写金额 | 先到第 4 级（成交单数），金额要等读发票 |
| 物流（B2B） | 成交在聊天里，靠对话入库 + 人确认 | 短期到第 3 级（合格开聊成本） |
| 地产（只要线索的楼盘客户） | 周期长，成交不经我们 | 止于第 3 级，**不承诺 ROI** |

### 1c.3 多平台之后，工作日历要加的活（加在 §1b.1 上）

| 什么时候 | 新增的活 | 要不要人 | 现状 |
|---|---|---|---|
| 接入新投放平台 | 查授权 → 能读到逐日花费和结果 → 跟成交记录对上号 → 写这一份渠道手册 | 授权要人 | Meta 有；Google 半；其他无 |
| 每天 | 所有渠道的花费合成一个数，对客户总预算（日、月两个口径；两者关系待 PM 定，见 §10 第 2 问）。**币种闸：各渠道币种必须齐全；币种一致才直接相加；不一致时只许按「有日期的汇率」换成同一个报告币种后再加，并标出汇率日期；缺币种或缺汇率 → 不合计，只分渠道并排显示并写「币种不一致，不可合计」**（Meta 日表现在没有币种列，Google 返回的是账户币种） | 不用 | 无（前置：Google 花费先改成逐日入库、各渠道补齐币种） |
| 每天 | **转化追踪还活不活**（线索还在不在正常进来、有没有被记到广告头上）——它一断，后面所有判断都失真 | 不用 | 半 |
| 每天 | 任何一个渠道悄悄停了，当天要有人知道 | 要人处理 | Meta 半；其他无 |
| 每周 | 各渠道第 3 级成本并排比，带样本量，不够写「判不了」 | 不用 | 无 |
| 每周 | **线索多久被跟进**（隔天才回的线索会被误判成「广告差」） | 不用 | 无 |
| 每周 | 同一个客人在两个渠道都留了资料 → 去重 | 不用 | 半 |
| 每周 | **渠道专属的活**（例：搜索类要看搜索词、加否定词；社交类没有对应物） | 改 = 人批 | Meta 的在 §3–§7；搜索类无 |
| 每月 | 各渠道 ROI 一页 + 下月钱在渠道间怎么分的建议 | **挪钱 = PM 本人** | 无 |
| 每月 | **给客户的一页，固定四句**：花了多少 / 带来多少 / 算到第几级 / 下月做什么 | 人审后发 | 无 |
| 每月 | 账户结构体检（**从每周改到每月**：低量账户每周查会被诱导乱动） | 改 = 人批 | 无 |
| 每季 | 渠道组合复盘；复核「上游渠道豁免」 | PM | 无 |
| 试新渠道 | 先定好「花多少钱、跑多少天、看到什么算成」，到点就判 | **开 = PM 本人** | 无 |

### 1c.4 渠道间挪钱的规矩

| 条件 → 动作 | 谁 | 门槛 | 现状 |
|---|---|---|---|
| 两个渠道第 3 级成本持续同方向有差距，**且两边累计合格线索数都够** → 建议往便宜的那边挪一小步 | **PM 本人** | 累计合格数门槛、「一小步」是多少：**待 PM 定 / 待验证**（现在没有任何客户有两个渠道同时逐日入库的数据）。**不用「连续几周」当门槛**——每周只有几条合格线索时那是噪音 | 尚无代码 |
| 只有第 2 级数据 → 不出挪钱建议，只并排显示并标「各平台自报，不可比」 | 系统 | — | 尚无代码 |
| **便宜不等于加得进钱**：搜索类有天花板（搜的人就那么多）。挪之前看「多花一块钱」的成本，不看平均成本；数据不够判就明说 | 系统 | — | 尚无代码 |
| **四道保护**：被挪出的渠道留最低预算地板；事先写好回滚条件；旺季和试跑期不挪；一次只挪一处、挪完两边冻结观察 | PM 本人 | — | 尚无代码 |
| 上游渠道、品牌词搜索、试跑期的新渠道不参加排名 | 系统 | — | 尚无代码 |

挪钱这条链跨多步、还动钱，落地时必须走工作流编排，每一步留回执（提出 → PM 批 → 执行 → 读回 → 对照）。

### 1c.7 适用范围

本手册 v1.0 **只适用于我们代管的月付客户**。自助客户没有「我们的 PM」「我们的同事」「内容团队」这些角色；将来要适用，把「PM 本人」读成「**这个客户的出钱人**」（代管客户是 PM，自助客户是老板本人）。自助轨目前没有付费客户，**只改措辞，不开发**。

### 1c.8 外部有没有可借的（只读公开网页，没安装、没运行、没花钱）

**结论：有几条值得借，都是「规矩」不是「工具」；小预算做不了的两样明确不借。**

| 借什么 | 出处 | 局限 | 结论 |
|---|---|---|---|
| 一本账以客户自己的成交记录为准，平台自报数只作参考 | Google 官方只保证同平台内去重；跨平台无官方方案 | 每条线索落库时要带来源 | **要**（已写成硬规矩 2） |
| 把合格 / 成交回传给投放平台，让它按真成交学 | Google 官方「增强型线索转化」；Meta 官方 CRM 阶段回传 | Google：点击后 63 天内（纯点击编号 90 天），高单价生意常超期，只能回传窗口内的中间阶段；Meta：只支持站内表单线索，事件时间最多早 7 天 | **要**，但这是**往外发客户数据**，要 PM 批、A 级；Meta 侧已有回传封装，Google 侧没有 |
| 看效果至少等 2 个完整转化周期，最近几天的数因延迟偏低，改动后等 1–2 个周期 | Google 官方 | 「满 50 个转化」低量客户常达不到 | **当校准起点**，写进将来的 Google 渠道手册 |
| 质量得分只当诊断，不当考核 | Google 官方 | — | **要**（Google 渠道手册） |
| 搜索词报告 + 否定关键词例行检查 | Google 官方 | 官方没给频率 | **要**，频率自定（暂定每周，待验证） |
| 平台活动日志当「动了什么」的回执数据源 | Meta / Google 官方 | Google 官方接入目前只读；Meta 的可写但没有逐次确认，人审闸要自己做 | **要**（与 C-05、C-17 一致） |

**明确不借**：①轻量营销组合模型（官方自己举例说两年周数据都不够用，月预算几千的客户更不够）；②增量测试（要找平台代表开通，预算门槛高）；③「70 / 20 / 10 探索池」（出处是别的领域的二手转述，没有广告数据支撑；**我们自己那份「每月 20% 探索池」是 PM 批的政策，不是外部证据，两者别混**）；④按边际成本分预算的现成公式（只有代理商博客，低量下噪音太大）。
**没找到**：适用于小预算、可核实的跨渠道分钱方法——所以 §1c.4 是我们自己定的规矩，门槛全部标了「待验证」。
**未核实**：Meta 线下转化接口是否已并入转化接口；Google 学习期天数；ChatGPT 广告在澳新的可用性与接口。

## 1d. 开发工作包（把这套方案切成能交给 DeepSeek 的块；只是建议，逐包要 PM 说「开始」）

> 分工（CLAUDE.md §5）：默认 Claude Code 出每轮指令、DeepSeek 写、Claude Code 审和测；**碰授权内核 / 数据库结构 / 定时任务的包（A 级）不能自动合，要 PM 在对话里批**。
> 三维打分：频次 / IMPACT 闭环关键度 / 收入关联度；先数低、再数高。

| 包 | 一句话目标 | 打分 → 优先级 | 风险级 | 谁写 | 当场能试跑吗 | 依赖 |
|---|---|---|---|---|---|---|

## 2. 总则

### 2.1 规则格式（每条都按这个写，实现窗口不许自己加字段）

`编号` ｜ **条件 → 动作** ｜ **谁做**（档1–4）｜ **证据来源**（哪张表 / 哪个口径）｜ **样本门槛** ｜ **代码**（已有 = 文件路径；缺 = 写「尚无代码」）

- 每个数字都带来源和样本量。**没有证据的写「待验证」，不许编阈值。**
- 「代码」栏写「已有」只表示**该文件存在并实现了这条判据**，不表示**生产里有人调用**。写好了没调用的，明确写「**零调用方**」。

> **PM 2026-10-10 更新（经分叉窗口转述 PM 原话：「如果是增加预算，必须我来审。如果是换素材，就不用我审了，自己换就好了。」）**
> 1. **加预算：一律 PM 本人审。** 不设「每周最多几条」的上限，不合并排队，来一条审一条。
> 2. **换素材：系统自己换，事后报，不用 PM 审。** 从档3 移到**档1（自动执行 + 事后报告）**。机制约束一条不松（RL-03）：新建创意后指过去、改完立刻读回、不是在投状态当场改回、换完冻结 7 天、不往在投的组里加广告；视频仍只走视频工厂（RL-11）。
> 3. **「自己换」只限素材库里已经审过的素材（PM 2026-10-11 已定，经统筹窗口转述）。未过审的素材一律不得自动换，必须先审过、进了可换名单才行。**
>    - **什么叫「过审」**：该客户素材池（`ad_strategy_configs.creative_pool`）里这条素材的状态是 `approved`，并且带着**谁批的**（`approved_by`）和**什么时候批的**（`approved_at`）。这两项只能由服务端从登录身份生成，**不接受调用方自己填**；系统自己不能把一条素材标成过审。
>    - **谁审**：做素材的和审素材的不能是同一个角色（**现有批准入口还验不了这一条，见 §11 行 A1；补上之前，自动换素材不得上线**）。视频必须先走完视频工厂的审查（苏东坡 / 马良审，PM 授权发布，RL-11、C-10）才有资格进池；图片与文案同样要人审过。
>    - **记在哪**：素材池那一条记录（客户配置）；每次自动换素材的回执里必须写明用的是哪条素材、谁批的、什么时候批的。
>    - **拿不到过审素材时**：状态是 `candidate`（候选）、没有批准人或批准时间、或者读配置失败 → **不换**，明说「没有可换的已过审素材」，并向内容团队下单，不拿候选素材顶上。
> 4. 开投、改受众、关整个系列 PM 这次没提，**仍是 PM 本人**。
> 以上是转述，若与 PM 本人说的不一致，以他本人为准。

### 2.2 授权四档（对应 52 号 §3.5、卫青人设 §四、上海团计划 §8.5）

| 档 | 名字 | 意思 | 例子 |
|---|---|---|---|
| **1** | 系统自动 | 只读、只记录、只出建议、只发待办；不碰对外内容、不花钱。**例外（单列）：建 `PAUSED` 草稿**——无花费、必须读回核对，仍属档1，但**不得自动开启**（开启 = 档3）。**第二个单列例外：自动换素材**——只限素材池里已过审的素材、且带齐读回 / 失败改回 / 冻结 7 天三道机制闸（RL-03）。**这两个例外不放宽档1 的通用定义**：其余档1 动作仍然不许碰对外内容 | 日循环全部判据、周盘、体检、读回、回执 |

- 会花新钱 / 多花钱 → 档3 起。

- 只会让花费变少且可撤回 → 档2。
- 只读 → 档1。
- 任何「状态字段 = 已授权」的写法都不算授权（记忆 `feedback-status-field-as-authorization-leaks-gates`）；转述的授权对不可逆动作不算（`feedback-relayed-pm-approval-counts-by-cost-not-by-relayer`）。

### 2.2b 「PM 本人授权」怎么变成机器能验的事件（档3 的落地定义）

- 聊天里的一句话**不是**系统事件。落地形态只有两种：①已登录 PM 身份在**待办卡的授权按钮 / 审批页**上点击（`approveDraft` 那一类，先写回执、写不进去就不执行）；②PM 在对话里点名说「开 X」后，**由执行窗口把原话与时间写进回执**，且该动作的审批路径仍须由 PM 身份的审批接口放行。现有代码里「人按的」身份由调用方自报（`kernel/authorize.ts` 注释自承），**所以档3 的闸必须装在审批接口里验登录身份，不能装在调用方自称**。
- 每个档2 / 档3 动作的回执至少含：`request_id`、`client_id`、`source_record_id`（建议卡 / 广告对象 id）、`status`（proposed / authorized / applied / verified / rolled_back / failed）、`authorization`（`not_required_readonly` / `pending_pm` / `granted` / `denied`）、授权人与批的是哪个版本（**建议被改过则旧授权作废**）、`cost`（provider + 金额，没有写 0）、改前基线与改后读回、`created_at`、怎么撤回。没有授权事件 + provider 回执，不许标「完成」。事件名业务可读：`ads.change.proposed → authorized → applied → verified`（P3 实现，见 §11 A1；P1 只在回执里用这些步骤名，不真发事件）。
