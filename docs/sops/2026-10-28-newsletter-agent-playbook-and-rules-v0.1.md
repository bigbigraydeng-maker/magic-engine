## 0. 给 PM 的一页话

**为什么要有它。** 10/28 的核查翻出 9 个洞：H1 官网订阅的新人收不到欢迎信；H2 在用的欢迎信含已下架的团、过期价、过期手册；H3 表格里的定时任务天天报错、队里排着数百人；H4 每周 2 封上限没人拦；H5 13 封草稿收件人是「全员」；H6 台账与 Mailchimp 实际对不上；H7 欢迎信两条路并行、同一人收两封；H8 流程暂停 / 报错没有变更留痕、原因不明；H9 名单超档被自动加收费用。它们是同一个病：邮件这条链路没有「一个负责人 + 一本账 + 每天自动巡检」。

**它是什么。** 一个每天新西兰早上跑一次的「邮件负责人」例行，加发信前、发信后两道闸。三个互相独立的角色（做事的人不给自己验收）：① 策划（在已有的 Marketing Plan 邮件维度上补处方与 CRM 进线，§2A）② 发前闸 ③ 巡检（每日 + 发后 1 / 3 / 7 天）。按 IMPACT 走一圈：看 → 量 → 开方 → 做 → 核 → 调。

**它不是什么。** 不自己发信：排期、立即发送、开 / 重启自动流程都要你本人说话（NL-14）。不是新支柱，不碰 CRM 一对一邮件，第一期不写 Mailchimp，只读 + 出待办。网页里有人直接点「发送」它拦不住，只能当天发现并报警（NL-18）。

**它怎么定计划（PM 10-28 追加）。** 策划这一层吃两个输入：已批准的营销计划（这一期主推什么、什么时间、什么目标）+ CRM 进线（每天进多少人、从哪来、选了什么偏好、谁销售在跟、谁近 7 天已收几封）。产出一份发布日历：每封写清日期时间、发给哪个分组、主题方向、依据、要过哪几道闸。日历只是建议，发不发仍由你本人授权。详见 §2A。

**复审结论。** 子牙、魏征都给了「有条件通过」：第一期可以做，但要先改几处硬伤（发送动作平台内核第一版不放行、每人封数 ME 库里数不出来、读不到数据时巡检会假绿、没有个人信息规则等），本版已改。魏征另指出一件**不用等 agent、比手册更急**的事：表格里 E2 / E3 / E4 的队列一旦被人「修好」就会群发旧信，13 封「全员」草稿也还躺着——建议先拆这两颗雷，见 §10 第 1 问。

## 2. 分工：三层 + 三个角色

- **平台层**：跨客户的检查、证据口径、授权档、留痕。进共享代码，阈值、标签名、数字一律读客户配置（NL-16）。
- **行业层（只算候选，证据仅来自旅游一家）**：团下架 / 改价 / 售完后，在用邮件、流程、手册里的对应内容当天更新或撤下；已订客人的行前信与营销信分收件人，**额度默认仍合计**（例外要 PM 确认）。现有行业剧本只装参数与词表，装不下判断规则，所以这些先留在本手册当候选文字，不进 `playbooks/`。
- **客户层**：标签体系、每周封数、退订线、品牌口径、署名。见 §9，进客户配置（L4），**不进共享代码**。

## 2A. 策划层：从营销处方 + CRM 进线到发布日历（PM 2026-10-28 追加）

**一条线**：已批准的营销计划 → 策划结合 CRM 进线排出发布日历（建议）→ PM 授权（档 3）→ 发前闸 → 发送 → 发后对账 → 结果回写营销计划周复盘 → 必要时修正处方（沿用 `AdjustDecision`：`fix_data` / `fix_execution` / `revise_prescription` / `continue`）。这就是邮件渠道自己的 IMPACT 一圈。

**分工**：计划回答「发什么、为什么」；策划 agent 回答「现在要不要发、发给谁、哪天发、占不占额度」。

**两个输入（都只读）**

| 输入 | 内容 | 来源（读过类型 / 文件名，口径待设计稿定） |
|---|---|---|
| 营销处方 / 计划 | 只认 `approved` 的计划。**邮件有两条路**：`plan_data.email`（`EmailPlan` / `EmailTopicPlan`：标题、角度、`due_date`、`rationale`、`target_segment`、`requires_link`，派发 `kind='newsletter_email'` 任务）；推广计划 `promo` 里的 `newsletter_email` 步骤（只有 `topic` / `due_date` / `requires_link`，**没有收件分组、没有「为什么这时发」**，`promo/schedule.ts` 已把它排进推广日历）。策划两条路都读 | `src/lib/marketing-plan/`。注意 `prescription-chain/` 是广告链（终点是「开投」），**不是**邮件处方来源 |
| CRM 进线 | 近 7 / 14 / 28 天每天新进人数，按来路（表单 / 官网 / WhatsApp / 邮件 / 电话）、偏好（如 TOURPREF）、阶段与意向、销售在跟、别再联系、已订团；沉默池规模。**进线 = CRM 联系人 ∪ Mailchimp 新成员**（官网订阅的人不一定进 CRM） | `contacts`、`contact_touchpoints`、`src/lib/crm/`（`pipeline`、`qualified-buyer`、`dnc` 等）、Mailchimp 成员 |

**产出：发布日历**（未来 4 周，每封邮件一行）：日期时间（NZ）、类型（newsletter / 欢迎 / 行前 / 召回）、收件分组定义（包含与排除条件）、主题方向与要放的官网团页、依据（计划目标 + CRM 快照与取数时间）、预计收件人数、要过的闸、状态。

**落点**：第一版是**现算的只读视图，不存库、不新建计划表、不进执行看板**。执行看板（`execution_items`）上的任务默认含义是「已批准、去发」，且它只有 pending / in_progress / completed / skipped / superseded 五种状态，装不下日历状态；放进去会被当成授权。模型对齐社媒的「候选 → 日历 → 发布器」（`docs/specs/2026-10-14-publishing-calendar-design.md`：日历是平台通用机制）。缺的字段（机器可读的收件分组、CRM 快照）要不要加、要不要迁移，由 WP2 设计稿定；真要加则 WP2 升 A 级。

**策划规则**

| 规则 | 条件 → 动作 | 证据 / 说明 |
|---|---|---|
| **PL-01 计划挂在已批准的计划上** | 日历项必须能追溯到一条 `approved` 计划里的邮件任务或推广步骤（plan id、`source_email_topic_index` 或 `promo_ref`）；没有已批准计划只出「建议」；处方被修正（`revise_prescription`）→ 受影响日历项标「待重排」，不自动沿用 | 防止 agent 自己编主题 |
| **PL-02 进线只调欢迎优先级与分群配比，不压掉计划** | 进线骤增（如广告恢复）→ 欢迎路径优先、新人第一周额度优先；进线为 0 的时期，老名单仍按**已批准计划的发送间隔**走，同样受每周 2 封上限。任何「建议压掉 / 推迟某封」只产出调整建议，等人确认（沿用调整记录），不得自动生效 | 10/11–10/26 Facebook 表单新留资 0 条，但同期官网订阅仍进 4 人，10/16 那封 694 人的 newsletter 有 33 人点击——按「进线 0 就不发」会错压这一类邮件 |
| **PL-03 分群来自 CRM 实际状态；排除集 = 客户默认值 + 每封信 PM 可改** | 已订团 → 只收行前信；销售在跟 / 别再联系 / 已付款 / 明年再说 → 默认不收营销信，但 PM 对某一封可以改（改动记进授权回执）；偏好指向某团 → 内容倾向该团；沉默超 N 天 → 「召回」类（额度仍合计）。排除按 CRM 事实（`dnc`、预订、销售阶段）现算，再与标签对账 | `target_segment` 现在是自由文本，由客户配置映射成机器可读分组。10/7 台账记 SP1 的「销售跟进中 / 明年再说」是按 PM 10/8 要求纳入的，10/14 盘点又把它列为问题——口径不一致，默认排除集交 PM 定（§10） |
| **PL-04 日历占用封数额度（预估）** | 排期时按 7 天（168 小时）滚动窗口预占每人额度，口径与 NL-04 完全一致、只用同一个计数函数；排不下的顺延或合并；日历项取消即退回预占，信发出后预占转成「已收」，不双算 | 计划与闸同一口径，避免两套数数 |
| **PL-05 每个日历项写明依据** | 为什么发这封、发给谁、为什么是这天：引用计划目标 + CRM 进线快照（取数时间、样本量）；缺数写「没读到」，不写 0（NL-09） | `EmailTopicPlan.rationale` 已要求写「为什么这个时间点」 |
| **PL-06 日历只出建议，授权是另一件事** | 状态只到 `proposed`；排期、发送 = 档 3（NL-14）。`pm_authorized` **不是可改字段**，只能由真实授权事件生成，并绑定（内容指纹 + 收件分组 + 人数 + 发送时间），任一项改动即作废 | 「状态字段 = 已授权」是已知的老毛病 |

**边界**：不替代 CRM 一对一外发（76 号「给客人发第一封邮件」设计稿 v0.2，Outlook）。**每周 2 封上限默认对一切群发合计**：Mailchimp 群发、CRM 批量邮件（员工邮箱密送）都算；一对一人工邮件是否计入，PM 原话只说「群发」，这是假设，列入 §10 待确认。

## 6. 数据源、读写边界与复用

- **Mailchimp**：已有 `src/lib/mailchimp/`（`listSentCampaigns`、`getCampaignActivity`、`ping`、`subscribeMember`、标签与抑制同步等）。**现状是单客户**：全局一把 `MAILCHIMP_API_KEY`，`listSentCampaigns` 不按名单过滤；所以每次读取必须带客户自己的凭据引用与名单 id（WP1 起），同账号多名单时按名单过滤。第一期要新增的**只读**调用待探针验证（NL-21）：每位成员的活动记录（含流程信）、草稿 / 排期活动的收件人设置、自动流程状态。
- **官网**：站点地图 + 团页 title / h1 / 价格 / Next confirmed departure（只读抓取）。复用清单见 NL-02。
- **ME 库**：联系人与触点、客户配置；营销计划、CRM 进线与阶段（只核对了文件 / 类型名，口径待设计稿定）。触点**记不到**「收到但没打开」的人，所以封数计数不能只用它（NL-04）。
- **外部脚本**：PM Google 账号里的表格脚本 ME 读不到、改不了。它不只发信：还每小时同步新线索，并写「销售在跟」之类的标签。**WP0a / WP0b 只停发信类任务（E1 批次、E2 / E3 / E4）；同步类任务不动**，否则标签会悄悄停止更新。欢迎信改用 Mailchimp 自带流程后，邮件链路上仍有 ME 看不见的发信 / 加人方（休眠的 Zapier / Make / 原生集成、有人直接在网页里发送），由 NL-18 当天发现。
- **WP0b 的两处上游联动**：营销计划生成器按活动标题以 `auto_` 开头统计「近 7 天欢迎序列触达」（`generate/route.ts`，写死了 CTS 脚本的命名）——停了批次后它恒为 0，会告诉 AI「没有欢迎信」；另据子牙：`sync.ts` 只读普通活动，改成自动流程后新客人对欢迎信的点击可能不再进 CRM 的「点了链接」一组（Mailchimp 接口是否列出流程邮件没验证）。这两处要改或标「判不了」，之前不得激活新流程。
- **写入**：第一期只写 ME 自己的东西。待办：新增待办种类必须在 `pm-todo/five-kinds.ts` 的车道表里归类（决定 / 一键 / 客户侧 / 复核 / 判真假，或开发欠账 / 周报），NL-12、NL-06 之类走周报或拍板卡，避免重演 9-25 那封 166 件的待办邮件。运行记录：照抄 `inngest/functions/promo-plan-daily-watch`（只读，回执进 `cron_run_logs`，待办读回执，不自己现算；新增函数要在 Inngest 后台重新 Sync，机器判 A 级）。**台账卡不由线上写**（NL-08）。
- **工作流层**：每日巡检 = Inngest 定时函数（带时区）；发送审批（WP5）= Inngest 事件接力，事件名业务可读：`newsletter.campaign.proposed` → `newsletter.campaign.pm_authorized` → `newsletter.campaign.sent` → `newsletter.campaign.verified_t1`；每步机器可读回执（request id、client id、活动 id、status、authorization、provider 回执、created_at），没有授权事件与回执不得发送。
- **不另建**：第二套邮件系统、学习库、dashboard、计划表。NL-06 / NL-13 要判断「有没有变化」就得存历史，复用 `cron_run_logs`，不新建表。

## 7. 层级判断（Tier Gate · Full，给复审人看）

- **被判定对象**：邮件渠道的「执行 + 核验 agent」。
- **建议层级**：既有邮件渠道（ROADMAP 2026-09-08 判定「不是新 L1，补齐已有策略层缺的邮件渠道」）的执行与核验扩展 + L3 Mailchimp Connector（只读起步，受治理写后置）+ L2 旅游行业规则（候选）+ L4 CTS 配置。策划层复用 Marketing Plan 邮件维度与现有 CRM 数据，不新建计划表、不新建第二套客户库。
- **归属**：不新增支柱。代码里 newsletter 任务归在社媒 dimension 下（`task-dispatcher.ts`：「邮件本质是自有渠道内容，不新增 dimension 枚举值」）。
- **换客户测试**：⚠ **部分成立**。无邮件渠道的客户（Roman、Oztop）agent 天然空壳；但现状整个系统只有一把全局 Mailchimp 密钥，连接器**目前只支持 CTS 一个客户**，要换成有 Mailchimp 的悉尼地产客户，必须先补「每客户凭据引用 + 名单 id」（WP1 起）。标签、封数、退订线、禁用词都读客户配置，共享代码不用改。
- **换行业测试**：旅游 → 地产：「团下架」换成「房源已售 / 已租」；旅游 → 物流：对账对象换成「服务线 / 报价」。NL-02 要先定义一个「在售商品来源」接口（官网页面 + 目录），否则共享代码会带上「团」的形状。差异进行业层。
- **智能层 or 执行手**：核验与闸是智能层输出；发送是执行手，走 Connector 且档 3。
- **红线**：1 ✓ 不以「智能层」包装新能力线；2 ✓ 客户名 / 数字只在客户层；3 ✓ 不直建 L1，单客户证据默认落客户层 / 行业候选；4–5 见上两条；6 落共享代码时走五道 Build Gate；7 ✓ 行业层只装行业级判断。
- **PM 待拍板项**：无新支柱 / 新版本；商业口径是发送授权（NL-14 默认最严，放宽等 PM 另说）与默认排除集（§10）。
- **结论**：原本想法「专门的 newsletter agent」→ 判定「既有邮件渠道的执行核验扩展」，不新增能力线；无新 L1 候选，不登记。第一期动共享代码前再出一次完整报告。
- **Reuse Statement**：复用 Marketing Plan 邮件维度与批准流、推广计划日检的只读模式、`site-diff` 等官网对账件、`net/safe-fetch`、今日待办五类车道、`cron_run_logs`、Mailchimp 只读封装；平台共享新增 0（本稿无代码）；行业级 = 旅游候选规则；客户级 = CTS 配置（§9）；没有把客户名 / ID 写进共享代码。
