## 0. 给 PM 的一页话

**为什么要有它。** 10/28 的核查一口气翻出 9 个洞（见 §3「证据」列）。它们是同一个病：邮件这条链路没有「一个负责人 + 一本账 + 每天自动巡检」。发信的有你 Google 表格里的脚本、Mailchimp 自带流程、几个窗口、客户账号里的 Zapier / Make，各管一段，没人对「每个新客人收到了什么、对不对」负责。

**它是什么。** 一个每天新西兰上午跑一次的「邮件负责人」例行，加发信前、发信后两道闸。三个互相独立的角色（做事的人不给自己验收）：① 策划（沿用 Marketing Plan 已有的邮件维度，不重做）② 发前闸 ③ 巡检（每日 + 发后 1 / 3 / 7 天）。按 IMPACT 走一圈：看 → 量 → 开方 → 做 → 核 → 调。

**它不是什么。** 不自己发信：排期、立即发送、开 / 重启自动流程都要你本人说话（NL-14）。不是新支柱，不碰 CRM 一对一邮件，第一期不写 Mailchimp，只读 + 出待办。

**它怎么定计划（PM 10-28 追加）。** 策划这一层吃两个输入：营销处方（这一期主推什么、什么时间、什么目标——已有的 Marketing Plan 邮件维度）+ CRM 进线（每天进多少人、从哪来、选了什么偏好、谁销售在跟、谁近 7 天已收几封）。产出一份发布日历：每封写清日期时间、发给哪个分组、主题方向、依据、要过哪几道闸；日历只是建议，发不发仍由你本人授权。详见 §2A。

**第一期交付。** 把这 9 个洞变成每天自动跑的检查；发现问题进你的今日待办，说清 what / how / 直达链接，不再靠人记。

## 2. 分工：三层 + 三个角色

- **平台层**：跨客户的检查、证据口径、授权档、留痕。进共享代码，但阈值、标签名、数字一律读客户配置（NL-16）。
- **行业层（只算候选，证据仅来自旅游一家）**：团下架 / 改价 / 售完后，在用邮件和流程里的对应内容要在当天更新或撤下；「已订客人的行前信」与「营销信」分收件人、分额度。进 `playbooks/`（L2）。
- **客户层**：标签体系、每周封数、退订线、品牌口径、署名。见 §9，进客户配置（L4），**不进共享代码**。

| 角色 | 干什么 | 独立性 | 现状 |
|---|---|---|---|
| ① 策划 | 下一封发什么、何时发、发给谁 | 在 Marketing Plan 邮件维度之上补两个输入（处方 / CRM 进线），产出发布日历，见 §2A；不新建计划表 | 邮件维度已有（是否已合并本手册未核）；两个输入与日历为新 |

## 2A. 策划层：从营销处方 + CRM 进线到发布日历（PM 2026-10-28 追加）

**一条线**：处方 → 营销计划的邮件维度（主题、节奏）→ **策划**结合 CRM 进线排出发布日历（建议）→ PM 授权（档 3）→ 发前闸 → 发送 → 发后对账 → 结果回写营销计划周复盘 → 必要时修正处方（沿用既有的 `AdjustDecision`：`fix_data` / `fix_execution` / `revise_prescription` / `continue`）。这就是邮件渠道自己的 IMPACT 一圈。

**分工**：营销计划的邮件维度回答「发什么、为什么」（已有 `EmailPlan` / `EmailTopicPlan`：标题、角度、`due_date`、`rationale`、`target_segment`、`requires_link`，以及 `kind='newsletter_email'` 的任务）；策划 agent 回答「现在要不要发、发给谁、哪天发、占不占额度」。**不新建第二张计划表**：日历项落在现有邮件任务与 `execution_items` 上；缺的字段（机器可读的收件分组、额度预占、CRM 快照、与处方 `promo_ref` 的绑定）要不要加，由 WP2 设计稿定。

**两个输入（都只读）**：

| 输入 | 内容 | 来源（只核对了文件 / 类型名，口径待设计稿定） |
|---|---|---|
| 营销处方 / 计划 | 目标与 KPI、推广阶段与步骤（`promo_ref`）、邮件主题与节奏、计划状态（只认 `approved`） | `src/lib/marketing-plan/`、`src/lib/prescription-chain/` |
| CRM 进线 | 近 7 / 14 / 28 天每天新进人数，按来路（表单 / 官网 / WhatsApp / 邮件 / 电话）、偏好（如 TOURPREF）、阶段与意向、销售在跟、别再联系、已订团、近 7 天已收封数；沉默池规模 | `contacts`、`contact_touchpoints`、`src/lib/crm/`（`pipeline`、`qualified-buyer`、`dnc` 等） |

**产出：发布日历**（未来 4 周，每封邮件一行）：日期时间（NZ）、类型（newsletter / 欢迎 / 行前 / 召回）、收件分组定义（包含与排除条件）、主题方向与要放的官网团页、依据（处方目标 + CRM 快照与取数时间）、预计收件人数（扣掉封数闸之后）、要过的闸、状态（`proposed` → `pm_authorized` → `sent` → `verified`）。

**策划规则**

| 规则 | 条件 → 动作 | 证据 / 说明 |
|---|---|---|
| **PL-01 计划挂在已批准的处方 / 计划上** | 日历项必须能追溯到一条 `approved` 的邮件维度任务（plan id、`source_email_topic_index`、处方目标）；没有已批准计划只出「建议」、不进日历；处方被修正（`revise_prescription`）→ 受影响日历项标「待重排」，不自动沿用 | 防止 agent 自己编主题；沿用 Marketing Plan 的批准流 |
| **PL-02 进线驱动，不为凑节奏而发** | 取近 7 / 14 / 28 天 CRM 进线；进线为 0 的时期不对全名单「例行群发」；进线骤增（如广告恢复）→ 欢迎路径优先，newsletter 为新人让路 | CTS 10/11–10/26 Facebook 表单新留资 0 条，10/27 起 2 条 |
| **PL-03 分群来自 CRM 实际状态** | 已订团 → 只收行前信；销售在跟 / 别再联系 / 已付款 / 明年再说 → 不收营销信；偏好指向某团 → 内容倾向该团；沉默超 N 天 → 单独「召回」额度；分群定义放客户配置，agent 只引用 | `target_segment` 现在是自由文本，由客户配置映射成机器可读分组 |
| **PL-04 日历占用封数额度** | 排期时就按 7 天滚动窗口预占每人额度（与 NL-04 同口径）；排不下的项顺延或合并，不等发前才发现超限 | 计划与闸同一口径，避免两套数数 |
| **PL-05 每个日历项写明依据** | 为什么发这封、发给谁、为什么是这天：引用处方目标 + CRM 进线快照（取数时间、样本量）；缺数写「没读到」，不写 0（NL-09） | `EmailTopicPlan.rationale` 已要求写「为什么这个时间点」 |
| **PL-06 日历只出建议，不自动排期** | 状态只走到 `proposed`；排期、发送 = 档 3（NL-14） | — |

**边界**：不替代 CRM 一对一外发（76 号「给客人发第一封邮件」设计稿 v0.2，Outlook）。一对一人工邮件是否计入每周封数上限——按 PM 原话上限只管群发，这是假设，未与 PM 确认。

## 6. 数据源、读写边界与复用

- **Mailchimp**：已有 `src/lib/mailchimp/`（`listSentCampaigns`、`getCampaignActivity`、`ping`、`subscribeMember`、标签与抑制同步等）。第一期需新增的**只读**调用待设计稿验证：每位成员的活动记录、草稿 / 排期活动的收件人设置、自动流程状态。新版自动流程（Customer Journey）有没有只读接口**没验证**，所以 NL-01 看结果、不依赖它。
- **官网**：站点地图 + 团页 title / h1 / 价格 / Next confirmed departure（只读抓取），对照团目录。
- **ME 库**：联系人与触点、客户配置；营销计划（`src/lib/marketing-plan/`，邮件维度与 `newsletter_email` 任务）、处方链（`src/lib/prescription-chain/`）、CRM 进线与阶段（`src/lib/crm/`）——只核对了文件 / 类型名，口径待设计稿定。
- **外部脚本**：PM Google 账号里的表格脚本（每天 8:01 欢迎批次 + E2–E4）ME 读不到、改不了，不纳入 agent。欢迎信改用 Mailchimp 自带流程后停用（WP0），此后邮件链路上没有 ME 看不见的发信方。
- **写入**：第一期只写 ME 自己的东西：待办（复用现有人工任务入口，三件套 what / how / href）、运行记录、台账更正卡。
- **工作流层**：每日巡检 = Inngest 定时函数；发送审批（WP5）= Inngest 事件接力，事件名业务可读：`newsletter.campaign.proposed` → `newsletter.campaign.pm_authorized` → `newsletter.campaign.sent` → `newsletter.campaign.verified_t1`；每步机器可读回执（request id、client id、活动 id、status、authorization、provider 回执、created_at），没有授权事件与回执不得发送。
- **不另建**：第二套邮件系统、学习库、dashboard。

## 7. 层级判断（Tier Gate · Full，给复审人看）

- **被判定对象**：邮件渠道的「执行 + 核验 agent」。
