# 合并「栈式 PR」流程（一个方案 PR 上叠着好几个补丁 PR）

2026-10-07 PM 要求这套流程日后复用，来源：上海周边团广告方案栈（方案主 PR 加若干补丁 PR）。

## 先弄清什么叫栈
补丁 PR 的合并目标（base）不是主干，而是方案主 PR 的分支。补丁合并后只进了那条分支，**不等于进了主干**。
说「已合进主干」之前必须读回：`git cat-file -e origin/main:<文件路径>`。2026-10-06 统筹窗口曾把「合进方案分支」说成「合进主干」，教训见台账卡 2026-10-06-pr2299-merged-by-pm-before-weiqing-review。

## 步骤
1. 找栈：`gh pr list --state open --base <主 PR 的分支名>` 列出所有叠在上面的 PR；已合并的补丁用 `--state merged` 核对数量。
2. 逐个体检：头提交、是否草稿、红灯、未解决审查意见（GraphQL 查 reviewThreads）。红灯逐个判原因，常见的是台账卡 front matter 里有「空格+#」、卡里有 10 位以上连续数字、正文超 5 行；刷新分支不是万能药。
3. 顺序：从上到下。先合叠在最上面的补丁（合进它的 base 分支），最后合最底下的主 PR 进主干。
4. 每一个都钉头提交：`gh pr merge <号> --merge --match-head-commit <体检时的头提交>`，体检后头提交变了就重新体检。
5. 合进非主干分支的：普通合并，不需要 `--admin`。合进主干的 A 级：必须 PM 本人在对话里说「合」，再用 `--admin` 钉头提交；B/C 级交给机器自动合，不要手动合。
6. 合进主干后读回：关键文件在主干上存在；主干最新提交已触发部署。
7. 报给 PM 时，用「合进主干会带来什么、不会带来什么」两句话说清，别写栈内部编号。

## 不要做
不要用 `--admin` 绕过 Risk gate 合 B/C 级；不要为放行批量标审查意见已解决；不要刷新分支当万能药（刷新会重新判级，可能把绿刷成红）。
