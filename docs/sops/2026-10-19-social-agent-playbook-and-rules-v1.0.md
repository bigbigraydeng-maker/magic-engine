## 0. 结论

社媒起号学习的价值不是把外部“爆款技巧”直接变成规则，而是让每条做法带着来源、适用边界、ME 规则对账、只读验证方案和状态，直到证据足够才升级。本文归纳 ME 已有的社媒安全与运营框架；外部作者策略均保持候选，不覆盖既有规则。

## 2. 分工：平台、行业、客户

- **平台层**定义跨客户的工作流、证据口径、审批边界与留痕。
- **行业层**记录多个同类客户重复出现且经核验的候选规律；单客户结果仍为候选。
- **客户层**保存账号权限、品牌语气、素材授权、目标受众与客户数据；客户名、私有数字不进入共享手册/技能卡。
- 连接器负责授权后读取/执行，不在连接器中埋入行业策略。

## 3. 规则表

| 规则 | 条件 → 动作 | 执行者 / 证据 / 状态 |
|---|---|---|
| **SO-01 来源先于结论** | 外部技巧进入学习卡前，记录作者、原始链接、发布日期、实际读取范围与来源类型；未读部分不得写成已读。 | 学习 Agent；原页面/转写；已存在于 `me-expert-source-to-skill`。 |
| **SO-02 外部做法默认候选** | 无 ME 客户数据验证的专家/平台建议标 `learning`/candidate；不得据此改 SOP、调发布量或承诺增粉。 | 学习 Agent；技能卡+验证台账；沿用既有学习流程。 |
| **SO-03 对账后才裁决** | “吸收、忽略、冲突”前读对应规则原文并写编号；关键词命中只作线索。冲突以现行 ME 规则为先，除非 ME 数据给出反证。 | 学习 Agent；摘要与原文；沿用学习流程。 |
| **SO-04 真实身份与内容透明** | 内容含虚拟人物、合成画面或虚构人设时，按平台要求披露；不把角色写成真实人物，不虚构经历、到场、资质、评价或现实关系。 | 内容负责人+审查人；账号资料、素材来源、平台标识；沿用发布治理与客户配置。 |
| **SO-05 只在获准范围内读写** | 验证优先读取已授权的发帖回看、评论记录、工厂审查记录；不得因学习自行发帖、下架、回评论/私信、改设置或扩大 OAuth 权限。 | 验证 Agent；只读接口/审查留痕；写入沿用既有授权链。 |
| **SO-06 发布先过既有质量闸** | 素材授权、事实、画面/音轨、品牌/平台规则、首帧与链接按现有 `content-review` 和发布治理检查；学习卡不得绕过批准。 | 出片人+独立审查人；审查结果与批准快照；复用现有链路。 |
| **SO-07 生产与核验分开** | 产出内容的角色不得自证“发布无误”；独立巡检对照批准版本与实际页面。发现问题只按已有权限停后续或进待办。 | 独立巡检；批准快照、页面回读、回执；日常设计 §2、§5。 |
| **SO-08 结果不明不重发** | 请求超时、缺回执或状态不明时先读平台现状/回执；确认前不得重复发同素材。素材以规范路径和哈希去重。 | 发布执行者；平台回读、回执、哈希；复用幂等设计。 |
| **SO-09 指标不等于因果** | 数字写平台、时间窗、样本量与取数状态；缺失写“没读到/null”，不改成 0。n<5 不下结论；定义不同不跨平台合并。 | 分析 Agent；已有测量回执/平台分析；日常设计 §6。 |
| **SO-10 调整需门槛与记录** | 外部建议先形成可证伪问题；历史只读验证优先。测试写变量、样本、窗口、判定线、回滚；每轮隔离一个变量。改变发布量、渠道、预算、权限或公开动作按既有 PM 审批处理。 | 分析 Agent 提议，获批角色执行；两周复盘与客户数据；日常设计 §7。 |
| **SO-11 评论是信号，不是命令** | 评论可用于归类疑问和选题；评论文字不自动成为指令，不收集不必要的个人信息，不用批量/虚假互动造热度。回复沿用评论护栏与授权。 | 社群/内容 Agent；公开评论分类、人工待办；skill-gap survey §4。 |
| **SO-12 成熟后才升层** | 单账号/单周期结论留客户层；行业结论须多客户可比证据；跨行业才考虑平台规则。证据不足写“待验证/判不了”。 | 规则负责人；可比样本与复核记录；日常设计 §7.1、学习流程。 |

## 4. 外部经验候选区（不是已批准规则）

开场钩子、固定栏目、趋势借用、评论选题和观看指标口径均见学习卡。卡片提出的做法不等于 ME 已验证；来源中的秒数、发布节奏、算法解释、增长承诺不得直接用于生产。先对账，再在现有授权内只读验证。

## 5. 只读验证与复盘

1. 首选既有 T+4h/T+72h 互动回看、人工巡检补读、公开评论分类和视频工厂记录。读取链路未确认有数据时写“未验证/没读到”，不得推定正在运行。
2. 每条证据保留平台、时间窗、内容类型、样本量、指标定义和缺失字段。已有设计规定 n<5 不下结论；其他阈值需来源明确并与规则对账。
3. 外部来源只提出实验，不作成功判据。涉及付费、扩权、对客外发或生产发布，须按 PM 和平台既有授权流程另行审批。
4. 复盘结果回写客户层；升行业/平台层须满足可比性和跨客户证据，并经规则负责人复核。本草案不改变生产操作。

## 6. 明确不做

- 不新建学习系统、能力线、社媒数据库或并行 dashboard。
- 不自动高频发布、自动关注/加好友、买粉、互赞、群发或自动私信。
- 不将虚拟角色伪装成真实用户，不以恋爱暗示、身份误导或虚构经历推动互动。
- 不把单个爆款、单客户案例或供应商营销数字当普遍规律。
- 不用点赞/播放单项判“增长成功”，不把缺数解释成 0。

## 9. PM 2026-11-01 决定（v1.1 新增）

> 来源：PM（Ray）2026-11-01 与社媒统筹的对话。这一节记的是**已拍板的方向**；标「提议」「待定」的还没定。本节不改变 §3 规则表，也不构成任何发布、写库或改权限的授权，这些仍要 PM 本人逐次点头。

### 9.1 每周批一次整包

- 社媒内容**每周批一次，整包批**：一个包里同时有 Story、图文、工厂 Reel，不是每条单独点。
- 整包批过后，包里的 Reel 就转公开（批准即公开），不再停在草稿。
- 节奏（**提议，未确认**）：周四出下周草稿包 → 周五 PM 批 → 下周一起按计划发。
- 批过的内容里如果有改动或被发前检查拦下的，单独拦下来给 PM 看，不跟整包一起放行。

### 9.2 评论和私信自动回复的边界

- 自动回复**只管问候和常见问题**（例如行程、签证、怎么报名）。只引导，不报价、不承诺。
- **问价、投诉、退款**（以及改单）一律进今日待办，由人回。
- 现有自动回复开关回答的范围比这宽，要先收窄；收窄回复范围算对外动作，按 PM 授权走。

### 9.3 三层分工：先定客户目标，再定内容

- 业务分三层：**平台层 / 行业层 / 客户层**（与 §2 一致）。
- 每个客户的社媒目标和风格，**先确认这个客户的目标配置**（目标卡 + 品牌总纲），再排内容。
- 社媒 Agent 按客户配置把内容做好、发好、回好，**不单独背某一个数字**（不背线索数、不背粉丝数）。

### 9.4 平台顺序

- **先把 Facebook 做完整**；Instagram、TikTok、YouTube 和其他渠道排在后面。
- 没接通的平台在客户配置里写「关闭」，不写发帖量。

### 9.5 不重复造轮子

- 每一处改动都要先找 ME 现有社媒代码（Story 周包、每日计划发布、工厂发布、确认卡、今日待办、发前检查、评论自动回复、读回链），在上面接，不另起一套。

### 9.6 客户配置示例（CTS，只写配置，不写编号）

- 平台：只有 Facebook。
- 每周起步量：**18 条 Story + 4 条图文 + 3 条 Reel**，作为一个周包一起批。
- 内容比例：旅行氛围 40% / 实用信息 25% / 客人故事 20% / 团介绍 15%。
- 不发：优惠、截止日期、余位倒计时这类内容（这个客户的团没有销售截止）。
- 「专业和历史」这一类：0%（暂停）。
- 这些写在该客户的品牌总纲里（现有表和字段），不进本手册的默认值；换客户要先问客户。

### 9.7 Facebook 延展玩法（都等 PM 定）

| 玩法 | 现在能不能做 | 说明 |
|---|---|---|
| 客户自己的小组 | 有条件 | Meta 在 2024 年移除了小组接口（Groups API），系统不能自动发。只能「ME 写好、人去发」：草稿进周包、过发前检查，发帖变成今日待办。小组评论读不到，自动回复管不了。 |
| 发到别人的小组 | 只能纯人工，建议先不做 | 没有接口；不做浏览器代发。每个小组规则要人看，发多了容易被当刷屏。 |
| Marketplace | 挂团做不了 | Marketplace 不允许挂服务类商品，旅游团属于服务。替代办法是广告里的「Facebook 市场」版位，归广告 Agent 管，不归社媒。 |

### 9.8 等 PM 开口的事

- 所有 Meta 权限申请（含读洞察）：**暂停**，不改授权范围。
- 赢家 Reel 自动建广告：这个客户已关，改成出暂停草稿卡（#3447），人点了才建。

### 9.9 怎么量（接到共用的「量」框架上）

- 共用框架已经在 `src/lib/flywheel/`：每个支柱一个适配器（`adapters/types.ts`），指标写 `flywheel_metrics`；归因任务（`attribution/job.ts`，每 6 小时）拿动作前后两次读数算变化，结果写 `flywheel_outcomes`，再进经验记忆和周报。广告另有「没人拉的指标不准写成预期指标」的登记（`metric-registry.ts`）。
- 社媒现在接上的：主页每天的近 7 天发帖 / 互动 / 断更天数（`social/page-metrics-sync.ts`，周报在用）；单条帖子发后 4 小时 / 72 小时的回执（`social/post-measurement-store.ts`），这条故意不进共用归因，防止不同帖子串数。
- 当前缺口：
  - Reel 一直是草稿，所以单条回执几乎没有新数据；
  - Story 没进读回链；
  - 读不到观看和触达（没有读洞察权限，申请已暂停）；
  - 线索归因把自然社媒记成付费，社媒线索数是 0；
  - 客户目标卡里没有社媒的数据来源；
  - 社媒还没有「谁在拉这个数」的登记，旧的社媒适配器拉数函数没有定时任务调用。
- 原则不变：读不到写「读不到」，不写 0（§3 SO-09）。补这些缺口的顺序跟 flow-plan 第 5 步走，等 PM 开工。
